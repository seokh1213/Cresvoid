# Kotlin 버전별 기능 문제 트랙 계획

## 목표와 범위

Kotlin 릴리스마다 새로 쓰거나 안정화된 언어 문법, 표준 라이브러리 API, 컴파일러 동작을 작은 문제에서 직접 사용한다. 코루틴은 별도 라이브러리인 `kotlinx.coroutines`의 버전 축도 있으므로 Kotlin 릴리스의 기능으로 섞어 적지 않는다. 첫 제작 범위는 JVM에서 재현할 수 있는 Kotlin 1.9~2.4다. 그 뒤 1.0~1.8의 주요 릴리스로 거슬러 확장하고, 새 릴리스가 나오면 후보를 보탠다. Native·JS·Wasm·Android·Compose의 변화는 같은 문제로 JVM에서 검증할 수 없으면 별도 후보로 둔다.

## 단계 후보

| 기준 릴리스 | 문제로 만들 기능 후보 | 풀이에서 확인할 행동 |
|---|---|---|
| 1.9 | `data object`, 안정화된 `Enum.entries`, 안정화된 열린 범위 표준 라이브러리 API | 상태 모델과 범위 경계를 구현하고 기존 표현과 결과를 비교한다 |
| 2.0 | K2의 스마트 캐스트·진단 차이, 안정화된 `AutoCloseable` | 같은 소스의 컴파일 결과를 비교하고 자원 종료를 구현한다 |
| 2.1 | `when` 가드, 비지역 `break`·`continue`, 다중 달러 문자열의 프리뷰 | 문제를 풀되 프리뷰 플래그와 안정화 시점을 분리해 기록한다 |
| 2.2 | 안정화된 가드·비지역 반복 탈출·다중 달러 문자열, `Base64` | 입력 분기와 문자열 템플릿을 구현하고 프리뷰 해제 후 결과를 검증한다 |
| 2.3 | 중첩 타입 별칭, `when` 완전성 검사, 안정화된 시간 API | 모델의 분기 누락과 시간 계산을 컴파일·실행으로 확인한다 |
| 2.4 | 안정화된 컨텍스트 매개변수·명시적 backing field·UUID API | 암묵적 의존성 전달, 읽기 전용 외부 속성, 식별자 처리를 구현한다 |

위 표는 출제 후보이지 단계 확정 목록이 아니다. 특히 2.1의 세 언어 기능은 당시 프리뷰였고 2.2에서 안정화됐다. 같은 기능을 두 번 낼 때는 2.1에서 플래그·제약을 다루고 2.2에서 안정 API로 옮기는 차이를 문제로 만들어야 한다.

## 제작 전 계약

1. 릴리스별 공식 변경 문서에서 도입 버전과 안정화 버전을 따로 확인한다. 문법, 표준 라이브러리, 컴파일러 진단을 구분하고 `kotlinx.coroutines` 같은 라이브러리 릴리스는 자체 버전으로 기록한다.
2. 각 문제는 기능을 써야만 의미가 있는 입력·출력과 실패 조건을 정한다. 결과만 같으면 옛 문법으로 우회할 수 있는 과제에는 소스 검사 또는 두 버전 컴파일 비교가 필요하다. 현재 build 엔진은 출력만 검사하므로 이 검증 계약을 먼저 설계한다.
3. 릴리스별 실제 컴파일러와 표준 라이브러리를 고정해 같은 풀이를 이전 버전과 해당 버전에서 확인한다. 최신 컴파일러의 `languageVersion`만 낮추는 방법은 옛 컴파일러 전체를 재현하지 못한다. 여러 컴파일러 설치·배포 방식은 제작할 때 결정한다.
4. 각 단계의 문서에는 버전, 안정성 상태, 필요한 플래그, JVM·JDK 조건, 이전 버전에서의 실패 형태를 적는다. 참조 풀이·독립 테스트·블라인드 풀이를 분리한다.
5. 카드와 트랙 단계 번호는 검증 방식과 첫 범위를 확정한 뒤 만든다. 패치 릴리스마다 문제를 강제로 하나씩 만들지 않고 학습할 만한 동작 변화가 있는 릴리스만 채택한다.

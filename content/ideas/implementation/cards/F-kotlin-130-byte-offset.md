# F-kotlin-130 한글에서 어긋나는 파일 구간 위치

- 맥락: 파일을 줄 레코드 단위로 나눠 다른 작업자에게 보내는 처리기다. UTF-8 파일의 구간은 시작 포함·끝 제외 바이트 위치이며 LF와 CRLF를 모두 받는다. 구간을 다시 읽으면 각 레코드가 한 번씩 나와야 한다.
- 버그 후보: 디코딩한 문자열의 길이를 누적해 바이트 위치로 사용하는 원인 하나를 심는다. 줄 끝과 부분 읽기 처리는 올바르게 둔다.
- 버그 신고: 영문 레코드만 있을 때는 정상이지만 한글이나 보조 평면 문자가 있는 파일을 둘로 나누면 뒤 구간의 첫 레코드가 잘리거나 앞 레코드가 섞인다. 공개 신고에는 작은 UTF-8 파일과 잘못 읽힌 결과를 함께 준다.
- 형식: 150~260줄, 파일 2~4개. 파일 저장소·구간 생성·구간 읽기를 분리한다. 수정은 위치를 계산하는 몇 줄로 끝나게 한다.
- 검증: 고정 테스트 6~10개로 ASCII, 한글, 보조 평면 문자, LF·CRLF, 마지막 개행 유무와 여러 구간의 연속성을 확인한다. 실제 바이트를 잘라 복원한 레코드로 판정하고 특정 길이 계산 API를 강제하지 않는다.
- 출처: [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)의 UTF-8 인코딩 설명, [Java SE 21 String](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/String.html)의 UTF-16 표현과 `getBytes` 계약. 실제 문제를 만들 때 고정 입력의 바이트 위치를 별도로 계산해 대조한다.
- 피할 것: 한글 NFC·NFD 정규화를 원인으로 삼는 것. F-search-40과 달리 인코딩된 파일의 위치가 목표다. BOM과 잘못된 UTF-8을 추가 원인으로 넣지 않는다.

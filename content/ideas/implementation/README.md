# 구현

AI 없이 스펙을 읽고 설계해 끝까지 구현하는 힘(build), 남의 코드를 끝까지 읽고 동작을 예측하는 힘(code), 버그를 재현하고 원인을 찾아 고치는 힘(fix)을 기른다.

Kotlin 언어·표준 라이브러리·컴파일러의 릴리스별 기능을 문제로 푸는 별도 구상은 [Kotlin 버전별 기능 문제 트랙 계획](kotlin-versions.md)에 있다. 버전별 컴파일 검증 계약을 정한 뒤 카드로 옮긴다.

## 1. build: 스펙을 읽고 끝까지 구현한다

### 1.1 주제 선정 기준

- 단계 3개 이상으로 나눌 수 있고 뒤 단계가 앞 단계 위에 쌓인다. 뒤 단계는 앞 단계 명령의 출력을 바꾸지 않는다.
- 입출력이 표준 입력과 표준 출력의 명령 처리기로 정해진다. 출력이 입력만으로 정해진다(시각은 입력 명령으로 준다).
- 배워 둘 만한 배경 개념이 있다. 예: 역색인, BM25, 위치 색인, 로그 구조 저장, 질의 계획.
- 대규모 테스트가 올바른 자료구조 없이는 제한 시간을 넘게 만든다.
- 단계마다 숙련 개발자에게 1~3시간이 걸린다.
- 외부 의존성 없이 Kotlin 표준 라이브러리로 풀 수 있다. `coroutine-patterns`는 kotlinx-coroutines-core와 kotlinx-coroutines-test를 쓰고, `coroutine-runtime`은 표준 라이브러리와 JDK만 쓴다(D16, D26).

## 2. code: 남의 코드를 끝까지 읽는다

### 2.1 주제 선정 기준

- 실제 서비스에서 볼 법한 모듈이다. 쇼핑 카탈로그 백엔드와 가까운 도메인을 고르되 회사 고유 정보는 쓰지 않는다.
- 문항의 함정은 실무 코드에서 자연스럽게 생기는 선택에서 나온다. Kotlin 언어 규칙, 표준 라이브러리 동작, 순서와 경계가 그 예다. 일부러 꼬은 코드를 쓰지 않는다.
- 단계마다 다른 언어·라이브러리 영역을 다룬다. 같은 함정을 두 단계에서 반복하지 않는다.
- 코드는 150~400줄, 파일 2~5개다. 단계가 오를수록 규모와 추적할 상태가 늘어난다.
- 외부 의존성 없이 실행된다. 예외는 코루틴 코드 읽기(C-coroutines-30, C-coroutines-32)이며 kotlinx.coroutines 를 쓴다(D16). 코루틴 학습 전체는 [../backend/coroutines/README.md](../backend/coroutines/README.md) 에 있다.

## 3. fix: 버그를 재현하고 고친다

### 3.1 주제 선정 기준

- 버그는 실무에서 흔히 생기는 종류다. 경계값, 상태 공유, 시간대, 정밀도, 컬렉션 의미, 지연 평가 같은 원인을 쓴다.
- 한 단계의 원인은 하나다. 증상은 여러 개일 수 있다. 수정은 몇 줄로 끝난다.
- 버그 신고에는 증상과 재현 입력만 적는다. 원인은 적지 않는다.
- 코드는 버그 말고는 올바르게 동작한다. 버그는 실무에서 그렇게 쓰기 쉬운 형태로 심는다. 일부러 틀린 티가 나면 안 된다.
- 테스트는 같은 버그를 다른 방식으로 고쳐도 통과해야 한다.

## 4. 카드

카드는 `cards/` 에 한 장씩 있다. B 는 build, C 는 code, F 는 fix 카드다. 목록과 상태는 [../INDEX.md](../INDEX.md) 의 "구현" 절에서 확인한다.

백엔드 도메인을 다루는 build·code·fix 카드는 그 도메인 폴더(`../backend/<도메인>/cards/`)에 둔다. 출제 기준은 이 문서를 따른다.

# R-design-patterns-10 객체를 만드는 책임과 생성 패턴

- 분야: 기술(소프트웨어 설계)
- 목표: 객체를 만드는 책임을 어디에 두는지에 따라 생성 패턴을 구분하고 Kotlin 언어 기능이 어떤 패턴을 대신하며 어떤 문제를 남기는지 판단한다.
- 다룰 내용: 생성 코드를 쓰는 쪽에서 떼어 내는 이유(쓰는 쪽이 구체 클래스를 몰라도 되게 하기), 팩토리 메서드(하위 클래스가 만들 객체를 정한다)와 추상 팩토리(서로 맞는 객체 묶음을 함께 만든다)의 차이, 빌더(단계적 조립과 불변 결과), 프로토타입(복제로 만들기, 얕은 복사와 깊은 복사), 싱글턴(인스턴스 하나와 전역 상태의 비용, 지연 초기화). Kotlin의 기본 인자와 이름 붙인 인자, `object`(처음 접근할 때 스레드 안전하게 초기화된다), data class의 `copy`, `lazy`가 각각 무엇을 대신하는지.
- 난도: 수능 기술 지문 고난도.
- 형식: 2,600~3,000자, 6~7문단, 5~6문항. `<보기>` 하나는 요구 변경 사례(새 제품군 추가, 새 조립 단계 추가)를 주고 어느 패턴이 변경을 한 곳에 모으는지 고르게 한다. 다른 하나는 가변 목록을 담은 객체를 `copy`로 복제한 뒤 원본의 목록을 바꾸는 순서를 주고 두 객체의 상태를 판단하게 한다.
- 함정과 엣지 케이스: 팩토리 메서드와 추상 팩토리를 만드는 객체 수로만 구분한 선지, `copy`를 깊은 복사로 읽은 선지, `object`가 프로그램 시작 때 초기화된다고 비튼 선지, 싱글턴이 남긴 상태가 다음 테스트에 새는 문제.
- 검증: 패턴의 의도는 GoF 원전으로, Kotlin 동작은 Kotlin 문서와 짧은 Kotlin 스크립트로 확인한다.
- 출처: 이 도메인 README의 '출처' 절.
- 피할 것: 다섯 패턴의 UML 구조를 외우게 하는 문항, 구조 패턴과 행위 패턴을 같은 지문에 섞는 것.

# B-pipeline-10 현재 상태를 보존하는 이력 압축기 만들기

- 목표: 기준 시점의 상태와 이후 변경을 보존하면서 오래된 변경 이력을 정리한다. 바뀐 필드만 복사했을 때 사라지는 상태를 이해하고 막는다.
- 입출력 모양: 키·필드·시각·순번·값을 가진 변경을 등록하고 시점 조회, 기준 상태 생성, 정리 계획·적용 명령을 처리한다. 시각은 입력 정수이며 실제 데이터베이스를 쓰지 않는다.
- 1단계 `01-materialize`: 필드별 변경과 삭제 표식으로 지정 시점의 상태를 재구성한다. 같은 시각의 변경은 입력 순번으로 정하고 삭제된 필드와 값이 없는 필드를 구분한다.
- 2단계 `02-baseline`: 기준 시각 미만의 상태를 기준 상태로 접고 그 이후 변경은 원래 순번과 함께 유지한다. 이번 창에 변경된 키의 전체 상태를 생성하며 바뀌지 않은 필드와 키를 보존한다. 새 기준 이후의 시점 조회 결과는 압축 전과 같아야 한다.
- 3단계 `03-retention`: 기준 상태를 적재·확인한 키만 옛 이력을 제거한다. 계획과 적용을 분리하고 입력 버전이 달라졌으면 적용을 거절한다. 같은 계획의 재적용은 같은 결과를 내며 새 기준 이전 조회는 명시한 보관 오류로 처리한다.
- 난도: 단계마다 1~3시간. 작은 입력은 모든 변경을 재생해 검증하고 큰 입력은 키별 이력을 반복 전수 검색하는 방식과 구분한다. 제한은 제작 때 실측한다.
- 함정: 변경 없는 필드의 소실, 필드 삭제 후 재생성, 기준과 같은 시각, 동점 순번, 0건 정리, 계획 이후의 새 쓰기, 재실행.
- 검증: 스펙만 읽은 테스트 작성자가 압축 전후의 여러 시점 상태를 직접 유도한다. 키 수나 필드 수가 같다는 검사만으로 내용 보존을 판정하지 않는다. 이전 기준의 조회 제한도 검사한다.
- 출처: [Kafka Design의 Log Compaction](https://kafka.apache.org/42/design/design/), [Event Sourcing pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)의 스냅숏과 재생성. 필드별 병합·기준 포함 여부·보관 오류는 과제 규칙이며 이벤트 저장소의 영구 이력을 삭제하라는 지침이 아니다.
- 피할 것: HBase timestamp의 1ms 규약이나 실제 저장소의 삭제 API를 그대로 요구하는 것. table-format의 스냅숏 메타데이터 구현을 반복하지 않는다.

# R-incidents-30 잘못 입력한 용량 제거 명령

- 분야: 기술(장애 보고서)
- 목표: 입력 실수 하나가 큰 장애로 번지고 회복이 늦어진 조건을 구별하고 셀 구조가 줄이는 것과 줄이지 못하는 것을 판단한다.
- 사건: 2017-02-28 오전 9:37(PST), 결제 처리에 쓰는 S3 하위 시스템의 서버 몇 대를 제거하려던 명령에 잘못된 입력이 들어가 의도보다 많은 서버가 제거됐다. 모든 객체의 메타데이터와 위치를 관리하는 색인 하위 시스템과 새 저장 공간을 배정하는 배치 하위 시스템이 영향을 받았다. 배치는 색인이 동작해야 제대로 작동한다. 큰 지역에서는 두 하위 시스템을 여러 해 동안 완전히 재시작한 적이 없었고 그사이 규모가 커져 재시작과 안전 확인이 오래 걸렸다. 색인은 오후 12:26 에 GET, LIST, DELETE 를 다시 처리하기 시작해 1:18 에 완전히 회복했고 배치는 색인이 동작하기 시작한 뒤 회복을 시작해 1:54 에 끝냈다.
- 다룰 내용: 운영 도구의 입력 실수가 큰 영향으로 번지는 조건, 하위 시스템 사이 의존, 오래 하지 않은 재시작이 회복 시간을 늘린 이유, 상태 대시보드 관리 콘솔이 S3 에 기대어 상태를 갱신하지 못한 점.
- 재발 방지책: 용량을 천천히 제거하도록 도구 수정, 하위 시스템이 최소 용량 아래로 내려가면 제거하지 못하게 막기, 색인 하위 시스템을 더 작은 셀로 나누는 계획을 앞당겨 바로 시작, 대시보드 관리 콘솔을 여러 지역에서 실행.
- 난도: LEET 언어이해 수준.
- 형식: 2,600~3,000자, 6~7문단, 6문항. `<보기>` 는 셀 수와 셀 크기를 바꿨을 때 영향 범위와 재시작 시간을 비교하는 자료를 준다.
- 함정과 엣지 케이스: 사람의 실수가 근본 원인이라고 본 선지(도구에 안전장치가 없었다), 셀로 나누면 사건이 생기지 않는다고 본 선지(영향 범위가 줄어든다), 색인과 배치의 회복 순서를 뒤집은 선지.
- 검증: 시각과 수치는 보고서로 확인한다.
- 이어지는 카드: system-design README 의 '빅테크 공개 사례' 절의 셔플 샤딩 사례.
- 출처: AWS 사후 보고서.
- 피할 것: 보고서에 없는 원인 추측, 사람을 탓하는 서술, 지문에서 수치를 찾기만 하면 풀리는 문항.

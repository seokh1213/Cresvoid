# R-incidents-70 연휴 뒤 첫 월요일의 급증

- 분야: 기술(장애 보고서)
- 목표: 조용한 기간 뒤의 급증이 네트워크 확장 지연, 지표 왜곡, 설정 서비스 한도로 번진 과정을 따라가고 위험 구간을 판단한다.
- 사건: 2021-01-04 은 연휴 뒤 첫 월요일이었다. 클라이언트 캐시가 비어 있어 클라이언트가 평소보다 많은 데이터를 내려받았다. VPC 를 잇는 AWS Transit Gateway 는 빨리 확장하지 못해 패킷을 버렸다. 백엔드 호출이 느려지자 웹 계층은 CPU 사용률이 떨어져 자동 축소가 먼저 일어났고 곧 스레드 사용률이 올라 대규모 자동 확장이 이어졌다. 오전 7:01~7:15(PST) 웹 계층에 서버 1,200대를 더하려 했지만 새 인스턴스를 설정하는 provision-service 가 Linux 열린 파일 수 한도와 AWS 할당량에 막혀 대부분이 설정을 마치지 못했다. 7시 무렵 Slack 을 쓸 수 없게 됐고 9:15 무렵 중단에서 저하로 바뀌었다. 10:40 AWS 가 게이트웨이 용량을 수동으로 늘린 변경이 모든 가용 영역에 퍼지며 네트워크가 정상으로 돌아왔다.
- 다룰 내용: 조용한 기간 뒤의 급증과 차가운 캐시, 관리형 네트워크 구성 요소의 확장 속도, 지연이 CPU 지표를 낮춰 자동 축소를 부르는 경로, 급히 늘린 서버가 설정 서비스 한도에 막힌 과정, 대시보드와 알림 서비스가 장애 난 게이트웨이에 기댄 문제.
- 재발 방지책: 대시보드와 알림 서비스를 백엔드 DB 와 같은 VPC 로 옮기기, provision-service 정기 부하 시험, 다음 연휴 시즌 끝에 게이트웨이 확장을 미리 요청, AWS 는 초당 패킷이 크게 늘 때의 확장 알고리즘을 점검.
- 난도: LEET 언어이해 수준.
- 형식: 2,600~3,000자, 6~7문단, 5문항. `<보기>` 는 다른 서비스의 월요일 아침 트래픽과 캐시 적중률 자료를 주고 위험 구간을 고르게 한다.
- 함정과 엣지 케이스: 트래픽 총량만으로 장애를 설명한 선지(차가운 캐시가 늘린 요청량과 게이트웨이 확장 속도가 함께 작용했다), 자동 확장이 언제나 도움이 된다고 본 선지, CPU 사용률이 낮으니 여유가 있다고 본 선지.
- 검증: 시각과 수치는 보고서로 확인한다.
- 이어지는 카드: L-load-40(동시 만료), L-load-60(캐시 장애와 원천 보호).
- 출처: Slack Engineering 사후 보고서.
- 피할 것: 보고서에 없는 원인 추측, 사람을 탓하는 서술, 지문에서 수치를 찾기만 하면 풀리는 문항.

# R-incidents-60 기능 플래그 없는 코드 경로와 빈 필드

- 분야: 기술(장애 보고서)
- 목표: 실행된 적 없는 코드 경로, 전역 즉시 복제, 백오프 없는 재시작이 이어진 사슬을 구별하고 각 방지책이 끊는 고리를 짝짓는다.
- 사건: 2025-05-29 Service Control 에 할당량 정책 검사를 더하는 코드가 들어갔다. 이 코드에는 오류 처리도 기능 플래그 보호도 없었다. 이 코드 경로는 특정 정책 변경이 있어야 실행돼서 지역별 단계 배포 동안 한 번도 실행되지 않았다. 2025-06-12 오전 10:45(PDT) 무렵 의도하지 않은 빈 필드가 든 정책 변경이 지역 Spanner 테이블에 들어갔고 몇 초 만에 전 세계로 복제됐다. 모든 지역에서 새 코드 경로가 빈 필드로 널 포인터를 역참조해 충돌과 재시작을 반복했다. 2분 안에 대응을 시작했고 10분 안에 원인을 찾았다. 기능을 비활성화하는 장치는 약 25분 만에 준비됐고 40분 안에 배포가 끝났다. 회복은 작은 지역부터 시작됐다. 큰 지역(us-central1)은 무작위 지수 백오프가 없어 재시작하는 작업들이 Spanner 테이블에 몰렸고 완전 회복에 약 2시간 40분이 걸렸다.
- 다룰 내용: 기능 플래그로 새 코드 경로를 가두는 이유, 입력 검증, 전역 즉시 복제되는 메타데이터, 충돌 반복, 몰려드는 재시작(herd effect)과 지터 있는 백오프.
- 재발 방지책: 기능을 분리해 검사가 실패해도 요청을 처리하게(fail open), 전역 복제 데이터를 검증할 시간을 두고 점진적으로 퍼뜨리기, 중요 바이너리 변경은 기능 플래그로 보호하고 기본값은 비활성으로, 정적 분석과 시험 강화, 무작위 지수 백오프 점검, 외부 공지 개선, 자사 감시 제품이 멈춰도 감시와 공지 체계 유지.
- 난도: LEET 언어이해 수준.
- 형식: 2,600~3,000자, 6~7문단, 6문항. `<보기>` 는 재시작 작업 수와 백오프 방식(없음, 고정, 지터 있는 지수)을 주고 하위 저장소에 몰리는 초당 요청을 비교하게 한다.
- 함정과 엣지 케이스: 코드 배포와 장애가 2주 떨어진 이유, 기능 플래그만 있으면 버그가 사라진다고 본 선지(비활성화해 둘 수 있게 된다), 원인을 빨리 찾았는데도 한 지역이 늦게 회복한 이유, 단계 배포를 거쳤으니 안전했다고 본 선지(그 경로가 실행되지 않았다).
- 검증: 시각과 수치는 Google Cloud 공식 사건 보고로 확인한다. `<보기>` 계산은 Kotlin 스크립트로 확인한다.
- 이어지는 카드: L-load-70(재시도와 백오프).
- 출처: Google Cloud Service Health 사건 보고.
- 피할 것: 보고서에 없는 원인 추측, 사람을 탓하는 서술, 지문에서 수치를 찾기만 하면 풀리는 문항.

# R-incidents-20 43초 분할이 만든 하루 동안의 장애

- 분야: 기술(장애 보고서)
- 목표: 43초 분할이 자동 장애 조치를 거쳐 두 데이터센터의 갈라진 쓰기로 이어진 사슬을 따라가고 정합성을 고른 판단의 근거를 설명한다.
- 사건: 2018-10-21 22:52 UTC, 고장 난 100G 광 장비를 바꾸는 정기 작업 중 미국 동부 네트워크 허브와 동부 주 데이터센터 사이가 끊겼다가 43초 뒤 다시 연결됐다. 장애 조치 도구(Orchestrator)는 Raft 합의로 리더를 바꿨고 서부 데이터센터와 동부 퍼블릭 클라우드의 노드가 정족수를 이뤄 쓰기 대상을 서부 DB 로 바꿨다. 동부 DB 에는 서부로 복제되지 않은 짧은 구간의 쓰기가 남았고 가장 바쁜 클러스터 하나에서만 954건이었다. 서부 DB 는 거의 40분 동안 애플리케이션의 쓰기를 받아 동부로 바로 되돌릴 수 없었다. 서비스 저하는 24시간 11분 이어졌다.
- 다룰 내용: 자동 장애 조치의 정족수와 지역, 복제 지연과 쓰기 유실의 관계, 가용성보다 데이터 정합성을 고른 판단(웹훅 전송과 Pages 빌드를 멈춤), 두 데이터센터에 갈라진 쓰기를 맞춘 과정.
- 재발 방지책: 지역 경계를 넘어 기본 DB 를 승격하지 못하게 Orchestrator 설정 변경, 새 상태 보고 방식으로 이전 가속, 세 데이터센터에서 동시에 서비스하는 설계, 결함 주입과 카오스 엔지니어링 도구 투자.
- 난도: LEET 언어이해 수준.
- 형식: 2,600~3,000자, 6~7문단, 6문항. `<보기>` 는 다른 서비스의 DB 두 곳과 복제 지연, 분할 시간표를 주고 장애 조치 정책별로 생기는 갈라진 쓰기를 묻는다.
- 함정과 엣지 케이스: 분할 시간이 짧으면 피해도 작다고 본 선지, 자동 장애 조치가 언제나 가용성을 높인다고 본 선지, 동부의 미복제 쓰기와 서부의 새 쓰기를 섞은 선지.
- 검증: 시각과 수치는 보고서로 확인한다.
- 이어지는 카드: R-distributed-10, B-distributed-20(Raft 의 정족수와 커밋 규칙).
- 출처: GitHub 사후 보고서.
- 피할 것: 보고서에 없는 원인 추측, 사람을 탓하는 서술, 지문에서 수치를 찾기만 하면 풀리는 문항.

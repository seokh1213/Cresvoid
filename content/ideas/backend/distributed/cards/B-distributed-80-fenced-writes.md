# B-distributed-80 저장소가 검사하는 펜싱 토큰 만들기

- 목표: lease 잠금을 얻은 사실과 저장소가 쓰기를 승인하는 조건을 분리한다. 획득마다 증가하는 번호를 펜싱 토큰으로 넘기고 저장소가 자신이 이미 관측한 더 큰 번호보다 오래된 쓰기를 거절하게 한다.
- 입출력 모양: 앞 단계에 `WRITE <key> <token> <value>`, `READ <key>`를 더한다. 키마다 저장 값과 관측한 최대 토큰을 유지하고 쓰기의 수락·거절을 출력한다. 획득 번호 발급과 앞 단계 명령의 출력은 바꾸지 않는다.
- 3단계 `03-fenced-writes`: 더 큰 토큰을 받은 쓰기는 값과 최대 토큰을 함께 원자적으로 갱신한다. 같은 토큰의 연속 쓰기는 입력 순서대로 허용하고 더 작은 토큰은 상태를 바꾸지 않고 거절한다. 자원마다 관측한 토큰을 따로 관리하고 저장소 재시작 모형을 넣는다면 값과 최대 토큰을 함께 보존한다.
- 난도: 1~3시간. 늦게 전달된 요청과 쓰기의 수락 순서를 따라가며 저장소 상태를 구현한다. 토큰의 발급 범위와 유효한 입력 범위는 스펙에 고정한다.
- 함정: 비교를 잠금 서비스에서만 하고 저장소는 무조건 쓰는 경우, 토큰 검사와 값 갱신을 나누는 경우, 같은 토큰을 잘못 거절하는 경우, 서로 다른 키의 최대 토큰을 섞는 경우.
- 검증: 앞 단계 누적 검사에 고정 테스트 10~14개와 생성 테스트 2~3개를 더한다. 새 토큰의 쓰기가 반영된 뒤 옛 요청을 전달해 거절되는지 검사한다. 새 토큰이 아직 저장소에 도착하지 않은 상태에서 옛 토큰의 쓰기가 수락되는 경우도 계약에 맞춰 확인한다.
- 출처: [Chubby 논문](https://research.google/pubs/the-chubby-lock-service-for-loosely-coupled-distributed-systems/)의 획득 번호와 서버의 오래된 요청 거절, [원문 PDF](https://storage.googleapis.com/gweb-research2023-media/pubtools/4444.pdf)의 Design 부분. 이 카드의 명령과 키별 비교 규칙은 학습용으로 명세한다.
- 피할 것: 펜싱만으로 lease 만료 시각 이후의 모든 쓰기가 즉시 거절된다고 주장하는 것. 이 모형은 저장소가 더 큰 토큰을 관측한 뒤의 역행을 막는다. 실제 만료 검증과 클라이언트 인증은 범위 밖이다.

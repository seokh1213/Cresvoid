# F-distributed-70 늦은 해제가 새 잠금을 지우는 버그

- 맥락: 여러 문서 생성 작업이 같은 자원의 lease 잠금을 얻는다. 입력으로 획득·시각 이동·해제 사건을 주고 저장소가 조건부 갱신을 원자적으로 처리한다. 해제 요청에는 획득 당시 받은 번호가 들어 있다.
- 버그 후보: 해제 경로가 현재 획득 번호를 확인하지 않고 키만으로 잠금을 삭제하는 원인 하나를 심는다. 만료 판단과 새 잠금 획득, 번호 발급은 올바르게 동작한다.
- 버그 신고: "작업 A의 잠금이 만료된 뒤 작업 B가 같은 자원을 얻었다. 뒤늦게 도착한 A의 해제 요청 다음에 B의 잠금이 사라졌고 작업 C도 획득에 성공했다."
- 형식: Kotlin 150~250줄, 파일 2~4개. 버그 수정은 몇 줄로 끝나고 `spec.md`에 획득 번호의 의미와 저장소 연산의 원자적 범위를 밝힌다. 실제 스레드와 시간을 쓰지 않는다.
- 난도: 같은 클라이언트가 만료 후 재획득하는 경우도 둔다. 클라이언트 이름만 확인하는 수정으로는 획득 세대가 다른 두 요청을 구분할 수 없다.
- 검증: 고정 테스트 6~10개로 정상 해제·중복 해제·다른 자원 해제의 기존 동작과 늦은 해제를 확인한다. 동일 클라이언트 재획득 뒤 옛 요청도 넣는다. 조건부 삭제 방식이 달라도 공개 계약을 만족하면 통과시킨다.
- 출처: [etcd 3.6 concurrency API](https://etcd.io/docs/v3.6/dev-guide/api_concurrency_reference_v3/)의 소유권 키와 해제, [Chubby 논문](https://research.google/pubs/the-chubby-lock-service-for-loosely-coupled-distributed-systems/)의 잠금 세대. 공개 API와 실패 입력은 과제의 모형으로 새로 정한다.
- 피할 것: 해제 순서 오류와 만료 계산 오류를 함께 심는 것, 배경 설명이나 테스트 이름에 수정 위치를 드러내는 것. 저장소의 늦은 쓰기 차단까지 이 단계의 통과 조건에 넣지 않는다.

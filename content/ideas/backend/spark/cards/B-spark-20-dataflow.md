# B-spark-20 데이터 흐름 엔진 만들기

- 목표: Spark 같은 데이터 흐름 엔진의 핵심인 지연 실행, 스테이지 분할, 해시 파티셔닝, 셔플, 맵 쪽 결합, 조인 전략, 적응 실행을 표준 입출력 명령 처리기로 직접 만든다.
- 입출력 모양: 데이터 정의(이름, 파티션 수, 키와 값 행), 파이프라인 정의(source, map, filter, reduceByKey n, groupByKey n, repartition n, coalesce n, join 다른 파이프라인 n), `PLAN` 과 `RUN` 명령이다. map 과 filter 의 식은 명세가 정한 작은 내장 함수 집합으로 제한해 데이터 흐름에 집중하게 한다.
- 1단계 `01-plan`: 변환을 좁은 의존과 넓은 의존으로 나눠 스테이지 번호, 스테이지마다 태스크 수, 셔플 경계를 출력한다. `RUN` 은 결과 행을 정해진 순서로 출력한다. 행동 하나가 잡 하나다.
- 2단계 `02-shuffle`: 해시 파티셔닝 규칙을 명세로 고정한다(예: 키의 Java `String.hashCode` 를 파티션 수로 나눈 음이 아닌 나머지). 셔플마다 쓰는 레코드 수와 바이트 수를 보고한다. reduceByKey 의 맵 쪽 결합이 셔플 레코드를 얼마나 줄이는지 드러난다. 메모리 한도를 넘으면 흘림 파일 수를 센다.
- 3단계 `03-join`: 크기 추정과 임계값으로 브로드캐스트 조인과 정렬 병합 조인을 고른다. 두 전략의 결과는 같고 계획과 셔플량만 다르다. 같은 파티셔너로 나뉜 입력의 조인은 셔플이 없다. NULL 키는 `=` 의미론대로 짝이 없고 null-safe 조인 옵션은 NULL 끼리 맞춘다. 쏠린 키를 (중앙값 × 배수) 와 절대 크기 두 조건으로 판정하고 쪼갠 계획을 출력한다.
- 4단계 `04-adaptive`: 셔플 뒤 실제 파티션 크기로 파티션을 병합하고(권장 크기, 최소 크기 규칙) 조인 전략을 바꾼다. 대규모 테스트는 행 수백만 개다.
- 난도: 단계마다 숙련 개발자 2~3시간. 4단계 대규모 테스트는 행마다 객체를 만들고 복사하는 구현으로는 제한 시간을 넘게 만든다.
- 함정: coalesce 가 셔플 없이 앞 스테이지와 합쳐진다는 점, 음수 해시의 나머지, 빈 파티션, 같은 파티셔너 조인의 셔플 생략, 쏠림 판정의 두 조건, 병합 뒤 파티션 번호를 다시 매기는 규칙.
- 검증: build 스킬의 교차 검증. 작은 입력의 계획은 손으로 계산한 결과와 대조한다.
- 출처: Spark RDD Programming Guide 의 Shuffle operations 절, Performance Tuning 의 Adaptive Query Execution 절, Zaharia 외 NSDI 2012.
- 피할 것: Spark 의 실제 출력 형식이나 내부 구현(셔플 파일 형식, Tungsten)을 흉내 내게 하는 것. 명세가 정한 단순한 형식을 쓴다.

# B-coroutines-35 코루틴 동시 처리 심화

- 배경: B-coroutines-20 의 학습자 검토는 4단계 `04-flow` 가 목표 난도(2~3시간)보다 쉽다고 판단했다. 함수 매개변수와 배경 설명이 `stateIn`, `buffer`, `conflate` 를 거의 알려 주어서 연산자를 고르고 판매가 계산을 25줄 정도 쓰면 끝났다. 4단계를 고치려면 B-coroutines-20 의 범위를 바꿔야 한다. 그래서 4단계는 그대로 두고 학습자가 구조를 직접 설계해야 하는 단계를 같은 트랙 뒤에 더한다(2026-10-12 사용자 제안).
- 목표: 실무에서 자주 짜는 동시 처리 구조를 라이브러리 연산자에 기대지 않고 안정 API 로 설계해 구현한다. 묶음 저장과 요청 합치기를 다룬다.
- 난도를 올리는 장치: 이런 일에 바로 쓸 API 는 1.11.0 에서 실험 표시가 붙어 있어 학습자에게 요구할 수 없다(이 도메인 README 의 '환경' 절). 학습자는 `channelFlow`, `Channel`, `select` 의 `onReceive`, `Mutex`, `Semaphore`, `CompletableDeferred`, `SupervisorJob`, `withTimeoutOrNull` 같은 안정 API 로 구조를 짠다.
- 입출력 모양: 1~4단계와 같다. 시나리오 명령으로 가짜 하위 서비스와 이벤트를 정한다. 실행 틀은 학습자 함수의 결과와 사건 기록을 가상 시각과 함께 출력한다. 같은 시각의 사건 줄은 1단계 [3.12] 의 정렬 규칙을 그대로 쓴다. 새 단계 명령은 앞 단계 명령의 출력을 바꾸지 않는다. 시작 코드에 새 명령의 실행 틀과 가짜 서비스를 더하고 학습자 함수는 본문만 비운다.
- 5단계 `05-batching`: 가격 변경 이벤트를 묶어 일괄 저장하는 Flow 연산자를 직접 만든다.
  - 묶음은 이벤트가 N개 차거나 묶음의 첫 이벤트 뒤 T 가 지나면 닫는다. 두 조건이 같은 시각에 맞을 때의 처리는 스펙이 정한다.
  - 저장은 한 번에 하나씩 한다. 저장을 기다리는 묶음이 정한 수를 넘으면 앞단을 늦춘다.
  - 위쪽 흐름이 끝나면 남은 묶음을 저장한다. 위쪽이 실패했을 때와 수집이 취소됐을 때 남은 묶음과 진행 중인 저장을 어떻게 끝낼지는 스펙이 정한다.
- 6단계 `06-single-flight`: 같은 상품을 여러 요청이 동시에 찾으면 하위 호출 한 번을 나눠 쓴다.
  - 기다리던 요청 하나가 취소되거나 시간 제한에 걸려도 공유 호출은 계속한다. 기다리는 요청이 모두 떠나면 공유 호출을 취소한다.
  - 실패는 그때 기다리던 요청에게만 전하고 캐시하지 않는다.
  - 캐시 값이 만료되면 만료된 값을 바로 돌려주고 뒤에서 한 번만 갱신한다. 갱신이 실패했을 때의 처리는 스펙이 정한다.
- 난도: 단계마다 숙련 개발자에게 2~3시간. 단계마다 학습자가 직접 정해야 하는 구조가 있다. 5단계는 묶음 상태와 타이머, 6단계는 공유 호출의 주인과 대기자 수다. 배경 개념은 라이브러리 동작 사실만 설명하고 풀이 구조를 알려 주지 않는다(B-coroutines-20 마지막 수정과 같은 기준).
- 대규모 테스트: 6단계는 진행 중인 호출을 목록으로 훑는 풀이를 제한 시간으로 가른다. 5단계처럼 가를 자료구조가 없으면 무작위 입력으로 넓게 확인한다고 쓴다(implementation README 의 'build: 스펙을 읽고 끝까지 구현한다' 절).
- 함정: 묶음 타이머를 이벤트마다 다시 거는 코드, 위쪽이 끝났는데 남은 묶음을 버리는 코드, 공유 호출을 처음 요청의 스코프에서 실행해 그 요청이 취소되면 모두 실패하는 코드, 실패를 캐시해 다음 요청까지 실패하는 코드, Mutex 를 쥔 채 하위 호출을 기다려 다른 상품까지 막는 코드, `withContext(NonCancellable)` 없이 정리 작업을 하는 코드.
- 검증: build 스킬의 교차 검증. 참조 풀이와 구조가 다른 올바른 구현도 통과해야 한다. 5단계는 묶음 타이머를 `select` 의 `onReceive` 와 타이머 코루틴으로 짠 풀이와 `withTimeoutOrNull` 로 짠 풀이가 같은 출력을 내야 한다. 6단계는 Mutex 와 맵으로 짠 풀이와, 명령을 Channel 로 받는 코루틴 하나가 상태를 혼자 가지는 풀이가 같은 출력을 내야 한다.
- 출처: Kotlin 문서(Asynchronous Flow, Channels, Shared mutable state and concurrency, Cancellation and timeouts, Coroutine exceptions handling), kotlinx.coroutines API 문서(Mutex, CompletableDeferred, channelFlow, select). 동작 서술은 1.11.0 으로 실행해 확인한다.
- 피할 것: 실험 표시가 붙은 API 를 요구하는 것, 실제 시간 대기, 실행마다 달라지는 출력, 배경 개념에서 풀이 구조를 알려 주는 것.
- 단계 수: 2026-10-12 에 사용자와 두 단계로 정했다. 처음 안의 7단계(키별 순서를 지키는 병렬 처리와 종료)는 작업자 풀과 정리 작업이 2·3단계와 겹쳐서 제외했다. 그 안은 이 도메인 README 의 '아이디어' 절에 남겼다.

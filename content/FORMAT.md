# 컨텐츠 형식

이 문서는 엔진과 컨텐츠 사이의 계약이다. 엔진은 이 문서에 적힌 파일만 읽는다. 이 형식을 지키는 컨텐츠는 엔진을 고치지 않고 추가할 수 있다.

프로젝트에 남기는 코드는 엔진, 참조 풀이, 생성기, 검사 스크립트까지 모두 Kotlin 이다.

엔진은 `engine/bin/cresvoid` 로 실행한다. 이 문서는 줄여서 `cresvoid` 로 쓴다.

## 1. 디렉터리

```
content/tracks/<트랙 id>/
├── track.json
├── starters/<언어>/          build 트랙의 시작 코드
└── stages/<단계 디렉터리>/
    ├── spec.md               build·fix 트랙 문서
    ├── passage.md            reading 트랙 문서
    ├── guide.md              code 트랙 안내 문서
    ├── code/                 code 트랙에서 읽을 Kotlin 프로젝트
    ├── starter/              fix 트랙. 버그가 있는 Kotlin 프로젝트
    └── hidden/               채점용 파일
        ├── quiz.json         build·reading·code 트랙
        ├── tests.json        build·fix 트랙
        ├── allowed-edits.txt 선택. fix 트랙에서 수정 가능한 파일 목록
        ├── gen.main.kts      선택. 무작위 입력 생성기
        ├── api-check.main.kts 선택. build 트랙의 공개 API 동작 검사
        ├── ApiProbe.kt       선택. API 검사가 컴파일할 Kotlin 코드
        └── solution/         build·fix 트랙. 참조 풀이 Kotlin 프로젝트
```

- 학습자가 보는 문서와 코드는 단계 디렉터리에 둔다. 채점용 파일은 단계의 `hidden/` 에 두고 학습자는 열지 않는다.
- 트랙 id 는 트랙 디렉터리 이름이다. `progress` 는 트랙 id 로 쓰지 않는다. 작업 공간 기본 경로가 진행 기록 디렉터리 `practice/progress/` 와 겹친다. 엔진은 id 가 `progress` 인 트랙을 읽지 않는다.
- 단계 디렉터리 이름은 `두 자리 번호-영문 slug` 형식이다. 예: `01-boolean`.
- 트랙 종류는 네 가지다.

| 종류 | 이름 | 학습자가 하는 일 |
|---|---|---|
| `build` | 구현 | 스펙을 읽고 단계마다 기능을 더해 프로그램 하나를 완성한다 |
| `reading` | 독해 | 비문학 지문을 읽고 문항을 푼다 |
| `code` | 코드 읽기 | Kotlin 코드와 안내 문서를 읽고 실행 결과와 동작을 묻는 문항을 푼다 |
| `fix` | 버그 수정 | 단계마다 버그가 있는 Kotlin 프로그램을 받아 스펙대로 동작하게 고친다 |

## 2. track.json

```json
{
  "title": "나만의 검색 엔진",
  "kind": "build",
  "summary": "한 줄 소개",
  "stages": [
    { "dir": "01-boolean", "title": "색인과 불리언 검색" },
    { "dir": "02-ranking", "title": "BM25 랭킹" }
  ]
}
```

| 필드 | 필수 | 뜻 |
|---|---|---|
| title | 예 | 트랙 제목 |
| kind | 예 | `build`, `reading`, `code`, `fix` 가운데 하나 |
| summary | 예 | 한 줄 소개 |
| stages[].dir | 예 | 단계 디렉터리 이름. 배열 순서가 단계 순서다 |
| stages[].title | 예 | 단계 제목 |
| stages[].target_minutes | 아니오 | reading·code 트랙의 목표 풀이 시간(분) |

엔진은 이 표에 없는 필드가 있는 track.json 을 읽지 않는다.

## 3. 문서

build·fix 트랙 단계는 `spec.md` 를, reading 트랙 단계는 `passage.md` 를, code 트랙 단계는 `guide.md` 를 둔다. 모두 마크다운이다.

문단 번호 규칙은 다음과 같다.

- 줄 맨 앞이 `[번호]` 와 공백으로 시작하면 번호 문단이 시작된다. 번호는 `3`, `2.4`, `2.4.1` 처럼 숫자를 점으로 이은 것이다.
- 번호 문단은 빈 줄, 다음 번호 문단, `#` 제목 줄, 코드 펜스 줄 바로 앞에서 끝난다.
- 한 문서 안에서 같은 번호를 두 번 쓰지 않는다.
- 문항과 테스트가 가리키는 문장은 모두 번호 문단 안에 있어야 한다. 제목, 표, 코드 블록은 가리킬 수 없다.

code 트랙 문항은 코드 위치도 가리킬 수 있다.

- 코드 위치는 `<파일>:<줄>` 이나 `<파일>:<시작 줄>-<끝 줄>` 로 쓴다. 파일은 `code/src/main/kotlin/` 기준 상대 경로다. 예: `Cart.kt:12-30`.
- 줄 번호는 1부터 센다. 범위는 파일 안에 있어야 한다.
- 코드 위치를 가리키는 문항의 quote 는 그 줄 범위 안에 들어 있어야 한다. 비교할 때 공백은 하나로 줄인다.

본문은 해라체 평서형으로 쓴다.

## 4. quiz.json

build·reading·code 트랙 단계의 `hidden/quiz.json` 이다.

```json
{
  "questions": [
    {
      "id": "q1",
      "type": "choice",
      "prompt": "윗글의 내용과 일치하지 않는 것은?",
      "context": "<보기> 같은 추가 자료. 선택",
      "choices": ["선지1", "선지2", "선지3", "선지4", "선지5"],
      "answer": 3,
      "refs": ["2", "4"],
      "quote": "refs 문단의 핵심 문장",
      "explanation": "해설"
    },
    {
      "id": "q2",
      "type": "short",
      "prompt": "다음 입력의 출력은?",
      "input": ["ADD 1 apple pie", "QUERY apple"],
      "answers": ["1"],
      "refs": ["2.1"],
      "quote": "refs 문단의 핵심 문장",
      "explanation": "해설"
    }
  ]
}
```

| 필드 | 대상 | 뜻 |
|---|---|---|
| id | 공통 | 파일 안에서 겹치지 않는 문항 id |
| type | 공통 | `choice` 또는 `short` |
| prompt | 공통 | 발문 |
| context | 공통, 선택 | 발문 아래에 보여 줄 자료. 여러 줄 가능 |
| choices | choice | 선지 |
| answer | choice | 정답 선지 번호. 1부터 센다 |
| input | short | 프로그램 입력 줄. 화면에 코드 블록으로 보여 준다 |
| answers | short | 정답으로 인정할 문자열 목록 |
| refs | 공통 | 근거 문단 번호나 코드 위치 목록. 1개 이상 |
| quote | 공통 | refs 가운데 하나에 그대로 들어 있는 핵심 문장 |
| explanation | 공통 | 해설 |

트랙 종류마다 허용하는 문항이 다르다.

| 종류 | choice 선지 수 | short |
|---|---|---|
| build | 2~5 | 쓸 수 있다. input 은 선택이다 |
| reading | 5 | 쓰지 않는다 |
| code | 2~5 | 쓸 수 있다. input 이 반드시 있어야 한다 |
| fix | quiz.json 을 두지 않는다 | |

- short 답은 앞뒤 공백을 지우고 연속 공백을 하나로 줄인 뒤 비교한다. 대소문자는 구분한다.
- input 이 있는 short 문항은 실행으로 정답을 확인한다. build 트랙은 그 단계 참조 풀이에, code 트랙은 그 단계 `code/` 프로그램에 input 을 표준 입력으로 준다. 정확히 한 줄이 나와야 하고 그 줄이 `answers[0]` 과 같아야 한다.

## 5. tests.json

build·fix 트랙 단계의 `hidden/tests.json` 이다.

```json
{
  "timeout_sec": 10,
  "tests": [
    {
      "name": "add-and-query",
      "refs": ["2.4"],
      "quote": "refs 문단의 핵심 문장",
      "input": ["ADD 1 apple", "ADD 1 banana", "QUERY apple"],
      "expected": ["(none)"]
    },
    {
      "name": "random-mixed",
      "refs": ["3.1", "3.3"],
      "quote": "refs 문단의 핵심 문장",
      "gen": ["kotlin", "gen.main.kts", "--docs", "40", "--commands", "80"],
      "repeat": 3
    }
  ]
}
```

| 필드 | 필수 | 뜻 |
|---|---|---|
| timeout_sec | 아니오 | 테스트 하나의 제한 시간(초). 기본 10 |
| tests[].name | 예 | 단계 안에서 겹치지 않는 영문 kebab-case 이름. 화면에 보이므로 숨은 케이스의 조건이나 답을 담지 않는다(11.2 절) |
| tests[].refs | 예 | 테스트가 실패하면 다시 읽을 곳으로 보여 줄 근거 문단 번호 목록 |
| tests[].quote | 예 | refs 문단 가운데 하나에 그대로 들어 있는 핵심 문장. 테스트가 실패하면 보여 준다 |
| tests[].input | input 과 gen 중 하나 | 입력 줄 목록 |
| tests[].gen | input 과 gen 중 하나 | 입력을 만드는 명령. 6절 |
| tests[].expected | 아니오 | 기대 출력 줄 목록. gen 테스트에는 쓰지 않는다 |
| tests[].repeat | 아니오 | gen 테스트를 서로 다른 seed 로 몇 번 돌릴지. 기본 1 |
| tests[].timeout_sec | 아니오 | 이 테스트만의 제한 시간 |

`expected` 가 없으면 그 단계 참조 풀이의 출력이 기대값이다.

## 6. 무작위 입력 생성기

- 생성기는 단계 `hidden/` 의 Kotlin 스크립트(`*.main.kts`)다. `gen` 명령은 `["kotlin", "gen.main.kts", 인자...]` 처럼 스크립트 파일 이름으로 쓴다.
- 엔진은 단계의 `hidden/` 에서 명령을 실행하고 명령 끝에 `--seed <정수>` 를 붙인다.
- 생성기는 입력 줄을 표준 출력에 쓴다. 출력은 64MB 를 넘지 않는다.
- 같은 인자와 같은 seed 면 같은 출력을 내야 한다. 난수는 `kotlin.random.Random(seed)` 로 만든다.
- Kotlin 표준 라이브러리와 JDK 만 쓴다.

## 7. Kotlin 프로젝트

참조 풀이(`hidden/solution/`), build 트랙 시작 코드(`starters/<언어>/`), fix 트랙 시작 코드(`starter/`), code 트랙 코드(`code/`)는 모두 같은 모양의 Kotlin 프로젝트다.

```
<프로젝트>/
├── src/main/kotlin/     .kt 파일. 진입점은 최상위 main 함수 하나다
├── lib/                 선택. kotlinx.coroutines jar. 카드 env 가 kotlinx-coroutines 인 단계의 프로젝트에만 둔다
├── build.sh             kotlinc 로 build/app.jar 를 만든다. jar 가 소스보다 새로우면 건너뛴다
├── run.sh               자기 디렉터리로 이동해 java -jar build/app.jar 를 실행한다
├── build.gradle.kts     IntelliJ 로 열 때 쓰는 Gradle 설정
├── settings.gradle.kts
└── .java-version        21
```

- `src/main/kotlin/` 밖의 파일은 `content/templates/kotlin/` 의 파일과 같은 내용으로 둔다. `kotlin content/templates/sync.main.kts` 가 템플릿을 모든 Kotlin 프로젝트에 복사하고 실행 권한을 맞춘다. `--check` 를 붙이면 템플릿과 다른 파일만 알린다.
- `lib/` 가 있는 프로젝트는 `content/templates/kotlin/lib/` 의 jar 를 모두 같은 내용으로 갖는다. sync 가 jar 를 복사하고 템플릿에 없는 jar 는 지운다. 새 프로젝트는 빈 `lib/` 를 만든 뒤 sync 를 실행한다.
- `build.sh` 는 임시 파일로 컴파일한 뒤 `build/app.jar` 를 바꾼다. 빌드가 중간에 끊겨도 잘린 jar 가 남지 않는다.
- `build.sh` 는 `lib/` 의 jar 를 컴파일 classpath 에 넣고 `build/app.jar` manifest 의 Class-Path 에 적는다. 그래서 `run.sh` 는 `lib/` 가 있어도 `java -jar build/app.jar` 로 실행한다.
- Kotlin 표준 라이브러리와 JDK 만 쓴다. `lib/` 가 있는 프로젝트는 kotlinx.coroutines 도 쓴다(`docs/decisions.md` D21).
- 엔진은 `run.sh` 를 실행하기 전에 `build.sh` 가 있으면 그 디렉터리에서 한 번 실행한다.
- build 단계에서 표준 입력·출력만으로 확인할 수 없는 공개 API가 필수라면 `hidden/api-check.main.kts`를 둘 수 있다. 엔진은 빌드 뒤 이 스크립트를 단계의 `hidden/`에서 실행하고 풀이 프로젝트의 절대 경로를 인자 하나로 넘긴다. 스크립트는 Kotlin 표준 라이브러리와 JDK만 사용하며 60초 안에 종료 코드 0으로 끝나야 한다. 필요하면 같은 `hidden/`의 Kotlin 소스를 풀이의 `build/app.jar`에 대해 컴파일하고 호출한다. 이 검사의 실패 화면에는 숨은 검사 코드와 출력이 나오지 않는다.

참조 풀이 기준은 다음과 같다.

- 그 단계까지의 규칙을 모두 구현한 완성본이다. fix 트랙에서는 버그를 고친 프로그램이다.
- 같은 입력에 같은 출력을 내야 한다.
- 학습자가 `cresvoid solution` 으로 읽는 모범 코드다. 파일과 함수가 처리 단계를 드러내고 이름만으로 뜻이 보이게 쓴다. 주석은 11.8 절을 따른다.
- 학습자는 참조 풀이를 `hidden/` 에서 직접 열지 않고 `cresvoid solution` 으로 본다.

## 8. 시작 코드

- build 트랙: `cresvoid start` 가 `starters/<언어>/` 를 트랙 작업 공간으로 복사한다. 시작 코드는 빌드와 실행은 되지만 1단계 테스트는 통과하지 못해야 한다.
- fix 트랙: `cresvoid start` 가 단계의 `starter/` 를 그 단계 작업 공간으로 복사한다. 시작 코드는 빌드되고 그 단계 테스트 가운데 하나 이상에서 실패해야 한다. 참조 풀이와의 차이는 버그를 고치는 데 필요한 줄뿐이다.
- fix 단계가 `hidden/allowed-edits.txt` 를 두면 각 줄에 `starter/` 기준으로 수정 가능한 `src/main/kotlin/*.kt` 경로 하나를 적는다. `cresvoid test` 는 빌드 전에 이 파일 외의 시작 코드와 제출 작업 공간을 비교한다. `build/`, `.gradle/`, `.kotlin/`, `.idea/`, `.DS_Store` 는 비교하지 않는다. 허용하지 않은 소스의 추가·삭제와 실행 스크립트 수정도 거절한다. `cresvoid validate` 는 참조 풀이에도 같은 범위를 검사한다.
- 복사할 때 `build/` 디렉터리와 `.DS_Store` 는 빼고 실행 권한은 유지한다.

## 9. 엔진 동작

### 9.1 테스트 실행

1. build 트랙은 1단계부터 대상 단계까지 차례로 테스트를 실행한다. 앞 단계 테스트는 회귀 검사다. fix 트랙은 대상 단계 테스트만 실행한다.
   build 단계에 공개 API 검사가 있으면 각 단계의 입력 테스트보다 먼저 실행한다.
2. 테스트마다 풀이의 `run.sh` 를 새 프로세스로 실행한다. 작업 디렉터리는 풀이 디렉터리다.
3. 입력 줄을 줄바꿈으로 잇고 마지막 줄 뒤에도 줄바꿈을 붙여 표준 입력에 쓴 뒤 닫는다.
4. 프로세스가 끝나기를 제한 시간까지 기다린다. 제한 시간을 넘기면 프로세스와 그 자손 프로세스를 모두 종료하고 실패로 처리한다. 프로세스가 끝난 뒤 남은 자손 프로세스도 종료한다.
5. 종료 코드가 0 이 아니면 실패다. 표준 출력이 64MB 를 넘어도 실패다.
6. 표준 출력을 기대 출력과 비교한다. 각 줄 끝의 공백·탭·CR 을 지우고 끝의 빈 줄을 지운 뒤 줄 수와 각 줄을 글자 그대로 비교한다.
7. 첫 실패에서 멈춘다.
8. 테스트 도중 Ctrl-C 로 엔진을 멈추면 실행 중인 프로세스와 자손 프로세스를 모두 종료한다.

### 9.2 테스트 실패 출력

테스트가 실패하면 다음만 보여 준다.

| 항목 | 내용 |
|---|---|
| 테스트 이름 | 실패한 테스트의 name |
| 실패 종류 | 제한 시간 초과, 0 이 아닌 종료 코드, 출력 불일치 같은 판정 문구 |
| 다시 읽을 곳 | 실패한 테스트가 속한 단계의 문서 경로와 refs 문단 번호 |
| 핵심 문장 | 실패한 테스트의 quote |
| 다시 실행 명령 | gen 테스트일 때만. 같은 입력을 다시 만드는 `-seed` 를 붙인 `cresvoid test` 명령 |
| 참조 풀이 보기 명령 | `cresvoid solution <트랙> -stage <실패한 테스트가 속한 단계 번호>` |

- 테스트 입력, 기대 출력, 풀이 프로그램의 표준 출력과 표준 오류는 어떤 경우에도 화면에 보여 주지 않고 파일로도 남기지 않는다.
- 테스트 도중 참조 풀이나 입력 생성기가 실패하면 실패한 프로그램과 단계, 종료 사유만 보여 준다. 두 프로그램의 표준 오류는 `cresvoid validate` 에서만 보여 준다.
- 테스트 실패는 진행 기록에 남기지 않는다. 같은 테스트가 몇 번 실패해도 보여 주는 항목은 같다.
- 빌드(`build.sh`)가 실패하면 빌드 출력을 보여 준다. 학습자가 쓴 코드를 빌드한 출력이라 숨은 케이스와 상관없다.

### 9.3 읽기와 문항 풀이

1. `cresvoid read` 는 단계 문서를 보여 준다. code 트랙은 `guide.md` 뒤에 `code/src/main/kotlin/` 의 파일을 줄 번호와 함께 이어 보여 주고 코드 디렉터리 경로도 알려 준다.
2. 아직 닫히지 않은 문항을 모두 차례로 묻고 다 답한 뒤 한꺼번에 채점한다.
3. 처음 제출할 때 첫 시도 점수와 걸린 시간을 기록한다. 걸린 시간은 읽기를 시작한 시각부터 잰다. 마지막으로 읽은 지 한 시간 안에 문서를 다시 열면 읽기를 시작한 시각을 유지한다. 한 시간이 지나 다시 열면 그 시각부터 다시 잰다. 마지막으로 읽은 시각은 `cresvoid read` 를 실행하거나 문서 보기를 닫은 때다.
4. 문항을 풀기 시작할 때 읽은 기록이 없거나 마지막으로 읽은 지 한 시간이 지났으면 시간을 기록하지 않는다.
5. 첫 시도에서 답을 하나도 하지 않고 입력이 끝나면(Ctrl-C, Ctrl-D) 그 시도는 저장하지 않는다. 하나 이상 답한 뒤 입력이 끝나면 답한 문항을 채점하고 답하지 않은 문항은 오답으로 센다. 두 번째 시도부터는 그만두면 아무것도 저장하지 않는다.
6. 모든 문항이 닫히면 해설을 모두 보여 준다.
7. build 트랙은 1단계부터 대상 단계까지 문항을 모두 닫아야 대상 단계 테스트가 열린다. fix 트랙은 테스트를 여는 조건이 없다. reading·code 트랙은 문항을 모두 닫으면 그 단계를 마친다.

문항 오답 횟수는 문항마다 따로 센다.

| 오답 횟수 | 보여 주는 것 |
|---|---|
| 1 | 다시 읽을 문단 번호나 코드 위치 |
| 2 | 위 내용, 핵심 문장 |
| 3 | 정답과 해설. 이 문항은 공개됨으로 닫힌다 |

### 9.4 진행 기록

- 진행 기록은 `practice/progress/progress.json` 이고 cresvoid 만 쓴다.
- 여러 명령을 동시에 실행해도 기록을 잃지 않도록 `practice/progress/` 의 잠금 파일로 잠근 뒤 최신 기록을 다시 읽어 고친다. 쓸 때는 임시 파일에 쓴 뒤 이름을 바꾼다.

### 9.5 작업 공간과 복습

- build 트랙은 트랙마다 작업 공간 하나를 쓴다. 기본 경로는 `practice/<트랙>/` 다.
- fix 트랙은 단계마다 작업 공간을 쓴다. 기본 경로는 `practice/<트랙>/<단계 디렉터리>/` 다.
- `cresvoid start` 에 `-dir` 로 다른 경로를 줄 수 있다. `-lang` 은 build 트랙 시작 코드의 언어를 고른다.
- `cresvoid start` 에 준 경로에 실행할 수 있는 `run.sh` 가 있으면 복사하지 않고 그 작업 공간을 고른다.
- 복습은 처음 통과하고 14일이 지난 뒤 처음과 다른 디렉터리에서 다시 통과했을 때만 기록한다.

### 9.6 초기화

- `cresvoid reset` 은 모든 트랙의 진행 기록을, `cresvoid reset <트랙>` 은 그 트랙의 기록을, `-stage N` 을 붙이면 그 단계의 기록만 지운다.
- 지우기 전에 지울 내용을 보여 주고 확인을 받는다. 표준 입력이 터미널이 아니면 `-yes` 가 있어야 지운다.
- 지우기 전에 `practice/progress/backups/progress-<시각>.json` 에 진행 기록 사본을 남긴다.
- 작업 공간은 지우지 않는다.

### 9.7 참조 풀이 보기

- `cresvoid solution <트랙> [-stage N]` 은 통과 여부와 상관없이 참조 풀이를 보여 준다. `-stage` 를 생략하면 아직 마치지 않은 첫 단계를 고르고 모두 마쳤으면 마지막 단계를 고른다.
- build 트랙은 `hidden/solution/` 의 Kotlin 소스를 파일마다 줄 번호와 함께 보여 준다. fix 트랙은 시작 코드와 참조 풀이의 차이(`diff -ruN -x build -x .DS_Store starter hidden/solution`)를 보여 준다.
- 참조 풀이 디렉터리 경로도 알려 준다.
- reading·code 트랙은 참조 풀이가 없다고 알리고 끝낸다.

## 10. 검증

`cresvoid validate <트랙>` 이 확인하는 항목이다.

1. 파일이 모두 있고 JSON 에 이 문서에 없는 필드가 없다. JSON 키는 영문 소문자 snake_case 이고 한 객체 안에서 겹치지 않는다. 파일에는 JSON 값이 하나만 있다. track.json 에는 title, kind, summary, stages 가 있고 단계마다 dir 과 title 이 있다. 단계 디렉터리에 quiz.json, tests.json, solution/, `*.main.kts` 가 있으면 `hidden/` 으로 옮기라고 알리고 실패한다.
2. 문서의 문단 번호가 겹치지 않는다. 모든 refs 가 문서나 코드에 있다. 모든 quote 가 refs 가운데 하나에 들어 있다. 이때 공백은 하나로 줄이고 백틱과 `**` 는 무시한다.
3. 문항 id 가 겹치지 않고 문항 모양이 4절의 종류별 규칙을 지킨다. input 이 있는 short 문항은 실행 결과가 정답과 같다.
4. build 트랙에서 단계 N 의 참조 풀이는 1~N 단계 테스트와 공개 API 검사를 모두 제한 시간 안에 통과한다. gen 테스트는 seed 1 과 2 로 실행한다. 기대값은 그 테스트가 속한 단계의 참조 풀이로 만든다. `expected` 가 없는 테스트는 같은 입력으로 두 번 실행해 같은 출력이 나와야 한다.
5. build 트랙의 시작 코드는 1단계 테스트에서 실패한다. N 이 2 이상이면 N−1 단계 참조 풀이는 N 단계 테스트 가운데 하나 이상에서 실패한다.
6. fix 트랙에서 단계마다 참조 풀이는 그 단계 테스트를 모두 제한 시간 안에 통과하고 시작 코드는 하나 이상에서 실패한다. 시작 코드와 참조 풀이 사이에 바뀐 줄 수를 보여 준다.
   `allowed-edits.txt` 가 있으면 참조 풀이의 수정 범위도 검사한다.
7. code 트랙에서 단계마다 `code/` 가 빌드되고 실행된다.

## 11. 작성 기준

### 11.1 build 트랙 스펙

- 독자는 경력 개발자다. 단계마다 1~3시간이 걸리는 난도로 쓴다.
- 개요, 배경 개념, 입출력 규칙, 명령 규칙, 오류 규칙, 예시, 검사 방식 순서로 쓴다.
- 테스트가 확인하는 규칙은 모두 번호 문단 안에 산문으로 쓴다. 예시는 규칙을 보여 줄 뿐 정의하지 않는다.
- 배경 개념은 설명하되 자료구조 선택 같은 구현 방법은 지시하지 않는다.
- 뒤 단계 스펙은 새 규칙만 설명한다. 뒤 단계는 앞 단계 명령의 출력을 바꾸지 않는다.

### 11.2 build·fix 트랙 테스트

- build 트랙은 단계마다 고정 테스트 10~14개와 gen 테스트 2~3개를 둔다. 마지막 테스트는 대규모 테스트다.
- fix 트랙은 단계마다 고정 테스트 6~10개를 둔다. 버그를 드러내는 테스트와 버그 근처의 올바른 동작을 지키는 회귀 테스트를 함께 둔다. gen 테스트는 선택이다.
- 첫 테스트는 가장 단순한 정상 동작이다. 뒤로 갈수록 규칙 조합과 경계 조건을 다룬다.
- 고정 테스트는 모두 `expected` 를 적는다. 기대값은 참조 풀이가 아니라 스펙에서 유도한다.
- 엔진은 통과하거나 실패한 테스트 이름을 화면에 보여 준다. 그래서 테스트 이름에 숨은 케이스의 조건이나 답을 담지 않는다. 엔진은 이 규칙을 검사하지 않는다.
- 숨은 케이스의 조건은 그 케이스의 입력에 일부러 넣은 특징이다. 경계가 놓인 자리, 겹치게 넣은 값, 특정 수치가 여기에 해당한다.
- refs 문단이 규칙으로 직접 정한 조건은 이름에 써도 된다. 테스트가 실패하면 refs 문단 번호와 quote 도 함께 나오므로 규칙을 담은 이름이 더 알려 주는 것은 없다. 예: `rounded-score-ties`, `near-same-token`.
- refs 문단에 없는 조건은 이름에 쓰지 않는다. 예를 들어 `tie-across-boundary` 는 동점 상품이 페이지 경계에 걸쳐 있다는 조건을 알려 준다. 조건을 이름에 쓸 수 없는 케이스는 `rain-boots-browse-to-end` 처럼 평범한 사용 상황으로 이름을 짓는다.
- 앞 단계 테스트에는 뒤 단계에서 뜻이 바뀌는 입력을 쓰지 않는다.
- fix 트랙 테스트는 구현 세부가 아니라 스펙의 동작만 확인한다. 같은 버그를 다른 방식으로 고쳐도 통과해야 한다.

### 11.3 build 트랙 문항

- 단계마다 5문항이다. choice 3개, short 2개를 둔다.
- 대충 읽으면 틀리는 세부 규칙을 겨냥한다. 오답 선지 가운데 하나 이상은 규칙 두 개를 엮어야 지울 수 있게 만든다.

### 11.4 reading 트랙 지문

- 비문학 지문이다. 기존 시험 지문이나 번역문을 옮기지 않고 새로 쓴다.
- 사실관계가 정확해야 한다. 문항을 푸는 데 필요한 정보는 지문이나 `<보기>` 에 모두 있어야 한다.
- 문항이 가리키는 구절 앞에는 ㉠, ㉡ 같은 표지를 붙인다.

### 11.5 reading 트랙 문항

- 단계마다 5~6문항이고 모두 choice 다. 선지는 5개, 정답은 1개다.
- `<보기>` 적용 문항을 하나 이상 둔다. `<보기>` 는 context 필드에 쓴다.
- 해설은 선지 다섯 개가 각각 왜 맞거나 틀리는지 쓴다.

### 11.6 code 트랙

- 한 단계는 `guide.md` 와 Kotlin 코드 150~400줄(파일 2~5개)이다.
- 코드는 실제 서비스에서 볼 법한 문제를 푼다. 장난감 예제, 뜻 없는 이름, 퍼즐을 위해 일부러 꼬은 코드를 쓰지 않는다.
- `guide.md` 는 코드가 놓인 맥락, 입력 형식, 문항이 가정하는 상황을 번호 문단으로 설명한다. 코드의 동작을 미리 풀어 주지 않는다.
- 단계마다 5~6문항이다. 실행 결과를 예측하는 short 문항을 2개 이상 둔다. 나머지는 동작 판단, 변경 영향 추론, 원인 찾기 choice 문항이다.
- 문항은 코드를 따라가며 상태를 추적해야 풀린다. Kotlin 언어 규칙이나 표준 라이브러리 동작에 기대는 문항은 그 동작을 실행으로 확인한다.

### 11.7 fix 트랙

- `spec.md` 는 제품 맥락, 의도한 동작 규칙, 버그 신고를 번호 문단으로 쓴다. 버그 신고에는 증상, 재현 입력, 기대한 결과와 실제 결과를 적는다. 원인은 적지 않는다.
- 버그는 실무에서 흔히 생기는 종류로 고른다. 경계값, 상태 공유, 시간대, 정밀도, 컬렉션 의미, 동시성, 지연 평가 같은 원인이 그 예다.
- 한 단계의 원인은 하나다. 증상은 여러 개일 수 있다. 수정은 몇 줄로 끝난다.
- 코드는 150~400줄(파일 2~5개)이고 버그 말고는 올바르게 동작한다.

### 11.8 코드 컨텐츠의 antislop 기준

code·fix 트랙 코드와 모든 참조 풀이에 적용한다. 기준은 `antislop` 과 `antislop-code` 스킬에서 가져왔다.

- 주석은 코드가 보여 주지 않는 이유, 제약, 비직관적인 동작만 한 줄로 쓴다. 장식 구분선, 코드를 다시 말하는 주석, 단계 번호 나열, 빈 라벨, 할 일이 없는 TODO, 이모지, 블록 끝 표시를 쓰지 않는다.
- 이름은 도메인의 말을 쓴다. `data`, `temp`, `foo`, `helper` 같은 이름을 쓰지 않는다.
- 버그 종류, 문항의 함정, 코드 구조처럼 컨텐츠의 모든 결정은 이유를 한 줄로 적을 수 있어야 한다. 이유는 제작 기록에 남긴다.
- 코드 동작에 대한 주장은 모두 실행으로 확인한다. 문항 정답, 해설, 버그 증상, 스펙 예시가 여기에 해당한다.
- 없는 API, 지어낸 라이브러리 동작, 출처 없는 수치를 쓰지 않는다.
- 전달하기 전에 PASS/FAIL 점검표를 증거와 함께 남긴다.

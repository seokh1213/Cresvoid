# 워크플로우 설계 원칙

스킬의 workflow.js 가 왜 이렇게 생겼는지 남긴다. Workflow 도구가 없는 에이전트(Codex 등)가 같은 절차를 손으로 실행하거나 실행기를 새로 만들 때, 도구가 바뀌어도 지킬 것과 바꿔도 되는 것을 이 문서로 가린다.

## 지킬 것

도구와 상관없이 지킨다.

- 만드는 에이전트와 검증하는 에이전트를 나눈다. 자기 결과를 검증하면 자기 착각을 잡기 어렵다(cresvoid-content 스킬의 '원칙' 절).
- 검증 에이전트는 정답, 참조 풀이, 숨은 테스트를 보지 않는다. 학습자가 받는 자료만으로 풀어 봐야 문서만으로 정답이 하나로 정해지는지 알 수 있다(품질 관문의 '정답 하나').
- 기대값은 서로 보지 않는 두 갈래가 따로 만든 뒤 맞춰 본다. build 트랙의 고정 테스트 기대값은 참조 풀이가 아니라 스펙에서 유도한다(D5). 두 갈래가 같은 실수를 할 가능성이 낮아서 교차 검증이 서로의 실수를 잡는다.
- 계산, 코드 동작, 라이브러리 동작은 실행으로 확인한다. coroutine-patterns 4단계의 `stateIn` 서술처럼 그럴듯하지만 틀린 서술을 학습자 검토가 실행으로 잡은 일이 있다(2026-10-11 작업 기록).
- 불일치는 스펙이나 지문을 기준으로 틀린 쪽을 고친다. 테스트나 문항을 지워서 불일치를 없애지 않는다.
- 고친 뒤에는 처음과 같은 방법으로 다시 검증한다. 다시 검증하지 못한 수정은 작업 기록과 handoff 에 남긴다.

## 스크립트로 둔 이유

- 단계 순서, 건너뛰기 조건, 동시 실행 수를 코드로 고정한다. 그래서 실행할 때마다 같은 절차를 거치고 검증 단계가 빠지지 않는다.
- 모의 실행기(`mock-workflow.mjs`)로 에이전트 없이 호출 순서, 동시 실행 수, 프롬프트에 섞인 `undefined` 를 검사할 수 있다.
- 결과는 schema 로 받는다. 다음 단계가 자유 텍스트를 해석하지 않아도 되게 하려는 것이다. 필수 필드는 다음 단계가 읽는 것만 둔다.
- 프롬프트는 args 만으로 만든다. 시각과 난수를 쓰지 않는 것은 Workflow 도구가 바뀌지 않은 호출의 결과를 캐시로 다시 쓰기 때문이다.
- JavaScript 인 것은 Claude Code 의 Workflow 도구가 JavaScript 만 받기 때문이다. 프로젝트의 다른 코드는 모두 Kotlin 이다.

## 바꿔도 되는 것

- 동시 실행 수: 지금의 2 는 사용자 규칙이다(D6). 사용자가 한도를 바꾸면 따른다. Kotlin 빌드가 겹치면 validate 가 느려지는 것도 함께 본다. code-reading 의 validate 는 다른 워크플로우와 CPU 를 나눠 쓰는 동안 16분 걸렸다(2026-10-11 작업 기록).
- 모호성 검토 횟수, 마지막 수정을 실행하는 조건, 프롬프트 문구: 비용과 결과를 보고 고친다. 고치면 모의 실행으로 확인하고 작업 기록에 이유를 남긴다.
- 실행 수단: Workflow 도구, 손으로 따라 하기(cresvoid-content 스킬의 '워크플로우 도구 없이 실행하기' 절), 실행기 가운데 무엇을 쓰든 '지킬 것' 을 지키면 된다.

## 멈춘 실행 이어 가기

- Workflow 도구의 캐시 재개(`resumeFromRunId`)는 쓰지 않는다. 캐시 키가 전체 호출 순서에 묶여 있어서 병렬 갈래가 있으면 끝난 agent 가 다시 실행된다(D7).
- 대신 끝난 호출의 결과를 기록에서 읽고 남은 단계만 실행한다. 멈춘 호출이 파일을 반쯤 남겼을 수 있다. 다시 실행하기 전에 그 호출이 맡은 파일을 확인한다.

## 실행기를 만들 때

workflow.js 를 그대로 실행하는 실행기는 아직 없다. 2026-10-12 에 사용자는 지금 만들지 말고 Codex 가 직접 쓸 때 만들게 하라고 했다("코덱스용으로 본인이 쓸때만들라고 철학문서를 남겨놓든지. 이거는 왜이렇게 했었다 정도로"). 실행기를 만드는 에이전트는 아래를 따른다.

- 출발점은 `mock-workflow.mjs` 다. workflow.js 가 기대하는 전역 이름(`args`, `agent`, `parallel`, `pipeline`, `phase`, `log`, `budget`)을 이미 채우고 있다. 가짜 결과를 돌려주는 `agent` 만 실제 에이전트 실행으로 바꾼다.
- `agent(prompt, opts)` 는 호출마다 새 에이전트를 실행한다. 앞 호출의 대화가 섞이면 블라인드 검증이 깨진다. Codex 라면 호출마다 `codex exec -C <cresvoid> -s workspace-write` 를 새 프로세스로 실행한다. Git 저장소 밖의 사본에서만 `--skip-git-repo-check` 를 붙인다. 프롬프트를 넘기는 방법(인자나 표준 입력)은 만들 때 `codex exec --help` 로 확인한다.
- `opts.schema` 가 있으면 그 schema 를 파일로 써서 `--output-schema` 로 넘긴다. `-o` 로 받은 마지막 메시지를 JSON 으로 읽어 돌려준다. schema 가 없으면 마지막 메시지 텍스트를 돌려준다.
- 에이전트가 끝내 실패하면 `null` 을 돌려준다. Workflow 도구도 끝내 실패한 agent 의 결과를 `null` 로 돌려준다. 결과가 schema 에 맞지 않으면 한 번 더 실행한다. 그래도 맞지 않으면 `null` 을 돌려준다. workflow.js 는 출제 agent 의 `null` 결과를 처리한다(모의 실행의 author-null 시나리오).
- `parallel` 은 모든 항목을 기다리고 실패한 항목은 `null` 로 둔다. `pipeline` 은 항목마다 단계를 차례로 실행하고 실패한 항목은 그 자리에서 `null` 이 된다. 둘 다 전체를 실패시키지 않는다. 모의 실행기와 같은 동작이다.
- 동시에 실행하는 에이전트는 2개를 넘기지 않는다(D6).
- 호출마다 label, 프롬프트, 결과를 실행 디렉터리에 남긴다. 멈췄다가 다시 시작할 때 이 기록으로 남은 호출을 찾는다.
- `Date.now`, `Math.random` 은 모의 실행기처럼 막는다.
- 실행기는 `content/skills/_shared/` 에 JavaScript 로 둔다. workflow.js 와 같은 예외이므로 `docs/agents.md` 의 '코드와 컨텐츠' 절에 더한다.
- 확인은 두 번 한다. 먼저 모의 실행과 같은 args 로 호출 순서가 같은지 확인한다. 그다음 작은 워크플로우 하나를 실제로 실행해 schema 결과와 만든 파일을 살핀다. 실제 실행에는 그 에이전트의 사용량이 든다.
- 만든 뒤에는 cresvoid-content 스킬의 '워크플로우 도구 없이 실행하기' 절과 `docs/agents.md` 의 '도구별 차이' 절을 고친다.

# 1단계: 경계와 문맥을 보존하는 청크

## 1. 개요

[1.1] rag 트랙은 문서를 작은 검색 단위로 나누고, 낱말과 벡터로 검색하고, 결과를 결합한 뒤 검색 품질을 평가하는 프로그램을 만든다. 실제 임베딩 모델이나 외부 서비스를 호출하지 않는다. 1단계는 문서 적재, 청크 설정, 청크 생성과 조회를 구현한다. 목표 작업 시간은 2시간 안팎이다.

## 2. 배경 개념

[2.1] 검색 증강 생성(RAG)은 질문과 관련된 자료를 찾아 생성 모델에 함께 주는 방식이다. 이 트랙은 자료를 찾는 부분까지만 다룬다. 문서 전체를 검색 단위로 쓰면 서로 다른 주제가 한 점수에 섞이고, 너무 작은 단위를 쓰면 그 문장이 무엇을 설명하는지 알기 어렵다. 청크는 이 사이에서 정하는 검색 단위다.

[2.2] 겹침은 앞 청크의 끝부분을 다음 청크에 다시 넣는 것이다. 경계 양쪽에 나뉜 정보를 함께 검색할 기회가 생기지만 같은 내용이 여러 결과로 나타날 수도 있다. 글자 수로 정확히 겹치는 방식과 문장 전체를 겹치는 방식은 실제 겹치는 길이가 다르다.

[2.3] 문장 경계를 지켜도 문서 제목이나 앞부분에만 있는 주어를 잃을 수 있다. 이 트랙은 제목을 각 청크 앞에 붙이는 결정적 문맥 규칙을 사용한다. Anthropic의 [Introducing Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)은 청크별 설명 문맥을 검색 전에 덧붙이는 접근을 설명한다. 여기서 구현하는 제목 접두는 그 아이디어를 단순화한 별도의 규칙이며 모델이 문맥을 작성하지 않는다.

[2.4] 사람이 세는 글자 수와 JVM 문자열의 길이는 다를 수 있다. 보충 평면 문자는 UTF-16 코드 단위 두 개로 표현된다. 이 트랙에서 글자와 위치는 유니코드 코드 포인트를 기준으로 센다. 결합 문자는 각각 센다. 정규화된 본문에서 위치 0은 첫 코드 포인트 앞이고, 구간 [s,e)는 s부터 e 직전까지다.

## 3. 입출력 규칙

[3.1] UTF-8 표준 입력을 EOF까지 한 줄씩 처리한다. 명령 하나는 한 줄이며 필드는 실제 탭(U+0009) 하나로 구분한다. 연속 탭과 마지막 탭이 만드는 빈 필드도 보존한다. 필드 내부의 탭과 줄바꿈, 이스케이프 문법은 없다. CRLF의 줄 끝 CR은 제거한다. 빈 줄은 무시한다. 명령 이름과 열거형은 대소문자를 구분한다.

[3.2] 정수 필드는 `0` 또는 `[1-9][0-9]*` 형식만 허용하며 각 규칙의 범위 안이어야 한다. 부호, 선행 0, 공백은 허용하지 않는다. 문서 id는 1 이상 1,000,000,000 이하 정수다. 이 문서에서 id 순서는 문자열 순서가 아닌 수 크기 순서다.

[3.3] 제목과 본문의 정규화는 ASCII 공백(U+0020)이 연속된 구간을 공백 하나로 줄이고 양 끝의 ASCII 공백을 지우는 것이다. 다른 유니코드 문자는 바꾸지 않는다. 입력 텍스트에는 탭·CR·LF 이외의 제어 문자도 없으며 잘못된 유니코드 인코딩도 없다. 텍스트 필드를 정규화하는 것은 문서 적재 때뿐이며 청크 조각을 따로 trim하지 않는다.

[3.4] 출력의 필드도 탭 하나로 나누고 행 끝에 줄바꿈을 쓴다. 정상 변경 명령은 명시한 응답 한 줄을 출력한다. 목록은 지정된 순서로 출력하며 빈 목록은 `(none)` 한 줄이다. 안내문과 로그는 표준 출력에 쓰지 않는다. 모든 명령 처리를 마치면 종료 코드 0으로 끝난다.

[3.5] 실행할 때 문서 집합은 비어 있고 설정은 `200,20,SENTENCE,TITLE`이다. 청크는 아직 생성되지 않은 상태다. 실행 사이에 상태를 저장하지 않는다.

## 4. 명령 규칙

[4.1] `DOC<TAB>id<TAB>title<TAB>body`는 문서를 추가하거나 같은 id의 문서를 통째로 대체하고 `OK`를 출력한다. 제목과 본문은 빈 필드도 허용한다. 정규화한 값으로 저장한다. 빈 본문은 제목이 있어도 청크를 만들지 않는다.

[4.2] `DEL<TAB>id`는 있는 문서를 삭제하고 `OK`를 출력한다. `CONFIG<TAB>size<TAB>overlap<TAB>mode<TAB>context`는 설정을 바꾸고 `OK`를 출력한다. size는 1~10,000, overlap은 0 이상 size 미만이다. mode는 `CHAR` 또는 `SENTENCE`, context는 `NONE` 또는 `TITLE`이다. size와 overlap은 제목 접두를 제외한 본문 구간의 길이에만 적용한다.

[4.3] 성공한 DOC·DEL·CONFIG는 기존 청크를 모두 폐기하고 미생성 상태로 만든다. DOC의 내용이나 CONFIG의 값이 이전과 같아도 폐기한다. 실패한 명령은 아무 상태도 바꾸지 않는다.

[4.4] 인자가 없는 `BUILD`는 현재 문서와 설정으로 모든 청크를 새로 생성하고 `OK<TAB>청크수`를 출력한다. 빈 문서 집합도 생성된 상태가 되며 청크 수는 0이다. BUILD를 반복해도 청크의 내용과 id는 같다.

[4.5] 청크 id는 `문서id:순번`이다. 순번은 문서마다 0부터 생성 순서대로 붙이며 선행 0을 붙이지 않는다. 청크의 기본 순서는 문서 id 오름차순, 같은 문서에서는 순번 오름차순이다. 이후 단계에서 청크 id로 동점을 정할 때도 이 순서를 쓴다.

[4.6] CHAR에서는 본문 길이를 n, 현재 시작 위치를 s라 할 때 끝 위치 e는 `min(s+size,n)`이다. 첫 s는 0이며 [s,e)를 청크로 만든다. e가 n이면 끝내고, 아니면 다음 s를 `e-overlap`으로 정한다. 빈 본문은 이 과정을 수행하지 않는다. 청크가 공백으로 시작하거나 끝나더라도 그 공백을 유지한다.

[4.7] SENTENCE의 문장 끝은 `.`, `?`, `!` 바로 뒤가 본문 끝이거나 ASCII 공백인 위치다. 연속 문장 부호에서는 이 조건을 만족하는 마지막 부호 뒤만 문장 끝이다. `v1.2`의 마침표나 `a!b`의 느낌표는 문장 끝이 아니다. 마지막 문장 끝 뒤에 내용이 남으면 그 내용도 마지막 문장이다. 문장 끝이 하나도 없으면 본문 전체가 한 문장이다. 문장 사이의 공백 한 글자는 어느 문장에도 속하지 않는다. 문장 끝 부호는 앞 문장에 포함된다.

[4.8] SENTENCE에서 문장 하나가 size보다 길면 문장 시작부터 size글자씩 잘라 마지막 조각만 짧을 수 있는 연속 조각으로 나눈다. 그 밖의 문장은 한 조각이다. 이렇게 얻은 모든 조각을 원래 위치 순으로 놓고, 조각 번호를 0부터 붙인다. 조각 사이의 원문 공백은 그대로 남아 있다.

[4.9] 첫 청크는 조각 0부터 시작한다. 시작 조각을 a라 하면 본문 구간 `[조각a의 시작, 조각b의 끝)` 길이가 size 이하인 가장 큰 b를 골라 이 구간을 청크로 만든다. 사이의 공백도 구간 길이에 포함한다. b가 마지막 조각이면 끝난다.

[4.10] 다음 청크의 시작은 a보다 크고 b 이하인 조각 j 가운데, `조각b의 끝-조각j의 시작 ≤ overlap`이면서 `조각(b+1)의 끝-조각j의 시작 ≤ size`인 가장 작은 j다. 그런 j가 없으면 b+1에서 시작한다. 이 규칙으로 문장 또는 긴 문장의 조각 전체만 겹치고 매 청크에 새 조각이 하나 이상 들어간다. overlap이 커도 같은 조각들만 반복하지 않으며, 공백을 포함해 조건을 만족하는 접미부가 없으면 겹침은 0이다.

[4.11] 청크의 본문 조각은 정규화된 원문 구간 그대로다. context가 TITLE이고 정규화한 제목이 비어 있지 않으면 검색용 텍스트는 `제목 + " | " + 본문 조각`이다. 나머지는 본문 조각만 쓴다. 접두의 공백과 세로줄은 문자 그대로이며 시작·끝 위치는 제목이 없는 원문 위치다.

[4.12] 인자가 없는 `CHUNKS`는 모든 청크를 기본 순서로 한 줄씩 `청크id<TAB>시작<TAB>끝<TAB>검색용텍스트`로 출력한다. 시작과 끝은 2.4의 위치다. 목록의 개수나 헤더는 따로 출력하지 않는다.

## 5. 오류 규칙

[5.1] 이 단계의 명령은 DOC·DEL·CONFIG·BUILD·CHUNKS다. 이 명령들의 필드 수가 정확히 맞지 않거나 필드가 정해진 형식·범위를 어기면 `ERR BAD_ARGUMENT`를 출력한다. CHUNKS처럼 인자가 없는 명령 뒤의 탭도 빈 인자 하나이므로 오류다. 제목과 본문에는 정수 필드 검증을 적용하지 않는다.

[5.2] 형식이 올바른 DEL의 id가 없으면 `ERR NOT_FOUND`를 출력한다. 형식이 올바른 CHUNKS에서 청크가 미생성 상태면 `ERR NOT_BUILT`를 출력한다. 오류 검사는 필드 수·값 검증을 먼저 하고 그 뒤 상태를 검사한다. 명령 하나는 오류 한 줄만 출력하고 다음 줄을 계속 처리한다.

[5.3] VEC·BM25·VECTOR·RRF·MMR·GROUP·QRY·REL·EVAL·EVALALL·COMPARE는 뒤 단계에서 정의할 예약 명령이다. 아직 정의하지 않은 예약 명령의 출력은 이 단계의 검사 대상이 아니다. 그 밖의 알 수 없는 명령은 인자와 관계없이 `ERR UNKNOWN_COMMAND`다. 뒤 단계는 앞 단계가 정의한 입력의 동작과 출력을 바꾸지 않는다.

## 6. 예시

[6.1] 코드 블록의 `> `는 입력 표시이며 실제 입력에 포함하지 않는다. 필드 사이는 실제 탭이다. 블록 하나마다 새 프로그램을 실행한다. 이 표기는 뒤 단계에서도 같다.

[6.2] CHAR에서는 네 글자가 겹친다. 마지막 청크를 만든 뒤에는 남은 접미부를 다시 출력하지 않는다.

```text
> CONFIG	6	4	CHAR	TITLE
OK
> DOC	2	 안내 	abcdefghij
OK
> BUILD
OK	3
> CHUNKS
2:0	0	6	안내 | abcdef
2:1	2	8	안내 | cdefgh
2:2	4	10	안내 | efghij
> CONFIG	6	6	CHAR	NONE
ERR BAD_ARGUMENT
> CHUNKS
2:0	0	6	안내 | abcdef
2:1	2	8	안내 | cdefgh
2:2	4	10	안내 | efghij
```

[6.3] 문장 세 개의 범위는 [0,3), [4,7), [8,11)이다. 가운데 문장을 통째로 겹치며 실제 겹침은 3글자다.

```text
> CONFIG	7	4	SENTENCE	NONE
OK
> DOC	1		aa.  bb! cc?
OK
> BUILD
OK	2
> CHUNKS
1:0	0	7	aa. bb!
1:1	4	11	bb! cc?
> DOC	1		abcdefgh?
OK
> CHUNKS
ERR NOT_BUILT
> BUILD
OK	2
> CHUNKS
1:0	0	7	abcdefg
1:1	7	9	h?
```

[6.4] 이모지는 코드 포인트 하나다. 빈 본문은 제목을 청크로 만들지 않는다.

```text
> CONFIG	2	0	CHAR	NONE
OK
> DOC	10		가😀나
OK
> DOC	9	제목만	
OK
> BUILD
OK	2
> CHUNKS
10:0	0	2	가😀
10:1	2	3	나
> DEL	7
ERR NOT_FOUND
```

## 7. 검사 방식

[7.1] 각 테스트는 새 프로세스에 입력 줄을 마지막 줄바꿈까지 표준 입력으로 보내고 닫는다. 종료 코드 0을 요구한다. 표준 출력은 행 끝의 공백·탭·CR과 마지막 빈 줄만 제거한 뒤 줄 수와 각 줄을 글자 그대로 비교한다. 줄 내부 탭, 위치와 청크 순서도 비교한다. 부가 출력은 실패다.

[7.2] 일반 테스트 제한 시간은 JVM 실행부터 10초이며 빌드 시간은 제외한다. 대규모 테스트 제한 시간은 20초다. 대규모 테스트는 문서 최대 10,000개, 정규화 전 제목·본문 합계 최대 2,000,000코드 포인트, 생성 청크 최대 50,000개와 명령 최대 20,000줄을 사용한다. 출력은 64MB 이하이며, 각 DOC의 제목은 최대 200글자, 본문은 최대 100,000글자다. 이 한계는 오류 입력이 아니라 모든 테스트가 지키는 자원 상한이다.

[7.3] 검사에는 빈 본문, 문서 대체·삭제, 재생성, 정확히 맞는 경계, 긴 문장, 문장 부호와 공백, 큰 겹침, 제목 접두, 한글·보충 평면 문자가 포함된다. 뒤 단계에서도 이 단계의 테스트를 다시 실행한다.

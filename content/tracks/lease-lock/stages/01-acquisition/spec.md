# 01. 획득 번호와 조건부 해제

## 1. 개요

[1.1] 같은 작업을 맡으려는 여러 클라이언트 사이에서 키별 배타 잠금을 관리하는 프로그램을 만든다. 이번 단계는 획득, 조회, 해제를 익히는 도입 단계다. 실제 서버나 병렬 스레드는 사용하지 않고 입력 줄의 순서로 요청의 도착 순서를 나타낸다. 목표 풀이 시간은 숙련 개발자 기준 30~60분이다. 다음 단계에서 만료와 갱신을 더해 사건 순서와 처리 효율을 함께 다룬다.

[1.2] 프로세스가 시작하면 잠금 저장소는 비어 있고 현재 시각은 0이다. 이번 단계에서는 시각이 변하지 않는다. TTL과 만료 시각은 처음부터 저장하고 출력하지만, 양수 TTL로 얻은 잠금은 시간이 흘러 자동으로 없어지지 않는다. 다음 단계에서 시각 이동과 만료를 더한다.

## 2. 배경 개념

[2.1] 배타 잠금은 어떤 키의 소유권을 동시에 하나의 획득에만 부여하는 약속이다. 키는 보호하려는 작업이나 자원을 나타내고, 클라이언트 이름은 요청을 보낸 주체를 나타낸다. 같은 클라이언트가 서로 다른 키의 잠금을 함께 보유할 수 있다. 이 과제에는 공유 잠금, 대기열, 자동 재시도가 없다.

[2.2] 클라이언트 이름과 획득 번호는 다르다. 클라이언트가 잠금을 해제한 뒤 다시 얻으면 이름은 같아도 소유권은 새로 생긴다. 이전 획득의 해제 요청이 뒤늦게 도착할 수 있으므로, 소유권을 바꾸는 요청은 이름 대신 획득 한 번을 식별하는 번호를 제시한다. 획득 번호는 비밀 인증정보가 아니며, 요청자의 신원을 검증하는 기능은 구현하지 않는다.

[2.3] 원자적 연산은 조건 검사와 상태 변경이 중간에 끊기지 않는 하나의 사건처럼 관찰된다는 뜻이다. 먼저 빈 키인지 읽고 나중에 무조건 쓰는 두 연산만으로는 경쟁하는 두 요청이 모두 성공하지 않는다고 보장할 수 없다. 이 과제의 저장소는 키가 없을 때만 레코드를 만드는 조건부 생성과 현재 레코드의 획득 번호가 요청 번호와 같을 때만 지우는 조건부 삭제를 각각 원자적 연산 하나로 보장한다. 조건이 거짓이면 저장소를 바꾸지 않는다.

[2.4] 저장 레코드는 키, 클라이언트 이름, 획득 번호, 만료 시각으로 구성된다. 조회는 현재 레코드 전체의 일관된 값을 반환한다. 원자성은 과제가 제공하는 저장소 모형의 보장이며, 학습자는 그 모형 위의 명령 처리를 메모리에서 구현한다. 특정 클래스명이나 공개 API는 요구하지 않으며 실제 저장소 연결, 스레드 동기화, 장애 복구는 검사하지 않는다.

[2.5] lease는 정해진 시각까지만 유지되는 소유권이다. TTL은 획득 시각부터 소유권을 유지할 기간이고 만료 시각은 그 둘을 더한 값이다. 이번 단계에서도 이 값을 기록하되 시각은 0에 고정한다. 잠금 서비스가 소유권을 관리한다는 사실만으로 외부 저장소에 늦게 도착한 쓰기까지 차단되지는 않는다. 외부 쓰기와 펜싱 토큰 검사는 이 트랙의 이번 두 단계 범위 밖이다.

[2.6] 배경 자료는 [etcd 3.6 concurrency API](https://etcd.io/docs/v3.6/dev-guide/api_concurrency_reference_v3/)의 lease와 소유권 키, [Chubby 논문](https://research.google/pubs/the-chubby-lock-service-for-loosely-coupled-distributed-systems/)의 잠금 세대다. 여기서 사용하는 명령, 전역 획득 번호, 원자적 저장 연산, 가상 시각은 과제가 정한 별도 모형이다. 실제 제품의 API나 재획득 동작을 그대로 구현하지 않는다.

## 3. 입출력 규칙

[3.1] 표준 입력을 EOF까지 줄 단위로 읽는다. 앞뒤의 ASCII 공백과 탭을 제거하고 나머지를 하나 이상의 ASCII 공백 또는 탭으로 구분한 토큰으로 읽는다. 빈 줄과 공백·탭만 있는 줄은 무시하고 출력하지 않는다. 명령과 이름은 대소문자를 구분한다. 주석 문법은 없다.

[3.2] 명령은 `ACQUIRE <key> <client> <ttl>`, `RELEASE <key> <acquisition_id>`, `STATUS <key>`다. 꺾쇠괄호 안은 인자 자리이며 실제 입력에 괄호를 쓰지 않는다. 명령 토큰까지 포함한 토큰 수는 각각 4개, 3개, 2개여야 한다.

[3.3] 키와 클라이언트 이름은 ASCII 영문자로 시작하고 그 뒤에는 ASCII 영문자, 숫자, 밑줄, 하이픈만 올 수 있다. 전체 길이는 1~32자다. 이름 사이에 정규화나 별칭 처리는 없다.

[3.4] 숫자 토큰은 하나 이상의 ASCII 십진 숫자로 구성하며 맨 앞에 마이너스 한 개를 붙일 수 있다. 수학적 값은 부호 있는 64비트 정수 범위 안이어야 한다. 앞자리 0은 허용하고 `+`, 소수점, 지수 표기는 허용하지 않는다. TTL은 1 이상 1,000,000,000,000 이하여야 한다. 요청 획득 번호는 1 이상 9,223,372,036,854,775,807 이하여야 한다. 범위 안이지만 발급된 적 없는 양수 획득 번호도 유효한 요청 인자다.

[3.5] 무시하는 줄을 제외한 각 입력 줄마다 결과를 정확히 한 줄 출력한다. 출력 토큰은 ASCII 공백 한 개로 구분하고, 모든 숫자는 앞자리 0이나 `+`가 없는 십진수로 출력한다. 안내문, 프롬프트, 디버그 출력은 표준 출력에 쓰지 않는다. 입력이 비어 있으면 출력도 없다.

## 4. 명령 규칙

[4.1] 획득 번호는 한 프로세스의 모든 키와 클라이언트가 공유한다. 첫 성공에 1을 부여하고 이후 획득 성공마다 정확히 1씩 증가한다. 실패한 획득, 조회, 해제, 잘못된 입력은 번호를 소비하지 않는다. 키가 비거나 모든 잠금이 없어져도 번호를 초기화하거나 재사용하지 않는다. 입력 크기 제한상 발급 번호가 300,000을 넘는 경우는 없다.

[4.2] 유효한 `ACQUIRE <key> <client> <ttl>`에서 키가 비어 있으면 조건부 생성으로 새 레코드를 저장한다. 새 획득 번호를 부여하고 만료 시각을 현재 시각 더하기 TTL로 정한 뒤 `ACQUIRED <acquisition_id> <expires_at>`을 출력한다. 이번 단계에서는 현재 시각이 0이므로 만료 시각은 TTL과 같다.

[4.3] 유효한 ACQUIRE에서 키가 이미 차 있으면 `BUSY <acquisition_id> <client> <expires_at>`을 출력한다. 출력하는 값은 현재 소유권의 값이다. 요청 클라이언트가 현재 클라이언트와 같아도 BUSY다. TTL을 바꾸거나 보유 횟수를 늘리거나 미래의 획득을 예약하지 않는다.

[4.4] 유효한 `RELEASE <key> <acquisition_id>`는 해당 키의 현재 획득 번호가 요청 번호와 같을 때만 조건부 삭제에 성공하고 `RELEASED`를 출력한다. 키가 비어 있거나 번호가 다르면 `DENIED`를 출력하고 상태를 보존한다. 같은 키와 번호로 해제를 반복해도 두 번째 요청은 DENIED다. 다른 키에서 발급된 번호로 해제할 수 없다.

[4.5] 유효한 `STATUS <key>`는 키가 비어 있으면 `FREE`, 차 있으면 `HELD <acquisition_id> <client> <expires_at>`을 출력한다. 조회는 어떤 상태도 바꾸지 않는다.

[4.6] 입력의 각 명령은 앞선 명령의 처리가 모두 끝난 상태에서 시작한다. 같은 키에 대한 경쟁, 해제 뒤 재획득, 늦은 해제는 이 순서로 판정한다. 입력에 없는 요청이나 사건을 임의로 추가하지 않는다.

## 5. 오류 규칙

[5.1] 알 수 없는 명령, 잘못된 토큰 수, 이름 형식 위반, 숫자 형식 또는 64비트 범위 위반, TTL 또는 요청 획득 번호의 허용 범위 위반은 모두 `ERROR`를 출력한다. 입력 줄 전체의 형식과 인자 범위를 검사한 뒤 명령을 수행한다. 따라서 이미 차 있는 키의 ACQUIRE라도 TTL이 잘못되면 BUSY가 아니라 ERROR다.

[5.2] ERROR인 줄은 저장소, 획득 번호 발급 상태, 현재 시각을 전혀 바꾸지 않는다. 오류 뒤에도 다음 줄을 계속 처리하고 EOF에서 정상 종료한다. BUSY와 DENIED는 유효한 명령의 업무 결과이며 입력 오류가 아니다.

## 6. 예시

[6.1] 다음은 두 클라이언트의 경쟁과 같은 클라이언트의 재획득을 나타낸다. 첫 번째와 두 번째 획득은 이름이 같아도 다른 소유권이다. 뒤늦게 도착한 번호 1의 해제는 번호 2를 지우지 않는다.

```text
입력
STATUS invoice
ACQUIRE invoice workerA 10
ACQUIRE invoice workerB 20
RELEASE invoice 1
ACQUIRE invoice workerA 7
RELEASE invoice 1
STATUS invoice
ACQUIRE report workerB 4
RELEASE report 2
STATUS report

출력
FREE
ACQUIRED 1 10
BUSY 1 workerA 10
RELEASED
ACQUIRED 2 7
DENIED
HELD 2 workerA 7
ACQUIRED 3 4
DENIED
HELD 3 workerB 4
```

[6.2] 다음은 입력 오류의 상태 보존과 번호를 소비하지 않는 실패를 나타낸다. 양수 99는 발급 이력과 관계없이 유효한 요청 번호이므로 ERROR가 아닌 DENIED를 낸다.

```text
입력
ACQUIRE task agent 0
ACQUIRE task agent 0005
ACQUIRE task other -1
RELEASE task 99
STATUS task
RELEASE task 0001
ACQUIRE task agent 1000000000000

출력
ERROR
ACQUIRED 1 5
ERROR
DENIED
HELD 1 agent 5
RELEASED
ACQUIRED 2 1000000000000
```

## 7. 검사 방식

[7.1] Kotlin 표준 라이브러리와 JDK 21만 사용한다. 검사기는 테스트마다 새 프로세스를 실행하고 명령을 줄바꿈으로 이어 마지막 줄 뒤에도 줄바꿈을 붙여 표준 입력에 전달한 뒤 입력을 닫는다. 파일이나 실제 시계, 외부 서비스에 의존하지 않는다. 시작 코드의 main은 `TODO()`로 비어 있으며 학습자가 명령 처리를 구현한다.

[7.2] 결과는 표준 출력의 줄별 문자열로 비교한다. 각 줄 끝의 공백·탭·CR과 출력 마지막의 빈 줄은 제거하지만, 줄 안의 공백과 대소문자는 그대로 비교한다. 종료 코드는 0이어야 하며 표준 출력은 64MiB 이하여야 한다. 실행 제한은 테스트 하나당 15초이며 컴파일 시간은 포함하지 않는다.

[7.3] 테스트 하나의 입력은 무시하지 않는 줄 300,000개 이하, 전체 32MiB 이하이며, 각 줄은 줄바꿈을 제외하고 ASCII 문자 256개 이하로 구성된다. 서로 다른 키와 동시에 보유하는 잠금은 각각 최대 120,000개다. 오류 입력도 이 크기 제한 안에 있다. TTL과 만료 시각은 32비트 정수 범위를 넘을 수 있다.

[7.4] 고정 테스트 10~14개와 생성 테스트 2~3개로 경쟁, 재획득, 전역 번호, 잘못된 해제, 오류 뒤 상태 보존, 수치 경계를 확인한다. 마지막 생성 테스트는 서로 다른 키의 획득 120,000회, 그 키들의 조회 120,000회, 그중 60,000개 키의 해제를 합친 총 300,000개 명령이다. 키마다 모든 레코드를 순회하는 처리로는 제한 시간을 맞추기 어려운 규모다. 자료구조와 파일 구성은 학습자가 정한다.

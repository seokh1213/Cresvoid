[1] 보안 프로그램은 실행 코드를 바꾸지 않고도 탐지 조건을 갱신한다. CrowdStrike의 Windows 센서는 이런 조건을 채널 파일로 받아 콘텐츠 해석기에서 처리했다. 템플릿 유형은 탐지에 사용할 입력 필드의 틀이며 템플릿 인스턴스는 그 틀에 맞춰 작성한 구체적인 일치 조건이다. 유형은 센서 코드에 포함되어 배포되지만 인스턴스는 나중에 콘텐츠로 공급될 수 있다. 해석기는 센서가 수집한 입력값을 인스턴스의 조건과 대조한다. 따라서 콘텐츠가 실행 코드가 아니라는 사실만으로 기존 코드가 그 조건을 안전하게 처리한다고 보장할 수는 없다. 2024년 7월 19일 발생한 장애는 이 두 배포 경로가 만나는 지점에서 시작되었다.

[2] 프로세스 간 통신을 다루는 IPC 템플릿 유형의 정의에는 입력 필드가 21개로 적혀 있었으나 센서의 연동 코드는 해석기에 값 20개만 전달했다. 정의를 따라 만든 인스턴스는 21개 필드의 조건을 담을 수 있었으므로 콘텐츠의 형식과 실행 중 공급되는 입력 사이에 불일치가 있었다. 그러나 시험에 쓰거나 앞서 배포한 인스턴스들은 마지막 필드에 와일드카드 조건을 사용했다. 와일드카드는 특정 값과의 비교 없이 일치를 허용하여 그 위치의 입력값을 읽을 필요가 없는 조건이었다. 이 경로에서는 실제로 값 하나가 빠져 있어도 장애가 드러나지 않았다. 와일드카드가 입력을 보충하거나 불일치를 해소한 것은 아니며 나중에 구체적인 조건을 쓰는 순간에는 이전과 다른 읽기 동작이 필요했다.

[3] 불일치는 센서 출시 시험과 템플릿 유형의 부하 시험, 초기 인스턴스의 운영 배포를 거치면서도 발견되지 않았다. 개발 중에는 수동 시험과 자동 시험이 모두 수행되었고 자동 시험은 보안 관련 데이터의 흐름과 탐지 알림이 적절한지 확인했다. 그러나 그 시험에 쓰인 인스턴스들은 마지막 필드에 와일드카드를 두었다. 부하 시험도 시험용 인스턴스로 여러 운영체제와 작업 부하에서 수행되었다. 환경과 부하를 달리하는 일은 조건이 달라져 새로 요구되는 필드 읽기를 대신 시험해 주지 않았다. ㉠유형이 시험을 통과했다는 결과는 그때 사용한 인스턴스의 조건 아래에서 얻은 결과이며 이후 작성될 모든 인스턴스의 안전성을 뜻하지 않았다. 시험 단계가 많다는 사실만으로 각 단계가 서로 다른 실패 조건을 살폈다고 볼 수는 없었다.

[4] 7월 19일 배포된 추가 인스턴스 중 하나는 21번째 필드에 처음으로 와일드카드가 아닌 조건을 넣었다. 배포 전 콘텐츠 검증기는 이를 평가했으나 정의대로 입력 21개가 공급될 것이라고 전제하여 통과시켰다. 검사가 없었던 것이 아니라 검사에서 가정한 입력과 센서가 공급한 입력이 달랐던 것이다. 이 인스턴스를 담은 새 채널 파일 291을 받은 센서는 다음 IPC 알림을 처리할 때 마지막 조건을 평가하려 했다. 해석기는 실제 입력 배열의 끝을 넘어 21번째 값을 읽으려 했고 시스템이 멈췄다. 새 콘텐츠는 기존 코드의 잠재된 범위 밖 읽기를 드러냈다. 정의와 실제 입력의 불일치, 이를 드러내지 않은 시험 조건, 실행 중 경계 검사의 부재가 연결되어 장애가 된 것이다.

[5] 2024년 8월 6일 원인 분석 보고서에 실린 방지책들은 이 연결의 서로 다른 지점을 겨냥한다. ㉡센서를 빌드할 때 수행하는 필드 수 검증은 정의된 입력 수와 코드가 제공하는 입력 수의 불일치를 찾아낸다. 실제 입력도 21개를 공급하도록 코드가 수정되었다. 이에 비해 ㉢실행 시 배열 범위 검사는 이미 전달된 입력을 읽을 때 배열 밖 접근을 막는다. 입력 배열의 크기와 콘텐츠가 기대하는 입력 수를 대조하는 검사도 추가되었다. 빌드 단계에서는 불일치가 있는 센서의 제작을 막고 실행 단계에서는 잘못된 요구가 도달하더라도 위험한 접근을 차단한다. 따라서 범위 밖 읽기를 막았다는 사실만으로 원래 의도한 탐지 판단까지 정상적으로 수행된다고 단정할 수는 없다.

[6] 시험과 콘텐츠 검증의 보완 역시 구별된다. 각 필드에 와일드카드가 아닌 조건을 쓰는 자동 시험은 종전에 값 읽기를 피했던 자리도 실제로 시험하도록 한다. 콘텐츠 검증기에는 조건이 참조하는 필드가 해석기에 공급되는 입력 범위를 넘지 않는지 확인하는 검사를 추가하기로 했다. 이는 정의가 정확하리라는 전제만으로 인스턴스를 승인하던 빈틈을 메운다. 채널 파일 291의 21번째 필드에는 와일드카드만 허용하도록 검증기를 바꾸기도 했다. 이 제한은 입력 20개인 센서의 위험한 읽기를 피하지만 입력 자체를 늘리는 조치는 아니다. 유형과 최초 인스턴스를 함께 시험한 것으로 끝내지 않고 새 인스턴스마다 해석기 안에서 시험하도록 절차를 보완했다. 유형의 시험 범위를 넓히는 일과 이후 개별 콘텐츠를 확인하는 일은 어느 한쪽으로 대체되지 않는다.

[7] 보고서는 새 인스턴스마다 단계적으로 배포하도록 절차를 보완했다고 밝혔다. 일부 센서에 먼저 적용하는 카나리 시험을 통과한 인스턴스를 더 넓은 배포 집단으로 차례로 확대하고 단계마다 관찰 시간을 두어 이상이 있으면 되돌리는 방식이다. 이는 앞선 검증을 빠져나간 결함의 영향을 제한한다. 관찰 중 결함이 드러날 조건이 나타나지 않았다면 확대 전 이상이 없었다는 사실만으로 결함의 부재를 증명할 수는 없다. 고객이 콘텐츠의 배포 위치와 시점을 고르는 기능도 제공되었다. 외부 보안 업체 두 곳은 센서 코드의 보안과 품질 검토를 시작했다. 개발부터 배포까지의 품질 절차에 대한 독립 검토도 진행되었다. 입력 관계의 검증, 실행 중 접근의 보호, 시험 조건의 확장, 배포 범위의 통제는 목적이 다르며 독립 검토도 이 방어들을 대신하는 안전 보증으로 읽어서는 안 된다.

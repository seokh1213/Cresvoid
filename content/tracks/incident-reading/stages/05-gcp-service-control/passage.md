[1] 여러 지역에 나뉜 서비스는 한 지역의 실패를 다른 지역과 격리할 수 있다. 그러나 실행 위치가 분산돼 있다는 사실만으로 실패 조건까지 독립적인 것은 아니다. Google Cloud의 Service Control은 API 요청에 권한과 할당량 정책 등의 검사를 적용하는 지역 서비스다. 각 지역의 저장소에서 정책 정보를 읽지만 할당량을 전 세계에서 관리하기 위해 그 메타데이터는 거의 즉시 전역으로 복제됐다. 따라서 지역마다 별도 실행 파일이 동작해도 같은 정책 데이터가 같은 결함을 자극하면 여러 지역이 함께 실패할 수 있다. 이때 코드를 배포하는 순서와 코드를 작동시키는 데이터가 퍼지는 순서를 따로 살펴야 한다.

[2] 2025년 5월 29일에는 할당량 정책 검사를 추가하는 코드가 들어갔다. 지역별 단계 배포를 거쳤지만 새 경로는 특정 정책 변경이 있어야 실행됐으므로 그 과정에서 한 번도 실행되지 않았다. 이 코드에는 적절한 오류 처리와 기능 플래그 보호가 없었다. ㉠기능 플래그는 배포된 코드의 실행 여부를 별도로 제어하여 내부 프로젝트부터 지역과 프로젝트별로 기능을 점진적으로 활성화하는 장치다. 플래그를 둔다고 결함이 제거되지는 않지만 기본값을 비활성으로 두면 코드가 도착했다는 이유만으로 모든 곳에서 새 기능이 활성화되는 것을 막는다. 단계 배포에서 이상이 없었다는 관찰은 그때 실행된 동작의 관찰이지, 특정 입력을 기다리는 경로의 안전성을 입증한 것은 아니다.

[3] 6월 12일 오전 10시 45분 무렵, 의도하지 않은 빈 필드를 포함한 정책 변경이 지역 Spanner 테이블에 들어갔다. 시각은 미국 태평양 일광 절약 시간인 PDT 기준이다. 이 변경은 몇 초 만에 전 세계로 복제됐고 각 지역에서 새 검사 경로를 실행시켰다. 빈 필드 때문에 널 포인터를 역참조한 실행 파일들은 충돌과 재시작을 반복했다. 코드가 들어간 시점과 장애 시점이 약 2주 떨어진 까닭은 정책 변경이 뒤늦게 실행 조건을 충족했기 때문이다. 입력 검증으로 빈 필드를 걸러내는 것과 ㉡정책 데이터를 검증할 시간을 두고 점진적으로 전파하는 것은 구별된다. 전자는 잘못된 값의 진입을 막고, 후자는 검증을 빠져나온 값이 있더라도 전 지역으로 번지기 전에 문제를 발견할 기회를 둔다.

[4] 대응팀은 충돌 시작 후 2분 안에 대응을 시작했고 10분 안에 원인을 찾았다. 해당 정책 처리 경로를 비활성화하는 비상 장치는 원래 마련돼 있었으며, 이를 배포할 준비가 된 것은 장애 시작 약 25분 뒤였다. 40분 안에 배포를 마치자 작은 지역부터 회복되기 시작했다. 이 장치는 장애 뒤 경로를 중단하는 수단이며, 배포된 기능을 미리 제한된 대상부터 활성화하는 플래그 보호와는 운용 시점이 다르다. 원인 식별은 어느 경로를 비활성화할지 정해 주지만, 그 조치의 전파와 정상 처리 능력의 회복까지 즉시 끝내 주지는 않는다. 경로 비활성화의 완료와 모든 지역의 회복을 같은 사건으로 보면 이후의 지연을 설명할 수 없다.

[5] 큰 지역인 us-central1에서는 재시작한 작업들이 의존하던 Spanner 테이블에 몰려 하위 기반 시설을 과부하시켰다. Service Control에는 이를 피할 적절한 무작위 지수 백오프가 없었다. 작업 생성 속도를 제한하고 트래픽을 다중 지역 데이터베이스로 전환해 부하를 줄였다. 이 지역의 Service Control과 API 처리가 회복되기까지 장애 시작부터 약 2시간 40분이 걸렸으며 일부 개별 제품의 회복은 더 늦었다. 이처럼 회복하려는 동작 자체가 회복에 필요한 자원을 압박하는 현상을 군집 효과라 한다. ㉢지터를 둔 지수 백오프는 설정한 한도 안에서 재시도 차수에 따라 대기 범위를 지수적으로 넓히고 각 작업의 대기 시간을 무작위로 정한다. 같은 간격으로 쉬는 고정 백오프는 빈도를 줄여도 작업들의 시점이 같으면 집중을 남긴다. 지터는 집중을 완화하지만 특정 순간에 요청이 겹치지 않거나 저장소 한도를 넘지 않는다는 보장은 아니다.

[6] 재발 방지책도 끊으려는 고리에 따라 다르다. Google은 기능을 분리하여 ㉣검사가 실패하더라도 API 요청을 계속 처리하는 fail open 구조를 추진한다고 밝혔다. 이는 검사 실패가 요청 처리 전체의 중단으로 이어지는 결합을 줄이는 조치다. fail open으로 빈 필드를 걸러내거나 정상적인 검사 결과를 얻는 것은 아니다. 중요 바이너리 변경의 플래그 보호와 기본 비활성화, 정적 분석과 시험 강화는 결함의 노출을 제한하고 오류 처리를 점검한다. 전역 복제 데이터의 점진적 전파는 노출 범위가 한꺼번에 커지는 것을 막으며 무작위 지수 백오프 점검은 회복 중 부하 집중을 겨냥한다. 어느 한 조치를 갖췄다는 사실을 나머지 고리의 안전성으로 바꿔 읽을 수 없다.

[7] 장애는 관측과 공지에도 영향을 미쳤다. Cloud Service Health 기반 시설도 멈춰 첫 사건 공지는 충돌 시작 약 한 시간 뒤에 게시됐고, 일부 고객의 Google Cloud 기반 감시도 실패했다. 내부에서 원인을 파악했다는 것과 고객이 장애를 알아 대응할 수 있다는 것은 별개의 조건이었다. 이에 Google은 자동·수동 외부 공지를 개선하고 자사 클라우드와 주요 감시 제품이 중단돼도 감시와 공지 기반 시설을 운영하겠다고 밝혔다. 이런 대책은 빈 필드의 발생이나 재시작 집중을 직접 차단하지 않는다. 다만 장애를 줄이는 수단이 실패한 때에도 고객에게 판단 근거를 전달한다. 최초 실패의 방지, 실패 범위의 제한, 회복 부하의 제어, 장애 정보의 전달은 서로 보완하지만 서로의 성공을 대신 증명하지는 않는다.

[1] Elasticsearch 색인은 여러 샤드로 나뉠 수 있고 샤드 하나는 Lucene 색인 하나다. Lucene 색인은 여러 세그먼트와 그 목록을 기록한 커밋 지점으로 이루어진다. 세그먼트는 단어마다 그 단어가 든 문서를 적어 둔 역색인을 담고 한 번 쓰이면 바뀌지 않는다. 그래서 새 문서는 기존 세그먼트에 끼워 넣을 수 없어 새 세그먼트에 담긴다. 검색할 때는 열려 있는 세그먼트마다 따로 찾은 결과를 합친다.

[2] 색인한 문서는 먼저 메모리의 색인 버퍼에 모이며 이 상태에서는 검색되지 않는다. ㉠refresh 는 버퍼에 모인 문서를 새 세그먼트로 쓰고 그 세그먼트를 열어 직전 refresh 뒤에 처리된 연산을 모두 검색에 보이게 하는 작업이다. 검색은 가장 최근의 refresh 때까지 열린 세그먼트만 읽으므로 색인 요청에 성공 응답이 왔더라도 그 연산을 처리한 뒤 refresh 가 한 번 일어나기 전까지는 문서가 검색되지 않는다. refresh 는 정해진 주기마다 일어나고 요청에 refresh=true 를 붙이거나 refresh API 를 호출할 때도 곧바로 일어난다.

[3] refresh 가 Lucene 커밋보다 가벼운 것은 디스크 기록을 기다리지 않기 때문이다. Elasticsearch 와 디스크 사이에는 운영체제의 파일 시스템 캐시가 있다. 새 세그먼트는 이 캐시에 먼저 쓰이고 디스크에는 나중에 기록된다. 캐시에 든 파일은 디스크에 기록되기 전에도 여느 파일처럼 열어 읽을 수 있다. 반면 커밋은 버퍼에 남은 문서까지 세그먼트로 쓰고 세그먼트 파일을 fsync 로 디스크에 기록한 다음 새 커밋 지점을 남기는 비싼 작업이어서 연산마다 할 수 없다. fsync 는 캐시에 있는 파일 내용이 디스크에 기록될 때까지 기다리게 하는 호출이다. 프로세스가 끝나거나 하드웨어가 고장 나면 Lucene 은 마지막 커밋 뒤의 변경을 모두 버린다. refresh 로 열린 세그먼트도 커밋에 들기 전이면 함께 사라진다. 커밋이 세그먼트로 쓴 문서라도 refresh 를 거쳐야 검색된다. refresh 에도 비용은 있다. 자주 할수록 작은 세그먼트가 늘어 검색할 세그먼트와 나중에 이들을 합칠 일이 함께 많아진다.

[4] refresh 주기는 index.refresh_interval 로 정하고 Elastic Stack 의 기본값은 1초다. 문서가 색인된 즉시 검색되지는 않고 refresh 를 거쳐야 하므로 Elasticsearch 의 검색을 거의 실시간 검색이라 부른다. 주기를 따로 지정하지 않은 색인에서는 검색 요청도 get 요청(ID 로 문서를 가져오는 요청)도 일정 시간(index.search.idle.after, 기본 30초) 동안 받지 않은 샤드가 검색 유휴 상태가 되어 주기적인 refresh 를 건너뛴다. 이런 샤드에 검색이 왔을 때 건너뛴 refresh 가 밀려 있으면 검색이 닿은 그 샤드만 검색 과정에서 refresh 를 하고 나서 결과를 낸다. 검색을 받은 샤드는 검색 유휴 상태에서 벗어나므로 다시 그 상태가 되기 전까지는 주기적인 refresh 를 건너뛰지 않는다. 이 생략은 검색 없이 대량으로 색인할 때 드는 refresh 비용을 줄이려는 장치다. 주기를 명시해 두면 기본값과 같은 1초라도 refresh 를 건너뛰지 않는다.

[5] 세그먼트가 바뀌지 않으므로 삭제도 문서를 세그먼트에서 지우지 못한다. 삭제는 그 문서에 삭제 표시를 남길 뿐이고 검색은 표시된 문서를 결과에서 제외한다. 이 표시도 다음 refresh 때에야 검색에 반영되므로 그 전까지는 지운 문서가 계속 검색된다. 문서를 갱신할 때도 옛 판은 지워지지 않고 삭제 표시가 붙은 채 남으며 새 판이 따로 색인된다. 병합은 Elasticsearch 가 뒤에서 작은 세그먼트 여럿을 큰 세그먼트로 다시 쓰는 작업이고 이때 표시된 문서를 걸러 내 그 문서가 차지하던 디스크 공간을 회수한다. 병합이 진행되는 동안에는 임시 디스크 공간이 더 든다.

[6] 커밋을 자주 할 수 없으므로 샤드의 사본마다 translog 라는 연산 기록을 둔다. 색인과 삭제 연산은 모두 Lucene 이 처리한 뒤 성공 응답이 나가기 전에 translog 에 쓰인다. translog 에는 아직 커밋에 들지 않은 연산이 담긴다. 장애 뒤 샤드를 복구할 때는 마지막 커밋에 들지 못한 연산을 translog 에서 다시 실행해 되찾는다. 다만 translog 도 fsync 로 디스크에 동기화된 부분만 남는다. 마지막 동기화 뒤에 쓰인 내용은 장애가 나면 사라진다.

[7] 동기화 시점은 index.translog.durability 가 정한다. 기본값인 request 에서는 요청마다 주 샤드와 할당된 모든 복제본에서 translog 를 동기화한 뒤에 성공을 알리므로 성공 응답을 받은 쓰기는 하드웨어 장애 뒤에도 모두 남는다. 동기화를 요청 단위로 하므로 bulk 요청은 그 안의 연산을 모두 처리한 뒤 한꺼번에 동기화한다. async 에서는 쓰기가 있든 없든 index.translog.sync_interval 마다 뒤에서 동기화하고 성공은 동기화를 기다리지 않고 알린다. 요청마다 디스크를 기다리지 않는 대신 장애가 나면 마지막 동기화 뒤에 성공을 알린 쓰기를 잃는다. 이 설정은 세그먼트를 열지 않으므로 문서가 검색되는 시점을 바꾸지 않는다. refresh 역시 translog 를 동기화하지 않으므로 장애 뒤에 남는 범위를 바꾸지 않는다.

[8] ㉡flush 는 Lucene 커밋을 하고 translog 의 새 세대를 시작하는 작업이다. flush 전에 처리된 연산은 모두 커밋되어 Lucene 색인에 영구히 남으므로 더는 translog 로 지킬 필요가 없다. 필요 없어진 translog 세대 파일은 지워지고 그만큼 디스크 공간이 회수된다. translog 가 커지면 복구 때 다시 실행할 연산이 늘어 복구가 오래 걸리기 때문에 Elasticsearch 는 translog 크기가 한도(index.translog.flush_threshold_size)에 이르면 스스로 flush 한다. flush API 로 직접 요청할 수도 있지만 그럴 일은 드물다. 다시 시작한 샤드는 마지막 커밋 지점의 세그먼트들을 연 다음 translog 에 남은 그 뒤의 연산을 다시 실행한다.

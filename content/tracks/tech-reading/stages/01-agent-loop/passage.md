[1] 검색, 도구, 기억을 덧붙인 LLM 을 증강 LLM 이라 한다. 증강 LLM 은 검색어를 스스로 만들고 쓸 도구를 고르며 남겨 둘 정보를 정한다. 그렇다고 모델이 도구를 직접 실행하지는 않는다. 모델은 어떤 도구를 어떤 입력으로 실행해 달라는 구조화된 도구 호출을 낼 뿐이고 실행은 모델 밖의 실행기가 맡는다. Claude API 를 예로 들면 실행기는 응답이 도구 호출 때문에 멈췄을 때 그 호출대로 도구를 실행해 결과를 덧붙여 다시 요청한다. 모델이 답을 마쳐 응답이 멈췄으면 순환을 끝낸다. API 는 앞선 요청을 기억하지 않으므로 실행기는 요청할 때마다 지금까지의 대화 전체를 다시 보낸다.

[2] LLM 과 도구를 엮은 시스템은 워크플로와 에이전트로 나뉜다. 워크플로는 미리 정한 코드 경로대로 LLM 과 도구를 조율하고 에이전트에서는 LLM 이 과정과 도구 사용을 스스로 정한다. 워크플로의 패턴 가운데 프롬프트 연쇄는 일을 정해진 하위 단계로 나누어 각 단계의 LLM 이 앞 단계의 출력을 처리하게 하며 단계 사이에 코드로 검사를 넣을 수 있다. 범주가 뚜렷하고 분류가 정확할 때 쓰는 라우팅은 입력을 분류해 전문화된 처리로 보내므로 한 종류의 입력에 맞춘 최적화가 다른 입력의 성능을 해치지 않는다. ㉠병렬화는 작업을 미리 정한 독립 하위 작업으로 나누거나 같은 작업을 여러 번 시켜 동시에 실행하고 결과를 코드로 모은다. 하위 작업을 미리 정할 수 없을 때는 오케스트레이터-워커를 쓴다. 중앙 LLM 이 입력을 보고 하위 작업을 정해 워커 LLM 에게 맡기고 결과를 종합하는 방식이다.

[3] 단계를 정할 수 있는 일에는 예측 가능하고 일관된 워크플로가 맞다. 에이전트는 필요한 단계 수를 예측하기 어렵고 경로를 고정할 수 없는 열린 문제에 맞다. 에이전트는 매 단계 도구 실행 결과처럼 환경에서 얻은 실제 결과로 진행 상황을 판단하며 순환한다. 스스로 여러 차례 순환하는 만큼 비용과 지연이 크고 오류가 쌓일 수 있으므로 격리된 환경에서 시험하고 최대 반복 횟수 같은 중지 조건을 둔다. 가장 단순한 해법에서 출발해 필요할 때만 복잡도를 늘린다.

[4] 도구 정의에는 이름, 설명, 그리고 받을 입력의 모양을 JSON 스키마로 적은 입력 스키마가 들어간다. API 는 도구 정의로 특별한 시스템 프롬프트를 만들어 모델에 넘긴다. 모델은 도구의 구현을 보지 못하고 정의와 돌아온 결과만 보므로 도구 성능을 가장 크게 좌우하는 것은 도구가 하는 일, 써야 할 때와 쓰지 말아야 할 때, 인자마다의 뜻과 한계를 밝힌 자세한 설명이다. 결과에도 다음 판단에 필요한 정보만 담는다. 입력 스키마는 모델이 입력을 만들 때 따르는 기준일 뿐이어서 따로 강제하지 않으면 모델이 필수 인자를 빠뜨린 호출을 낼 수도 있다.

[5] 응답 속 도구 호출은 식별자, 도구 이름, 입력을 담은 도구 사용 블록으로 나타난다. 실행기는 다음 사용자 메시지에 결과 블록을 담아 보낸다. 결과 블록은 자신이 답하는 호출의 식별자와 결과 내용을 담고 실행이 실패했으면 오류 표시를 단다. 결과 내용은 비워 둘 수도 있다. 도구 사용 블록마다 같은 식별자를 단 결과 블록이 짝으로 있어야 한다. 결과를 담은 메시지는 도구 사용 메시지 바로 다음에 와야 하며 그 안에서 결과 블록은 모든 텍스트보다 앞에 놓여야 한다. 모델의 응답에서는 할 일을 밝히는 텍스트가 도구 사용 블록 앞에 오기도 하지만 결과를 담는 쪽에는 이런 여지가 없다. 이 규약을 어긴 요청은 API 가 오류로 돌려보내므로 모델은 그 메시지를 읽지 못한다.

[6] 한 응답에 도구 사용 블록이 여러 개 담기는 ㉡병렬 도구 호출에서 API 는 실행 순서를 정하지 않는다. 독립된 읽기 작업은 동시에 실행해 지연을 줄이고 부수 효과가 있거나 상태를 공유하거나 순서에 기대는 작업은 차례로 실행하는 편이 낫다. 어느 쪽이든 결과는 모두 다음 사용자 메시지 하나에 담는다. 도구가 실패했거나 입력이 잘못되었으면 실행기는 오류 표시를 단 결과에 무엇이 잘못되었고 무엇을 해 볼 수 있는지를 적는다. 모델은 이를 읽고 입력을 고쳐 다시 호출하거나 안내대로 다시 시도하고 그럴 수 없으면 사용자에게 사정을 알린다. 차례로 실행하다 앞 호출이 실패해 뒤 호출을 건너뛰었다면 그 호출에도 오류 결과를 돌려주어 모델이 다음 차례에 다시 판단하게 한다. ㉢실패를 빈 결과로 감추면 메시지는 규약에 맞아도 모델은 도구가 성공했지만 돌려줄 것이 없었던 경우와 도구가 실패한 경우를 구분하지 못한다.

[7] 순환이 이어질수록 도구 결과가 대화에 쌓이고 요청마다 실리는 토큰이 늘어난다. 토큰이 늘면 모델이 컨텍스트 속 정보를 정확히 떠올리는 능력이 떨어진다. 이 현상은 모든 모델에서 나타나며 어느 길이에서 갑자기 무너지기보다 점점 나빠진다. 트랜스포머에서는 토큰마다 다른 토큰과 관계를 맺어 쌍 관계의 수가 토큰 수의 제곱에 비례하므로 길이가 늘수록 이 관계를 고루 포착하기 어렵다. 게다가 모델은 짧은 시퀀스를 주로 보며 학습해 긴 범위의 의존 관계를 덜 겪었다. 그러므로 컨텍스트는 한정된 주의 예산으로 다룬다. 데이터를 미리 다 싣지 않고 파일 경로나 링크 같은 가벼운 참조만 들고 있다가 필요할 때 도구로 불러오는 방법이 그 예다. 컴팩션은 한도에 가까워진 대화를 요약하고 그 요약에서 새 컨텍스트를 시작하는 기법이다. 너무 많이 버리면 나중에야 중요성이 드러나는 맥락을 잃으므로 요약 프롬프트는 먼저 빠짐없이 담게 다듬고 그다음 군더더기를 줄인다. 요약보다 가볍고 안전한 방법으로는 이미 처리한 오래된 도구 결과의 내용을 지웠다는 표시로 바꾸는 것이 있다.

[8] 도구 결과에는 웹 페이지나 받은 메일처럼 개발자가 통제하지 못하는 내용이 들어오곤 한다. 그 안에 지시를 심어 모델을 조종하는 공격이 간접 프롬프트 주입이다. 이때 사용자는 믿을 수 있고 위험은 모델이 사용자를 대신해 읽는 제3자 내용에서 온다. 방어는 신뢰 경계를 긋는 데서 시작한다. 모델은 도구 결과 속 지시를 의심하도록 훈련되었으므로 신뢰할 수 없는 내용은 도구 결과 안에만 두고 시스템 프롬프트나 사용자 텍스트로 옮기지 않는다. 개발자가 따로 내리는 지시는 결과 블록 뒤에 사용자 텍스트로 둔다. 도구 결과에 섞으면 같은 까닭으로 무시되거나 주입으로 의심받을 수 있기 때문이다. 경계를 지켜도 모델의 판별은 완전하지 않으므로 권한은 꼭 필요한 만큼만 주고 송금이나 외부 발송처럼 되돌리기 어려운 행동은 실행 전에 사람이 확인하게 한다. 두 장치는 주입이 성공해도 피해를 줄인다.

[1] 디렉터리 테이블은 분산 저장소의 디렉터리 하나를 파티션 하나로 삼고 그 아래 파일의 행을 모두 테이블의 행으로 본다. 테이블의 상태가 곧 디렉터리 목록이므로 질의를 계획하려면 읽을 파티션마다 디렉터리 목록을 받아야 한다. 여러 파티션에 걸친 변경도 디렉터리마다 따로 반영되므로 한 번에 커밋되지 않는다. 파티션 값은 테이블에 열로 드러나 있어 쓰는 쪽이 직접 넣어야 하므로 틀린 값이 들어가도 걸러지지 않는다. 질의도 그 열에 조건을 따로 걸어야 파일을 건너뛴다. 테이블 포맷인 Apache Iceberg 는 테이블에 속한 파일을 디렉터리 단위로 다루지 않고 메타데이터에 하나씩 적어 이 문제들을 푼다.

[2] 테이블의 상태는 메타데이터 파일에 있다. 상태를 바꾸는 커밋마다 새 메타데이터 파일이 테이블의 새 판이 된다. 메타데이터 파일은 스키마, 파티션 설정, 속성, 스냅숏 목록과 그 가운데 현재 스냅숏이 무엇인지를 담는다. 스냅숏은 어느 시점에 테이블에 속한 데이터 파일 전체를 나타내며 매니페스트 목록 하나를 가리킨다. 매니페스트 목록은 매니페스트마다 담긴 파티션 값의 범위를 요약해 두어 읽을 필요 없는 매니페스트를 건너뛰게 한다. 매니페스트에는 데이터 파일마다 경로, 파티션 값, 열별 값의 하한과 상한 같은 통계가 적혀 있어 데이터 파일 단위로도 건너뛸 수 있다. 매니페스트 하나는 여러 파티션의 파일을 담을 수 있지만 한 파티션 설정으로 쓴 파일만 담는다. 이 계층의 파일은 한 번 쓰면 고치지 않으며 바뀌지 않은 매니페스트는 다음 스냅숏의 매니페스트 목록에도 그대로 들어간다.

[3] 쓰는 쪽은 새 데이터 파일을 먼저 쓰고 그 파일을 적은 매니페스트, 매니페스트 목록, 새 메타데이터 파일을 차례로 쓴다. 메타스토어 같은 곳에 둔 포인터가 옛 메타데이터 파일을 가리키는 동안 이 파일들은 테이블에 속하지 않는다. 커밋은 쓰는 쪽이 출발점으로 삼은 기준 판에서 새 메타데이터 파일로 이 포인터를 바꾸는 한 번의 원자적 교체다. 그래서 여러 파티션에 걸친 변경도 모두 보이거나 하나도 보이지 않는다. 읽는 쪽은 테이블을 불러온 때 현재였던 스냅숏을 기준으로 읽으며 새로 불러오기 전에는 그 뒤의 커밋을 보지 않고 잠금도 잡지 않는다. 교체는 포인터가 아직 기준 판을 가리킬 때만 성공하므로 새 판은 언제나 바로 앞 판을 기준으로 한다. 판들이 한 줄로 이어지므로 동시에 들어온 쓰기가 덮여 사라지지 않는다. 이것이 직렬화 격리의 바탕이다.

[4] 쓰는 쪽은 기준 판이 커밋 전에 바뀌지 않으리라 낙관하고 새 메타데이터를 만든다. 같은 판을 기준으로 한 두 커밋 가운데 하나만 교체에 성공하며 실패한 쪽은 새 현재 판을 기준으로 다시 시도한다. 재시도는 작업을 처음부터 되풀이하지 않고 메타데이터 변경만 새 판에 다시 적용한다. 이미 쓴 데이터 파일은 다시 쓰지 않으며 매니페스트 목록과 메타데이터 파일은 시도할 때마다 새로 쓴다. 다만 다시 적용하기 전에 작업이 기댄 조건이 새 판에서도 맞는지 확인한다. 파일을 더하기만 하는 추가는 확인할 것이 없어 늘 다시 적용된다. 파일 여러 개를 같은 행을 담은 새 파일 하나로 바꾸는 압축은 바꿀 파일이 모두 테이블에 남아 있어야 한다. 다른 커밋이 그 가운데 하나를 테이블에서 제거했다면 새 파일이 제거된 행을 되살리게 되므로 압축은 실패한다. 무엇을 확인할지는 쓰는 쪽이 고르며 그 선택이 보장되는 격리 수준을 정한다.

[5] 파티션 설정은 원본 열의 값에 변환을 적용해 파티션 값을 만든다. 변환은 값을 그대로 두거나 해시값으로 버킷을 정하거나 날짜나 시각을 연, 월, 일, 시 단위로 묶는 식이다. 이렇게 얻은 값은 메타데이터에 적힐 뿐 테이블의 열이 아니어서 숨은 파티셔닝이라 한다. 질의는 데이터 열에 술어를 걸고 계획할 때 이 술어를 파티션 값에 거는 술어로 바꾼다. 맞는 행이 있을 수 있는 파티션을 빠뜨리지 않도록 넓게 바꾸므로 고른 파일에는 맞지 않는 행이 섞일 수 있다. 파티션 설정을 바꾸면 이미 쓴 파일은 옛 설정의 매니페스트에 그대로 남고 새 파일만 새 설정으로 쓰인다. 술어는 현재 설정과 상관없이 각 매니페스트를 쓸 때의 설정에 맞춰 바꾸므로 테이블을 새로 만들거나 질의를 고치지 않아도 두 방식의 파일을 모두 걸러 낼 수 있다.

[6] 스키마의 열마다 테이블 안에서 겹치지 않는 필드 ID 가 있고 데이터 파일에도 열마다 이 ID 가 적힌다. 읽는 쪽은 파일의 열을 이름이나 순서가 아니라 ID 로 고른다. 열 이름을 바꾸면 ID 는 그대로이므로 옛 파일의 그 열이 새 이름으로 읽히고 순서를 바꿔도 마찬가지다. 새 열은 한 번도 배정된 적 없는 ID 를 받으므로 옛 파일에서는 열을 더할 때 정한 기본값으로, 기본값이 없으면 null 로 채워진다. 지운 열과 같은 이름으로 열을 다시 더해도 옛 파일에 남은 지운 열의 값은 읽히지 않는다. 열을 이름으로 고르는 포맷은 이때 지운 열을 되살린다. 스키마를 바꿔도 데이터 파일은 다시 쓰지 않는다. 파티션 설정과 매니페스트의 열 통계도 열을 ID 로 가리킨다.

[7] 데이터 파일을 고치지 않고 몇 행만 지울 때는 지울 행을 적은 삭제 파일을 더한다. ㉠위치 삭제는 데이터 파일 경로와 그 파일 안의 행 위치로 행을 가리킨다. 지울 행이 어느 파일의 몇 번째 행인지 찾아야 쓸 수 있지만 읽을 때는 그 위치의 행만 제외하면 된다. ㉡동등 삭제는 id = 5 처럼 열 값으로 행을 가리키며 열을 필드 ID 로 적는다. 행을 찾지 않고도 쓸 수 있지만 읽는 쪽은 적용 대상 파일의 행마다 값을 맞춰 봐야 한다.

[8] 커밋에 성공한 스냅숏에는 앞선 스냅숏보다 큰 순서 번호가 붙는다. 스냅숏이 더한 파일은 그 번호를 이어받는다. 압축처럼 옛 행을 옮겨 담은 파일에는 더 작은 번호를 따로 적을 수도 있다. 쓰는 쪽은 커밋을 시도할 때 번호를 받아 두지만 재시도하면 번호를 새로 받는다. 이어받을 번호는 매니페스트에 비워 두고 읽을 때 매니페스트 목록에 적힌 번호로 채우므로 번호가 바뀌어도 새 파일을 적은 매니페스트는 다시 쓸 필요가 없다. 삭제 파일은 원칙적으로 같은 파티션에서 자기보다 번호가 작은 데이터 파일에만 적용된다. 그래서 동등 삭제는 같은 커밋이나 그 뒤의 커밋이 새로 더한 행을 값이 같아도 지우지 않는다. 예외는 둘이다. 위치 삭제는 번호가 같은 파일에도 적용되어 같은 커밋에서 더한 행을 지울 수 있다. 파티션을 나누지 않는 설정으로 저장한 동등 삭제는 파티션을 가리지 않고 번호가 더 작은 모든 데이터 파일에 적용된다.

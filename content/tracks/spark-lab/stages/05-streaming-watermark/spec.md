# 워터마크와 늦은 이벤트

[1] 이 단계는 워터마크와 재호출을 관찰하는 입문 실험이다. 같은 파일 입력을 append와 update 출력 모드로 실행하고, 각 묶음을 넣기 전에 출력 창과 개수를 예측해라. 시작 코드의 관찰 결과를 합격 불변식과 비교한 뒤 `src/main/kotlin/lab/Pipeline.kt`의 워터마크 설정과 배치 출판을 고쳐라. 나머지 서비스·체크포인트·실패 주입·빌드 파일은 바꾸지 마라. 결과를 완전히 소비하는 코드는 서비스가 제공하므로 구현 과제는 지연 한도와 배치별 중복 출판 제어다. Spark를 흉내 낸 집계나 입력별 정답 상수로 대체하지 마라.

[2] 실행 환경은 기존 spark 묶음의 Spark SQL 4.3.0, JDK 21, Kotlin이다. `.lab-libs`는 spark이고 `build.sh`는 `build/app.jar`를 만든다. `run.sh`는 PORT 환경 변수의 포트를 호스트 127.0.0.1에 공개한다. 두 스크립트를 실행 가능하게 유지해라. SparkSession은 local[2], UTC, 셔플 파티션 2개, UI 비활성화로 고정한다. 실험기는 고정 실행 이미지의 앱 한 개를 띄우고 준비를 확인하며 마지막에 제거한다. 새 라이브러리나 외부 부하 도구를 쓰지 마라.

[3] 공개 HTTP 계약은 다음과 같다. GET /health는 준비 뒤 200이다. POST /open의 본문은 append 또는 update이며 이전 실험을 지우고 독립 입력·체크포인트·출력 디렉터리를 만든다. POST /batch의 본문은 쉼표로 구분한 이벤트 분 정수다. 정수의 범위는 0부터 1440까지이고 기준 시각은 2024-01-01T00:00:00Z다. 예를 들어 12는 00:12 UTC다. 각 요청은 JSON 파일 하나를 입력 디렉터리에 원자적으로 이동한 뒤 AvailableNow 쿼리가 끝날 때까지 기다려 200을 반환한다. 같은 쿼리의 재실행은 같은 체크포인트를 쓴다. 쿼리는 eventTime 열에 워터마크를 적용한 뒤 10분 텀블링 창으로 count 집계한다. 창은 시작을 포함하고 끝을 제외한다.

[4] POST /fail은 /batch와 같은 입력을 받되 처음으로 비어 있지 않은 foreachBatch 결과를 출판한 직후 예외를 던져 503을 반환한다. POST /restart는 새 파일 없이 같은 출력 모드·입력·체크포인트로 쿼리를 다시 시작하고 끝나면 200을 반환한다. 실패한 배치를 재호출해도 출판은 한 번만 반영되어야 한다. 이 단계의 재시작은 HTTP 프로세스 재기동이 아닌 StreamingQuery 재시작이다. 출력과 batchId를 같은 원자적 파일 이동으로 확정해라. 결과를 소비하기 전에 재호출을 건너뛰면 안 된다.

[5] /batch, /fail, /restart 응답과 GET /snapshot은 줄 형식의 누적 관찰값이다. WATERMARK 뒤에는 마지막 완료 쿼리 진행 보고의 워터마크를 기준 시각부터 센 분으로 적는다. 초기값은 -1이며 최초 실패 응답에서는 아직 완료 쿼리의 값이 없다. DROPPED 뒤에는 완료 쿼리의 stateOperators.numRowsDroppedByWatermark 합계를 누적한 값을 적는다. ATTEMPT batchId는 비어 있는 배치를 포함한 실제 foreachBatch 호출 순서다. ROW batchId 창시작분 count는 출판된 결과 행이다. update의 ROW는 최종값 덮어쓰기 화면이 아니라 변경 이력이다. 따라서 같은 창의 2, 3, 4는 서로 다른 배치의 정당한 출력이다. 행 순서는 판정하지 않는다.

[6] 지연 한도와 창 크기는 모두 10분이다. 엔진이 관찰한 최대 이벤트 시각에서 지연 한도를 뺀 값이 워터마크를 전진시킨다. 현재 입력 묶음의 최대 시각을 이용해 같은 묶음의 이전 이벤트를 미리 버리지 마라. AvailableNow는 필요한 무입력 배치까지 처리한 뒤 끝나므로 각 성공 응답의 관찰에는 그 정리 배치도 포함한다. append는 정리된 창의 최종값만 한 번 출력하고 update는 그 배치에서 달라진 창의 현재값을 출력한다. 워터마크보다 오래된 이벤트가 일반적으로 항상 버려진다고 외우지 마라. 아래 개수는 이 파일 소스·창 집계·트리거에서 실행으로 확인할 불변식이다.

[7] window-sequence의 입력 묶음은 순서대로 1,4,12 / 8,16 / 31 / 3,14,26,34 / 51이다. 이 순서를 append와 update 각각 새 세션에서 실행해라. 각 응답 뒤 워터마크는 2, 6, 21, 24, 41분이어야 한다. 처음 두 묶음 뒤 append 출력은 비어 있어야 한다. 셋째 묶음 뒤 창 0의 3개와 창 10의 2개가 출판되어야 한다. 넷째 묶음 뒤 append 출력은 추가되지 않아야 한다. 다섯째 묶음 뒤 창 20의 1개와 창 30의 2개가 추가되어야 하며 창 50은 아직 출력되지 않아야 한다.

[8] update의 묶음별 추가 출력은 각각 (창 0,2개)와 (창 10,1개) / (창 0,3개)와 (창 10,2개) / (창 30,1개) / (창 20,1개)와 (창 30,2개) / (창 50,1개)다. 두 모드 모두 DROPPED 누적값은 0,0,0,2,2여야 한다. 넷째 묶음의 3분과 14분 이벤트가 정리된 창에 들어가려는 경우와 26분 이벤트가 남아 있는 창에 들어가는 경우를 구별해라. 실패 주입 없는 실행에서 같은 batchId의 콜백을 두 번 기록하면 안 된다.

[9] recovery-sequence는 update 세션에서 /fail에 2,7을 보내고 /restart를 호출한다. 실패 응답에 창 0의 2개가 이미 한 번 출판되어 있어야 하며 재시작 뒤에도 같은 행은 한 번이어야 한다. 이어 /batch에 8,14를 보내면 창 0의 3개와 창 10의 1개가 추가된다. 다시 /fail에 9,17을 보내고 /restart를 호출하면 창 0의 4개와 창 10의 2개가 한 번씩 추가되어야 한다. 이때 누적 출력은 5행이고 워터마크는 순서대로 재시작 뒤 -3, 다음 정상 입력 뒤 4, 두 번째 재시작 뒤 7이다. DROPPED는 계속 0이다. 서로 다른 두 실패 배치의 batchId가 각각 정확히 두 번 호출되어야 한다. 추가 /restart는 출력 행을 바꾸면 안 된다. 모든 재시작에서 같은 배치의 출판 중복과 다른 배치의 정당한 갱신을 함께 확인해라.

[10] 부하는 공통 load.main.kts의 개방형 요청 스케줄로 보낸다. 인과 순서가 필요한 입력 묶음마다 이전 쿼리가 끝난 뒤 별도 스케줄을 시작하고 그 스케줄의 0ms에 요청 하나를 예정한다. 동시에 여러 파일을 넣지 않는다. 이 실험은 처리량 경쟁이 아닌 이벤트 순서 실험이다. 준비 한도는 150초, 요청별 한도는 150초, 시나리오 한도는 600초다. 지연 시간은 합격 기준으로 쓰지 않는다. 각 시나리오를 3회 반복해라. 시간 초과나 서비스 실행 실패는 불변식 실패가 아닌 실험 오류다.

[11] 판정 지표는 http_errors, output_errors, watermark_errors, dropped_errors, replay_errors의 다섯 개다. 각각 HTTP 상태 불일치 횟수, 관찰 시점별 출력 다중집합 불일치 횟수, 워터마크 불일치 횟수, 폐기 행 수 불일치 횟수, 재호출 조건 불일치 횟수다. 다섯 판정 지표가 모두 0이어야 통과한다. 각 관찰 시점의 누적 출력 전체를 비교하므로 조기 출력, 누락, 중복을 함께 잡는다. 진단 지표 first_output_observation은 첫 출력 불일치 관찰 번호, first_expected_rows와 first_actual_rows는 그때의 기대·실제 누적 ROW 행 수다. 출력 불일치가 없으면 세 진단 지표는 모두 0이다. 행 수가 같아도 창이나 count가 다르면 출력 불일치다. 관찰 번호는 시나리오마다 1부터 세며 window-sequence는 append의 다섯 응답 뒤 update의 다섯 응답 순서다. recovery-sequence는 [9]의 실패·재시작·정상 입력·실패·재시작·추가 재시작의 여섯 응답 순서다. /open은 관찰 번호에 세지 않는다. 실험기는 표준 출력에 METRIC 행만 내며 종료 코드 0은 통과, 1은 불변식 실패, 2는 실험 오류다.

[11.1] 수동으로 원인을 좁히려면 run.sh로 서버를 띄우고 POST /open에 해당 모드를 보낸 뒤 [7] 또는 [9]의 요청을 한 번씩 보내라. 요청마다 GET /snapshot을 호출해 ROW와 ATTEMPT를 보관하고 first_output_observation이 가리키는 응답까지 비교해라. ROW는 순서를 무시하되 같은 행의 반복 횟수는 세라. 재시작 전후 같은 batchId의 ROW가 늘었는지, 실패 batchId의 ATTEMPT가 두 번인지 따로 확인해라. window-sequence의 update를 재현할 때는 새 /open으로 초기화해라. 관찰을 마치면 서버를 종료해라.

[11.2] DROPPED는 원시 입력 이벤트 폐기 수가 아니라 상태 연산자가 보고한 행 수다. 창 집계 전에 같은 창의 입력이 부분 집계될 수 있으므로 늦은 원시 이벤트 수와 같다고 일반화하지 마라. 이 구분은 새 update 세션에 31을 보낸 뒤 1,2,3을 보내 관찰해라. 뒤 묶음의 세 이벤트는 모두 같은 닫힌 창에 속하지만 이 실행 환경에서 DROPPED 증가분은 1이고 ROW는 추가되지 않는다.

[12] 근거는 Spark 4.3.0의 [Structured Streaming API 문서](https://spark.apache.org/docs/4.3.0/streaming/apis-on-dataframes-and-datasets.html)다. Handling Late Data and Watermarking, Conditions for watermarking to clean aggregation state, Semantic Guarantees of Aggregation with Watermarking, Output Modes, Triggers, Using Foreach and ForeachBatch 절을 읽어라. 파일의 원자적 배치, 집계 전 withWatermark, 한 방향의 지연 데이터 보장, AvailableNow의 무입력 배치, foreachBatch의 최소 한 번의 쓰기와 batchId 중복 제거가 이 실험의 API 근거다. 이 실험의 단일 로컬 파일 출판은 장애 창을 제한한 모델이며 여러 외부 저장소에 걸친 트랜잭션 보장을 뜻하지 않는다.

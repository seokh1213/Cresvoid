# 03. 정산 파일 대조

## 1. 개요

[1.1] 대행사의 정산 파일과 로컬에서 성공 확정한 결제·환불을 대조한다. 누락, 금액 차이, 통화 차이, 중복을 분류하고 통화별 총계를 보고한다. 차이를 발견해도 원장이나 요청 상태를 자동으로 고치지 않는다. 예상 구현 시간은 2~3시간이다. 앞 두 단계 명령과 출력 계약을 유지한다.

[1.2] 정산 파일은 이 실행의 전체 결제·환불 범위를 대상으로 하는 명세다. 기간, 가맹점, 수수료, 지급 지연, 환율과 부분 파일 병합은 다루지 않는다. 파일마다 독립적으로 대조하며 서로 다른 파일의 행을 합치지 않는다.

## 2. 배경 개념

[2.1] 결제 응답과 로컬 원장이 각각 옳아 보여도 대행사가 보낸 최종 명세와 일치하는지는 따로 확인해야 한다. 이 작업을 정산 대조(reconciliation)라고 한다. 계정 간 돈의 보존을 확인하는 시산과 달리, 정산 대조는 서로 다른 시스템이 같은 사건을 같은 내용으로 기록했는지 확인한다. 원장 분개 합이 0이라는 사실만으로 외부 기록과의 일치를 보장할 수 없다.

[2.2] 총액만 비교하면 서로 상쇄되는 누락이나 중복을 놓칠 수 있다. 요청별 식별자로 짝을 찾고 통화와 금액을 확인해야 한다. 환불은 원결제를 지우는 사건이 아니라 별도 요청이다. 정산에서는 결제를 양수, 환불을 음수로 놓아 순액을 계산하지만, 원장 분개 항목의 금액은 앞 단계처럼 양수로 유지한다.

[2.3] 외부 파일의 중복 행을 임의로 하나 고르면 진짜 기록이 무엇인지 알 수 없어진다. 불일치 분류와 통화별 순액은 서로 다른 관찰값이다. 분류에서는 중복으로만 보고하더라도 외부 순액에는 들어온 행을 모두 포함해야 파일이 실제로 주장하는 금액을 보존할 수 있다. 이 과제의 구체적인 분류 우선순위는 아래에서 정한다.

## 3. 입출력 규칙

[3.1] `IMPORT <파일ID> <행수>` 다음의 정확히 행수만큼의 물리적 입력 줄을 CSV 데이터로 읽는다. 파일ID는 앞 단계 계정 ID와 같은 문법이고 별도 이름 공간을 가진다. 행수는 0~100,000이다. CSV 줄에는 공백, 빈 줄, 헤더, 따옴표, 이스케이프가 없고 각 줄은 `<요청키>,<통화>,<부호있는금액>` 세 필드다. 이 데이터 줄은 명령으로 해석하지 않는다. 데이터 줄을 모두 읽은 뒤 다음 명령을 처리한다.

[3.2] 요청키와 통화는 앞 단계 문법을 따른다. 금액은 -1,000,000,000,000 이상 1,000,000,000,000 이하의 정수이며 잘못된 명세를 보고할 수 있도록 0도 허용한다. 존재하지 않는 요청키, 다른 통화와 중복된 요청키도 입력으로 허용한다. CSV 문법, 행수와 실제 줄 수는 올바르게 주어진다.

[3.3] 이 단계에서도 표준 입력 EOF까지 명령을 처리하며 앞 단계의 금액 합 범위를 따른다. CSV 줄을 제외한 빈 명령 줄은 무시한다. 추가된 `RECONCILE`의 응답만 여러 줄이며, 보고서의 필드 순서와 정렬 순서는 출력 계약의 일부다.

## 4. 명령 규칙

### 파일 가져오기

[4.1] `IMPORT`는 주어진 행 전체를 입력 순서대로 보존하고 `OK IMPORT <파일ID>`를 출력한다. 파일은 가져온 뒤 변경하거나 삭제할 수 없다. 가져오기는 계정, 분개, 요청, PSP, 미반영 관찰에 영향을 주지 않으며 현재 로컬 요청의 존재나 상태를 검사하지 않는다.

[4.2] 이미 있는 파일ID에 순서 있는 행 목록이 모두 같으면 `OK DUP <파일ID>`를 출력하며 아무것도 바꾸지 않는다. 정수는 값으로 비교한다. 행 순서만 달라도 다른 파일 내용이다. 다른 내용이면 `ERR FILE_CONFLICT`이며 기존 파일을 보존한다. 두 경우 모두 명령에 지정된 CSV 줄을 끝까지 읽은 다음 응답한다. 파일이 달라도 같은 요청키가 있는 것은 가져오기 오류가 아니다.

### 대조 대상과 불일치

[4.3] `RECONCILE <파일ID>`는 명령 실행 시점의 로컬 성공 요청들과 지정 파일을 대조한다. 로컬 대상은 `SUCCEEDED`인 `PAY`·`REFUND` 요청뿐이다. 요청키가 대조 키이고, 기대 통화는 요청 통화, 기대 금액은 `PAY`면 양의 요청 금액, `REFUND`면 음의 요청 금액이다. `READY`, `RETRYABLE`, `UNKNOWN`, `FAILED` 요청과 사용자 `POST` 분개는 로컬 대조 대상에서 제외한다. PSP가 이미 성공했더라도 로컬 사후 기록 전이면 제외한다.

[4.4] 로컬 대상의 키와 파일에 나오는 키의 합집합을 대조한다. 파일의 행은 요청키만으로 묶으며 통화와 금액이 달라도 같은 요청키면 같은 묶음이다. 각 키에는 아래 우선순위에서 처음 해당하는 불일치 하나만 보고한다. 아무 불일치도 없으면 그 키의 상세 줄을 출력하지 않는다.

[4.5] 파일의 같은 키 행이 2개 이상이면 로컬 대상 유무와 통화·금액에 관계없이 `DUPLICATE <키> <행개수>`다. 같은 값의 행을 여러 번 받은 경우도 중복이며, 행개수는 첫 행을 포함한 전체 개수다. 이 키에는 누락·통화 차이·금액 차이를 따로 출력하지 않는다.

[4.6] 중복이 아닌 키에서 로컬 대상만 있고 파일 행이 없으면 `MISSING_REMOTE <키> <기대통화> <기대금액>`이다. 파일 행 하나만 있고 로컬 대상이 없으면 `MISSING_LOCAL <키> <실제통화> <실제금액>`이다. 로컬 요청이 존재하지만 성공 확정되지 않은 경우도 후자다.

[4.7] 양쪽에 하나씩 있으면 먼저 통화를 비교한다. 다르면 `CURRENCY_MISMATCH <키> <기대통화> <기대금액> <실제통화> <실제금액>`이다. 통화가 같고 금액이 다르면 `AMOUNT_MISMATCH <키> <통화> <기대금액> <실제금액>`이다. 둘 다 같으면 일치다. 금액은 부호까지 비교하므로 환불을 양수로 보낸 행은 금액 차이다.

### 보고서와 총계

[4.8] 보고서 첫 줄은 `REPORT <파일ID> <불일치키수> <통화수>`다. 그다음 불일치 상세 줄을 요청키의 ASCII 사전순으로 출력한다. 오류 유형별로 묶지 않는다. 불일치키수는 상세 줄 수이며 중복 행 수가 아니다. 상세 줄 뒤에는 4.9의 통화별 총계를 통화 코드의 ASCII 사전순으로 출력한다.

[4.9] 로컬 대상과 파일 행에서 나오는 모든 통화에 대해 `TOTAL <통화> <로컬순액> <외부순액> <차액>`을 출력한다. 로컬순액은 그 통화의 모든 로컬 기대 금액 합, 외부순액은 그 통화의 모든 파일 행 금액 합, 차액은 외부순액에서 로컬순액을 뺀 값이다. 중복·누락·불일치로 보고한 행도 총계에서 빼지 않는다. 통화가 다르면 각 통화에 따로 더한다. 한쪽에만 통화가 있으면 다른 쪽 합은 0이며, 합이 0이 되어도 그 통화 줄을 출력한다. 단순히 열린 계정에만 있는 통화는 포함하지 않는다.

[4.10] 양쪽 대상이 모두 없으면 `REPORT <파일ID> 0 0` 한 줄만 출력한다. 대조는 원장, 요청, PSP, 파일과 미반영 관찰을 바꾸지 않는다. 같은 상태에서 반복하면 같은 결과가 나오고, 이후 요청이 성공 확정되면 같은 파일의 대조 결과도 바뀔 수 있다. 파일을 가져온 시점의 로컬 상태를 고정하지 않는다.

## 5. 오류 규칙

[5.1] 앞 단계 오류 규칙을 유지한다. `IMPORT`의 오류는 4.2의 `FILE_CONFLICT`뿐이다. `RECONCILE`에 없는 파일ID를 주면 `ERR NOT_FOUND` 한 줄을 출력한다. CSV 행의 업무상 이상은 가져오기 오류가 아니라 대조 결과로 보고한다. 오류가 나도 기존 파일이나 원장 상태는 바뀌지 않는다.

## 6. 예시

[6.1] `a`의 중복은 금액을 합쳐 정상 거래처럼 취급하지 않는다. `r`은 환불이므로 로컬순액에서는 -30이고, USD와 EUR는 합치지 않는다. KRW의 외부순액은 중복 두 행도 포함하여 380이다.

입력:
```text
OPEN psp KRW D ANY
OPEN merchant KRW C ANY
OPEN usd USD D ANY
OPEN owed USD C ANY
PAY a psp merchant KRW 100
PSP a OK
CALL a
COMMIT a
PAY b psp merchant KRW 200
PSP b OK
CALL b
COMMIT b
PAY c usd owed USD 50
PSP c OK
CALL c
COMMIT c
REFUND r a KRW 30
PSP r OK
CALL r
COMMIT r
IMPORT batch 5
a,KRW,100
b,KRW,180
a,KRW,100
c,EUR,50
ghost,USD,7
RECONCILE batch
TRIAL KRW
TRIAL USD
TRIAL EUR
```

출력:
```text
OK OPEN psp
OK OPEN merchant
OK OPEN usd
OK OPEN owed
STATE a READY
OK PSP a
OBSERVED a OK
STATE a SUCCEEDED
STATE b READY
OK PSP b
OBSERVED b OK
STATE b SUCCEEDED
STATE c READY
OK PSP c
OBSERVED c OK
STATE c SUCCEEDED
STATE r READY
OK PSP r
OBSERVED r OK
STATE r SUCCEEDED
OK IMPORT batch
REPORT batch 5 3
DUPLICATE a 2
AMOUNT_MISMATCH b KRW 200 180
CURRENCY_MISMATCH c USD 50 EUR 50
MISSING_LOCAL ghost USD 7
MISSING_REMOTE r KRW -30
TOTAL EUR 0 50 50
TOTAL KRW 270 380 110
TOTAL USD 50 7 -43
TRIAL KRW 270 270 0
TRIAL USD 50 50 0
TRIAL EUR 0 0 0
```

[6.2] 외부 성공 뒤 사후 기록을 하기 전에는 파일에만 있는 거래다. 같은 파일을 다시 대조하더라도 사후 기록을 끝낸 뒤에는 일치한다. 파일ID가 충돌한 뒤에도 원본은 남는다.

입력:
```text
OPEN psp USD D ANY
OPEN merchant USD C ANY
PAY p psp merchant USD 10
PSP p OK
CALL p
IMPORT snap 1
p,USD,10
RECONCILE snap
COMMIT p
RECONCILE snap
IMPORT snap 1
p,USD,10
IMPORT snap 0
RECONCILE snap
TRIAL USD
```

출력:
```text
OK OPEN psp
OK OPEN merchant
STATE p READY
OK PSP p
OBSERVED p OK
OK IMPORT snap
REPORT snap 1 1
MISSING_LOCAL p USD 10
TOTAL USD 0 10 10
STATE p SUCCEEDED
REPORT snap 0 1
TOTAL USD 10 10 0
OK DUP snap
ERR FILE_CONFLICT
REPORT snap 0 1
TOTAL USD 10 10 0
TRIAL USD 10 10 0
```

## 7. 검사 방식

[7.1] 표준 입출력으로 검사하며 프로세스 초기화와 출력 비교 방식은 앞 단계와 같다. 실행 제한 시간은 테스트 하나당 빌드 시간을 제외하고 60초다. 대조 결과는 상세 줄과 통화별 총계까지 모두 비교한다.

[7.2] 한 테스트의 상한은 계정 2,000개, 접수 요청 100,000개, CSV 행을 제외한 명령 600,000개, 파일 하나의 행 100,000개, 모든 파일의 행 합 200,000개, `RECONCILE` 10회다. CSV 줄을 포함한 전체 입력과 기대 출력은 각각 64MB 이하로 구성한다. 앞 단계에서 더 작게 정한 규모는 그 단계 테스트의 범위이며 이 단계의 입력은 이 문단의 상한까지 주어질 수 있다.

[7.3] 마지막 생성 테스트는 로컬 성공 요청 100,000개와 파일 행 100,000개를 대조하는 명령을 2회 포함한다. 요청키와 파일 행 순서를 다르게 배치하고 일치·누락·금액 차이·통화 차이·중복을 섞는다. 로컬 요청마다 파일 전체를 다시 찾는 방식은 이 규모에서 반복 비교가 크게 늘어난다. 파일의 행 순서에 기대지 않고 제한 시간 안에 대조해야 한다.

[7.4] 고정 테스트와 생성 테스트로 같은 총액인 다른 불일치, 환불 부호, 통화 분리, 중복 우선순위, 파일ID 충돌과 사후 기록 전후의 결과 변화를 확인한다. 모든 테스트는 사용한 통화의 `TRIAL` 차이가 0인지 함께 확인한다. 정산의 `TOTAL` 차액은 0이 아닐 수 있지만 원장 시산의 차이는 항상 0이어야 한다. 앞 두 단계 테스트도 누적 실행한다.

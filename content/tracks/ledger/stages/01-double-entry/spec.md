# 01. 복식 부기 원장

## 1. 개요

[1.1] 결제 서비스의 돈 이동을 기록하는 원장을 만든다. 계정을 열고 여러 차변·대변 항목을 분개 하나로 반영하며, 잔액과 기록을 조회한다. 금액 보존과 계정별 잔액 제한을 동시에 지키는 것이 목표다. 숙련 개발자 기준 예상 구현 시간은 2~3시간이다.

[1.2] 이 트랙은 명령을 순서대로 처리하는 단일 프로세스 프로그램이다. 데이터베이스, 실제 결제망, 동시 실행, 디스크 저장은 다루지 않는다. 뒤 단계는 같은 프로그램에 결제 호출과 정산 대조를 더한다.

## 2. 배경 개념

[2.1] 복식 부기는 돈의 이동을 두 방향으로 기록한다. 차변(debit, `D`)과 대변(credit, `C`)은 기록의 방향이며 그 자체로 수입·지출이나 양수·음수를 뜻하지 않는다. 분개는 같은 사건의 기록 항목들을 묶은 것이고, 같은 통화의 차변 금액 합과 대변 금액 합이 같아야 한다. 한쪽만 기록하면 돈이 생기거나 사라진 것처럼 보인다.

[2.2] 계정에는 잔액이 늘어나는 방향인 정상 잔액 방향이 있다. 현금 같은 차변 정상 계정은 차변에 기록하면 늘고, 부채 같은 대변 정상 계정은 대변에 기록하면 는다. 이 과제에서는 계정 종류 대신 정상 잔액 방향을 직접 지정한다. 정상 방향으로 계산한 계정 잔액이 음수일 수 있는지는 별도 정책으로 정한다.

[2.3] 분개는 항목 하나씩 성공시키는 작업이 아니다. 각 항목만 보면 잔액이 잠시 음수가 되더라도 분개 전체를 반영한 결과가 허용 범위라면 성립할 수 있다. 반대로 계정 하나라도 최종 제한을 어기면 모든 항목과 기록을 함께 거절해야 한다. 이것을 분개의 원자성이라고 한다.

[2.4] 금액은 소수 대신 통화의 최소 단위를 나타내는 정수로 기록한다. 여기서 USD 125는 1달러 25센트를 뜻한다. 서로 다른 통화는 정수 값이 같아도 교환할 수 없으며, 이 과제에는 환율과 반올림이 없다. 배경 주제는 Xu·Lam의 『System Design Interview』 2권 11장이다. 아래의 명령과 세부 규칙은 이 과제에서 정한 계약이다.

## 3. 입출력 규칙

[3.1] 표준 입력을 EOF까지 읽는다. 한 줄이 명령 하나이며 명령 수를 먼저 주지 않는다. 토큰은 하나 이상의 ASCII 공백으로 구분한다. 줄 앞뒤 공백과 빈 줄은 무시한다. 명령과 열거 값은 대문자이고 대소문자를 구분한다. 별도 언급이 없는 명령의 응답은 한 줄이다. 출력에는 안내 문구를 섞지 않는다.

[3.2] 계정 ID와 사용자가 정하는 분개 ID는 `[A-Za-z][A-Za-z0-9_-]{0,31}`에 맞는다. ID의 이름 공간은 계정과 분개가 각각 따로 가진다. 통화는 `[A-Z]{3}`에 맞는 코드이며 실제 통화 목록에 있는지는 검사하지 않는다. 숫자 토큰은 10진 정수이고 선행 `+`나 불필요한 선행 0이 없다. 금액 토큰은 -1,000,000,000,000 이상 1,000,000,000,000 이하이며, 0과 음수의 허용 여부는 명령 규칙으로 정한다.

[3.3] 입력은 정의한 명령 이름, 토큰 수, ID·통화·정수 문법을 지킨다. `POST`의 항목 수는 2~100이고 그 수만큼 항목이 주어진다. 존재하지 않는 ID, 통화 불일치, 0 이하의 금액처럼 의미가 잘못된 입력은 오류 규칙으로 처리한다. 한 실행의 입력은 64MB 이하이며 모든 금액 합, 잔액, 잔액 변화량은 부호 있는 64비트 정수 범위 안이다.

## 4. 명령 규칙

[4.1] `OPEN <계정> <통화> <정상방향> <정책>`은 잔액 0인 계정을 열고 `OK OPEN <계정>`을 출력한다. 정상방향은 `D` 또는 `C`이고, 정책은 `NONNEG` 또는 `ANY`다. `NONNEG` 계정은 정상방향으로 계산한 잔액이 0 이상이어야 하며 `ANY` 계정에는 이 제한이 없다. 계정의 통화·정상방향·정책은 변경할 수 없다.

[4.2] `POST <분개> <통화> <항목수> <계정1> <방향1> <금액1> ... <계정N> <방향N> <금액N>`은 분개를 반영하고 `OK POST <분개>`를 출력한다. 항목 방향은 `D` 또는 `C`이고 금액은 반드시 양수다. 모든 계정의 통화가 분개 통화와 같고 차변 합과 대변 합이 같아야 한다. 같은 계정이 여러 번 나오거나 양쪽 방향에 함께 나와도 된다. 항목 순서는 입력 그대로 보존한다.

[4.3] 계정의 원시 잔액은 그 계정에 기록된 차변 금액 합에서 대변 금액 합을 뺀 값이다. 정상방향이 `D`면 표시 잔액은 원시 잔액과 같고, `C`면 원시 잔액의 부호를 뒤집는다. `POST`는 같은 계정의 모든 항목을 합친 뒤 최종 표시 잔액으로 `NONNEG`를 검사한다. 계정별 검사가 모두 통과할 때만 잔액과 분개를 함께 반영한다.

[4.4] 이미 반영한 분개 ID에 통화와 순서 있는 항목 목록이 모두 같은 `POST`가 오면 잔액이나 기록을 바꾸지 않고 `OK DUP <분개>`를 출력한다. 숫자는 정수 값으로 비교한다. 항목을 합치거나 순서를 바꾼 요청은 같은 요청이 아니다. ID만 같고 내용이 다르면 `ERR JOURNAL_CONFLICT`다. 거절된 분개 ID는 사용한 것으로 보지 않으므로 올바른 내용으로 다시 제출할 수 있다.

[4.5] `BALANCE <계정>`은 `BALANCE <계정> <통화> <표시잔액>`을 출력한다. 음수에는 `-`를 붙이고 0은 `0`으로 쓴다.

[4.6] `JOURNAL <분개>`는 첫 줄에 `JOURNAL <분개> <통화> <항목수>`를 출력하고, 다음 줄부터 입력 순서대로 `ENTRY <계정> <방향> <금액>`을 항목마다 한 줄 출력한다. 아직 반영되지 않았거나 거절된 분개는 조회할 수 없다.

[4.7] `TRIAL <통화>`는 `TRIAL <통화> <차변잔액합> <대변잔액합> <차이>`를 출력한다. 해당 통화의 계정마다 원시 잔액이 양수면 차변잔액합에 더하고, 음수면 절댓값을 대변잔액합에 더한다. 차이는 차변잔액합에서 대변잔액합을 뺀 값이다. 정상방향과 관계없이 원시 잔액을 사용하며, 해당 통화의 계정이 없으면 세 수는 모두 0이다. 올바른 원장에서 차이는 항상 0이다.

## 5. 오류 규칙

[5.1] 실패한 명령은 `ERR <오류코드>` 한 줄만 출력하며 어떤 상태도 바꾸지 않는다. 여러 잘못이 겹치면 이 절에 적은 검사 순서에서 먼저 걸린 오류 하나를 출력한다. 문법이 잘못된 입력과 지원하지 않는 명령은 검사 대상이 아니다.

[5.2] `OPEN`은 계정 ID가 이미 있으면 내용이 같아도 `ACCOUNT_EXISTS`다. `BALANCE`와 `JOURNAL`은 조회 대상이 없으면 `NOT_FOUND`다.

[5.3] `POST`는 먼저 이미 반영된 분개 ID를 4.4에 따라 처리한다. 새 ID라면 항목 중 하나라도 0 이하의 금액이면 `AMOUNT`, 없는 계정이 있으면 `NOT_FOUND`, 통화가 다른 계정이 있으면 `CURRENCY`, 차변·대변 합이 다르면 `UNBALANCED`, 최종 표시 잔액이 음수인 `NONNEG` 계정이 있으면 `INSUFFICIENT` 순서로 검사한다. 같은 종류의 오류가 여러 개여도 코드는 하나만 출력한다.

## 6. 예시

[6.1] 현금은 차변 정상, 고객에게 지급할 의무는 대변 정상으로 연다. 같은 현금 계정이 한 분개에서 줄었다 늘어도 최종 잔액으로 판정한다. 마지막 분개는 거절되므로 잔액에 영향을 주지 않는다.

입력:
```text
OPEN cash KRW D NONNEG
OPEN payable KRW C NONNEG
POST sale KRW 2 cash D 100 payable C 100
POST rotate KRW 4 cash C 150 cash D 150 payable D 20 payable C 20
BALANCE cash
BALANCE payable
POST sale KRW 2 cash D 100 payable C 100
POST large KRW 2 cash C 101 payable D 101
TRIAL KRW
JOURNAL sale
```

출력:
```text
OK OPEN cash
OK OPEN payable
OK POST sale
OK POST rotate
BALANCE cash KRW 100
BALANCE payable KRW 100
OK DUP sale
ERR INSUFFICIENT
TRIAL KRW 100 100 0
JOURNAL sale KRW 2
ENTRY cash D 100
ENTRY payable C 100
```

[6.2] 다른 통화끼리 분개할 수 없다. 통화 오류가 있는 분개의 ID는 소모되지 않는다. 차변 정상인 `ANY` 계정에는 음수 잔액이 생길 수 있다.

입력:
```text
OPEN bank USD D ANY
OPEN debt USD C ANY
OPEN won KRW D ANY
POST move USD 2 bank C 25 won D 25
POST move USD 2 bank C 25 debt D 25
BALANCE bank
BALANCE debt
TRIAL USD
TRIAL KRW
```

출력:
```text
OK OPEN bank
OK OPEN debt
OK OPEN won
ERR CURRENCY
OK POST move
BALANCE bank USD -25
BALANCE debt USD -25
TRIAL USD 25 25 0
TRIAL KRW 0 0 0
```

## 7. 검사 방식

[7.1] JDK 21과 Kotlin 표준 라이브러리로 구현한다. 공개 함수나 자료구조의 모양은 강제하지 않고 표준 입출력으로 검사한다. 테스트마다 빈 상태의 새 프로세스를 실행한다. 출력은 줄 단위로 대소문자와 줄 순서까지 비교한다. 각 줄 끝의 공백·탭·CR과 출력 끝의 빈 줄만 무시한다. 실행 제한 시간은 테스트 하나당 30초이며 빌드 시간은 제외한다.

[7.2] 고정 테스트와 시드를 고정한 생성 테스트로 반복 분개, 계정 방향, 복수 항목의 원자성, 오류 우선순위와 통화 분리를 확인한다. 한 테스트의 최대 규모는 계정 2,000개, 명령 10,000개, 전체 분개 항목 50,000개다. 별도의 성능 전용 대규모 테스트는 두지 않는다. 이 단계의 난도는 처리량보다 금액 보존과 거절 시 상태 보존에 둔다.

[7.3] 모든 테스트는 사용한 각 통화에 대해 마지막에 `TRIAL`을 실행하여 차이가 0인지 함께 확인한다. 잔액 합만 맞는 잘못된 구현을 걸러 내도록 개별 잔액과 분개 항목도 비교한다. 뒤 단계에서도 이 단계의 명령과 출력 계약을 유지하며 앞 단계 테스트를 누적 실행한다.

# 1단계: 토큰 버킷과 새는 버킷

## 1. 개요

[1.1] 이 트랙에서는 API 서버 앞에서 요청 수를 제한하는 처리율 제한기를 만든다. 프로그램은 표준 입력으로 명령을 받아 제한기를 정의하고 요청마다 허용할지 거절할지 판정해 표준 출력에 쓴다. 시각은 입력 줄에 들어 있고 프로그램은 실제 시계를 읽지 않는다. 1단계에서는 토큰 버킷과 새는 버킷을 만든다.

[1.2] 1단계의 명령은 아래 세 가지다.

| 명령 | 하는 일 | 정상 출력 |
|---|---|---|
| `TOKEN <제한기> <용량> <채우는 속도>` | 토큰 버킷 제한기를 정의한다 | 없음 |
| `LEAKY <제한기> <대기열 길이> <내보내는 간격>` | 새는 버킷 제한기를 정의한다 | 없음 |
| `REQ <제한기> <키> <시각>` | 키의 요청 하나를 판정한다 | 1줄 |

[1.3] 2단계는 같은 요청을 고정 창, 요청 시각 기록, 미끄러지는 창 근사의 세 방식으로 판정해 비교한다. 3단계는 게이트웨이 여러 대가 지연이 있는 공유 저장소의 카운터를 함께 쓰는 분산 제한과 저장소 장애, 부하 차단을 다룬다. 이 문서의 입출력 규칙과 명령 규칙은 3단계까지 그대로 쓴다. 뒤 단계는 이 문서가 정한 출력을 바꾸지 않는다. 이 문서는 뒤 단계에서 뜻이 생기는 줄과 그 뒤에 오는 줄의 출력을 정하지 않는다. 그런 줄은 5.2 에 적는다.

## 2. 배경 개념

[2.1] 처리율 제한은 사용자나 API 키, IP 주소 같은 대상 하나가 정해진 시간 동안 보낼 수 있는 요청 수를 제한하는 일이다. 한도를 넘은 요청은 처리하지 않고 거절한다. HTTP API 는 이때 429(Too Many Requests) 상태 코드를 돌려준다. 처리율 제한은 한 사용자가 몰아 보낸 요청이 다른 사용자의 몫까지 차지하는 일을 막고 서버를 과부하에서 지킨다. 결제 서비스 Stripe 는 사용자마다 초당 요청 수를 제한하는 제한기를 두고 이 제한기를 토큰 버킷 알고리즘으로 만든다고 밝혔다. 이 트랙은 요청을 보낸 대상을 키라 부르고 키마다 따로 센다.

[2.2] 토큰 버킷은 토큰을 담는 버킷으로 요청 수를 제한한다. 버킷에 담을 수 있는 토큰의 최대 개수를 용량이라 한다. 토큰은 정해진 속도로 끊임없이 채워진다. 버킷이 가득 차면 넘치는 몫은 버려진다. 요청이 오면 토큰 하나를 꺼내 쓰고 허용한다. 꺼낼 토큰이 없으면 거절하고 토큰을 쓰지 않는다.

[2.3] 토큰 버킷은 용량만큼의 순간 폭주를 허용한다. 한동안 요청이 없어 버킷이 가득 차 있으면 용량만큼의 요청을 한꺼번에 받고 그 뒤로는 채우는 속도만큼만 받는다. 그래서 오랜 시간에 걸친 평균은 채우는 속도를 넘지 않지만 짧은 순간에는 몰린 요청을 받아 준다. 용량이 10 이고 초당 1개를 채우는 버킷은 쉬던 사용자가 한꺼번에 보낸 요청 10개를 모두 받고 그 뒤로는 1초에 1개씩 받는다.

[2.4] 토큰은 정해진 순간마다 한 개씩 생기지 않고 시간에 비례해 연속으로 찬다. 초당 2개를 채우는 버킷은 250밀리초 동안 토큰 0.5개를 채운다. 요청 하나에는 토큰 한 개가 온전히 있어야 하므로 토큰이 0.5개인 버킷은 요청을 거절한다.

[2.5] 새는 버킷은 바닥에 구멍이 난 양동이에 빗댄 알고리즘이다. 들어온 요청은 대기열에 줄을 서고 맨 앞의 요청부터 일정한 간격으로 하나씩 빠져나가 실제로 처리된다. 대기열이 가득 차 있으면 새 요청을 거절한다. 요청이 아무리 몰려도 빠져나가는 요청은 정해진 간격보다 촘촘해지지 않으므로 뒤쪽 서버가 받는 부하가 고르다. 대신 요청은 대기열에서 기다린 만큼 늦게 처리된다. 몰린 요청을 곧바로 통과시키는 토큰 버킷과 다른 점이다.

[2.6] 새는 버킷이라는 이름은 요청이 올 때마다 물이 차고 일정한 속도로 물이 새는 측정기에도 쓰인다. 이 측정기는 넘칠 요청을 기다리게 하지 않고 바로 거절하므로 토큰 버킷과 같은 판정을 낸다. 이 트랙의 새는 버킷은 요청을 대기열에서 기다리게 하는 방식이다.

[2.7] 거절할 때 언제 다시 보내면 받아 줄지를 함께 알려 주면 클라이언트가 헛된 재시도를 줄일 수 있다. HTTP 의 Retry-After 헤더가 이런 정보를 담는다. 토큰 버킷은 토큰 한 개가 다 차는 시각을, 새는 버킷은 대기열에 자리가 나는 시각을 알려 줄 수 있다.

[2.8] 서버의 벽시계는 시각 동기화 때문에 뒤로 돌아갈 수 있다. 제한기가 그런 시각을 그대로 쓰면 지난 요청과의 시간 차가 음수가 되어 토큰이 줄어드는 것처럼 계산한다. 이 트랙의 시계는 뒤로 가지 않는다. 입력의 시각이 지금까지의 시각보다 이르면 지금까지의 시각을 쓴다(4.2).

[2.9] 이 트랙의 시각은 밀리초 단위의 정수다. 프로그램은 0 에서 시작하는 가상의 시계를 쓰고 이 시계는 입력 줄로만 움직인다.

## 3. 입출력 규칙

[3.1] 프로그램은 표준 입력에서 명령을 한 줄씩 읽어 입력이 끝날 때까지 처리하고 결과를 표준 출력에 쓴다.

[3.2] 입력이 끝나면 종료 코드 0 으로 끝난다.

[3.3] 입력은 UTF-8 이다. 줄은 LF(U+000A)로 나눈다. 마지막 줄 뒤에 LF 가 없어도 그 줄을 처리한다.

[3.4] 이 문서에서 공백은 U+0020 한 글자만 가리킨다. 탭(U+0009)과 CR(U+000D)은 공백이 아니다.

[3.5] 줄 앞뒤의 공백은 무시한다. 빈 줄과 공백만 있는 줄은 건너뛰고 아무것도 출력하지 않는다.

[3.6] 명령어는 줄 맨 앞부터 첫 공백 바로 앞까지다. 공백이 없으면 줄 전체가 명령어다. 명령어 뒤의 나머지에서 공백이 아닌 문자가 최대로 이어진 구간 하나하나가 인자다. 공백이 여럿 이어져도 빈 인자는 생기지 않는다.

[3.7] 명령어는 대소문자를 구분한다. `req` 와 `Req` 는 REQ 가 아니다.

[3.8] 출력하는 줄은 모두 LF 로 끝낸다.

[3.9] 이 문서의 정규식은 문자열 전체에 적용한다.

[3.10] 정수 인자는 `^(0|[1-9][0-9]*)$` 에 맞는 10진수다. 부호를 붙이거나 0 으로 시작하는 두 자리 이상의 수는 쓸 수 없다. 정수 인자마다 범위가 정해져 있고 범위 밖의 수는 형식에 맞지 않는 인자다. 자릿수가 많아 64비트 정수에 담기지 않는 수도 범위 밖의 수다.

[3.11] 제한기 이름과 키는 `^[A-Za-z0-9._:-]{1,64}$` 에 맞는 이름이다. 이름은 대소문자를 구분한다. `user:42` 와 `10.0.0.1` 은 이름이고 `a/b` 와 65글자짜리 문자열은 이름이 아니다.

[3.12] 시각 인자는 0 이상 1,000,000,000,000 이하인 정수이고 단위는 밀리초다.

[3.13] 프로그램은 제한기가 하나도 없고 지금 시각이 0 인 상태로 시작한다. 이전 실행의 상태를 이어받지 않는다.

## 4. 명령 규칙

### 시각

[4.1] 프로그램에는 지금 시각이 하나 있다. 처음 값은 0 이다. 지금 시각은 키나 제한기와 상관없이 프로그램 전체에 하나다.

[4.2] REQ 의 시각 인자가 지금 시각 이상이면 그 요청의 시각은 시각 인자이고 지금 시각도 그 값으로 바뀐다. 시각 인자가 지금 시각보다 작으면 시계가 뒤로 간 것으로 판정하고 그 요청의 시각을 지금 시각으로 한다. 이때 지금 시각은 바뀌지 않는다. 이 문서에서 요청의 시각은 이렇게 정한 값이다.

[4.3] 다른 키나 다른 제한기의 요청이 지금 시각을 움직였어도 4.2 는 같다. 키 a 의 요청이 지금 시각을 5000 으로 움직인 뒤 키 b 의 요청이 시각 인자 3000 으로 오면 키 b 의 요청의 시각은 5000 이다. 오류를 낸 줄은 지금 시각을 바꾸지 않는다(5.1).

### 제한기와 키

[4.4] TOKEN 과 LEAKY 는 이름을 붙여 제한기를 정의한다. 제한기 이름은 제한기의 종류와 상관없이 겹칠 수 없다. 이미 있는 이름으로 정의하면 `ERR EXISTS` 를 출력한다. 정의한 제한기는 바꾸거나 지울 수 없다.

[4.5] 제한기에는 키마다 상태가 따로 있다. 한 키의 요청은 다른 키의 상태를 바꾸지 않는다. 키가 같아도 제한기가 다르면 상태가 따로다. 키의 첫 요청이 오기 전에는 그 키의 상태가 없다.

[4.6] `REQ <제한기> <키> <시각>` 은 그 제한기로 키의 요청 하나를 판정하고 결과 한 줄을 출력한다. 제한기가 없으면 `ERR NO_LIMITER` 를 출력한다.

### 토큰 버킷

[4.7] `TOKEN <제한기> <용량> <채우는 속도>` 는 토큰 버킷 제한기를 정의한다. 용량은 1 이상 1,000,000,000 이하이고 채우는 속도는 1 이상 1,000,000 이하인 정수다. 채우는 속도의 단위는 초당 토큰 수다. 성공하면 아무것도 출력하지 않는다.

[4.8] 키의 첫 요청을 판정할 때 그 키의 버킷은 용량만큼 토큰이 찬 상태다.

[4.9] 버킷은 1밀리초에 채우는 속도 ÷ 1000 개씩 토큰을 연속으로 채운다. 같은 제한기에서 그 키로 온 바로 앞 요청의 시각을 s, 그 요청을 판정한 뒤의 토큰 수를 x 라 하면 지금 요청의 시각 t 의 토큰 수는 x + 채우는 속도 × (t − s) ÷ 1000 과 용량 가운데 작은 값이다.

[4.10] 토큰 수는 반올림하지 않은 정확한 값이다. 4.8, 4.9, 4.11 대로 계산하면 토큰 수는 언제나 0.001 의 정수배다.

[4.11] REQ 는 요청의 시각 t 의 토큰 수를 구해 그 값이 1 이상이면 허용한다. 허용하면 토큰 수에서 1 을 빼고 `ALLOW <남은 토큰>` 을 출력한다. 남은 토큰은 1 을 뺀 뒤의 토큰 수다.

[4.12] 시각 t 의 토큰 수가 1 보다 작으면 거절하고 `DENY <토큰> <다시 시도할 시각>` 을 출력한다. 토큰은 시각 t 의 토큰 수다. 거절한 요청은 토큰을 쓰지 않는다.

[4.13] 다시 시도할 시각은 그 뒤로 이 키의 요청이 없다고 할 때 토큰 수가 1 이상이 되는 가장 이른 정수 시각이다. 곧 t 보다 늦은 정수 시각 가운데 4.9 로 구한 토큰 수가 1 이상인 첫 시각이다.

[4.14] 토큰 수는 정수 부분, 점(`.`), 소수점 아래 세 자리를 차례로 붙여 쓴다. 정수 부분은 앞에 0 을 붙이지 않고 1 보다 작으면 `0` 이다. 소수점 아래는 끝자리가 0 이어도 세 자리를 모두 쓴다. `0.000`, `0.500`, `12.250` 처럼 쓴다.

### 새는 버킷

[4.15] `LEAKY <제한기> <대기열 길이> <내보내는 간격>` 은 새는 버킷 제한기를 정의한다. 대기열 길이와 내보내는 간격은 1 이상 1,000,000 이하인 정수이고 내보내는 간격의 단위는 밀리초다. 성공하면 아무것도 출력하지 않는다.

[4.16] 새는 버킷은 허용한 요청마다 내보내는 시각을 정한다. 그 키에서 처음 허용한 요청의 내보내는 시각은 요청의 시각이다. 그 뒤로 허용한 요청의 내보내는 시각은 요청의 시각과, 그 키에서 바로 앞에 허용한 요청의 내보내는 시각에 내보내는 간격을 더한 값 가운데 큰 값이다. 거절한 요청은 내보내는 시각이 없고 뒤 요청의 내보내는 시각에도 영향을 주지 않는다.

[4.17] 시각 t 에 대기 중인 요청은 그 키에서 허용한 요청 가운데 내보내는 시각이 t 보다 늦은 요청이다. 내보내는 시각이 t 인 요청은 시각 t 에 이미 나갔으므로 대기 중이 아니다.

[4.18] REQ 는 요청의 시각 t 에 대기 중인 요청 수가 대기열 길이보다 작으면 허용하고 `ALLOW <내보내는 시각> <남은 자리>` 를 출력한다. 남은 자리는 대기열 길이에서 이 요청을 허용한 뒤 시각 t 에 대기 중인 요청 수를 뺀 값이다. 이 요청의 내보내는 시각이 t 이면 이 요청은 대기하지 않으므로 남은 자리를 줄이지 않는다.

[4.19] 대기 중인 요청 수가 대기열 길이보다 작지 않으면 거절하고 `DENY <자리가 나는 시각>` 을 출력한다. 자리가 나는 시각은 대기 중인 요청 가운데 가장 이른 내보내는 시각이다.

## 5. 오류 규칙

[5.1] 오류가 나면 `ERR` 로 시작하는 오류 줄 하나만 출력한다. 오류를 낸 줄은 지금 시각을 포함해 어떤 상태도 바꾸지 않는다. 프로그램은 다음 줄을 이어서 처리한다.

[5.2] 명령어가 TOKEN, LEAKY, REQ 가운데 어느 것과도 정확히 같지 않으면 `ERR UNKNOWN_COMMAND` 를 출력한다. 다만 WINDOW 와 REPORT 는 2단계에서, GATEWAY, RW, ATOMIC, LOCAL, CALL, PEEK, DOWN, UP 은 3단계에서 명령이 된다. 뒤 단계에서는 이런 명령이 뒤에 오는 줄의 출력에도 영향을 줄 수 있다. 그래서 이 문서는 명령어가 이 열 가지 가운데 하나인 줄이 처음 나온 곳부터 입력 끝까지 모든 줄의 출력을 정하지 않는다.

[5.3] 인자 수가 맞지 않거나 인자가 형식에 맞지 않으면 `ERR BAD_ARGUMENT` 를 출력한다. 인자 수는 TOKEN, LEAKY, REQ 모두 3 이다. 제한기와 키 자리는 3.11 의 이름이어야 하고 수 자리는 3.10 의 정수이면서 명령마다 정한 범위 안에 있어야 한다.

[5.4] 줄마다 명령어, 인자 수, 인자 형식을 차례로 확인한 뒤 TOKEN 과 LEAKY 는 이름이 겹치는지, REQ 는 제한기가 있는지를 확인한다. 처음 걸린 오류 하나만 출력한다.

[5.5] 이 단계의 오류 줄은 아래와 같다.

| 오류 줄 | 뜻 |
|---|---|
| `ERR UNKNOWN_COMMAND` | 모르는 명령어 |
| `ERR BAD_ARGUMENT` | 인자 수나 형식이 틀림 |
| `ERR EXISTS` | 이미 있는 제한기 이름으로 정의하려 함 |
| `ERR NO_LIMITER` | 없는 제한기로 요청함 |

## 6. 예시

[6.1] 예시 블록 하나는 프로그램을 한 번 실행한 기록이다. `> ` 로 시작하는 줄은 입력이고 나머지 줄은 바로 위 입력의 출력이다. 실제 입력에는 `> ` 가 없다.

[6.2] 토큰 버킷의 기본 동작이다. 용량이 3 이고 초당 2개를 채우는 버킷이다. 시각 100 에는 100밀리초 동안 찬 0.2개가 더해져 토큰이 1.2개가 된다. 거절한 요청은 토큰을 쓰지 않는다. 시각 100 의 토큰 0.2개에 0.8개가 더 차려면 400밀리초가 걸리므로 다시 시도할 시각은 500 이다. bob 은 처음 온 키라서 버킷이 가득 차 있다.

```
> TOKEN api 3 2
> REQ api alice 0
ALLOW 2.000
> REQ api alice 0
ALLOW 1.000
> REQ api alice 100
ALLOW 0.200
> REQ api alice 100
DENY 0.200 500
> REQ api bob 100
ALLOW 2.000
> REQ api alice 350
DENY 0.700 500
> REQ api alice 500
ALLOW 0.000
```

[6.3] 다시 시도할 시각과 뒤로 간 시계와 용량이다. 초당 3개를 채우면 1밀리초에 0.003개가 찬다. 토큰 0개에서 1개가 되려면 333.33…밀리초가 걸리므로 시각 1000 의 다시 시도할 시각은 1000 + 334 = 1334 다. 시각 인자 900 은 지금 시각 1333 보다 이르므로 그 요청의 시각은 1333 이다. 오래 쉬어도 토큰은 용량 2 를 넘지 않는다.

```
> TOKEN slow 2 3
> REQ slow k 1000
ALLOW 1.000
> REQ slow k 1000
ALLOW 0.000
> REQ slow k 1000
DENY 0.000 1334
> REQ slow k 1333
DENY 0.999 1334
> REQ slow k 900
DENY 0.999 1334
> REQ slow k 1334
ALLOW 0.002
> REQ slow k 100000
ALLOW 1.000
```

[6.4] 새는 버킷이다. 대기열 길이는 2 이고 내보내는 간격은 100 이다. 시각 0 의 첫 요청은 곧바로 나가므로 자리를 차지하지 않는다. 대기 중인 요청이 둘이면 거절하고 가장 이른 내보내는 시각 100 을 알려 준다. 시각 100 에는 내보내는 시각이 100 인 요청이 이미 나갔으므로 대기 중인 요청은 하나다. 시각 1050 에는 대기열이 비어 있지만 바로 앞에 허용한 요청이 1000 에 나갔으므로 이 요청은 1100 에 나간다.

```
> LEAKY q 2 100
> REQ q u 0
ALLOW 0 2
> REQ q u 0
ALLOW 100 1
> REQ q u 0
ALLOW 200 0
> REQ q u 0
DENY 100
> REQ q u 100
ALLOW 300 0
> REQ q u 150
DENY 200
> REQ q u 1000
ALLOW 1000 2
> REQ q u 1050
ALLOW 1100 1
```

[6.5] 오류와 지금 시각이다. 이름은 제한기의 종류와 상관없이 겹칠 수 없다. 오류를 낸 줄은 지금 시각을 바꾸지 않으므로 시각 인자 5000 이 들어 있던 오류 줄 뒤의 요청은 시각 3000 에 판정한다. 시각 인자 2999 는 지금 시각 3000 보다 이르므로 그 요청의 시각은 3000 이다. 인자 사이의 공백이 여럿이어도 인자는 셋이다.

```
> TOKEN api 0 5
ERR BAD_ARGUMENT
> TOKEN api 5 5
> TOKEN api 1 1
ERR EXISTS
> LEAKY api 1 1
ERR EXISTS
> LEAKY gate 1 0
ERR BAD_ARGUMENT
> REQ web alice 5000
ERR NO_LIMITER
> REQ api alice 3000
ALLOW 4.000
> REQ api alice 2999
ALLOW 3.000
> REQ api alice 01
ERR BAD_ARGUMENT
> REQ api alice 1000000000001
ERR BAD_ARGUMENT
> REQ api ali/ce 3000
ERR BAD_ARGUMENT
> REQ api alice
ERR BAD_ARGUMENT
> req api alice 3000
ERR UNKNOWN_COMMAND
> REQ  api   alice   3000
ALLOW 2.000
> REQ api alice 1000000000000
ALLOW 4.000
```

## 7. 검사 방식

[7.1] 엔진은 테스트마다 풀이의 `run.sh` 를 새 프로세스로 실행한다. 작업 디렉터리는 풀이 디렉터리다.

[7.2] 엔진은 테스트의 입력 줄을 LF 로 잇고 마지막 줄 뒤에도 LF 를 붙여 표준 입력에 쓴 뒤 표준 입력을 닫는다.

[7.3] 프로세스가 0 이 아닌 종료 코드로 끝나면 실패다.

[7.4] 표준 출력만 기대 출력과 비교하고 표준 오류는 비교하지 않는다. 각 줄 끝의 공백, 탭, CR 을 지우고 끝에 붙은 빈 줄을 지운 뒤 줄 수와 각 줄의 내용이 정확히 같아야 한다.

[7.5] 일반 테스트의 제한 시간은 10초다. 제한 시간을 넘기면 엔진이 프로세스를 끝내고 실패로 판정한다.

[7.6] 대규모 테스트는 키 300,000개 안팎에 REQ 1,000,000줄 안팎인 입력이다. 토큰 버킷과 새는 버킷 제한기를 여러 개 섞고 시각 인자는 0 부터 1,000,000,000,000 근처까지 걸친다. 1% 안팎의 줄은 시계가 뒤로 간다. 대기열 길이가 100,000 인 새는 버킷에 몇 개 키의 요청이 450,000줄 안팎 몰려 대기열이 오랫동안 가득 찬다. 제한 시간은 15초다. 요청마다 대기 중인 요청을 하나씩 훑어 세는 풀이와 시각이 움직일 때마다 모든 키의 버킷을 채우는 풀이는 이 제한 시간을 넘기도록 규모를 정했다.

[7.7] 검사 입력의 한 줄은 UTF-8 로 1,000바이트 이하다.

[7.8] 1단계 검사 입력에는 5.2 가 출력을 정하지 않은 줄이 나오지 않는다.

[7.9] 2단계와 3단계를 검사할 때도 1단계 테스트를 다시 실행한다.

[7.10] 3.3 의 마지막 문장과 3.8 은 엔진이 검사하지 않는다. 엔진은 입력의 마지막 줄 뒤에도 LF 를 붙이고(7.2) 출력 줄 끝의 CR 과 끝에 붙은 빈 줄을 지운 뒤 비교하기(7.4) 때문이다. 두 규칙은 표준 입출력 프로그램의 관례라서 적어 둔다.

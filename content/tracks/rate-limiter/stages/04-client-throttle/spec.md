# 4단계: 호출자 쪽 적응형 쓰로틀링

## 1. 개요

[1.1] 4단계는 과부하인 서버에 요청을 보내는 호출자가 서버의 거절 응답을 보고 전송을 줄이는 기능을 더한다. 호출자는 최근 구간의 시도 수와 서버가 받아들인 수로 로컬 거절 확률을 정한다. 서버에 보내지 않은 시도도 세며, 서버가 준 Retry-After 기간에는 전송을 멈춘다. 구현과 확인의 목표 시간은 2시간 안팎이다.

[1.2] 1~3단계의 명령과 그 상태·출력 규칙은 그대로 유지한다. 이 단계는 CLIENT, TRY, CSTAT 세 명령만 더한다. 이 세 명령이 없는 입력의 출력은 3단계와 완전히 같다. 3단계 5.1의 명령어 목록에 세 명령을 추가하며, 나머지 모르는 명령어는 여전히 `ERR UNKNOWN_COMMAND`다.

[1.3] 호출자 하나는 한 애플리케이션이 한 서버를 호출하는 관계 하나를 나타낸다. TRY에는 전송했을 때 즉시 돌아올 서버 응답을 인자로 준다. 실제 네트워크나 기존 제한기를 호출하지 않는다. 이 방식으로 같은 서버 응답 조건에서 K와 집계 구간이 로컬 거절과 회복에 미치는 영향을 관찰한다. 지연을 이용한 동시성 추정과 자동 재시도는 다루지 않는다.

[1.4] 새 명령의 형식은 다음과 같다. 구체적인 범위와 출력은 3~4절이 정한다.

| 명령 | 하는 일 | 정상 출력 |
|---|---|---|
| `CLIENT <호출자> <구간 길이> <K> <시드>` | 호출자를 정의한다 | 없음 |
| `TRY <호출자> <시각> <응답 코드> <Retry-After>` | 시도 하나를 로컬에서 거절하거나 서버에 보낸다 | 사건 줄 0줄 이상과 결과 1줄 |
| `CSTAT <호출자> <시각>` | 현재 구간의 통계와 다음 시도의 거절 확률을 보여 준다 | 사건 줄 0줄 이상과 통계 1줄 |

## 2. 배경 개념

[2.1] 서버 쪽 제한은 요청을 받은 뒤 처리할지 거절할지 정한다. 거절 응답을 만드는 데도 연결 처리와 응답 전송 같은 비용이 든다. 거절할 요청이 계속 몰리면 서버는 요청을 거절하는 일만으로도 과부하가 될 수 있다. 호출자 쪽 쓰로틀링은 요청이 서버에 닿기 전에 일부를 로컬에서 거절해 그 비용을 줄인다. 3단계의 게이트웨이 부하 차단과는 거절하는 위치와 판단에 쓰는 정보가 다르다.

[2.2] 적응형 쓰로틀링은 최근의 서버 응답에 맞춰 로컬 거절 비율을 바꾼다. 최근 시도 수를 requests, 서버가 받아들인 수를 accepts라 할 때 이 단계의 거절 확률은 `max(0, (requests − K × accepts) / (requests + 1))`이다. requests에는 서버가 거절한 시도와 호출자가 로컬에서 거절한 시도가 모두 들어간다. 로컬 거절을 빼면 애플리케이션이 시도를 더 많이 해도 서버에 도달한 수만 보여 부하의 크기를 놓친다. 분모에 1을 더하므로 accepts가 0이어도 확률은 1 미만이며 서버 상태를 다시 확인할 여지가 남는다.

[2.3] K는 성공 수에 비해 시도가 얼마나 많아질 때 전송을 줄일지 정하는 배수다. K가 작으면 같은 기록에서 더 적극적으로 로컬 거절을 한다. 서버가 거절 응답을 만드는 비용이 비싸면 이런 선택이 도움이 된다. K가 크면 서버로 더 많은 요청이 가므로 거절 비용을 더 감수하지만 서버의 회복을 관찰할 기회도 늘어난다. 이는 서버의 허용량을 보장하는 배수가 아니다. 같은 난수에서 한 시도의 판정이 달라지면 이후의 성공 기록도 달라진다.

[2.4] 통계 구간은 현재 시각과 함께 미끄러진다. 길이가 W인 구간에서는 시도한 지 W 이상 지난 기록이 빠진다. 서버가 회복되어도 호출자가 로컬에서 거절한 시도에서는 성공 응답을 관찰할 수 없다. 실제로 전송한 시도가 성공하면 accepts가 늘고 과거 기록이 구간 밖으로 나가도 두 개수의 비율이 바뀐다. 회복 뒤 거절 확률은 시도 간격과 구간 길이에도 영향을 받으며 과거의 성공 기록이 먼저 빠지면 일시적으로 높아질 수도 있다.

[2.5] Retry-After는 다음 요청까지 기다리도록 서버가 알려 주는 값이다. RFC 9110은 HTTP 날짜와 응답을 받은 뒤 기다릴 초 수를 허용한다. 이 단계는 초 수만 입력받으며 대기 종료 시각 전에는 확률과 무관하게 전송을 막는다. 대기는 성공할 때까지 무한히 재시도하라는 뜻이 아니며, 종료 시각이 되었다고 서버가 반드시 받아 준다는 뜻도 아니다.

[2.6] 배경 개념의 출처는 Beyer 외, 『Site Reliability Engineering』(O'Reilly, 2016) 21장 [Client-Side Throttling](https://sre.google/sre-book/handling-overload/#client-side-throttling-a7sYUg)과 [RFC 9110 10.2.3절](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)이다. 이 단계의 입력 응답, 구간 경계, 집계 순서, 난수 생성과 대기 정책은 재현 가능한 검사를 위해 3~5절에서 정한 모형이다.

## 3. 입출력 규칙

[3.1] 1단계의 UTF-8, 줄과 공백 처리, 대소문자 구분, 정수 표기, 출력 줄 끝 규칙을 그대로 따른다. 호출자 이름은 1단계 3.11의 이름이다. 호출자 이름은 다른 호출자 이름과만 중복을 검사하므로 같은 이름의 호출자·제한기·게이트웨이가 함께 있을 수 있다. 호출자 이름을 기존 명령에 쓰더라도 기존 명령은 원래의 제한기나 게이트웨이만 찾는다.

[3.2] 구간 길이 W는 1 이상 1,000,000,000 이하의 정수이고 단위는 밀리초다. K는 정수 부분과 점과 소수 세 자리를 모두 쓰는 1.000 이상 100.000 이하의 값이다. K의 정수 부분은 앞에 0을 붙이지 않는다. `1.100`, `2.000`, `100.000`은 허용하고 `1`, `1.1`, `01.100`, `0.999`, `100.001`은 허용하지 않는다. K의 정확한 값에 1000을 곱한 정수를 k라 한다.

[3.3] 시드는 0 이상 4,294,967,295 이하의 정수다. TRY와 CSTAT의 시각 인자는 0 이상 1,000,000,000,000 이하의 밀리초 정수다. 응답 코드는 `200`, `429`, `503` 중 하나다. Retry-After 인자는 헤더가 없음을 뜻하는 `-` 또는 0 이상 1,000,000 이하의 정수 초 수다. 응답 코드가 200이면 Retry-After는 반드시 `-`여야 한다. 429와 503에는 `-`와 초 수를 모두 쓸 수 있다. 날짜 형식은 받지 않는다.

[3.4] 모든 출력 정수는 앞에 0을 붙이지 않는 10진수로 쓰고 값이 0이면 `0`으로 쓴다. 4절의 확률은 소수로 바꾸거나 약분하지 않고 지정한 분자와 분모를 `/`로 이어 쓴다. 출력 필드 사이에는 공백 한 개만 둔다.

[3.5] 프로그램은 호출자가 없고 지금 시각이 0인 상태로 시작한다. 호출자 기록과 난수 상태는 이전 실행에서 이어받지 않는다. 시각은 3단계까지의 프로그램 전체 시계 하나를 공유한다.

## 4. 명령 규칙

### 호출자와 시각

[4.1] `CLIENT <호출자> <구간 길이> <K> <시드>`는 설정을 고정한 호출자를 만든다. 같은 이름의 호출자가 이미 있으면 `ERR EXISTS`다. 성공하면 아무것도 출력하지 않는다. 처음에는 시도 기록이 없고 대기 종료 시각 U는 0이며 난수 상태 x는 시드다. 호출자를 바꾸거나 지우는 명령은 없다. 정의할 때 현재 시각이 0보다 커도 U는 0이다.

[4.2] 오류가 없는 TRY와 CSTAT도 3단계 4.3의 시각 인자가 있는 줄이다. 먼저 줄의 시각 t를 현재 시각과 시각 인자 중 큰 값으로 정한다. 시각이 t 이하인 기존 예약 사건을 3단계의 순서대로 모두 처리하고 사건 줄을 먼저 출력한 뒤, 지금 시각을 t로 두고 새 명령을 처리한다. 시계가 뒤로 가는 인자도 오류가 아니며 보정한 t를 기록과 대기에 쓴다. CLIENT는 시각이나 예약 사건을 진행시키지 않는다.

[4.3] 호출자 명령은 기존 서버 제한기·저장소·게이트웨이의 상태를 바꾸지 않고 CALL의 요청 번호나 예약 번호를 쓰지 않는다. TRY는 서버 응답을 같은 시각 t에 즉시 반영하며 새 사건을 예약하지 않는다. 기존 사건 처리로 변하는 서버 상태는 3단계 규칙 그대로다. 입력이 끝나면 기존 예약 사건만 3단계 4.6대로 처리하며 호출자의 대기나 재시도 때문에 일을 새로 예약하지 않는다.

### 집계 구간과 확률

[4.4] 호출자마다 자기 TRY 기록만 센다. 시각 t에서 구간 안 기록은 시도 시각 s가 `t − W < s ≤ t`인 기록이다. 정확히 t − W인 기록은 빠진다. 같은 시각의 여러 TRY는 입력 순서대로 각각 별개의 시도다. 다른 호출자의 시도와 REQ, CALL, CSTAT은 이 기록에 들어가지 않는다.

[4.5] TRY는 현재 시도를 추가하기 전에 구간 안에 있는 이전 기록으로 확률을 계산한다. R은 그 이전 시도 수 requests이고 A는 그중 실제로 서버에 전송하여 200을 받은 수 accepts다. 429, 503, 확률에 의한 로컬 거절, 대기에 의한 로컬 거절은 A를 늘리지 않는다. 현재 시도의 응답은 현재 시도의 확률에 영향을 주지 않는다.

[4.6] 확률의 분자 N은 `max(0, 1000 × R − k × A)`이고 분모 D는 `1000 × (R + 1)`이다. 거절 확률 p는 정확한 유리수 N/D다. 중간 나눗셈의 정수 버림이나 반올림으로 판정을 바꾸면 안 된다. R과 A가 모두 0이면 N은 0, D는 1000이다. CSTAT은 그 명령의 시각에서 구간 안 기록 전체를 R, A로 하여 같은 식을 쓴다.

### 난수

[4.7] 난수 상태는 호출자마다 따로 있다. 난수를 한 번 뽑을 때 `x = (1664525 × x + 1013904223) mod 4294967296`으로 갱신하고 갱신한 x를 뽑은 정수로 쓴다. 수학적 정수로 곱하고 더한 뒤 나머지를 취하며 결과는 0 이상 4,294,967,295 이하다. 다른 호출자의 명령은 이 상태를 바꾸지 않는다.

[4.8] 대기 중이 아닌 유효한 TRY는 확률이 0이어도 난수를 정확히 한 번 뽑는다. 뽑은 x에 대해 `x × D < 4294967296 × N`이면 확률에 의해 로컬에서 거절한다. 같으면 거절하지 않는다. 이는 0 이상 1 미만인 난수 x/4294967296이 p보다 작은지 비교하는 규칙이다. CSTAT과 대기 중인 TRY는 난수를 뽑지 않는다.

### TRY와 Retry-After

[4.9] `TRY <호출자> <시각> <응답 코드> <Retry-After>`는 애플리케이션이 시도한 요청 하나다. 모든 인자와 호출자의 존재를 확인한 뒤 4.2대로 시각을 진행시키고 4.5~4.6의 이전 기록으로 N과 D를 구한다. 그다음 대기 여부, 확률에 의한 로컬 거절 여부, 실제 서버 응답 순서로 결과를 정한다.

[4.10] t가 U보다 작으면 결과는 `WAIT`다. 난수를 뽑지 않고 서버에 전송하지 않는다. t가 U와 같으면 대기는 끝났으므로 확률 판정으로 넘어간다. 확률 판정으로 거절하면 결과는 `DROP`이며 서버에 전송하지 않는다. WAIT와 DROP에서는 입력에 주어진 응답과 Retry-After를 상태에 반영하지 않는다. 다만 이 인자들도 항상 3.3의 형식과 조합을 만족해야 한다.

[4.11] 전송한 시도는 입력에 주어진 응답을 시각 t에 받는다. 응답 200이면 결과는 `SERVER_200`이고, 429이면 `SERVER_429`, 503이면 `SERVER_503`이다. 200만 서버가 받아들인 시도로 센다. 429와 503은 통계와 대기에서 동일하게 취급하지만 결과 이름은 구분한다.

[4.12] 실제로 받은 429 또는 503에 Retry-After 초 수 h가 있으면 U를 `max(U, t + 1000 × h)`로 바꾼다. 헤더가 없거나 응답이 200이면 U를 그대로 둔다. 헤더가 0이면 그 응답을 받은 시각보다 더 기다리게 하지 않는다. 한 번 정한 U는 그 시각이 지나거나 원래 응답 기록이 구간 밖으로 나가도 초기화하지 않는다. 출력의 U는 마지막으로 정한 절대 시각이며 대기 여부는 항상 t < U로 판단한다. U는 시각 인자 상한인 1,000,000,000,000보다 클 수 있다.

[4.13] 결과가 무엇이든 유효한 TRY 하나는 시각 t의 시도 기록 하나를 남긴다. WAIT와 DROP도 예외가 아니다. 그 기록은 결과가 SERVER_200일 때만 성공 기록이기도 하다. 대기 기간의 시도를 모아 두었다가 나중에 전송하지 않으며 로컬 거절과 서버 거절을 자동으로 재시도하지 않는다.

[4.14] TRY는 `<t> <호출자> <결과> requests=<시도 수> accepts=<성공 수> p=<N>/<D> draw=<난수> retry_at=<U>` 한 줄을 출력한다. 시도 수와 성공 수는 현재 시도를 반영한 뒤의 구간 안 개수다. p는 현재 시도를 반영하기 전에 계산한 판정용 확률이다. draw는 뽑은 x이며, WAIT에서는 뽑지 않았으므로 `-`다. U는 응답까지 반영한 값이다. 출력되는 시도 수에서 1을 뺀 값이 이번 판정의 R이고, SERVER_200이면 성공 수에서 1을 뺀 값이 이번 판정의 A다.

### CSTAT

[4.15] `CSTAT <호출자> <시각>`은 4.2대로 시각을 진행시킨 뒤 `<t> <호출자> STATS requests=<R> accepts=<A> p=<N>/<D> draw=- retry_at=<U>` 한 줄을 출력한다. R과 A는 그 시각의 구간 안 기록 전체이며, p는 그 시각에 곧바로 TRY를 하나 더 실행한다면 쓸 확률이다. CSTAT은 시도를 추가하거나 U와 난수 상태를 바꾸지 않는다. p는 대기 여부와 별개로 보여 주므로 t < U이면 p가 0이어도 TRY는 WAIT다.

## 5. 오류 규칙

[5.1] 기존 명령은 기존 오류 규칙을 그대로 따른다. 새 명령도 오류 줄 하나만 출력하고 다음 입력으로 넘어간다. 오류가 난 줄은 지금 시각, 예약 사건, 시도 기록, U, 난수 상태를 포함한 어떤 상태도 바꾸지 않는다.

[5.2] 새 명령의 인자 수는 CLIENT 4개, TRY 4개, CSTAT 2개다. 명령어를 확인한 다음 인자 수, 모든 인자의 형식·범위와 응답 코드/Retry-After 조합을 확인한다. 하나라도 맞지 않으면 `ERR BAD_ARGUMENT`다. TRY가 WAIT나 DROP이 될 상황이어도 형식 검사를 생략하지 않는다.

[5.3] 인자가 모두 유효하면 CLIENT는 호출자 이름의 중복을 확인하고 중복이면 `ERR EXISTS`를 출력한다. TRY와 CSTAT은 호출자의 존재를 확인하고 없으면 `ERR NO_CLIENT`를 출력한다. 같은 이름의 제한기나 게이트웨이만 있어도 호출자가 없으면 NO_CLIENT다. 형식 오류와 존재 오류가 함께 있으면 BAD_ARGUMENT가 우선이다. 존재를 확인하기 전에는 시각을 진행시키지 않는다.

## 6. 예시

[6.1] 블록 하나는 프로그램을 한 번 실행한 기록이다. `> `로 시작하는 줄은 입력이고 나머지 줄은 그 입력을 처리하며 나온 출력이다. 실제 입력에는 `> `가 없다. 각 블록은 서로 독립적이다.

[6.2] 실패 뒤 회복이다. 시드 0에서 첫 난수는 1013904223이다. 첫 시도는 이전 기록이 없어 전송되고 서버가 거절한다. 두 번째는 확률 1/2에서 로컬 거절되지만 requests가 늘어난다. 세 번째는 확률 2/3보다 난수가 커서 전송되고 성공한다. 그 성공은 네 번째 판정의 확률을 1/4로 낮춘다. 네 번째 성공까지 반영하면 다음 확률은 0이다. CSTAT은 난수를 소비하지 않으므로 시각 400의 TRY는 다섯 번째 난수를 쓴다.

```text
> CLIENT c 1000 2.000 0
> TRY c 0 503 -
0 c SERVER_503 requests=1 accepts=0 p=0/1000 draw=1013904223 retry_at=0
> TRY c 100 503 -
100 c DROP requests=2 accepts=0 p=1000/2000 draw=1196435762 retry_at=0
> TRY c 200 200 -
200 c SERVER_200 requests=3 accepts=1 p=2000/3000 draw=3519870697 retry_at=0
> TRY c 300 200 -
300 c SERVER_200 requests=4 accepts=2 p=1000/4000 draw=2868466484 retry_at=0
> CSTAT c 300
300 c STATS requests=4 accepts=2 p=0/5000 draw=- retry_at=0
> TRY c 400 200 -
400 c SERVER_200 requests=5 accepts=3 p=0/5000 draw=1649599747 retry_at=0
> CSTAT c 1000
1000 c STATS requests=4 accepts=3 p=0/5000 draw=- retry_at=0
```

[6.3] Retry-After가 2초라 대기 종료 시각은 2000이다. 시각 1000에는 시각 0의 시도가 구간에서 빠지고, 시각 1500에는 시각 500의 시도가 빠진다. 그때에도 U는 2000이다. 시각 1999의 입력에 있는 100초는 전송하지 않아 반영하지 않는다. 시각 2000에는 대기가 끝나지만 시각 1999의 WAIT가 requests에 남아 확률 1/2로 판정한다. WAIT는 난수를 쓰지 않았으므로 이때 두 번째 난수가 나온다.

```text
> CLIENT hold 1000 1.000 0
> TRY hold 0 503 2
0 hold SERVER_503 requests=1 accepts=0 p=0/1000 draw=1013904223 retry_at=2000
> TRY hold 500 200 -
500 hold WAIT requests=2 accepts=0 p=1000/2000 draw=- retry_at=2000
> TRY hold 1000 200 -
1000 hold WAIT requests=2 accepts=0 p=1000/2000 draw=- retry_at=2000
> CSTAT hold 1500
1500 hold STATS requests=1 accepts=0 p=1000/2000 draw=- retry_at=2000
> TRY hold 1999 429 100
1999 hold WAIT requests=2 accepts=0 p=1000/2000 draw=- retry_at=2000
> TRY hold 2000 200 -
2000 hold DROP requests=2 accepts=0 p=1000/2000 draw=1196435762 retry_at=2000
> TRY hold 2000 200 -
2000 hold SERVER_200 requests=3 accepts=1 p=2000/3000 draw=3519870697 retry_at=2000
> CSTAT hold 2000
2000 hold STATS requests=3 accepts=1 p=2000/4000 draw=- retry_at=2000
```

[6.4] K와 호출자의 독립성이다. 두 호출자는 같은 시드와 같은 응답을 받는다. 각자 시도 두 개 중 하나가 성공했을 때 K가 1.100인 a의 다음 거절 확률은 0.3이고, K가 2.000인 b의 다음 확률은 0이다. a의 TRY가 b의 난수 상태를 진행시키지 않는다.

```text
> CLIENT a 1000 1.100 0
> CLIENT b 1000 2.000 0
> TRY a 0 200 -
0 a SERVER_200 requests=1 accepts=1 p=0/1000 draw=1013904223 retry_at=0
> TRY b 0 200 -
0 b SERVER_200 requests=1 accepts=1 p=0/1000 draw=1013904223 retry_at=0
> TRY a 0 429 -
0 a SERVER_429 requests=2 accepts=1 p=0/2000 draw=1196435762 retry_at=0
> TRY b 0 429 -
0 b SERVER_429 requests=2 accepts=1 p=0/2000 draw=1196435762 retry_at=0
> CSTAT a 0
0 a STATS requests=2 accepts=1 p=900/3000 draw=- retry_at=0
> CSTAT b 0
0 b STATS requests=2 accepts=1 p=0/3000 draw=- retry_at=0
```

[6.5] 기존 사건과 시계와 오류다. CSTAT이 시각 20까지 기존 사건을 먼저 처리하므로 CALL의 사건 줄이 통계보다 앞선다. 그 뒤 시각 인자 5는 20으로 보정된다. 없는 호출자나 잘못된 응답 조합의 오류는 시각을 9000으로 움직이지 않는다. 같은 이름의 토큰 버킷을 정의하고 요청해도 호출자의 개수는 늘지 않는다. 마지막 통계에서는 시각이 정확히 t − W인 시각 20의 기록이 빠진다.

```text
> GATEWAY g 10 2 0
> ATOMIC s 1 1000
> CLIENT c 1000 2.000 0
> CALL s k 0 g critical
> CSTAT c 20
20 #1 ALLOW 1
20 c STATS requests=0 accepts=0 p=0/1000 draw=- retry_at=0
> TRY c 5 200 -
20 c SERVER_200 requests=1 accepts=1 p=0/1000 draw=1013904223 retry_at=0
> TRY missing 9000 200 -
ERR NO_CLIENT
> TRY c 9000 200 1
ERR BAD_ARGUMENT
> CLIENT c 0 2.000 0
ERR BAD_ARGUMENT
> CLIENT c 1000 2.000 0
ERR EXISTS
> TOKEN c 1 1
> REQ c k 20
ALLOW 0.000
> CSTAT c 20
20 c STATS requests=1 accepts=1 p=0/2000 draw=- retry_at=0
> CSTAT c 1020
1020 c STATS requests=0 accepts=0 p=0/1000 draw=- retry_at=0
```

## 7. 검사 방식

[7.1] 엔진은 테스트마다 풀이 디렉터리에서 `run.sh`를 새 프로세스로 실행한다. 입력 줄을 LF로 잇고 마지막 줄 뒤에도 LF를 붙여 표준 입력에 쓴 뒤 닫는다. 종료 코드는 0이어야 한다. 표준 출력만 기대 출력과 비교한다. 줄 끝의 공백·탭·CR과 끝의 빈 줄을 지운 뒤 줄 수와 각 줄의 내용이 정확히 같아야 한다. 표준 출력이 64MB를 넘거나 제한 시간을 넘으면 실패다.

[7.2] 새 단계의 일반 테스트 제한 시간은 10초다. 새 단계의 테스트 한 번에 TRY는 최대 500,000줄이며 각 입력 줄은 UTF-8로 1,000바이트 이하다. 1~3단계의 테스트를 먼저 다시 실행하며 그 테스트의 제한 시간과 규모는 원래대로다. 새 단계는 호출자 여러 개, K의 소수 부분, 구간의 양쪽 경계, 같은 시각의 반복, 뒤로 간 시각, 대기 중 시도, 헤더의 부재와 0, 최대 시드, 오류의 무변경, 기존 예약 사건과의 순서를 조합해 검사한다.

[7.3] 새 단계의 대규모 테스트는 이름이 짧은 호출자 4개 이하에 TRY 400,000줄 안팎과 CSTAT 수백 줄을 보내며 제한 시간은 30초다. 구간 길이는 최대 1,000,000,000이고, 한 호출자에 300,000개 이상의 시도가 몰려 구간 안에 함께 남는다. 뒤에는 시각을 움직여 오래된 기록이 일부 또는 전부 빠지는 구간을 둔다. 시계가 뒤로 가는 입력과 대기도 섞되 출력은 64MB 이하로 둔다. 요청마다 구간 안 기록을 전부 다시 세는 단순 구현이 제한 시간을 넘도록 한 호출자의 기록을 충분히 쌓는다.

[7.4] 고정 테스트 기대값은 스펙에서 직접 유도한다. 작은 무작위 입력에서는 각 시도마다 기록을 전부 다시 세는 독립 계산과 출력을 비교해 집계와 확률 판정을 검증한다. 이 독립 계산에는 대규모 테스트의 제한 시간을 적용하지 않는다. 실제 벽시계, 네트워크, 스레드 실행 순서는 정답에 영향을 주지 않는다.

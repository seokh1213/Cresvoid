# 3단계: 분산 제한과 부하 차단

## 1. 개요

[1.1] 3단계는 게이트웨이 여러 대가 공유 저장소의 카운터를 함께 써서 키마다 한도를 지키는 분산 제한을 더한다. 게이트웨이와 저장소 사이에는 지연이 있어서 저장소로 보낸 연산은 시간이 지난 뒤에 처리되고 응답도 시간이 지난 뒤에 돌아온다. 저장소는 입력에 따라 멈췄다가 되살아난다. 공유 제한기는 카운터를 쓰는 방식에 따라 세 종류다. RW 는 카운터를 읽은 뒤에 쓴다. ATOMIC 은 카운터를 원자적으로 증가시킨다. LOCAL 은 게이트웨이마다 사본을 두고 가끔 동기화한다. 게이트웨이는 일꾼이 바쁘면 등급이 낮은 요청부터 버린다.

[1.2] 1단계와 2단계의 규칙은 그대로다. 이 문서는 새로 생기는 규칙만 설명한다. 1단계 5.2 가 출력을 정하지 않은 명령 가운데 남은 여덟 명령의 출력을 이 문서가 정한다.

| 명령 | 하는 일 | 정상 출력 |
|---|---|---|
| `GATEWAY <게이트웨이> <지연> <일꾼 수> <처리 시간>` | 게이트웨이를 등록한다 | 없음 |
| `RW <제한기> <한도> <창 길이>` | 읽고 쓰는 공유 제한기를 정의한다 | 없음 |
| `ATOMIC <제한기> <한도> <창 길이>` | 원자적으로 증가시키는 공유 제한기를 정의한다 | 없음 |
| `LOCAL <제한기> <한도> <창 길이> <동기화 주기>` | 로컬 사본을 쓰는 공유 제한기를 정의한다 | 없음 |
| `CALL <제한기> <키> <시각> <게이트웨이> <등급>` | 게이트웨이에 요청 하나가 도착한다 | 사건 줄 0줄 이상 |
| `PEEK <제한기> <키> <시각>` | 저장소의 카운터 값을 보여 준다 | 사건 줄 0줄 이상과 값 1줄 |
| `DOWN <시각>` | 저장소를 멈춘다 | 사건 줄 0줄 이상 |
| `UP <시각>` | 저장소를 되살린다 | 사건 줄 0줄 이상 |

[1.3] 사건 줄은 요청의 결과를 알리는 줄이다(4.16). 시각 인자가 있는 줄은 자기 출력보다 먼저 그 시각까지 일어난 사건 줄을 출력할 수 있다(4.3). 1단계와 2단계의 REQ 도 마찬가지다.

## 2. 배경 개념

[2.1] 한 서비스 앞에 게이트웨이가 여러 대 있으면 같은 키의 요청이 여러 게이트웨이로 나뉘어 들어온다. 게이트웨이마다 따로 세면 키 전체의 한도를 지킬 수 없으므로 Redis 같은 공유 저장소에 키마다 카운터를 두고 모든 게이트웨이가 그 카운터를 쓴다. Stripe 도 처리율 제한기를 Redis 로 만들었다. 저장소에 다녀오는 데는 네트워크 왕복만큼 시간이 걸린다. 그동안 다른 게이트웨이의 요청도 같은 카운터를 다룬다.

[2.2] 읽고 쓰는 방식은 카운터를 읽고 한도보다 작으면 1 을 더한 값을 다시 쓴다. 한 게이트웨이가 읽은 뒤 쓰기 전에 다른 게이트웨이가 같은 카운터를 읽으면 둘은 같은 값을 보고 함께 허용한다. 둘이 쓰는 값도 같아서 증가 하나가 사라진다. 이를 갱신 손실이라 한다. 지연이 길수록 읽기와 쓰기 사이가 벌어져 이런 겹침이 잦아진다.

[2.3] 원자적 증가는 저장소가 더하기와 더한 값 돌려주기를 한 연산으로 처리한다. Redis 의 INCR 이 그런 연산이다. 그 사이에 다른 연산이 끼어들 수 없으므로 갱신 손실이 없다. 게이트웨이는 돌려받은 값으로 판정한다. 대신 판정할 때마다 저장소 왕복을 기다려야 한다. 거절할 요청도 카운터를 늘린다.

[2.4] 로컬 사본 방식에서는 게이트웨이가 키마다 저장소 값의 사본을 두고 저장소에 묻지 않고 바로 판정한다. 게이트웨이는 자기가 허용한 몫을 모아 두었다가 저장소에 더하고 새 합계를 받아 사본을 고친다. 이 트랙에서는 동기화 주기가 지난 뒤 그 키의 요청이 올 때 이렇게 동기화한다(4.31). 판정이 빠르고 저장소가 멈춰도 판정을 이어 간다. 대신 동기화 사이에 다른 게이트웨이가 허용한 요청을 모르므로 한도보다 많이 허용할 수 있다. 동기화 주기가 길수록 더 많이 넘친다.

[2.5] 제한기는 서비스를 지키는 보조 장치이므로 제한기가 고장 나서 정상 요청이 실패하면 안 된다. Stripe 는 제한기 코드에 버그가 있거나 Redis 가 멈춰도 요청이 영향을 받지 않도록 모든 층에서 예외를 포착해 실패하면 허용(fail open)한다고 밝혔다. 실패하면 거절하는 방식에서는 저장소 장애가 곧 서비스 장애가 된다. 실패하면 허용하는 방식은 장애 동안 한도를 지키지 못한다.

[2.6] 부하 차단은 서버가 감당할 수 있는 양보다 요청이 많을 때 덜 중요한 요청부터 버려 중요한 요청을 처리할 여력을 남기는 일이다. 처리율 제한이 사용자 한 명의 몫을 지킨다면 부하 차단은 서버 전체를 지킨다. Stripe 는 트래픽을 중요한 메서드, POST, GET, 테스트 모드 트래픽의 네 등급으로 나누고 서버가 너무 바쁘면 테스트 모드 트래픽부터 버린다. 인프라의 일정 몫을 중요한 요청에 남겨 두기도 한다. 남겨 둘 몫이 20% 이면 중요하지 않은 요청은 나머지 80% 를 넘는 몫부터 503 으로 거절한다.

[2.7] 이 트랙의 게이트웨이와 저장소는 시뮬레이션이다. 메시지는 정해진 지연 뒤에 반드시 도착하고 저장소는 연산이 도착한 순간에 처리한다. 메시지 손실과 시간 초과는 다루지 않는다. 같은 시각에 일어나는 일의 순서는 4.2 와 4.3 이 정한다.

## 3. 입출력 규칙

[3.1] 1단계의 입출력 규칙을 그대로 따른다.

[3.2] 게이트웨이 이름은 1단계 3.11 의 이름이다. 게이트웨이 이름은 제한기 이름과 겹쳐도 된다. 이름이 api 인 게이트웨이와 이름이 api 인 제한기가 함께 있을 수 있다.

[3.3] 등급은 `critical`, `post`, `get`, `test` 가운데 하나이고 소문자로만 쓴다.

[3.4] 1단계 4.2 의 시각 규칙은 시각 인자가 있는 모든 줄, 곧 REQ, CALL, PEEK, DOWN, UP 에 쓴다. 이 문서에서 줄의 시각은 그 규칙으로 정한 값이다. CALL 의 줄의 시각은 요청이 도착한 시각이다.

## 4. 명령 규칙

### 예약된 일

[4.1] 3단계에서는 나중에 일어날 일을 예약한다. 연산이 저장소에 도착하는 일, 응답이 게이트웨이에 도착하는 일, 요청이 일꾼을 돌려주는 일의 세 가지다. 예약된 일마다 일어날 시각이 있고 일을 예약할 때마다 프로그램 전체에서 1 부터 차례로 예약 번호를 붙인다.

[4.2] 예약된 일은 시각이 이른 것부터 처리하고 시각이 같으면 예약 번호가 작은 것부터 처리한다. 예약된 일을 처리하는 동안 지금 시각은 그 일의 시각이다.

[4.3] 시각 인자가 있는 줄에 오류가 없으면 프로그램은 먼저 줄의 시각 t 를 정한다. 그다음 시각이 t 이하인 예약된 일을 4.2 의 순서로 모두 처리한다. 이 처리 도중 새로 예약된 일도 시각이 t 이하이면 같은 차례 안에서 처리한다. 그다음 지금 시각을 t 로 하고 그 줄의 명령을 처리한다. 같은 시각이면 예약된 일이 입력 줄보다 먼저 일어난다.

[4.4] 줄의 명령을 처리하며 예약한 일은 시각이 t 와 같아도 그 줄에서 처리하지 않는다. 그 뒤에 오는 줄 가운데 시각 인자가 있고 오류가 없는 첫 줄이 4.3 대로 처리한다. 그런 줄이 없으면 입력이 끝난 뒤 4.6 대로 처리한다.

[4.5] 시각 인자가 없는 줄과 오류가 난 줄은 예약된 일을 처리하지 않는다.

[4.6] 입력이 끝나면 남은 예약된 일을 4.2 의 순서로 모두 처리한다. 이 처리 도중 새로 예약된 일도 모두 처리한다.

[4.7] 1단계와 2단계는 명령어가 GATEWAY, RW, ATOMIC, LOCAL, CALL, PEEK, DOWN, UP 가운데 하나인 줄이 처음 나온 곳부터 출력을 정하지 않는다(1단계 5.2, 2단계 5.1). 그런 줄이 처음 나오기 전까지 모든 줄의 출력은 3단계에서도 1단계나 2단계에서와 같다. 그런 줄이 없는 입력은 출력 전체가 같다.

### 게이트웨이

[4.8] `GATEWAY <게이트웨이> <지연> <일꾼 수> <처리 시간>` 은 게이트웨이를 등록한다. 지연은 0 이상 1,000,000 이하, 일꾼 수는 1 이상 1,000,000 이하, 처리 시간은 0 이상 1,000,000 이하인 정수다. 지연과 처리 시간의 단위는 밀리초다. 이미 등록된 게이트웨이 이름이면 `ERR EXISTS` 를 출력한다. 성공하면 아무것도 출력하지 않는다.

[4.9] 지연은 그 게이트웨이와 저장소 사이에서 메시지 하나가 가는 데 걸리는 시간이다. 게이트웨이가 시각 s 에 보낸 연산은 시각 s + 지연에 저장소에 도착한다. 저장소가 시각 u 에 그 게이트웨이로 보낸 응답은 시각 u + 지연에 도착한다. 메시지를 보낼 때마다 그 메시지가 도착하는 일을 예약한다.

### 공유 제한기와 저장소

[4.10] `RW <제한기> <한도> <창 길이>`, `ATOMIC <제한기> <한도> <창 길이>`, `LOCAL <제한기> <한도> <창 길이> <동기화 주기>` 는 공유 제한기를 정의한다. 한도와 창 길이는 1 이상 1,000,000,000 이하인 정수다. LOCAL 의 동기화 주기는 0 이상 1,000,000,000 이하인 정수다. 창 길이와 동기화 주기의 단위는 밀리초다. 제한기 이름은 1단계 4.4 대로 제한기의 종류와 상관없이 겹칠 수 없다. 성공하면 아무것도 출력하지 않는다.

[4.11] 공유 제한기는 2단계 4.3 의 고정 창으로 센다. 요청이 도착한 시각이 든 창이 그 요청의 창이다. 연산이 저장소에서 처리되는 시각이 다른 창에 들어도 요청의 창은 바뀌지 않는다.

[4.12] 저장소에는 공유 제한기와 키와 창 번호의 조합마다 카운터가 하나 있다. 카운터의 처음 값은 0 이다. 요청 때문에 보내는 연산은 모두 그 요청의 제한기와 키와 창의 카운터를 다룬다. 프로그램은 저장소가 동작하는 상태로 시작한다.

[4.13] 저장소는 연산이 도착한 순간에 그 연산을 처리한다. 연산은 네 가지다. GET 은 카운터 값을 돌려준다. SET v 는 카운터를 v 로 바꾸고 아무것도 돌려주지 않는다. INCR 은 카운터에 1 을 더하고 더한 뒤의 값을 돌려준다. ADD n 은 카운터에 n 을 더하고 더한 뒤의 값을 돌려준다. 저장소는 돌려줄 값이 있는 연산을 처리한 시각에 그 값을 담은 응답을 연산을 보낸 게이트웨이로 보낸다.

[4.14] 저장소가 멈춘 동안 도착한 연산은 실패한다. 실패한 연산은 카운터를 바꾸지 않는다. GET, INCR, ADD 가 실패하면 저장소는 값 대신 실패를 담은 응답을 보낸다. 실패 응답도 4.9 대로 지연 뒤에 도착한다. SET 이 실패하면 아무것도 보내지 않는다.

### CALL 과 사건 줄

[4.15] `CALL <제한기> <키> <시각> <게이트웨이> <등급>` 은 공유 제한기로 판정할 키의 요청 하나가 줄의 시각에 게이트웨이에 도착한 것이다. 게이트웨이가 등록되어 있지 않으면 `ERR NO_GATEWAY` 를 출력한다. 오류가 없는 CALL 은 사건 줄 말고는 아무것도 출력하지 않는다. 오류가 없는 CALL 마다 제한기, 키, 게이트웨이와 상관없이 프로그램 전체에서 1 부터 차례로 요청 번호를 붙인다. 오류가 난 CALL 은 번호를 쓰지 않는다.

[4.16] 요청마다 결과 하나가 정해지고 결과가 정해질 때 사건 줄 하나를 출력한다. 사건 줄은 `<시각> #<요청 번호> <결과>` 이고 시각은 결과가 정해진 시각이다. 결과는 `ALLOW <개수>`, `DENY <개수>`, `OPEN`, `SHED` 가운데 하나이고 뜻은 아래와 같다.

| 결과 | 뜻 |
|---|---|
| `ALLOW <개수>` | 허용 |
| `DENY <개수>` | 한도를 넘어 거절 |
| `OPEN` | 저장소 연산이 실패해 허용 |
| `SHED` | 부하 차단으로 버림 |

[4.17] 개수는 판정에 쓴 개수이고 이 요청을 더한 값이다. 개수가 한도 이하이면 ALLOW, 한도보다 크면 DENY 다.

### 부하 차단과 일꾼

[4.18] 게이트웨이는 일꾼 수만큼의 요청을 동시에 처리할 수 있다. 요청이 차지한 일꾼은 돌려줄 때까지 바쁘다.

[4.19] 오류가 없는 CALL 은 4.3 대로 예약된 일을 처리한 다음 부하 차단부터 확인한다. 이 요청이 일꾼을 차지하기 전에 그 게이트웨이의 바쁜 일꾼 수 × 100 이 일꾼 수 × 등급의 상한 이상이면 요청을 버리고 그 시각에 `SHED` 사건 줄을 출력한다. 등급의 상한은 test 40, get 60, post 80, critical 100 이다. 일꾼이 10 이면 test 요청은 바쁜 일꾼이 4 이상일 때, critical 요청은 10 일 때 버린다.

[4.20] 버린 요청은 일꾼을 차지하지 않고 저장소로 연산을 보내지 않으며 카운터와 사본을 바꾸지 않는다.

[4.21] RW 와 ATOMIC 요청은 도착한 시각부터 일꾼 하나를 차지한다. 결과가 DENY 이면 결과가 정해진 시각에 일꾼을 돌려준다. 결과가 ALLOW 나 OPEN 이면 결과가 정해진 시각에서 처리 시간이 지난 시각에 돌려준다.

[4.22] LOCAL 요청은 도착한 시각에 결과가 정해진다. 결과가 DENY 이면 일꾼을 차지하지 않는다. 결과가 ALLOW 이면 도착한 시각부터 처리 시간이 지난 시각까지 일꾼 하나를 차지한다.

[4.23] 일꾼을 돌려주는 시각이 결과가 정해진 시각보다 늦으면 돌려주는 일을 예약한다. 두 시각이 같으면 결과를 정할 때 바로 돌려준다. 처리 시간이 0 인 게이트웨이에서 LOCAL 요청은 일꾼을 차지하지 않는 것과 같다.

### RW

[4.24] RW 요청은 도착한 시각에 저장소로 GET 을 보낸다.

[4.25] GET 의 응답이 도착하면 결과를 정한다. 실패 응답이면 결과는 OPEN 이다. 값 v 를 받았으면 개수는 v + 1 이다.

[4.26] 결과가 ALLOW 이면 결과가 정해진 시각에 SET v + 1 을 보낸다. 게이트웨이는 SET 이 처리되기를 기다리지 않는다. 결과가 DENY 나 OPEN 이면 아무 연산도 보내지 않는다.

### ATOMIC

[4.27] ATOMIC 요청은 도착한 시각에 INCR 을 보낸다. 응답이 도착하면 결과를 정한다. 실패 응답이면 결과는 OPEN 이고 값 n 을 받았으면 개수는 n 이다. DENY 로 판정된 요청이 더한 1 도 카운터에 남는다.

### LOCAL

[4.28] 게이트웨이에는 LOCAL 제한기의 키마다 사본이 하나씩 있을 수 있다. 게이트웨이나 제한기가 다르면 사본도 따로다. 사본은 창 번호 하나에 속한다. 사본에는 저장소 값, 보낸 몫, 안 보낸 몫, 응답을 기다리는지 여부, 마지막 동기화 시각이 있다.

[4.29] LOCAL 요청이 부하 차단을 통과하면 게이트웨이는 그 키의 사본을 확인한다. 사본이 없거나 사본의 창 번호가 요청의 창 번호와 다르면 요청의 창에 속한 새 사본으로 바꾼다. 새 사본은 저장소 값과 두 몫이 0 이고 응답을 기다리지 않으며 동기화한 적이 없다. 바뀌기 전 사본의 안 보낸 몫은 저장소로 보내지 않고 버린다.

[4.30] 개수는 저장소 값 + 보낸 몫 + 안 보낸 몫 + 1 이다. 결과가 ALLOW 이면 안 보낸 몫에 1 을 더한다. 결과는 도착한 시각에 정해지므로 사건 줄도 그 시각에 출력한다. LOCAL 요청의 결과는 OPEN 이 되지 않는다.

[4.31] 결과를 정하고 4.30 대로 안 보낸 몫을 고친 다음 두 조건을 모두 만족하면 동기화를 시작한다. 첫째 조건은 사본이 응답을 기다리지 않는 것이다. 둘째 조건은 사본이 동기화한 적이 없거나 줄의 시각이 마지막 동기화 시각 + 동기화 주기 이상인 것이다. 결과가 DENY 여도 마찬가지다. 동기화는 안 보낸 몫을 n 이라 할 때 ADD n 을 보내는 일이다. n 이 0 이어도 보낸다. 보낸 몫을 n 으로, 안 보낸 몫을 0 으로 바꾸고 응답을 기다리는 상태가 되며 마지막 동기화 시각을 줄의 시각으로 한다.

[4.32] ADD 의 응답이 도착했을 때 그 게이트웨이가 가진 그 키의 사본이 ADD 를 보낸 사본과 창 번호가 같으면 응답을 반영한다. 값을 받았으면 저장소 값을 그 값으로 바꾸고 보낸 몫을 0 으로 한다. 실패 응답이면 보낸 몫을 안 보낸 몫에 더하고 보낸 몫을 0 으로 한다. 어느 쪽이든 사본은 응답을 기다리지 않는 상태가 된다. 사본이 창 번호가 다른 새 사본으로 바뀌었으면 응답을 버린다.

### DOWN 과 UP

[4.33] `DOWN <시각>` 은 줄의 시각부터 저장소를 멈추고 `UP <시각>` 은 줄의 시각부터 저장소를 되살린다. 이미 멈춘 저장소에 DOWN 을 하거나 동작 중인 저장소에 UP 을 해도 오류가 아니다. 저장소는 멈춘 상태나 동작하는 상태를 그대로 유지한다. 이런 줄도 오류가 없는 다른 줄처럼 4.3 대로 예약된 일을 처리하고 지금 시각을 줄의 시각으로 한다. 두 명령은 사건 줄 말고는 아무것도 출력하지 않는다.

[4.34] DOWN 이나 UP 줄의 시각에 도착한 연산은 4.3 에 따라 그 줄보다 먼저 처리되므로 그 줄을 처리하기 전의 저장소 상태로 성공과 실패가 정해진다. 동작 중인 저장소에 DOWN 을 하면 같은 시각에 도착한 연산은 성공하지만 이미 멈춘 저장소에 DOWN 을 하면 실패한다. 멈춘 저장소에 UP 을 하면 같은 시각에 도착한 연산은 실패하지만 동작 중인 저장소에 UP 을 하면 성공한다.

[4.35] 저장소가 멈춰도 카운터는 지워지지 않는다. 되살아난 저장소는 멈추기 전의 카운터 값을 그대로 쓴다.

### PEEK

[4.36] `PEEK <제한기> <키> <시각>` 은 4.3 대로 예약된 일을 처리한 뒤 그 공유 제한기와 키와 줄의 시각이 든 창의 카운터 값을 출력한다. 저장소가 멈춰 있어도 값을 출력한다. PEEK 는 저장소로 연산을 보내지 않고 카운터를 바꾸지 않는다.

### 제한기의 종류가 맞지 않을 때

[4.37] CALL 과 PEEK 의 제한기가 공유 제한기가 아니면 `ERR WRONG_KIND` 다. REQ 의 제한기가 공유 제한기이면 `ERR WRONG_KIND` 다. REPORT 의 제한기가 공유 제한기이면 2단계 4.13 대로 `ERR WRONG_KIND` 다.

## 5. 오류 규칙

[5.1] 1단계와 2단계의 오류 규칙을 그대로 따른다. 명령어 목록에 GATEWAY, RW, ATOMIC, LOCAL, CALL, PEEK, DOWN, UP 이 더해진다. 이제 명령어가 이 트랙의 열세 명령 가운데 어느 것과도 정확히 같지 않으면 언제나 `ERR UNKNOWN_COMMAND` 다.

[5.2] 인자 수는 GATEWAY 4, RW 3, ATOMIC 3, LOCAL 4, CALL 5, PEEK 3, DOWN 1, UP 1 이다. 인자 수가 맞지 않거나 인자가 형식에 맞지 않으면 `ERR BAD_ARGUMENT` 다. 게이트웨이 자리는 3.2 의 이름이어야 하고 등급 자리는 3.3 의 등급이어야 한다.

[5.3] 인자를 확인한 다음의 확인 순서는 아래와 같다. GATEWAY 는 게이트웨이 이름이 겹치는지 확인한다. RW, ATOMIC, LOCAL 은 제한기 이름이 겹치는지 확인한다. CALL 은 제한기가 있는지, 공유 제한기인지, 게이트웨이가 있는지를 차례로 확인한다. PEEK 는 제한기가 있는지, 공유 제한기인지를 차례로 확인한다. REQ 는 제한기가 있는지, 공유 제한기가 아닌지를 차례로 확인한다. DOWN 과 UP 은 인자 말고 확인할 것이 없다.

[5.4] 이 단계에서 새로 생기는 오류 줄은 아래와 같다.

| 오류 줄 | 뜻 |
|---|---|
| `ERR NO_GATEWAY` | 등록하지 않은 게이트웨이로 요청함 |

## 6. 예시

[6.1] 예시의 표기는 1단계 6.1 과 같다. 줄을 처리하며 출력한 사건 줄은 그 입력 줄 밑에 적는다. 입력이 끝난 뒤 4.6 대로 처리하며 출력한 줄은 `(입력 끝)` 밑에 적는다. 실제 입력에는 `(입력 끝)` 도 없다.

[6.2] 갱신 손실과 원자적 증가다. g1 의 지연은 10, g2 의 지연은 5 다. RW 에서 두 GET 은 시각 10 과 5 에 도착해 모두 0 을 읽는다. 한도가 1 인데 두 요청이 모두 허용되고 두 SET 이 모두 1 을 써서 카운터는 1 이다. 결과는 PEEK 가 시각 100 까지의 예약된 일을 처리할 때 출력된다. ATOMIC 에서는 g2 의 INCR 이 먼저 도착해 1 을 받고 g1 의 INCR 은 2 를 받아 거절된다. 거절된 요청의 증가도 카운터에 남는다. 요청 번호는 제한기와 상관없이 이어진다.

```
> GATEWAY g1 10 10 0
> GATEWAY g2 5 10 0
> RW api 1 1000
> CALL api alice 0 g1 get
> CALL api alice 0 g2 get
> PEEK api alice 100
10 #2 ALLOW 1
20 #1 ALLOW 1
1
> ATOMIC cnt 1 1000
> CALL cnt alice 1000 g1 get
> CALL cnt alice 1000 g2 get
> PEEK cnt alice 1100
1010 #4 ALLOW 1
1020 #3 DENY 2
2
```

[6.3] 로컬 사본이다. 동기화 주기는 100 이다. a 와 b 는 첫 요청에서 바로 판정하고 ADD 1 을 보낸다. #3 의 개수는 저장소 값 0, 보낸 몫 1, 안 보낸 몫 0 에 1 을 더한 2 다. 두 ADD 는 모두 시각 10 에 도착하고 먼저 예약된 a 의 ADD 가 먼저 처리되므로 시각 20 에 a 는 1 을, b 는 2 를 받는다. #4 의 개수는 1 + 0 + 1 + 1 = 3, #5 의 개수는 2 + 0 + 0 + 1 = 3 이고 한도 3 에서 다섯 요청이 허용된다. #6 은 거절되지만 시각 100 은 마지막 동기화 시각 0 에서 100 이 지난 때라 a 는 ADD 2 를 보낸다. 시각 1000 의 #7 은 창 1 의 요청이라 b 의 사본이 새 사본으로 바뀌고 #5 가 더한 안 보낸 몫 1 은 버려진다. 마지막 PEEK 의 시각 인자 999 는 지금 시각 1100 보다 이르므로 줄의 시각은 1100 이고 창 1 의 카운터를 보여 준다.

```
> GATEWAY a 10 10 0
> GATEWAY b 10 10 0
> LOCAL lim 3 1000 100
> CALL lim k 0 a get
0 #1 ALLOW 1
> CALL lim k 0 b get
0 #2 ALLOW 1
> CALL lim k 5 a get
5 #3 ALLOW 2
> CALL lim k 25 a get
25 #4 ALLOW 3
> CALL lim k 30 b get
30 #5 ALLOW 3
> CALL lim k 100 a get
100 #6 DENY 4
> PEEK lim k 130
4
> CALL lim k 1000 b get
1000 #7 ALLOW 1
> PEEK lim k 1100
1
> PEEK lim k 999
1
```

[6.4] 저장소 장애와 실패 시 허용이다. #1 의 INCR 은 DOWN 과 같은 시각 100 에 도착하므로 DOWN 보다 먼저 처리되어 성공한다. 시각 인자 95 는 지금 시각 100 보다 이르므로 #2 는 시각 100 에 도착한다. #2 의 INCR 은 멈춘 저장소에 도착해 실패한다. #3 의 INCR 은 UP 과 같은 시각 120 에 도착하므로 UP 보다 먼저 처리되어 실패한다. #4 의 INCR 은 되살아난 저장소에 도착하고 카운터는 멈추기 전의 1 에서 2 가 된다.

```
> GATEWAY g 10 10 0
> ATOMIC at 5 1000
> CALL at k 90 g get
> DOWN 100
> CALL at k 95 g get
> CALL at k 110 g get
110 #1 ALLOW 1
> UP 120
120 #2 OPEN
> CALL at k 120 g get
(입력 끝)
130 #3 OPEN
140 #4 ALLOW 2
```

[6.5] 사라진 SET 이다. #1 은 시각 220 에 허용되고 SET 1 을 보내지만 SET 은 저장소가 멈춘 시각 230 에 도착해 실패한다. 그래서 #1 이 허용되었는데도 카운터는 0 이고 #2 도 0 을 읽는다.

```
> GATEWAY g 10 10 0
> RW rw 5 1000
> CALL rw k 200 g get
> DOWN 225
220 #1 ALLOW 1
> UP 240
> PEEK rw k 240
0
> CALL rw k 240 g get
(입력 끝)
260 #2 ALLOW 1
```

[6.6] 부하 차단이다. 일꾼이 5 이므로 test 는 바쁜 일꾼이 2 이상일 때, get 은 3 이상일 때, post 는 4 이상일 때, critical 은 5 일 때 버린다. 허용된 LOCAL 요청은 지연과 상관없이 도착한 시각부터 처리 시간 100 동안 일꾼을 차지한다. 시각 100 에는 요청 다섯 개가 일꾼을 모두 돌려준 뒤 #10 을 판정한다.

```
> GATEWAY w 10 5 100
> LOCAL s 1000 1000 0
> CALL s u1 0 w test
0 #1 ALLOW 1
> CALL s u2 0 w test
0 #2 ALLOW 1
> CALL s u3 0 w test
0 #3 SHED
> CALL s u3 0 w get
0 #4 ALLOW 1
> CALL s u4 0 w get
0 #5 SHED
> CALL s u4 0 w post
0 #6 ALLOW 1
> CALL s u5 0 w post
0 #7 SHED
> CALL s u5 0 w critical
0 #8 ALLOW 1
> CALL s u6 0 w critical
0 #9 SHED
> CALL s u6 100 w test
100 #10 ALLOW 1
```

[6.7] 저장소 왕복 동안 차지하는 일꾼이다. 일꾼이 2 이므로 test 는 바쁜 일꾼이 1 이상일 때, critical 은 2 일 때 버린다. ATOMIC 요청은 결과가 정해질 때까지 일꾼을 차지하므로 처리 시간이 0 이어도 #1 과 #3 은 시각 20 까지 일꾼을 하나씩 차지한다. 시각 20 에 두 결과가 정해지면서 두 요청이 일꾼을 돌려주므로 #5 는 버려지지 않는다.

```
> GATEWAY slow 10 2 0
> ATOMIC hold 10 1000
> CALL hold k 0 slow critical
> CALL hold k 0 slow test
0 #2 SHED
> CALL hold k 0 slow critical
> CALL hold k 0 slow critical
0 #4 SHED
> CALL hold k 20 slow test
20 #1 ALLOW 1
20 #3 ALLOW 2
(입력 끝)
40 #5 ALLOW 3
```

[6.8] 오류다. 일꾼 수 0 은 범위 밖이다. 이름이 g 인 게이트웨이와 이름이 g 인 제한기는 함께 있을 수 있다. CALL 은 제한기를 게이트웨이보다 먼저 확인한다. 오류가 난 CALL 은 번호를 쓰지 않으므로 마지막 CALL 의 요청 번호는 1 이다. 지연이 0 이라 마지막 CALL 이 예약한 일은 시각이 줄의 시각과 같은 5 지만 4.4 에 따라 그 줄에서 처리하지 않는다. 오류가 난 다음 줄도 예약된 일을 처리하지 않으므로 그 일은 PEEK 가 처리한다. 그래서 사건 줄은 오류 줄 뒤, PEEK 의 값 앞에 나온다.

```

> CALL tb k 0 g get
ERR WRONG_KIND
> RW g 1 10
> REQ g k 0
ERR WRONG_KIND
> REPORT g
ERR WRONG_KIND
> CALL g k 0 h get
ERR NO_GATEWAY
> CALL g k 0 g GET
ERR BAD_ARGUMENT
> CALL nope k 0 h get
ERR NO_LIMITER
> PEEK tb k 0
ERR WRONG_KIND
> LOCAL lz 1 10
ERR BAD_ARGUMENT
> CALL g k 5 g get
> DOWN
ERR BAD_ARGUMENT
> PEEK g k 5

1
```

## 7. 검사 방식

[7.1] 1단계 7.1~7.5, 7.7, 7.10 을 그대로 따른다.

[7.2] 대규모 테스트는 키 300,000개 안팎에 CALL 600,000줄 안팎인 입력이다. 게이트웨이는 12대 안팎이고 지연은 1 부터 500 까지, 처리 시간은 2,000 이하다. 1밀리초에 요청이 20개 안팎 도착해 예약된 일이 한때 10,000개를 넘게 쌓인다. RW, ATOMIC, LOCAL 제한기를 섞고 DOWN 과 UP 과 PEEK 도 섞는다. 1% 안팎의 줄은 시계가 뒤로 간다. 제한 시간은 15초다. 예약된 일을 하나 꺼낼 때마다 모든 예약된 일을 훑는 풀이는 이 제한 시간을 넘기도록 규모를 정했다.

[7.3] 3단계를 검사할 때는 1단계와 2단계 테스트를 먼저 다시 실행한다.

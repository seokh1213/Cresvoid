# 1단계: 리더 선출

## 1. 개요

[1.1] 이 트랙에서는 Raft 합의 알고리즘으로 동작하는 노드 여러 개와 그 사이의 네트워크를 한 프로그램 안에서 흉내 내는 결정적 시뮬레이터를 만든다. 프로그램은 표준 입력으로 명령을 받아 노드를 만들고 가상 시계를 움직이며 네트워크의 지연과 유실과 분할을 바꾸고 노드의 상태를 보여 준다. 같은 입력에는 늘 같은 출력을 낸다. 1단계에서는 노드가 임기를 올리며 선거를 치러 리더를 뽑고 더 높은 임기를 보면 물러나는 규칙을 만든다.

[1.2] 1단계의 명령은 아래 일곱 가지다.

| 명령 | 하는 일 | 정상 출력 |
|---|---|---|
| `NODE <노드> <타임아웃>...` | 노드를 만든다 | 없음 |
| `TICK <틱 수>` | 시각을 움직이고 그동안 일어난 선거 시작과 역할 변화를 보여 준다 | 0줄 이상 |
| `DELAY <보내는 노드> <받는 노드> <틱 수>` | 링크의 지연을 바꾼다 | 없음 |
| `DROP <보내는 노드> <받는 노드> <개수>` | 링크로 보낼 메시지 몇 개를 잃게 한다 | 없음 |
| `PARTITION <무리>...` | 노드를 무리로 나누어 무리 사이의 링크를 끊는다 | 없음 |
| `HEAL` | 끊긴 링크를 모두 잇는다 | 없음 |
| `STATE <노드>` | 노드의 역할, 임기, 투표, 알고 있는 리더, 선거 시각을 보여 준다 | 1줄 |

[1.3] 2단계는 클라이언트 요청을 로그 항목으로 받아 팔로워에게 복제하고 어긋난 로그를 리더의 로그에 맞춘다. 3단계는 과반수에 복제된 항목을 커밋해 상태 기계에 적용하고 투표에 로그 비교 조건을 더한다. 이 문서의 입출력 규칙과 명령 규칙은 3단계까지 이어진다. 뒤 단계는 이 규칙에 조건과 메시지 내용을 더하지만 더한 조건은 로그에 항목이 있을 때만 결과를 바꾼다. 이 문서가 출력을 정한 입력에는 로그에 항목을 넣는 REQUEST 가 없으므로 뒤 단계도 그 입력에서는 이 문서와 같은 출력을 낸다. 뒤 단계에서 뜻이 생기는 입력은 5.2 에 적는다.

## 2. 배경 개념

[2.1] 여러 서버에 같은 상태를 복제해 두면 그 가운데 몇 대가 멈추어도 서비스를 이어 갈 수 있다. 복제된 상태 기계에서는 서버마다 명령을 차례로 적은 로그를 둔다. 같은 명령을 같은 순서로 받으면 늘 같은 결과를 내는 상태 기계가 로그의 명령을 적힌 순서대로 실행한다. 로그가 같으면 상태도 같으므로 합의 알고리즘이 할 일은 서버들의 로그를 같게 유지하는 것이다. 이런 알고리즘은 서버의 과반수가 동작하며 서로 통신할 수 있는 동안 진행할 수 있으므로 다섯 대로 된 클러스터는 두 대가 멈추어도 견딘다. Raft 는 Ongaro 와 Ousterhout 가 2014년에 발표한 합의 알고리즘이다. 이해하기 쉬운 구조를 목표로 리더 선출, 로그 복제, 안전성을 나누어 설계했다. 이 트랙은 이 셋을 한 단계에 하나씩 만든다.

[2.2] Raft 의 서버는 팔로워, 후보, 리더 가운데 한 역할을 맡는다. 평소에는 리더가 하나이고 나머지는 모두 팔로워다. 팔로워는 스스로 요청을 보내지 않고 받은 요청에 응답만 한다. 리더는 클라이언트의 명령을 받아 로그에 덧붙이고 팔로워에게 복제한다. 후보는 새 리더를 뽑는 동안 거치는 역할이다. 이 문서는 서버를 노드라 부른다.

[2.3] Raft 는 시간을 연속된 정수로 번호를 매긴 임기로 나눈다. 임기는 선거로 시작하고 당선된 후보가 그 임기의 남은 동안 리더를 맡는다. 표가 갈려 아무도 당선되지 못하면 그 임기는 리더 없이 끝나고 다음 선거가 새 임기를 연다. 노드는 저마다 현재 임기를 저장하고 메시지를 보낼 때마다 임기를 싣는다. 받은 메시지에 담긴 임기가 자기 임기보다 크면 자기 임기를 그 값으로 바꾸고 후보나 리더였다면 곧바로 팔로워가 된다. 자기 임기보다 작은 임기가 담긴 요청은 거절한다. 임기는 이렇게 낡은 리더와 낡은 메시지를 가려내는 논리 시계 구실을 한다. 노드마다 임기가 바뀌는 때가 달라서 같은 시각에도 노드들의 임기는 다를 수 있다.

[2.4] 리더는 항목이 없는 AppendEntries 요청을 하트비트로 삼아 주기적으로 보내 자기가 리더임을 알린다. 팔로워는 현재 리더의 AppendEntries 를 받지 못하고 후보에게 표를 주지도 않은 채 선거 타임아웃이 지나면 리더가 없다고 보고 선거를 시작한다. 선거를 시작한 노드는 임기를 하나 올려 후보가 되고 자신에게 투표한 뒤 다른 모든 노드에 RequestVote 요청을 보낸다. 노드는 한 임기에 많아야 한 후보에게 표를 주며 먼저 도착한 요청부터 처리한다. 후보는 같은 임기에서 전체 노드의 과반수 표를 얻어야 당선되므로 한 임기의 리더는 많아야 하나다. 논문은 이 성질을 선거 안전성이라 부른다. 당선된 후보는 곧바로 하트비트를 보내 다른 노드가 선거를 시작하지 않게 한다.

[2.5] 후보의 선거는 세 가지로 끝난다. 후보는 과반수 표를 얻어 당선될 수 있다. 자기 임기 이상인 리더의 AppendEntries 를 받아 팔로워로 돌아갈 수도 있다. 아무도 당선되지 못한 채 선거 타임아웃이 지날 수도 있다. 여러 팔로워가 거의 동시에 후보가 되면 표가 갈려 셋째 경우가 된다. 이때 후보들은 타임아웃이 지나면 임기를 올려 다시 선거를 치른다.

[2.6] 표 갈림이 되풀이되지 않도록 Raft 는 선거 타임아웃을 정해진 구간(논문의 예는 150~300ms)에서 무작위로 고른다. 그러면 대개 한 노드만 먼저 타임아웃되어 다른 노드들이 타임아웃되기 전에 당선되고 하트비트를 보낸다. 후보도 선거를 시작할 때마다 타임아웃을 새로 고르므로 다음 선거에서 다시 표가 갈릴 가능성이 줄어든다. 이 트랙은 실행을 결정적으로 만들려고 무작위 값 대신 노드마다 타임아웃 목록을 입력으로 받아 선거를 시작할 때마다 다음 값을 쓴다(4.9).

[2.7] 논문은 브로드캐스트 시간이 선거 타임아웃보다 훨씬 짧고 선거 타임아웃이 서버의 평균 고장 간격보다 훨씬 짧아야 한다고 적는다. 브로드캐스트 시간은 한 노드가 다른 모든 노드에 요청을 보내고 응답을 받기까지 걸리는 평균 시간이다. 선거 타임아웃이 메시지 왕복보다 짧으면 후보는 표를 다 모으기 전에 다시 선거를 시작하고 리더가 좀처럼 뽑히지 않는다. Raft 의 안전성은 이런 시간 조건에 기대지 않지만 리더를 뽑고 유지하는 가용성은 시간 조건에 기댄다.

[2.8] 실제 네트워크와 스레드 위에서 분산 알고리즘을 시험하면 메시지가 오가는 순서가 실행마다 달라 한 번 본 실패를 다시 보기 어렵다. 결정적 시뮬레이션은 모든 노드를 한 프로그램의 가상 시계 위에서 실행한다. 메시지 도착과 타이머 만료 같은 사건을 시각 순서대로 처리하고 같은 시각의 사건은 정해 둔 규칙으로 줄을 세운다. 그러면 같은 입력은 늘 같은 실행을 낳으므로 실패를 그대로 재현할 수 있다. FoundationDB 는 클러스터 전체를 한 스레드 프로세스 안에서 시뮬레이션하며 네트워크와 기계의 장애를 넣어 시험한다. 이 트랙의 프로그램도 그런 시뮬레이터다. 노드는 실제로 통신하지 않고 시뮬레이터가 정한 시각에 메시지를 받는다.

[2.9] Raft 는 메시지가 늦게 오거나 사라지거나 보낸 순서와 다르게 도착해도 안전해야 한다. 이 트랙의 네트워크는 링크마다 지연을 두고 메시지를 잃게 하거나 노드 사이의 링크를 끊을 수 있다. 늦게 도착한 메시지는 이미 지난 임기의 것일 수 있으므로 노드는 메시지에 담긴 임기를 보고 낡은 메시지를 가려낸다. 시뮬레이터는 사라진 메시지를 다시 보내 주지 않는다. 리더는 하트비트를 되풀이해 보내므로 사라진 하트비트는 다음 하트비트가 메우지만 사라진 RequestVote 는 다시 보내지 않는다.

[2.10] 이 트랙은 노드의 고장과 재시작, 디스크에 남기는 상태, 구성원 변경, 스냅숏을 다루지 않는다. 노드는 멈추지 않는다. 노드가 멈춘 상황은 그 노드와 다른 노드 사이의 링크를 끊어 흉내 낸다.

## 3. 입출력 규칙

[3.1] 프로그램은 표준 입력에서 명령을 한 줄씩 읽어 입력이 끝날 때까지 처리하고 결과를 표준 출력에 쓴다.

[3.2] 입력이 끝나면 종료 코드 0 으로 끝난다.

[3.3] 입력은 UTF-8 이다. 줄은 LF(U+000A)로 나눈다. 마지막 줄 뒤에 LF 가 없어도 그 줄을 처리한다.

[3.4] 이 문서에서 공백은 U+0020 한 글자만 가리킨다. 탭(U+0009)과 CR(U+000D)은 공백이 아니다.

[3.5] 줄 앞뒤의 공백은 무시한다. 빈 줄과 공백만 있는 줄은 건너뛰고 아무것도 출력하지 않는다.

[3.6] 명령어는 줄 맨 앞부터 첫 공백 바로 앞까지다. 공백이 없으면 줄 전체가 명령어다. 명령어 뒤의 나머지에서 공백이 아닌 문자가 최대로 이어진 구간 하나하나가 인자다. 공백이 여럿 이어져도 빈 인자는 생기지 않는다.

[3.7] 명령어는 대소문자를 구분한다. `tick` 과 `Tick` 은 TICK 이 아니다.

[3.8] 출력하는 줄은 모두 LF 로 끝낸다.

[3.9] 이 문서의 정규식은 문자열 전체에 적용한다.

[3.10] 정수 인자는 `^(0|[1-9][0-9]*)$` 에 맞는 10진수다. 부호를 붙이거나 0 으로 시작하는 두 자리 이상의 수는 쓸 수 없다. 정수 인자마다 범위가 정해져 있고 범위 밖의 수는 형식에 맞지 않는 인자다. 자릿수가 많아 64비트 정수에 담기지 않는 수도 범위 밖의 수다.

[3.11] 노드 이름은 `^[a-z][a-z0-9]{0,7}$` 에 맞는다. 영문 소문자로 시작하고 영문 소문자와 숫자로 된 1~8글자다.

[3.12] 프로그램은 시각 0 에서 노드도 메시지도 없는 상태로 시작한다. 이전 실행의 상태를 이어받지 않는다.

## 4. 명령 규칙

### 시각과 틱

[4.1] 시각은 0 이상의 정수이고 단위는 틱이다. 시각은 TICK 으로만 움직인다. TICK 이 아닌 명령은 모두 그 명령을 읽었을 때의 시각, 곧 지금 시각에 일어나고 메시지를 보내지 않는다.

[4.2] `TICK <틱 수>` 는 시각을 틱 수만큼 움직인다. 틱 수는 1 이상 1,000,000 이하인 정수다. 지금 시각이 t 이면 t + 1 부터 t + 틱 수 까지 한 틱씩 차례로 처리한다. 틱 T 를 처리할 때는 지금 시각을 T 로 바꾼 뒤 전달 단계(4.3)와 타이머 단계(4.4)를 차례로 실행한다. TICK 이 끝나면 지금 시각은 t + 틱 수 다. 처리하는 동안 일어난 사건을 사건 줄(4.29)로 출력하고 사건이 없으면 아무것도 출력하지 않는다.

[4.3] 전달 단계에서는 도착 시각이 T 인 메시지를 모두 보낸 순서(4.5)대로 하나씩 받는 노드에 전달한다. 메시지 하나를 받아 일어나는 일을 모두 마친 뒤에 다음 메시지를 전달한다. 전달 단계에서 새로 보낸 메시지는 T 보다 뒤에 도착하므로(4.12) 이번 전달 단계에서는 전달하지 않는다.

[4.4] 타이머 단계에서는 노드 순서대로 노드마다 한 번씩 아래를 확인한다. 리더는 하트비트를 보낸다(4.26). 팔로워나 후보는 선거 시각(4.9)이 T 이면 선거를 시작한다(4.22). 타이머 단계에서 보낸 메시지도 T 보다 뒤에 도착한다.

[4.5] 노드 순서는 NODE 로 노드를 만든 순서다. 보낸 순서는 시뮬레이터 전체에서 노드들이 메시지를 보낸 차례다. 한 노드가 여러 노드에 한꺼번에 보내는 메시지는 받는 노드의 노드 순서대로 보낸다. 보낸 시각이 이른 메시지는 보낸 순서도 앞선다. 도착 시각이 같은 메시지는 보낸 순서대로 전달하므로 지연이 서로 다른 메시지가 같은 틱에 도착하면 먼저 보낸 메시지가 먼저 전달된다.

### 노드

[4.6] `NODE <노드> <타임아웃>...` 은 노드를 만든다. 노드 이름 뒤에 선거 타임아웃 목록을 1개 이상 10개 이하로 주고 타임아웃은 1 이상 1,000,000 이하인 정수다. 같은 값이 여러 번 나와도 된다. 새 노드는 임기 0 의 팔로워이고 아무에게도 표를 주지 않았으며 알고 있는 리더가 없고 시작한 선거 수는 0 이다. 선거 시각은 목록의 첫째 값이다. 성공하면 아무것도 출력하지 않는다.

[4.7] NODE 는 지금 시각이 0 일 때만 쓸 수 있다. 지금 시각이 0 보다 크면 `ERR STARTED` 를 출력한다. 같은 이름의 노드가 이미 있으면 `ERR NODE_EXISTS` 를 출력한다.

[4.8] 클러스터의 노드 수는 만든 노드의 수다. 표 수가 노드 수의 절반보다 크면 과반수다. 노드가 4개이면 3표 이상이 과반수이고 5개이면 3표 이상, 1개이면 1표 이상이 과반수다.

[4.9] 노드가 지금까지 시작한 선거 수를 e, 타임아웃 목록의 길이를 k 라 하면 노드의 현재 선거 타임아웃은 목록의 앞에서부터 센 (e mod k) + 1 번째 값이다. 노드가 선거 타이머를 다시 맞추면 선거 시각은 지금 시각에 현재 선거 타임아웃을 더한 값이 된다. 목록이 `5 9` 인 노드의 선거 타임아웃은 처음에 5 이고 첫 선거를 시작한 뒤에는 9, 둘째 선거를 시작한 뒤에는 다시 5 다.

[4.10] 노드는 아래 네 경우에만 선거 타이머를 다시 맞춘다. 후보나 리더가 팔로워가 될 때(4.21), 후보에게 표를 줄 때(4.23), AppendEntries 를 받아들일 때(4.27), 선거를 시작할 때(4.22)다. 그 밖에는 선거 시각이 바뀌지 않는다. 리더에게는 선거 시각이 없다.

### 네트워크

[4.11] 서로 다른 두 노드 사이에는 방향마다 링크가 하나씩 있다. 노드 a 에서 b 로 가는 링크와 b 에서 a 로 가는 링크는 다른 링크다. 링크마다 지연, 잃을 메시지 수, 끊김 여부가 있다. 처음에는 지연이 1, 잃을 메시지 수가 0 이고 끊겨 있지 않다. 노드는 자기 자신에게 메시지를 보내지 않는다.

[4.12] 노드가 메시지를 보내는 순간 그 링크의 상태로 메시지의 운명이 정해진다. 링크가 끊겨 있으면 메시지는 사라진다. 끊겨 있지 않고 잃을 메시지 수가 1 이상이면 메시지는 사라지고 잃을 메시지 수가 1 준다. 둘 다 아니면 메시지는 지금 시각에 링크의 지연을 더한 시각에 도착한다. 사라진 메시지는 전달되지 않는다. 메시지를 보낸 뒤에 실행한 DELAY, DROP, PARTITION, HEAL 은 이미 보낸 메시지의 운명과 도착 시각을 바꾸지 않는다.

[4.13] `DELAY <보내는 노드> <받는 노드> <틱 수>` 는 보내는 노드에서 받는 노드로 가는 링크의 지연을 틱 수로 바꾼다. 틱 수는 1 이상 1,000,000 이하인 정수다. 바뀐 지연은 그 뒤에 보내는 메시지부터 쓰므로 지연을 줄이면 나중에 보낸 메시지가 먼저 보낸 메시지보다 먼저 도착할 수 있다. 성공하면 아무것도 출력하지 않는다.

[4.14] `DROP <보내는 노드> <받는 노드> <개수>` 는 보내는 노드에서 받는 노드로 가는 링크의 잃을 메시지 수를 개수로 바꾼다. 개수는 0 이상 1,000,000 이하인 정수다. 앞서 남아 있던 수에 더하지 않고 개수로 바꾸므로 개수가 0 이면 남은 수를 없앤다. 끊긴 링크에서 사라진 메시지는 잃을 메시지 수를 줄이지 않는다(4.12). 성공하면 아무것도 출력하지 않는다.

[4.15] DELAY 와 DROP 은 보내는 노드나 받는 노드가 없으면 `ERR NO_NODE` 를 출력하고 두 노드가 같으면 `ERR SAME_NODE` 를 출력한다.

[4.16] `PARTITION <무리>...` 는 노드를 무리로 나누고 서로 다른 무리에 든 두 노드 사이의 링크를 두 방향 모두 끊는다. 무리는 노드 이름을 쉼표로 이은 인자이고 무리는 하나 이상 준다. 같은 무리에 든 두 노드 사이의 링크와 어느 무리에도 들지 않은 노드가 낀 링크는 모두 이어진다. 앞서 끊긴 링크도 이 규칙대로 다시 정하므로 새 PARTITION 은 앞선 분할을 대신한다. 링크의 지연과 잃을 메시지 수는 바뀌지 않는다. 성공하면 아무것도 출력하지 않는다.

[4.17] PARTITION 의 무리에 적은 이름 가운데 없는 노드가 있으면 `ERR NO_NODE` 를 출력한다. 한 노드가 두 번 이상 나오면 같은 무리 안이든 다른 무리든 `ERR BAD_PARTITION` 을 출력한다.

[4.18] `HEAL` 은 끊긴 링크를 모두 잇는다. 링크의 지연과 잃을 메시지 수는 바뀌지 않는다. 성공하면 아무것도 출력하지 않는다.

### 메시지와 임기

[4.19] 메시지는 네 종류다. RequestVote 는 후보의 임기를 싣는다. RequestVote 응답은 응답하는 노드의 임기와 표를 주었는지를 싣는다. AppendEntries 는 리더의 임기를 싣는다. AppendEntries 응답은 응답하는 노드의 임기와 성공 여부를 싣는다. 요청에는 보내는 노드의 그때 임기를 싣고 응답에는 요청을 처리한 뒤의 자기 임기를 싣는다. 요청을 받은 노드는 그 요청을 처리하자마자 요청을 보낸 노드에 응답을 보낸다.

[4.20] 노드가 받은 메시지에 담긴 임기가 자기 임기보다 크면 다른 일을 하기 전에 자기 임기를 그 값으로 바꾸고 표를 준 기록과 알고 있는 리더를 비운다. 이때 후보나 리더였다면 팔로워가 된다(4.21). 요청이든 응답이든 같다. 그다음 메시지 종류마다 정한 규칙을 따른다.

[4.21] 후보나 리더가 팔로워가 되면 FOLLOWER 사건을 출력하고 선거 타이머를 다시 맞춘다. 이미 팔로워인 노드가 4.20 으로 임기만 바꿀 때는 사건이 없고 선거 시각도 그대로다.

### 선거

[4.22] 노드가 선거를 시작하면 임기를 1 올리고 후보가 되며 자기에게 표를 준다. 알고 있는 리더를 비우고 시작한 선거 수를 1 늘린 뒤 선거 타이머를 다시 맞춘다. 그래서 새 선거 시각에는 늘어난 선거 수로 고른 타임아웃을 쓴다(4.9). 그다음 CANDIDATE 사건을 출력한다. 자기 표만으로 과반수이면 곧바로 리더가 된다(4.25). 그렇지 않으면 다른 모든 노드에 노드 순서대로 RequestVote 를 보낸다.

[4.23] RequestVote 를 받은 노드는 4.20 을 따른 뒤 요청의 임기가 자기 임기보다 작으면 표를 주지 않는 응답을 보낸다. 요청의 임기가 자기 임기와 같으면 이 임기에 아직 아무에게도 표를 주지 않았을 때만 그 후보에게 표를 준다. 표를 주는 노드는 그 후보를 표를 준 기록에 남기고 선거 타이머를 다시 맞춘 뒤 표를 준 응답을 보낸다. 이 임기에 이미 표를 주었으면 표를 주지 않는 응답을 보낸다. 후보와 리더는 자기 임기에 자기에게 표를 주었으므로 같은 임기의 다른 후보에게 표를 주지 않는다.

[4.24] RequestVote 응답을 받은 노드는 4.20 을 따른 뒤 자기가 후보이고 응답의 임기가 자기 임기와 같으며 표를 준 응답일 때만 응답한 노드의 표를 센다. 자기 표를 포함해 현재 임기에 받은 표가 과반수가 되면 리더가 된다. 그 밖의 응답은 4.20 말고는 아무 일도 일으키지 않는다. 지난 임기에 보낸 요청의 응답이 늦게 도착한 경우가 여기에 해당한다.

[4.25] 리더가 되는 노드는 역할을 리더로 바꾸고 알고 있는 리더를 자기로 정한다. 리더에게는 선거 시각이 없다. LEADER 사건을 출력한 뒤 다른 모든 노드에 노드 순서대로 AppendEntries 를 곧바로 보낸다.

[4.26] 리더는 타이머 단계마다 다른 모든 노드에 노드 순서대로 AppendEntries 를 보낸다. 리더가 될 때 보내는 AppendEntries(4.25)와 이것을 모두 하트비트라 부른다. 다만 리더가 된 틱의 타이머 단계에서는 보내지 않는다. 리더가 될 때 이미 보냈기 때문이다.

[4.27] AppendEntries 를 받은 노드는 4.20 을 따른 뒤 요청의 임기가 자기 임기보다 작으면 실패 응답을 보내고 다른 일은 하지 않는다. 요청의 임기가 자기 임기와 같으면 요청을 받아들인다. 받아들인 노드는 후보였다면 팔로워가 되고(4.21) 알고 있는 리더를 보낸 노드로 정한 뒤 선거 타이머를 다시 맞추고 성공 응답을 보낸다. 한 임기의 리더는 하나뿐이므로 리더가 자기 임기와 같은 임기의 AppendEntries 를 받는 일은 없다.

[4.28] AppendEntries 응답을 받은 노드는 4.20 을 따른다. 1단계에서는 그 밖에 아무 일도 일어나지 않는다.

### 사건 줄과 STATE

[4.29] TICK 은 처리하는 동안 일어난 사건을 일어난 차례대로 한 줄에 하나씩 출력한다. 노드가 선거를 시작하면 `<시각> <노드> CANDIDATE <임기>` 를, 리더가 되면 `<시각> <노드> LEADER <임기>` 를, 후보나 리더가 팔로워가 되면 `<시각> <노드> FOLLOWER <임기>` 를 출력한다. 시각은 사건이 일어난 틱이고 임기는 사건이 일어난 뒤 그 노드의 임기다. 팔로워가 임기만 바꾸는 일은 사건이 아니다.

[4.30] `STATE <노드>` 는 `<노드> <역할> term=<임기> vote=<표를 준 노드> leader=<알고 있는 리더> deadline=<선거 시각>` 한 줄을 출력한다. 역할은 `follower`, `candidate`, `leader` 가운데 하나다. 현재 임기에 아무에게도 표를 주지 않았으면 표를 준 노드 자리에 `-` 를 쓴다. 알고 있는 리더가 없으면 그 자리에 `-` 를 쓴다. 리더는 선거 시각 자리에 `-` 를 쓴다. 노드가 없으면 `ERR NO_NODE` 를 출력한다.

[4.31] 알고 있는 리더는 노드가 AppendEntries 를 받아들일 때 보낸 노드로 정하고 리더가 될 때 자기로 정한다. 4.20 으로 임기를 바꿀 때와 선거를 시작할 때 비운다. 그 밖에는 바뀌지 않는다.

## 5. 오류 규칙

[5.1] 오류가 나면 `ERR` 로 시작하는 오류 줄 하나만 출력한다. 오류를 낸 명령은 상태를 바꾸지 않는다. 프로그램은 다음 줄을 이어서 처리한다.

[5.2] 명령어가 NODE, TICK, DELAY, DROP, PARTITION, HEAL, STATE 가운데 어느 것과도 정확히 같지 않으면 `ERR UNKNOWN_COMMAND` 를 출력한다. 다만 REQUEST, LOG, NEXT 는 2단계에서, COMMIT, GET 은 3단계에서 명령이 되므로 이 문서는 명령어가 이 다섯 가운데 하나인 줄의 출력을 정하지 않는다.

[5.3] 인자 수가 맞지 않거나 인자가 형식에 맞지 않으면 `ERR BAD_ARGUMENT` 를 출력한다. 인자 수는 NODE 가 2 이상 11 이하, TICK 과 STATE 가 1, DELAY 와 DROP 이 3, PARTITION 이 1 이상, HEAL 이 0 이다. 노드 이름 자리는 3.11 의 노드 이름이어야 하고 수 자리는 3.10 의 정수이면서 명령마다 정한 범위 안에 있어야 한다. PARTITION 의 무리는 노드 이름 하나 이상을 쉼표 하나씩으로 이은 문자열이어야 한다. 무리 안에는 공백이 들어갈 수 없으므로 `PARTITION a, b` 의 인자는 `a,` 와 `b` 이고 `a,` 는 형식에 맞지 않는다.

[5.4] 명령은 명령어를 먼저 확인하고 인자 수와 형식을 확인한 뒤 4절에 명령마다 적은 확인을 한다. NODE 는 `ERR STARTED` 를 `ERR NODE_EXISTS` 보다 먼저 확인한다. DELAY 와 DROP 은 `ERR NO_NODE` 를 `ERR SAME_NODE` 보다 먼저, PARTITION 은 `ERR NO_NODE` 를 `ERR BAD_PARTITION` 보다 먼저 확인한다. 처음 걸린 오류 하나만 출력한다.

[5.5] 이 단계의 오류 줄은 아래와 같다.

| 오류 줄 | 뜻 |
|---|---|
| `ERR UNKNOWN_COMMAND` | 모르는 명령어 |
| `ERR BAD_ARGUMENT` | 인자 수나 형식이 틀림 |
| `ERR NO_NODE` | 없는 노드를 가리킴 |
| `ERR NODE_EXISTS` | 같은 이름의 노드가 이미 있음 |
| `ERR STARTED` | 시각이 0 보다 큰데 노드를 만들려 함 |
| `ERR SAME_NODE` | 보내는 노드와 받는 노드가 같음 |
| `ERR BAD_PARTITION` | PARTITION 에 같은 노드가 두 번 이상 나옴 |

## 6. 예시

[6.1] 예시 블록 하나는 프로그램을 한 번 실행한 기록이다. `> ` 로 시작하는 줄은 입력이고 나머지 줄은 바로 위 입력의 출력이다. 실제 입력에는 `> ` 가 없다.

[6.2] 기본 선거다. 시각 5 에 a 가 먼저 타임아웃되어 임기 1 의 후보가 된다. RequestVote 는 시각 6 에 b 와 c 에 도착하고 둘 다 표를 준다. 시각 7 에 b 의 응답이 먼저 전달되어 a 는 자기 표와 합쳐 과반수인 2표를 얻고 리더가 된다. c 의 응답은 a 가 이미 리더라서 세지 않는다. a 는 리더가 된 시각 7 에 하트비트를 보내고 시각 8 부터는 타이머 단계마다 보낸다. TICK 이 끝난 시각 10 에 b 의 선거 시각은 시각 10 에 받은 하트비트로 다시 맞춘 18 이다.

```
> NODE a 5
> NODE b 8
> NODE c 9
> TICK 10
5 a CANDIDATE 1
7 a LEADER 1
> STATE a
a leader term=1 vote=a leader=a deadline=-
> STATE b
b follower term=1 vote=a leader=a deadline=18
> STATE c
c follower term=1 vote=a leader=a deadline=19
```

## 7. 검사 방식

[7.1] 엔진은 테스트마다 풀이의 `run.sh` 를 새 프로세스로 실행한다. 작업 디렉터리는 풀이 디렉터리다.

[7.2] 엔진은 테스트의 입력 줄을 LF 로 잇고 마지막 줄 뒤에도 LF 를 붙여 표준 입력에 쓴 뒤 표준 입력을 닫는다.

[7.3] 프로세스가 0 이 아닌 종료 코드로 끝나면 실패다.

[7.4] 표준 출력만 기대 출력과 비교하고 표준 오류는 비교하지 않는다. 각 줄 끝의 공백, 탭, CR 을 지우고 끝에 붙은 빈 줄을 지운 뒤 줄 수와 각 줄의 내용이 정확히 같아야 한다. 사건 줄의 시각, 순서, 임기나 STATE 의 값이 하나라도 다르면 실패다.

[7.5] 일반 테스트의 제한 시간은 10초다. 제한 시간을 넘기면 엔진이 프로세스를 끝내고 실패로 판정한다.

[7.6] 대규모 테스트는 노드 7개 안팎에 TICK 으로 흐르는 시각이 모두 200,000틱 안팎인 입력이다. 몇몇 링크의 지연을 수만 틱까지 늘려 보냈지만 아직 도착하지 않은 메시지가 수십만 개에 이르는 구간이 길다. 분할과 복구와 DROP 으로 선거가 수백 번 일어나고 STATE 가 수천 개 섞인다. 제한 시간은 20초다. 틱마다 아직 도착하지 않은 메시지를 모두 훑어 그 틱에 도착할 메시지를 고르는 풀이는 이 제한 시간을 넘기도록 규모를 정했다.

[7.7] 검사 입력의 한 줄은 UTF-8 로 1,000바이트 이하다. 노드는 15개 이하이고 한 입력에서 흐르는 시각은 모두 1,000,000틱 이하다.

[7.8] 1단계 검사 입력에는 5.2 가 출력을 정하지 않은 줄이 나오지 않는다.

[7.9] 2단계와 3단계를 검사할 때도 1단계 테스트를 다시 실행한다. 1단계 검사 입력에는 REQUEST 가 없어 모든 노드의 로그가 비어 있으므로 뒤 단계의 규칙도 1단계 명령의 출력을 바꾸지 않는다.

[7.10] 3.3 의 마지막 문장과 3.8 은 엔진이 검사하지 않는다. 엔진은 입력의 마지막 줄 뒤에도 LF 를 붙이고(7.2) 출력 줄 끝의 CR 과 끝에 붙은 빈 줄을 지운 뒤 비교하기(7.4) 때문이다. 두 규칙은 표준 입출력 프로그램의 관례라서 적어 둔다.

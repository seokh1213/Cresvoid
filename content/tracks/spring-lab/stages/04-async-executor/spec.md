# @Async 실행기와 큐

[1] 이 단계는 observe 뒤 tune 순서로 진행한다. 먼저 관찰용 실행기의 수락·실행·큐·거절 수를 예측하고 근거를 적어라. 시작 코드를 빌드하고 실험의 지표와 /stats를 관찰한 뒤 `src/main/kotlin/lab/ExecutorPolicy.kt`만 고쳐라. tuned의 세 부하 조건마다 큐가 차는 시점과 스레드가 늘어나는 시점을 설명하고, 관찰용 buffered 설정을 그대로 쓰면 어떤 예산을 어기는지 확인하라. `@Async`가 붙은 Worker는 Spring 컨테이너에서 가져온 프록시를 통해 호출한다. 같은 객체 안에서 직접 호출하는 구조로 바꾸지 마라.

[2] 프로젝트 루트의 `.lab-libs`는 `spring`이다. JDK 21과 저장소가 제공하는 실행 이미지의 Spring을 사용한다. `build.sh`는 `build/app.jar`를 만들고 `run.sh`는 PORT 환경 변수로 받은 포트에서 서비스를 실행한다. 호스트의 공개 주소는 루프백뿐이며, 컨테이너 안에서는 포트 전달을 위해 전체 인터페이스에 바인딩한다. 라이브러리를 추가하거나 내려받지 마라. 실험기는 앱을 한 번 시작하고 준비 확인부터 종료까지 맡는다.

[3] 서비스에는 서로 독립적인 wide, direct, buffered, tuned-small, tuned-mid, tuned 실행기가 있다. 앞의 세 실행기는 관찰용으로 고정하며 core=4, max=8, 거절 정책은 AbortPolicy다. 큐 용량은 wide가 Int.MAX_VALUE, direct가 0, buffered가 8이다. wide는 이 실험에서 사실상 무제한인 큐다. 뒤의 세 실행기는 같은 tunedExecutor 함수로 각각 새로 만들므로 설정은 같고 작업·문·계측은 독립적이다. 실제 작업은 문(CountDownLatch 게이트)이 열리기를 기다린 뒤 1,000ms 동안 Thread.sleep을 한 번 호출한다. 문을 기다리는 작업도 실행 중으로 센다. 작업 수·대기·완료 시각·실행 스레드 기록은 바꾸지 마라.

[4] GET /health는 준비 후 200과 ready를 반환한다. POST /jobs?lane=<실행기>&id=<0 이상 2147483647 이하의 정수>는 작업 하나를 제출하며 수락하면 202, 실행기가 거절하면 503, 이미 수락한 id이면 409를 반환한다. id는 실행기별로 구분한다. 거절한 id는 기록에서 제거하여 다시 제출할 수 있게 한다. POST /release?lane=<실행기>는 그 실행기의 문을 영구히 열고 200을 반환하며 재호출해도 같다. GET /stats?lane=<실행기>는 accepted, running, completed, peak, queued, threads, failed를 각 한 줄의 key=정수로 반환한다. accepted는 수락한 고유 작업 수, running은 현재 실행 중인 수, completed는 정상 완료 수, peak는 running의 최댓값, queued는 실제 실행기 큐의 크기, threads는 실행기가 만든 스레드 수의 최댓값, failed는 중단된 작업 수다. GET /events?lane=<실행기>는 수락한 작업마다 id,submitted_ms,started_ms,finished_ms,thread 형식의 CSV 한 줄을 id순으로 반환한다. 시각은 실행기 생성 이후 단조 시계의 경과 밀리초다. 시작·완료 전 시각은 -1이며 모든 조회는 200이다. 실행기나 id가 잘못되면 400, 알려진 경로의 메서드가 다르면 405, 그 밖의 경로는 유효한 lane에 대해 404다.

[5] 실험은 새 서비스에서 wide, direct, buffered, tuned-small, tuned-mid, tuned 순으로 각각 100, 100, 100, 4, 9, 40개를 제출한다. 각 묶음의 id는 0부터 시작하며 개방형 부하로 1ms 간격의 예정 시각에 제출한다. 앞선 응답이 늦어져도 다음 요청의 도착을 늦추지 않는다. 각 묶음 뒤에는 문을 닫아 둔 채 최대 10초 동안 작업 시작을 기다리고 상태를 읽는다. 아직 작업이 완료될 수 없으므로 실행 수와 큐 길이의 관계를 시간 추정 없이 비교할 수 있다. 관찰용 세 실행기의 상태는 [3]과 [11]의 규칙에서 유도하라.

[6] tuned의 목적은 평상시 스레드 비용을 줄이면서 유한한 큐와 폭주 처리 여력을 확보하는 것이다. 문을 열기 전 tuned-small의 4개 요청은 전량 수락하고 running, peak, threads가 각각 2여야 한다. tuned-mid의 9개 요청도 전량 수락하되 running, peak, threads는 각각 4 이하, queued는 5 이하여야 한다. tuned의 40개 요청에서는 running, peak, threads 각각 6 이하와 queued 5 이하의 예산을 모두 사용하여 수락 수를 최대화하고 나머지는 거절해야 한다. 각 묶음의 accepted, running, queued, 거절 수는 이 예산과 큐 우선 삽입 규칙에서 유도하라. completed와 failed는 모든 실행기에서 0이어야 한다. 제출 요청은 202 또는 503으로만 끝나야 하며 실행기별 제출 응답 p95는 3,000ms 이하여야 한다. 큐 한도를 없애거나 예산보다 풀을 키우거나 호출자에게 작업을 실행시키는 방식으로 폭주를 넘기지 마라. 이 제한은 작업 내용 대신 응답만 빨리 반환하는 구현도 허용하지 않는다.

[7] 여섯 묶음의 상태를 읽은 뒤 모든 문을 열어라. 실험은 최대 75초 동안 배출을 기다린다. 수락한 모든 id는 정확히 한 번 정상 완료되고 거절한 id는 실행 기록에 없어야 한다. 최종 running과 queued와 failed는 0이며 accepted와 completed는 HTTP 202 수와 같아야 한다. 각 기록은 0 ≤ submitted_ms ≤ started_ms, finished_ms - started_ms ≥ 1,000을 만족해야 한다. 실행 스레드 이름은 async-<실행기>-로 시작해야 한다. 완료 시각으로 배치가 끝나는 순서를 관찰하라. wide의 작업 100개를 core 4개가 처리하면 작업 시간만으로 약 25초가 필요하지만 공유 기계에서는 더 걸릴 수 있다. 약 25초라는 값을 합격 경계로 쓰지 않는다.

[8] 배출이 끝나면 tuned에 id 100~103인 요청 4개를 10ms 간격의 개방형 부하로 제출하라. 네 요청 모두 202여야 하고 10초 안에 정확히 한 번 정상 완료되어야 한다. 이 기록도 작업 시간과 async-tuned- 스레드 이름 계약을 지켜야 한다. 누적 peak는 6을 넘지 않아야 하며 큐와 실행 중인 작업은 다시 0이 되어야 한다. 일시적 폭주 뒤에 실행기를 영구히 닫거나 이후 작업을 버리면 실패다.

[9] 실험 지표 wide_parallel, direct_parallel, buffered_parallel, tuned_parallel은 문을 열기 전 각 peak다. tuned_queue, tuned_accepted, tuned_rejected는 tuned의 문을 열기 전 큐 길이와 최초 40개 제출의 수락·거절 수다. max_lane_submit_p95_ms는 여섯 묶음 각각에서 구한 제출 응답 p95의 최댓값이며 후속 4개는 제외한다. p95는 응답 시간을 오름차순으로 정렬한 뒤 ceil(0.95 × 요청 수)번째 값이다. invariant_failures는 실패한 검사 수이며 합격은 0이다. failure_mask는 실패한 검사 종류에 해당하는 비트값을 비트 OR로 합친 정수다. 값 1은 관찰용 상태, 2는 tuned-small 상태, 4는 tuned-mid 상태, 8은 tuned 폭주 상태, 16은 실행기별 p95, 32는 문 열기·배출·최종 개수, 64는 최초 작업 기록·최종 peak, 128은 후속 회복이다. 예를 들어 6이면 작은 부하와 중간 부하 상태가 모두 실패한 것이므로 해당 lane의 /stats를 확인하라. 같은 종류의 검사 여러 개가 실패해도 비트는 한 번만 켜진다. 시간 제한 안에서 지표를 낸 뒤 종료 코드 1로 끝나면 불변식 실패이며 빌드 실패·실험 오류·시간 초과는 같은 결과로 취급하지 않는다.

[10] 수정은 ExecutorPolicy.kt의 tunedExecutor 설정과 거절 정책에 한정한다. 반환형 ThreadPoolTaskExecutor와 공개 함수 이름을 유지하라. Main.kt, Work.kt, 관찰용 세 실행기, HTTP 계약, 문, 1,000ms 작업, 계측, .lab-libs와 빌드·실행 스크립트는 바꾸지 마라. 별도 실행기나 스레드, 외부 저장소, 작업을 담는 다른 큐를 추가하지 마라.

[11] 근거는 [Spring 실행 및 스케줄링 문서](https://docs.spring.io/spring-framework/reference/integration/scheduling.html), [ThreadPoolTaskExecutor API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/concurrent/ThreadPoolTaskExecutor.html), [JDK 21 ThreadPoolExecutor API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)에서 확인하라. Spring 7.0.10 문서 기준으로 @Async의 기본 프록시 모드는 프록시를 거치는 호출에 적용된다. ThreadPoolTaskExecutor의 양수 큐 용량은 LinkedBlockingQueue를, 0은 SynchronousQueue를 사용한다. ThreadPoolExecutor는 core까지 스레드를 만든 뒤 큐에 넣고, 큐에 넣지 못할 때 max까지 늘린다. AbortPolicy의 거절은 Spring 경계에서 TaskRejectedException으로 전달된다. 이 단계의 core=4와 max=8은 관찰용 실행기에 명시한 실험값이며 Spring이나 Spring Boot의 기본값을 뜻하지 않는다.

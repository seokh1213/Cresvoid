# 가상 스레드와 풀

[1] 이 단계는 견적 서비스의 동시 실행 정책을 고치는 tune 실험이다. 먼저 `starter/`를 빌드하고 `quote-arrivals` 시나리오의 지표를 관찰해라. 가상 요청 스레드 수와 DB 연결 수, 하위 호출 수를 구분해 병목과 대기 위치를 설명한 뒤 `QuoteService.kt`를 수정하고 같은 실험을 다시 실행해라. 정답이나 실험기 대신 공개 계약과 시작 코드를 근거로 판단해라.

[2] 실행 환경은 JDK 21과 고정 실행 이미지에 담긴 Spring Boot, HikariCP, H2다. 루트의 `.lab-libs`는 `spring`이며 모든 서비스 코드는 `lab` 패키지에 있다. `./build.sh`가 `build/app.jar`를 만들고 `PORT=18080 ./run.sh`가 호스트의 `127.0.0.1:18080`에서 서비스를 공개한다. 이미지 안에서는 8080에 바인딩한다. 실험기는 `JAVA_OPTS`에 `-Djdk.virtualThreadScheduler.parallelism=2 -Djdk.virtualThreadScheduler.maxPoolSize=2`를 넣어 가상 스레드 스케줄러를 둘로 고정한다. 손으로 같은 조건을 보려면 같은 `JAVA_OPTS`를 붙여 `./run.sh`를 실행해라. 새 라이브러리를 내려받지 마라. Gradle 파일은 IDE용이며 검증은 두 셸 스크립트를 사용한다.

[3] `spring.threads.virtual.enabled=true`를 유지해라. 가상 스레드는 블로킹 대기를 저렴하게 만들지만 DB 연결이나 하위 서비스의 처리 용량을 늘리지 않는다. 예를 들어 동시에 연결을 빌리는 가상 스레드가 1,000개이고 연결이 10개라면 나머지는 연결 획득 지점에서 기다릴 수 있다. JDK 21에서 가상 스레드가 `synchronized` 모니터 안에서 블로킹하면 운반 스레드를 고정할 수 있다. 이 단계는 운반 스레드를 2개로 제한하며, 차단 가능한 호출을 모니터로 감싸지 마라. JDK 24의 모니터 고정 개선을 JDK 21의 동작으로 가정하지 마라.

[4] 공개 작업 API는 `GET /quote/{id}`다. 이 단계의 입력 계약은 `0..2147483540` 범위의 정수 id이며, 범위 밖 입력의 처리는 평가하지 않는다. 상한은 `Int` 가격이 넘치지 않는 최댓값이다. 성공은 HTTP 200과 UTF-8 평문 `id:가격`이며 가격은 `id + 107`이다. 예를 들어 `/quote/3`의 본문은 `3:110`이다. 작업 용량이 꽉 찼으면 대기열에 넣거나 DB를 빌리지 말고 HTTP 429와 평문 `busy`를 반환해라. 성공마다 `Resources.price(id)`로 H2의 매개변수 쿼리를 정확히 한 번 실행하고 그 결과로 `Downstream.quote(price)`를 정확히 한 번 호출해라. 재시도, 캐시, 고정 응답, 비동기 작업 누적은 허용하지 않는다.

[5] `GET /health`는 200과 `ready`를 반환한다. 관찰용 `GET /metrics`는 `이름=정수` 형식의 평문을 반환한다. `received`, `virtual`, `finished`는 작업 API의 진입 수, 가상 스레드에서 진입한 수, 응답을 결정한 수다. `queries`, `calls`는 실제 DB 쿼리와 하위 호출 누적 수, `active`, `peak`는 하위 호출의 현재·최대 동시 실행 수다. `pool_active`, `pool_pending`은 Hikari가 빌려준 연결과 획득 대기 스레드의 현재 수다. 이 값의 계측 코드는 수정하지 마라.

[6] 시나리오는 빈 루프백 포트를 골라 서비스를 한 번 시작하고 준비를 확인한다. 보류하지 않은 정상 요청 4개를 순차 실행한 뒤 보류 구간 두 번과 복구 구간을 실행한다. 보류 구간마다 `POST /fixture/hold`로 하위 호출의 반환을 막고, 앞 요청의 완료와 무관하게 초당 40개씩 1.2초 동안 서로 다른 id의 작업 요청 48개를 보낸다. 모든 요청이 진입하고 완료되었거나 하위 호출에 들어간 상태까지 최대 12초 기다린 뒤 `POST /fixture/release`로 풀어 준다. 보류 요청의 제한 시간은 30초이며 예열·복구 요청은 5초다. 하위 호출 보류는 느린 의존성을 모사한다. 각 DB 작업은 연결을 빌린 상태에서 150ms 대기한 뒤 쿼리를 실행하고 즉시 연결을 반환한다. 각 보류 구간에서 48개 중 정확히 4개가 200, 나머지 44개가 429여야 한다.

[7] 하위 호출의 최대 동시 실행 수는 정확히 4여야 하고, 보류 중 약 20ms 간격으로 관측한 Hikari 연결 대기 수의 최댓값은 0이어야 한다. 모든 보류 요청은 해제 전에 진입하고 완료되었거나 하위 호출에서 대기해야 한다. 429 응답은 DB 쿼리나 하위 호출을 만들면 안 된다. 두 보류 구간 사이에 실행 허가가 복구되어야 한다. 전역 직렬화나 모든 요청 거절로 상한만 지키는 수정은 통과하지 않는다.

[8] 마지막에는 보류를 해제한 상태로 초당 5개씩 1.6초 동안 복구 요청 8개를 보내며 모두 200이어야 한다. 예열을 포함한 108개 작업 요청 모두 가상 스레드에서 처리되어야 한다. 종료 시 모든 요청의 처리가 끝나야 하고 하위 실행 수와 빌린 연결 수는 0이어야 한다. DB 쿼리 수와 하위 호출 수는 각각 전체 200 응답 수인 20과 같아야 한다. 성공 본문과 거절 본문은 [4]를 그대로 따라야 하며 네트워크 오류, 다른 상태 코드, 작업 예외는 실패다.

[9] 지표 `burst_success=8`, `burst_rejected=88`, `recovery_success=8`, `downstream_peak=4`, `pool_wait_peak=0`, `virtual_requests=108`, `received=108`을 만족해라. `work_imbalance`는 |쿼리 수−200 수| + |하위 호출 수−200 수| + 종료 시 하위 실행 수 + 빌린 연결 수이며 0이어야 한다. `invalid_responses`는 계약을 어긴 응답 수와 12초 안에 [7]의 상태에 도달하지 못한 보류 구간 수의 합이며 0이어야 한다. `p95_ms`는 예열·보류·복구 응답 시간 108개에서 최근접 순위법으로 계산한 95백분위수다. 보류 시간이 포함되므로 이 값은 관찰용이며 합격 시간 기준으로 사용하지 않는다. 전체 합계가 맞아도 보류 구간 하나의 4개 성공 조건이 깨지면 실패다.

[10] 수정 범위는 `src/main/kotlin/lab/QuoteService.kt` 한 파일이다. 클래스와 `fun quote(id: Int): Int?`의 계약을 유지하되 내부 상태와 동시 실행 정책은 바꿀 수 있다. 허가를 받은 작업은 성공·실패·중단 어느 경로로 끝나도 자원을 반납해야 한다. HTTP 부하 전에 별도 JVM에서 DB 대기 중 중단 4회, 하위 호출 보류 중 중단 4회 뒤 정상 호출이 성공하는지 확인한다. 닫힌 DB 풀에서 SQL 예외를 8회 연속 일으켜도 허가 부족으로 거절하지 않아야 한다. 이 직접 호출은 HTTP 요청 108개의 지표에 포함하지 않는다. DB 풀 크기 4, 가상 스레드 설정, 가격 계산, 계측, fixture, 실행·빌드 파일은 바꾸지 마라.

[10.1] 직접 검사는 DB 중단·정상 호출, 하위 호출 중단·정상 호출, SQL 예외 순서로 실행하며 첫 실패에서 멈춘다. 실패하면 `permit_recovery=0`과 진단 지표를 출력하고 HTTP 부하 전에 불변식 실패로 끝낸다. `db_interruptions`, `downstream_interruptions`는 예외 전파와 자원 반환을 확인한 중단 횟수로 각각 4가 기대값이다. `db_recovery`, `downstream_recovery`는 각 중단 검사 뒤 `quote(3)`의 반환값으로 110이 기대값이다. 두 복구 지표에서 -1은 거절(null), -2는 예외, -3은 아직 실행하지 않았다는 뜻이다. `sql_exceptions`는 닫힌 풀에서 SQL 예외를 확인한 횟수로 8이 기대값이며, 닫힌 풀은 정상 호출로 복구하지 않는다. 중단·SQL 횟수의 초깃값은 0이다. 직접 검사를 모두 통과하면 이 진단 지표 대신 [9]의 HTTP 지표 10개를 출력한다.

[11] 배경은 [JEP 444](https://openjdk.org/jeps/444)의 가상 스레드와 JDK 21의 pinning 설명을 참고해라. Spring의 가상 스레드 설정은 [공식 task execution 문서](https://docs.spring.io/spring-boot/reference/features/task-execution-and-scheduling.html)를 참고해라. 이 실험은 모니터 고정 시간을 수치 판정하지 않으며, 실제 가상 요청 스레드 여부와 자원 용량을 계수로 판정한다.

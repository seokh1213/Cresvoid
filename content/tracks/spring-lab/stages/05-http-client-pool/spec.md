# HTTP 클라이언트 커넥션 풀

[1] 이 단계는 tune 실험이다. Spring 웹 서비스가 하나의 하위 서비스에 HTTP/1.1 요청을 보내는 상황을 다룬다. 현재 실행 이미지에는 Apache HttpClient가 없으므로 JDK 소켓으로 만든 교육용 풀을 사용한다. Apache의 설정 API나 기본값을 재현하는 단계는 아니다. 이 풀은 실제 TCP 연결을 재사용하며 전체 한도, 대상별 한도, 연결 임대 대기, 응답 본문 반납을 관측할 수 있다. 여기서 경로별 한도란 URL 경로가 아니라 같은 호스트와 포트로 향하는 연결의 한도다.

[2] 먼저 `src/main/kotlin/lab/PoolSettings.kt`, `Gateway.kt`, `HttpPool.kt`를 읽어라. 실험 전에 한도 5개와 응답 지연 100ms에서 가능한 처리량을 계산해라. 시작 코드를 실행해 응답 정확도, 임대 수, 대기 초과를 기록하고 세 값의 관계로 원인을 설명해라. 그다음 허용된 코드를 고쳐 같은 실험을 다시 실행해라. 정상 트래픽, 일부 본문만 읽는 요청, 하위 서비스 오류, 순간 폭주와 본문 장애 뒤의 상태를 비교해라. 관찰한 뒤에도 원인을 좁히기 어렵다면 마지막 힌트를 읽어라.

[3] 프로젝트 루트에서 `./build.sh`로 `build/app.jar`를 만들고 `PORT=<포트> ./run.sh`로 실행해라. Docker Desktop과 기존 실행 이미지의 `spring` 묶음을 사용한다. 임의 작업 공간에서는 `CRESVOID_ROOT`에 저장소 루트를 지정해라. 서비스 포트는 호스트의 루프백으로만 공개한다. 실험기는 앱을 compose로 시작하고 준비 상태를 확인한다. 하위 서비스는 실험기가 제공하며 앱에는 `UPSTREAM_HOST`와 `UPSTREAM_PORT`로 위치를 전달한다. `run.sh`로 직접 실행하면 같은 응답 계약의 내장 모의 하위 서비스를 사용한다. 하위 서비스 연결에는 프록시, TLS, 청크 전송, 재시도를 쓰지 않는다.

[4] 공개 계약은 다음과 같다. `GET /health`는 200과 `ready`를 반환한다. `GET /fetch?id=<식별자>&mode=<모드>`는 캐시나 재시도 없이 정확히 한 번 `/reply`를 호출하고 같은 식별자를 전달한다. 식별자는 영문자·숫자·하이픈으로 구성된다. `full`과 `hold`는 본문을 모두 읽어 200과 본문의 첫 `|` 앞 식별자를 반환한다. `peek`는 첫 바이트만 사용하고 200과 요청 식별자를 반환한다. `error`는 하위 서비스의 503을 502와 요청 식별자로 바꾼다. 풀에서 연결을 빌리지 못하면 하위 서비스를 호출하지 않고 504와 `POOL_TIMEOUT:<식별자>`를 반환한다. `GET /metrics`는 제공된 풀의 실제 계수와 설정을 `이름=정수` 형식으로 반환한다.

[5] `weekday-traffic`은 10/s로 1초 동안 정상 요청 10개를 보내 예열한다. 이어서 100/s로 3초 동안 `full` 요청 300개를 보내고, 30/s로 2초 동안 `full`, `peek`, `error` 순서를 반복해 60개를 보낸다. 하위 서비스는 요청마다 100ms를 기다린 뒤 식별자와 구분자, 8192바이트의 채움 본문을 보낸다. 각 구간은 이전 구간이 모두 끝나면 시작한다. 느린 응답이 다음 도착을 늦추지 않는 개방형 부하를 사용한다.

[6] `evening-traffic`은 `hold` 요청 64개를 같은 예정 시각에 보낸다. 하위 서비스는 이 모드에서 2000ms를 기다린다. 이 구간이 끝나면 40/s로 1초 동안 정상 요청 40개를 보내 회복을 확인한다. 두 시나리오 모두 HTTP 요청 제한 시간은 8초이며, 응답 시간은 부하 클라이언트가 요청을 보내기 시작한 시점부터 본문을 모두 받은 시점까지 측정한다. 백분위수는 오름차순으로 정렬한 표본의 올림 순위를 사용한다.

[7] 정상·혼합 부하에서는 예열을 포함한 370개 요청이 모두 완료되어야 한다. 모든 응답은 상태와 본문이 계약에 맞아야 한다. 하위 서비스 호출 수와 고유 식별자 수는 각각 370이어야 하며, 정상 부하 300개의 응답 시간 p95는 1000ms 이하여야 한다. 전체 측정 구간에서 하위 서비스의 최대 동시 처리 수는 8 이상이어야 한다. 풀 한도가 5일 때의 직렬화와 구별하기 위한 조건이다. 풀 대기 시간 초과는 0건이어야 한다.

[8] 폭주에서는 64개 중 적어도 40개를 풀 대기 초과로 거절하고 나머지는 정상 완료해야 한다. 풀 대기로 거절한 응답의 p95는 1200ms 이하여야 한다. 폭주 구간의 하위 서비스 호출 수는 정상 완료 수와 같아야 한다. 회복 구간의 40개는 모두 정상 완료하고 각각 하위 서비스를 한 번 호출해야 하며, 이 구간의 p95는 1000ms 이하여야 한다. 풀의 대기 시간 초과 계수는 관측한 504 응답 수와 같아야 한다. TCP 연결 수립 제한 2000ms와 소켓 읽기 제한 5000ms는 풀 임대 대기 제한과 별개다.

[9] 모든 시나리오에서 `maxTotal`과 `maxPerRoute`는 각각 1 이상 24 이하여야 한다. 앱 풀의 최대 임대 수, 생성한 TCP 연결의 누적 수, 하위 서비스가 본 서로 다른 연결 수와 최대 동시 처리 수는 모두 24 이하여야 한다. 측정 구간이 끝나고 200ms 뒤에는 임대 중 연결과 대기 요청이 모두 0이어야 한다. 폭주는 직후에도 임대·대기가 0인지 확인한다. 본문 장애 구간의 추가 관측 시점은 [13]을 따라라.

[10] 실험 결과의 `correct_responses`, `incorrect_responses`는 계약에 맞는 응답과 어긋난 응답의 개수다. `regular_p95_ms`, `timeout_p95_ms`, `recovery_p95_ms`는 해당 구간의 지연이다. `source_calls`, `source_peak`는 실험기 측 하위 서비스의 호출 수와 최대 동시 처리 수다. `open_connections`는 지금 열린 수가 아니라 앱이 생성한 연결의 누적 수다. `leased_after`, `pending_after`, `lease_timeouts`는 풀의 실제 계수다. `rejected`는 504 개수, `recovery_correct`는 회복 구간의 올바른 응답 수다. `budget_ok`가 1이면 설정·누적 연결·동시 처리 상한을 모두 지켰다는 뜻이다. 지표는 시나리오마다 최대 10개만 출력한다.

[11] 수정 범위는 `src/main/kotlin/lab/PoolSettings.kt`와 `src/main/kotlin/lab/Gateway.kt`뿐이다. 공유 풀은 하나만 사용해라. 나머지 소스와 빌드·실행 파일, 공개 경로, 하위 호출 규칙과 관측 계수는 바꾸지 마라. 신규 라이브러리, 풀 바깥 연결, 가짜 응답, 비동기 지연 호출, 캐시, 재시도로 통과시키지 마라.

[12] 공식 API 근거를 확인해라. [Apache PoolingHttpClientConnectionManager](https://hc.apache.org/httpcomponents-client-5.6.x/current/httpclient5/apidocs/org/apache/hc/client5/http/impl/io/PoolingHttpClientConnectionManager.html)는 전체 한도와 route별 한도를 구분한다. [RequestConfig.Builder](https://hc.apache.org/httpcomponents-client-5.6.x/current/httpclient5/apidocs/org/apache/hc/client5/http/config/RequestConfig.Builder.html)의 `setConnectionRequestTimeout`은 연결 관리자에서 연결을 빌리는 대기 제한이며 `setResponseTimeout`과 구분된다. [JDK 21 Socket](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/net/Socket.html)의 `connect(endpoint, timeout)`과 `setSoTimeout`은 연결 수립과 읽기 제한을 각각 정한다. 이 교육용 풀의 본문 반납 동작은 제공된 `PooledBody`의 계약을 따른다.

## 본문 장애와 회복

[13] `interrupted-traffic`은 새 앱에서 `eof` 요청 한 개와 `stall` 요청 한 개를 차례로 보낸다. 각 요청은 `/reply`를 정확히 한 번 호출하고 본문을 끝까지 읽는다. 하위 서비스는 100ms 뒤 200 상태와 정상 본문의 Content-Length를 보내고 첫 바이트만 전송한다. `eof`는 즉시 TCP 연결을 끊는다. `stall`은 추가 바이트 없이 연결을 30초 동안 유지한다. 두 요청 모두 502와 `UPSTREAM_IO:<식별자>`를 반환해야 한다. 장애 요청의 HTTP 제한 시간은 전송 시작부터 20초다. 직접 실행할 때의 내장 하위 서비스도 같은 장애를 재현한다.

[13.1] 각 장애 응답 본문을 부하 클라이언트가 모두 받은 시점에서 200ms 뒤에는 임대·대기가 모두 0이어야 한다. 이어서 40/s로 1초 동안 `full` 요청 40개를 보내 모두 계약대로 완료하고 p95가 1000ms 이하인지 확인한다. 하위 서비스 호출 수와 고유 식별자 수는 각각 42이고 풀 대기 초과는 0이어야 한다. 마지막 회복 응답 완료 200ms 뒤에도 임대·대기는 0이어야 한다.

[13.2] `fault_correct`는 올바른 장애 응답 수다. `fault_leased`와 `fault_pending`은 두 장애 후 관측값의 최댓값이다. 나머지 지표와 예산은 [9]와 [10]을 따른다.

## 관찰 뒤 힌트

[14] 응답 성공과 연결 반납은 별개의 사건이다. 본문을 전부 읽었다는 사실만으로 임대가 반납되지는 않는다. 제공된 `PooledBody.close()`는 남은 본문을 소비한 뒤 연결을 반납하고, 소비에 실패하면 연결을 폐기한다. 정상 분기뿐 아니라 부분 읽기, 하위 오류, 본문 읽기 예외 뒤의 경로를 추적해라. 읽기 제한 5000ms는 각 소켓 읽기에 적용되므로, 첫 읽기 시간 초과 뒤 정리 중에 다시 읽으면 최대 5000ms를 더 기다릴 수 있다. 정리 호출 순간의 반납을 요구하지 않는 이유다.

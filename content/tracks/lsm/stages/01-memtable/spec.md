# 01. 메모리 테이블과 정렬 파일

## 1. 개요

[1.1] 문자열 키와 값을 저장하는 LSM 저장소를 구현한다. 이번 단계는 메모리 테이블의 갱신, 삭제 표식, 정렬 파일 생성, 최신 버전을 반환하는 단건 조회를 다룬다. 목표 풀이 시간은 2~3시간이다.

[1.2] 정렬 파일은 메모리 안의 불변 데이터 묶음으로 모사한다. 실제 파일 입출력, 로그 복구, 동시 실행, 트랜잭션, 과거 시점 조회는 구현 범위에 없다. 프로그램은 표준 입력의 명령을 순서대로 실행하며, 프로세스가 끝나면 상태를 버린다.

## 2. 배경 개념

[2.1] LSM(Log-Structured Merge) 저장소는 갱신을 메모리에 모은 뒤 정렬된 묶음으로 내보낸다. 메모리 테이블은 아직 내보내지 않은 갱신을 담고, 정렬 파일인 SSTable은 내보낸 레코드를 키 순서로 보관한다. 내보내기는 flush라고 부른다. 한 키의 새 값이 생겨도 기존 정렬 파일을 직접 고치지 않으므로 여러 파일에 같은 키가 남을 수 있다.

[2.2] 삭제할 때 현재 메모리에서 키만 없애면 이전 파일의 값이 다시 보일 수 있다. 툼스톤(tombstone)은 이 키가 삭제됐다는 사실을 기록하는 레코드다. 조회가 최신 툼스톤을 만나면 더 오래된 값을 반환해서는 안 된다. 값 레코드와 툼스톤 모두 키와 갱신 순서를 갖는다.

[2.3] 쓰기 순서와 키 정렬 순서는 다르다. 정렬 파일에서는 키로 레코드를 찾지만, 여러 파일에 같은 키가 있으면 갱신 순서로 최신 버전을 판단한다. 파일을 다시 만드는 압축이 추가되면 파일 생성 순서만으로 레코드의 최신성을 판단할 수 없게 된다.

[2.4] 배경 자료는 [O'Neil 외, The Log-Structured Merge-Tree(1996)](https://www.cs.umb.edu/~poneil/lsmtree.pdf), Kleppmann의 Designing Data-Intensive Applications 초판 3장, [LevelDB 구현 설명의 Sorted tables 절](https://github.com/google/leveldb/blob/main/doc/impl.md)이다. 이 과제의 명령, 한도, 출력 형식은 아래에서 따로 정한 교육용 모형이다.

## 3. 입출력 규칙

[3.1] 입력은 UTF-8 표준 입력이며 EOF까지 한 줄씩 처리한다. 줄바꿈은 LF 또는 CRLF다. 줄 앞뒤의 ASCII 공백과 탭을 무시하고, 그 사이에 연속한 ASCII 공백과 탭은 토큰 구분자로 취급한다. 토큰이 없는 줄은 출력 없이 무시한다. 명령어는 대문자만 인정한다. 명령 개수를 나타내는 첫 줄은 없다.

[3.2] 키는 정규식 `[a-z][a-z0-9]{0,15}`에 맞는 1~16자 문자열이다. 값은 `[A-Za-z0-9_]{1,32}`에 맞는 1~32자 문자열이다. 따옴표, 이스케이프, 공백이 있는 값은 지원하지 않는다. 키 비교는 ASCII 사전순이며, 공통 접두부가 같으면 짧은 키가 먼저다. `a10`은 `a2`보다 앞선다.

[3.3] 정수 인자는 `[0-9]+` 형식만 인정하며 선행 0은 허용한다. 부호, 소수점, 지수 표기는 인정하지 않는다. 별도의 자리수 상한은 없고 정수의 유효성은 표기의 길이와 관계없이 수학적 값으로 판정한다. 형식이 맞아도 해당 명령의 범위를 벗어난 정수는 잘못된 인자다. 범위를 벗어난 정수는 표기가 매우 길어도 프로그램을 중단시키지 않고 오류로 처리한다.

[3.4] 출력은 각 명령에서 정한 줄만 표준 출력에 쓴다. 출력 토큰 사이는 ASCII 공백 하나이며, 파일 번호와 개수는 선행 0 없는 십진수다. 안내문이나 입력 에코는 출력하지 않는다. 정상 처리한 입력은 종료 코드 0으로 끝나야 한다.

[3.5] 한 입력은 비어 있지 않은 명령 줄 200,000개 이하이며, 잘못된 명령 줄도 이 수에 포함한다. 한 줄은 줄바꿈을 제외하고 1,024바이트 이하이다. 입력이 이 두 한도를 넘는 경우의 동작은 검사하지 않는다.

## 4. 명령 규칙

[4.1] `RESET <capacity>`는 용량이 capacity인 새 저장소를 만들고 `OK`를 출력한다. capacity의 범위는 1~4,096이다. 이미 저장소가 있어도 모든 레코드, 파일, 번호, 누적 계수를 버리고 다시 시작한다. 저장소는 프로그램 시작 시에는 없다. RESET의 성공 이후에만 다른 명령을 실행할 수 있다.

[4.2] 저장소의 메모리 테이블은 키마다 레코드를 하나만 가진다. 크기는 서로 다른 키의 수이며, 값과 툼스톤을 각각 레코드 1개로 센다. 같은 키의 새 레코드는 메모리 테이블의 기존 레코드를 교체한다. 키와 값의 길이는 크기에 영향을 주지 않는다.

[4.3] `PUT <key> <value>`는 해당 키의 새 값 레코드를 메모리 테이블에 기록하고 `OK`를 출력한다. `DEL <key>`는 새 툼스톤을 기록하고 `OK`를 출력한다. 존재하지 않는 키를 삭제하거나 같은 값을 다시 써도 새 갱신이다. 성공한 PUT과 DEL마다 전역 갱신 번호가 1씩 증가하며, 첫 갱신 번호는 1이다. 각 레코드는 자신이 만들어진 갱신 번호를 보존한다. 다른 명령과 실패한 명령은 갱신 번호를 소비하지 않는다.

[4.4] PUT 또는 DEL의 기록을 마친 직후 메모리 테이블 크기가 capacity와 같으면 즉시 전체를 flush한다. flush는 현재 레코드를 키 오름차순으로 정렬한 파일 하나를 레벨 0에 만들고 메모리 테이블을 비운다. 파일에는 같은 키가 두 번 들어가지 않으며, 툼스톤도 버리지 않는다. 자동 flush를 하더라도 해당 쓰기 명령의 출력은 `OK` 한 줄이다.

[4.5] `FLUSH`는 메모리 테이블이 비어 있지 않으면 4.4와 같은 flush를 실행하고 `OK`를 출력한다. 비어 있으면 파일을 만들지 않고 `OK`만 출력한다. EOF에서는 자동 flush를 하지 않는다.

[4.6] 새 파일은 저장소 전체에서 증가하는 파일 번호를 받는다. 첫 번호는 1이고, 파일을 하나 만들 때마다 1씩 증가한다. 빈 FLUSH와 오류는 번호를 소비하지 않는다. 파일 번호와 갱신 번호는 별개이며 RESET은 둘 다 초기화한다. 이번 단계의 모든 파일은 레벨 0에 있고 생성 이후 바뀌거나 사라지지 않는다.

[4.7] `GET <key>`는 메모리 테이블을 먼저 확인하고, 거기에 없으면 레벨 0 파일을 파일 번호 내림차순으로 확인한다. 키를 처음 발견한 레코드가 값이면 `VALUE <value>`, 툼스톤이면 `NOT_FOUND`를 출력하고 조회를 끝낸다. 어디에도 없으면 `NOT_FOUND`를 출력한다. 조회는 레코드, 파일, 번호를 바꾸지 않는다.

[4.8] `LAYOUT`은 첫 줄에 `MEM <메모리 테이블 크기>`를 출력한다. 이어서 현재 파일마다 `FILE <파일 번호> <레벨 번호> <레코드 수> <최소 키> <최대 키>`를 한 줄씩 출력하고 마지막 줄에 `END`를 출력한다. 파일 행은 레벨 번호 오름차순, 같은 레벨에서는 파일 번호 오름차순이다. 최소·최대 키에는 툼스톤의 키도 포함한다. 파일이 없으면 MEM 행과 END 행만 출력한다. LAYOUT은 상태를 바꾸지 않는다.

## 5. 오류 규칙

[5.1] 오류는 명령 줄마다 `ERROR` 한 줄로 출력하고 다음 줄을 계속 처리한다. 알 수 없는 명령, 인자의 개수·형식·범위가 틀린 명령, RESET 전에 실행한 RESET 이외의 명령은 오류다. 이번 단계에서 정의한 명령은 RESET, PUT, DEL, FLUSH, GET, LAYOUT뿐이다.

[5.2] 실패한 명령은 저장소 생성 여부, 메모리 테이블, 파일, 용량, 모든 번호와 누적 계수를 전혀 바꾸지 않는다. 이미 존재하는 저장소에 잘못된 RESET을 입력해도 기존 상태를 유지한다. 입력 전체를 미리 거절하지 않고 줄마다 성공과 실패를 결정한다.

## 6. 예시

[6.1] 다음 예시는 같은 키를 교체해도 메모리 크기가 늘지 않는 경우와 삭제 뒤 재기록을 보여 준다. 첫 flush의 `a`는 `NEW`이며 두 번째 flush의 `a`는 툼스톤이다.

입력:
```text
RESET 2
PUT a OLD
PUT a NEW
LAYOUT
PUT b B
DEL a
GET a
FLUSH
LAYOUT
GET b
PUT a BACK
GET a
```

출력:
```text
OK
OK
OK
MEM 1
END
OK
OK
NOT_FOUND
OK
MEM 0
FILE 1 0 2 a b
FILE 2 0 1 a a
END
VALUE B
OK
VALUE BACK
```

[6.2] 다음 예시에서는 잘못된 RESET 뒤에도 기존 레코드를 읽을 수 있다. 빈 FLUSH는 파일 번호를 쓰지 않는다.

입력:
```text
GET a
RESET 0001
FLUSH
PUT a A
RESET 0
GET a
put a B
LAYOUT
```

출력:
```text
ERROR
OK
OK
OK
ERROR
VALUE A
ERROR
MEM 0
FILE 1 0 1 a a
END
```

## 7. 검사 방식

[7.1] 각 검사는 프로그램을 새 프로세스로 시작하고, 명령 줄들을 표준 입력에 보낸 뒤 EOF로 닫는다. 표준 출력은 줄 끝 공백·탭·CR과 출력 끝의 빈 줄을 제거한 뒤 기대 출력과 줄 수 및 내용을 비교한다. 종료 코드가 0이 아니거나 표준 출력이 64MB를 넘으면 실패다. Kotlin 컴파일 시간은 실행 제한 시간에 포함하지 않는다.

[7.2] 일반 검사 하나의 실행 제한 시간은 20초, 대규모 검사 하나는 60초다. 고정 검사 10~14개와 생성 검사 2~3개를 사용하며, 마지막 검사는 대규모 입력이다. 생성 입력의 GET 결과는 PUT과 DEL을 바로 반영하는 단순한 맵 모형과 대조한다. LAYOUT은 파일 생성 규칙에서 별도로 기대값을 계산한다.

[7.3] 대규모 입력은 RESET 1줄, 서로 다른 키를 쓰는 PUT 100,000줄, GET 90,000줄로 총 190,001줄이며 capacity는 1,024이다. 조회에는 첫 파일과 마지막 파일의 키, 없는 키를 섞는다. 매 조회마다 모든 파일의 모든 레코드를 순회하는 구현을 구별하기 위한 규모다. 실제 디스크 처리량과 파일 입출력 시간은 채점하지 않는다.

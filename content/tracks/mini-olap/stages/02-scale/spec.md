# 2단계: 열 배치와 사전 부호화

## 1. 개요

[1.1] 2단계는 행 수백만 개를 다룬다. 탭으로 나눈 데이터 줄을 한꺼번에 넣는 COPY 명령과 서로 다른 값의 수를 세는 COUNT(DISTINCT) 집계를 더하고 1단계의 질의를 행 2,000,000개 안팎의 테이블에서 제한 시간과 메모리 상한 안에 실행하게 한다.

[1.2] 1단계의 입출력 규칙과 명령은 그대로다. 이 문서는 새로 생기는 규칙만 설명한다. 1단계 5.2 가 출력을 정하지 않은 명령어 가운데 COPY 와 1단계 5.4 의 넷째 경우인 COUNT(DISTINCT) 는 이 문서가 출력을 정한다.

| 더하는 것 | 하는 일 | 정상 출력 |
|---|---|---|
| `COPY <테이블> FROM STDIN` | 뒤따르는 데이터 줄을 행으로 넣는다 | 없음 |
| `COUNT(DISTINCT <열>)` | 그룹 안에서 그 열의 서로 다른 값을 센다 | SELECT 항목 |

[1.3] 새 규칙은 많지 않다. 이 단계의 일은 대부분 같은 질의를 큰 테이블에서 빠르고 작게 실행하도록 테이블을 담는 방식과 실행 방식을 고치는 데 있다.

## 2. 배경 개념

[2.1] 1단계까지는 행을 어떻게 담든 결과만 맞으면 되었다. 2단계는 같은 질의를 행 2,000,000개 안팎에서 실행하므로 테이블을 메모리에 어떤 모양으로 담는지가 속도와 메모리를 정한다. 기술 지문(`tech-reading` 트랙 3단계 "열 저장과 분석 질의")이 디스크의 행 저장과 열 저장을 견주었듯이 메모리 안의 테이블도 행 배치와 열 배치로 나눌 수 있다.

[2.2] 행 배치는 행 하나의 값들을 한 덩어리로 묶어 둔다. 행 하나를 넣거나 꺼내기는 쉽지만 열 하나를 집계하려 해도 모든 행 덩어리를 차례로 찾아가야 한다. 열 배치는 열마다 그 열의 값을 행 순서대로 이어 둔다. 열 몇 개만 쓰는 집계는 그 열들의 값만 앞에서부터 읽는다. 같은 자료형의 값이 메모리에 이어져 있어 CPU 캐시와 미리 읽기가 잘 듣고 연산은 배열을 도는 단순한 반복이 된다. 행 i 의 값은 열마다 i 번째 자리에 있으므로 여러 열의 같은 자리를 모으면 행을 언제든 다시 맞출 수 있다.

[2.3] JVM 에서는 이 차이가 더 크다. 행마다 객체나 배열을 만들고 값을 String 객체와 박싱한 Long 으로 담으면 객체마다 머리말이 붙고 값을 읽을 때마다 참조를 따라가야 한다. 이 문서를 쓰며 JDK 21 에서 7.4 와 같은 모양의 행 2,000,000개를 담아 보았다. 행마다 값 배열을 두고 값을 String 과 박싱한 Long 으로 담으면 힙을 460MB 남짓 썼고 최대 힙 256MB 에서는 OutOfMemoryError 로 멈췄다. 열 배치로 담고 문자열을 2.5 의 사전 부호화로 바꾸면 80MB 남짓이었다.

[2.4] 열 배치에서도 NULL 은 값과 다른 표시다. 0 이나 빈 문자열로 NULL 을 대신하면 진짜 0 과 빈 문자열을 NULL 과 구별할 수 없다. 1단계의 NULL 규칙은 2단계에서도 그대로다.

[2.5] 사전 부호화는 열에 나오는 서로 다른 값마다 작은 정수 번호를 붙이고 행에는 값 대신 번호를 담는 방식이다. 번호와 값의 대응을 사전이라 한다. 같은 문자열이 여러 행에 나와도 문자열은 사전에 한 번만 있고 행마다 번호 하나만 차지한다. 같은지 따지는 비교와 그룹 나누기는 문자열 대신 번호로 할 수 있다. 서로 다른 값의 수, 곧 카디널리티가 낮을수록 이득이 크다. Parquet 는 열마다 사전 부호화를 쓰다가 사전이 너무 커지면 사전 없는 방식으로 돌아간다. ClickHouse 설명서는 LowCardinality 자료형의 사전 부호화가 서로 다른 값이 10,000개보다 적을 때 특히 효과가 크고 100,000개를 넘으면 오히려 효율이 떨어질 수 있다고 적는다.

[2.6] 번호는 대개 값이 처음 나온 순서로 붙는다. 그러면 번호의 순서는 값의 순서(1단계 4.9)와 다를 수 있다. 같은지 따지는 비교와 그룹 나누기에는 번호만으로 충분하지만 `<` 와 `>` 같은 비교, MIN, MAX, 정렬에는 값의 순서가 필요하다.

[2.7] 기술 지문의 벡터화 실행처럼 열 배치에서는 연산자를 행 하나가 아니라 열 값의 묶음 단위로 실행할 수 있다. 조건을 열 단위로 계산해 통과한 행의 표시를 먼저 만들고 그 표시를 따라 필요한 열만 집계하면 행을 다시 맞추는 일을 끝까지 미룰 수 있다. 이렇게 필요할 때까지 행을 다시 맞추지 않는 방식을 늦은 실체화라 한다.

[2.8] 고유 수, 곧 서로 다른 값의 수를 정확히 세려면 이미 본 값을 모두 기억해야 하므로 메모리가 고유 수에 비례해 는다. 그룹마다 세면 그룹마다 따로 기억해야 한다. 기술 지문의 설명대로 나누어 센 고유 수를 더해서는 전체의 고유 수를 얻지 못한다. 사전 부호화한 열에서는 기억할 값이 작은 정수다.

[2.9] PostgreSQL 의 `COPY … FROM STDIN` 은 SQL 문 대신 데이터 줄을 받아 행을 넣는다. 텍스트 형식에서는 한 줄이 한 행이고 열 값을 탭으로 나누며 NULL 을 `\N` 으로 쓰고 `\.` 만 있는 줄로 데이터의 끝을 알린다. 넣던 도중에 실패하면 그때까지 넣은 행은 보이지 않는다. 이 트랙의 COPY 는 이 텍스트 형식을 줄인 것이다. 값을 작은따옴표로 감싸지 않으므로 빈 문자열은 아무 글자도 없는 칸이고 NULL 은 `\N` 이다. 행마다 SQL 문을 해석하지 않으므로 같은 행을 INSERT 보다 짧게 쓰고 빨리 읽는다.

## 3. 입출력 규칙

[3.1] 1단계의 입출력 규칙은 명령 줄에 그대로 쓴다. COPY 가 받는 데이터 줄(4.2)에는 1단계 3.5 와 3.6 을 쓰지 않는다. 데이터 줄은 앞뒤의 공백을 지우지 않고 빈 줄과 공백만 있는 줄도 데이터 줄이다.

[3.2] 1단계 4.8 의 INT 값 범위와 4.5 의 문자열 글자 규칙은 COPY 로 넣는 값에도 그대로 쓴다.

## 4. 명령 규칙

### COPY

[4.1] `COPY <테이블> FROM STDIN` 은 다음 줄부터 오는 데이터 줄을 그 테이블에 행으로 넣는다. 이 줄은 1단계 4.1~4.7 대로 토큰으로 나누고 COPY, 테이블 이름, FROM, STDIN 네 토큰이어야 한다. COPY 와 STDIN 은 이 단계에서 더하는 키워드다. 성공하면 아무것도 출력하지 않는다.

[4.2] 명령어가 COPY 인 줄 다음 줄부터 `\.` 두 글자만으로 된 줄 바로 앞까지가 그 COPY 의 데이터 줄이다. `\.` 줄은 COPY 를 끝낼 뿐 데이터 줄이 아니다. 앞뒤에 공백이 붙은 `\.` 은 끝 줄이 아니라 데이터 줄이다. COPY 줄에 오류가 있어도 데이터 줄은 같은 방식으로 정해진다. 데이터 줄은 명령으로 처리하지 않으므로 명령처럼 보이는 줄도 데이터 줄이다.

[4.3] 데이터 줄은 탭으로 나눈 칸들이다. 탭이 k 개인 줄은 칸이 k + 1 개다. 그래서 빈 데이터 줄은 빈 칸 하나이고 탭으로 끝나는 줄의 마지막 칸은 빈 칸이다.

[4.4] 칸은 앞에서부터 테이블의 열과 짝지어 값이 된다. 칸이 `\N` 이면 NULL 이다. INT 열의 칸은 1단계 4.3 에 맞는 정수여야 하고 그 정수가 값이다. STRING 열의 칸은 1단계 4.5 에서 쓸 수 있는 글자로만 되어 있어야 하고 칸의 글자 그대로가 값이다. 그래서 빈 칸은 STRING 열에서 빈 문자열이고 INT 열에서는 정수가 아니다. `NULL` 이라고 쓴 칸은 STRING 열에서 네 글자짜리 문자열이고 INT 열에서는 정수가 아니다. 칸의 앞뒤 공백도 값의 일부다.

[4.5] COPY 는 아래 순서로 확인하고 처음 걸린 오류 하나를 출력한다. 첫째, COPY 줄이 4.1 의 꼴이 아니면 `ERR SYNTAX` 다. 둘째, 테이블이 없으면 `ERR NO_TABLE` 이다. 앞의 두 오류에서는 데이터 줄을 확인하지 않는다. 셋째, 데이터 줄을 앞에서부터 하나씩 확인한다. 칸 수가 테이블의 열 수와 다르면 `ERR VALUE_COUNT <n>` 이고 칸 수가 맞지만 4.4 에 맞지 않는 칸이 있으면 `ERR TYPE <n>` 이다. n 은 그 데이터 줄이 그 COPY 의 몇째 데이터 줄인지를 1 부터 센 번호다.

[4.6] 오류가 나면 한 행도 넣지 않는다. 오류가 없으면 데이터 줄 하나를 행 하나로 보고 쓴 순서대로 테이블 끝에 넣는다. 데이터 줄이 하나도 없는 COPY 도 성공한다. COPY 로 넣은 행은 INSERT 로 넣은 행과 다르지 않다.

[4.7] COPY 의 출력은 많아야 한 줄이다. 오류가 나도 그 COPY 의 데이터 줄은 끝까지 데이터 줄로 읽고 `\.` 줄 다음 줄부터 명령으로 처리한다.

### COUNT(DISTINCT)

[4.8] `COUNT(DISTINCT <열>)` 은 1단계 4.15 의 집계에 더하는 꼴이다. DISTINCT 는 이 단계에서 더하는 키워드다. 그룹에서 NULL 이 아닌 그 열 값 가운데 서로 다른 값의 수다. 빈 문자열도 값으로 센다. NULL 이 아닌 값이 없으면 0 이다. INT 열과 STRING 열을 모두 받는다.

[4.9] 머리줄에는 COUNT, 여는 괄호, DISTINCT, 공백 하나, 열 이름, 닫는 괄호를 이어 `COUNT(DISTINCT user)` 처럼 쓴다. COUNT(DISTINCT) 의 열도 1단계 4.19 의 둘째 확인 대상이다. ORDER BY 의 키로 쓸 때는 1단계 4.20 대로 SELECT 목록의 같은 항목과 짝짓는다. `COUNT(DISTINCT ms)` 와 `COUNT(ms)` 는 다른 항목이다.

## 5. 오류 규칙

[5.1] 2단계에서 생기는 오류 줄은 `ERR VALUE_COUNT <n>` 과 `ERR TYPE <n>` 이다. INSERT 의 오류 줄은 1단계대로 번호 없는 `ERR VALUE_COUNT` 와 `ERR TYPE` 이다.

| 오류 줄 | 뜻 |
|---|---|
| `ERR VALUE_COUNT <n>` | COPY 의 n 째 데이터 줄의 칸 수가 열 수와 다름 |
| `ERR TYPE <n>` | COPY 의 n 째 데이터 줄에 열의 자료형에 맞지 않는 칸이 있음 |

[5.2] 명령어가 영문 대문자로만 이뤄졌는데 CREATE, INSERT, SELECT, COPY 가 아닌 줄이나 1단계 5.4 의 첫째, 둘째, 셋째, 다섯째 경우인 줄이 나오면 이 문서도 그 줄부터 입력 끝까지의 출력을 정하지 않는다. `\.` 줄이 오기 전에 입력이 끝나는 COPY 의 출력도 정하지 않는다.

## 6. 예시

[6.1] 예시의 형식은 1단계 6.1 과 같다. 데이터 줄의 탭은 `⇥` 로 나타낸다. 실제 입력에는 `⇥` 대신 탭 한 글자가 있다. 6.3 과 6.4 는 6.2 의 CREATE TABLE 과 COPY 를, 곧 6.2 의 입력 아홉 줄을 먼저 실행한 것으로 보고 그 줄들을 생략한다.

[6.2] COPY 와 COUNT(DISTINCT) 다. 둘째 데이터 줄의 page 는 빈 문자열이고 셋째 데이터 줄의 page 는 문자열 `'NULL'` 이다. 넷째 데이터 줄은 맨 앞에 공백이 있어 user 가 `' u1'` 이다. 이 값은 `'u1'` 과 다른 그룹이 되고 공백이 `u` 보다 앞서므로 먼저 나온다. page 가 `'NULL'` 인 그룹에서 user 는 NULL 뿐이라 COUNT(DISTINCT user) 가 0 이다.

```
> CREATE TABLE visits (user STRING, page STRING, ms INT)
> COPY visits FROM STDIN
> u1⇥/home⇥120
> u2⇥⇥\N
> \N⇥NULL⇥30
>  u1⇥/cart⇥45
> u1⇥/home⇥80
> u3⇥/cart⇥\N
> \.
> SELECT user, COUNT(*), COUNT(DISTINCT page), SUM(ms) FROM visits GROUP BY user
user|COUNT(*)|COUNT(DISTINCT page)|SUM(ms)
' u1'|1|1|45
'u1'|2|1|200
'u2'|1|1|NULL
'u3'|1|1|NULL
NULL|1|1|30
> SELECT page, COUNT(*), COUNT(DISTINCT user) FROM visits GROUP BY page
page|COUNT(*)|COUNT(DISTINCT user)
''|1|1
'/cart'|2|2
'/home'|2|1
'NULL'|1|0
> SELECT COUNT(DISTINCT user), COUNT(user), COUNT(*) FROM visits
COUNT(DISTINCT user)|COUNT(user)|COUNT(*)
4|5|6
> SELECT COUNT(*) FROM visits WHERE page = 'NULL'
COUNT(*)
1
> SELECT COUNT(*) FROM visits WHERE page IS NULL
COUNT(*)
0
```

[6.3] COPY 의 오류다. 첫 COPY 에서는 둘째 데이터 줄의 칸이 둘인 오류가 셋째 데이터 줄의 `x` 보다 먼저 걸린다. 둘째 COPY 의 ` 7` 은 앞에 공백이 있어 정수가 아니다. 셋째 COPY 의 마지막 칸은 비어 있어 INT 열에 맞지 않는다. 넷째 COPY 의 데이터 줄은 SELECT 처럼 보이지만 탭이 없는 칸 하나다. `stdin` 은 키워드가 아니므로 다섯째 COPY 는 문법 오류이고 그 뒤의 데이터 줄은 읽혀 버려진다. 오류가 난 COPY 는 한 행도 넣지 않으므로 마지막 SELECT 의 COUNT(*) 는 6.2 의 6 그대로다. 데이터 줄이 없는 COPY 는 성공한다.

```
> COPY visits FROM STDIN
> u4⇥/a⇥10
> u5⇥/b
> u6⇥/c⇥x
> \.
ERR VALUE_COUNT 2
> COPY visits FROM STDIN
> u4⇥/a⇥10
> u5⇥/b⇥ 7
> \.
ERR TYPE 2
> COPY visits FROM STDIN
> u5⇥/b⇥
> \.
ERR TYPE 1
> COPY visits FROM STDIN
> SELECT COUNT(*) FROM visits
> \.
ERR VALUE_COUNT 1
> COPY visits FROM stdin
> u7⇥/a⇥1
> \.
ERR SYNTAX
> COPY nope FROM STDIN
> u7⇥/a⇥1
> \.
ERR NO_TABLE
> COPY visits FROM STDIN
> u8⇥it's⇥1
> u9⇥/a⇥NULL
> \.
ERR TYPE 1
> COPY visits FROM STDIN
> \.
> SELECT COUNT(*), COUNT(DISTINCT ms) FROM visits
COUNT(*)|COUNT(DISTINCT ms)
6|4
```

[6.4] COPY 와 INSERT 로 넣은 행은 함께 집계된다. u1 의 ms 는 120, 80, 120 이라 COUNT(DISTINCT ms) 가 2 다. 고유 수가 1 인 그룹 가운데 user 가 NULL 인 그룹은 `user DESC` 의 기본값에 따라 맨 앞에 온다.

```
> INSERT INTO visits VALUES ('u1', '/home', 120), ('u9', NULL, NULL)
> SELECT user, COUNT(DISTINCT ms), MIN(page) FROM visits GROUP BY user ORDER BY COUNT(DISTINCT ms) DESC, user DESC LIMIT 3
user|COUNT(DISTINCT ms)|MIN(page)
'u1'|2|'/home'
NULL|1|'NULL'
' u1'|1|'/cart'
```

## 7. 검사 방식

[7.1] 입력 방식, 종료 코드 검사, 표준 출력 비교, 일반 테스트 제한 시간 10초는 1단계와 같다.

[7.2] 검사 입력의 한 줄은 UTF-8 로 65,536바이트 이하다. 테이블 하나의 열은 16개 이하이고 행은 10,000,000개 이하다. 검사 입력의 COPY 는 언제나 `\.` 줄로 끝난다.

[7.3] 2단계 검사 입력에는 5.2 가 출력을 정하지 않은 줄이 나오지 않는다.

[7.4] 대규모 테스트는 STRING 열 3개와 INT 열 3개로 된 테이블 하나에 COPY 로 행 2,000,000개를 넣는다. 데이터 줄은 모두 50MB 안팎이다. STRING 열의 서로 다른 값은 차례로 250,000개 안팎, 5,000개 안팎, 20개이고 INT 열의 값은 차례로 1~365, 1~20, 100~9,999 에 있다. 열마다 행의 몇 퍼센트는 NULL 이다. 그 뒤로 SELECT 180개 안팎이 이어진다. 질의의 5분의 2 는 서로 다른 값이 250,000개 안팎인 열로 묶은 뒤 정렬하고 LIMIT 으로 몇 행만 남긴다. 다른 5분의 2 는 그 열의 값 하나로 거른다. 나머지에는 그룹 수백 개 이하에서 COUNT(DISTINCT) 를 세는 질의와 STRING 열의 범위 비교, MIN, MAX 를 쓰는 질의가 섞인다. 제한 시간은 15초다. 행마다 값 배열을 두고 값을 String 과 박싱한 Long 으로 담는 풀이는 질의 실행 방식을 다듬어도 이 제한 시간을 넘기도록 규모를 정했다.

[7.5] 풀이는 최대 힙 256MB 에서도 대규모 테스트를 통과해야 한다. 엔진은 JVM 의 힙 크기를 정하지 않으므로 이 상한은 엔진이 검사하지 않는다. 테스트 입력은 공개하지 않으니 7.4 의 모양대로 입력을 만드는 프로그램을 직접 써서 `java -Xmx256m -jar build/app.jar < 입력 파일` 처럼 실행해 확인한다. 2.3 에서 잰 것처럼 행마다 값 배열을 두고 값을 String 과 박싱한 Long 으로 담는 배치는 이 상한을 넘는다.

[7.6] 2단계를 검사할 때 1단계 테스트도 다시 실행한다. 3단계를 검사할 때도 1단계와 2단계 테스트를 다시 실행한다.

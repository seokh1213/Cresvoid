# 1단계: 실행 계획과 스테이지

## 1. 개요

[1.1] 이 트랙에서는 작은 데이터 흐름 엔진을 만든다. 프로그램은 표준 입력으로 명령을 한 줄씩 받아 데이터셋을 정의하고 변환을 이어 붙여 파이프라인을 만들고 파이프라인의 실행 계획이나 실행 결과를 출력한다. 실행 모델은 Spark 의 RDD 를 줄인 것이다. 데이터는 파티션으로 나뉘어 있고 변환은 행동이 올 때까지 계산되지 않으며 셔플이 필요한 곳에서 스테이지가 나뉜다.

[1.2] 1단계의 명령은 아래 다섯 가지다.

| 명령 | 하는 일 | 정상 출력 |
|---|---|---|
| `DATA <이름> <파티션 수>` 와 행 블록 | 데이터셋을 만든다 | 없음 |
| `APPEND <이름>` 과 행 블록 | 데이터셋에 행을 더한다 | 없음 |
| `PIPE <이름> = <변환> \| <변환> …` | 파이프라인을 정의한다 | 없음 |
| `PLAN <이름>` | 실행 계획을 출력한다 | 스테이지마다 1줄 |
| `RUN <이름> [<개수>]` | 파이프라인을 실행해 결과 행을 출력한다 | 머리줄 1줄과 결과 행 0줄 이상 |

[1.3] 1단계는 지연 실행, 좁은 의존과 넓은 의존, 파티셔너, 스테이지 나누기, 결과 행의 순서를 다룬다. 1단계의 출력은 파티션마다 어떤 행이 놓이는지에 기대지 않는다. RUN 은 결과 행을 정해진 순서로 정렬해 출력하므로 엔진이 행을 어느 파티션에서 계산했는지는 출력에 드러나지 않는다.

[1.4] 2단계는 해시 파티셔닝 규칙을 정하고 셔플마다 쓴 레코드 수, 바이트 수, 흘림 파일 수를 보고하는 PROFILE 과 설정 명령 SET 을 더한다. 3단계는 두 파이프라인을 잇는 조인과 조인 전략, 쏠림 처리를 더한다. 4단계는 셔플 뒤의 실제 크기로 계획을 고치는 적응 실행을 더하고 행 수백만 개를 제한 시간 안에 처리하게 한다. 이 문서의 입출력 규칙과 명령 규칙은 4단계까지 그대로 쓴다. 뒤 단계는 이 문서가 정한 출력을 바꾸지 않는다. 뒤 단계에서 뜻이 생기는 줄이 나오면 이 문서는 그 줄부터 입력 끝까지의 출력을 정하지 않는다. 그런 줄은 4.15 와 5.2 에 적는다.

## 2. 배경 개념

[2.1] 데이터 흐름 엔진은 큰 데이터를 파티션이라는 조각으로 나누어 여러 실행기에서 나누어 처리한다. 파티션은 실행기 하나에 맡기는 데이터의 단위이고 파티션 수가 병렬로 처리할 수 있는 작업의 수를 정한다. 이 트랙의 데이터는 모두 키와 값으로 된 행이다. 같은 키를 가진 행끼리 모아 합치는 일이 이 트랙의 중심이다.

[2.2] 프로그램이 데이터에 적용하는 연산은 변환과 행동으로 나뉜다. map 이나 filter 같은 변환은 호출해도 바로 계산하지 않는다. 엔진은 어떤 데이터에 어떤 변환을 차례로 적용했는지만 기록하고 이 기록을 계보라 부른다. 결과를 프로그램에 돌려주는 연산을 행동이라 한다. 행동이 호출되면 엔진은 잡 하나를 만들어 계보를 따라 계산을 시작한다. 계산을 미루어 두므로 엔진은 계산하기 전에 변환 전체를 보고 실행 계획을 세울 수 있다. 이 방식을 지연 실행이라 한다.

[2.3] 지연 실행에는 눈에 보이는 결과가 있다. 변환을 정의한 때가 아니라 행동이 호출된 때 데이터를 읽으므로 그 사이에 원천 데이터가 늘었으면 행동은 늘어난 데이터로 계산한다. 엔진은 행동의 결과를 다음 행동에 물려주지 않는다. 같은 파이프라인에 행동을 두 번 호출하면 잡이 둘 생기고 두 잡은 저마다 원천부터 다시 계산한다. Spark 는 캐시를 지시받은 데이터나 이미 써 둔 셔플 출력을 다음 잡에서 다시 쓰기도 한다. 이 트랙의 엔진은 잡 사이에 아무것도 남기지 않는다.

[2.4] 실행 계획을 세우는 기준은 변환이 부모 파티션과 자식 파티션을 잇는 방식이다. 변환이 레코드를 넘길 자식 파티션을 부모 파티션 단위로 정하면 좁은 의존이고 레코드 단위로 정하면 넓은 의존이다. map 과 filter 는 부모 파티션 i 의 행을 자식 파티션 i 에만 넘기므로 좁은 의존이다. 키별로 모으는 연산은 같은 키의 행이 어느 부모 파티션에 있을지 모르면 행마다 키를 보고 넘길 자식 파티션을 정해 같은 키를 한곳에 모아야 하므로 넓은 의존이다. 데이터를 이렇게 파티션 사이에서 다시 나누는 일을 셔플이라 한다. 셔플은 앞쪽 실행기가 출력을 받을 파티션별로 디스크에 쓰고 뒤쪽 실행기가 여러 곳에서 제 몫을 네트워크로 가져오는 일이라 비싸다.

[2.5] 행동이 호출되면 엔진은 좁은 의존으로 이어진 변환을 되도록 한 스테이지에 넣고 셔플이 필요한 곳에 스테이지 경계를 둔다. 스테이지 안에서는 태스크 하나가 파티션 하나를 맡아 스테이지의 변환을 행마다 이어서 적용하므로 한 스테이지의 태스크 수는 그 스테이지에서 마지막으로 계산하는 데이터의 파티션 수와 같다. 셔플 뒤 스테이지는 앞 스테이지의 모든 태스크가 쓴 출력에서 제 몫을 받아야 하므로 앞 스테이지가 끝나야 시작한다.

[2.6] 파티셔너는 키를 파티션 번호로 바꾸는 규칙과 파티션 수로 이루어진다. Spark 의 reduceByKey 와 groupByKey 는 키의 해시값으로 파티션을 정하는 해시 파티셔너로 셔플하므로 결과 데이터는 그 파티셔너로 나뉘어 있다. 어떤 키든 제 번호의 파티션에만 있다는 뜻이다. 입력이 이미 같은 파티셔너로 나뉘어 있으면 같은 키는 이미 한 파티션에 모여 있으므로 Spark 는 셔플하지 않고 파티션마다 따로 모은다. 이때 키별로 모으는 연산도 좁은 의존이 된다. 두 해시 파티셔너는 파티션 수가 같을 때 같은 파티셔너다.

[2.7] 변환이 파티셔너를 이어받는지는 변환마다 다르다. filter 는 행을 버리기만 하고 남은 행의 키와 자리를 바꾸지 않으므로 파티셔너를 그대로 이어받는다. map 은 키를 바꿀 수 있다. Spark 는 map 이 실제로 키를 바꾸는지 따지지 않으므로 값만 바꾸는 함수를 받은 map 도 파티셔너를 잃는다. Spark 는 값만 바꾸는 mapValues 를 따로 두어 파티셔너를 지키게 하지만 이 트랙의 엔진에는 mapValues 가 없다. 그래서 reduceByKey 뒤에 값만 고치는 map 을 두고 같은 파티션 수로 다시 reduceByKey 하면 셔플이 한 번 더 생긴다.

[2.8] 파티션 수를 바꾸는 방법은 두 가지다. coalesce 는 기존 파티션 여러 개를 새 파티션 하나가 맡게 하는 좁은 의존이라 셔플이 없고 앞 변환과 같은 스테이지에 들어가 그 스테이지의 태스크 수를 줄인 파티션 수로 만든다. 파티션을 하나로 줄이면 같은 스테이지의 앞 변환까지 태스크 하나에서 실행된다. coalesce 에 지금보다 큰 수를 주면 파티션 수는 그대로다. 새 파티션이 어떤 키를 담을지는 기존 파티션의 배치에 달려 있으므로 coalesce 의 결과는 파티셔너가 없다. repartition 은 모든 행을 고르게 다시 나누는 셔플이다. 셔플 비용을 치르는 대신 스테이지 경계가 생기므로 셔플 앞 스테이지는 원래 파티션 수대로 병렬로 실행된다. repartition 은 키를 보지 않고 행을 나누므로 결과에 파티셔너가 없다.

[2.9] 키별 합계는 reduceByKey 로도, groupByKey 로 값을 모은 뒤 더해서도 낼 수 있다. reduceByKey 는 셔플하기 전에 태스크마다 같은 키의 값을 먼저 합쳐 보내고 groupByKey 는 값을 모두 보낸다. 2단계는 두 방식이 셔플로 옮기는 양을 잰다.

[2.10] 키가 없는 행도 있다. 이 트랙은 그런 키를 NULL 로 쓴다. 키별로 모을 때 NULL 키 행은 모두 한 묶음이 된다. SQL 의 GROUP BY 가 NULL 을 한 묶음으로 다루는 것과 같다. 반면 NULL 은 어떤 문자열과도 같다고도 다르다고도 할 수 없으므로 키를 문자열과 비교하는 조건은 NULL 키 행에서 참이 되지 않는다.

## 3. 입출력 규칙

[3.1] 프로그램은 표준 입력에서 줄을 하나씩 읽어 입력이 끝날 때까지 처리하고 결과를 표준 출력에 쓴다. 입력이 끝나면 종료 코드 0 으로 끝난다.

[3.2] 입력은 UTF-8 이다. 줄은 LF(U+000A)로 나눈다. 마지막 줄 뒤에 LF 가 없어도 그 줄을 처리한다.

[3.3] 이 문서에서 공백은 U+0020 한 글자만 가리킨다. 탭(U+0009)과 CR(U+000D)은 공백이 아니다.

[3.4] 줄 앞뒤의 공백은 무시한다. 빈 줄과 공백만 있는 줄은 건너뛰고 아무것도 출력하지 않는다.

[3.5] 줄은 공백으로 나눈 토큰의 열이다. 토큰 사이의 공백은 몇 개든 구분자일 뿐이다. 명령 줄의 첫 토큰을 명령어라 한다. `=` 와 `|` 도 앞뒤가 공백으로 떨어진 토큰이어야 한다.

[3.6] 출력은 UTF-8 이고 출력하는 줄은 모두 LF 로 끝낸다. 한 줄 안에서 토큰 사이는 공백 하나로 띄우고 줄 앞뒤에는 공백을 두지 않는다.

[3.7] 이 문서의 정규식은 토큰 전체에 적용한다.

[3.8] 프로그램은 데이터셋도 파이프라인도 없는 상태에서 시작한다. 이전 실행의 상태를 이어받지 않는다.

## 4. 명령 규칙

### 이름, 정수, 키, 값

[4.1] 데이터셋과 파이프라인의 이름은 `^[a-z][a-z0-9_]{0,31}$` 에 맞는 토큰이다. 이름이 오는 자리는 줄의 꼴에 `<이름>` 으로 적은 자리다. DATA, APPEND, PIPE, PLAN, RUN 줄의 둘째 토큰, 변환 `source <이름>` 의 둘째 토큰, 뒤 단계가 더하는 명령과 변환의 `<이름>` 자리가 여기에 든다. 이름이 오는 자리에 이 정규식에 맞지 않는 토큰이 오면 그 줄은 꼴에 맞지 않는다. 데이터셋과 파이프라인은 이름 공간 하나를 함께 쓴다. 같은 이름의 데이터셋과 파이프라인은 함께 있을 수 없다.

[4.2] 정수 토큰은 `^(0|-?[1-9][0-9]*)$` 에 맞는 토큰이다. `007`, `-0`, `+3` 은 정수 토큰이 아니다. 정수 토큰이 오는 자리마다 허용 범위를 따로 정한다. 범위를 벗어난 정수 토큰은 그 자리에 올 수 없다.

[4.3] 키는 `^[a-z0-9_]{1,24}$` 에 맞는 문자열이거나 NULL 이다. 행과 출력에서는 NULL 키를 `NULL` 네 글자로 쓴다. `NULL` 은 키 정규식에 맞지 않으므로 문자열 키와 헷갈리지 않는다.

[4.4] 값은 정수 값과 목록 값 두 종류다. 정수 값은 −2^63 이상 2^63 − 1 이하의 정수다. 목록 값은 정수 값 하나 이상을 담은 목록이다. 덧셈과 곱셈은 64비트 2의 보수로 계산해 범위를 넘으면 2^64 를 더하거나 빼서 범위 안으로 감싼다. JVM 의 Long 연산과 같다.

### DATA 와 APPEND

[4.5] `DATA <이름> <파티션 수>` 는 데이터셋을 만든다. 파티션 수는 1 이상 1,000 이하의 정수 토큰이다. 이 줄은 정확히 세 토큰이어야 한다.

[4.6] 명령어가 DATA 나 APPEND 인 줄 다음 줄부터 처음으로 `END` 만 있는 줄 바로 앞까지가 그 명령의 행 블록이다. 앞뒤 공백을 지운 줄이 `END` 이면 `END` 만 있는 줄로 본다. `END` 줄은 블록을 끝낼 뿐 행이 아니다. 블록 안의 빈 줄과 공백만 있는 줄은 건너뛰고 나머지 줄을 행 줄이라 한다. 행 줄은 명령으로 처리하지 않는다. DATA 나 APPEND 줄에 오류가 있어도 블록은 같은 방식으로 정해진다.

[4.7] 행 줄은 `<파티션 번호> <키> <값>` 세 토큰이다. 파티션 번호는 0 이상 (데이터셋의 파티션 수 − 1) 이하의 정수 토큰이다. 키는 4.3 의 키 정규식에 맞는 토큰이거나 `NULL` 이다. 값은 −1,000,000,000 이상 1,000,000,000 이하의 정수 토큰이다.

[4.8] 행은 행 줄에 적힌 파티션 번호의 파티션에 들어간다. 파티션 안의 행은 순서를 가진다. 블록의 행은 블록에 나온 차례대로 그 파티션의 끝에 붙는다. 행이 하나도 없는 파티션도 파티션이다. 블록에 행 줄이 하나도 없어도 된다.

[4.9] `APPEND <이름>` 은 이미 있는 데이터셋에 블록의 행을 더한다. 이 줄은 정확히 두 토큰이어야 한다. 데이터셋의 파티션 수는 바뀌지 않는다.

[4.10] DATA 는 아래 순서로 확인하고 처음 걸린 오류 하나를 출력한다. 첫째, DATA 줄이 4.5 의 꼴이 아니면 `ERR SYNTAX` 다. 둘째, 같은 이름의 데이터셋이나 파이프라인이 있으면 `ERR EXISTS` 다. 셋째, 행 줄을 앞에서부터 하나씩 확인해 4.7 에 맞지 않는 줄이 있으면 `ERR ROW <n>` 이다. n 은 그 줄이 블록에서 몇째 행 줄인지를 1 부터 센 번호다. APPEND 도 같은 순서로 확인하되 둘째 확인은 그 이름의 데이터셋이 없으면 `ERR NOT_FOUND <이름>` 이다. 그 이름이 파이프라인이어도 데이터셋이 없는 것으로 본다. 앞의 두 확인에서 걸리면 행 줄을 확인하지 않는다. 오류가 나면 데이터셋을 만들지 않고 행을 하나도 더하지 않는다.

### PIPE

[4.11] `PIPE <이름> = <변환> | <변환> | …` 는 파이프라인을 정의한다. 줄은 PIPE, 이름, `=` 세 토큰으로 시작한다. 넷째 토큰부터를 `|` 토큰 자리에서 끊은 조각 하나하나가 변환이다. 변환은 하나 이상이고 빈 조각은 올 수 없다. 첫 변환은 source 이고 source 는 첫 자리에만 온다. 성공하면 아무것도 출력하지 않는다.

[4.12] 변환은 아래 토큰 열 가운데 하나와 정확히 같아야 한다. `<n>` 과 `<k>` 와 `<c>` 는 정수 토큰, `<s>` 는 4.3 의 키 정규식에 맞는 토큰, `<이름>` 은 4.1 의 이름이다. `source <이름>`. `map key prefix <k>`, k 는 1 이상 24 이하. `map value add <c>` 와 `map value mul <c>`, c 는 −1,000,000,000 이상 1,000,000,000 이하. `map value sum`, `map value min`, `map value max`, `map value count`. `filter key = <s>` 와 `filter key != <s>`, s 자리에 `NULL` 은 올 수 없다. `filter value <비교> <c>`, 비교는 `=`, `!=`, `<`, `<=`, `>`, `>=` 가운데 하나이고 c 의 범위는 map 과 같다. `reduceByKey <함수> <n>`, 함수는 sum, min, max 가운데 하나. `groupByKey <n>`. `repartition <n>`. `coalesce <n>`. n 은 모두 1 이상 1,000 이하다.

[4.13] 파이프라인의 행은 값 종류를 하나 가진다. 데이터셋의 행은 정수 값이다. 변환은 입력의 값 종류를 받아 출력의 값 종류를 정한다. `map key prefix`, `filter key`, `repartition`, `coalesce` 는 어느 값 종류든 받고 그대로 내보낸다. `map value add`, `map value mul`, `filter value`, `reduceByKey` 는 정수 값만 받고 정수 값을 내보낸다. `groupByKey` 는 정수 값만 받고 목록 값을 내보낸다. `map value sum`, `map value min`, `map value max`, `map value count` 는 목록 값만 받고 정수 값을 내보낸다. `source <이름>` 의 값 종류는 데이터셋이면 정수 값이고 파이프라인이면 그 파이프라인의 마지막 변환이 내보내는 값 종류다.

[4.14] PIPE 는 아래 순서로 확인하고 처음 걸린 오류 하나를 출력한다. 첫째, 줄이 4.11 과 4.12 의 꼴이 아니면 `ERR SYNTAX` 다. 둘째, 같은 이름의 데이터셋이나 파이프라인이 있으면 `ERR EXISTS` 다. 셋째, 변환 안에 나온 이름을 앞에서부터 확인해 데이터셋도 파이프라인도 아닌 것이 있으면 `ERR NOT_FOUND <이름>` 이다. 정의하려는 파이프라인의 이름을 변환 안에 쓰면 아직 없는 이름이므로 이 확인에서 오류가 난다. 넷째, 변환을 앞에서부터 확인해 4.13 에서 받지 않는 값 종류를 입력으로 받는 변환이 있으면 `ERR TYPE <i>` 다. i 는 그 변환이 몇째 변환인지를 1 부터 센 번호이고 source 가 1 이다. 오류가 나면 파이프라인을 정의하지 않는다.

[4.15] 변환 조각의 첫 토큰이 join 이면 이 문서는 그 PIPE 줄부터 입력 끝까지의 출력을 정하지 않는다. join 은 3단계에서 더하는 변환이다. 이 규칙은 4.14 의 모든 확인보다 앞선다.

[4.16] 파이프라인 이름은 그 정의를 그 자리에 펼친 것과 같다. `source p` 는 파이프라인 p 의 변환을 모두 그 자리에 늘어놓은 것이다. 이렇게 데이터셋 하나에서 시작하도록 모두 펼친 변환 목록을 계보라 한다. 계보의 첫 변환은 언제나 `source <데이터셋>` 이다. 데이터셋 이름 d 를 파이프라인처럼 쓰면 계보는 `source d` 하나다. 파이프라인 p 를 정의한 뒤 p 가 가리키는 데이터셋에 행을 더하면 p 를 쓰는 행동은 더한 행까지 읽는다.

### 변환의 뜻

[4.17] `source d` 의 행은 행동을 실행하는 때 데이터셋 d 에 있는 모든 행이다.

[4.18] `map key prefix <k>` 는 행의 키를 앞 k 글자로 바꾼다. 키가 k 글자 이하이면 그대로 둔다. NULL 키는 NULL 그대로다. `map value add <c>` 는 값에 c 를 더하고 `map value mul <c>` 는 값에 c 를 곱한다. `map value sum`, `map value min`, `map value max` 는 목록 값을 그 원소의 합, 가장 작은 원소, 가장 큰 원소로 바꾸고 `map value count` 는 원소의 개수로 바꾼다. map 은 행 수를 바꾸지 않는다.

[4.19] `filter key = <s>` 는 키가 NULL 이 아니고 s 와 같은 행만 남긴다. `filter key != <s>` 는 키가 NULL 이 아니고 s 와 다른 행만 남긴다. 그래서 NULL 키 행은 두 filter 를 모두 통과하지 못한다. `filter value <비교> <c>` 는 값과 c 를 수로 비교해 관계가 성립하는 행만 남긴다.

[4.20] `reduceByKey <함수> <n>` 은 입력의 행을 키가 같은 것끼리 묶어 묶음마다 행 하나를 낸다. NULL 키 행은 모두 한 묶음이다. 그 행의 키는 묶음의 키이고 값은 묶음의 값 전체를 함수로 줄인 값이다. sum 은 합, min 은 가장 작은 값, max 는 가장 큰 값이다.

[4.21] `groupByKey <n>` 은 4.20 처럼 묶음을 만들고 묶음마다 그 묶음의 값을 모두 담은 목록 값을 가진 행 하나를 낸다. 같은 값이 여러 번 있으면 그만큼 담는다.

[4.22] `repartition <n>` 과 `coalesce <n>` 은 행을 바꾸지 않는다. 출력의 행은 입력의 행과 같다.

### 파티션 수와 파티셔너

[4.23] 계보의 변환마다 출력의 파티션 수가 정해진다. `source d` 는 데이터셋 d 의 파티션 수다. map 과 filter 는 입력의 파티션 수 그대로다. `reduceByKey`, `groupByKey`, `repartition` 은 인자 n 이다. `coalesce <n>` 은 n 과 입력의 파티션 수 가운데 작은 쪽이다.

[4.24] 변환마다 출력에 파티셔너가 있거나 없다. 이 문서에서 해시 파티셔너 n 은 파티션 수가 n 인 해시 파티셔너를 뜻한다. `source` 의 출력에는 파티셔너가 없다. `reduceByKey <함수> <n>` 과 `groupByKey <n>` 의 출력은 해시 파티셔너 n 으로 나뉘어 있다. filter 의 출력은 입력의 파티셔너를 그대로 가진다. map, repartition, coalesce 의 출력에는 파티셔너가 없다. map 은 키를 바꾸지 않는 `map value` 꼴이어도 파티셔너를 잃고 coalesce 는 파티션 수가 그대로여도 파티셔너를 잃는다.

[4.25] 변환마다 입력과의 의존이 좁은 의존인지 넓은 의존인지 정해진다. map, filter, coalesce 는 언제나 좁은 의존이다. repartition 은 언제나 넓은 의존이다. `reduceByKey <함수> <n>` 과 `groupByKey <n>` 은 입력이 해시 파티셔너 n 으로 나뉘어 있으면 좁은 의존이고 그렇지 않으면 넓은 의존이다. 넓은 의존인 변환의 입력과 출력 사이에서 셔플이 일어난다.

### 스테이지

[4.26] 계보를 넓은 의존인 변환마다 그 변환 바로 앞에서 끊는다. 끊어진 조각 하나하나가 스테이지다. 넓은 의존인 변환은 그 셔플을 읽는 스테이지의 첫 변환이다. 첫 스테이지는 source 로 시작한다.

[4.27] 스테이지 번호는 source 가 든 스테이지부터 계보의 차례대로 0, 1, 2, … 다. 스테이지의 태스크 수는 그 스테이지의 마지막 변환이 내보내는 파티션 수다. 마지막 스테이지가 아닌 스테이지는 출력을 다음 번호의 스테이지로 셔플한다. 마지막 스테이지의 출력은 행동의 결과다.

### PLAN

[4.28] `PLAN <이름>` 은 그 이름의 계보로 실행 계획을 세워 스테이지마다 한 줄을 스테이지 번호 순서로 출력한다. 이 줄은 정확히 두 토큰이어야 하고 이름은 데이터셋이나 파이프라인이다. PLAN 은 데이터를 계산하지 않고 잡을 만들지 않는다.

[4.29] 스테이지 줄은 `stage <번호> tasks <태스크 수>` 뒤에 그 스테이지의 변환 표시를 계보의 차례대로 쓰고 `->` 와 보낼 곳을 붙인 것이다. 변환 표시는 source 가 `source(<데이터셋 이름>)` 이고 나머지는 `map`, `filter`, `reduceByKey`, `groupByKey`, `repartition`, `coalesce` 처럼 변환 이름만 쓴다. 보낼 곳은 셔플하는 스테이지가 `shuffle <받는 스테이지 번호>`, 마지막 스테이지가 `result` 다. 예를 들어 `stage 0 tasks 4 source(sales) map coalesce -> shuffle 1` 이다.

### RUN

[4.30] `RUN <이름>` 과 `RUN <이름> <개수>` 는 그 이름의 계보를 실행한다. 이름은 데이터셋이나 파이프라인이다. 개수는 0 이상 1,000,000,000 이하의 정수 토큰이다.

[4.31] RUN 하나가 잡 하나다. 잡 번호는 입력의 첫 잡이 0 이고 잡이 생길 때마다 1 씩 는다. 오류가 난 명령과 PLAN 은 잡을 만들지 않는다. RUN 은 먼저 머리줄 `job <잡 번호> stages <스테이지 수> tasks <태스크 수> rows <행 수>` 를 출력한다. 스테이지 수는 계획의 스테이지 개수이고 태스크 수는 모든 스테이지의 태스크 수를 더한 값이고 행 수는 결과 행의 개수다.

[4.32] 결과 행은 RUN 을 실행하는 때의 데이터셋으로 계보의 변환을 차례로 적용해 얻은 행이다. 결과 행은 4.17~4.22 의 뜻만으로 정해지고 파티션 수와 스테이지 구성에 따라 달라지지 않는다.

[4.33] 머리줄 다음에 결과 행을 정렬해 한 줄에 하나씩 출력한다. 개수가 있으면 정렬한 결과의 앞 개수 행만 출력하고 결과 행이 그보다 적으면 모두 출력한다. 개수가 0 이면 머리줄만 출력한다. 머리줄의 행 수는 개수와 상관없이 결과 행 전체의 개수다.

[4.34] 결과 행의 순서는 먼저 키로 정한다. NULL 키 행이 가장 앞에 오고 문자열 키끼리는 앞 글자부터 차례로 글자 코드를 비교해 처음 다른 글자에서 순서를 정한다. 한쪽이 다른 쪽의 앞부분이면 짧은 쪽이 앞선다. 키가 같으면 값으로 정한다. 정수 값은 작은 값이 앞선다. 목록 값은 원소를 작은 것부터 늘어놓은 열끼리 앞 원소부터 비교해 처음 다른 원소에서 순서를 정하고 한쪽이 다른 쪽의 앞부분이면 짧은 쪽이 앞선다. 키와 값이 모두 같은 행이 여러 개면 그 수만큼 이어서 출력한다.

[4.35] 결과 행 한 줄은 키와 값을 공백 하나로 이은 것이다. 키는 문자열 그대로 쓰고 NULL 키는 `NULL` 로 쓴다. 정수 값은 10진수로 쓰고 음수에는 `-` 를 붙인다. 목록 값은 원소를 작은 것부터 쉼표로 이어 대괄호로 감싼다. `apple 8`, `NULL -3`, `kiwi [1,2,2]` 처럼 쓴다.

## 5. 오류 규칙

[5.1] 오류가 나면 `ERR` 로 시작하는 오류 줄 하나만 출력한다. 오류를 낸 명령은 상태를 바꾸지 않는다. 프로그램은 다음 줄을 이어서 처리한다. DATA 와 APPEND 는 오류가 나도 4.6 의 블록을 모두 읽은 뒤 `END` 줄 다음 줄부터 명령으로 처리한다.

[5.2] 명령어가 DATA, APPEND, PIPE, PLAN, RUN 가운데 하나이면 그 명령으로 처리한다. 명령어가 SET 이나 PROFILE 이면 이 문서는 그 줄부터 입력 끝까지의 출력을 정하지 않는다. 두 명령은 2단계에서 더한다. 그 밖의 명령어는 `ERR UNKNOWN_COMMAND` 다. `run` 처럼 소문자로 쓴 명령어와 블록 밖에 나온 `END` 도 여기에 든다.

[5.3] PLAN 과 RUN 은 먼저 줄이 4.28 이나 4.30 의 꼴인지 확인해 아니면 `ERR SYNTAX` 를 출력한다. 이름이 오는 자리의 토큰이 4.1 의 정규식에 맞지 않는 줄도 여기서 `ERR SYNTAX` 다. 꼴이 맞으면 다음으로 이름이 데이터셋도 파이프라인도 아닐 때 `ERR NOT_FOUND <이름>` 을 출력한다. DATA, APPEND, PIPE 의 확인 순서는 4.10 과 4.14 에 있다.

[5.4] 이 단계의 오류 줄은 아래와 같다.

| 오류 줄 | 뜻 |
|---|---|
| `ERR UNKNOWN_COMMAND` | 모르는 명령어 |
| `ERR SYNTAX` | 줄의 꼴이 틀림 |
| `ERR EXISTS` | 같은 이름이 이미 있음 |
| `ERR NOT_FOUND <이름>` | 없는 데이터셋이나 파이프라인 |
| `ERR ROW <n>` | 블록의 n 째 행 줄이 틀림 |
| `ERR TYPE <i>` | i 째 변환이 받지 않는 값 종류 |

## 6. 예시

[6.1] 예시 블록 하나는 프로그램을 한 번 실행한 기록이다. `> ` 로 시작하는 줄은 입력이고 나머지 줄은 바로 위 입력의 출력이다. 실제 입력에는 `> ` 가 없다. 6.3 과 6.4 는 6.2 의 입력을 먼저 실행하고 앞 예시를 차례로 실행한 것으로 보고 그 줄들을 생략한다. 6.4 의 잡 번호가 1 부터인 것은 6.2 의 RUN 이 잡 0 을 썼고 6.3 의 PLAN 은 잡을 만들지 않기 때문이다.

[6.2] 기본 동작이다. 데이터셋 sales 는 파티션 3개에 행 6개를 담는다. totals 의 reduceByKey 는 넓은 의존이므로 계보가 그 앞에서 끊겨 스테이지가 둘이 된다. 스테이지 0 의 태스크 수는 sales 의 파티션 수 3 이고 스테이지 1 의 태스크 수는 reduceByKey 의 인자 2 다. NULL 키 행은 한 묶음이 되고 결과의 맨 앞에 온다.

```
> DATA sales 3
> 0 apple 5
> 0 kiwi 2
> 1 apple 3
> 1 banana 4
> 2 kiwi 1
> 2 NULL 7
> END
> PIPE totals = source sales | reduceByKey sum 2
> PLAN totals
stage 0 tasks 3 source(sales) -> shuffle 1
stage 1 tasks 2 reduceByKey -> result
> RUN totals
job 0 stages 2 tasks 5 rows 4
NULL 7
apple 8
banana 4
kiwi 3
```

[6.3] 계획이다. a 의 coalesce 는 좁은 의존이라 source, map, filter 와 같은 스테이지에 들고 그 스테이지의 태스크 수를 2 로 줄인다. b 의 repartition 은 넓은 의존이고 뒤따르는 coalesce 는 repartition 이 연 스테이지에 든다. c 에서 totals 의 reduceByKey 는 해시 파티셔너 2 로 나뉜 데이터를 내고 filter 가 그 파티셔너를 이어받으므로 뒤의 reduceByKey 와 groupByKey 는 좁은 의존이다. d 는 값만 바꾸는 map 이 파티셔너를 잃어 셔플이 한 번 더 생긴다. e 의 coalesce 5 는 파티션 수 2 를 바꾸지 못하지만 파티셔너를 잃게 한다.

```
> PIPE a = source sales | map key prefix 1 | filter value >= 2 | coalesce 2 | reduceByKey sum 4
> PLAN a
stage 0 tasks 2 source(sales) map filter coalesce -> shuffle 1
stage 1 tasks 4 reduceByKey -> result
> PIPE b = source sales | repartition 6 | coalesce 4
> PLAN b
stage 0 tasks 3 source(sales) -> shuffle 1
stage 1 tasks 4 repartition coalesce -> result
> PIPE c = source totals | filter value > 3 | reduceByKey max 2 | groupByKey 2
> PLAN c
stage 0 tasks 3 source(sales) -> shuffle 1
stage 1 tasks 2 reduceByKey filter reduceByKey groupByKey -> result
> PIPE d = source totals | map value add 1 | reduceByKey max 2
> PLAN d
stage 0 tasks 3 source(sales) -> shuffle 1
stage 1 tasks 2 reduceByKey map -> shuffle 2
stage 2 tasks 2 reduceByKey -> result
> PIPE e = source totals | coalesce 5 | reduceByKey sum 2
> PLAN e
stage 0 tasks 3 source(sales) -> shuffle 1
stage 1 tasks 2 reduceByKey coalesce -> shuffle 2
stage 2 tasks 2 reduceByKey -> result
```

[6.4] 결과 행이다. g 의 목록 값은 원소를 작은 것부터 쓴다. n 은 목록 값을 원소 개수로 바꾼다. f 의 `filter key != kiwi` 는 kiwi 행과 함께 NULL 키 행도 버린다. 남은 행의 키를 앞 한 글자로 줄이면 키가 a 인 행이 둘 생기고 두 행은 값 순서로 놓인다. f 에는 넓은 의존이 없어 스테이지가 하나다. `RUN f 2` 의 머리줄은 출력한 행 수가 아니라 결과 행 전체의 수를 보인다.

[6.5] 지연 실행이다. hits 를 정의한 뒤 visits 에 행을 더하면 다음 RUN 은 더한 행까지 읽는다. PLAN 은 잡을 만들지 않으므로 마지막 RUN 의 잡 번호는 2 다. 이 블록은 6.2 를 실행하지 않은 새 실행이다.

## 7. 검사 방식

[7.1] 엔진은 테스트마다 풀이의 `run.sh` 를 새 프로세스로 실행한다. 작업 디렉터리는 풀이 디렉터리다.

[7.2] 엔진은 테스트의 입력 줄을 LF 로 잇고 마지막 줄 뒤에도 LF 를 붙여 표준 입력에 쓴 뒤 표준 입력을 닫는다.

[7.3] 프로세스가 0 이 아닌 종료 코드로 끝나면 실패다.

[7.4] 표준 출력만 기대 출력과 비교하고 표준 오류는 비교하지 않는다. 각 줄 끝의 공백, 탭, CR 을 지우고 끝에 붙은 빈 줄을 지운 뒤 줄 수와 각 줄의 내용이 정확히 같아야 한다.

[7.5] 일반 테스트의 제한 시간은 10초다. 제한 시간을 넘기면 엔진이 프로세스를 끝내고 실패로 판정한다.

[7.6] 검사 입력의 한 줄은 4,096바이트 이하다. 데이터셋과 파이프라인은 모두 합쳐 10,000개 이하이고 데이터셋 하나의 행은 5,000,000개 이하다. PLAN 과 RUN 이 다루는 계보의 변환은 1,000개 이하다.

[7.7] 대규모 테스트는 데이터셋 여러 개에 행을 모두 300,000개 안팎 넣고 서로 다른 키를 100,000개 안팎 둔다. APPEND 100개 안팎, PIPE 100개 안팎, PLAN 50개 안팎, RUN 20개 안팎이 섞인다. RUN 은 모두 개수를 20 이하로 주고 대부분 reduceByKey 나 groupByKey 를 거친다. 제한 시간은 15초다. 행마다 지금까지 만든 묶음을 처음부터 훑어 제 묶음을 찾는 풀이는 이 제한 시간을 넘기도록 규모를 정했다.

[7.8] 1단계 검사 입력에는 4.15 와 5.2 가 출력을 정하지 않은 줄이 나오지 않는다. 검사 입력의 DATA 와 APPEND 는 언제나 `END` 줄로 끝난다.

[7.9] 2단계부터 4단계까지 검사할 때도 1단계 테스트를 다시 실행한다.

[7.10] 3.2 의 마지막 문장과 3.6 의 LF 규칙은 엔진이 검사하지 않는다. 엔진은 입력의 마지막 줄 뒤에도 LF 를 붙이고(7.2) 출력 줄 끝의 CR 과 끝에 붙은 빈 줄을 지운 뒤 비교하기(7.4) 때문이다. 두 규칙은 표준 입출력 프로그램의 관례라서 적어 둔다.

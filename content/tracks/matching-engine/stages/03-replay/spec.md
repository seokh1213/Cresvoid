# 03. 기록 재생과 스냅숏 복원

## 1. 개요

[1.1] 02단계까지의 매칭 엔진에 입력 기록, 명시적 순번 재생, 스냅숏 출력과 복원을 더한다. 같은 기록을 빈 엔진에서 재생하거나 스냅숏 뒤의 기록만 재생해 같은 후속 체결과 호가창을 얻는다. 기존 명령의 출력은 바꾸지 않는다. 목표 풀이 시간은 2~3시간이다.

[1.2] 이번 단계의 새 명령은 `EVENT`, `JOURNAL`, `SNAPSHOT`, `RESTORE`다. 저장 매체는 표준 입출력이다. 파일 경로, 디스크 동기화, 장애 주입, 여러 프로세스 간 합의는 다루지 않는다. 테스트가 출력된 기록과 스냅숏을 다른 실행의 입력으로 옮길 수 있어야 한다.

## 2. 배경 개념

[2.1] 입력 기록은 이미 계산한 잔량을 적는 대신 상태를 바꾸려고 들어온 명령을 순서대로 보관한다. 이 과제에서는 성공한 주문뿐 아니라 알려진 변경 명령의 실패 시도도 기록한다. 잘못된 수량이나 이미 취소된 주문을 다시 취소한 결과까지 같은 순서로 재현하기 위해서다. 출력된 체결 행 자체는 입력 기록이 아니다.

[2.2] 기록의 순서 번호는 입력을 몇 번째로 처리했는지를 나타낸다. 도착 시계는 시간 우선을 발급한 횟수이고 체결 시계는 체결이 발생한 횟수다. 수량 감소 정정은 기록 순번만 늘릴 수 있으며, 여러 maker를 소진하는 주문 하나는 체결 순번을 여러 번 늘린다. 세 값을 같은 것으로 취급하면 재생 후 출력이나 우선순위가 달라질 수 있다.

[2.3] 스냅숏은 어느 기록 순번까지 반영한 상태의 사본이다. 호가 잔량만으로는 충분하지 않다. 같은 가격의 대기 순서, 이미 닫힌 주문의 ID 사용 이력, 다음에 발급할 두 시계도 복원해야 한다. 스냅숏까지의 체결을 다시 출력하는 대신 그 뒤 입력에서 발생할 체결을 동일하게 만드는 것이 복원의 목표다.

[2.4] 스냅숏을 만든 시점의 상태는 이후 처리로 바뀌어서는 안 된다. 이 과제에서는 복원할 내용을 외부의 입력 행으로 다시 받는다. 따라서 메모리에 원본 객체의 참조만 보관하거나 기록을 지운 뒤 과거 기록이 여전히 있다고 가정해서는 계약을 만족할 수 없다.

## 3. 입출력 규칙

[3.1] 기존 줄 처리와 명령 규칙은 그대로 적용한다. 엔진의 추가 상태는 마지막 기록 순번 `lastSeq`, 보관 기록의 기준 순번 `baseSeq`, `baseSeq` 뒤의 입력 기록이다. 빈 엔진에서는 둘 다 0이고 기록도 비었다. 순번 토큰은 기존 정수 문법을 따르며 명시적 `EVENT`의 순번 범위는 1~1,000,000,000이다. 테스트에서는 자동 발급을 포함해 이 상한을 넘지 않는다.

[3.2] 변경 명령은 이름이 `LIMIT`, `MARKET`, `IOC`, `FOK`, `AMEND`, `CANCEL`인 명령이다. 이 이름으로 시작한 직접 입력 행은 인자가 틀려도 `lastSeq + 1`을 배정하고 변경 명령의 토큰을 기록한 다음 실행한다. 성공·실패 여부와 무관하게 `lastSeq`는 그 순번으로 바뀐다. 출력은 이전 단계에서 정한 출력뿐이며 순번 확인 행을 더하지 않는다. 빈 줄, 알 수 없는 명령, 조회·복원 명령과 그 오류는 기록하지 않는다.

[3.3] 기록은 변경 명령의 모든 토큰을 원래 철자로 보존하되 구분자는 공백 하나로 통일한다. 앞자리 0이나 잘못된 수량 토큰도 그대로 보존한다. `EVENT`로 받은 경우에는 바깥의 `EVENT`와 순번 토큰을 제외한 본문만 보관한다. 기록 순번은 출력할 때 앞자리 0 없는 십진수로 쓴다.

## 4. 명령 규칙

[4.1] `EVENT <seq> <변경 명령과 인자>`는 순번이 붙은 기록 한 건을 적용한다. 바깥 형식과 순번을 확인한 뒤 `seq`가 정확히 `lastSeq + 1`일 때만 본문을 기록하고 실행한다. 본문이 출력하는 `TRADE`, `ORDER`, `AMEND`, `CANCEL`, `ERR` 행을 그대로 출력한다. 별도 재생 확인 행은 없다. 같은 기록을 빈 엔진에서 같은 순서로 적용하면 직접 입력 때와 같은 출력을 얻는다.

[4.2] 정상 순번으로 받은 알려진 변경 명령의 본문은 형식 오류나 값 오류가 있어도 기록을 소비한다. 본문의 오류는 기존 호가창·사용 ID·도착 시계·체결 시계를 바꾸지 않지만 `lastSeq`와 기록은 바뀐다. FOK의 전량 취소, 같은 값의 정정, 없는 주문 취소도 각각 기록 한 건이다. 재생한 명령을 다시 자동 순번으로 기록해 기록 두 건으로 만들지 않는다.

[4.3] `JOURNAL`은 첫 행에 `JOURNAL <baseSeq> <count>`를 출력하고 이어서 기록 순서대로 `EVENT <seq> <본문>`을 `count`행 출력한다. `count`는 `lastSeq - baseSeq`다. 비었으면 첫 행만 출력한다. 조회는 상태를 바꾸지 않는다. 재생할 때에는 이 헤더가 아니라 `EVENT` 행들만 입력으로 준다. 빈 엔진은 `baseSeq`가 0인 기록을 처음부터 재생할 수 있으며, 기준 순번이 양수인 기록은 해당 순번의 스냅숏을 복원한 엔진에서 재생한다.

[4.4] `SNAPSHOT`은 첫 행에 `SNAPSHOT <lastSeq> <arrivalClock> <tradeClock> <usedCount> <openCount>`를 출력한다. `arrivalClock`은 01·02단계의 도착 시계이고 `tradeClock`은 마지막 체결 순번이다. 이어서 사용한 모든 ID를 ASCII 사전순으로 `USED <id>` 행에 하나씩 출력하고, 현재 대기 주문을 도착 순번 오름차순으로 `OPEN <id> <owner> <side> <price> <remainingQty> <arrivalNo>` 행에 하나씩 출력한다. 추가 종료 행은 없다. 대기 주문의 방향과 가격이 달라도 전체 도착 순번으로 정렬한다. 출력은 상태·시계·기록을 바꾸지 않는다.

[4.5] 스냅숏의 두 개수는 각각 뒤따르는 `USED`, `OPEN` 행 수다. 사용 ID에는 전량 체결, 취소, 시장가 잔량 취소, FOK 전량 취소로 닫힌 주문도 포함하고 오류로 접수하지 못한 ID는 포함하지 않는다. 현재 대기 주문의 잔량은 양수다. 각 `arrivalNo`는 현재 주문의 도착 순번이며 정정으로 시간 우선을 잃었다면 새 순번이다. 모든 활성 순번은 서로 다르고 `arrivalClock` 이하다. 체결 내역과 입력 기록 본문은 스냅숏에 포함하지 않는다.

[4.6] `RESTORE <lastSeq> <arrivalClock> <tradeClock> <usedCount> <openCount>`는 뒤의 `usedCount + openCount`개 행을 스냅숏 본문으로 읽는다. `SNAPSHOT` 출력의 헤더 첫 토큰만 `RESTORE`로 바꾸면 입력 형식이 된다. 기존 상태를 전부 버리고 그 본문과 메타데이터로 호가창·사용 ID·두 시계·마지막 기록 순번을 교체한다. 대기 주문을 복원하면서 체결을 시도하거나 도착 순번을 새로 발급하지 않는다. `baseSeq`를 복원한 `lastSeq`로 설정하고 보관 입력 기록은 빈 것으로 바꾼다. 마지막에 `RESTORED <lastSeq>` 한 줄만 출력한다.

[4.7] `RESTORE` 본문 행은 명령이 아니므로 개별 실행·기록·출력을 하지 않는다. 테스트에서 형식과 값이 올바른 `RESTORE` 헤더의 본문은 이 계약의 엔진이 출력한 완전하고 유효한 스냅숏임을 보장한다. 다른 실행에서 가져온 스냅숏과 이전 순번으로 되돌리는 복원도 허용한다. 본문 누락·손상·잘못된 정렬·필드 간 불일치 처리는 구현 범위 밖이다. 복원은 다른 엔진에서 출력한 스냅숏도 받아야 하므로 현재 프로세스가 전에 출력한 적 있는지를 검사하지 않는다.

[4.8] 복원 후 첫 변경 입력의 순번은 복원한 `lastSeq + 1`이다. 스냅숏 이전 체결은 다시 출력하지 않지만 체결 시계는 이어진다. 복원 뒤의 도착 순번도 `arrivalClock`에서 이어진다. 스냅숏에 들어 있던 닫힌 ID를 재사용하면 `ERR DUPLICATE`다. 반대로 복원으로 버린 미래 상태에만 있던 ID는 다른 사용 이력이 없다면 다시 쓸 수 있다. 복원 직후 `JOURNAL`은 `JOURNAL <lastSeq> 0`이고 새 스냅숏의 본문은 복원한 것과 같다.

## 5. 오류 규칙

[5.1] 인자가 붙은 `JOURNAL`·`SNAPSHOT`, 바깥 토큰이 세 개 미만인 `EVENT`, 순번이 정수 문법에 맞지 않는 `EVENT`, 본문 첫 토큰이 알려진 변경 명령 이름이 아닌 `EVENT`는 `ERR FORMAT`이다. `EVENT` 안에 조회·복원·다른 `EVENT`를 넣을 수 없다. 이 바깥 형식 검사를 먼저 하고 순번 값 범위를 검사한다. 순번 값 범위 위반은 `ERR VALUE`, 유효 범위이지만 다음 순번과 다르면 `ERR SEQUENCE`다. 같은 순번의 중복 기록도 내용이 같더라도 `ERR SEQUENCE`다.

[5.2] `EVENT` 바깥 검사가 실패하면 본문을 실행하지 않으며 어떤 상태도 바꾸지 않는다. 다음 순번 확인까지 통과했다면 그 뒤 본문의 오류는 3.2·4.2 문단을 따른다. 따라서 `EVENT 3 CANCEL`의 순번이 현재 다음 순번이면 `ERR FORMAT`을 출력하면서 3번 기록을 소비하고, 다음 순번이 아니면 `ERR SEQUENCE`만 출력하며 기록을 소비하지 않는다.

[5.3] `RESTORE` 헤더의 인자 수·정수 문법이 잘못되면 `ERR FORMAT`이고, 정수 값이 허용 범위를 벗어나면 `ERR VALUE`다. 헤더의 다섯 수는 모두 0~1,000,000,000이며 두 개수도 signed 64비트 정수로 해석한다. 헤더 오류에서는 뒤의 행을 본문으로 소비하지 않고 다음 명령으로 처리하며 상태를 바꾸지 않는다. 헤더 검사를 통과한 복원 본문은 4.7 문단의 유효성 보장을 따른다. 복원으로 읽는 본문 행에는 빈 행이 없다.

## 6. 예시

[6.1] 다음은 원래 실행과 그 기록을 다른 빈 프로세스에서 재생한 예시다. 실패한 취소도 2번을 소비하므로 S1은 3번이다. 중복 3번 기록과 빠진 4번을 건너뛴 5번 기록은 거절한다.

원래 실행의 입력:
```text
LIMIT B1 u BUY 100 3
CANCEL gone
LIMIT S1 v SELL 99 2
JOURNAL
```

원래 실행의 출력:
```text
ORDER B1 3 0
ERR NOT_FOUND
TRADE 1 B1 S1 100 2
ORDER S1 0 0
JOURNAL 0 3
EVENT 1 LIMIT B1 u BUY 100 3
EVENT 2 CANCEL gone
EVENT 3 LIMIT S1 v SELL 99 2
```

새 프로세스의 입력:
```text
EVENT 1 LIMIT B1 u BUY 100 3
EVENT 2 CANCEL gone
EVENT 3 LIMIT S1 v SELL 99 2
EVENT 3 LIMIT S1 v SELL 99 2
EVENT 5 CANCEL B1
BOOK
```

새 프로세스의 출력:
```text
ORDER B1 3 0
ERR NOT_FOUND
TRADE 1 B1 S1 100 2
ORDER S1 0 0
ERR SEQUENCE
ERR SEQUENCE
BOOK B 100:1 S -
```

[6.2] 다음 입력에서는 2번 순번에서 스냅숏을 만들고, 이후의 B2를 버린 뒤 그 스냅숏을 복원한다. 닫힌 S1의 ID와 다음 체결 순번이 보존된다. `SNAPSHOT`이 출력한 본문과 `RESTORE`가 읽는 본문은 같다.

입력:
```text
LIMIT B1 u BUY 100 3
LIMIT S1 v SELL 99 2
SNAPSHOT
LIMIT B2 w BUY 100 5
RESTORE 2 2 1 2 1
USED B1
USED S1
OPEN B1 u BUY 100 1 1
JOURNAL
LIMIT S1 v SELL 99 1
LIMIT B2 w BUY 100 2
EVENT 5 MARKET S2 v SELL 2
BOOK
JOURNAL
```

출력:
```text
ORDER B1 3 0
TRADE 1 B1 S1 100 2
ORDER S1 0 0
SNAPSHOT 2 2 1 2 1
USED B1
USED S1
OPEN B1 u BUY 100 1 1
ORDER B2 5 0
RESTORED 2
JOURNAL 2 0
ERR DUPLICATE
ORDER B2 2 0
TRADE 2 B1 S2 100 1
TRADE 3 B2 S2 100 1
ORDER S2 0 0
BOOK B 100:1 S -
JOURNAL 2 3
EVENT 3 LIMIT S1 v SELL 99 1
EVENT 4 LIMIT B2 w BUY 100 2
EVENT 5 MARKET S2 v SELL 2
```

## 7. 검사 방식

[7.1] 기본 실행 환경, 표준 입력 방식, 출력 비교와 테스트별 60초 제한은 01단계와 같다. 01·02단계 테스트도 누적 실행한다. 고정·무작위 검사에서는 직접 실행과 기록 재생의 체결·호가를 비교하고, 스냅숏 복원 후 같은 후속 기록이 같은 출력을 내는지 확인한다. 실패한 명령의 순번 소비, 기록 순번 중복·누락, 정정 후 시간 우선, 닫힌 ID, 미래 상태 폐기, 서로 다른 실행 간 복원을 함께 확인한다. 유효 스냅숏의 전체 출력도 필드별 계약대로 비교한다.

[7.2] 대규모 검사는 재생을 포함한 새 주문 명령 총 1,000,000건, 추가 취소·정정 최대 200,000건, 서로 다른 가격 최대 500,000개, 실제 체결 최대 500,000건이다. 스냅숏 출력·복원은 각각 최대 4번이고 `JOURNAL` 출력은 최대 4번이다. 유효 스냅숏 본문 행을 포함한 전체 입력과 기대 출력은 각각 64MiB 이하다. 실패 FOK에 대한 02단계의 상대 주문 수 제한도 유지한다. 순번 검사나 기록 추가 때마다 과거 입력 전체를 다시 실행하거나, 체결마다 호가 전체를 훑는 방식이 제한 시간을 넘는 규모를 의도한다. 제한 시간은 테스트별 60초다.

# 캐시와 원천의 불일치

[1] 상품 가격을 조회하고 수정하는 서비스다. 시작 코드와 아래 부하 순서를 읽고 캐시 상태와 GET 응답 버전을 먼저 예측해라. 시작 코드를 실행해 `cache_mismatches`와 `stale_ratio`를 관찰하고 예측과 다른 결과가 있으면 요청 순서로 설명해라. 일관성 전략을 구현한 뒤 두 시나리오를 다시 실행하고 수렴과 응답 신선도를 각각 설명해라.

[2] JDK 21과 Kotlin 표준 라이브러리만 사용한다. 캐시는 Docker의 Redis이며 실행기가 `REDIS_HOST`, `REDIS_PORT`, `PORT`를 전달한다. `./build.sh`로 실행 jar를 만들고 `./run.sh`로 `127.0.0.1:$PORT`에 서비스를 띄워라. 실험기는 빈 포트, Redis 준비 확인, 서버 시작과 종료를 맡는다. 시나리오를 실행할 때마다 반복 회차를 포함해 상품 키와 보조 키가 모두 없는 독립 Redis와 새 서버로 시작한다. 한 시나리오 안의 라운드 사이에는 같은 Redis와 서버를 유지한다. 기존 Redis 상태를 유지한 서버 재시작, Redis와 원천의 장애, 복제 지연은 이번 실험의 범위 밖이다.

[3] 상품 id는 1부터 12까지다. 각 상품의 초기 가격은 100이고 버전은 0이다. `GET /products/{id}`는 200과 `id,price,version` 형식의 텍스트 한 줄을 반환한다. `PUT /products/{id}/price`는 가격 정수 하나를 본문으로 받아 원천 가격을 바꾸고, 해당 상품 버전을 정확히 1 늘린 뒤 200과 같은 형식의 결과를 반환한다. 가격 범위는 1부터 1000000까지다. 원천 버전은 상품마다 단조 증가한다. 예를 들어 상품 1의 가격을 101로 바꾼 첫 PUT의 본문은 `1,101,1`이다. 원천 값과 버전은 하나의 불변 스냅샷으로 갱신한다.

[4] 존재하지 않는 상품은 404, 상품 경로의 지원하지 않는 메서드는 405, 가격 형식이나 범위 오류는 400이다. `GET /health`는 준비 뒤 200을 반환한다. 실험의 정상 요청은 모두 200이어야 하고 통신 실패, 5xx, 형식 오류, 다른 상품의 응답, 존재하지 않는 가격·버전 조합은 0건이어야 한다.

[5] `Source.read`는 원천 스냅샷을 확보한 뒤 80ms를 기다린다. 실험용 장벽이 설정되어 있으면 이 지연 전에 추가로 대기한다. 반환 시점에는 이미 원천이 바뀌었을 수 있다. 캐시 키는 `product:{id}`이고 값은 HTTP 본문과 같은 형식이다. 시작 코드의 캐시 TTL은 30000ms다. GET은 유효한 캐시를 사용하고, 미스에서는 반드시 `Source.read`를 거쳐라. 캐시를 끄거나 원천 스냅샷·지연을 우회해서는 안 된다.

[6] 읽기 경로의 캐시 기록과 응답 선택, 쓰기 경로의 원천 갱신과 캐시 처리 순서를 구현해라. `ProductCache.kt`만 수정하고 필요하면 이 파일 안에 보조 선언을 추가해라. HTTP 처리, 원천 저장소, 장벽, RedisClient, 실행·빌드 파일은 바꾸지 마라. 원천을 수정할 때는 `Source.update`를 사용하고 `Source.current`는 호출하지 마라. 별도 로컬 캐시나 전역 잠금으로 원천 지연을 숨기지 마라. Redis 안에 보조 키를 둘 수 있고, 만료·비교·삭제 전략과 재시도 방식을 선택할 수 있다.

[7] 실험용 `POST /admin/hold`는 모든 상품 캐시 값만 비우고 이후 원천 읽기의 스냅샷을 장벽에서 기다리게 한다. 보조 키와 원천 값은 지우지 않는다. `GET /admin/pending`은 장벽에서 기다리는 읽기 수다. `POST /admin/release`는 장벽을 풀며, 이미 확보된 스냅샷은 바꾸지 않는다. `GET /admin/state`는 상품마다 `원천값|캐시값`을 한 줄로 반환하고 빈 캐시는 `empty`로 표시한다. 이 조회는 캐시를 채우거나 TTL을 갱신하지 않는다. `GET /admin/reads`는 `Source.read` 누적 호출 수다. 이 경로들은 관찰 전용이며 제품 경로에서 호출해서는 안 된다.

[8] `shop-browse`는 한 라운드, `price-rounds`는 세 라운드를 실행한다. 라운드마다 캐시를 비우고 상품별 GET을 같은 예정 시각에 하나씩 보낸다. 12개 읽기가 모두 스냅샷을 확보한 것을 확인한 뒤 같은 12개 상품에 PUT을 동시에 보낸다. 라운드 r의 새 가격은 모든 상품에서 100+r이고 버전은 r이다. PUT 완료 후 장벽을 풀고 최초 GET 12개의 완료를 기다린다. 이 GET들은 PUT 전에 시작했으므로 이전 라운드 값 또는 이번 라운드 값을 반환할 수 있다. 준비 장벽 확인은 최대 10초, 보류된 GET의 요청 제한은 25초이며 서비스의 장벽 자체 제한은 20초다.

[9] 이어서 초당 80개의 GET을 3초 동안 개방형 모델로 보낸다. 상품은 1부터 12까지 순환하며, 요청 하나가 느려져도 다음 요청의 예정 시각은 미루지 않는다. 각 GET의 기준 버전은 그 요청을 보내기 전에 응답으로 확인한 해당 상품의 마지막 PUT 버전이다. 이 구간에는 추가 PUT이 없으므로 기준은 라운드 r이다. `stale_responses`는 이 측정 GET의 반환 버전이 기준보다 작은 건수다. `stale_ratio`는 `stale_responses / (라운드 수 × 240)`이며 0.01 이하여야 한다. 늦게 끝난 최초 GET 12개는 이 비율에 포함하지 않는다. 실패·누락된 요청을 분모에서 빼지 마라.

[10] 마지막 측정 GET까지 모두 끝난 시점을 부하 종료로 삼는다. 그 뒤 상태를 즉시 확인하고 약 100ms 간격으로 2초 동안 관찰한다. 원천은 모든 키에서 최종 가격과 버전을 유지해야 하고, 캐시는 원천과 같거나 비어 있어야 한다. `cache_mismatches`는 마지막 관찰에서 이 조건을 어긴 상품 수이며 0이어야 한다. `convergence_ms`는 이후 관찰에서 다시 불일치가 나타나지 않은 최초 일치 시각이다. 2000ms 이하여야 하고, 끝까지 일치하지 않으면 2001로 표시한다. 두 지표는 마지막 HTTP 관찰이 2초 경계를 넘기며 완료될 수 있는 샘플링 측정이다.

[11] 수렴 관찰 뒤 12개 상품을 한 번씩 GET해 현재 값을 채우고, 같은 GET을 다시 보낸다. 첫 번째 조회 뒤 12개 캐시 모두 원천과 같은 값이어야 한다. 두 번째 조회에서는 원천 읽기 호출 수가 늘지 않아야 한다. 이 조건과 최신 응답 검사를 어긴 건수를 `cache_use_errors`에 합산하며 0이어야 한다. 만료 직전 경계를 피하도록 첫 번째 조회와 검사·재조회는 쉬지 않고 수행한다. 캐시 기능 자체를 제거해서 불일치만 없애는 수정은 통과하지 못한다.

[12] `responses`는 라운드마다 최초 GET 12개, PUT 12개, 측정 GET 240개를 더한 수로 라운드 수 × 264여야 한다. 수렴 뒤 확인 요청과 제어 요청은 포함하지 않는다. `response_errors`는 이 요청들의 통신·상태·본문 계약 위반 수이며 0이어야 한다. 모든 요청을 보낸 뒤 완료까지 기다리며, 누락된 지표나 실험 시간 초과를 정상 실패로 취급하지 않는다. 합격하려면 응답 계약, 오래된 응답 비율, 수렴, 캐시 사용 조건을 모두 만족해야 한다.

[13] 수정안을 평가할 때는 캐시 상태와 HTTP 응답을 따로 기록해라. 같은 요청 순서에서도 두 관찰이 각각 어떤 합격 조건을 만족하는지 확인해라. 두 시나리오를 실행하고 수정안을 검토한 뒤 [관찰 후 해설](debrief.md)을 읽어라.

[14] 이번 실험의 통과는 [2]의 실행 범위에서만 보장된다. 범위 밖의 장애나 재시작까지 같은 전략이 유효하다고 일반화하지 마라.

[15] 사용할 Redis 명령의 동작은 공식 문서에서 확인해라. [명령 목록](https://redis.io/docs/latest/commands/)과 [프로그래밍 인터페이스](https://redis.io/docs/latest/develop/programmability/)를 참고하되 구현 전략은 직접 선택해라.

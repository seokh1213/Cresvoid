# 속도 제한

[1] 두 HTTP 인스턴스가 같은 Redis를 쓰는 서비스다. 사용자별 속도 제한을 구현해라. 먼저 문항을 풀고 시작 코드를 실험해 허용량을 관찰한 뒤 `src/main/kotlin/RateLimiter.kt`를 고쳐라. 시작 코드는 빌드되지만 동시에 도착한 요청을 너무 많이 허용한다.

[2] 실험은 고정 이미지로 Redis를 실행하고 실행마다 데이터 공간을 분리한다. 같은 프로그램을 두 JVM으로 실행하며 `PORT`, `INSTANCE_ID`(a 또는 b), `REDIS_HOST`, `REDIS_PORT`, `REDIS_PREFIX`를 환경 변수로 준다. 두 인스턴스의 Redis 주소와 접두사는 같다. `build.sh`로 빌드하고 `run.sh`로 실행한다. 서버는 `127.0.0.1:$PORT`에서만 요청을 받는다. Docker Desktop과 JDK 21이 필요하며 별도 라이브러리는 설치하지 않는다.

[3] `GET /health`는 Redis의 PING이 성공하면 200과 `ok`를 반환한다. 준비 확인은 사용자 할당량을 소비하지 않는다. `POST /requests`는 본문 없이 `X-User` 헤더로 사용자를 지정한다. 사용자 이름은 소문자 영문자·숫자·하이픈으로 된 1~40자다. 헤더 누락이나 잘못된 값은 400, 알려진 경로의 잘못된 메서드는 405, 다른 경로는 404다. 이 요청들도 할당량을 소비하지 않는다.

[4] 허용한 요청은 200, 거절한 요청은 429를 반환한다. 본문은 `{"allowed":true,"decision_us":1234567890000000,"instance":"a"}` 형태이며 거절할 때는 `allowed`가 false다. `decision_us`는 허용 여부를 결정한 Redis 서버의 Unix 시각을 마이크로초 단위로 나타낸 정수다. 응답 순서나 클라이언트 수신 시각을 판정 시각으로 쓰지 마라. 429에는 `Retry-After: 1`을 붙인다. Redis 통신 실패는 503이며 실험 중에는 한 건도 허용하지 않는다.

[5] 한도 L은 사용자당 초당 20건, 버스트 여유 B는 10건이다. 두 인스턴스의 허용 요청을 합쳐 어떤 구간 `(t − 1초, t]`에서도 한 사용자에게 L + B = 30건을 초과해 허용하지 마라. 정수 초에 맞춘 창만 검사하는 규칙이 아니다. 사용자별 상태는 독립적이어야 한다. 모든 요청을 거절하는 방식도 금지한다.

[6] 토큰 버킷이나 미끄러지는 창으로 구현해라. 이 실험에서는 최근 1초의 허용 요청을 최대 30건 보관하는 미끄러지는 창도 허용한다. 토큰 버킷을 고르면 초당 20개를 보충하고 최대 10개를 보관하도록 해라. 새 사용자의 버킷은 가득 찬 상태다. 두 방식의 짧은 구간 허용량은 다르지만 [5]의 상한과 아래 최소 허용량을 모두 만족해야 한다. 거절한 요청은 허용 기록에 넣지 마라.

[7] Redis Lua 스크립트 안에서 서버 시각 조회, 오래된 상태 정리, 할당량 확인과 소비를 하나의 원자적 판단으로 묶어라. JVM 잠금은 다른 인스턴스를 막지 못한다. 스크립트는 짧게 유지해라. Redis 키는 모두 `REDIS_PREFIX` 뒤에 콜론을 붙인 이름으로 만들고, 마지막 판단 뒤 2,500ms 안에 만료되도록 해라. 사용자가 다시 오지 않아도 상태가 남지 않아야 한다.

[8] 고정 창은 경계 직전과 직후에 각각 할당량을 허용해 최근 1초 상한을 넘을 수 있다. `INCR`와 `EXPIRE`를 별도 호출하면 그 사이 클라이언트가 죽어 만료 없는 키가 남을 수 있다. Lua의 원자성은 다른 요청의 끼어들기를 막지만 실행 오류가 앞선 쓰기를 되돌려 주는 트랜잭션 롤백은 아니다. 이 실험은 프로세스 장애를 주입하지 않으므로 장애 사이의 TTL 누락은 문항과 코드 검토에서도 확인해라.

[9] `shared-traffic`은 준비 확인 후 같은 사용자에게 시작 시각에 120건을 보내고 초당 240건을 5초 동안 추가한다. 매 요청의 목적지를 두 인스턴스에 번갈아 배정한다. 별도 사용자 둘에게는 각각 초당 4건을 5초 동안 보낸다. 이전 요청의 응답과 관계없이 예정 시각에 보내는 개방형 부하다. 같은 사용자에게 총 1,320건, 저빈도 사용자에게 총 40건을 보낸다.

[10] `shared-traffic`에서는 같은 사용자의 허용 수가 90건 이상이고, 저빈도 사용자의 40건은 모두 허용되어야 한다. 거절은 적어도 한 건이어야 한다. 요청 1,360건이 모두 완료되고 [5]의 상한을 지켜야 한다. 다른 사용자의 폭주가 저빈도 사용자를 막으면 실패다.

[11] `paced-traffic`은 Redis의 정수 초 시각을 기준으로 700ms와 1,100ms에 같은 사용자에게 각각 80건을 보낸다. 각 무리는 1ms 간격이고 두 인스턴스를 번갈아 사용한다. 같은 쌍을 2초 간격으로 세 번 반복해 총 480건을 보낸다. 각 쌍의 시작 전에는 직전 허용 기록이 1초 창 밖으로 나간다. 경계 양쪽의 요청을 함께 관찰하고 유휴 시간 뒤의 할당량 회복도 확인해라.

[12] `paced-traffic`에서는 각 쌍마다 10건 이상을 허용해야 한다. 세 쌍 중 최소 허용량을 지표로 낸다. 거절은 적어도 한 건이어야 하며 [5]의 최근 1초 상한도 지켜야 한다. 정수 초가 바뀌었다는 이유로 직전 허용 기록을 잊으면 실패다.

[13] 두 시나리오 모두 전체 측정 요청에서 통신 오류, 200·429 이외 상태, 응답 필드와 HTTP 상태의 불일치, 잘못된 인스턴스 표시가 0건이어야 한다. 판단 시각은 부하 전후에 따로 읽은 Redis 시각 사이에 있어야 한다. p99 응답 시간은 1,500ms 이하여야 한다. 요청별 타임아웃은 5초다. 속도 제한만 하는 서비스에 긴 대기열을 만들어 상한을 피하지 마라. 제공된 HTTP 서버는 Redis 호출 실패를 포함한 요청 처리 예외를 모두 503으로 바꾸므로 503만으로 Redis 장애를 단정하지 마라.

[14] `requests`, `accepted`, `rejected`는 각각 예정 요청 수와 200·429 응답 수다. `max_window`는 사용자별 허용 시각을 정렬한 뒤 임의의 1초 반개구간에 들어가는 건수의 최댓값이며 30 이하여야 한다. 같은 마이크로초의 허용 기록도 별도 요청으로 센다. `minimum_accepted`는 shared-traffic의 폭주 사용자 전체 허용 수 또는 paced-traffic의 쌍별 허용 수 최솟값이다.

[15] `quiet_rejections`는 저빈도 사용자의 비허용 수이며 0이어야 한다. paced-traffic에는 저빈도 부하가 없으므로 0이다. `request_errors`는 [13]의 위반 요청 수와 공개 HTTP 예시 검사의 실패 수를 합한 값이며 0이어야 한다. `p99_ms`는 전체 측정 요청의 응답 시간 99백분위다. 부하가 끝난 뒤 2,700ms를 기다려 해당 접두사로 시작하는 키 수를 `remaining_keys`로 내며 0이어야 한다. 초과 허용, 과도한 거절, 영구 상태를 각각 확인해라.

[15.1] `first_error`는 오류가 없으면 0, 통신 실패면 1, 서버의 503 응답이면 2, 그 밖의 비정상 HTTP 상태면 3, 응답 형식·allowed·인스턴스 불일치면 4, 판단 시각 범위 위반이면 5, 공개 HTTP 예시의 상태·본문 불일치면 6이다. 한 요청에서 여러 위반이 있으면 이 순서에서 먼저 해당하는 유형 하나만 센다. 예시 검사에서 통신 실패와 503은 각각 1과 2로 분류하고 나머지 불일치는 6으로 분류한다. 예시 검사를 먼저 확인한 뒤 부하 요청을 예정 시각순으로 확인해 처음 발견한 오류 유형을 낸다. 실제 실패 발생 시각의 순서는 아니다. 이 지표로 통신·요청 처리 예외·HTTP 응답 계약 문제를 구분해라.

[16] 예를 들어 새 사용자에게 순서대로 보낸 요청 두 건은 모두 200이다. `X-User` 없이 보낸 요청은 400이고, `GET /requests`는 405다. 처음 한 무리의 80건을 보냈을 때 미끄러지는 창 구현은 30건을 허용하고 나머지를 거절할 수 있다. 정확한 판단 시각과 인스턴스 표시는 실행마다 달라진다.

[17] 수정 범위는 `RateLimiter.kt`와 그 파일에서 호출하는 새 Kotlin 파일이다. `Main.kt`, 제공된 `RedisClient.kt`, 빌드·실행 스크립트와 환경 변수 계약은 유지해라. `Decision(allowed, atMicros)`의 뜻을 바꾸거나 응답 시각을 꾸며 지표를 맞추지 마라. 숨은 파일과 다른 단계, `practice/`는 수정하지 마라.

[18] 근거는 Redis 공식 문서의 [Lua 실행과 원자성](https://redis.io/docs/latest/develop/programmability/eval-intro/), [INCR의 rate limiter와 만료 경쟁](https://redis.io/docs/latest/commands/incr/), [TIME의 초·마이크로초 응답](https://redis.io/docs/latest/commands/time/), [ZREMRANGEBYSCORE의 포함 경계](https://redis.io/docs/latest/commands/zremrangebyscore/)다. `ZREMRANGEBYSCORE`의 양 끝은 기본적으로 포함되므로 `(t − 1초, t]`에서 제외할 과거 경계까지 지울 수 있다. 구현한 전략의 짧은 구간 동작과 한계를 이 근거로 설명해라.

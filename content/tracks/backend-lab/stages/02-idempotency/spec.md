# 중복 요청과 멱등 키

[1] 결제 버튼 중복 클릭과 재시도로 같은 결제가 여러 번 접수되는 상황을 다룬다. 먼저 `cresvoid read backend-lab -stage 2`로 계약을 읽고 문항을 푼 뒤 시작 코드를 실험하라. 대행 호출 수와 응답 불일치를 관찰하고 `IdempotencyStore.execute(key, request)`를 구현한 다음 같은 실험을 다시 실행하라.

[2] 서비스는 JDK 21의 HTTP 서버 한 개와 메모리 저장소 한 개로 실행된다. `build.sh`는 실행 jar를 만들고 `run.sh`는 환경 변수 `PORT`가 지정한 `127.0.0.1` 포트에서 서버를 실행한다. `GET /health`는 준비되면 200과 `{"status":"ready"}`를 준다. 각 실험은 새 프로세스와 빈 저장소로 시작한다. Redis나 다른 외부 서비스는 쓰지 않는다.

[3] `POST /payments`에는 `Idempotency-Key` 헤더와 UTF-8 JSON 본문을 보낸다. 키와 `orderId`는 영문 대소문자·숫자·밑줄·하이픈으로 된 1~64자다. 본문은 `{"orderId":"order-1","amount":1000}`처럼 두 필드만 가지며 필드 순서와 필드 사이 공백은 바뀔 수 있다. `amount`는 1~9999999의 정수이며 선행 0은 허용하지 않는다. 통화는 KRW로 고정한다. 본문 크기는 1024바이트 이하다. 키가 없거나 형식이 틀리면 400과 `{"error":"invalid_request"}`를 반환하고 키를 예약하거나 대행을 호출하지 않는다.

[4] 처음 접수한 유효 요청은 대행을 한 번 호출한다. 같은 키와 같은 필드 값으로 요청하면 처리 중에는 첫 결과를 기다리고 완료 뒤에는 저장한 결과를 반환한다. JSON의 필드 순서와 공백은 요청의 동일성에 영향을 주지 않는다. 상태 코드와 응답 본문 바이트를 모두 재사용하라. 처리 중이라는 이유로 409·202나 빈 본문을 반환해서는 안 된다.

[5] 같은 키로 `orderId` 또는 `amount`가 다른 유효 요청이 오면 처리 중과 완료 뒤 모두 422와 `{"error":"key_conflict"}`를 반환한다. 충돌 요청은 대행을 호출하거나 첫 요청의 결과를 덮어쓰지 않는다. 충돌 응답은 첫 대행 결과의 완료를 기다리지 않는다. 키가 다르면 본문이 같아도 별개 결제로 처리한다.

[6] 가짜 대행 `PaymentGateway.charge`는 호출 수와 전역 시도 번호를 늘린다. 실험용 보류가 설정된 키는 해제를 기다리고, 그 뒤 모든 호출이 100ms 기다린다. 금액이 7의 배수가 아니면 201과 `{"paymentId":"p-<시도 번호>","orderId":"<주문>","amount":<금액>}`을 반환한다. 금액이 7의 배수면 대행이 결제를 접수한 뒤 응답이 유실된 상황을 504와 `{"error":"gateway_timeout","attemptId":"a-<시도 번호>"}`로 나타낸다. 시도 번호는 프로세스 안에서 1부터 증가하며 동시 요청의 번호 순서는 정하지 않는다. 이는 HTTP 클라이언트의 전송 타임아웃과 다르다.

[7] 이 단계에서는 504도 확정된 첫 HTTP 결과로 보관한다. 504를 받은 클라이언트가 같은 키로 재시도해도 대행을 다시 호출하지 않고 같은 504와 같은 본문을 돌려준다. 504는 결제가 취소되었다는 뜻이 아니다. 키는 프로세스가 살아 있는 동안 지우지 않는다. 재시작 뒤 복원, 여러 서버의 공유 저장소, 실제 대행의 상태 조회·정산은 구현 범위 밖이다. 프로세스가 대행 접수와 결과 저장 사이에서 죽으면 메모리 저장소만으로 중복 결제를 막을 수 없다는 한계를 설명할 수 있어야 한다.

[8] 두 시나리오는 먼저 별도 키 `probe`와 주문 `probe-order`, 금액 1000으로 처리 중 충돌을 검사한다. 환경 변수 `LAB_HOLD_KEY=probe`로 시작하면 대행은 이 키의 호출 수와 시도 번호를 늘린 뒤 결과를 보류한다. `GET /gate`의 200과 `{"held":true}`로 보류 진입을 확인하고 금액만 1100으로 바꾼 요청과 주문만 `other-probe-order`로 바꾼 요청을 함께 보낸다. 두 충돌 응답을 수집할 때까지 원래 요청은 미완료이고 대행도 보류 중이어야 한다. 그 뒤 `POST /gate/release`에 빈 본문을 보내 200과 `{"released":true}`를 확인하고 원래 결과를 수집한 다음 같은 키와 원래 값으로 재요청한다. 이 키의 대행 호출은 1회이고 원래 응답과 재요청 응답은 같아야 한다. 보류 조회는 최대 15초 동안 반복하며 각 충돌 요청에도 15초 전송 제한을 둔다. 이 제한은 교착을 끝내는 장치이며 짧은 응답 시간을 요구하는 성능 기준이 아니다.

[8.1] 이어서 `parallel-arrivals`는 키 14개에 금액 1400~1413을, `later-arrivals`는 키 21개에 금액 2100~2120을 배정한다. 단, 두 번째 키에는 첫 키와 같은 주문과 금액을 배정해 키의 독립성도 확인한다. 나머지 키의 주문은 서로 다르다. 키 묶음은 100ms 간격으로 도착하며 묶음마다 같은 요청 3개를 같은 예정 시각에 보낸다. 모든 첫 응답을 수집한 뒤 두 번째 개방형 부하를 시작한다. 같은 간격으로 키마다 재요청 3개와 금액만 바꾼 충돌 요청 1개, 주문만 바꾼 충돌 요청 1개를 같은 예정 시각에 보낸다. 재요청 가운데 하나는 JSON 필드 순서와 공백을 바꾼다. 후속 부하에는 504를 받은 키도 포함한다. 각 부하 안의 도착 시각은 앞 요청의 완료 여부와 관계없이 유지한다.

[9] 두 개방형 부하에서 각 키의 원래 요청에 대한 응답은 첫 부하 3개와 후속 부하 3개, 총 6개다. 충돌 응답은 이 비교에서 제외한다. `GET /stats?key=<키>`는 관찰 전용이며 200과 `{"calls":<해당 키의 대행 호출 수>}`를 준다. 두 부하가 끝난 뒤 키별 호출 수를 읽는다. 보류 검사 키의 원래 응답은 첫 요청과 해제 뒤 재요청, 총 2개다. 이 키까지 포함한 두 시나리오의 키 수는 각각 15개와 22개이고 결제 요청 수는 각각 116개와 172개다. 각 HTTP 요청에는 15초 전송 제한을 두며 전송 오류와 누락은 실패로 센다. 이 제한은 멈춘 요청을 끝내기 위한 장치이며 성능 합격선이 아니다.

[10] 합격 조건은 모든 키의 대행 호출 수가 정확히 1이고, 같은 키의 원래 요청이 모두 같은 상태 코드와 같은 본문을 반환하며 충돌 요청이 모두 422와 지정된 충돌 본문을 반환하는 것이다. 원래 요청의 상태와 본문 형식은 [6]의 성공·타임아웃 계약에도 맞아야 한다. 504는 의도한 대행 결과이므로 허용하지만 그 밖의 5xx와 전송 오류는 0건이어야 한다. 서로 다른 키가 만든 결제·시도 식별자도 서로 달라야 한다. 보류 검사에서는 충돌 응답 두 개가 끝날 때까지 첫 결과가 미완료여야 한다. 서로 다른 키의 대행 실행이 겹치는지는 합격 조건이 아니며, 충돌 응답을 첫 결과보다 먼저 반환하고 나머지 조건을 지키면 서로 다른 키의 대행 호출을 전역으로 직렬화해도 된다. 참조 풀이와 수정본은 각 시나리오를 세 번 통과해야 한다.

[11] 지표 `key_count`는 키 수, `gateway_calls`는 대행 호출 수 합계, `call_violations`는 호출 수가 1이 아닌 키 수다. `response_mismatches`는 원래 요청의 응답이 키 안에서 일치하지 않는 키 수, `unexpected_responses`는 원래 요청의 계약 위반 응답 수와 서로 다른 키 사이 식별자 중복 수와 통계 응답 오류 수의 합이다. `conflict_failures`는 422 또는 지정 본문을 지키지 않은 충돌 요청 수, `transport_errors`는 전송 오류 수다. `inflight_failures`는 보류 진입·유지·해제 확인에 실패한 횟수와 충돌 응답을 수집하기 전에 원래 요청이 완료된 횟수의 합이다. 여섯 오류 지표는 모두 0이어야 한다. `p99_ms`는 보류 제어와 통계 조회를 제외한 전체 결제 요청의 응답 시간 99백분위수이며 참고용이다. 절대 시간보다 개수와 관계로 판정한다.

[12] 수정 범위는 `src/main/kotlin/IdempotencyStore.kt`의 저장 상태와 `execute` 구현이다. 이 파일 안에 자료형이나 보조 함수를 추가해도 된다. HTTP 라우터·대행·통계·빌드·실행 파일과 다른 소스는 바꾸지 마라. 100ms 지연과 504 발생 조건을 그대로 유지하라. 보류 제어는 실험 장치이므로 바꾸지 마라.

[13] 시작 코드를 먼저 실험하고 호출 수와 응답 지표를 기록하라. 구현 방향이 필요하면 첫 관찰 뒤 `hints.md`를 읽어라.

[14] [Stripe의 멱등 요청 API 문서](https://docs.stripe.com/api/idempotent_requests)는 API v1에서 첫 실행의 상태 코드와 본문을 실패 응답까지 저장하며 같은 키의 매개변수를 비교한다고 설명한다. 이 실험의 504 보관은 이 원칙을 연습하도록 정한 계약이다. Stripe의 키 보관 기간과 동시 실행 충돌 정책을 그대로 재현하는 것은 아니다. 실제 서비스에서는 키의 보관 기간이 재시도 기간보다 짧을 때의 중복, 처리 중 크래시, 실패 결과 보관 정책을 별도로 정해야 한다. 멱등 키가 부작용 중복을 막아도 지터 없는 동시 재시도 자체의 부하는 사라지지 않는다.

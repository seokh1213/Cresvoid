# 타임아웃, 재시도, 백오프

[1] 느려진 하위 서비스에 같은 요청을 곧바로 반복하면 장애 중인 서비스가 처리할 일이 더 늘어난다. 이 단계에서는 조회 API의 재시도 정책을 구현한다. 먼저 예측 문항을 풀고 재시도를 늘렸을 때 성공률과 하위 호출 수가 어떻게 달라질지 예상하라. 학습자 작업 공간에서 `./build.sh`로 빌드한 뒤 프로젝트 루트에서 `engine/bin/cresvoid test backend-lab -stage 7`로 실험해 하위 호출 수, 오류 응답, 지연을 관찰하라. 수정 후 같은 실험을 반복해 예측과 측정을 비교하라.

[2] JDK 21과 Kotlin 표준 라이브러리만 사용한다. `./build.sh`는 `build/app.jar`를 만들고 `./run.sh`는 `PORT` 환경 변수로 받은 포트의 `127.0.0.1`에서 HTTP 서비스를 실행한다. 실험기가 하위 HTTP 서버를 띄우고 `DOWNSTREAM_URL`로 주소를 전달한다. 별도 Docker 서비스나 외부 부하 도구는 필요하지 않다. 준비 확인용 `GET /health`는 하위 호출 없이 200과 `{"ready":true}`를 반환한다.

[3] 공개 조회는 `GET /quotes/{id}`다. id는 영문 소문자, 숫자, 하이픈으로 된 1~64자다. 하위 호출은 `GET ${DOWNSTREAM_URL}/quote/{id}`이며 본문은 보내지 않는다. 하위 서비스의 200 또는 404는 상태와 UTF-8 본문을 그대로 돌려준다. 재시도를 포기하면 503과 `{"error":"unavailable"}`, `Retry-After: 1`을 반환한다. 다른 메서드는 405, 다른 경로는 404다. 조회에는 부작용이 없으며, 같은 id의 재시도는 같은 논리 요청을 뜻한다. 응답을 합성하거나 캐시하지 말고 모든 조회에서 최초 하위 호출을 한 번 수행하라.

[4] 하위 서비스의 평상시 처리 지연은 20ms다. 정상·회복 구간은 각각 전송 순번 1~60을 사용한다. 매 20개 묶음에서 10번째 요청은 첫 호출부터 404를 주고, 20번째 요청은 처음 두 번 503을 주고 세 번째 호출에서 200을 준다. 나머지는 첫 호출에서 200을 준다. 모든 id는 실행마다 새 UUID로 만들며, 전송 순번으로 정한 역할은 응답 완료 순서나 재시도 시각과 무관하게 유지한다. 각 id의 하위 호출 횟수로 그 역할에 따른 응답을 정한다. 404는 재시도하지 않는다. 하위 HTTP 상태 중 200·404·503만 실험·평가하며 다른 상태의 처리는 이 단계 범위 밖이다. 503과 통신 오류에는 재시도할 수 있지만 최초 호출을 포함해 id당 하위 호출은 최대 3번이다. `InterruptedException`은 재시도하지 말고 중단 상태를 보존하라.

[5] 요청마다 타임아웃을 두고, 대기와 재시도를 포함한 전체 처리 마감도 두어라. 연결 타임아웃만으로 응답 대기를 제한할 수는 없다. 재시도는 요청마다 따로 허용하지 말고 서비스 전체 예산으로 제한하라. 한 요청의 최대 시도 수와 전체 예산은 서로 다른 제한이다. 예산을 기다리는 무제한 큐도 두지 마라. 타임아웃이 발생해도 하위 서버에서 이미 시작한 처리가 사라지는 것은 아니다.

[6] 첫 번째 재시도 전에는 40~80ms, 두 번째 재시도 전에는 80~160ms에서 정수 지연을 독립적으로 무작위 선택해 기다려라. 지수적으로 늘어나는 대기 상한은 일반식으로도 320ms를 넘기지 않도록 구현하라. 이는 이 실험의 백오프 계약이며 운영 서비스의 보편적 설정값은 아니다. 하위 요청의 `X-Attempt`는 최초 0, 이후 1과 2다. `X-Backoff-Ms`에는 이번 호출 직전에 선택한 대기 시간을 적고 최초에는 0을 적는다. 진단 헤더 값만 바꾸지 말고 실제로 기다려라.

[7] 각 시나리오는 새 서비스 프로세스에서 열린 부하를 보낸다. 준비 확인 뒤 정상 조회 60개를 30/s로 보내고, 부하 시작 2.5초부터 장애 조회 160개를 40/s로 보낸다. 6.5초부터 회복 조회 60개를 30/s로 보낸다. 이전 응답이 느려져도 후속 요청의 예정 시각은 바꾸지 않는다. 모든 id는 서로 다르며 어느 구간인지 서비스에 별도 헤더로 알려 주지 않는다. 클라이언트의 요청 제한 시간은 6초다.

[8] `morning-traffic`의 장애 조회는 하위 호출마다 20ms 뒤 503을 받는다. `afternoon-traffic`의 장애 조회는 하위 호출마다 3000ms 뒤 503을 받는다. 회복 조회에는 즉시 평상시 동작을 적용한다. 경계에 걸친 재시도도 최초 상위 요청의 구간에 귀속한다. 장애가 끝났다고 진행 중인 하위 처리를 취소하지 않는다. 실험기는 서비스를 준비시킨 뒤 부하를 보내고, 통계를 집계한 다음 서비스와 하위 서버를 종료한다.

[9] 장애 구간의 하위 요청 수는 상위 요청 수의 1.2배 이하여야 한다. `fault_upper_requests`는 예정대로 보낸 장애 조회 수 160, `fault_lower_requests`는 그 id들에 대해 하위 서버가 실제 받은 최초 호출과 재시도의 합이다. 따라서 하위 호출은 최대 192번이다. 빠른 503과 느린 응답 모두에서 이 제한을 지켜라. 최초 호출을 생략해 이 비율을 낮추는 것은 허용하지 않는다.

[10] `normal_success_ratio`는 정상 구간과 회복 구간 각각에서 기대한 상태와 본문을 받은 비율 중 작은 값이다. 둘 다 0.98 이상이어야 한다. 404도 기대한 본문이면 정상 완료로 센다. `protocol_errors`는 최초 호출 누락, 잘못된 하위 경로·메서드·시도 번호, 최초 대기 헤더 오류, 404 재시도, 장애 조회의 503·본문 계약 위반을 합한 값이며 0이어야 한다. `max_attempts`는 id별 하위 호출 수의 최댓값이며 3 이하여야 한다. 오류를 숨기거나 재시도를 모두 끈 구현도 이 조건으로 구별한다.

[11] `fault_p95_ms`는 장애 조회의 전송 시작부터 응답 완료까지 지연 중 최근접 순위 방식 p95이며 1800ms 이하여야 한다. 통신 오류의 대기 시간도 포함한다. `recovery_p95_ms`는 회복 조회의 같은 지연 p95다. 정상 구간 p95의 4배를 최소 400ms, 최대 1200ms로 제한해 구한 `recovery_limit_ms` 이하여야 한다. 회복 조회를 장애 종료 직후부터 2초 동안 보내고 모두 6초 안에 끝내므로 이 조건은 장애 종료 후 10초 안의 회복을 확인한다. 측정 대상은 상위 HTTP 응답이며 하위 서버에서 뒤늦게 끝나는 작업 시간은 포함하지 않는다.

[12] `backoff_errors`는 재시도 지연 헤더가 [6]의 범위를 벗어나거나 실제 간격이 선언한 대기보다 15ms 넘게 짧은 인접 호출 쌍의 수다. 응답을 받은 재시도는 직전 하위 응답 기록부터 다음 호출 수신까지, 응답 전 타임아웃 재시도는 직전 호출 수신부터 잰다. 응답을 받은 경우에는 간격이 선언한 대기보다 1000ms 넘게 길어져도 오류로 센다. 값은 0이어야 한다. `jitter_values`는 정상·회복 구간에서 첫 재시도에 사용한 서로 다른 대기 값의 수이며 3 이상이어야 한다. 이는 지터가 없는 정책을 구별하는 표본 검사다. p95는 정렬한 N개 값의 `ceil(0.95 × N)`번째 값이다.

[13] 수정 범위는 `src/main/kotlin/DownstreamClient.kt`다. 필요하면 같은 디렉터리에 예산·백오프 정책 파일을 추가하라. 공개 HTTP 계약, `Main.kt`, 빌드·실행 스크립트와 실험기는 바꾸지 마라. 상태 코드, 호출 수, 대기 시간을 구간이나 특정 id에 맞춰 조작하지 말고 모든 요청에 같은 정책을 적용하라. 처음에는 실패 지표 하나를 골라 원인을 설명하고, 고친 뒤 나머지 불변식까지 함께 지켜지는지 확인하라.

[14] API 근거는 JDK 21의 [HttpRequest.Builder.timeout](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpRequest.Builder.html#timeout(java.time.Duration))과 [HttpClient.Builder.connectTimeout](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.Builder.html#connectTimeout(java.time.Duration))이다. 전자는 응답 대기를 제한하며 지정하지 않으면 무기한 대기할 수 있고, 후자는 새 연결을 맺는 시간을 제한한다. 재시도 한도를 한 계층에서 관리하고, 백오프 상한·지터·토큰 예산을 함께 쓰는 배경은 Amazon Builders' Library의 [Timeouts, retries, and backoff with jitter](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)를 읽어라. 이 단계의 요청률·지연·합격 수치는 위 실험을 위한 계약이다.

[15] 엔진은 집계 지표만 표시하므로 실패 원인을 더 보려면 빌드한 뒤 프로젝트 루트에서 `kotlin content/tracks/backend-lab/stages/07-retry-storm/hidden/experiment.main.kts <학습자 작업 공간 절대 경로> <시나리오 이름> --diagnose`를 실행하라. 이 명령은 숨은 파일을 읽거나 고치는 대신 실험기를 직접 실행하는 진단 절차다. 같은 부하와 불변식으로 새 실험을 하며 종료 코드는 통과 0, 불변식 실패 1, 실행 오류 2다. 진단에는 위반 종류별 건수와 관측값·기대 범위를 표시한다. 하위 경로·메서드, 시도 번호, 최초 대기 헤더, 최초 호출 누락, 404 재시도, 장애 응답 계약, 재시도 헤더 범위, 실제 대기 간격을 구분한다. 요청 id와 본문은 출력하지 않는다. `protocol_errors`는 [10]의 합계이고 `backoff_errors`는 위반한 인접 호출 쌍의 수이므로, 한 호출이나 쌍에서 여러 종류를 위반하면 진단 종류별 건수의 합과 다를 수 있다.

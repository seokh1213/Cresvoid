# 캐시 관통과 동시 만료

[1] 상품 조회 서비스의 캐시 정책을 구현해라. 없는 상품의 반복 조회와 여러 상품의 동시 만료가 원천에 주는 부하를 관찰하고 요청 결과를 보존하면서 원천을 보호해라. 시작 코드는 빌드되지만 합격 불변식을 만족하지 않는다.

[2] 먼저 `./build.sh`로 빌드를 확인해라. 문항을 마친 뒤 `cresvoid test backend-lab`으로 실험해라. 첫 실행에서 `missing_origin_calls`, `origin_peak_1s`, `origin_peak_active`, `ttl_span_ms`를 기록해라. `src/main/kotlin/CachePolicy.kt`를 고친 뒤 같은 실험으로 전후 값을 비교해라. Docker Desktop을 켜 두어라. 실험기는 격리된 Redis와 HTTP 서버를 시작하고 준비 확인, 부하, 통계 수집, 종료를 맡는다. 수동 실행에는 `REDIS_PORT`와 `PORT`가 필요하며 서버는 `127.0.0.1:$PORT`에서만 듣는다.

[3] 공개 API는 `GET /products/{id}`다. id는 1 이상 20000 이하의 정수다. 처음에는 1부터 10000까지의 상품이 존재한다. 있는 상품은 HTTP 200과 `{"id":7,"price":1007}` 같은 JSON을, 없는 상품은 HTTP 404와 `{"error":"not_found"}`를 반환해라. 가격은 1000 + id다. 응답 본문은 이 형식과 정확히 같아야 한다. 예를 들어 `/products/7`은 위의 200 본문을 반환하고 `/products/10001`은 처음에는 위의 404 본문을 반환한다. 잘못된 id는 400이다. `/health`는 준비가 끝났을 때 200을 반환한다.

[4] Redis의 키는 `product:{id}`다. 캐시 미스일 때만 `Origin.fetch(id)`로 원천을 조회해라. 원천은 실제로 조회를 시작할 때마다 호출 수를 세고 80ms 뒤 결과를 반환한다. 임의의 이동 1000ms 구간에서 호출 시작이 300건을 넘으면 초과 호출은 HTTP 503으로 이어진다. 원천 동시 호출 수도 별도로 측정한다. 같은 키를 기다리는 요청은 캐시를 다시 확인해라. 값이 없다는 결과는 캐시 미스와 구별되는 표식으로 저장해라. 원천 호출을 우회해 상품 본문을 만들거나 로컬 영구 캐시로 Redis를 대체하지 마라.

[5] 있는 상품의 TTL은 `ttlMillis(id)`에서 정해라. 모든 TTL은 5000ms 이상 15000ms 이하여야 한다. 1만 키의 최댓값과 최솟값 차이는 8000ms 이상이어야 하며, `floor((TTL − 5000) / 1000)`으로 나눈 버킷을 8개 이상 채워야 한다. 재조회 뒤 저장할 때도 이 함수를 써라. 난수 지터나 키마다 재현 가능한 분산을 써도 된다. 없는 상품의 음성 TTL은 저장 시점부터 2000ms다. 만료 없는 표식은 허용하지 않는다. 음성 TTL이 길면 새로 생긴 상품도 그동안 보이지 않는다. 블룸 필터의 거짓 양성은 없는 상품을 원천까지 보내므로 음성 캐시와 원천 보호를 따로 검토해라.

[6] 시나리오 `mixed-catalogue`는 빈 Redis에서 시작한다. 예열 없이 6초 동안 초당 300건을 예정 시각에 보내는 개방형 부하다. 요청 순번 i는 0부터 센다. `i % 10 < 3`이면 id는 `10001 + (floor(i / 10) × 3 + i % 10) % 6`이고, 나머지 요청의 id는 `1 + i % 100`이다. 매 10건의 처음 3건은 없는 상품, 나머지 7건은 있는 상품에 보낸다. 총 1800건이며 없는 상품 요청은 540건이다. 누락된 요청과 통신 실패도 응답 오류로 센다. 부하가 끝나면 10001번을 원천에 만들고, 생성 응답에서 2500ms 뒤 조회 1건을 더 보내 HTTP 200과 해당 상품 본문을 확인한다.

[7] 시나리오 A의 없는 상품 원천 호출 수는 24건 이하여야 한다. 상한은 서로 다른 없는 id 6개 × (floor(실행 시간 6초 / 음성 TTL 2초) + 1)이다. `missing_origin_calls`는 추가 생성 전에 완료된 원천의 없는 상품 조회 수이며, 1건 이상이어야 한다. `missing_limit`은 24다. 마지막 생성 후 조회의 상태·본문·통신 오류 수인 `late_visibility_errors`는 0이어야 한다. 최초 1800건의 상태와 본문이 [3]과 다르면 `response_errors`에 센다.

[8] 시나리오 `catalogue-sweep`는 `/admin/seed`로 1만 상품을 채운다. 모든 키에 같은 기준 시각을 쓰고 만료 시각을 기준 시각 + `ttlMillis(id)`로 설정하므로, 고정 TTL 구현은 한꺼번에 만료된다. 채우기가 끝나면 예열 없이 12초 동안 초당 500건, 총 6000건을 보낸다. 요청 순번 i를 0부터 셀 때 id는 `1 + (i × 73) % 10000`이다. 부하는 앞 요청 완료를 기다리지 않는다. 모든 응답은 HTTP 200과 해당 상품 본문이어야 한다. TTL 분포도 실제 채우기에 사용한 1만 개의 값으로 측정한다.

[9] 두 시나리오 모두 원천 호출 시작의 이동 1초 최댓값은 100건 이하, 원천 동시 호출 최댓값은 12건 이하, HTTP 5xx와 응답 오류는 각각 0건이어야 한다. 100건은 [4]의 503 발생 기준인 300건보다 낮은 보호 목표다. B에서는 실제 만료와 재조회가 일어나 원천 호출이 500건 이상이어야 하며, [5]의 TTL 분포도 만족해야 한다. 동시성 상한만으로 이 시작률 목표를 보장할 수는 없다. 실제 호출 시작 간격도 검토해라. 호출 상한만 두면 만료 시점의 대기를 줄이지 못하므로 TTL 분산도 필요하다. 캐시 재시작으로 모든 키가 사라지면 지터만으로는 원천을 보호할 수 없으며, 예열과 호출 상한이 필요하다.

[10] `requests`는 예정된 상품 요청의 결과 수다(A 1801, B 6000). `origin_calls`는 B의 전체 원천 호출 시도 수다. `origin_peak_1s`는 모든 실제 호출 시작 시각에서 직전 1000ms 안의 호출 수를 센 최댓값이며, 거절된 호출도 포함한다. `origin_peak_active`는 동시 원천 호출 최댓값이다. `server_errors`는 5xx 응답 수다. `ttl_span_ms`는 TTL 최댓값 − 최솟값, `ttl_bins`는 [5]의 버킷 수, `ttl_invalid`는 범위 밖 TTL 수다. 각 실험은 해당 지표만 최대 9개 출력한다. 상품 요청의 HTTP 제한 시간은 30초다. 제한 시간 초과를 합격으로 보지 않는다. 불변식 실패는 종료 코드 1, 서비스 준비·제어 요청·Docker 오류는 2다. 각 시나리오를 세 번 모두 통과해야 한다.

[11] 수정 범위는 `src/main/kotlin/CachePolicy.kt` 하나다. TTL 계산, 음성 결과 저장과 해석, 같은 키의 중복 조회 억제, 원천 호출의 동시성 및 시작률 제어를 구현해라. 필요한 필드와 보조 함수를 이 파일 안에 추가해도 된다. 원천·통계·HTTP 라우팅·Redis 클라이언트·실험용 관리 API·빌드 파일은 고치지 마라. `/admin/seed`는 [8]의 초기 상태를 만들고, `/admin/stats`는 [10]의 원천 통계를 반환하고, `PUT /admin/products/{id}`는 원천에 상품을 만든다. 이 관리 API는 실험 전용이다. 새 의존성을 추가하지 마라.

[12] 공식 API 근거를 확인해라. [Redis SET](https://redis.io/docs/latest/commands/set/)은 `PX`를 밀리초 TTL로, `PXAT`를 밀리초 절대 만료 시각으로 정의하며, 옵션 없는 덮어쓰기는 기존 TTL을 지운다. 값과 만료를 한 SET에 넣어라. [JDK 21 Semaphore](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Semaphore.html)의 허가 수는 동시 진입 수를 제한하며 초당 진입 수를 정하지 않는다. [Amazon Builders’ Library의 캐시 전략](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/)은 음성 결과 캐시와 원천 과부하 방어를 다룬다. [AWS의 캐싱 모범 사례](https://aws.amazon.com/caching/best-practices/)는 TTL에 무작위 값을 더해 여러 키가 같은 시간대에 만료되는 현상을 줄이는 방법을 설명한다. 이 단계의 수치와 부하·채점 계약은 [3]부터 [10]까지를 따라라.

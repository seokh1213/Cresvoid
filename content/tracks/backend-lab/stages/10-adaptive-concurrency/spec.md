# 적응형 동시성 제한

[1] 주문 집계 API 앞에 적응형 동시성 제한기를 구현해라. 하위 서비스의 처리 능력이 줄면 실행 중인 호출이 쌓이고 응답이 늦어진다. 처리 능력이 돌아왔는데도 낮은 한도를 유지하면 성공 처리량을 회복하지 못한다. 호출 지연으로 동시 실행 한도를 조절하고 한도를 넘은 요청은 하위 서비스를 부르기 전에 빠르게 거절해라.

[2] 먼저 `Limiter.kt`의 허용 경로와 `Main.kt`의 측정·반납 경로를 읽어라. 시작 코드를 빌드해 실험하고 `accepted_p99_ms`, 세 goodput 비율, `rejected`를 비교해라. 한도가 너무 클 때와 너무 작을 때 어떤 지표가 실패할지 예측해라. 제한기를 고친 뒤 두 시나리오를 각각 세 번 실행해라. 한 번 통과한 결과만으로 끝내지 마라.

[3] `build.sh`는 `build/app.jar`를 만들고 `run.sh`는 `PORT` 환경 변수의 포트에서 `127.0.0.1`에만 HTTP 서비스를 연다. `GET /health`는 200과 본문 `ready`를 반환한다. `POST /work`는 영문자·숫자·하이픈 1~80자로 된 요청 ID를 본문으로 받는다. 허용하면 `DOWNSTREAM_URL`의 `POST /execute`에 같은 ID를 정확히 한 번 보내고 그 호출이 완료된 뒤 200과 `done:<요청 ID>`를 반환한다. 거절하면 하위 호출 없이 429, 본문 `busy`, `Retry-After: 1`을 반환한다. 잘못된 ID는 400과 `invalid`, 없는 경로는 404와 `missing`, 하위 호출 실패는 502와 `unavailable`이다. 실험 부하는 유효한 ID만 쓰고 하위 서비스는 200을 반환하므로 부하 중에는 200과 429만 허용한다.

[4] `Limiter.tryAcquire()`는 대기열이나 sleep 없이 허용 여부를 반환한다. 허용 여부 확인과 실행 중 개수 증가는 원자적으로 수행해라. 허용한 호출에는 `onComplete(elapsedNanos)`가 성공·실패와 관계없이 정확히 한 번 호출된다. 경과 시간에는 하위 HTTP 호출 전체가 들어가고, 클라이언트에게 본문을 쓰는 시간은 들어가지 않는다. 한도를 낮춰 이미 실행 중인 개수보다 작아져도 기존 호출을 취소하거나 반납 개수를 잃지 마라. 거절한 요청의 지연을 하위 서비스의 정상 지연 표본으로 섞지 마라.

[5] 부하는 공용 `load.main.kts`의 개방형 일정으로 24초간 보낸다. 앞 요청이 끝나기를 기다리지 않고 예정된 시각마다 새 요청을 보내며, 거절된 요청을 재시도하지 않는다. `weekday-traffic`은 정상 동시 처리 능력 C=12, 기본 처리 시간 S=120ms, 도착률 120/s이고, `evening-traffic`은 C=8, S=160ms, 60/s이다. 8초에 C를 절반으로 줄이고 16초에 원래 값으로 되돌린다. 서비스와 제한기를 재시작하지 않는다. 하위 서비스는 요청 진입 시 실행 중 개수 A와 현재 C를 읽고 S + min(2000, 80 × max(0, A−C)²)ms 동안 처리한다. 이는 동시 실행이 처리 능력을 넘을 때 경합 비용이 급증하는 모형이며 실제 서버의 성능 예측식은 아니다. 실험기는 별도 HTTP 하위 서비스를 소유한다. 제한기가 관측할 수 있는 입력은 호출 완료 지연과 자신이 관리하는 실행 중 개수뿐이다.

[6] 0~4초는 초기 탐색, 8~12초와 16~20초는 변화 뒤 적응 구간이다. 안정 구간은 예정 도착 시각 기준 [4,8), [12,16), [20,24)초다. 따라서 능력이 바뀐 뒤 4초 안에 적응해 다음 4초 동안 처리량과 지연을 지켜야 한다. goodput은 해당 구간에 도착해 실제 하위 호출을 한 번 완료하고 650ms 이내에 HTTP 200으로 끝난 요청 수를 4초로 나눈 값이다. 각 구간의 goodput 비율은 이 값을 해당 구간의 기준 처리량 C×1000/S로 나눈 값이다. 기준 처리량은 첫 시나리오에서 100→50→100/s, 두 번째에서 50→25→50/s이다. 요청 지연은 클라이언트의 실제 전송 시작부터 본문 수신 완료까지 재고, 요청은 최대 5초 기다린다. 부하 종료 뒤 진행 중 요청도 끝까지 집계한다.

[7] 각 안정 구간의 goodput 비율은 0.60 이상이어야 한다. `initial_goodput_ratio`, `reduced_goodput_ratio`, `restored_goodput_ratio`가 그 세 값이다. 각 안정 구간에서 HTTP 200 요청의 최근접 순위 p99를 구한 뒤 그중 최댓값인 `accepted_p99_ms`는 650 이하여야 한다. 전체 429 요청의 같은 방식 p99인 `rejected_p99_ms`는 250 이하여야 한다. 최근접 순위는 정렬한 n개 중 ceil(0.99×n)번째다. 빈 표본의 p99는 0으로 두지만 goodput 조건은 그대로 적용한다. `rejected`는 전체 429 개수이며 1 이상이어야 한다. 정상 능력보다 부하가 높으므로 지연을 지키려면 일부를 거절해야 한다. 적응 구간의 200은 안정 구간의 지연·goodput 계산에서 제외하며, 잘못된 응답과 호출 계약 검사는 24초 전체에 적용한다.

[8] `attempted`는 예정한 요청 수이며 각각 2880과 1440이다. `downstream_calls`는 실험기가 직접 센 하위 호출 수다. `unexpected_responses`는 HTTP 200·429 이외의 응답과 통신 실패의 합이며 0이어야 한다. `contract_errors`도 0이어야 한다. 이는 200 본문 불일치·하위 완료 누락·중복 호출, 429 본문 불일치·하위 호출 발생, 예정 요청에 없는 ID의 하위 호출을 센다. 지표는 합계 10개다. 즉시 200을 반환하거나 모든 요청을 거절해 처리량을 꾸미지 마라. `attempted`가 예정 수와 다르거나 필수 지표가 빠진 실행, 빌드 실패와 실험 시간 초과는 불변식 실패로 인정하지 않는다.

[9] 수정 범위는 `src/main/kotlin/Limiter.kt` 하나다. 같은 파일에 제한기에 필요한 타입을 더할 수 있다. `Main.kt`, 빌드·실행 스크립트와 하위 서비스 계약을 바꾸지 마라. 새 의존성, 추가 하위 호출, 재시도, 환경 변수나 요청 ID로 시나리오를 알아내는 분기, 실험 시간표에 맞춘 한도 변경은 금지한다. 초기 한도·탐색 간격·안전 상하한은 둘 수 있지만 고정 동시 실행 한도나 고정 RPS를 최종 제한 정책으로 쓰지 마라. 측정 피드백으로 실행 중 처리 능력 C의 변화에 대응해라. 이 단계에서는 각 시나리오의 기본 처리 시간 S가 실행 내내 고정되며, 실행 중 S 변화에 대한 적응과 지연 기준의 갱신은 검증 범위 밖이다.

[10] 리틀의 법칙 L=λW는 안정 상태에서 평균 실행 중 개수 L, 처리율 λ, 평균 체류 시간 W를 연결한다. 예를 들어 80/s와 120ms는 평균 9.6개에 해당한다. 평균 관계만으로 꼬리 지연이나 과도 구간을 보장하지는 못한다. 오래된 최소 지연을 영구히 기준으로 쓰면 정상 처리 시간이 달라졌을 때 경합으로 오해할 수 있다. 반대로 경합 표본으로 기준을 너무 빨리 올리면 과부하를 정상으로 받아들인다. 429를 받는 클라이언트가 즉시 재시도하면 도착률이 더 커지므로 실제 서비스에서는 재시도 예산과 백오프도 함께 설계해라.

[11] 구현 근거는 JDK 21의 [HttpServer](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.httpserver/com/sun/net/httpserver/HttpServer.html), [System.nanoTime](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/System.html#nanoTime()), [Executors.newVirtualThreadPerTaskExecutor](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Executors.html#newVirtualThreadPerTaskExecutor()) 공식 API다. `nanoTime`의 차이로 경과 시간을 재고, 별도 executor로 동시 HTTP 요청을 처리한다. [Netflix concurrency-limits](https://github.com/Netflix/concurrency-limits)는 지연 기반 동시성 추정과 리틀의 법칙을 설명한다. 특정 알고리즘이나 라이브러리를 그대로 구현할 필요는 없다. 이 단계의 부하·경합식·임계값은 교육용 실험 계약으로 정한 값이다.

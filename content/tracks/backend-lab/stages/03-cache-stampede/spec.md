# 캐시 스탬피드

[1] 인기 상품의 캐시가 비는 순간을 관찰하고 `ProductCache.get(id)`를 구현해라. 먼저 시작 코드를 빌드하고 두 실험의 지표를 기록해라. 원천 조회 수와 만료 횟수를 비교한 뒤 고치고 같은 실험을 다시 실행해라. 마지막으로 한 JVM 안의 요청 병합만으로 두 인스턴스를 보호할 수 있는지 설명해라.

[2] 서비스는 `PORT`가 지정한 `127.0.0.1` 포트에서 HTTP로 실행된다. `GET /health`는 200과 `ok`를 반환한다. `GET /products/{id}`는 1~100의 정수 id에 대해 200과 `{"id":1,"name":"product-1","price":100}` 형태의 JSON을 반환한다. name은 `product-<id>`, price는 id × 100이다. 범위 밖 id나 경로는 404다. 이 단계에서는 상품이 변경되지 않는다.

[3] 실험기는 고정 이미지의 Redis 하나와 같은 프로그램의 JVM 두 개를 시작한다. 두 JVM은 `REDIS_HOST`, `REDIS_PORT`를 공유하고 `ORIGIN_DELAY_MS`만큼 걸리는 원천을 사용한다. `Origin.fetch(id)`는 실제 조회마다 Redis의 `origin:calls:<id>`를 1 늘린 뒤 지연하고 상품을 반환한다. `origin:gate:<id>`가 `closed`이면 지연 전에 기다린다. 이 계수와 게이트, 원천 지연은 관찰 장치이므로 바꾸지 마라.

[4] Redis의 상품 키는 `product:<id>`, 잠금 키는 `lock:product:<id>`다. 상품 값은 HTTP 응답과 같은 JSON이며 저장할 때마다 TTL을 5,000ms로 설정해라. 조회 적중만으로 TTL을 늘리거나 Redis를 우회하는 영구 로컬 캐시를 만들지 마라. 만료된 상품은 원천에서 다시 읽어라. 잠금 토큰은 획득 시도마다 새로 만들고, 잠금은 유한한 TTL을 가져야 한다.

[5] 같은 키의 캐시가 비어도 두 JVM을 합쳐 원천 조회가 겹치지 않게 해라. 잠금을 얻기 전에 읽은 캐시 상태는 획득 시점의 상태와 다를 수 있다. 원천 조회 중 임대가 끝나는 경우와 다른 요청이 먼저 캐시를 채운 경우를 모두 고려해라. 요청 병합과 임대 정책, 대기 간격은 직접 설계해라.

[6] 잠금을 해제할 때는 현재 값이 자신이 획득한 토큰일 때만 삭제해라. 토큰 확인과 삭제는 원자적으로 실행해라. 후속 토큰 보존 검사는 상품 99의 게이트를 닫고 원천 조회 시작을 확인한 뒤 잠금 값을 다른 토큰과 5초 TTL로 교체하고 게이트를 연다. 기존 요청이 끝나도 새 소유자의 잠금이 그대로 남아야 한다. 이 검사만으로 확인과 삭제 사이의 원자성을 판별할 수는 없다. 별도의 상품 93 검사에서는 Redis 프록시가 잠금 GET의 결과를 받은 직후, 그 결과를 JVM에 전달하기 전에 후속 토큰과 5초 TTL을 설치한다. 이후 별도 DEL이 후속 토큰을 지우면 실패다. 원자적 비교 삭제는 이 틈을 만들지 않는다. 두 검사 모두 상품이 변경되지 않으므로 먼저 시작한 조회의 응답과 캐시 저장을 허용한다.

[7] 종료된 보유자의 잠금을 기다리는 상황도 복구해라. 실험은 상품 98에 300ms 뒤 만료되는 잠금만 남긴 다음 두 JVM에 총 20개의 요청을 500요청/초로 보낸다. 모두 올바른 200 응답으로 끝나고 합친 원천 조회 수가 정확히 1이어야 한다. 복구 지연 보장은 잔여 TTL이 300ms인 이 상황에 한정한다. 실제 JVM을 임대 획득 직후 종료하는 검사는 하지 않으며, 긴 임대의 잔여 시간까지 300ms 안에 복구하라는 요구는 아니다. 별도로 상품 94~97을 두 JVM에서 각각 동시에 조회해, 키마다 원천 조회가 정확히 1번인지 확인한다. 서로 다른 키를 하나의 긴 임계 구역으로 직렬화하지 마라.

[8] `storefront-morning`은 원천 지연 200ms, `storefront-evening`은 1,000ms로 실행한다. 각 실험은 사전 확인 뒤 빈 인기 상품 캐시에서 시작해 500요청/초로 40초 동안 총 20,000개의 도착을 예약한다. 매 5개 요청 중 4개는 상품 1, 나머지는 상품 2~5를 차례로 조회하며 JVM을 번갈아 선택한다. 앞 요청의 완료를 기다리지 않는 개방형 부하다. HTTP 요청 제한 시간은 5초다. JVM 준비 확인은 부하에 포함하지 않는다.

[9] `hot_origin_calls`는 본 부하가 끝난 뒤 상품 1의 원천 조회 수다. `hot_expirations`는 부하 중 25ms 간격으로 Redis의 상품 1 TTL을 읽어 존재 상태에서 부재 상태로 바뀐 횟수다. 최초의 빈 상태는 세지 않는다. 인기 상품의 원천 조회 수는 만료 횟수 + 2 이하여야 한다. 40초 동안 관찰한 만료는 5회 이상이어야 한다. `ttl_violations`는 이 관찰에서 TTL이 없는 상품 키나 5,000ms보다 큰 상품 TTL이 발견되면 1, 아니면 0이며 0이어야 한다. 관찰 간격 사이의 지연은 허용 예산 2회로 흡수한다.

[10] `completed_requests`는 본 부하의 결과 수이며 정확히 20,000이어야 한다. `http_errors`는 본 부하와 사전 확인에서 200이 아니거나 통신 오류가 난 요청 수다. `over_two_seconds`는 같은 요청 중 송신 직전부터 응답 본문을 다 받을 때까지 2,000ms를 초과한 요청 수다. 두 지표 모두 0이어야 한다. HTTP 오류를 줄이려고 503이나 빈 상품을 반환하는 구현은 통과하지 못한다.

[11] `ownership_violations`는 [6]의 두 검사에서 후속 토큰이 사라지거나 달라진 횟수이며 0이어야 한다. 상품 93에서 잠금 GET 없이 원자적으로 해제해 토큰 교체가 발생하지 않은 경우는 위반이 아니다. `recovery_violations`는 [7]의 상품 98 원천 조회 수가 1이 아닌 경우 1이며 0이어야 한다. `body_violations`는 [2]의 상품 본문과 다른 200 응답 수다. `distinct_key_violations`는 [7]의 상품 94~97 중 원천 조회 수가 1이 아닌 키 수다. 두 지표도 0이어야 한다. 만료 횟수 부족은 `hot_expirations`로, TTL 위반은 `ttl_violations`로 구별해라. 모든 불변식은 두 실험에서 각각 만족해야 한다.

[12] 수정 범위는 `src/main/kotlin/ProductCache.kt`다. 이 파일 안에 필요한 함수나 상태를 추가할 수 있다. `Main.kt`, `Origin.kt`, 공통 `RedisClient.kt`, 빌드·실행 스크립트와 외부 환경은 바꾸지 마라. `./build.sh`는 `build/app.jar`를 만들고 `./run.sh`는 서비스를 실행한다. 새 의존성이나 외부 부하 도구는 추가하지 마라. JDK 21과 기존 Kotlin 템플릿만으로 해결해라.

[13] API 근거는 Redis 공식 [SET 문서](https://redis.io/docs/latest/commands/set/)의 NX·PX 옵션과 [분산 잠금 문서](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)의 토큰 비교 후 Lua 삭제다. HTTP 서비스는 JDK의 가상 스레드 실행기를 사용한다([Executors 공식 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Executors.html)). 이 실험은 단일 Redis에서 캐시 재계산을 합치는 문제이며, 네트워크 분할에서 변경 가능한 원천에 대한 쓰기 순서를 보장하는 분산 합의 실험은 아니다.

[14] `SET key token NX PX ttl`은 키가 없을 때만 만료 시간이 있는 잠금을 만든다. 잠금 획득 후 캐시를 다시 확인하면 획득 전에 다른 요청이 채운 값을 활용할 수 있다. 획득 실패 후에는 캐시 확인과 잠금 재시도를 조합해라. 임대가 원천 조회보다 먼저 끝나지 않게 TTL이나 소유권 확인을 포함한 연장을 설계해라.

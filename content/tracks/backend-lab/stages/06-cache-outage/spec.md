# 캐시 장애와 원천 보호

[1] 상품 조회 서비스에서 캐시 장애가 원천 장애로 번지는 경로를 관찰하고 고쳐라. 먼저 시작 코드를 빌드하고 실험해 정상 구간과 장애 구간의 지표를 비교해라. 원천 호출 수, 거절 응답, 지연을 함께 보고 어느 경로가 원천을 보호하지 못하는지 설명해라. 수정 뒤 같은 실험을 세 번 반복해 모든 불변식이 유지되는지 확인해라.

[2] `build.sh`로 빌드하고 `run.sh`로 서비스를 실행해라. 서비스는 `PORT` 환경 변수의 루프백 포트에서 HTTP를 받고 `GET /health`에 200과 `ready`를 반환해야 한다. 실험기는 별도 루프백 HTTP 원천을 띄워 `ORIGIN_URL`을 제공하고 Redis 주소는 `127.0.0.1`과 `REDIS_PORT`로 제공한다. `REDIS_PORT`는 장애와 복구 전후에 유지된다. Redis는 Docker의 고정 이미지로 실행되며 인증과 영속화는 사용하지 않는다. Docker Desktop이 실행 중이어야 한다.

[3] 공개 조회 API는 `GET /products/{id}`다. id는 1부터 41까지이며 모두 존재한다. 성공 응답은 200과 원천에서 받은 JSON 본문 그대로다. 원천은 `{"id":1,"price":1001,"version":1,"loadedAtMillis":1700000000000}`과 같은 본문을 반환한다. price는 1000에 id를 더한 값이고 version은 1이다. loadedAtMillis는 그 조회가 완료될 때 원천이 찍은 시각이므로 예시 숫자를 재사용하지 마라. 잘못된 id는 404, 지원하지 않는 메서드는 405다. 조회를 제공할 수 없으면 503과 양의 정수 초를 담은 `Retry-After` 헤더를 반환해라. 모든 부하 요청은 유효한 GET이며 클라이언트는 자동 재시도하지 않는다.

[4] 원천 조회는 `ORIGIN_URL/products/{id}`로 보내며 정상 조회에는 200ms가 걸린다. 원천은 직전 1초의 호출이 100회를 넘으면 503을 반환한다. 거절된 호출도 원천 호출 수에 포함한다. 원천 본문을 직접 만들거나 시각을 바꾸지 마라. Redis의 키는 `product:{id}`이며 값은 같은 원천 본문, 물리 TTL은 5초 이하다. 로컬에 보관한 값은 원천에서 받은 시각부터 6초까지만 제공해라. 실험기는 원천이 발급한 본문인지 대조하고 전송·스케줄링 여유 500ms를 더해 6.5초를 넘긴 본문을 거부한다. 소프트 TTL은 재조회할 시점이고 이 보관 상한과 다르다. Redis가 복구되면 Redis를 다시 사용해야 하며 실험 종료 시 `product:1`에 원천이 발급한 값이 있어야 한다.

[5] `catalog-traffic`은 개방형 일정으로 초당 500건을 40초간 보내 총 20,000건을 만든다. 매 다섯 요청 중 네 건은 id 1, 한 건은 id 2부터 41까지 순환한다. 앞선 응답이 늦어져도 다음 요청의 예정 시각을 늦추지 않는다. 처음 5초는 예열이며 지연과 구간별 오류율에서만 제외한다. 원천 호출 수와 응답 계약은 예열을 포함해 검사한다. 프로세스와 Redis의 준비 확인은 부하 시작 전에 끝낸다.

[6] 부하 시작 8초에 Redis를 일시 정지해 응답 없는 연결을 만들고 10초에 종료한다. 25초에 같은 Redis 컨테이너를 다시 시작하며 캐시는 비어 있다. 실험기가 PING 응답으로 복구 준비를 확인한 시각을 R이라 한다. 장애 구간은 예정 도착 시각이 10초 이상 R 미만인 요청이며, 복구 판정 구간은 R+5초 이상 40초 미만인 요청이다. 실제 재시작 준비 시간은 `redis_recovery_ms`로 공개한다. 준비 실패나 복구 판정 구간을 최소 2초, 예정 요청 1,000건 이상 확보하지 못한 실행은 실험 오류로 처리한다.

[7] 모든 이동 1초 구간의 원천 호출 수는 120회 이하여야 한다. `origin_peak_1s`는 예열을 포함한 전체 실행에서 원천이 실제로 받은 호출 시작 시각을 정렬해 구한 최댓값이다. 고정된 정각 초 버킷으로 계산하지 않는다. 원천의 정상 처리 한도 100회와 검사 상한 120회는 다르므로 원천 거절을 상한 안에서 반복하는 것만으로 충분하지 않다. `origin_rejections`는 원천이 거절한 총 호출 수이며 진단용이다.

[8] 장애 구간 오류율은 30% 이하여야 한다. `outage_error_pct`는 해당 구간의 200이 아닌 응답 수를 전체 예정 요청 수로 나눈 백분율이다. 복구 판정 구간의 200이 아닌 응답 수인 `recovery_errors`는 0이어야 한다. 예열 후 실제 전송 시작부터 본문 수신까지 3초를 넘긴 요청 수인 `responses_over_3s`도 0이어야 한다. 클라이언트 타임아웃은 5초이며 연결 오류와 타임아웃을 성공으로 세지 않는다. 일부 요청을 버리거나 부하 전체를 늦추는 방식으로 오류율을 낮추지 마라.

[9] `contract_violations`는 잘못된 성공 본문, 잘못된 id의 본문, 보관 상한 초과, 503의 Retry-After 누락·잘못된 값, 200·503 이외 응답, 전송 실패, Redis TTL 위반, 종료 시 Redis 인기 키 누락을 합한 수이며 0이어야 한다. 전송 실패도 예열을 포함해 센다. Redis가 정상인 구간에는 200ms 간격으로 상품 키의 남은 TTL을 조회하며 만료가 없거나 5초를 초과하는 키를 발견할 때마다 TTL 위반으로 센다. `completed_requests`는 성공·실패를 포함한 전체 요청 결과 수이며 20,000이어야 한다. `response_p99_ms`는 예열 후 응답 시간의 최근접 순위 99백분위이며 진단용이다. 통과에는 [7]부터 [9]까지의 불변식을 모두 만족해야 한다. 시간 초과, 빌드 실패, 지표 누락은 의도한 불변식 실패로 인정하지 않는다.

[9.1] `first_contract_violation`은 실험기가 처음 기록한 계약 위반의 종류이며 진단용이다. 코드는 0=위반 없음, 1=원천이 발급하지 않은 성공 본문, 2=요청 id와 다른 본문, 3=6.5초를 넘긴 본문, 4=503의 Retry-After 누락·잘못된 값, 5=200·503 이외 응답, 6=전송 실패, 7=Redis TTL 위반, 8=종료 시 Redis 인기 키 누락이다. 한 응답에 여러 위반이 있으면 1, 2, 3 순서로 처음 해당하는 종류 하나만 센다. 동시 위반은 실험기가 먼저 기록한 종류를 표시한다. TTL 위반은 해당 조회가 끝났을 때 기록한다.

[10] `src/main/kotlin/ProductCache.kt`만 수정해라. 같은 파일에 보조 타입을 추가해도 된다. Main.kt의 HTTP 계약, OriginClient.kt의 원천 요청, RedisClient.kt, 실행 스크립트와 빌드 설정은 바꾸지 마라. 실패한 불변식과 관찰 지표를 근거로 보호 전략을 정하고 선택 이유를 설명해라. RedisClient 생성자의 timeoutMillis는 풀 대기·연결·소켓 읽기에 각각 적용되므로 전체 요청의 단일 마감 시각으로 생각하지 마라. 종료할 때 직접 만든 실행기와 클라이언트를 닫아라. 새 의존성은 추가하지 마라.

[11] 공식 API 근거로 JDK 21 [Socket.connect와 setSoTimeout](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/net/Socket.html)을 읽어 연결 제한 시간과 읽기 제한 시간이 별개임을 확인해라. Redis [SET](https://redis.io/docs/latest/commands/set/)의 PX는 밀리초 만료다. HTTP 503과 Retry-After의 의미는 [RFC 9110의 15.6.4절과 10.2.3절](https://www.rfc-editor.org/rfc/rfc9110.html)을 따른다. 이 단계의 100회·120회·30%·3초는 외부 제품의 성능 보장이 아니라 이 실험의 계약이다.

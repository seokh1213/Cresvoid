# 외부 결제 호출 재시도 정책

읽을 파일과 순서는 `code/src/main/kotlin/RetryPolicy.kt` → `Backoff.kt` → `PaymentGateway.kt` → `Main.kt`다.

[1] 쇼핑 카탈로그에서 주문으로 넘어온 결제 요청을 외부 결제 대행사로 보내는 모듈이다. 대행사는 결제 ID를 멱등 키로 취급한다고 가정한다. 이 프로그램은 실제 결제를 보내거나 시간을 기다리지 않는다. 입력으로 호출 결과를 주고 다음 시도의 대기 시간을 예약한다. 목표 풀이 시간은 25분이다.

[2] 표준 입력을 EOF까지 한 줄씩 읽는다. 명령의 각 항목은 공백으로 구분하며 ID와 정책 이름에는 공백을 쓰지 않는다. 빈 줄은 무시한다. 문항마다 새 프로세스에서 시작하며 문항에 적힌 입력 외의 명령은 없다.

[3] `POLICY 이름 기본대기ms 상한ms 최대시도수 지터`로 정책을 등록한다. 기본 대기는 유한한 Double 값으로 1 이상이며 `1e30` 같은 표기도 받는다. 상한은 양수 Long 값이고 최대 시도 수는 1~100이다. 지터는 `NONE`, `FULL`, `EQUAL` 중 하나다. 같은 이름을 다시 등록하면 이후 OPEN에 쓸 정책을 교체한다. 명령은 출력하지 않는다.

[4] `OPEN 결제ID 정책이름 시드 완료시도수 남은예산ms`로 진행 중인 결제 요청을 연다. 완료 시도 수는 이미 끝난 호출 횟수이며 0 이상, 정책의 최대 시도 수 미만이다. 남은 예산은 앞으로 예약할 대기 시간의 총합에 쓸 수 있는 0 이상의 Long 값이다. 각 OPEN은 전달한 시드로 난수 생성기를 새로 만들며 이전에 뽑은 난수는 복원하지 않는다. 같은 결제 ID로 다시 열면 기존 세션을 교체한다. 명령은 출력하지 않는다.

[5] `CALL 결제ID 결과`로 한 번의 호출 결과를 전달한다. 결과는 `OK`, `TIMEOUT`, `CONNECT`, `HTTP400`~`HTTP599` 중 하나다. 각각 성공, 응답 시간 초과, 연결 실패, HTTP 오류를 나타낸다. 오류 분류와 재시도 여부는 코드를 읽고 판단한다. 종료된 요청에 CALL이 더 들어오는 경우도 문항에 포함한다.

[6] CALL은 `결제ID attempt=횟수 result=판정 reason=이유 wait=대기ms remaining=남은예산ms` 형식으로 한 줄을 출력한다. 판정은 `SUCCESS`, `RETRY`, `STOP`, `IGNORED` 중 하나다. `LIMIT:`과 `BUDGET:`은 이유 앞에 붙을 수 있는 접두사다. 모든 시간의 단위는 밀리초다. 잘못된 명령은 `ERROR 이유` 한 줄을 출력하지만 문항에서는 올바른 명령만 사용한다.

[7] 산술 계산에 사용할 값은 `2^30 = 1073741824`, `Int.MAX_VALUE = 2147483647`, `Long.MAX_VALUE = 9223372036854775807`이다. `1e30`은 10의 30제곱이다. 큰 기본 대기와 복구된 시도 횟수는 경계 동작을 관찰하기 위한 입력이다. 실제 서비스의 권장 정책값은 아니다.

[8] 문항은 Kotlin 2.4.21의 난수 수열을 가정한다. 시드 7로 만든 새 Random에서 `nextLong(51)`만 연속 호출하면 첫 네 값은 차례로 `49, 32, 27, 38`이다. 시드 17로 만든 새 Random에서 `nextLong(10)`만 연속 호출하면 첫 다섯 값은 `7, 2, 1, 7, 4`다. 이 값들은 계산에 필요한 난수 원자료이며 대기 시간 자체를 뜻하지 않는다.

[9] 재시도 부하와 멱등성에 관한 배경 자료는 Amazon Builders' Library의 [Timeouts, retries, and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)다. 이 단계의 판정 근거는 제공한 코드다.

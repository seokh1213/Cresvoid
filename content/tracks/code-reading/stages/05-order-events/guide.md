# 주문 이벤트 처리

[1] 읽을 파일과 순서는 `OrderEvent.kt` → `OrderTransitions.kt` → `EventInbox.kt` → `OrderReport.kt` → `Main.kt`다. 모두 `code/src/main/kotlin/`에 있다. 목표 풀이 시간은 30분이다.

[2] 쇼핑 카탈로그 서비스의 주문 조회 화면과 배송 운영 도구가 같은 주문 이벤트를 사용한다. 결제·배송 시스템에서 이벤트가 순서 없이 들어오며, 재전송 과정에서 같은 식별자의 내용이 달라질 수도 있다. 이 프로그램은 수신 기록을 보관하고 지정한 관찰 시각의 주문 상태를 재계산하는 학습용 모델이다.

[3] 표준 입력에서 명령을 한 줄씩 EOF까지 읽는다. 명령의 필드는 공백으로 구분한다. 주문 ID는 영문자로 시작하고 영문자·숫자·밑줄·하이픈을 쓴다. 순번과 묶음 크기는 양의 Int이며, 이벤트 시각과 관찰 시각은 0 이상의 Long이다. 시각은 외부 시스템이 붙인 논리 시각이고 실제 시계는 사용하지 않는다.

[4] `EVENT <주문 ID> <순번> <종류> <이벤트 시각>`은 수신 기록을 추가하며 출력하지 않는다. 종류는 `PAY`, `SHIP`, `CANCEL`, `REFUND`다. 이벤트 식별자는 주문 ID와 순번의 조합이다. 수신 순서, 순번, 이벤트 시각은 서로 다른 정보다. 상태 전이와 수신 기록의 선택 기준은 코드에서 확인한다.

[5] `REPORT <관찰 시각> <주문 ID>`는 해당 주문의 재계산 결과를 한 줄로 출력한다. 필드 순서는 `주문 ID|상태|applied=…|rejected=…|next=…|pending=…|first=…|reads=…|builds=…`다. `applied`는 반영한 순번, `rejected`는 거부한 순번과 사유, `next`는 다음에 검사할 순번, `pending`은 아직 검사하지 않은 이벤트 수다. 순번 목록은 쉼표로, 거부 항목은 `순번:사유`로 표시한다.

[6] 상태 표시는 `WAITING`, `PAID@시각`, `SHIPPED@시각`, `CANCELLED@시각`, `REFUNDED@시각` 중 하나다. `first`는 선택 과정이 보고한 첫 이벤트의 `주문 ID#순번`이다. `reads`는 후보 조회가 기록한 원시 이벤트 접근 횟수이고, `builds`는 보고 객체의 상태 재계산 횟수다. 목록이나 식별자가 없으면 `-`를 쓴다.

[7] `RECEIPTS <주문 ID>`는 관찰 시각을 지정하지 않고 수신 기록을 점검한다. 출력은 `주문 ID|canonical=…|latest=…|deliveries=…`다. 두 목록은 관찰 시각을 적용하지 않은 수신 기록의 비교용 목록이다. 항목은 `순번:종류@시각`으로 표시한다. `deliveries`는 해당 주문의 전체 수신 건수다.

[8] `PLAN <관찰 시각> <묶음 크기>`는 배송 완료 주문의 연속 감사 묶음과 배송 명세서 묶음을 만든다. 출력은 `checks=…|batches=…|reads=…|builds=…`다. 묶음 안의 주문 ID는 `+`로, 묶음 사이는 `/`로 구분한다. 배송 완료 여부와 두 묶음의 구성은 코드에서 추적한다.

[9] `EXPORT <관찰 시각>`는 재계산 결과를 검사하고 내보낼 문자열을 만든다. 성공하면 `OK|orders=…,applied=…,rejected=…,pending=…|records=…|audit=…|reads=…|builds=…`를 출력한다. 각 레코드는 `주문 ID:상태:소비한 마지막 순번`이며 레코드 사이는 `;`로 구분한다. 검사가 실패하면 `ERROR|실패 사유|audit=…|reads=…|builds=…`를 출력한다. `audit`는 이 요청의 처리 기록이며 쉼표로 구분한다.

[10] `TRACE <관찰 시각>`는 후보 조회의 접근 기록과 전체 집계를 점검한다. 출력은 `trace=…|orders=…,applied=…,rejected=…,pending=…|reads=…|builds=…`다. `trace`의 항목은 `주문 ID#순번`이며 쉼표로 구분한다. 명령 형식이 잘못되면 `ERROR input`을 출력하고 다음 줄을 처리한다. 빈 줄은 무시한다.

[11] 문항마다 새 프로세스를 시작하며 입력은 모두 유효하다. 각 조회 명령은 그때까지의 수신 기록으로 새 보고 객체를 만든다. 앞 문항의 기록은 다음 문항으로 이어지지 않는다. 변경을 명시한 문항에서만 지정한 코드 한 곳을 바꾼 것으로 가정한다.

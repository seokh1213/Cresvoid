# 알림 발송 작업 큐

[1] 읽을 파일은 `NotificationQueue.kt`, `DispatchWorker.kt`, `DispatchShutdown.kt`, `Main.kt`이며 이 순서로 읽는다. 파일은 모두 `code/src/main/kotlin/`에 있다. 목표 풀이 시간은 25분이다.

[2] 쇼핑 카탈로그 서비스가 재입고 알림을 발송한다. 요청 ID를 큐에 넣고 작업자가 꺼내 발송한다. `DispatchEntry.Stop`은 작업자 종료에 쓰는 독약 객체다. `ReceiptExport`는 발송 작업자와 같은 실행기에 제출하는 발송 내역 내보내기 작업이다.

[3] 외부 발송 API는 `DeliveryGate` 대역으로 바꿨다. `entered`와 `open()`은 시나리오가 발송 진행을 통제하는 지점이다. 실제 네트워크와 시계는 쓰지 않는다. `awaitSignal()`과 `finish()`의 5초 제한에 걸리지 않는 정상 실행을 가정한다.

[4] 표준 입력에서 한 줄에 명령 하나를 받아 EOF까지 처리한다. 명령은 인자 없는 `BURST`, `ABORT`, `SHORTAGE`, `TAIL`, `GRACEFUL`이다. 빈 줄은 건너뛴다. 각 명령은 새 큐와 실행기를 만들어 독립된 시나리오를 실행하고 보고 한 줄을 출력한다. 요청 ID는 알림 종류를 구분하기 위한 시험용 값이다.

[5] `BURST`는 요청이 몰리는 상황, `ABORT`는 강제 종료, `SHORTAGE`는 작업자 수와 종료 객체 수가 다른 상황, `TAIL`은 종료 객체 전후의 요청 배치, `GRACEFUL`은 발송 중 종료 요청을 다룬다. 스레드의 진행 순서는 각 함수에 있는 큐 연산과 래치를 따라 판단한다.

[6] 보고의 `sent`는 발송 완료 ID, `interrupted`는 인터럽트 당시 발송 중이던 ID이며 발송 중인 요청이 없으면 `idle`이다. `pending`은 알림 큐에 남은 요청 ID로, 종료 객체는 제외한다. 목록은 쉼표로 잇고 빈 목록은 `-`로 쓴다. `dropped`는 접수 거절 수, `waiting`은 관찰 시점의 생산자 완료 래치 상태, `returned`는 강제 종료에서 반환받은 내보내기 작업의 배치 ID다.

[7] `stopped`는 종료 객체를 받아 끝낸 작업자 수다. `terminated`는 종료 대기 호출의 반환값이며, `before`와 `after`도 해당 위치에서 호출한 종료 대기의 반환값이다. 문항은 원본 코드를 가정하며 별도 변경 조건이 있으면 발문에 제시한다.

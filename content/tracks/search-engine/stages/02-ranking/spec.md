# 2단계: BM25 랭킹

## 1. 개요

[1.1] 2단계는 BM25 점수가 높은 순으로 문서를 보여 주는 SEARCH 명령을 더한다.

[1.2] 1단계의 입출력 규칙, 토큰화 규칙, ADD·DEL·STATS·QUERY 는 그대로다. 1단계 4.33 이 출력을 정하지 않은 QUERY 는 이 문서도 출력을 정하지 않는다. 이 문서는 새로 생기는 규칙만 설명한다.

| 명령 | 하는 일 | 정상 출력 |
|---|---|---|
| `SEARCH <k> <낱말> …` | 후보 문서를 BM25 점수 순으로 k 개까지 출력한다 | 1줄 이상 k줄 이하 |

## 2. 배경 개념

[2.1] 불리언 검색은 맞는 문서의 집합만 돌려주고 문서 사이의 순서를 매기지 않는다. 결과가 수천 건이면 사람이 다 읽을 수 없다. 랭킹은 문서마다 질의와의 관련도 점수를 매기고 높은 순으로 보여 준다.

[2.2] BM25 는 1990년대 Okapi 검색 시스템에서 나온 랭킹 함수이고 지금도 Lucene 과 Elasticsearch 의 기본 점수 함수다. BM25 는 세 가지 직관을 한 식에 담는다. 질의 토큰이 문서에 많이 나올수록, 그 토큰이 드물수록, 문서가 짧을수록 점수가 높다.

[2.3] 첫째 직관은 출현 횟수 tf 에 관한 것이다. 횟수가 늘면 점수가 오르지만 오르는 폭은 줄어든다. 한 번과 두 번의 차이는 크지만 스무 번과 스물한 번의 차이는 작다. BM25 의 TF 부분 `tf × (k1 + 1) / (tf + k1 × L)` 은 tf 가 아무리 커도 k1 + 1 을 넘지 않는다. L 은 2.4 의 길이 보정 값이다. L 이 1 이고 k1 이 1.2 일 때 tf 가 1, 2, 10, 100 이면 TF 부분은 1, 1.375, 약 1.964, 약 2.174 다. k1 이 클수록 포화가 늦게 온다.

[2.4] 둘째 직관은 문서 길이 보정에 관한 것이다. 긴 문서는 주제와 상관없이 어떤 토큰이든 많이 담는다. 길이 보정 값은 `L = 1 − b + b × dl / avgdl` 이다. avgdl 은 문서 길이의 평균이다. 평균 길이의 문서는 L 이 1 이다. 문서가 길수록 L 이 커져 TF 부분이 작아진다. b 는 보정의 세기다. b 가 0 이면 길이를 무시하고 b 가 1 이면 길이 비율을 그대로 반영한다.

[2.5] 셋째 직관은 드문 토큰에 무게를 주는 idf 에 관한 것이다. 모든 문서에 나오는 토큰은 문서를 가려내지 못한다. `idf(t) = ln(1 + (N − df + 0.5) / (df + 0.5))` 는 df 가 작을수록 크다. N 은 문서 수, df 는 토큰 t 를 포함한 문서 수다. 고전적인 식 `ln((N − df + 0.5) / (df + 0.5))` 는 df 가 N 의 절반을 넘으면 음수가 되지만 로그 안에 1 을 더한 이 변형은 언제나 양수다. Lucene 의 BM25 도 이 변형을 쓴다.

[2.6] 문서의 점수는 질의 토큰마다 idf 와 TF 부분을 곱해 더한 값이다. 이 트랙은 토큰 하나가 점수에 더하는 값을 그 토큰의 몫이라 부른다. 문서에 없는 토큰은 tf 가 0 이라 0 을 더한다. 평균 길이의 문서에 토큰이 한 번 나오면 TF 부분이 1 이므로 그 토큰의 몫은 idf 와 같다.

[2.7] 아래는 문서 네 개에서 kotlin 의 점수를 구한 예다. N 은 4, 문서 길이의 합은 9 라 avgdl 은 2.25 다. kotlin 은 문서 1, 2, 4 에 있으므로 df 는 3 이다.

```
문서 1: kotlin coroutine kotlin   dl 3
문서 2: kotlin flow               dl 2
문서 3: java stream flow          dl 3
문서 4: kotlin                    dl 1

idf(kotlin) = ln(1 + (4 − 3 + 0.5) / (3 + 0.5)) = ln(1.428571…) ≈ 0.356675

문서 1  tf 2  L = 0.25 + 0.75 × 3 / 2.25 = 1.25
        TF 부분 = 2 × 2.2 / (2 + 1.2 × 1.25) = 4.4 / 3.5 ≈ 1.257143
        점수 ≈ 0.356675 × 1.257143 ≈ 0.448391 → 0.4484

문서 4  tf 1  L = 0.25 + 0.75 × 1 / 2.25 ≈ 0.583333
        TF 부분 = 2.2 / (1 + 1.2 × 0.583333) = 2.2 / 1.7 ≈ 1.294118
        점수 ≈ 0.356675 × 1.294118 ≈ 0.461579 → 0.4616
```

[2.8] 문서 1 은 kotlin 이 두 번 나오는데도 문서 4 보다 점수가 낮다. 문서 1 은 평균보다 길고 문서 4 는 짧기 때문이다. tf 와 길이 보정이 함께 순위를 정한다.

[2.9] 접두 + 와 - 는 Lucene 의 질의 문법에도 있는 표기다. + 는 반드시 포함해야 하는 토큰, - 는 포함하면 안 되는 토큰을 뜻하며 접두가 없으면 선택 토큰이다. 필수 토큰이 있으면 선택 토큰은 후보를 넓히지 않고 점수만 더한다. 필수 토큰이 없으면 선택 토큰을 하나 이상 포함해야 후보가 된다. 제외 토큰만 있는 질의는 아무 문서도 찾지 않는다. Lucene 의 불리언 질의도 MUST, SHOULD, MUST_NOT 절을 같은 방식으로 다룬다.

[2.10] df, N, avgdl 은 후보가 아니라 현재 문서 전체에서 구한다. 그래서 문서 하나를 지우거나 대체하면 남은 문서의 점수도 바뀐다. Lucene 은 지운 문서가 정리될 때까지 통계에 남겨 두지만 이 트랙은 다음 명령부터 바로 반영한다.

## 3. 입출력 규칙

[3.1] 1단계의 입출력 규칙을 그대로 따른다.

[3.2] 점수는 소수점 아래 다섯째 자리에서 반올림해 넷째 자리까지 쓴다. 점수는 double 로 계산하고 그 값을 반올림한다. 소수점 아래 넷째 자리까지로 나타낼 수 있는 수 가운데 그 점수에 가장 가까운 수를 쓴다. 가장 가까운 수가 둘이면 큰 쪽을 쓴다. 소수 부분은 언제나 네 자리이고 소수점은 마침표(.)다. 1 보다 작은 점수는 정수 부분에 0 을 쓴다. 지수 표기는 쓰지 않는다. `0.4616`, `1.0998`, `2.0000` 처럼 쓴다.

## 4. 명령 규칙

### 형식

[4.1] `SEARCH <k> <낱말> …` 은 후보 문서를 BM25 점수 순으로 정렬해 앞에서부터 k 개까지 출력한다.

[4.2] k 는 `^[1-9][0-9]{0,3}$` 에 맞고 1000 이하인 10진 정수다.

[4.3] k 뒤의 인자 하나하나가 낱말이다. 낱말은 공백으로만 나뉜다.

[4.4] SEARCH 에서는 괄호와 AND, OR, NOT 에 특별한 뜻이 없다. 이들도 다른 문자와 똑같이 토큰화 규칙을 따른다. `AND` 는 토큰 `and` 가 되고 괄호는 구분자다.

### 접두

[4.5] 낱말의 첫 글자가 `+` 이면 필수 낱말, `-` 이면 제외 낱말, 그 밖이면 선택 낱말이다. 접두는 첫 글자 하나뿐이다. `++a` 는 필수 낱말이고 접두를 뗀 나머지는 `+a` 다.

[4.6] 필수 낱말과 제외 낱말은 접두를 뗀 나머지를 토큰화하고 선택 낱말은 낱말 전체를 토큰화한다. `+` 와 `-` 는 1단계 4.3 의 구분자이므로 어느 쪽으로 토큰화해도 나오는 토큰은 같다. `(+pie)` 는 첫 글자가 `(` 이므로 선택 낱말이다.

[4.7] 접두는 그 낱말에서 나온 모든 토큰에 적용된다. `+foo-bar` 는 foo 와 bar 를 모두 필수 토큰으로 만들고 `-foo-bar` 는 둘을 모두 제외 토큰으로 만든다.

[4.8] 토큰이 0개인 낱말은 무시한다. `+` 나 `-` 한 글자로 된 낱말도 여기에 해당한다.

### 토큰 집합

[4.9] 필수 토큰의 집합을 R, 제외 토큰의 집합을 E, 선택 토큰의 집합을 O 라 한다. 같은 토큰이 여러 번 나와도 집합에는 한 번만 들어간다.

[4.10] 같은 토큰이 R 과 O 에 모두 있으면 그 토큰은 R 에만 속한다. 이 규칙은 결과를 바꾸지 않는다. 4.11 의 S 와 4.13·4.14 의 후보 조건은 토큰이 O 에도 속하는지에 기대지 않기 때문이다.

[4.11] 점수를 매길 토큰의 집합 S 는 (R ∪ O) − E 다. O 와 E 에 모두 있는 토큰은 S 에 들어가지 않는다.

### 후보

[4.12] R 과 E 가 겹치면 후보가 없다.

[4.13] R 이 비어 있지 않으면 R 의 토큰을 모두 포함하고 E 의 토큰을 하나도 포함하지 않는 문서가 후보다. O 의 토큰은 후보를 정하는 데 쓰지 않는다.

[4.14] R 이 비어 있으면 S 의 토큰을 하나 이상 포함하고 E 의 토큰을 하나도 포함하지 않는 문서가 후보다.

[4.15] S 가 비어 있으면 후보가 없다. 제외 낱말만 있는 SEARCH 와 낱말이 하나도 없는 SEARCH 가 여기에 해당한다.

### 점수

[4.16] 후보 d 의 점수는 S 의 토큰 t 마다 `idf(t) × tf × (k1 + 1) / (tf + k1 × (1 − b + b × dl / avgdl))` 를 구해 모두 더한 값이다. k1 은 1.2, b 는 0.75 다.

[4.17] `idf(t) = ln(1 + (N − df + 0.5) / (df + 0.5))` 이다. ln 은 자연로그다.

[4.18] N 은 현재 문서의 수다. 토큰이 0개인 문서도 센다.

[4.19] df 는 t 를 포함한 현재 문서의 수다. 후보만이 아니라 현재 문서 전체에서 센다.

[4.20] tf 는 d 안에서 t 가 나온 횟수다. d 에 t 가 없으면 tf 는 0 이고 그 토큰의 몫도 0 이다.

[4.21] dl 은 d 의 문서 길이다. avgdl 은 현재 모든 문서의 길이를 더해 N 으로 나눈 값이다. 토큰이 0개인 문서도 N 에 들어간다. 후보가 하나라도 있으면 avgdl 은 0 보다 크다.

[4.22] ADD 나 DEL 로 문서가 추가·대체·삭제되면 N, df, avgdl 이 바로 바뀐다. 다음 SEARCH 부터 바뀐 값으로 계산한다.

### 출력

[4.23] 후보는 반올림한 점수의 내림차순으로 정렬하고 반올림한 점수가 같으면 id 의 수 크기 오름차순으로 정렬한다. 9 는 10 보다 앞에 온다. 반올림 전 점수가 달라도 반올림한 점수가 같으면 id 로 순서를 정한다.

[4.24] 정렬한 후보를 앞에서부터 k 개까지 한 줄에 하나씩 `<id> <점수>` 형식으로 출력한다. id 와 점수는 공백 하나로 나눈다. 후보가 k 개보다 적으면 후보를 모두 출력한다.

[4.25] 후보가 없으면 `(none)` 한 줄을 출력한다. k 만 있고 낱말이 없을 때도 `(none)` 이다.

## 5. 오류 규칙

[5.1] 1단계의 명령어 목록에 SEARCH 가 더해진다. 명령어가 SEARCH 인 줄은 1단계 5.2 가 출력을 정하지 않은 입력이고 그 출력은 이 문서가 정한다. SEARCH 는 `ERR UNKNOWN_COMMAND` 를 내지 않는다.

[5.2] SEARCH 에 인자가 없거나 k 가 4.2 의 형식에 맞지 않거나 k 가 1000 보다 크면 `ERR BAD_ARGUMENT` 를 출력한다. `SEARCH 0 a`, `SEARCH 01 a`, `SEARCH 1001 a`, `SEARCH -1 a` 가 여기에 해당한다.

[5.3] k 가 올바르면 SEARCH 는 오류를 내지 않는다. 토큰이 없는 낱말은 무시한다. 후보가 없으면 `(none)` 을 출력한다.

## 6. 예시

[6.1] 예시의 표기는 1단계와 같다. 예시 블록 하나는 프로그램을 한 번 실행한 기록이다.

[6.2] 2.7 의 문서 네 개로 검색한다. `SEARCH 2` 는 앞의 두 줄만 출력한다. 같은 토큰을 여러 번 써도 한 번 쓴 것과 같다.

```
> ADD 1 kotlin coroutine kotlin
> ADD 2 kotlin flow
> ADD 3 java stream flow
> ADD 4 kotlin
> SEARCH 10 kotlin
4 0.4616
1 0.4484
2 0.3737
> SEARCH 10 kotlin flow
2 1.0998
3 0.6100
4 0.4616
1 0.4484
> SEARCH 2 kotlin flow
2 1.0998
3 0.6100
> SEARCH 10 kotlin kotlin KOTLIN
4 0.4616
1 0.4484
2 0.3737
```

[6.3] 필수 토큰과 제외 토큰이다. `+kotlin flow` 에서 문서 1 과 4 는 flow 가 없지만 kotlin 이 있으므로 후보다. 문서 3 은 flow 가 있지만 kotlin 이 없으므로 후보가 아니다.

```
> ADD 1 kotlin coroutine kotlin

> ADD 3 java stream flow
> ADD 4 kotlin

1 0.4484
> SEARCH 10 kotlin -flow
4 0.4616
1 0.4484
> SEARCH 10 +flow -java kotlin
2 1.0998
> SEARCH 10 +kotlin -kotlin
(none)
> SEARCH 10 -kotlin
(none)
```

[6.4] 통계가 바뀌면 점수가 바뀐다. 문서 3 을 지우면 N, df, avgdl 이 바뀌어 문서 2 의 점수가 오른다. 토큰이 없는 문서 9 를 추가해도 N 이 늘고 avgdl 이 줄어 점수가 바뀐다.

> ADD 4 kotlin

[6.5] 접두의 세부, 동점, k 다. `-red-green` 은 red 와 green 가운데 하나라도 있는 문서를 후보에서 제외한다. 문서 4 와 5 는 점수가 같아 id 순으로 나온다. `(+pie)` 는 선택 낱말이고 `+-pie` 는 필수 낱말이다.

## 7. 검사 방식

[7.1] 입력 방식, 종료 코드 검사, 표준 출력 비교, 일반 테스트 제한 시간 10초, 입력 한계는 1단계와 같다.

[7.2] 2단계 테스트는 점수도 글자 그대로 비교한다. 3.2 의 형식을 하나라도 어기면 실패다. 소수 부분이 네 자리가 아니거나, 1 보다 작은 점수에 정수 부분 0 이 없거나, 지수 표기를 쓰면 실패다.

[7.3] 줄 수와 id 의 순서도 정확히 같아야 한다.

[7.4] 기대 출력의 점수는 64비트 부동소수점(IEEE 754 double)으로 계산한다.

[7.5] 대규모 테스트는 문서 30,000개와 SEARCH 3,000개로 이뤄진다. 제한 시간은 15초다.

[7.6] 2단계 검사 입력의 QUERY 에도 큰따옴표가 하나도 나오지 않고 `NEAR/` 로 시작하는 낱말도 나오지 않는다.

[7.7] 3~6단계를 검사할 때도 2단계 테스트를 다시 실행한다.

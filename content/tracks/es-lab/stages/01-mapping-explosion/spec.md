# 동적 매핑과 필드 폭증

[1] 판매자가 올린 상품 속성의 키는 계속 달라진다. 시작 코드는 속성을 JSON 객체로 Elasticsearch에 보내며 새 키를 동적 매핑에 추가한다. 먼저 필드 한도에 도달하는 과정을 예측하고 관찰한 뒤, 키가 늘어도 매핑 필드 수가 일정하고 같은 검색을 지원하도록 고쳐라. Elasticsearch 동적 매핑 입문 실습이며 HTTP 처리·저장·교체·재시작 코드는 제공한다. 매핑과 검색 경로를 바꾸는 작은 수정도 계약을 만족하면 충분하다. 실습 모드는 observe 뒤 implement다. JDK 21, Kotlin과 Docker Desktop을 사용한다.

[2] Elasticsearch의 `index.mapping.total_fields.limit`는 leaf 필드뿐 아니라 object, nested, multi-field와 runtime 필드도 센다. 메타데이터 `_id`, `_source`는 세지 않는다. 날짜·숫자 감지를 끈 동적 매핑에서 일반 문자열은 `text`와 `.keyword` 두 매퍼가 된다. 한도가 초과되면 기본 설정에서는 해당 문서의 색인을 거절한다. 이 실험은 `ignore_dynamic_beyond_limit=false`를 사용한다. [Mapping limit settings](https://www.elastic.co/docs/reference/elasticsearch/index-settings/mapping-limit)와 [Dynamic field mapping](https://www.elastic.co/docs/manage-data/data-store/mapping/dynamic-field-mapping)을 근거로 삼는다.

[3] 관찰용 색인은 주 샤드 1개, 복제본 0개, 필드 한도 12다. `id`, `seller`를 각각 `keyword`, `attributes`를 동적 `object`로 미리 선언하고 날짜·숫자 감지를 끈다. `o1`부터 `o5`까지 순서대로 `{"id":"oN","seller":"s1","attributes":{"kN":"plain-value"}}`를 넣는다. N은 문서 번호로 치환한다. `o6`은 새 키 대신 `k1`을 사용한다. 각 요청이 끝난 뒤 다음 요청을 보내라. 실행 전에 처음 거절될 문서, 성공한 문서 집합, 마지막 매퍼 수를 예측하라. 실패가 앞선 문서를 지우는지, 새 키 없는 쓰기도 막는지 구별하라. 실험기는 별도 관찰용 색인으로 이 순서를 재현하고 문서 존재와 원본을 확인한다. 관찰용 색인은 수정 대상이 아니다.

[4] 구현용 서비스는 `run.sh`로 실행한다. `PORT` 환경 변수의 포트에서 `127.0.0.1`에 HTTP 서버를 열어라. `ES_URL`은 Elasticsearch의 HTTP 주소이고 `ES_INDEX`는 서비스가 사용할 독립 색인 이름이다. 처음 시작할 때 색인을 만들고, 같은 환경으로 재시작하면 기존 색인을 보존하라. `GET /health`는 준비가 끝나면 200을 반환한다. `POST /refresh`는 Elasticsearch refresh가 완료되면 200을 반환한다. 색인 직후 검색 가시성을 검사하지 않으며 refresh 뒤 검사한다.

[5] `PUT /products/<id>`는 `{"seller":"s0","attributes":{"color":"red","size":"blue"}}`를 받아 저장 성공 뒤 HTTP 201과 `{}`를 반환한다. id와 seller는 `[a-z0-9-]{1,40}`, 속성 키는 `[a-z][a-z0-9_]{0,39}`, 값은 길이 1~1024인 문자열이다. 속성은 0~8개이고 키는 겹치지 않는다. JSON의 따옴표·역슬래시와 한글을 그대로 보존하라. 같은 id를 다시 쓰면 원본 전체를 교체한다. 올바른 요청의 Elasticsearch 실패는 502로 반환하라. 제공한 HTTP 클라이언트와 서버는 Elasticsearch의 오류 응답 본문을 그대로 반환하므로 `error.type`, `error.reason`, `error.root_cause`와 본문의 `status`를 확인할 수 있다. 연결 실패처럼 Elasticsearch 응답 자체가 없으면 502와 `{}`를 반환한다. 유효성 검증은 제공한 코드를 사용하며 잘못된 본문은 400, 없는 경로는 404다. 본문의 상품에는 seller와 attributes 외의 필드가 없다.

[6] `POST /search`는 `{"seller":"s0","filters":[{"key":"color","value":"red"}]}`를 받아 HTTP 200과 `{"ids":["p000"]}` 형태로 응답한다. seller는 생략할 수 있고 filters는 필수이며 0~3개다. seller가 있으면 해당 판매자만 검색하고 모든 필터를 AND로 적용한다. 하나의 필터는 같은 속성의 키와 값이 함께 일치해야 한다. 값은 분석·대소문자 변환 없이 전체 문자열로 비교하라. 서로 다른 키의 값이 우연히 같아도 대신 일치시키지 마라. 없는 키·값·판매자는 빈 결과가 된다. 결과 id는 중복 없이 사전순으로 정렬하라. 이 실험의 상품 수는 120개이므로 페이지 넘기기는 필요 없다.

[7] 구현용 색인의 필드 한도는 12, `ignore_dynamic_beyond_limit`는 false, 주 샤드는 1개, 복제본은 0개다. 상품을 넣기 전에 필요한 매핑을 모두 선언하라. 처음 매퍼 수는 1~8개이고, 적재와 재시작 뒤에도 같아야 한다. 속성마다 매핑을 추가하거나 한도를 올리거나 검색하지 못하는 속성을 버리는 방식은 허용하지 않는다. 원본의 최상위 id와 seller를 보존하라. attributes 원본은 입력과 같은 키-값 객체 또는 `{"key":"color","value":"red"}` 객체들의 배열로 저장할 수 있다. 모든 상품과 속성을 Elasticsearch에 저장하고 검색 조건도 Elasticsearch에서 평가하라. runtime 필드와 애플리케이션 내부의 별도 검색 저장소는 사용하지 마라. [nested](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/nested) 또는 [flattened](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/flattened)로 설계할 수 있다. object 배열은 원소 간 키와 값의 결합을 보존하지 않는다는 차이를 확인하라.

[8] `seller-catalog`는 새 Elasticsearch 컨테이너 한 개에서 관찰과 구현 측정을 차례로 수행한다. 구현에는 판매자 4명, 상품 120개를 사용한다. 상품마다 고유 키 3개와 공통 키 color·size 2개를 보낸다. 값에는 반복 값, 키 사이에 교차한 값, 한글·따옴표·역슬래시, 길이 300인 문자열이 들어 있다. 상품 쓰기는 초당 10건씩 12초 동안 예정된 시각에 보내는 개방형 부하다. 이전 요청의 완료가 다음 도착 시각을 늦추지 않는다. 적재 뒤 refresh하고 전체·판매자·각 고유 키·공통 키의 단일/복합·불일치·문자열 보존 검색을 초당 20건으로 보낸다. 그 뒤 기존 상품 두 개를 교체한다. 하나는 빈 속성, 다른 하나는 새 키 하나만 남기며 판매자도 바꾼다. refresh 뒤 서비스를 종료하고 같은 색인으로 재시작해 교체한 입력을 기준으로 검색을 반복한다. 각 요청의 제한 시간은 20초이고 전체 시나리오 제한은 480초다. 처리량·지연 시간 자체에는 합격 하한·상한을 두지 않는다.

[9] 저장한 상품의 수와 검색 결과를 Elasticsearch에서 직접 확인한다. `first_rejected`는 관찰 쓰기에서 처음 거절된 순번, `observed_fields`는 관찰 마지막 매퍼 수, `observed_documents`는 관찰의 refresh 뒤 문서 수다. 이 세 값은 관찰용 지표이므로 구현을 고쳐도 바뀌지 않는다. `accepted_products`는 최초 120회 쓰기 중 201인 횟수, `stored_products`는 구현용 `_count`의 상품 수다. 둘 다 120이어야 한다. `initial_fields`와 `final_fields`는 구현용 매핑의 properties와 fields를 재귀적으로 세어 얻고 object와 nested 자체도 각각 하나로 센다. 처음 값은 1~8이고 마지막 값은 처음과 같아야 한다. `_id`와 nested 내부 Lucene 문서는 상품 수에 더하지 않는다.

[10] `search_mismatches`는 재시작 전후의 검색에서 상태 코드나 정렬된 id 배열이 기대값과 다른 횟수다. refresh 실패와 교체 쓰기의 201 이외 응답도 각각 한 번으로 센다. `persistence_mismatches`는 Elasticsearch 원본의 id·seller·속성 중 하나라도 마지막 입력과 다른 상품 수에 예상하지 않은 상품 수를 더한 값이다. `policy_errors`는 필드 한도 변경, 초과 필드 무시 설정, runtime 매핑 사용의 위반 수다. 세 값 모두 0이어야 한다. 미완료 요청과 잘못된 응답도 성공으로 세지 않는다. 실험은 이 불변식 전부가 맞아야 종료 코드 0을 반환한다. 관찰용 환경이 공식 규칙과 다르거나 Docker가 준비되지 않으면 실험 오류다.

[11] 예를 들어 p000의 color=red, size=blue와 p001의 color=blue, size=red를 넣고 refresh하라. color=red는 p000만, color=red AND size=red는 아무 상품도 반환하지 않아야 한다. 구현 전 시작 코드로 실험하여 쓰기와 필드 지표를 남긴 뒤, 매핑·문서 변환·검색을 함께 고치고 같은 실험을 다시 실행하라. 컨테이너와 서비스는 실험이 끝날 때 정리된다.

[12] 수정 범위는 `src/main/kotlin/Catalog.kt`다. 공개 HTTP 계약, JSON 처리, Elasticsearch HTTP 클라이언트, 실행·빌드 스크립트와 외부 서비스 설정은 바꾸지 마라. 이 파일에 필요한 내부 함수를 추가할 수 있다. 새 의존성은 추가하지 마라. 작업 디렉터리에서 `./build.sh`로 빌드하라. 프로젝트 루트에서 `engine/bin/cresvoid quiz es-lab -stage 1`로 확인 문항을 마친 뒤 `engine/bin/cresvoid test es-lab -stage 1 -dir <작업 디렉터리>`로 실험하라. `<작업 디렉터리>`에는 구현한 프로젝트의 경로를 넣어라. 숨은 실험기·참조 풀이·실패 변형은 열지 마라.

[13] 집계된 `search_mismatches`의 원인을 구별하려면 먼저 작업 디렉터리에서 `./build.sh`를 실행하라. 프로젝트 루트에서 `kotlin content/tracks/es-lab/stages/01-mapping-explosion/starter/diagnostics/diagnose.main.kts <작업 디렉터리>`를 실행하라. 공개 진단 도구는 고정된 실습 이미지의 컨테이너 한 개와 서비스를 띄워 상품 8개 적재, refresh, 검색, 두 상품 교체, refresh, 재시작 후 검색을 순서대로 재현한다. `write_errors`, `refresh_errors`, `replacement_errors`, `search_request_errors`, `search_result_mismatches`를 각각 집계한다. HTTP 오류와 잘못된 JSON 응답은 검색 결과 불일치와 구별한다. 유형마다 첫 실패의 메서드·경로·요청 본문·기대 상태와 본문·실제 상태와 본문을 출력한다. 502이면 실제 본문의 Elasticsearch 오류 유형과 원인을 먼저 읽어라. 종료 코드 0은 이 작은 재현의 통과, 1은 불일치, 2는 실행 환경 오류다. 이 도구는 정식 120개 상품 실험을 대신하지 않는다. 실행이 끝나거나 중단되면 서비스와 컨테이너를 정리한다.

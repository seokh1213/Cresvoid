# 6단계: 상품별 요청 합치기와 오래된 캐시

## 1. 목표

[1.1] 같은 상품의 동시 조회가 진행 중이면 하위 서비스 호출 하나의 결과를 나눠 받게 하라. 요청 하나가 취소되거나 시간 제한에 걸려도 다른 요청은 계속 기다린다. 마지막 대기자가 떠나면 진행 중인 호출을 취소한다. 이 단계에서 구현할 코드는 `SingleFlight.kt` 의 `SingleFlightLookup` 이다.

[1.2] 1~5단계의 명령과 출력은 그대로다. 시작 코드에는 이 단계의 명령을 읽는 `LookupCommands.kt`, 가짜 하위 서비스, 가상 시각 실행 틀이 있다. `SingleFlightLookup` 의 생성자와 `lookup` 서명을 유지하라. 내부 자료구조와 코루틴 구조는 직접 정하라. `LookupServices.fetch` 를 기다리는 동안 다른 상품의 조회를 막지 마라.

## 2. 입력

[2.1] `SERVICE <상품> <지연>:OK:<값>|<지연>:FAIL:<코드> ...` 는 상품의 하위 호출 응답을 순서대로 정한다. 상품마다 한 번만 쓰고 응답은 하나 이상 둔다. 지연은 1~1,000,000,000 밀리초, 값은 0~1,000,000,000, 실패 코드는 400~599 다. 호출 횟수가 응답 수를 넘으면 마지막 응답을 다시 쓴다. 상품 이름은 1~20자의 영문 소문자·숫자·하이픈이다.

[2.2] `SEED <상품> <값> <기록 시각>` 은 실행 시작 때 캐시에 값을 넣는다. 상품마다 한 번만 쓴다. 값과 기록 시각은 각각 0~1,000,000,000 이다. 기록 시각은 그 상품의 첫 `ASK` 시각보다 늦을 수 없다. `SEED` 가 없는 상품은 처음에 캐시 값이 없다. `SEED` 상품도 `SERVICE` 를 정해야 한다.

[2.3] `ASK <시각> <id> <상품> <시간 제한> <취소 시각>` 은 조회 요청을 하나 예약한다. 시각은 1~1,000,000,000 이며 앞 `ASK` 보다 이르지 않다. 같은 시각의 `ASK` 는 입력 순서로 시작한다. id 는 실행 안에서 고유한 상품 이름 형식이다. `SERVICE` 가 있는 상품만 조회한다. 시간 제한은 요청 시작 뒤의 0~1,000,000,000 밀리초이고, 0 이면 없다. 취소 시각은 절대 시각이며 0 이면 없다. 양수면 요청 시작보다 늦어야 한다. 한 요청의 시간 제한 만료와 취소 시각은 같지 않다.

[2.4] `LOOKUPS <캐시 수명>` 은 모아 둔 `SERVICE`, `SEED`, `ASK` 로 한 번 실행하고 계획을 비운다. `ASK` 는 하나 이상 있어야 한다. 캐시 수명은 1~1,000,000,000 밀리초다. 시각은 모두 가상 시각이다. 새 실행은 시각 0 과 빈 요청 상태에서 시작한다.

## 3. 공유 호출과 요청 수명

[3.1] 캐시 값이 없는 상품을 조회할 때 진행 중인 호출이 없으면 `LookupServices.fetch(product)` 를 한 번 시작하라. 이미 진행 중이면 새 요청도 그 호출을 기다린다. 같은 상품의 대기자 전부에게 성공 값 또는 실패 코드를 전하라. 서로 다른 상품의 호출은 동시에 진행할 수 있다.

[3.2] 요청 하나가 취소되거나 시간 제한에 걸리면 그 요청만 기다리기를 끝낸다. 남은 대기자가 있으면 공유 호출을 계속한다. 마지막 대기자가 떠나면 그 상품의 진행 중인 호출을 취소하고 공유 상태에서 제거한다. 뒤에 온 요청은 새 호출을 시작한다. 요청의 취소를 하위 호출의 일반 실패로 바꾸지 마라.

[3.3] 하위 호출이 성공하면 모든 현재 대기자는 `FETCHED` 결과를 받는다. 그 성공 값은 완료 시각에 캐시에 기록한다. 하위 호출이 실패하면 현재 대기자는 `FAIL` 결과를 받고, 실패는 캐시에 기록하지 않는다. 그 뒤에 온 요청은 새 호출을 시작한다.

[3.4] 하위 호출의 수명은 맨 처음 요청의 Job 에 묶지 않는다. `SingleFlightLookup` 에 전달한 `owner` 가 공유 호출과 배경 갱신의 주인이다. `owner` 가 끝나면 남은 하위 호출도 취소된다. 이번 실행은 모든 요청의 결과와 시작된 배경 갱신이 끝난 뒤 `owner` 를 종료한다.

## 4. 캐시와 배경 갱신

[4.1] 값이 기록된 시각을 w, 캐시 수명을 T 라 하자. 조회 시각이 w+T 보다 이르면 캐시 값에 `FRESH` 를 붙여 즉시 반환한다. 조회 시각이 정확히 w+T 이거나 더 늦으면 `STALE` 을 붙여 그 값을 즉시 반환하고, 그 상품의 배경 갱신이 없다면 하나 시작한다. 오래된 값을 반환하는 요청은 갱신의 대기자가 아니다.

[4.2] 같은 상품에 오래된 값이 남아 있는 동안 여러 요청이 와도 진행 중인 배경 갱신은 하나다. 배경 갱신에는 전경 대기자가 없으므로 오래된 값을 받은 요청의 취소나 시간 제한은 갱신을 취소하지 않는다. 배경 갱신이 성공하면 완료 시각에 새 값을 기록하고 수명을 다시 센다. 이후 조회는 그 시각을 기준으로 `FRESH` 또는 `STALE` 을 정한다.

[4.3] 배경 갱신이 실패하면 오래된 값과 원래 기록 시각을 그대로 둔다. 그 실패를 이미 응답한 요청에게 다시 전하지 않는다. 실패 뒤 다음 오래된 값 조회는 새 배경 갱신을 시작한다. 전경 호출과 배경 갱신은 상품별로 관리한다.

## 5. 출력과 같은 시각

[5.1] 가짜 서비스는 하위 호출을 시작할 때 `start fetch <상품> <순번>`, 성공할 때 `ok fetch <상품> <순번> <값>`, 실패할 때 `fail fetch <상품> <순번> <코드>`, 기다리던 호출이 취소될 때 `cancel fetch <상품> <순번>` 을 기록한다. 순번은 상품마다 1부터 센다. 요청 시작에는 `arrive <id> <상품>` 을 기록한다.

[5.2] 사건 줄은 1단계 [3.12] 대로 시각, 같은 시각에는 사건 문구의 사전순으로 정렬한다. 그 뒤에 `ASK` 입력 순서대로 `LOOKUP <id> FETCHED|FRESH|STALE <완료 시각> <값>`, `LOOKUP <id> FAIL <완료 시각> <코드>`, `LOOKUP <id> TIMEOUT|CANCELLED <완료 시각>` 가운데 하나씩 출력한다. 마지막 줄은 `LOOKUPS DONE <종료 시각> requests=<요청 수> calls=<하위 호출 시작 수>` 다. `TRACE OFF` 면 사건 줄만 생략하고 요청 결과와 마지막 줄은 출력한다.

[5.3] 같은 시각에 여러 요청이 시작되면 입력 순서다. 요청 시작과 하위 호출 완료가 같으면 요청 시작을 먼저 처리한다. 따라서 그 요청은 아직 진행 중인 전경 호출에 합류하거나 아직 오래된 캐시 값을 받는다. 캐시 만료 시각과 조회 시각이 같으면 [4.1] 의 `STALE` 규칙을 따른다.

[5.4] 사건 줄은 실제 실행 순서가 아니라 [5.2] 의 정렬 결과다. 검사 입력은 요청의 취소·시간 제한 만료와 하위 호출 완료가 같은 시각에 겹치지 않게 만든다. 마지막 대기자의 종료와 새 요청 시작도 같은 시각에 두지 않는다. 서로 다른 상품의 사건이 같은 시각이면 [5.2] 로 정렬한다.

## 6. 예시

[6.1] a 와 b 는 p 의 전경 호출 하나를 기다린다. b 는 시간 제한이 7 에 끝나고 a 는 5 에 취소된다. 대기자가 모두 떠나 첫 호출이 취소된다. c 는 두 번째 호출을 시작한다.

```
> SERVICE p 10:OK:7 2:OK:8
> ASK 2 a p 0 5
> ASK 3 b p 4 0
> ASK 8 c p 0 0
> LOOKUPS 10
2 arrive a p
2 start fetch p 1
3 arrive b p
7 cancel fetch p 1
8 arrive c p
8 start fetch p 2
10 ok fetch p 2 8
LOOKUP a CANCELLED 5
LOOKUP b TIMEOUT 7
LOOKUP c FETCHED 10 8
LOOKUPS DONE 10 requests=3 calls=2
```

[6.2] 두 요청은 실패를 함께 받지만, 그 뒤의 요청은 실패를 캐시에서 받지 않고 새 호출을 시작한다.

```
> SERVICE p 4:FAIL:503 2:OK:8
> ASK 2 a p 0 0
> ASK 3 b p 0 0
> ASK 7 c p 0 0
> LOOKUPS 10
2 arrive a p
2 start fetch p 1
3 arrive b p
6 fail fetch p 1 503
7 arrive c p
7 start fetch p 2
9 ok fetch p 2 8
LOOKUP a FAIL 6 503
LOOKUP b FAIL 6 503
LOOKUP c FETCHED 9 8
LOOKUPS DONE 9 requests=3 calls=2
```

[6.3] 기록 시각 0 의 값은 수명 5 가 끝나는 시각 5 부터 오래된 값이다. b 는 오래된 값 10 을 즉시 받고 배경 갱신을 시작한다. c 도 같은 값을 받지만 호출을 더 만들지 않는다.

```
> SERVICE p 4:OK:20
> SEED p 10 0
> ASK 2 a p 0 0
> ASK 5 b p 0 0
> ASK 6 c p 0 0
> ASK 10 d p 0 0
> LOOKUPS 5
2 arrive a p
5 arrive b p
5 start fetch p 1
6 arrive c p
9 ok fetch p 1 20
10 arrive d p
LOOKUP a FRESH 2 10
LOOKUP b STALE 5 10
LOOKUP c STALE 6 10
LOOKUP d FRESH 10 20
LOOKUPS DONE 10 requests=4 calls=1
```

## 7. 검사

[7.1] 1단계 [7.1]~[7.5], [7.7], [7.10] 을 그대로 따른다. 6단계를 검사할 때는 1~5단계 테스트를 먼저 다시 실행한다. 이전 명령의 출력은 바꾸지 않는다.

[7.2] 고정 입력은 대기자 하나만 떠나는 경우, 전부 떠나는 경우, 실패와 재시도, 수명 경계, 갱신 성공과 실패, 서로 다른 상품의 병렬 진행을 다룬다. 무작위 입력은 이 조건의 조합을 바꾸어 확인한다. 대규모 입력은 서로 다른 상품 약 20,000개와 요청 약 80,000개를 한 실행에 넣는다. 제한 시간은 15초다. 진행 중인 호출을 요청마다 전체 목록에서 찾는 구현은 이 규모에서 늦어진다.

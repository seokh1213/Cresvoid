# 1단계: 동시 호출과 시간 제한

## 1. 개요

[1.1] 이 트랙에서는 kotlinx.coroutines 로 백엔드에서 자주 짜는 동시 처리를 구현한다. 프로그램은 표준 입력으로 시나리오를 받는다. 시나리오는 가짜 하위 서비스가 언제 어떤 응답을 할지 정하고 학습자가 구현한 코루틴 코드를 실행하게 한다. 프로그램은 하위 서비스가 받은 호출과 응답을 가상 시각과 함께 적은 사건 기록과 실행 결과를 표준 출력에 쓴다. 시각은 kotlinx-coroutines-test 의 가상 시간이다. 프로그램은 실제로 기다리지 않고 같은 입력에는 늘 같은 출력을 낸다.

[1.2] 1단계에서는 상품 상세 화면에 필요한 값을 하위 서비스 여러 곳에서 동시에 받아 합친다. 가격, 재고, 리뷰 서비스를 동시에 호출하고 가격이 오면 그 가격으로 쿠폰 서비스를 호출해 할인액을 받는다. 호출마다 시간 제한이 있고 상세 조회 전체에는 마감 시각이 있다. 가격과 재고는 반드시 있어야 하고 리뷰와 쿠폰은 없으면 기본값으로 대신한다.

[1.3] 시작 코드(`starters/kotlin`)에는 입력 해석, 가짜 하위 서비스, 사건 기록과 출력, 가상 시간 실행 틀이 이미 들어 있다. 학습자는 단계마다 정해진 함수를 구현한다. 1단계에서 구현할 함수는 `FanOut.kt` 의 `loadProductDetail` 이다. 이 함수는 하위 서비스를 호출하는 `DetailServices` 와 시간 제한을 담은 `DetailLimits` 를 받아 `DetailResult` 를 돌려준다. 이 타입들과 가짜 하위 서비스는 `Detail.kt` 에 있다. 시작 코드를 고쳐도 되지만 검사는 표준 출력만 비교한다.

[1.4] 2단계는 상품 수천 개의 가격을 동시 실행 상한 안에서 다시 조회하며 재시도와 사용자 취소를 다룬다. 3단계는 수집, 변환, 저장 단계를 Channel 로 잇는 파이프라인을, 4단계는 가격 변경 이벤트를 Flow 와 StateFlow 로 처리하는 흐름을 만든다. 시작 코드에는 2~4단계의 입력 해석과 가짜 하위 서비스도 들어 있고 학습자가 구현할 함수는 `Limits.kt`, `Channels.kt`, `Flows.kt` 에 있다. 이 문서의 입출력 규칙은 4단계까지 그대로 쓴다. 뒤 단계는 이 문서가 정한 명령의 출력을 바꾸지 않는다.

[1.5] 1단계의 명령은 아래와 같다.

| 명령 | 하는 일 | 출력 |
|---|---|---|
| `TRACE ON`, `TRACE OFF` | 사건 줄을 출력할지 정한다 | 없음 |
| `CALL <서비스> <지연> OK <값>` | 서비스가 지연 뒤에 값으로 응답하게 한다 | 없음 |
| `CALL <서비스> <지연> ERROR` | 서비스가 지연 뒤에 오류로 응답하게 한다 | 없음 |
| `TIMEOUT <서비스> <시간>` | 서비스 호출의 시간 제한을 정한다 | 없음 |
| `DEADLINE <시간>` | 상세 조회의 마감 시각을 정한다 | 없음 |
| `DETAIL` | 상세 조회를 한 번 실행한다 | 사건 줄 여러 개와 결과 줄 1개 |

## 2. 배경 개념

[2.1] 상품 상세 API 하나가 하위 서비스 여러 곳을 호출하는 일은 흔하다. 하위 서비스를 하나씩 차례로 호출하면 응답 시간은 호출마다 걸린 시간의 합이 된다. 서로의 결과를 기다릴 필요가 없는 호출을 동시에 보내면 응답 시간은 가장 오래 걸린 호출의 시간으로 줄어든다. 가격에 100ms, 재고에 80ms, 리뷰에 300ms 가 걸린다면 차례로 호출할 때는 480ms, 동시에 호출할 때는 300ms 가 걸린다. 앞 호출의 결과가 필요한 호출은 그 결과가 온 뒤에 보낼 수 있지만 상관없는 다른 호출이 끝나기까지 기다릴 까닭은 없다.

[2.2] 코루틴은 실행을 멈췄다가 이어 갈 수 있는 계산이다. 중단 함수가 응답을 기다리는 동안 코루틴은 중단하고 스레드를 놓는다. 응답이 오면 코루틴은 멈춘 곳에서 재개된다. 그래서 스레드 하나로도 응답을 기다리는 호출 여러 개를 함께 진행할 수 있다.

[2.3] kotlinx.coroutines 의 `async` 는 자식 코루틴을 시작하고 곧바로 `Deferred` 를 돌려준다. 결과는 `Deferred` 의 `await` 로 기다린다. 호출 셋을 모두 `async` 로 시작한 뒤에 `await` 하면 셋이 함께 진행된다. 하나를 시작하자마자 `await` 하면 그 결과가 올 때까지 다음 호출을 시작하지 못하므로 차례로 호출한 것과 같아진다.

[2.4] 구조적 동시성에서 코루틴은 스코프 안에서 시작되고 부모 아래 자식으로 연결된다. `coroutineScope` 는 자기 안에서 시작한 자식이 모두 끝나야 돌아온다. 자식 하나가 예외로 실패하면 `coroutineScope` 는 나머지 자식을 취소하고 그 예외를 던진다. `async` 로 시작한 자식도 같다. 실패한 `async` 의 `await` 를 try 로 감싸 예외를 포착해도 형제가 취소되는 것은 막지 못한다. 반드시 있어야 하는 값 하나를 얻지 못하면 나머지 호출도 쓸모가 없으므로 이 동작이 알맞다.

[2.5] `supervisorScope` 에서는 자식 하나가 실패해도 다른 자식과 스코프가 취소되지 않는다. 실패한 `async` 의 예외는 그 `await` 에서 던져지고 받는 쪽이 처리한다. 없어도 되는 값을 받을 때 알맞다. 리뷰 서비스가 실패해도 가격과 재고를 받아 리뷰 없이 화면을 보여 줄 수 있다. 일부가 실패해도 기본값으로 대신해 응답하는 방식을 우아한 성능 저하라 한다.

[2.6] 취소는 협력적이다. 코루틴이 취소되면 kotlinx.coroutines 의 중단 함수는 중단해 있던 자리에서 곧바로 `CancellationException` 을 던진다. 이미 취소된 코루틴이 `delay` 같은 중단 함수를 호출하면 기다리지 않고 바로 이 예외가 던져진다. 이 예외는 정상적인 취소의 신호여서 코루틴을 실패로 만들지 않는다. `catch (e: Exception)` 처럼 모든 예외를 포착하는 catch 는 `CancellationException` 도 포착한다. 포착한 뒤에 다른 예외를 던지거나 하던 일을 이어 가면 취소가 제대로 전해지지 않는다.

[2.7] `withTimeout` 은 블록이 정한 시간 안에 끝나지 않으면 블록을 취소하고 `TimeoutCancellationException` 을 던진다. 이 예외는 `CancellationException` 의 하위 타입이다. `withTimeoutOrNull` 은 같은 경우에 예외 대신 null 을 돌려준다. 블록 안의 응답이 시간 제한이 끝나는 바로 그 시각에 와도 시간 제한이 먼저 끝나 블록이 취소된다. kotlinx.coroutines 1.11.0 의 가상 시간에서 실행해 확인한 동작이다.

[2.8] 시간 제한을 겹쳐 걸면 어느 쪽이 끝났는지 구분해야 한다. 바깥 시간 제한이 끝나면 안쪽 블록도 취소되므로 안쪽에서도 `TimeoutCancellationException` 이 보인다. 안쪽에서 이 예외를 포착해 '안쪽 시간 초과' 를 뜻하는 다른 예외로 바꿔 던지면 바깥 `withTimeout` 도 그 예외를 던진다. 바깥 시간 제한이 끝났다는 정보가 사라지는 것이다. `withTimeoutOrNull` 은 자기 시간 제한이 끝났을 때만 null 을 돌려주고 바깥에서 온 취소는 그대로 전한다.

[2.9] 호출마다 두는 시간 제한과 따로 요청 전체에 마감 시각을 둔다. 사용자는 마감 시각까지는 응답을 받아야 한다. 마감 시각이 되면 끝나지 않은 호출은 더 기다려도 쓸모가 없다. 반드시 있어야 하는 값이 그때까지 오지 않았으면 요청은 실패한다. 없어도 되는 값만 남았으면 그 값을 기본값으로 대신해 응답한다. 앞 호출의 결과를 기다려 늦게 시작한 호출은 마감 시각까지 남은 시간이 자기 시간 제한보다 짧을 수 있다.

[2.10] kotlinx-coroutines-test 의 `runTest` 는 가상 시간 위에서 코루틴을 실행한다. `delay` 는 실제로 기다리지 않는다. `runTest` 는 지금 가상 시각에 실행할 일이 모두 끝나면 가상 시각을 다음 일이 예정된 시각으로 곧바로 옮긴다. 같은 가상 시각에 예정된 일은 예정된 순서대로 하나씩 실행된다. 이 순서는 코루틴을 어떤 순서로 시작했는지, 어떤 순서로 기다리기 시작했는지에 따라 달라진다. 같은 시각에 일어난 사건을 실행된 순서대로 쓰면 올바른 구현끼리도 출력이 달라질 수 있다. 그래서 이 트랙은 같은 시각의 사건 줄을 정해진 규칙(3.12)으로 정렬해 쓴다.

[2.11] 가상 시간은 `runTest` 의 디스패처에서 실행되는 코루틴에만 적용된다. `Dispatchers.Default` 나 `Dispatchers.IO` 로 옮긴 블록, `GlobalScope` 에서 시작한 코루틴, `runBlocking` 블록 안에서 `delay` 를 부르면 가상 시각은 움직이지 않고 실제 시간만큼 기다린다.

## 3. 입출력 규칙

[3.1] 프로그램은 표준 입력을 끝까지 한 줄씩 읽어 처리하고 종료 코드 0 으로 끝난다.

[3.2] 줄을 공백(U+0020)으로 나눈 조각을 낱말이라 한다. 공백이 여럿 이어져도 빈 낱말은 생기지 않는다. 낱말이 하나도 없는 줄은 건너뛴다. 첫 낱말이 명령어이고 나머지 낱말이 인자다. 명령어는 대소문자를 구분한다.

[3.3] 수 인자는 부호와 앞자리 0 이 없는 10진 정수다. 0 은 `0` 으로 쓴다. 명령마다 따로 정하지 않으면 0 이상 1,000,000,000 이하다. 출력하는 수도 이 꼴로 쓴다. 본문은 `15,000` 처럼 세 자리마다 쉼표를 넣지만 입력과 출력의 수에는 쉼표가 없다.

[3.4] 시각과 시간의 단위는 가상 시간의 밀리초다. 지연, 시간 제한, 마감 시각처럼 길이를 나타내는 인자는 명령마다 따로 정하지 않으면 1 이상이다. 실행 도중의 시각은 32비트 정수의 최댓값 2,147,483,647 을 넘을 수 있다.

[3.5] 2~4단계의 상품 이름과 수집자 이름은 영문 소문자, 숫자, 하이픈(`-`)으로 된 1~20글자다.

[3.6] `TRACE`, `CALL`, `TIMEOUT`, `DEADLINE` 은 설정 명령이다. 설정 명령이 정한 값은 같은 명령으로 다시 정할 때까지 남는다. `DETAIL` 을 실행해도 설정은 그대로다.

[3.7] `DETAIL` 처럼 실행을 시작하는 명령을 실행 명령이라 한다. 실행마다 가상 시각은 0 에서 시작하고 가짜 하위 서비스도 새로 만든다. 앞 실행의 시각과 호출은 다음 실행으로 이어지지 않는다.

[3.8] 실행 하나는 사건 줄 0개 이상과 결과 줄 1개를 출력한다. 사건 줄을 모두 쓴 뒤에 결과 줄을 쓴다. 실행 명령이 아닌 명령은 아무것도 출력하지 않는다.

[3.9] 사건은 가짜 하위 서비스가 기록한다. 4단계에서는 가짜 가격 원본과 수집자가 기록한다. 수집자는 시작 코드가 실행한다. 사건 줄은 `<시각> <종류> <대상>` 꼴이고 종류에 따라 뒤에 값이 붙는다. 종류는 `start`, `ok` 처럼 영문 소문자로 된 낱말이다.

[3.10] 시작 코드는 학습자 함수가 돌아온 뒤에도 가상 시간에 예정된 일이 없어질 때까지 실행을 이어 가고 그동안 생긴 사건도 기록한다. 결과 줄의 시각은 학습자 함수가 돌아온 시각이다.

[3.11] 학습자 함수가 돌아오지 않았는데 가상 시간에 예정된 일이 더 없으면 시작 코드는 함수를 취소하고 결과 줄로 `<실행 이름> STUCK <시각>` 을 쓴다. 시각은 할 일이 없어진 시각이다. 학습자 함수가 취소 예외로 끝나면 결과 줄로 `<실행 이름> CANCELLED <시각>` 을 쓴다. 실행 이름은 1단계에서 `DETAIL` 이다. 1단계의 올바른 풀이는 두 줄 가운데 어느 것도 출력하지 않는다. 학습자 함수가 취소 예외가 아닌 예외를 밖으로 던지면 프로그램은 0 이 아닌 종료 코드로 끝난다.

[3.12] 사건 줄은 시각이 이른 것부터 쓴다. 시각이 같은 사건 줄은 줄 전체를 문자열로 견주어 사전순으로 앞선 것부터 쓴다. 사전순은 두 줄의 글자를 앞에서부터 하나씩 견주어 처음 다른 글자의 코드 값이 작은 쪽이 앞선다. 한 줄 전체가 다른 줄의 앞부분과 같으면 짧은 줄이 앞선다. 사건 줄은 ASCII 글자만 쓴다. 그래서 시각이 같으면 `cancel` 줄이 `ok` 줄보다, `ok` 줄이 `start` 줄보다 앞서고 `ok price 100` 이 `ok price 99` 보다, `start lock p1` 이 `start lock p10` 보다 앞선다.

[3.13] `TRACE OFF` 뒤의 실행은 결과 줄만 출력한다. `TRACE ON` 은 사건 줄을 다시 출력하게 한다. 처음에는 `TRACE ON` 상태다.

[3.14] 출력하는 줄은 모두 LF 로 끝낸다.

[3.15] 검사 입력은 네 단계의 문서가 정한 명령만 이 문서들이 정한 형식대로 쓴다. 그 밖의 입력이 들어오면 출력을 정하지 않는다. 시작 코드는 그런 줄을 만나면 예외를 던지고 0 이 아닌 종료 코드로 끝난다.

[3.16] 학습자 함수와 그 안에서 시작하는 코루틴은 모두 시작 코드가 학습자 함수를 호출한 코루틴의 디스패처에서 실행된다. 학습자 함수는 일을 `Dispatchers.Default`, `Dispatchers.IO` 같은 다른 디스패처로 옮기거나 `GlobalScope`, `runBlocking` 으로 코루틴을 실행하지 않는다. 그렇게 실행한 코루틴은 가상 시각을 따르지 않아서(2.11) 사건 줄의 시각과 결과 줄이 이 문서와 달라지고 실행할 때마다 출력이 바뀔 수 있다.

## 4. 명령 규칙

### 설정 명령

[4.1] `CALL <서비스> <지연> OK <값>` 은 그 서비스가 호출을 받은 뒤 지연만큼 지나 값으로 응답하게 한다. `CALL <서비스> <지연> ERROR` 는 지연만큼 지나 오류로 응답하게 한다. 서비스는 `price`, `stock`, `review`, `coupon` 가운데 하나다. 값은 가격, 재고 수량, 리뷰 수, 쿠폰 할인액을 나타내는 0 이상 1,000,000,000 이하의 정수다.

[4.2] `TIMEOUT <서비스> <시간>` 은 그 서비스 호출의 시간 제한을 정한다. `DEADLINE <시간>` 은 마감 시각을 정한다. 마감 시각은 상세 조회를 시작한 시각 0 부터 잰다.

[4.3] 검사 입력에서 `DETAIL` 앞에는 네 서비스의 `CALL` 과 `TIMEOUT`, 그리고 `DEADLINE` 이 저마다 한 번 이상 나온다.

### 가짜 하위 서비스

[4.4] 가짜 하위 서비스는 호출을 받은 시각에 `start <서비스>` 를 기록한다. `coupon` 은 받은 가격을 붙여 `start coupon <가격>` 을 기록한다. 호출을 받은 시각에 지연을 더한 시각을 그 호출의 응답 시각이라 한다.

[4.5] 응답 시각까지 호출이 취소되지 않으면 서비스는 응답 시각에 응답한다. 값으로 응답하면 `ok <서비스> <값>` 을 기록하고 그 값을 돌려준다. 오류로 응답하면 `error <서비스>` 를 기록하고 `ServiceFailure` 예외를 던진다.

[4.6] 응답하기 전에 호출이 취소되면 서비스는 취소된 시각에 `cancel <서비스>` 를 기록하고 응답하지 않는다. 이미 취소된 코루틴에서 호출하면 `start` 와 `cancel` 이 같은 시각에 기록된다.

### 상세 조회

[4.7] `DETAIL` 은 `loadProductDetail` 로 상세 조회를 한 번 실행한다. 상세 조회는 시각 0 에 `price`, `stock`, `review` 를 호출한다. `coupon` 은 `price` 가 값으로 응답한 시각에 그 가격으로 호출한다. 상세 조회는 이 밖의 호출을 하지 않고 한 서비스를 두 번 호출하지 않는다.

[4.8] `price` 와 `stock` 은 필수 호출이고 `review` 와 `coupon` 은 선택 호출이다.

[4.9] 호출의 시간 제한이 끝나는 시각은 그 호출을 시작한 시각에 그 서비스의 시간 제한을 더한 시각이다. 이 시각까지 응답이 오지 않은 호출은 이 시각에 취소한다. 이것을 시간 초과라 한다. 응답 시각이 시간 제한이 끝나는 시각과 같아도 시간 초과다. 이때 서비스는 응답하지 않고 `cancel` 을 기록한다.

[4.10] 마감 시각이 되면 아직 응답을 받지 않았고 시간 초과로 취소되지도 않은 호출을 모두 취소한다. 응답 시각이 마감 시각과 같은 호출도 취소한다.

[4.11] 필수 호출 둘이 모두 값으로 응답하고 선택 호출 둘이 모두 끝나면 상세 조회는 성공한다. 선택 호출이 끝났다는 것은 값으로 응답했거나 5.4 에 따라 기본값으로 대신하게 되었다는 뜻이다. 상세 조회가 끝나는 시각은 이 네 호출 가운데 가장 늦게 끝난 호출이 끝난 시각이다.

[4.12] 마감 시각 전에 필수 호출 둘이 모두 값으로 응답했으면 상세 조회는 늦어도 마감 시각에는 성공한다. 마감 시각에 취소된 선택 호출은 기본값으로 대신한다.

[4.13] `loadProductDetail` 은 상세 조회가 끝나는 시각에 돌아온다. 상세 조회가 끝날 때에는 끝나지 않은 호출이 남지 않는다. 그래서 상세 조회가 끝난 시각보다 늦은 사건은 없다.

[4.14] 상세 조회가 성공하면 결과 줄 `DETAIL OK <시각> price=<가격> stock=<재고> review=<리뷰> coupon=<쿠폰>` 을 쓴다. 시각은 상세 조회가 끝난 시각이다. 가격과 재고에는 받은 값을 쓴다. 리뷰와 쿠폰에는 받은 값을 쓰거나, 기본값으로 대신했으면 그 원인(5.4)을 쓴다.

## 5. 오류 규칙

[5.1] 필수 호출이 마감 시각보다 이른 시각 t 에 오류로 응답하거나 시간 초과로 취소되면 상세 조회는 t 에 실패한다. 실패 이유는 `price` 의 오류 응답이면 `PRICE_ERROR`, `price` 의 시간 초과면 `PRICE_TIMEOUT`, `stock` 의 오류 응답이면 `STOCK_ERROR`, `stock` 의 시간 초과면 `STOCK_TIMEOUT` 이다.

[5.2] 마감 시각에 필수 호출 가운데 아직 값으로 응답하지 않은 호출이 있으면 상세 조회는 마감 시각에 실패하고 실패 이유는 `DEADLINE` 이다. 필수 호출의 시간 제한이 마감 시각보다 늦게 끝나더라도 그 호출이 마감 시각까지 응답하지 않으면 이유는 `DEADLINE` 이다.

[5.3] 상세 조회가 실패한 시각에 끝나지 않은 호출은 모두 그 시각에 취소한다. 실패한 뒤로는 새 호출을 하지 않는다. 그래서 `price` 가 실패하면 `coupon` 은 호출되지 않는다. `price` 가 응답하기 전에 `stock` 이 실패해도 `coupon` 은 호출되지 않는다.

[5.4] 선택 호출이 오류로 응답하거나 시간 초과로 취소되거나 마감 시각에 취소되면 그 값은 기본값으로 대신하고 다른 호출에는 영향을 주지 않는다. 기본값의 원인은 오류 응답이면 `ERROR`, 시간 초과면 `TIMEOUT`, 마감 시각에 취소되었으면 `DEADLINE` 이다. 상세 조회가 실패해서 취소된 선택 호출은 기본값으로 대신하지 않는다. 그 실행의 결과 줄은 실패를 알린다.

[5.5] 상세 조회가 실패하면 결과 줄 `DETAIL FAIL <시각> <이유>` 를 쓴다. 시각은 상세 조회가 실패한 시각이다.

[5.6] 호출의 시간 제한이 끝나는 시각과 마감 시각이 같은 입력은 출력을 정하지 않는다. 이 둘이 같으면 kotlinx.coroutines 에서 어느 시간 제한의 결과가 보이는지가 시간 제한을 겹친 방식에 따라 달라지기 때문이다. 검사 입력에서 `price`, `stock`, `review` 의 시간 제한은 마감 시각과 다르다. `coupon` 을 호출하는 실행에서는 `coupon` 을 시작한 시각에 그 시간 제한을 더한 값도 마감 시각과 다르다.

[5.7] 필수 호출이 마감 시각보다 이른 시각 t 에 실패하는 입력에서 t 에 다른 호출의 응답 시각이나 시간 제한이 끝나는 시각이 겹치면 출력을 정하지 않는다. 같은 시각의 일 가운데 무엇이 먼저 실행되는지가 구현에 따라 달라지기 때문이다. t 보다 이른 시각에 이미 응답했거나 취소된 호출은 t 에 일어날 일이 없으므로 그 호출의 응답 시각과 시간 제한이 끝나는 시각은 겹침으로 치지 않는다. 검사 입력에는 이런 겹침이 없다.

## 6. 예시

[6.1] 예시 블록 하나는 프로그램을 한 번 실행한 기록이다. `> ` 로 시작하는 줄은 입력이고 나머지 줄은 바로 위 입력의 출력이다. 실제 입력에는 `> ` 가 없다.

[6.2] 첫 번째 `DETAIL` 은 기본 동작이다. `review` 는 300 에 응답할 예정이지만 시간 제한이 150 에 끝나므로 150 에 취소되고 기본값의 원인은 `TIMEOUT` 이다. `coupon` 은 `price` 가 응답한 100 에 시작해 150 에 응답한다. 가장 늦게 끝난 호출이 150 에 끝나므로 상세 조회도 150 에 끝난다. 시각 100 의 두 줄은 사전순에 따라 `ok` 가 `start` 보다 앞선다. 설정은 남으므로 두 번째와 세 번째 `DETAIL` 은 `stock` 만 바꿔 실행한다. 두 번째 실행에서는 `stock` 이 60 에 오류로 응답한다. 그 시각에 `price` 와 `review` 를 취소하고 `coupon` 은 호출하지 않는다. 세 번째 실행에서는 `stock` 이 120 에 실패하기 전에 `price` 가 응답했으므로 `coupon` 이 100 에 시작했다가 120 에 취소된다.

```
> CALL price 100 OK 15000
> CALL stock 80 OK 7
> CALL review 300 OK 128
> CALL coupon 50 OK 1000
> TIMEOUT price 200
> TIMEOUT stock 200
> TIMEOUT review 150
> TIMEOUT coupon 100
> DEADLINE 400
> DETAIL
0 start price
0 start review
0 start stock
80 ok stock 7
100 ok price 15000
100 start coupon 15000
150 cancel review
150 ok coupon 1000
DETAIL OK 150 price=15000 stock=7 review=TIMEOUT coupon=1000
> CALL stock 60 ERROR
> DETAIL
0 start price
0 start review
0 start stock
60 cancel price
60 cancel review
60 error stock
DETAIL FAIL 60 STOCK_ERROR
> CALL stock 120 ERROR
> DETAIL
0 start price
0 start review
0 start stock
100 ok price 15000
100 start coupon 15000
120 cancel coupon
120 cancel review
120 error stock
DETAIL FAIL 120 STOCK_ERROR
```

[6.3] 마감 시각이 320 이다. 첫 번째 `DETAIL` 에서 필수 호출 둘은 마감 시각 전에 응답했다. `review` 는 330 에 응답할 예정이고 `coupon` 은 250 에 시작해 350 에 오류로 응답할 예정이었으나 둘 다 마감 시각 320 에 취소된다. 둘의 기본값 원인은 `DEADLINE` 이고 상세 조회는 320 에 성공한다. 두 번째 `DETAIL` 에서는 `price` 가 500 에 응답할 예정이어서 마감 시각에 아직 응답하지 않았다. `price` 의 시간 제한은 600 에 끝나지만 실패 이유는 `DEADLINE` 이다. `coupon` 은 호출되지 않는다.

```
> CALL price 250 OK 9900
> CALL stock 40 OK 3
> CALL review 330 OK 52
> CALL coupon 100 ERROR
> TIMEOUT price 300
> TIMEOUT stock 300
> TIMEOUT review 400
> TIMEOUT coupon 200
> DEADLINE 320
> DETAIL
0 start price
0 start review
0 start stock
40 ok stock 3
250 ok price 9900
250 start coupon 9900
320 cancel coupon
320 cancel review
DETAIL OK 320 price=9900 stock=3 review=DEADLINE coupon=DEADLINE
> CALL price 500 OK 9900
> TIMEOUT price 600
> DETAIL
0 start price
0 start review
0 start stock
40 ok stock 3
320 cancel price
320 cancel review
DETAIL FAIL 320 DEADLINE
```

[6.4] 시각이 겹치는 경우와 `TRACE OFF` 다. 첫 번째 `DETAIL` 에서 `coupon` 은 100 에 시작해 160 에 응답할 예정이지만 시간 제한도 160 에 끝나므로 시간 초과다. `review` 는 90 에 오류로 응답한다. 두 번째 `DETAIL` 에서는 `coupon` 의 시간 제한이 200 에 끝나지만 응답 시각 160 이 마감 시각과 같아 마감 시각에 취소된다. 세 번째 `DETAIL` 에서는 필수 호출 둘의 응답 시각 100 이 마감 시각과 같아 둘 다 취소되고 상세 조회가 실패한다. 네 번째 `DETAIL` 에서는 `price` 가 시간 제한이 끝나는 80 까지 응답하지 않는다.

```
> TRACE OFF
> CALL price 100 OK 5000
> CALL stock 100 OK 2
> CALL review 90 ERROR
> CALL coupon 60 OK 500
> TIMEOUT price 150
> TIMEOUT stock 150
> TIMEOUT review 120
> TIMEOUT coupon 60
> DEADLINE 400
> DETAIL
DETAIL OK 160 price=5000 stock=2 review=ERROR coupon=TIMEOUT
> TIMEOUT coupon 100
> DEADLINE 160
> DETAIL
DETAIL OK 160 price=5000 stock=2 review=ERROR coupon=DEADLINE
> DEADLINE 100
> DETAIL
DETAIL FAIL 100 DEADLINE
> TIMEOUT price 80
> DEADLINE 400
> DETAIL
DETAIL FAIL 80 PRICE_TIMEOUT
```

## 7. 검사 방식

[7.1] 엔진은 테스트마다 풀이의 `run.sh` 를 새 프로세스로 실행한다. 작업 디렉터리는 풀이 디렉터리다.

[7.2] 엔진은 테스트의 입력 줄을 LF 로 잇고 마지막 줄 뒤에도 LF 를 붙여 표준 입력에 쓴 뒤 표준 입력을 닫는다.

[7.3] 프로세스가 0 이 아닌 종료 코드로 끝나면 실패다.

[7.4] 표준 출력만 기대 출력과 비교하고 표준 오류는 비교하지 않는다. 각 줄 끝의 공백, 탭, CR 을 지우고 끝에 붙은 빈 줄을 지운 뒤 줄 수와 각 줄의 내용이 정확히 같아야 한다.

[7.5] 일반 테스트의 제한 시간은 10초다. 제한 시간을 넘기면 엔진이 프로세스를 끝내고 실패로 판정한다.

[7.6] 대규모 테스트는 `DETAIL` 을 2,000번 안팎 실행하는 입력이다. 실행마다 네 서비스의 지연, 응답, 시간 제한과 마감 시각을 무작위로 정하고 5.6, 5.7 의 겹침은 만들지 않는다. 제한 시간은 15초다. 이 테스트는 무작위 입력으로 규칙의 여러 조합을 넓게 확인한다. 참조 풀이는 1초 안에 끝난다.

[7.7] 검사 입력의 한 줄은 UTF-8 로 1,000바이트 이하다.

[7.8] `ITEM`, `LOCK`, `RETRY`, `BATCH` 는 2단계, `FEED`, `PIPELINE` 은 3단계, `EVENT`, `WATCH`, `AUDIT`, `MONITOR`, `PRICES` 는 4단계의 명령이다. 1단계 검사 입력에는 이 명령이 나오지 않는다.

[7.9] 2~4단계를 검사할 때도 1단계 테스트를 다시 실행한다.

[7.10] 3.14 는 엔진이 검사하지 않는다. 엔진은 출력 줄 끝의 CR 과 끝에 붙은 빈 줄을 지운 뒤 비교하기 때문이다(7.4). 표준 입출력 프로그램의 관례라서 적어 둔다.

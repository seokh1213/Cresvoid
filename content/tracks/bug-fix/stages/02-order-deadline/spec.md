# 주문 확정 제한 시간

## 1. 제품 맥락

[1.1] 이 프로그램은 쇼핑 카탈로그 서비스의 주문 확정 처리기를 흉내 낸 명령 처리기다. 고객이 결제 화면에서 주문하면 처리기는 하위 서비스 네 개를 차례로 호출해 주문을 확정한다.

[1.2] 결제 화면은 주문마다 정한 제한 시간까지만 응답을 기다린다. 처리기는 제한 시간 안에 끝내지 못한 주문을 포기하고 시간 초과로 응답한다. 포기한 주문을 위해서는 하위 서비스에 요청을 더 보내지 않는다. 포기한 뒤에 결제 승인 요청이 나가면 이중 결제가 생길 수 있다. 알림 요청이 나가면 고객이 잘못된 주문 완료 안내를 받는다. 시간 초과로 끝난 주문의 재고 예약과 결제 승인은 정산 배치가 나중에 되돌린다. 처리기는 되돌리지 않는다.

[1.3] 하위 서비스는 가끔 느리게 응답하거나 잠시 응답하지 못한다. 처리기는 요청 한 번마다 따로 제한 시간을 두고 일시적인 실패는 정한 횟수까지 다시 시도한다. 재고 없음이나 카드 거절 같은 업무상 거절은 다시 시도하지 않는다.

[1.4] 시각은 실제 시간과 상관없는 가상 시계로 잰다. 가상 시계는 처리기가 하위 서비스의 응답을 기다리는 동안에만 흐르므로 같은 입력에는 언제나 같은 출력이 나온다. 프로그램은 kotlinx-coroutines-test 의 가상 시간으로 이 시계를 만든다. 시각과 시간의 단위는 ms 다.

## 2. 입출력 규칙

[2.1] 프로그램은 표준 입력에서 명령을 한 줄씩 읽어 입력이 끝날 때까지 처리하고 결과를 표준 출력에 쓴다. 입력이 끝나면 종료 코드 0 으로 끝난다.

[2.2] 입력은 UTF-8 이고 줄은 LF(U+000A) 로 나눈다. 마지막 줄 뒤에 LF 가 없어도 그 줄을 처리한다.

[2.3] 이 문서에서 공백은 U+0020 한 글자만 가리킨다. 낱말은 공백이 아닌 문자가 최대로 이어진 구간이다. 줄의 첫 낱말이 명령어이고 나머지 낱말이 차례로 인자다. 공백이 여럿 이어져도 빈 인자는 생기지 않는다.

[2.4] 낱말이 하나도 없는 줄은 건너뛰고 아무것도 출력하지 않는다.

[2.5] 명령어는 대소문자를 구분한다. `order` 는 ORDER 가 아니다.

[2.6] 출력하는 줄은 모두 LF 로 끝낸다.

[2.7] 이 문서의 정규식은 낱말 전체에 적용한다. `^` 는 낱말의 처음, `$` 는 낱말의 끝이다.

## 3. 주문 확정 단계

[3.1] 주문 하나는 아래 네 단계를 이 순서로 거친다. 단계마다 하위 서비스 하나를 호출한다. 앞 단계가 끝나야 다음 단계를 시작한다.

[3.2] 1단계는 재고 예약이고 서비스 이름은 `stock` 이다. 필수 단계다. 시도 제한 시간은 200, 최대 시도 횟수는 2 다.

[3.3] 2단계는 결제 승인이고 서비스 이름은 `payment` 다. 필수 단계다. 시도 제한 시간은 300, 최대 시도 횟수는 3 이다.

[3.4] 3단계는 포인트 적립이고 서비스 이름은 `points` 다. 선택 단계다. 시도 제한 시간은 100, 최대 시도 횟수는 2 다.

[3.5] 4단계는 주문 알림이고 서비스 이름은 `notification` 이다. 선택 단계다. 시도 제한 시간은 100, 최대 시도 횟수는 2 다.

[3.6] 처리기는 단계마다 하위 서비스에 요청을 보내 응답을 기다린다. 요청 하나를 보낸 때부터 그 요청이 끝날 때까지를 시도라 한다. 시도는 요청을 보낸 시각에 시작한다. 시도를 시작한 시각에 그 단계의 시도 제한 시간을 더한 시각을 시도 제한 시각이라 한다.

[3.7] 응답이 시도 제한 시각보다 먼저 오면 시도는 그 응답으로 끝난다. 응답이 OK 면 단계가 성공한다. 응답이 REJECTED 면 단계가 거절로 실패하고 남은 시도는 하지 않는다. 응답이 UNAVAILABLE 이면 그 시도가 실패한다.

[3.8] 시도 제한 시각까지 응답이 오지 않으면 처리기는 그 시각에 요청을 취소하고 그 시도는 실패한다. 응답이 시도 제한 시각과 같은 시각에 오면 늦은 것으로 본다.

[3.9] 시도가 실패하고 남은 시도가 있으면 기다리지 않고 바로 다음 시도를 시작한다. 최대 시도 횟수만큼 모두 실패하면 단계가 응답 없음으로 실패한다.

[3.10] 필수 단계가 실패하면 주문은 실패로 끝나고 뒤 단계는 시작하지 않는다. 선택 단계가 실패하면 그 단계를 건너뛰고 다음 단계로 넘어간다.

[3.11] 네 단계를 모두 지나면 주문이 확정된다. 건너뛴 선택 단계가 있어도 확정이다.

## 4. 제한 시간

[4.1] 주문의 제한 시간은 ORDER 를 처리하기 시작한 시각부터 잰다. 이 시각을 그 주문의 0 시각이라 한다. 0 시각에 제한 시간을 더한 시각을 마감 시각이라 한다.

[4.2] 주문은 마감 시각보다 먼저 확정되거나 실패해야 한다. 마감 시각까지 확정되지도 실패하지도 않은 주문은 마감 시각에 시간 초과로 끝난다. 마지막 단계가 마감 시각과 같은 시각에 끝나도 시간 초과다.

[4.3] 마감 시각과 같은 시각에 오는 응답은 받지 않은 것으로 본다. 시도 제한 시각이 마감 시각과 같아도 다음 시도를 시작하지 않는다.

[4.4] 주문이 시간 초과로 끝나면 처리기는 기다리던 요청을 마감 시각에 취소한다. 그 뒤로는 그 주문을 위해 어떤 하위 서비스에도 요청을 보내지 않는다. 같은 단계의 남은 시도와 뒤 단계를 모두 시작하지 않는다.

## 5. 하위 서비스

[5.1] 하위 서비스 네 개는 입력이 정한 대로 응답하는 가짜 서비스다. 실제 하위 서비스는 다른 팀이 운영하므로 처리기 쪽에서 그 동작을 바꿀 수 없다. 응답은 OK, REJECTED, UNAVAILABLE 가운데 하나다. OK 는 처리 완료, REJECTED 는 업무상 거절, UNAVAILABLE 은 일시적인 장애를 뜻한다.

[5.2] 응답은 주문과 서비스의 짝마다 REPLY 로 정한다. 처리기가 그 주문을 위해 그 서비스에 요청을 보낼 때마다 서비스는 정해 둔 응답을 앞에서부터 하나씩 쓴다. 처리기가 요청을 취소해도 그 요청에 쓴 응답은 다시 쓰지 않는다.

[5.3] 정해 둔 응답이 남아 있지 않으면 서비스는 평소 응답 시간 뒤에 OK 로 응답한다. 평소 응답 시간은 stock 이 30, payment 가 50, points 가 20, notification 이 10 이다.

## 6. 명령 규칙

### REPLY

[6.1] `REPLY <주문 ID> <서비스> <응답> <지연>` 은 그 주문과 서비스의 짝에 응답 하나를 정해 둔다. 이미 정해 둔 응답이 있으면 새 응답은 그 뒤에 붙는다. 지연은 요청을 보낸 뒤 응답이 올 때까지의 시간이다. 성공하면 아무것도 출력하지 않는다.

[6.2] 이미 처리한 주문에 쓴 REPLY 는 아무 영향이 없다.

### ORDER

[6.3] `ORDER <주문 ID> <제한 시간>` 은 주문 하나를 처리하고 결과를 한 줄 출력한다. 주문이 끝난 뒤에 다음 줄을 처리하므로 두 주문이 함께 처리되는 일은 없다.

[6.4] 결과 줄에는 주문 ID, 결과, 걸린 시간을 공백 하나씩 띄워 쓴다. 결과는 확정이면 `CONFIRMED`, 실패면 `FAILED`, 시간 초과면 `TIMEOUT` 이다. 확정된 주문에 건너뛴 선택 단계가 있으면 뒤에 공백과 `SKIPPED` 를 쓰고 건너뛴 서비스 이름을 단계 순서대로 공백 하나씩 띄워 쓴다. 실패한 주문은 뒤에 공백, 실패한 필수 단계의 서비스 이름, 공백, 실패 이유를 차례로 쓴다. 실패 이유는 거절이면 `REJECTED`, 응답 없음이면 `UNAVAILABLE` 이다.

[6.5] 걸린 시간은 0 시각부터 결과가 정해진 시각까지다. 시간 초과로 끝난 주문의 걸린 시간은 제한 시간과 같다.

### TRACE

[6.6] `TRACE <주문 ID>` 는 그 주문을 위해 하위 서비스에 보낸 요청을 보낸 순서대로 한 줄씩 출력한다.

[6.7] 요청 한 줄은 `<서비스>#<시도 번호> <보낸 시각>-<끝난 시각> <결과>` 다. 시도 번호는 그 주문에서 그 서비스에 보낸 요청의 순번이고 1부터 센다. 시각은 그 주문의 0 시각부터 잰다.

[6.8] 응답을 받아 끝난 요청의 결과는 받은 응답 그대로 `OK`, `REJECTED`, `UNAVAILABLE` 가운데 하나이고 끝난 시각은 응답을 받은 시각이다. 처리기가 응답을 받기 전에 취소한 요청의 결과는 `CANCELLED` 이고 끝난 시각은 취소한 시각이다.

## 7. 오류 규칙

[7.1] 오류가 나면 오류 줄 하나만 출력한다. 오류를 낸 명령은 아무것도 바꾸지 않는다. 프로그램은 다음 줄을 이어서 처리한다.

[7.2] 명령어가 REPLY, ORDER, TRACE 가운데 어느 것과도 같지 않으면 `ERR UNKNOWN_COMMAND` 를 출력한다.

[7.3] 인자 수가 맞지 않으면 `ERR BAD_ARGUMENT` 를 출력한다. REPLY 는 인자가 4개, ORDER 는 2개, TRACE 는 1개다.

[7.4] REPLY 와 ORDER 의 인자가 형식에 맞지 않으면 `ERR BAD_ARGUMENT` 를 출력한다. 주문 ID 는 `^[A-Za-z0-9-]{1,20}$` 에 맞아야 한다. 서비스는 `stock`, `payment`, `points`, `notification` 가운데 하나이고 응답은 `OK`, `REJECTED`, `UNAVAILABLE` 가운데 하나여야 한다. 지연과 제한 시간은 `^[1-9][0-9]{0,5}$` 에 맞고 100000 이하인 정수여야 한다.

[7.5] ORDER 의 인자가 모두 형식에 맞지만 같은 주문 ID 의 주문을 이미 처리했으면 `ERR DUPLICATE_ORDER` 를 출력한다.

[7.6] TRACE 의 주문 ID 로 처리한 주문이 없으면 `ERR UNKNOWN_ORDER` 를 출력한다.

## 8. 예시

[8.1] 아래는 프로그램을 한 번 실행한 기록이다. `> ` 로 시작하는 줄은 입력이고 나머지 줄은 바로 위 입력의 출력이다. 실제 입력에는 `> ` 가 없다.

[8.2] A-1001 의 첫 결제 승인 요청은 응답이 380 에 올 예정이었지만 처리기가 시도 제한 시각 330 에 취소했다. 두 번째 시도는 평소 응답 시간 50 뒤에 OK 를 받았다. 포인트 적립은 REJECTED 를 받아 다시 시도하지 않고 건너뛰었다. A-1002 는 재고 예약의 두 시도가 모두 실패해 260 에 실패로 끝났다.

```
> REPLY A-1001 payment OK 350
> REPLY A-1001 points REJECTED 10
> ORDER A-1001 1000
A-1001 CONFIRMED 400 SKIPPED points
> TRACE A-1001
stock#1 0-30 OK
payment#1 30-330 CANCELLED
payment#2 330-380 OK
points#1 380-390 REJECTED
notification#1 390-400 OK
> REPLY A-1002 stock UNAVAILABLE 60
> REPLY A-1002 stock OK 250
> ORDER A-1002 1000
A-1002 FAILED 260 stock UNAVAILABLE
> TRACE A-1002
stock#1 0-60 UNAVAILABLE
stock#2 60-260 CANCELLED
```

## 9. 버그 신고

[9.1] 아래는 알림 서비스 개발자가 보낸 신고다. 결제 화면에서 시간 초과 안내를 받은 고객에게 주문 완료 알림이 갔다는 문의가 고객센터에 들어왔다. 알림 서비스 기록을 보면 처리기가 그 주문을 포기한 뒤에 알림 요청이 들어왔다.

[9.2] 포인트 서비스가 느렸던 날의 주문을 재현한 입력이다. 첫 포인트 적립 요청에 시도 제한 시각까지 응답이 오지 않아 처리기가 두 번째 요청을 보냈다. 두 번째 요청이 마감 시각 250 에 취소된 것까지는 정상이다. 그런데 TIMEOUT 응답이 나간 그 시각에 알림 요청이 두 번 들어왔다. 제한 시간이 지났다는 응답을 받았는데 호출 기록은 그 뒤로도 늘었다.

```
REPLY K-2001 points OK 150
REPLY K-2001 points OK 150
ORDER K-2001 250
TRACE K-2001
```

[9.3] 기대한 출력이다.

```
K-2001 TIMEOUT 250
stock#1 0-30 OK
payment#1 30-80 OK
points#1 80-180 CANCELLED
points#2 180-250 CANCELLED
```

[9.4] 실제 출력이다.

```
K-2001 TIMEOUT 250
stock#1 0-30 OK
payment#1 30-80 OK
points#1 80-180 CANCELLED
points#2 180-250 CANCELLED
notification#1 250-250 CANCELLED
notification#2 250-250 CANCELLED
```

# 문서 생성 작업의 잠금 상태 불일치

## 작업과 완료 알림

[1] 쇼핑 카탈로그 서비스는 상품군별 안내 문서를 생성한다. 작업은 자원의 lease 잠금을 얻은 뒤 실행하며, 생성이 끝나면 완료 알림을 보낸다. 알림 접수와 후처리는 별개다. 여러 작업의 알림을 접수한 뒤 묶어서 처리할 수 있고, 알림이 늦거나 중복으로 도착할 수도 있다. 이 프로그램은 입력된 사건 순서대로 작업 상태와 잠금 상태를 재현한다.

[2] 프로그램은 표준 입력에서 명령을 한 줄씩 EOF까지 읽는다. 빈 줄은 무시하고 나머지 명령마다 결과 한 줄을 표준 출력에 쓴다. 명령과 인자는 공백으로 구분한다. 작업·자원·클라이언트 이름은 영문 소문자로 시작하며 영문 소문자·숫자·하이픈으로 이루어진 1~40자 문자열이다. 이름은 변환 없이 그대로 식별한다.

[3] 명령은 최대 10,000개다. 모든 숫자는 십진 정수이며 TTL은 1~1,000,000,000, 시간 이동량은 0~1,000,000,000, 한 번의 후처리 한도는 0~10,000이다. 입력 전체의 시간 이동량 합계는 1,000,000,000,000 이하다. 입력은 문서에 정한 형식과 범위를 지킨다. 잘못된 입력에 대한 오류 출력은 정의하지 않는다.

## 시각과 잠금

[4] 처음에는 작업 목록과 잠금 저장소, 완료 대기열이 비어 있고 가상 시각은 0이다. 시각 단위는 밀리초다. `TICK <이동량>`은 가상 시각에 이동량을 더하고 `TIME <현재 시각>`을 출력한다. 다른 명령은 시각을 바꾸지 않는다. 실제 시계, 대기, 스레드는 사용하지 않는다.

[5] 잠금에는 자원, 클라이언트, 획득 번호, 만료 시각이 있다. 현재 시각이 만료 시각보다 작을 때만 유효하다. 현재 시각이 만료 시각과 같거나 크면 잠금이 없는 것처럼 처리한다. 만료된 잠금의 내부 정리 시점은 출력에 영향을 주지 않는다. 잠금 만료는 작업 상태를 바꾸지 않는다.

[6] 획득 번호는 잠금을 얻은 한 번의 획득을 식별한다. 프로그램 전체에서 성공한 획득 순서대로 1부터 하나씩 증가하며 자원이 달라도 서로 다른 번호를 받는다. 실패한 시작, 중복 시작, 조회, 시간 이동, 완료 알림, 후처리는 번호를 소비하지 않는다. 잠금을 해제하거나 만료시켜도 번호를 재사용하지 않는다.

## 명령

[7] `START <작업> <자원> <클라이언트> <TTL>`은 작업을 시작한다. 같은 작업 이름이 이미 등록되어 있으면 다른 인자와 관계없이 `EXISTS <작업 상태>`를 출력하고 아무것도 바꾸지 않는다. 등록된 적 없는 작업이고 해당 자원에 유효한 잠금이 있으면 `BUSY <현재 클라이언트> <현재 획득 번호> <현재 만료 시각>`을 출력하며 작업을 등록하지 않는다. 유효한 잠금이 없으면 잠금을 얻고 작업을 RUNNING 상태로 등록하며 `STARTED <획득 번호> <만료 시각>`을 출력한다. 만료 시각은 현재 시각에 TTL을 더한 값이다. 같은 클라이언트라도 유효한 잠금이 있으면 시작에 실패하며 TTL을 연장하지 않는다.

[8] `COMPLETE <작업>`은 완료 알림을 접수한다. 등록되지 않은 작업이면 `UNKNOWN`을 출력한다. RUNNING 작업이면 완료 대기열의 끝에 한 번 넣고 QUEUED로 바꾼다. QUEUED나 DONE 작업은 상태와 대기열을 바꾸지 않는다. 등록된 작업이면 접수 후 상태인 `QUEUED` 또는 `DONE`을 출력한다. 알림 접수만으로 잠금을 해제하지 않는다.

[9] `FLUSH <한도>`는 접수 순서대로 대기열의 앞에서 최대 한도 개의 알림을 꺼내 후처리한다. 알림마다 그 작업을 시작할 때 얻은 잠금을 해제하도록 요청하고 작업을 DONE으로 바꾼다. 해당 자원의 유효한 잠금과 작업 시작 당시의 클라이언트 및 획득 번호가 모두 일치할 때만 잠금을 없앤다. 잠금이 없거나 만료됐거나 소유권이 다르면 현재 잠금을 유지한다. 해제 여부와 관계없이 알림은 처리된 것으로 센다. `FLUSHED <실제 처리 개수>`를 출력한다. 한도가 0이거나 대기열이 비어 있으면 처리 개수는 0이다.

[10] `STATUS <자원>`은 유효한 잠금이 있으면 `HELD <클라이언트> <획득 번호> <만료 시각>`, 없으면 `FREE`를 출력한다. `JOB <작업>`은 등록된 작업이면 `RUNNING`, `QUEUED`, `DONE` 중 현재 상태를, 등록되지 않은 작업이면 `UNKNOWN`을 출력한다. 조회는 상태·유효 기간·획득 번호를 바꾸지 않는다. 작업 기록은 DONE이 된 뒤에도 유지한다.

[11] 명령은 한 스레드에서 입력 순서대로 실행된다. 잠금 획득과 해제에서는 상태 확인과 조건을 만족할 때의 변경을 원자적으로 처리한다. 한 작업의 후처리는 다른 자원의 잠금이나 다른 작업의 상태를 바꾸지 않는다. 저장소 구현 방법이나 함수 이름은 공개 계약이 아니며 문서 저장소에 도착하는 늦은 쓰기를 차단하는 기능은 이 단계에서 다루지 않는다. 소유권 식별과 획득 세대의 배경은 [etcd concurrency API](https://etcd.io/docs/v3.6/dev-guide/api_concurrency_reference_v3/)와 [Chubby 논문](https://research.google/pubs/the-chubby-lock-service-for-loosely-coupled-distributed-systems/)을 참고했다. 이 과제의 명령과 응답은 학습용 계약이며 두 시스템의 실제 API와는 다르다.

## 버그 신고

[12] 카탈로그 문서 생성 담당자가 보낸 신고다. “완료 알림을 모아서 처리한 뒤 생성 중인 상품군이 FREE로 표시됐다. 다른 상품군의 작업과 완료된 작업 목록은 예상대로였다. 다음 생성 요청도 받아들여져 같은 상품군의 생성 작업이 겹쳤다.” 다음은 담당자가 전달한 재현 입력이다.

```text
START spring apparel writer-a 15
START shoes footwear writer-b 40
TICK 9
COMPLETE shoes
START retry apparel writer-c 30
TICK 11
START summer apparel writer-b 25
COMPLETE spring
JOB summer
FLUSH 2
JOB spring
JOB shoes
STATUS footwear
STATUS apparel
START autumn apparel writer-c 12
```

```text
STARTED 1 15

TIME 9
QUEUED
BUSY writer-a 1 15
TIME 20
STARTED 3 45
QUEUED
RUNNING
FLUSHED 2
DONE
DONE
FREE
HELD writer-b 3 45
BUSY writer-b 3 45
```

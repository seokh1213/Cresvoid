# 두 번 시작되는 정산 작업

[1] 쇼핑 카탈로그 서비스는 날짜별 판매액을 모아 정산 원장에 반영한다. 여러 스케줄러가 하나의 JVM 안에 있는 같은 정산 작업 객체에 시작을 요청한다. 평소에는 하루 한 번 실행하지만 운영자가 완료 후 같은 날짜를 다시 실행할 수도 있다. 이 프로그램은 판매 등록, 시작 요청, 원장 반영을 명령으로 분리한 로컬 재현 도구다. 예시의 날짜와 금액은 재현을 위한 가상 자료다.

## 입력과 출력

[2] 표준 입력에서 명령을 한 줄씩 EOF까지 읽고 명령마다 결과 한 줄을 표준 출력에 쓴다. 빈 줄은 무시한다. 토큰은 공백으로 구분한다. 입력은 아래 형식을 지키며 날짜는 유효한 `YYYY-MM-DD` 형식이다. 판매액은 0 이상 1,000,000 이하의 정수이고 명령은 최대 500개다. 금액과 누적 합계의 단위는 원이다. 실행을 시작할 때 판매 내역과 원장은 비어 있고 작업은 대기 상태다.

[3] `SALE <날짜> <판매액>`은 해당 날짜에 판매 한 건을 추가하고 `SALE <날짜> OK`를 출력한다. 같은 날짜와 금액을 다시 등록해도 별개의 판매다. 판매 등록은 작업 상태와 무관하게 가능하다.

[4] `START <날짜> <요청 수>`는 1 이상 16 이하의 요청 수만큼 별도 스레드에서 같은 작업 객체에 해당 날짜의 시작을 요청한다. 모든 요청이 수락 또는 거부된 뒤 `START accepted=<수락 수> rejected=<거부 수>`를 출력한다. 요청 스레드 사이의 선후 관계는 보장하지 않는다. 재현 도구는 시험용 지점에서 요청들을 잠시 모으며 그 지점에 도달하지 않는 구현도 계속 실행되도록 대기 시간을 제한한다. 명령 사이에는 스레드가 남지 않는다.

## 정산 규칙

[5] 실행 중인 작업은 새 시작 요청을 모두 거부한다. 대기 상태에서 겹쳐 들어온 시작 요청 중 정확히 하나만 수락한다. 수락한 작업은 `FINISH` 또는 `ABORT`까지 실행 중 상태를 유지한다. 거부한 요청은 작업 상태, 대기 중인 정산 내역, 원장을 바꾸지 않는다. 이 제한은 날짜별이 아니라 작업 객체 전체에 적용한다.

[6] 시작을 수락하면 그 시점까지 등록된 대상 날짜의 판매 건수와 판매액 합계를 정산 내역으로 보관한다. 판매가 없어도 시작할 수 있다. 실행 중 추가된 판매는 이미 보관한 내역에 들어가지 않는다. 시작만으로 원장에 반영하지는 않는다.

[7] `FINISH`는 대기 중인 정산 내역을 원장에 반영하고 작업을 대기 상태로 돌린다. 내역 하나를 반영할 때 해당 날짜의 반영 횟수에 1을 더한다. 누적 판매 건수와 누적 판매액에는 내역의 건수와 합계를 각각 더한다. `FINISH batches=<반영한 내역 수> amount=<이번에 반영한 판매액 합계>`를 출력한다. 반영할 내역이 없으면 두 값은 모두 0이다. 반영한 내역은 다시 사용하지 않는다.

[8] `ABORT`는 대기 중인 정산 내역을 원장에 반영하지 않고 버린 뒤 작업을 대기 상태로 돌린다. `ABORT batches=<버린 내역 수>`를 출력한다. 대기 상태에서 실행하면 0을 출력한다. 판매 내역은 지우지 않는다.

[9] `FINISH` 또는 `ABORT` 후에는 같은 날짜도 다시 시작할 수 있다. 완료한 날짜를 중복 제거하는 기능은 없다. 다시 시작하면 그때까지 등록된 해당 날짜의 판매 전체를 새로 집계한다. 원장에는 각 완료 실행의 내역을 누적한다.

[10] `STATE`는 `STATE <IDLE 또는 RUNNING> pending=<대기 중인 내역 수>`를 출력한다. `REPORT <날짜>`는 `REPORT <날짜> runs=<반영 횟수> sales=<누적 판매 건수> amount=<누적 판매액>`을 출력한다. 아직 반영한 적 없는 날짜의 수치는 모두 0이다. 조회는 판매 내역, 작업 상태, 원장을 바꾸지 않는다.

## 버그 신고

[11] 정산 담당자의 신고다. “월말 정산을 확인하다가 한 날짜의 반영 횟수와 판매액이 함께 늘어난 기록을 발견했다. 판매 내역에는 두 건만 있어서 집계 결과와 맞지 않는다. 평소 사용하던 판매 등록과 조회를 포함해 아래 순서로 실행했다.”

```text
SALE 2026-10-30 12000
SALE 2026-10-31 7000
REPORT 2026-10-31
START 2026-10-30 1
FINISH
SALE 2026-10-31 5000
STATE
START 2026-10-31 2
FINISH
REPORT 2026-10-30
REPORT 2026-10-31
STATE
```

[12] 기대한 결과다. “10월 30일과 31일 모두 한 번씩 반영되고, 31일의 두 판매는 합계 12,000원으로 나와야 한다.”

```text
SALE 2026-10-30 OK
SALE 2026-10-31 OK
REPORT 2026-10-31 runs=0 sales=0 amount=0
START accepted=1 rejected=0
FINISH batches=1 amount=12000
SALE 2026-10-31 OK
STATE IDLE pending=0
START accepted=1 rejected=1
FINISH batches=1 amount=12000
REPORT 2026-10-30 runs=1 sales=1 amount=12000
REPORT 2026-10-31 runs=1 sales=2 amount=12000
STATE IDLE pending=0
```

[13] 실제 결과다. “10월 30일은 맞지만 31일은 반영 횟수 2회, 판매 4건, 합계 24,000원으로 나온다. 마지막 작업 상태는 대기 상태다.”

```text
SALE 2026-10-30 OK
SALE 2026-10-31 OK
REPORT 2026-10-31 runs=0 sales=0 amount=0
START accepted=1 rejected=0
FINISH batches=1 amount=12000
SALE 2026-10-31 OK
STATE IDLE pending=0
START accepted=2 rejected=0
FINISH batches=2 amount=24000
REPORT 2026-10-30 runs=1 sales=1 amount=12000
REPORT 2026-10-31 runs=2 sales=4 amount=24000
STATE IDLE pending=0
```

# 3단계: 취소와 정리

## 1. 개요

[1.1] 실행 중인 Job에 취소를 요청하고, 중단점에서 취소를 확인하며, 정리 코드와 완료 처리기를 실행하라. `YIELD`, `ENSURE`, `TIMEOUT`을 더한다. 1~2단계에서 허용한 입력과 출력은 그대로 유지한다.

## 2. 배경 개념

[2.1] 코루틴 취소는 스레드를 강제로 멈추지 않는다. Job이 취소 상태를 기록하고, 중단 함수나 명시적인 확인이 그 상태를 보고 `CancellationException`을 던진다. 계산만 오래 하는 본문은 확인 지점에 이르기 전까지 계속 실행할 수 있다. 이 단계의 `LOG`는 취소 확인 지점이 아니다.

[2.2] `finally`는 정상 완료와 취소 양쪽에서 실행된다. 취소된 Job에서 다시 중단하면 보통 즉시 취소 예외가 나오므로, 중단이 필요한 정리는 취소의 영향을 받지 않는 문맥에서 수행해야 한다. `SHIELD_DELAY`는 이 과제에서 `withContext(NonCancellable)`로 감싼 지연을 나타낸다.

[2.3] 완료 처리기는 Job이 최종 상태에 도달한 뒤 호출된다. `TIMEOUT`은 자식 작업의 실행 기한을 정한다. 기한이 지나면 자식과 그 후손의 취소를 요청하지만, 자식의 정리가 끝날 때까지 호출자를 풀어 주지 않는다.

## 3. 입출력 규칙

[3.1] 1~2단계의 입력과 출력 형식을 따른다. 새 사건은 `CANCELLED`, `TIMEOUT <자식 이름>`, `HANDLER <값> <DONE|CANCELLED>`이다. `STATE`는 2단계의 네 상태에 `CANCELLING`, `CANCELLED`를 더한다.

[3.2] `FINALLY`는 `TASK` 본문의 마지막 `RESULT` 뒤 또는 마지막 일반 명령 뒤에 한 번만 올 수 있다. `FINALLY`부터 `END` 앞까지가 정리 구간이다. 정리 구간에는 `LOG`, `DELAY`, `SHIELD_DELAY`만 쓸 수 있다. 정리 구간이 없는 작업은 1~2단계처럼 끝난다.

## 4. 취소와 명령 규칙

[4.1] `CANCEL <자식 이름>`은 현재 작업의 자식과 모든 후손에게 취소를 요청하고 기다리지 않고 돌아온다. 완료한 자식에는 영향이 없다. 한 작업과 후손을 함께 취소할 때는 그 작업을 먼저, 자식은 생성 순서의 깊이 우선으로 방문한다. 방문할 때마다 상태를 바꾸고 중단된 continuation을 준비 큐 끝에 넣거나 `NEW` 자식의 즉시 완료 사건을 낸다. 이미 취소를 요청했거나 최종 완료한 작업은 다시 처리하지 않는다. 취소 중인 부모가 새 자식을 `SPAWN`하면 만든 직후 그 자식에게도 취소를 요청한다. 요청을 받은 작업은 최종 완료 전까지 `CANCELLING`이며 `STATE`는 그 값을 출력한다. 본문과 정리, 남은 자식이 모두 끝나면 `CANCELLED` 사건을 낸다.

[4.2] 아직 시작하지 않은 `NEW` 자식을 취소하면 `CANCEL` 명령 안에서 즉시 `CANCELLED`를 낸 뒤 부모의 다음 명령으로 간다. 이 자식의 본문과 정리 구간은 실행하지 않는다. 시작을 요청해 큐에 있지만 `START`를 아직 내지 않은 자식은 큐에서 처음 실행될 때 `START`를 낸 뒤 곧바로 취소 정리로 들어간다. 이미 실행 중인 자식의 현재 계산은 끼어들어 중단하지 않는다.

[4.3] `DELAY`, `YIELD`, `JOIN`, `AWAIT`, `SCOPE`, `TIMEOUT`은 들어갈 때와 중단에서 돌아올 때 자신의 Job 취소를 확인한다. 취소됐으면 `CancellationException`을 던져 본문에서 남은 명령을 건너뛰고 정리 구간으로 간다. 이 명령에서 중단해 기다리는 작업에 취소를 요청하면 기존 타이머나 대기 등록을 무효화하고 재개 continuation을 그 시각 준비 큐 끝에 한 번 넣는다.

[4.4] `ENSURE`는 자신의 Job 취소를 즉시 확인하고 취소됐으면 [4.3]처럼 본문을 빠져나온다. 취소되지 않았으면 사건 없이 다음 명령으로 간다. `YIELD`는 취소되지 않았어도 현재 continuation을 준비 큐 끝에 넣어 반드시 한 번 중단한다. `LOG`, `STATE`, `CONTEXT`, `START`, `SPAWN`, `CANCEL`, `ON_COMPLETE`은 자체로 취소 확인을 하지 않는다.

[4.5] 자식을 취소하는 것만으로 부모는 취소되지 않는다. 취소된 자식의 `JOIN`은 자식 정리까지 기다린 뒤 정상적으로 돌아온다. 취소된 `ASYNC` 자식의 `AWAIT`는 `CancellationException`을 던진다. 이 예외를 잡지 않은 현재 작업은 자기 Job을 취소하고 [4.1] 순서로 다른 자식과 후손에게 취소를 요청한 뒤 자신의 정리로 간다. 그 작업은 `CANCELLED`로 끝나며, 취소 예외만으로는 조상 Job을 취소하지 않는다. 이미 완료한 자식에게 `AWAIT`하더라도 같은 규칙이다.

[4.6] `FINALLY` 구간은 정상 종료와 취소에서 한 번 실행한다. 정상 종료에서는 본문이 끝나자마자 정리를 실행한 뒤 남은 자식의 완료를 기다린다. 취소에서는 남은 본문을 건너뛰고 정리를 실행한 뒤 남은 자식을 기다린다. `LOG`는 취소 중에도 출력한다. 보통 `DELAY`는 취소 중에 들어가면 즉시 `CancellationException`을 던져 남은 정리 명령을 건너뛴다. `SHIELD_DELAY <밀리초>`는 취소 중에도 1단계 `DELAY`처럼 실제로 중단하고 가상 시간을 기다린 뒤 돌아와 다음 정리 명령을 실행한다. 정상 종료 때는 `DELAY`와 `SHIELD_DELAY`의 대기 순서가 같다.

[4.7] `ON_COMPLETE <값>`은 현재 작업의 완료 처리기를 등록하고 사건을 내지 않는다. 한 작업에 여러 번 적을 수 있다. 작업이 `DONE` 또는 `CANCELLED`를 낸 직후 그 작업의 처리기를 등록 순서로 `HANDLER <값> <상태>` 사건으로 낸다. 그 뒤에 `JOIN`·`AWAIT`·`SCOPE` 대기자와 부모의 완료를 처리한다. 등록 명령에 도달하기 전에 끝난 작업에는 처리기가 없다.

[4.8] `TIMEOUT <밀리초> <정의> <자식 이름>`은 `LAUNCH` 정의를 즉시 시작하는 `SCOPE`이며, 명령을 실행한 시각부터 지정 밀리초 뒤 기한 타이머를 먼저 등록한다. 밀리초는 1 이상 1,000,000,000 이하이다. 자식이 기한보다 먼저 `DONE` 또는 기한과 무관한 `CANCELLED`에 이르면 타이머를 무효화하고 정상적으로 돌아온다. 기한이 먼저 오면 자식을 취소하고 정리까지 기다린 다음 `TIMEOUT <자식 이름>` 사건을 낸 뒤 다음 명령으로 간다. 기한과 자식의 재개가 같으면 기한 타이머가 먼저 작동해 시간 초과가 이긴다.

[4.9] `TIMEOUT`을 기다리는 부모 자신이 취소되면 부모 취소가 우선한다. 자식에도 취소를 요청하고 정리를 기다린 뒤 부모 정리로 간다. 이때 `TIMEOUT` 사건은 내지 않는다. 부모가 취소 중에 있는 동안 자식이 늦게 정상 종료하더라도 부모는 `CANCELLED`로 끝난다.

[4.10] 이미 끝난 작업의 타이머와 대기 등록은 무효다. 같은 continuation을 타이머 만료와 취소 양쪽에서 두 번 재개하지 않는다. 취소 요청이나 타이머 만료로 생긴 준비 작업은 그 시각 준비 큐의 끝에 들어가며, 실행 중인 continuation을 끼어들어 실행하지 않는다.

## 5. 오류 규칙

[5.1] 1~2단계 오류 규칙을 따른다. `FINALLY`가 둘 이상이거나 정리 구간에 허용하지 않은 명령이 있으면 그 줄의 `FORMAT`이다. `SHIELD_DELAY`가 정리 구간 밖에 있거나 `TIMEOUT`의 시간·정의 종류가 틀려도 `FORMAT`이다. 없는 자식을 `CANCEL`에 적으면 `REFERENCE`다.

[5.2] `TIMEOUT`도 형제 사이에 고유한 자식 이름을 쓰고 정의 참조 순환 검사에 포함한다. 2단계 [5.2]의 지연 시작 의무는 이 단계부터 본문에 적힌 `CANCEL`로 끝낸 자식도 충족한다. 부모의 취소가 실행 중 자식에게 자동으로 전파되더라도 입력 검증에서 이 의무를 충족한 것으로 보지 않는다. `FINALLY`의 `DELAY`와 `SHIELD_DELAY`는 1단계 [3.4]의 정수 범위를 따른다. 실행 중 취소는 입력 형식 오류가 아니며 `ERR`을 출력하지 않는다.

## 6. 예시

[6.1] 자식이 중단된 뒤 취소된다. 취소된 Job의 정리에서 `SHIELD_DELAY`는 가상 시간을 기다리고, 완료 처리기는 최종 사건 뒤에 실행된다.

```text
> TASK child LAUNCH
> ON_COMPLETE close
> DELAY 5
> LOG late
> FINALLY
> LOG cleanup
> SHIELD_DELAY 2
> LOG cleaned
> END
> TASK parent LAUNCH
> SPAWN child c
> DELAY 0
> CANCEL c
> JOIN c
> LOG after
> END
> ROOT parent r
> RUN
0 r START
0 r.c START
0 r.c LOG cleanup
2 r.c LOG cleaned
2 r.c CANCELLED
2 r.c HANDLER close CANCELLED
2 r LOG after
2 r DONE
```

[6.2] `TIMEOUT`의 기한과 자식의 `DELAY` 재개가 같은 시각이면 기한이 먼저 작동한다.

```text
> TASK slow LAUNCH
> DELAY 3
> LOG late
> FINALLY
> LOG cleanup
> END
> TASK parent LAUNCH
> TIMEOUT 3 slow s
> LOG after
> END
> ROOT parent r
> RUN
0 r START
0 r.s START
3 r.s LOG cleanup
3 r.s CANCELLED
3 r TIMEOUT s
3 r LOG after
3 r DONE
```

## 7. 검사 방식

[7.1] 1~2단계의 입력 방식과 출력 비교 방식을 따르고 이전 테스트를 먼저 실행한다. 고정 테스트는 취소 전후 `STATE`, 시작 전 취소, 취소 뒤 `LOG`와 `ENSURE`, 기다리던 `DELAY`의 무효화, `YIELD`, 정리의 일반·취소 불가 지연, 완료 처리기 순서, 기한 경계를 확인한다.

[7.2] 대규모 입력은 약 10,000개 작업과 30,000개 명령에 취소와 타이머 경합을 섞는다. 한 테스트 제한 시간은 15초이고 모범 풀이 목표는 3초 이하다. 타이머 취소와 대기자 제거는 작업 수 전체에 비례하면 안 된다.

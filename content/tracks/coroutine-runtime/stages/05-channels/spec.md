# 5단계: Channel과 Mutex의 대기 순서

## 1. 개요

[1.1] 단일 스레드 실행기에 랑데부·버퍼 Channel과 Mutex를 더하라. 보내기, 받기, 잠금 획득은 필요할 때 실제로 중단하고 상대 작업이나 잠금 해제가 일어나면 continuation을 재개해야 한다. 1~4단계에서 허용한 입력의 출력은 그대로다.

## 2. 배경 개념

[2.1] 용량 0인 Channel은 보내는 쪽과 받는 쪽이 만날 때 값이 전달되는 랑데부 채널이다. 버퍼가 있는 Channel은 빈 자리에 값을 보관하므로 보내는 쪽이 먼저 진행할 수 있다. 버퍼가 차면 보내는 쪽이, 값이 없으면 받는 쪽이 중단된다. 닫힌 채널의 버퍼에 남은 값은 계속 받을 수 있지만 새 값은 보낼 수 없다.

[2.2] Mutex는 한 시각에 한 작업만 소유하는 잠금이다. 기다리는 작업들의 순서와 취소된 대기자를 언제 제거하는지가 재현 가능한 실행에 영향을 준다. 이 단계의 Mutex는 단일 스레드에서도 중단하는 작업 사이의 순서를 정하는 수단이다.

## 3. 입출력 규칙

[3.1] `TASK` 정의를 모두 적은 뒤 `ROOT` 선언 전에 `CHANNEL <이름> <용량>`과 `MUTEX <이름>`을 선언할 수 있다. 두 종류의 선언은 섞어 적어도 된다. 이름은 1단계 [3.2] 형식이며 각 종류 안에서 고유하다. 용량은 0 이상 10,000 이하인 정수이고 0은 랑데부다. 입력의 유일한 `RUN`은 빈 버퍼, 열린 채널, 비어 있는 잠금 상태에서 시작한다.

[3.2] 성공한 `RECV`는 현재 작업 경로에서 `RECEIVE <채널 이름> <값>` 사건을 낸다. `SEND`, `CLOSE`, `LOCK`, `UNLOCK`은 성공할 때 사건을 내지 않는다. 런타임 실패 코드는 `CHANNEL_CLOSED`, `MUTEX_REENTRANT`, `MUTEX_OWNER`이고 4단계의 일반 실패처럼 전파된다.

[3.3] 준비 큐와 타이머가 모두 비었는데 완료하지 않은 작업이 남아 있으면 기존 사건 뒤에 `DEADLOCK` 한 줄을 출력하고 실행을 끝낸다. 이 줄은 작업 사건이 아니므로 시각과 경로를 붙이지 않는다. 닫히지 않은 채널을 기다리거나 잠금을 풀지 못한 경우가 여기에 해당한다.

## 4. Channel 명령

[4.1] `SEND <채널 이름> <값>`은 열린 채널에 값을 보낸다. 대기 중인 수신자가 있으면 가장 먼저 기다린 수신자에게 값을 예약하고 그 continuation을 준비 큐 끝에 넣는다. 보내는 쪽은 중단하지 않고 다음 명령으로 간다. 수신자가 없고 버퍼에 자리가 있으면 값을 버퍼 끝에 넣고 계속한다. 두 경우 모두 아니면 보내는 쪽을 보낸 순서대로 대기시킨다.

[4.2] `RECV <채널 이름>`은 버퍼에 값이 있으면 맨 앞 값을 꺼낸다. 버퍼가 비었고 대기 송신자가 있으면 가장 먼저 기다린 송신자의 값을 꺼내며 송신자의 continuation을 준비 큐 끝에 넣는다. 값을 얻으면 `RECEIVE` 사건을 낸 뒤 계속한다. 열린 채널에 값과 송신자가 없으면 수신자를 대기시킨다.

[4.3] 버퍼에서 값을 꺼내 자리가 생기면 대기 송신자 가운데 가장 앞의 값을 곧바로 버퍼 끝에 넣고 그 송신자의 continuation을 준비 큐 끝에 넣는다. 따라서 뒤의 송신자가 앞의 송신자를 앞지르지 않는다. 랑데부 채널에는 버퍼를 만들지 않는다. 송신자가 먼저 기다린 경우 수신자는 같은 continuation에서 값을 출력하고, 송신자는 이후 준비 큐에서 재개한다.

[4.4] `CLOSE <채널 이름>`은 열린 채널을 닫는다. 처음 닫을 때 대기 송신자와 값이 예약되지 않은 대기 수신자를 각자 등록 순서대로 실패 재개 대상으로 준비 큐에 넣는다. 닫힌 뒤 `SEND`는 즉시 `CHANNEL_CLOSED`로 실패한다. `RECV`는 버퍼의 값을 끝까지 꺼낸 뒤, 빈 상태에서 `CHANNEL_CLOSED`로 실패한다. 이미 닫힌 채널의 `CLOSE`는 아무 일도 하지 않는다.

[4.5] 아직 상대와 짝지어지지 않은 `SEND`·`RECV` 대기자는 자신의 Job이 취소되면 채널 대기열에서 빠진다. 수신자에게 값이 예약된 뒤 그 수신자가 재개 전에 취소되면 값은 버리고, 이미 완료한 송신을 되돌리지 않는다. 취소된 대기자에게 새 값이나 버퍼 자리를 배정하지 않는다. 같은 시각의 전송·취소·닫힘은 1단계 준비 큐 순서로 판정한다.

## 5. Mutex 명령

[5.1] `LOCK <잠금 이름>`은 소유자가 없으면 현재 작업이 즉시 소유한다. 다른 소유자가 있으면 요청한 순서대로 대기한다. 소유자가 현재 작업 자신이면 중단하지 않고 `MUTEX_REENTRANT`로 실패한다.

[5.2] `UNLOCK <잠금 이름>`은 현재 작업이 소유할 때만 성공한다. 소유하지 않으면 `MUTEX_OWNER`로 실패한다. 성공하면 가장 먼저 기다린 활성 작업에게 그 시각에 소유권을 넘기고 continuation을 준비 큐 끝에 넣는다. 기다리는 작업이 없으면 소유자를 비운다. 소유권을 받은 작업의 `LOCK`은 재개 때 한 번만 완료한다.

[5.3] 취소된 `LOCK` 대기자는 대기열에서 빠진다. `UNLOCK`이 대기자에게 소유권을 넘겼지만 그 대기자의 `LOCK` continuation이 재개되기 전에 취소됐다면, 예약된 소유권을 즉시 거두어 다음 활성 대기자에게 넘기고 그 continuation을 준비 큐 끝에 넣는다. 그다음 취소된 대기자의 재개를 준비 큐 끝에 한 번 넣어 취소 정리로 보내며 잠금을 획득한 것으로 처리하지 않는다. 따라서 두 작업이 모두 같은 시각에 재개할 수 있으면 새 소유자가 먼저 실행한다. 다음 대기자가 없으면 소유자를 비운다. `LOCK`이 재개돼 완료된 뒤에는 소유 작업의 완료나 취소만으로 Mutex가 자동으로 풀리지 않는다. 정리 구간에서 `UNLOCK`을 쓸 수 있으며, 취소된 작업도 자신이 가진 잠금을 풀 수 있다. 소유자가 잠금을 풀지 않아 기다리는 작업이 남으면 [3.3]의 `DEADLOCK`을 낸다.

[5.4] `SEND`, `RECV`, `LOCK`은 3단계의 취소 확인 중단점이다. 들어갈 때와 기다리다 재개할 때 자신의 취소를 확인한다. `CLOSE`와 `UNLOCK`은 중단하지 않으며 자체로 취소를 확인하지 않는다. 정리 구간에는 `UNLOCK`, `CLOSE`를 쓸 수 있고, 실패하면 4단계의 정리 중 실패 규칙을 따른다.

## 6. 오류 규칙

[6.1] 앞 단계의 입력 형식 오류를 따른다. 중복 `CHANNEL` 또는 중복 `MUTEX` 선언은 뒤 선언 줄의 `DUPLICATE`다. 선언하지 않은 채널이나 잠금을 명령에서 참조하면 그 명령 줄의 `UNKNOWN`이다. 용량이나 명령 인자가 잘못되면 `FORMAT`이다.

[6.2] 채널·잠금 선언이 `TASK` 안이나 첫 `ROOT` 뒤에 있으면 `FORMAT`이다. `SEND` 값은 1단계 [3.2] 형식이다. 열린 채널에서의 대기, 닫힌 채널 사용, 잠금 소유 오류는 실행 결과이고 입력 형식 오류가 아니다.

## 7. 예시

[7.1] 랑데부 채널에서 송신자는 수신자가 값을 받을 때까지 멈춘다. 수신자가 송신자를 깨워도 송신자는 준비 큐를 거쳐 재개한다.

```text
> TASK producer LAUNCH
> LOG before
> SEND ch red
> LOG after
> END
> TASK consumer LAUNCH
> DELAY 0
> RECV ch
> LOG seen
> END
> CHANNEL ch 0
> ROOT producer p
> ROOT consumer c
> RUN
0 p START
0 p LOG before
0 c START
0 c RECEIVE ch red
0 c LOG seen
0 c DONE
0 p LOG after
0 p DONE
```

[7.2] 닫기 전에 버퍼에 넣은 값은 받을 수 있다. 그 뒤 빈 채널을 다시 받으면 일반 실패가 된다.

```text
> TASK producer LAUNCH
> SEND ch blue
> CLOSE ch
> END
> TASK consumer LAUNCH
> DELAY 1
> RECV ch
> RECV ch
> END
> CHANNEL ch 1
> ROOT producer p
> ROOT consumer c
> RUN
0 p START
0 p DONE
0 c START
1 c RECEIVE ch blue
1 c FAILED CHANNEL_CLOSED
1 c UNHANDLED CHANNEL_CLOSED
```

[7.3] 잠금 해제는 대기자에게 소유권을 넘기지만 현재 작업의 남은 본문을 끼어들지 않는다.

```text
> TASK owner LAUNCH
> LOCK m
> LOG got
> DELAY 2
> UNLOCK m
> END
> TASK waiter LAUNCH
> LOCK m
> LOG got
> UNLOCK m
> END
> MUTEX m
> ROOT owner a
> ROOT waiter b
> RUN
0 a START
0 a LOG got
0 b START
2 a DONE
2 b LOG got
2 b DONE
```

## 8. 검사 방식

[8.1] 앞 단계와 같은 입력·출력 비교 방식을 따르고 1~4단계 테스트를 먼저 다시 실행한다. 고정 테스트는 랑데부와 버퍼 경계, FIFO 송수신, 닫힘 뒤 버퍼 비우기, 취소된 대기자 제거, 소유권 이전, 정리에서의 잠금 해제, 교착 상태를 확인한다.

[8.2] 대규모 입력은 약 10,000개 작업과 30,000개 명령에 채널과 잠금 대기를 섞는다. 한 테스트 제한 시간은 15초이고 모범 풀이 목표는 3초 이하다. 대기열에서 매번 모든 작업을 찾지 않도록 설계해야 한다.

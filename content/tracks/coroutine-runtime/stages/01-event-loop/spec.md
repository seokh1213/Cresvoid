# 1단계: 가상 시간 이벤트 루프

## 1. 개요

[1.1] Kotlin 표준 라이브러리의 `Continuation`, `startCoroutine`, `suspendCoroutine`만으로 단일 스레드 코루틴 실행기를 만들어라. 입력으로 받은 작업 본문을 실제 `suspend` 함수로 실행하고, 중단된 계산을 준비 큐나 타이머에서 꺼내 재개하라. 사건 목록을 미리 계산하는 별도의 시뮬레이터는 이 과제의 구현 대상이 아니다.

[1.2] 이 단계는 작업의 시작, `DELAY`, 자식 시작, `AWAIT`, 완료를 다룬다. 모든 시각은 가상 밀리초이며 실제 시간, 스레드 풀, `kotlinx.coroutines`를 쓰지 않는다. 뒤 단계는 명령을 추가하지만 이 단계에서 허용한 입력의 출력은 바꾸지 않는다.

[1.3] 시작 코드의 `VirtualRuntime`, `RuntimeScope`, `RuntimeJob`, `RuntimeDeferred` 공개 계약을 유지하라. `VirtualRuntime.run`은 `suspend` 본문을 `startCoroutine`으로 시작해 준비 큐를 비울 때까지 구동하고, `RuntimeScope.delay`와 결과 대기는 `suspendCoroutine`으로 중단·재개한다. 2~6단계에서는 같은 계약에 필요한 메서드를 구현한다. 입력 해석과 사건 기록의 내부 구조는 자유지만 작업을 단순한 명령별 사건 계산으로 치환하지 않는다.

## 2. 배경 개념

[2.1] `suspend` 함수는 호출 스택을 막은 채 기다리는 함수가 아니다. 필요한 순간 현재 계산의 나머지를 `Continuation`에 맡기고 호출자에게 돌아간다. 실행기가 그 continuation을 나중에 재개하면 중단 지점 다음 문장부터 실행된다. `startCoroutine`은 중단 가능한 람다를 처음 시작하고, `suspendCoroutine`은 중단할 지점을 만든다.

[2.2] 준비 큐에는 지금 실행할 수 있는 continuation이 들어간다. 타이머에는 미래 시각에 준비 큐로 옮길 continuation이 들어간다. 가상 시계를 쓰면 실제로 기다리지 않고도 같은 입력에 같은 실행 순서를 얻을 수 있다. 이 실행기에서 디스패치는 continuation을 즉시 호출하는 대신 준비 큐의 끝에 넣는 동작이다.

[2.3] `LAUNCH` 작업은 반환값이 없는 자식이고 `ASYNC` 작업은 결과를 갖는 자식이다. `AWAIT`는 결과가 준비될 때까지 현재 코루틴을 중단한다. 부모의 본문이 끝나도 자식이 남아 있으면 부모의 완료를 미루는 규칙은 구조적 동시성의 가장 작은 형태다.

## 3. 입출력 규칙

[3.1] 표준 입력의 UTF-8 줄을 읽는다. 앞뒤 U+0020 공백을 버리고 공백만 있는 줄은 건너뛴다. 남은 줄의 인자는 하나 이상의 U+0020으로 나눈다. 탭과 다른 공백 문자는 허용하지 않는다. 명령어와 이름은 대소문자를 구분한다.

[3.2] 이름과 `LOG`·`RESULT` 값은 `^[a-z][a-z0-9_-]{0,31}$`에 맞는 한 토큰이다. 이름은 정의 이름, 루트 인스턴스 이름, 형제 사이의 자식 인스턴스 이름에 각각 적용한다. 같은 정의를 여러 번 실행할 수 있으며, 자식의 출력 이름은 `부모.자식`처럼 점으로 이은 인스턴스 경로다.

[3.3] 입력은 `TASK` 정의를 하나 이상 적고 `ROOT` 선언을 하나 이상 적은 뒤 마지막에 `RUN` 한 줄을 적는다. `TASK <정의> <LAUNCH|ASYNC>`부터 `END`까지가 한 본문이다. `LAUNCH` 본문은 비어 있어도 된다. 모든 `TASK`를 닫은 뒤 `ROOT <정의> <인스턴스>`를 적으며 루트는 `LAUNCH` 정의만 참조한다. `RUN` 뒤에는 빈 줄밖에 올 수 없다. 입력 전체를 검증한 다음 시각 0에서 모든 루트를 선언 순서로 한꺼번에 시작한다.

[3.4] 시각은 0 이상 1,000,000,000,000 이하이다. `DELAY` 인자는 0 이상 1,000,000,000 이하의 10진 정수이고 `0` 외에 앞에 0을 붙이지 않는다. 모든 작업과 타이머의 실행 시각도 상한을 넘지 않아야 한다. 검사 입력은 상한을 넘는 실행을 만들지 않는다.

[3.5] 각 사건은 `<시각> <인스턴스 경로> <사건>` 한 줄로 출력한다. 사건은 `START`, `LOG <값>`, `VALUE <자식 이름> <값>`, `DONE`이다. 줄 끝은 LF이며 출력은 사건이 실제 일어난 순서다. `RUN` 전에는 출력하지 않는다.

## 4. 명령과 실행 순서

[4.1] `TASK` 본문은 위에서 아래로 실행한다. `LOG <값>`은 현재 시각의 `LOG` 사건을 낸다. `DELAY <밀리초>`는 반드시 한 번 중단한다. 시각이 같은 `DELAY 0`도 현재 continuation을 준비 큐 끝에 보낸 뒤 다음 문장을 실행한다.

[4.2] `SPAWN <정의> <자식 이름>`은 현재 작업의 자식을 만들고 시작 continuation을 준비 큐 끝에 넣는다. 부모는 이 명령 뒤를 계속 실행한다. 자식은 자신의 첫 continuation이 큐에서 나올 때 `START`를 낸다. 자식의 종류는 참조한 `TASK` 정의에 적힌다.

[4.3] `ASYNC` 본문에는 `RESULT <값>`을 정확히 한 번, 마지막 실행 명령으로 둔다. 이 명령은 결과를 저장하고 사건을 내지 않는다. `LAUNCH` 본문에는 `RESULT`를 둘 수 없다. `AWAIT <자식 이름>`은 현재 작업의 `ASYNC` 자식을 기다린다. 이미 완료됐으면 중단 없이, 아직 끝나지 않았으면 완료 후 준비 큐에서 재개해 `VALUE <자식 이름> <결과>`를 낸다. 같은 자식을 여러 번 기다려도 같은 결과를 매번 낸다.

[4.4] 작업은 본문의 마지막 명령 뒤에 아직 완료하지 않은 자식이 있으면 기다린다. 마지막 자식이 완료한 시각에 `DONE`을 낸다. 자식이 없으면 본문 마지막 명령을 실행한 시각에 `DONE`을 낸다. 빈 `LAUNCH` 본문은 `START` 직후 같은 시각에 `DONE`을 낸다. 자식의 `DONE`은 부모의 `DONE`보다 앞에 나온다. 부모를 기다리는 continuation은 부모의 `DONE` 뒤에 준비 큐 끝으로 들어간다.

[4.5] `ROOT`로 선언한 루트의 시작 continuation은 선언 순서로 준비 큐에 들어간다. 이벤트 루프는 준비 큐 맨 앞의 continuation 하나를 꺼내 그 계산이 중단하거나 끝날 때까지 실행한다. 준비 큐가 비었으면 가장 이른 타이머 시각으로 시계를 옮겨 그 시각의 타이머를 등록 순서로 준비 큐에 넣는다. 시각이 같은 모든 타이머는 준비 큐에 들어간 순서를 지킨다.

[4.6] 재개와 작업 시작은 항상 준비 큐를 거친다. `SPAWN`한 자식, 완료를 기다리다 풀린 부모, `AWAIT`에서 풀린 작업은 이미 실행 중인 계산을 끼어들어 실행하지 않는다. 한 continuation이 즉시 다시 중단하면 그 다음 continuation을 큐에서 꺼낸다.

[4.7] 작업 정의 간의 `SPAWN` 참조는 순환하지 않아야 한다. 동일 정의를 다른 루트나 서로 다른 부모가 써도 각각 독립한 인스턴스와 결과를 갖는다. 형제 자식 이름은 그 부모의 본문에서 고유해야 한다.

## 5. 오류 규칙

[5.1] 실행 전에 전체 입력을 검증한다. 오류가 있으면 사건 대신 `ERR <원본 줄 번호> <코드>` 한 줄만 출력하고 종료 코드 0으로 끝낸다. 원본 줄 번호는 빈 줄도 세며 1부터 시작한다. `RUN`이 없으면 마지막 입력 줄 다음 번호를 쓴다.

[5.2] 명령, 인자 개수, 토큰 형식, 정수 범위, 정의·루트의 배치, `RESULT` 위치가 틀리거나 루트가 `ASYNC` 정의를 참조하면 `FORMAT`이다. 같은 정의·루트 이름이나 형제 자식 이름이 두 번 나오면 `DUPLICATE`다. 없는 정의를 참조하면 `UNKNOWN`이고, 아직 만들지 않은 자식을 `AWAIT`하거나 `LAUNCH` 자식을 기다리면 `REFERENCE`다. 현재 단계에서 허용된 작업 정의 참조에 순환이 있으면 순환을 닫은 참조 줄의 `CYCLE`이다.

[5.3] 여러 오류가 있으면 원본 줄 번호가 가장 작은 오류를 보고한다. 같은 줄에서 둘 이상 판정될 때는 `FORMAT`, `DUPLICATE`, `UNKNOWN`, `REFERENCE`, `CYCLE` 순서다. 참조할 정의가 뒤에 나와도 허용하며, 해당 줄에서 참조 오류를 판정한다. 순환 검사는 모든 정의를 읽은 뒤 현재 단계에서 허용된 작업 정의 참조 명령을 종류와 관계없이 원본 줄 순서로 하나씩 더한다. 그 참조를 더할 때 처음 순환이 생기면 그 줄을 `CYCLE`로 판정한다. 정상 입력의 실행 중에는 사용자에게 보이는 오류가 나지 않는다.

## 6. 예시

[6.1] 부모는 자식을 큐에 넣고 자기 본문을 계속한다. 두 `DELAY 2`가 같은 시각을 가리키면 등록 순서대로 재개하며, 부모의 완료는 자식 뒤로 밀린다.

```text
> TASK child LAUNCH
> LOG child
> DELAY 2
> LOG awake
> END
> TASK parent LAUNCH
> LOG begin
> SPAWN child c
> LOG after
> DELAY 2
> LOG resumed
> END
> ROOT parent r
> RUN
0 r START
0 r LOG begin
0 r LOG after
0 r.c START
0 r.c LOG child
2 r LOG resumed
2 r.c LOG awake
2 r.c DONE
2 r DONE
```

[6.2] `AWAIT`는 자식의 완료 뒤에 다시 큐를 거친다. `DELAY 0`도 다음 문장을 즉시 호출하지 않는다.

```text
> TASK answer ASYNC
> DELAY 0
> RESULT yes
> END
> TASK parent LAUNCH
> SPAWN answer a
> AWAIT a
> LOG after
> END
> ROOT parent r
> RUN
0 r START
0 r.a START
0 r.a DONE
0 r VALUE a yes
0 r LOG after
0 r DONE
```

## 7. 검사 방식

[7.1] 표준 입력에는 정의와 루트를 모아 놓고 마지막 `RUN`으로 실행한다. 고정 테스트는 준비 큐 순서, 같은 시각의 타이머, 0 지연, 여러 루트, 부모 완료 대기, 이미 끝난 자식과 아직 실행 중인 자식의 `AWAIT`, 오류 줄 번호를 확인한다.

[7.2] 표준 출력은 줄 끝 공백과 끝의 빈 줄을 제거한 뒤 줄 수와 각 줄을 글자 그대로 비교한다. 한 테스트의 제한 시간은 15초다. 대규모 생성 입력은 약 10,000개 작업 인스턴스와 약 30,000개 본문 명령을 포함하며, 모범 풀이의 목표 시간은 3초 이하다. 모든 작업을 시각마다 전수 검사하는 구현은 이 규모에서 느려진다.

# 예약 요청 ID와 중복 요청

## 1. 개요

[1.1] 1단계의 예약·취소에 요청 ID를 붙여 재전송을 처리한다. 같은 ID와 같은 내용은 처음 응답을 그대로 돌려주고 같은 ID에 다른 내용은 거절한다. 앞 단계 명령과 출력은 유지한다. 이 단계는 새 REQUEST 명령만 추가하며 목표 풀이 시간은 숙련 개발자 기준 1~3시간이다.

## 2. 배경 개념

[2.1] 요청을 보낸 쪽은 응답을 받지 못했을 때 서버가 작업을 끝냈는지 알기 어렵다. 예약 버튼을 다시 누르면 첫 요청이 이미 차지한 재고를 한 번 더 차지할 수 있다. 요청 ID는 하나의 의도를 식별하고 예약 ID는 생성된 예약을 식별한다. 둘은 역할과 이름 공간이 다르다.

[2.2] 같은 요청을 다시 받아도 효과가 늘어나지 않는 성질을 멱등성이라 한다. 이 과제는 최초 응답을 저장해 재전송에도 같은 응답을 제공한다. 예약 뒤에 취소가 일어나 현재 상태가 달라져도 최초 예약 요청의 응답은 바뀌지 않는다. 취소도 중복 실행하면 수량을 두 번 회수하므로 예약과 취소를 같은 요청 ID 규칙으로 보호한다.

[2.3] 요청 ID가 같아도 내용이 다르면 재전송인지 새 의도인지 판단할 수 없다. 따라서 저장된 내용과 새 내용을 비교하고 다르면 충돌로 거절한다. 성공뿐 아니라 재고 부족 같은 실패 응답도 저장하면, 재고가 늘어난 뒤의 같은 요청도 최초 실패를 반환한다. 새 의도로 다시 시도하려면 새 요청 ID가 필요하다.

[2.4] 결과 저장과 파라미터 비교라는 개념은 [Stripe의 멱등 요청 문서](https://docs.stripe.com/api/idempotent_requests)에서도 확인할 수 있다. 이 과제의 유효 기간, 오류 저장 범위와 명령 규칙은 아래에서 독자적으로 정한다. 실제 외부 서비스의 API를 구현하는 과제는 아니다.

## 3. 입출력 규칙

[3.1] 1단계의 입력·출력 형식, 식별자와 숫자·날짜 규칙, 명령 수와 날짜 차이 합의 상한을 그대로 적용한다. 요청 ID도 1단계 식별자 문법을 따른다. 요청 ID는 객실 유형·예약 ID와 독립된 이름 공간에 두며 예약 요청과 취소 요청은 하나의 요청 ID 이름 공간을 공유한다.

[3.2] 새 입력 형식은 `REQUEST <requestId> BOOK <reservationId> <type> <from> <to> <quantity>`와 `REQUEST <requestId> CANCEL <reservationId> <from> <to> <quantity>` 두 가지다. 중첩 REQUEST나 다른 명령은 감싸지 않는다. 응답은 감싼 BOOK 또는 CANCEL을 직접 실행했을 때의 응답 한 줄과 같으며 요청 ID나 중복 표시를 덧붙이지 않는다.

## 4. 명령 규칙

[4.1] REQUEST를 받으면 바깥 요청 ID와 감싼 명령의 모든 토큰 형식을 검사하고 이어서 1단계의 기본값 범위를 검사한다. ERROR INPUT이나 ERROR RANGE가 나면 요청 기록을 만들거나 비교하지 않고 즉시 그 오류를 출력한다. 이 검사는 이미 기록된 요청 ID에도 먼저 적용한다.

[4.2] 기본 검사를 통과한 요청의 내용은 동작 종류 BOOK 또는 CANCEL과 그 명령의 전체 인자 값이다. 요청 ID 자체는 내용에 포함하지 않는다. 식별자는 대소문자를 구분하고 날짜는 날짜 값으로, 수량은 정수 값으로 비교한다. 토큰 사이 공백과 수량의 선행 0은 내용 차이가 아니다. BOOK과 CANCEL은 예약 ID나 구간이 같아도 서로 다른 내용이다.

[4.3] 아직 기록하지 않은 요청 ID이면 감싼 명령을 1단계 규칙대로 한 번 실행하고 내용과 최종 응답 한 줄을 함께 기록한다. OK 응답뿐 아니라 ERROR TYPE_NOT_FOUND, ERROR RESERVATION_EXISTS, ERROR FULL, ERROR RESERVATION_NOT_FOUND, ERROR PERIOD, ERROR CANCEL_QUANTITY도 기록한다. 실행과 결과 기록 사이에 다른 입력 명령이 끼어들지 않는다.

[4.4] 기록된 요청 ID와 내용이 같으면 저장한 응답을 그대로 출력하고 감싼 명령은 실행하지 않는다. 재고와 예약 이력, 요청 기록을 바꾸지 않는다. 내용이 다르면 ERROR REQUEST_CONFLICT를 출력하고 최초 기록을 유지한다. 이 비교는 현재 유형·예약의 존재 여부와 재고·취소 가능 수량을 검사하기 전에 한다.

[4.5] 요청 기록은 해당 프로세스가 끝날 때까지 유지한다. 만료·삭제·덮어쓰기는 없다. 실패 응답을 저장해도 예약 ID를 사용한 것으로 만들지는 않는다. 감싸지 않은 BOOK과 CANCEL은 1단계와 똑같이 동작하며 요청 기록을 읽거나 쓰지 않는다.

## 5. 오류 규칙

[5.1] 새 오류는 ERROR REQUEST_CONFLICT뿐이다. REQUEST의 형식, 기본 범위, 기존 기록 비교, 감싼 명령의 상태 검사 순서로 판정한다. 예를 들어 기록된 ID로 수량 0을 보내면 ERROR RANGE이고 정상 범위의 다른 수량을 보내면 ERROR REQUEST_CONFLICT이다. 충돌 응답은 새 결과로 저장하지 않는다.

[5.2] 기본 검사를 통과한 뒤 발생한 상태 오류는 모두 최초 응답으로 남는다. 존재하지 않는 유형에 대한 예약 요청을 나중에 같은 내용으로 재전송하면, 그사이 TYPE으로 유형을 만들었어도 ERROR TYPE_NOT_FOUND를 반환한다. 같은 내용의 실패 재전송으로 현재 상태를 다시 검사하지 않는다.

## 6. 예시

[6.1] 다음 예시에서 k1의 재전송은 취소 전 응답을 돌려줄 뿐 재고를 다시 차지하지 않는다. k2는 예약과 취소가 공유하는 이름 공간에 있으므로 BOOK에 다시 쓰면 충돌한다.

```text
입력
TYPE Suite 0
STOCK Suite 2030-06-01 2030-06-03 2
REQUEST k1 BOOK r1 Suite 2030-06-01 2030-06-03 02
REQUEST k1 BOOK r1 Suite 2030-06-01 2030-06-03 2
REQUEST k2 CANCEL r1 2030-06-02 2030-06-03 1
REQUEST k2 CANCEL r1 2030-06-02 2030-06-03 1
REQUEST k1 BOOK r1 Suite 2030-06-01 2030-06-03 2
STATUS r1
REQUEST k2 BOOK r2 Suite 2030-06-02 2030-06-03 1
REQUEST k1 BOOK r1 Suite 2030-06-01 2030-06-03 0
출력
OK TYPE Suite
OK STOCK Suite
OK BOOK r1
OK BOOK r1
OK CANCEL r1
OK CANCEL r1
OK BOOK r1
STATUS r1 Suite 2030-06-01 2030-06-03 2,1
ERROR REQUEST_CONFLICT
ERROR RANGE
```

[6.2] 다음 예시에서 kFail의 최초 재고 부족은 재고 설정 뒤에도 유지된다. 이 실패는 예약 ID r의 사용 이력을 만들지 않는다. kBad의 범위 오류는 요청 ID를 차지하지 않으므로 올바른 취소 요청에 같은 ID를 사용할 수 있다.

```text
입력
TYPE Twin 0
REQUEST kFail BOOK r Twin 2031-01-01 2031-01-02 1
STOCK Twin 2031-01-01 2031-01-02 2
REQUEST kFail BOOK r Twin 2031-01-01 2031-01-02 1
REQUEST kNew BOOK r Twin 2031-01-01 2031-01-02 1
REQUEST kBad CANCEL r 2031-01-01 2031-01-02 0
REQUEST kBad CANCEL r 2031-01-01 2031-01-02 1
STATUS r
REQUEST kNew BOOK r Twin 2031-01-01 2031-01-02 1
STATUS r
출력
OK TYPE Twin
ERROR FULL
OK STOCK Twin
ERROR FULL
OK BOOK r
ERROR RANGE
OK CANCEL r
STATUS r Twin 2031-01-01 2031-01-02 0
OK BOOK r
STATUS r Twin 2031-01-01 2031-01-02 0
```

## 7. 검사 방식

[7.1] 1단계의 테스트를 누적 실행하고 새 입력에서도 표준 입력과 EOF를 사용한다. 출력 비교는 1단계와 같고 종료 코드는 0이어야 한다. 제한 시간은 컴파일을 제외하고 프로세스 한 번당 20초다. 한 입력 최대 3,000줄, 유형 최대 100개, 모든 구간 명령의 날짜 차이 합 최대 100,000일이라는 범위도 유지한다. REQUEST 한 줄의 구간 길이는 감싼 명령의 날짜 차이로 센다.

[7.2] 성공·실패 재전송, 부분 취소 뒤의 재전송, 서로 다른 동작의 ID 충돌, 범위 오류를 고친 재요청, 숫자 표기의 정규화와 감싸지 않은 명령의 회귀를 검사한다. 별도의 성능 강제용 대규모 테스트는 두지 않는다. 가장 큰 기능 검사도 [7.1]의 범위 안에서 여러 요청 ID의 최초 응답이 이후 상태에 영향을 받지 않는지 확인한다.

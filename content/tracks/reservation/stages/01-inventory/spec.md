# 날짜별 재고와 여러 박 예약

## 1. 개요

[1.1] 호텔 한 곳의 객실 유형별 재고를 관리하는 프로그램을 만든다. 객실을 날짜별로 판매하고 여러 박 예약과 일부 날짜의 부분 취소를 처리한다. 어느 날짜든 판매 한도를 넘지 않아야 하며 여러 날짜에 걸친 변경은 모두 성공하거나 모두 실패해야 한다. 목표 풀이 시간은 숙련 개발자 기준 1~3시간이다.

[1.2] 표준 입력의 명령을 순서대로 처리한다. 상태는 프로세스 안에서만 유지하며 시작할 때는 비어 있다. Kotlin 표준 라이브러리와 JDK 21만 사용한다. 객실 번호 배정, 요금, 결제, 실제 시각, 데이터베이스와 네트워크는 다루지 않는다.

## 2. 배경 개념

[2.1] 호텔의 재고 한 칸은 객실 유형과 숙박 날짜의 조합이다. 같은 객실 유형이라도 날짜마다 물리적인 객실 수가 다를 수 있다. 여러 박 예약은 각 날짜의 재고를 함께 차지한다. 숙박 구간은 체크인 날짜를 포함하고 체크아웃 날짜를 제외한다. 2028-02-28부터 2028-03-01까지의 예약은 윤년의 2월 28일과 29일, 두 날짜의 재고를 쓴다.

[2.2] 초과 예약은 취소나 미방문을 예상하여 물리적인 객실 수보다 많은 예약을 받는 정책이다. 이 과제의 판매 한도는 물리 객실 수를 B, 초과 예약 비율을 정수 P라 할 때 floor(B × (100 + P) / 100)이다. floor는 소수점 아래를 버리는 연산이다. 날짜마다 한도를 따로 계산하며 숙박 전체의 객실 수를 합친 뒤 한도를 계산하지 않는다. B가 3이고 P가 25이면 한도는 3이고 B가 4이면 5이다.

[2.3] 예약의 원자성은 숙박 날짜 중 하나라도 수용할 수 없으면 다른 날짜도 바꾸지 않는다는 뜻이다. 취소에도 같은 원칙이 필요하다. 일부 날짜의 취소 가능 수량이 부족한데 나머지 날짜만 먼저 회수하면, 실패한 요청이 재고를 바꾼다.

[2.4] 부분 취소 뒤에는 같은 예약이라도 날짜별 잔여 객실 수가 달라진다. 원래 예약한 구간과 수량은 예약의 이력이고 현재 남은 수량은 날짜별 상태다. 모든 날짜의 잔여 수량이 0이 된 예약도 식별자를 다시 쓰지 않도록 이력을 유지한다. 이 과제의 정책과 명령은 독자적으로 정하며 주제의 출발점은 『가상 면접 사례로 배우는 대규모 시스템 설계 기초 2』 7장의 호텔 예약이다.

## 3. 입출력 규칙

[3.1] 입력은 UTF-8 텍스트이며 한 줄에 명령 하나를 넣고 EOF까지 처리한다. 명령 수를 나타내는 첫 줄은 없다. 토큰은 하나 이상의 ASCII 공백 또는 탭으로 구분하며 앞뒤 공백과 탭은 무시한다. 빈 줄은 무시한다. 명령과 식별자는 대소문자를 구분한다.

[3.2] 객실 유형과 예약 ID는 각각 영문자로 시작하고 영문 대소문자, 숫자, 밑줄, 하이픈으로 이루어진 1~32자 문자열이다. 영문자는 ASCII A~Z와 a~z, 숫자는 ASCII 0~9를 뜻한다. 서로 다른 종류의 식별자는 같은 문자열을 사용할 수 있다. 정수 토큰은 선택적인 마이너스 부호와 하나 이상의 십진 숫자로 이루어지고 부호 있는 64비트 정수로 해석할 수 있어야 한다. 선행 0은 허용하며 값에는 영향을 주지 않는다. 플러스 부호는 허용하지 않는다.

[3.3] 날짜 토큰은 정확히 YYYY-MM-DD 형식의 실재하는 역산 그레고리력 날짜다. 날짜 형식 검사에는 연도 0000도 허용하며 400의 배수인 윤년으로 판정한다. 따라서 0000-02-29는 형식이 맞지만 허용 날짜 범위 밖이라 ERROR RANGE이고 0000-02-30은 ERROR INPUT이다. 날짜 값은 2000-01-01 이상 2099-12-31 이하다. from과 to가 있는 모든 명령은 from < to이고 날짜 차이가 1~366일이어야 한다. to는 포함하지 않는다. 비율은 0~100, 물리 객실 수는 0~1,000,000,000, 예약·취소 수량은 1~1,000,000,000이다. 모든 수량과 한도는 정수로 정확히 계산한다.

[3.4] 각 유효한 명령은 아래에서 정한 한 줄을 출력한다. 오류가 나도 다음 입력을 계속 처리한다. 출력 토큰 사이에는 ASCII 공백 하나를 쓰고 정수는 선행 0이나 플러스 부호 없이 출력한다. 성공·오류 응답 외의 안내문은 표준 출력에 쓰지 않는다.

## 4. 명령 규칙

### 4.1 객실 유형과 재고

[4.1.1] `TYPE <type> <percent>`는 객실 유형을 등록하고 그 유형에 적용할 초과 예약 비율을 고정한다. 성공 응답은 `OK TYPE <type>`이다. 같은 유형을 다시 등록하면 비율이 같더라도 ERROR TYPE_EXISTS이다. 등록된 비율을 바꾸는 명령은 없다.

[4.1.2] `STOCK <type> <from> <to> <base>`는 구간의 각 날짜에 물리 객실 수 base를 설정한다. 기존 수량을 대체한다. 아직 설정하지 않은 날짜의 물리 객실 수는 0이다. 성공 응답은 `OK STOCK <type>`이다. 유형이 없으면 ERROR TYPE_NOT_FOUND이다.

[4.1.3] STOCK이 만들 새 판매 한도보다 현재 예약된 수량이 큰 날짜가 하나라도 있으면 ERROR BELOW_RESERVED이고 구간 전체를 바꾸지 않는다. 한도가 예약 수량과 같은 경우와 기존과 같은 재고를 다시 설정하는 경우는 성공한다. 예약의 날짜별 잔여 수량은 STOCK으로 바뀌지 않는다.

[4.1.4] `AVAIL <type> <date>`는 해당 날짜의 재고를 조회한다. 응답은 `STOCK <type> <date> <base> <limit> <reserved> <remaining>`이다. limit는 판매 한도, reserved는 모든 예약의 해당 날짜 잔여 수량의 합, remaining은 limit - reserved이다. 물리 객실 수를 넘긴 예약도 reserved에 포함한다. 유형이 없으면 ERROR TYPE_NOT_FOUND이다.

### 4.2 예약

[4.2.1] `BOOK <reservationId> <type> <from> <to> <quantity>`는 구간의 모든 날짜에 quantity개씩 예약한다. 등록된 유형인지 먼저 확인하고 다음으로 예약 ID가 이미 성공한 예약에 쓰였는지 확인한다. 오류 응답은 각각 ERROR TYPE_NOT_FOUND와 ERROR RESERVATION_EXISTS이다. 완전히 취소된 예약 ID도 이미 쓰인 ID다.

[4.2.2] 각 날짜에서 현재 예약 수량 + quantity가 판매 한도 이하일 때만 예약을 확정하고 `OK BOOK <reservationId>`를 출력한다. 어느 날짜든 한도를 넘으면 ERROR FULL이다. 실패하면 재고와 예약 이력을 전혀 바꾸지 않으며 실패한 BOOK의 예약 ID는 이후에 사용할 수 있다. 예약은 같은 유형만 사용하며 날짜별 물리 객실 수와 한도가 달라도 예약 수량은 모든 날짜에 같다.

### 4.3 취소와 예약 조회

[4.3.1] `CANCEL <reservationId> <from> <to> <quantity>`는 해당 예약의 지정 날짜마다 quantity개씩 취소한다. 예약이 없으면 ERROR RESERVATION_NOT_FOUND이다. 취소 구간은 원래 예약 구간 안에 완전히 들어 있어야 한다. 그렇지 않으면 ERROR PERIOD이다. 원래 구간 안의 연속한 일부 날짜 또는 구간 전체를 취소할 수 있다.

[4.3.2] 취소 구간의 날짜 중 예약의 잔여 수량이 quantity보다 작은 날짜가 하나라도 있으면 ERROR CANCEL_QUANTITY이다. 그 외에는 모든 대상 날짜의 잔여 수량과 호텔의 예약 수량을 quantity씩 줄이고 `OK CANCEL <reservationId>`를 출력한다. 이미 회수한 수량을 다시 취소하지 않으며 취소 실패 시 어느 날짜도 바꾸지 않는다.

[4.3.3] `STATUS <reservationId>`는 `STATUS <reservationId> <type> <from> <to> <quantities>`를 출력한다. from과 to는 원래 예약 구간이고 quantities는 그 구간의 각 날짜에 남은 수량을 날짜 오름차순으로 쉼표만 넣어 이은 문자열이다. 수량 0인 날짜도 생략하지 않는다. 예약이 없으면 ERROR RESERVATION_NOT_FOUND이다.

## 5. 오류 규칙

[5.1] 알려지지 않은 명령, 잘못된 토큰 수, 식별자·정수·날짜 형식 위반은 ERROR INPUT이다. 실재하지 않는 날짜와 64비트 정수로 해석할 수 없는 토큰도 여기에 포함한다. 토큰 형식은 맞지만 [3.3]의 날짜 범위·구간·비율·수량 범위를 벗어나면 ERROR RANGE이다. 모든 토큰의 형식을 먼저 검사하고 이어서 모든 값의 기본 범위를 검사한다. 같은 줄에 두 종류의 문제가 있으면 ERROR INPUT을 출력한다.

[5.2] 형식과 기본 범위를 통과한 뒤 명령 규칙에 적힌 순서로 상태를 검사한다. STOCK은 유형 존재, 새 한도 순이다. BOOK은 유형 존재, 예약 ID 중복, 수용 가능 여부 순이다. CANCEL은 예약 존재, 원래 구간 포함 여부, 날짜별 취소 가능 수량 순이다. 오류는 한 줄만 출력하고 상태를 유지한다.

## 6. 예시

[6.1] 다음 예시는 날짜별 버림, 체크아웃 제외, 부분 취소 뒤의 수량 부족을 함께 보여 준다. 2028-02-28에는 물리 객실이 3개라 한도가 3이고 다음 날에는 4개라 한도가 5이다. r2는 부족한 2월 28일 때문에 어느 날짜에도 기록되지 않는다.

```text
입력
TYPE Deluxe 25
STOCK Deluxe 2028-02-28 2028-02-29 3
STOCK Deluxe 2028-02-29 2028-03-01 4
BOOK r1 Deluxe 2028-02-28 2028-03-01 3
AVAIL Deluxe 2028-03-01
BOOK r2 Deluxe 2028-02-28 2028-03-01 1
CANCEL r1 2028-02-29 2028-03-01 2
STATUS r1
CANCEL r1 2028-02-28 2028-03-01 2
STATUS r1
AVAIL Deluxe 2028-02-29
출력
OK TYPE Deluxe
OK STOCK Deluxe
OK STOCK Deluxe
OK BOOK r1
STOCK Deluxe 2028-03-01 0 0 0 0
ERROR FULL
OK CANCEL r1
STATUS r1 Deluxe 2028-02-28 2028-03-01 3,1
ERROR CANCEL_QUANTITY
STATUS r1 Deluxe 2028-02-28 2028-03-01 3,1
STOCK Deluxe 2028-02-29 4 5 1 4
```

[6.2] 다음 예시에서 실패한 재고 변경은 여유 있는 날짜도 바꾸지 않는다. 완전 취소 뒤에도 성공한 예약 ID는 남는다. 비율 100일 때 물리 객실 1개의 판매 한도는 2이다.

```text
입력
TYPE Twin 100
STOCK Twin 2030-01-01 2030-01-03 1
BOOK first Twin 2030-01-02 2030-01-03 2
STOCK Twin 2030-01-01 2030-01-03 0
AVAIL Twin 2030-01-01
CANCEL first 2030-01-02 2030-01-03 2
BOOK first Twin 2030-01-01 2030-01-02 1
STATUS first
출력
OK TYPE Twin
OK STOCK Twin
OK BOOK first
ERROR BELOW_RESERVED
STOCK Twin 2030-01-01 1 2 0 2
OK CANCEL first
ERROR RESERVATION_EXISTS
STATUS first Twin 2030-01-02 2030-01-03 0
```

## 7. 검사 방식

[7.1] 테스트마다 새 프로세스에 명령들을 표준 입력으로 주고 EOF를 보낸다. 종료 코드는 0이어야 한다. 표준 출력의 각 줄 끝 공백·탭·CR과 끝의 빈 줄을 제거한 뒤, 줄 수와 각 줄을 기대 출력과 글자 그대로 비교한다. 출력 순서도 비교한다. 숨은 고정 입력의 기대값은 스펙에서 독립적으로 계산하고 생성 입력은 참조 풀이와 교차 검증한다.

[7.2] 제한 시간은 컴파일을 제외하고 프로세스 한 번당 20초다. 한 입력은 비어 있지 않은 명령 최대 3,000줄이고 유형은 최대 100개다. 구간을 받는 명령들의 날짜 차이 합은 최대 100,000일이다. 별도의 성능 강제용 대규모 테스트는 두지 않는다. 가장 큰 기능 검사는 이 범위 안에서 재고 변경, 다박 예약, 부분 취소, 조회를 섞으며 특정 자료구조나 알고리즘을 요구하지 않는다.

[7.3] 날짜 경계와 윤년, 날짜별 한도의 버림, 한 날짜의 실패가 다른 날짜를 바꾸는지, 취소 후 재예약, 실패한 ID와 완전 취소한 ID의 차이, 상태에 따른 오류 우선순위를 검사한다. 시작 코드의 main은 TODO()로 비어 있으므로 구현을 마친 뒤 이 규칙에 맞게 입출력을 연결한다.

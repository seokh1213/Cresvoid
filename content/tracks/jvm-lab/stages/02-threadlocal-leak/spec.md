# 스레드 풀과 ThreadLocal

[1] 이 단계는 구현 실험이다. 먼저 코드를 읽고 예측 문항을 풀어라. 문항을 모두 닫은 뒤 시작 코드를 빌드하고 실험하여 `leaked_responses`와 `retained_payload_bytes`를 관찰해라. 인증 요청과 예외 응답 다음의 익명 요청이 예상대로 동작했는지 비교해라. 코드를 고친 뒤 같은 부하를 다시 실행하여 두 지표와 응답 계약을 함께 확인해라.

[2] JDK 21과 Kotlin 표준 라이브러리만 사용한다. `build.sh`는 `build/app.jar`를 만들고 `run.sh`는 환경 변수 `PORT`가 지정한 `127.0.0.1` 포트에서 HTTP 서비스를 시작한다. `GET /health`는 HTTP 200과 `ready`를 반환한다. 준비 확인과 관찰 요청은 사용자 요청 100,000개에 포함하지 않는다.

[3] 서비스에는 번호가 0부터 3까지인 작업 경로 네 개가 있다. 각 경로는 전용 단일 플랫폼 스레드 실행기를 사용한다. 같은 경로의 요청은 같은 스레드에서 차례로 처리하며, 네 작업 스레드는 준비 시점부터 관찰 종료까지 살아 있어야 한다. HTTP 수신 스레드는 별도로 사용한다. 작업 스레드를 교체하거나 요청마다 새로 만들어 값을 버리는 방법은 허용하지 않는다.

[4] 사용자 요청은 `GET /request?id=<번호>&lane=<경로>&fail=<0또는1>&bytes=<크기>`다. `id`는 0부터 9,223,372,036,854,775,807까지의 정수이며 응답에 같은 정수 값으로 돌려준다. `lane`은 0부터 3, `bytes`는 1부터 1,048,576까지다. 선택 매개변수 `user`는 영문자·숫자·하이픈 1~40자다. `user`가 있으면 인증 요청이고 없으면 익명 요청이다. 인증 요청은 그 요청의 사용자 이름과 지정 크기의 새 바이트 배열을 담은 문맥을 ThreadLocal에 넣고, 업무 코드는 ThreadLocal에서 사용자를 읽는다. 익명 요청의 사용자는 항상 `anonymous`다. 응답을 맞추려고 업무 코드에서 입력 사용자를 직접 반환하거나 ThreadLocal을 다른 저장소로 바꾸지 마라.

[5] 정상 요청은 HTTP 200으로 `id|lane|worker|principal` 한 줄을 반환한다. `worker`는 실제 업무 실행 스레드의 `threadId()`이고 `principal`은 문맥에서 읽은 사용자다. `fail=1`이면 문맥을 설정하고 사용자를 읽은 뒤 업무 예외를 발생시키며, 바깥 HTTP 계층이 HTTP 503과 같은 형식의 본문을 반환한다. 예외 응답도 올바른 사용자를 담아야 한다. 예를 들어 `id=7&lane=0&fail=0&bytes=4096&user=alice`의 응답은 `7|0|<작업 스레드 번호>|alice`이고, 그 뒤 같은 경로의 익명 요청은 `anonymous`를 담는다. 잘못된 매개변수는 HTTP 400으로 처리한다.

[6] 요청 처리가 끝나면 그 요청의 문맥과 바이트 배열을 작업 스레드에 남기지 마라. 정상 반환과 업무 예외에 같은 규칙을 적용한다. 부하가 모두 끝난 뒤 `GET /snapshot`을 호출하면 각 작업 스레드가 자기 ThreadLocal을 직접 읽어 `lane|worker|bytes` 한 줄씩 총 네 줄을 반환한다. 문맥이 없으면 `bytes`는 0이고 있으면 그 문맥의 바이트 배열 길이다. 이 관찰은 값을 지우지 않는다. `retained_payload_bytes`는 네 줄의 `bytes` 합계다. 작업 스레드에 남은 요청 배열만 측정한다. 전체 JVM 힙이나 RSS, GC 실행 시점, 다른 프로그램의 메모리 사용량은 판정에 넣지 않는다.

[7] `request-window` 시나리오는 사용자 HTTP 요청 100,000개를 보낸다. 먼저 네 경로에 인증 정상 요청, 익명 정상 요청, 인증 예외 요청, 익명 정상 요청을 네 묶음으로 보내며 묶음 사이에는 완료를 기다린다. 이어 99,980개를 초당 2,500개, 즉 번호순 0.4ms 간격의 예정 시각에 전송 대기열에 넣는다. 예정 시각의 밀리초 미만은 버린다. 이 구간은 완료를 기다려 다음 도착을 정하지 않는 개방형 부하다. 동시 전송은 최대 128개이며 자리가 없으면 대기열에서 기다린다. 대기해도 후속 요청의 예정 시각은 바꾸지 않는다. 경로는 순번을 4로 나눈 나머지이며, 같은 경로에 보내는 네 요청의 종류는 인증 정상·익명 정상·인증 예외·익명 정상 순서로 반복한다. 실제 처리 순서는 동시 도착으로 달라질 수 있다. 인증 사용자 이름은 요청마다 다르고 배열은 4,096바이트다. 마지막에는 각 경로에 1,048,576바이트의 인증 예외 요청 하나씩을 보내고 모두 완료한 뒤 관찰한다. 네 경로의 초기 관찰과 마지막 관찰에서 스레드 번호도 비교한다.

[8] 모든 불변식을 함께 만족해야 한다. `completed_requests`는 100,000이고 `unexpected_responses`, `leaked_responses`, `worker_changes`, `snapshot_errors`는 각각 0이어야 한다. `unexpected_responses`는 전송 실패, 상태·본문·사용자 불일치 건수다. `leaked_responses`는 사용자 칸에 기대값과 다르고 `anonymous`도 아닌 이름이 나온 건수이며 중복 집계할 수 있다. `worker_changes`는 초기 네 스레드가 서로 다르지 않으면 1을 더하고 응답·최종 관찰의 스레드 번호가 해당 경로의 초기 번호와 다를 때마다 1을 더한다. `snapshot_errors`는 관찰 응답의 상태나 네 줄 형식이 잘못된 횟수다. `retained_payload_bytes`는 65,536바이트 이하여야 한다. 요청 처리가 끝났을 때 배열이 없어야 한다는 [6]의 계약은 그대로 적용하며 이 수치에는 관찰 여유를 둔다.

[9] `p99_ms`는 본 부하 99,980개의 실제 전송 시작부터 본문 수신 완료까지 지연 시간의 99백분위수다. `p99_ms`는 10,000ms 이하여야 한다. HTTP 요청 제한 시간은 20초이고 서비스 준비에는 30초를 허용한다. `load_elapsed_ms`는 본 부하의 소요 시간이며 진단용이다. 정확성·잔류 바이트·스레드 재사용을 개수와 관계로 우선 판정하고, 지연 기준은 처리가 장시간 막힌 서비스를 걸러내는 보조 기준으로 쓴다. 실험 전체 제한 시간은 스크립트 준비 비용까지 포함해 240초다.

[10] 수정 범위는 `src/main/kotlin/RequestScope.kt`의 요청 문맥 처리다. ThreadLocal, 인증 요청마다 배열을 만드는 동작, 업무 예외, 사용자 조회를 유지해라. HTTP 계약, 작업 실행기, 관찰 코드, 빌드·실행 파일은 바꾸지 마라. 새 의존성을 추가하지 마라.

[11] JDK 21의 [ThreadLocal API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/ThreadLocal.html)는 스레드마다 별도 값을 가지며 살아 있는 스레드가 그 값에 대한 참조를 유지한다고 설명한다. `remove()`는 호출한 현재 스레드의 값을 제거하고, 이후 `get()`은 필요하면 초기값을 다시 구한다. 기본 ThreadLocal 초기값은 null이다. [HttpServer API](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.httpserver/com/sun/net/httpserver/HttpServer.html)의 `setExecutor`는 HTTP 처리 실행기를 지정한다.

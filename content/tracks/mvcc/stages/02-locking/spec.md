# 2단계: 잠금과 교착 감지

## 1. 개요

[1.1] 2단계는 잠금을 더한다. WRITE 는 쓰는 키에 배타 잠금을 건다. READ 와 SCAN 뒤에 `FOR SHARE` 나 `FOR UPDATE` 를 붙이면 공유 잠금이나 배타 잠금을 걸고 읽는다. SCAN 이 거는 잠금은 범위 전체를 덮어 아직 값이 없는 키에 쓰는 것도 막는다. 잠금을 얻지 못한 명령은 기다리고 그 트랜잭션의 다음 명령은 대기열에 쌓인다. 트랜잭션들이 서로 기다리는 교착이 생기면 정한 규칙으로 트랜잭션을 하나씩 골라 교착이 없어질 때까지 되돌린다.

[1.2] 1단계의 규칙은 그대로다. 이 문서는 새로 생기는 규칙만 설명한다. 1단계 4.23 과 4.24 가 출력을 정하지 않은 줄 가운데 겹친 쓰기와 FOR 절이 붙은 READ, SCAN 의 출력을 이 문서가 정한다. 인자가 둘이고 둘째 인자가 `SERIALIZABLE` 인 BEGIN 은 이 문서도 출력을 정하지 않는다.

| 명령 | 하는 일 | 정상 출력 |
|---|---|---|
| `READ <트랜잭션> <키> FOR SHARE` | 키에 공유 잠금을 걸고 읽는다 | 1줄 |
| `READ <트랜잭션> <키> FOR UPDATE` | 키에 배타 잠금을 걸고 읽는다 | 1줄 |
| `SCAN <트랜잭션> <시작 키> <끝 키> FOR SHARE` | 범위에 공유 잠금을 걸고 읽는다 | 1줄 |
| `SCAN <트랜잭션> <시작 키> <끝 키> FOR UPDATE` | 범위에 배타 잠금을 걸고 읽는다 | 1줄 |

[1.3] 새 출력 줄은 기다리기 시작했다는 `<트랜잭션> WAIT <트랜잭션> …` 과 교착의 희생자가 되었다는 `<트랜잭션> ABORT DEADLOCK` 이다. 기다린 명령의 결과 줄은 그 명령이 잠금을 얻어 실행될 때 나온다. 그래서 입력 한 줄이 다른 트랜잭션의 결과 줄을 여럿 내기도 한다.

## 2. 배경 개념

[2.1] 잠금에는 공유 잠금과 배타 잠금이 있다. 공유 잠금은 여러 트랜잭션이 한 대상에 함께 걸 수 있다. 배타 잠금은 한 트랜잭션만 걸 수 있고 다른 트랜잭션의 공유 잠금과도 함께 걸리지 않는다. 읽은 값이 바뀌지 않게 지킬 때는 공유 잠금을 쓰고 고칠 대상을 독차지할 때는 배타 잠금을 쓴다. 아래 표는 다른 트랜잭션이 건 잠금과 새로 요청한 잠금이 함께 걸리는지를 보여 준다.

| 걸린 잠금 \ 요청한 잠금 | 공유 | 배타 |
|---|---|---|
| 공유 | 함께 걸린다 | 충돌한다 |
| 배타 | 충돌한다 | 충돌한다 |

[2.2] 잠금을 언제 푸는지도 중요하다. 트랜잭션의 실행을 잠금을 얻기만 하는 구간과 풀기만 하는 구간으로 나누는 규약을 2PL(two-phase locking)이라 한다. 잠금을 트랜잭션이 끝날 때 한꺼번에 푸는 엄격한 2PL 에서는 커밋되지 않은 변경을 다른 트랜잭션이 읽거나 덮어쓰지 못한다. Berenson 외(1995)는 격리 수준을 잠금을 무엇에 얼마나 오래 거는지로도 정의했다. 이 트랙의 잠금은 트랜잭션이 끝날 때까지 남는다.

[2.3] MVCC 엔진의 일반 읽기는 잠금을 걸지 않는다. 읽은 값을 근거로 쓰기를 하려면 그 값이 커밋 전에 바뀌지 않게 해야 하는데 이때 잠금 읽기를 쓴다. InnoDB 와 PostgreSQL 은 SELECT 뒤에 FOR SHARE 를 붙이면 읽은 행에 공유 잠금을, FOR UPDATE 를 붙이면 배타 잠금을 건다. 잠금 읽기가 어느 버전을 읽는지는 엔진마다 다르다. InnoDB 의 잠금 읽기는 스냅숏과 상관없이 가장 최근에 커밋된 버전을 읽고 PostgreSQL 의 REPEATABLE READ 는 스냅숏을 만든 뒤에 바뀐 행을 잠그려 하면 직렬화 실패 오류를 낸다. 이 트랙의 잠금 읽기는 일반 읽기와 같은 스냅숏으로 읽는다(4.6). 쓰기는 격리 수준과 상관없이 고친 행에 배타 잠금을 걸어 1단계 2.3 의 더티 쓰기를 막는다. 이 트랙도 같다.

[2.4] 이미 있는 키만 잠그면 범위에 새로 들어오는 키, 곧 팬텀은 막지 못한다. 조건 자체에 잠금을 거는 술어 잠금이 이론적인 해법이다. InnoDB 의 REPEATABLE READ 는 범위 조건으로 잠금 읽기를 하면 훑은 인덱스 레코드와 레코드 사이의 틈을 함께 잠그는 갭 잠금과 넥스트키 잠금으로 삽입을 막는다. 넥스트키 잠금은 범위 바로 뒤의 레코드와 그 앞의 틈까지 잠글 수 있어 요청한 범위보다 넓게 막는다. 이 트랙의 범위 잠금은 SCAN 의 범위를 정확히 덮는다. 범위에 든 키라면 아직 값이 없는 키도 막고 범위 밖의 키는 막지 않는다.

[2.5] 잠금을 얻지 못한 트랜잭션은 잠금이 풀리기를 기다린다. 트랜잭션을 점으로 두고 'A 가 B 의 잠금이 풀리기를 기다린다' 를 A 에서 B 로 가는 화살표로 그리면 대기 그래프가 된다. 대기 그래프에 고리가 생기면 고리 위의 트랜잭션은 끝없이 기다린다. 이것이 교착이다. 교착을 풀려면 고리 위의 트랜잭션 하나를 되돌려 그 잠금을 풀어야 한다. 되돌리는 트랜잭션을 희생자라 한다.

[2.6] 교착을 찾는 때와 희생자를 고르는 방식은 엔진마다 다르다. InnoDB 는 기본 설정에서 교착을 바로 감지하고 넣거나 고치거나 지운 행이 적은 작은 트랜잭션을 되돌리려 한다. PostgreSQL 은 잠금을 deadlock_timeout(기본 1초) 동안 기다린 뒤에 교착을 확인한다. PostgreSQL 문서는 어느 트랜잭션이 되돌려질지 예측하기 어렵다고 적는다. 교착을 찾지 않고 정한 시간이 지나면 기다림을 포기하게 하는 방식도 있다. 이 트랙은 명령이 기다리기 시작할 때마다 교착을 확인하고 고리 위에서 가장 늦게 시작한 트랜잭션을 되돌린다. 늦게 시작한 트랜잭션일수록 한 일이 적다고 보는 단순한 규칙이다. 되돌린 뒤에도 고리가 남아 있으면 같은 규칙으로 하나를 더 되돌린다.

[2.7] 흔한 교착은 잠금 승격에서 생긴다. 두 트랜잭션이 같은 키에 공유 잠금을 걸고 읽은 뒤 둘 다 그 키를 고치려고 배타 잠금을 요청하면 서로 상대의 공유 잠금이 풀리기를 기다린다. 고칠 값을 읽을 때 처음부터 FOR UPDATE 로 배타 잠금을 걸면 뒤에 온 트랜잭션이 읽는 단계에서 기다리므로 이런 교착이 생기지 않는다.

[2.8] 실제 엔진의 잠금 관리자는 대개 잠금 요청을 들어온 순서로 줄 세워 공유 잠금 요청이 먼저 기다리던 배타 잠금 요청을 앞지르지 못하게 한다. 이 트랙은 단순하게 걸린 잠금만 따진다. 기다리는 요청은 다른 요청을 막지 않는다. 또 실제 세션은 문장 하나가 기다리는 동안 다음 문장을 보내지 못하지만 이 트랙의 입력에는 기다리는 트랜잭션의 다음 명령이 미리 들어올 수 있다. 그런 명령은 순서를 지키도록 그 트랜잭션의 대기열에 쌓아 둔다.

## 4. 명령 규칙

### 잠금

[4.1] 잠금은 모드와 대상으로 정한다. 모드는 공유(S)와 배타(X) 둘이다. 대상은 키 하나이거나 SCAN 의 범위(1단계 4.13)다. 범위가 대상인 잠금을 범위 잠금이라 한다. 범위 잠금의 대상은 범위에 든 모든 키다. 지금 값이 있는 키든 없는 키든 범위에 들면 대상이다.

[4.2] 서로 다른 트랜잭션이 건 두 잠금은 두 대상에 함께 든 키가 하나라도 있고 두 모드 가운데 하나라도 X 이면 충돌한다. 키 잠금과 범위 잠금은 그 키가 범위에 들 때 대상이 겹친다. 두 범위 잠금은 두 범위에 함께 든 키가 있을 때 대상이 겹친다. 끝 키는 범위에 들지 않으므로 끝 키가 `m` 인 범위 잠금과 키 `m` 의 잠금은 충돌하지 않는다. 같은 트랜잭션이 건 잠금끼리는 충돌하지 않는다.

[4.3] 트랜잭션이 건 잠금은 그 트랜잭션이 끝날 때 모두 한꺼번에 풀린다. COMMIT 으로 커밋할 때, 1단계 4.17 의 쓰기 충돌로 커밋에 실패할 때, ROLLBACK 할 때, 교착의 희생자가 될 때(4.17)가 그때다. 트랜잭션이 끝나기 전에는 잠금이 풀리지 않는다.

[4.4] 잠금을 요청하는 명령과 그 잠금은 아래와 같다. 나머지 명령은 잠금을 요청하지 않으므로 잠금을 기다리지 않는다. FOR 절이 없는 READ 와 SCAN 은 다른 트랜잭션이 건 잠금과 상관없이 바로 실행한다. 다만 기다리는 트랜잭션의 이름을 쓴 줄은 어느 명령이든 4.10 대로 처리한다.

| 명령 | 요청하는 잠금 |
|---|---|
| `WRITE <트랜잭션> <키> <값>` | 그 키에 X |
| `READ <트랜잭션> <키> FOR SHARE` | 그 키에 S |
| `READ <트랜잭션> <키> FOR UPDATE` | 그 키에 X |
| `SCAN <트랜잭션> <시작 키> <끝 키> FOR SHARE` | 그 범위에 S |
| `SCAN <트랜잭션> <시작 키> <끝 키> FOR UPDATE` | 그 범위에 X |

[4.5] 잠금을 요청하는 명령은 실행할 때 잠금을 요청한다. 다른 트랜잭션이 건 잠금 가운데 요청한 잠금과 충돌하는 잠금이 없으면 잠금을 얻는다. 다른 트랜잭션이 기다리며 요청하고 있는 잠금은 상관없다. 같은 트랜잭션이 이미 건 잠금과 대상이 겹쳐도 된다. 잠금을 얻으면 명령을 실행한다.

[4.6] FOR 절이 붙은 READ 와 SCAN 의 결과와 출력 형식은 FOR 절이 없는 같은 명령과 같다. 1단계 4.7 의 READ COMMITTED 스냅숏은 잠금을 얻은 뒤 명령을 실행하는 순간에 만든다. REPEATABLE READ 트랜잭션은 FOR 절이 있어도 자기 스냅숏으로 읽는다.

[4.7] 1단계 4.23 의 줄, 곧 다른 활동 중인 트랜잭션이 이미 쓴 키를 WRITE 하는 줄은 먼저 쓴 트랜잭션이 건 X 잠금과 충돌하므로 기다린다. REPEATABLE READ 트랜잭션이 이렇게 기다렸다가 쓴 키는 먼저 쓴 트랜잭션이 커밋했으면 COMMIT 에서 1단계 4.17 의 충돌한 키가 된다.

### 기다림과 대기열

[4.8] 트랜잭션의 시작 순서는 그 트랜잭션의 BEGIN 을 실행한 순서다.

[4.9] 요청한 잠금과 충돌하는 잠금이 있으면 명령은 실행되지 않고 기다린다. 이때 `<트랜잭션> WAIT <트랜잭션> …` 을 출력한다. WAIT 뒤에는 요청한 잠금과 충돌하는 잠금을 건 트랜잭션을 모두 시작 순서대로 공백 하나씩 띄워 쓴다. 충돌하는 잠금을 여러 개 건 트랜잭션도 이름을 한 번만 쓴다. 이 트랜잭션을 기다리는 트랜잭션, 이 명령을 기다리는 명령이라 한다. WAIT 줄을 출력한 때가 기다리기 시작한 때다. WAIT 줄은 기다리기 시작할 때 한 번만 출력하고 기다리는 동안 충돌하는 트랜잭션이 바뀌어도 다시 출력하지 않는다.

[4.10] 기다리는 트랜잭션의 이름을 쓴 문법에 맞는 줄은 BEGIN 이 아니면 실행하지 않고 그 트랜잭션의 대기열 끝에 넣는다. 이때는 아무것도 출력하지 않는다. COMMIT 과 ROLLBACK 도 대기열에 넣는다. BEGIN 은 대기열에 넣지 않고 바로 실행하므로 1단계 5.4 의 `ERR EXISTS` 가 된다. 문법에 맞지 않는 줄은 대기열에 넣지 않고 바로 1단계 5.2 나 5.3 의 오류를 출력한다.

[4.11] 기다리는 명령이 잠금을 얻으면 그 명령을 실행하고 이어서 대기열의 명령을 들어온 순서대로 실행한다. 대기열의 명령이 다시 기다리게 되면(4.9) 거기서 멈추고 남은 명령은 대기열에 그대로 둔다. 대기열의 명령도 실행할 때 1단계 5.4 의 상태 오류를 확인한다.

### 재개

[4.12] 재개는 아래를 되풀이하는 일이다. 기다리는 트랜잭션 가운데 지금 잠금을 얻을 수 있는(4.5) 트랜잭션이 없으면 재개가 끝난다. 있으면 그 가운데 가장 먼저 기다리기 시작한 트랜잭션 하나가 잠금을 얻고 4.11 대로 실행한다. 시작 순서가 아니라 기다리기 시작한 때로 고른다. 그 실행이 끝나면 다시 처음부터 고른다. 실행하는 동안 트랜잭션이 끝나거나 희생자가 되돌려져 잠금이 풀려도 재개는 이렇게 계속된다.

[4.13] 입력 한 줄은 아래 차례로 처리한다. 첫째, 문법에 맞지 않는 줄이면 오류를 출력하고 끝낸다. 둘째, BEGIN 이면 실행하고 끝낸다. 셋째, 기다리는 트랜잭션의 줄이면 대기열에 넣고 끝낸다(4.10). 넷째, 명령을 실행한다. 명령이 기다리게 되면 WAIT 줄을 출력하고 교착 처리(4.15~4.18)를 한다. 다섯째, 재개(4.12)를 한다. 재개가 끝나야 다음 줄을 읽는다.

### 교착

[4.14] 대기 그래프는 기다리는 트랜잭션 A 에서 A 의 기다리는 명령과 충돌하는 잠금을 건 트랜잭션 B 로 가는 화살표를 모두 모은 것이다. 화살표는 교착을 확인하는 순간 걸려 있는 잠금으로 정하므로 A 의 WAIT 줄(4.9)에 쓴 트랜잭션과 다를 수 있다. A 가 기다리는 동안 다른 트랜잭션이 A 의 기다리는 명령과 충돌하는 잠금을 얻으면(4.5) A 에서 그 트랜잭션으로도 화살표가 간다. WAIT 줄에 쓴 트랜잭션이라도 이미 끝났으면 그 트랜잭션으로는 화살표가 가지 않는다. 화살표를 따라가다 출발한 트랜잭션으로 돌아오는 길을 고리라 한다. 대기 그래프에 고리가 있으면 교착이다.

[4.15] 교착 확인은 명령이 기다리기 시작할 때마다 WAIT 줄을 출력한 직후에 한다. 교착이 없으면 교착 처리가 끝난다.

[4.16] 교착이면 고리 위에 있는 트랜잭션 가운데 시작 순서가 가장 늦은 트랜잭션을 희생자로 고른다. 고리가 여럿이면 고리 가운데 하나에라도 든 트랜잭션을 모두 놓고 고른다. 희생자는 방금 기다리기 시작한 트랜잭션이 아닐 수도 있다. 고리 위의 트랜잭션은 모두 기다리는 트랜잭션이다.

[4.17] 희생자는 롤백된다. 먼저 `<희생자> ABORT DEADLOCK` 을 출력한다. 희생자의 기다리는 명령은 실행되지 않는다. 희생자가 쓴 값은 모두 버려지고 잠금은 모두 풀리며 트랜잭션은 끝난다. 1단계 4.1 이 정한 트랜잭션이 끝나는 경우에 이 경우가 더해진다. 그다음 희생자의 대기열에 있던 명령을 들어온 순서대로 실행한다. 트랜잭션이 이미 끝났으므로 이 명령들은 저마다 `<희생자> ERR ENDED` 를 출력한다.

[4.18] 희생자를 되돌린 뒤 다시 교착을 확인한다. 아직 교착이면 4.16 과 4.17 을 되풀이하고 교착이 없어지면 교착 처리가 끝난다. 희생자의 잠금이 풀려 다른 트랜잭션이 잠금을 얻는 일은 교착 처리가 끝난 뒤의 재개에서 일어난다.

[4.19] 고리는 명령이 기다리기 시작할 때만 새로 생긴다. 잠금을 얻는 트랜잭션은 그 순간 기다리고 있지 않고 잠금이 풀리면 화살표가 없어질 뿐이기 때문이다. 그래서 4.15 의 확인만으로 교착을 모두 찾는다.

### 입력의 끝

[4.20] 입력이 끝나면 기다리는 명령과 대기열의 명령은 실행하지 않고 끝낸다. 1단계 3.2 처럼 아무것도 출력하지 않는다.

## 5. 오류 규칙

[5.1] 1단계의 오류 규칙을 그대로 따른다. 1단계 5.3 의 인자 형식에 아래 둘이 더해진다. FOR 절이 붙은 READ 의 인자는 트랜잭션, 키, `FOR`, `SHARE` 나 `UPDATE` 의 네 개다. FOR 절이 붙은 SCAN 의 인자는 트랜잭션, 시작 키, 끝 키, `FOR`, `SHARE` 나 `UPDATE` 의 다섯 개이고 시작 키가 끝 키보다 앞이어야 한다. `FOR`, `SHARE`, `UPDATE` 는 대소문자를 구분한다. 이 밖의 인자 수와 FOR 절은 형식에 맞지 않는다.

[5.2] 인자가 둘이고 둘째 인자가 `SERIALIZABLE` 인 BEGIN 은 이 문서도 출력을 정하지 않는다. 3단계에서 뜻이 생기기 때문이다. 그런 줄이 나온 뒤의 출력도 정하지 않는다.

[5.3] 문법 오류(1단계 5.2, 5.3)는 줄을 읽을 때 확인하고 상태 오류(1단계 5.4)는 명령을 실행할 때 확인한다. 대기열에 넣은 명령의 상태 오류는 대기열에서 꺼내 실행할 때 확인한다.

[5.4] 이 단계에서 새로 생기는 오류 줄은 없다.

## 6. 예시

[6.1] 예시의 표기는 1단계 6.1 과 같다. 대기열에 넣은 줄 아래에는 출력이 없다.

[6.2] 잠금 읽기로 막는 갱신 손실이다. READ COMMITTED 인 p 와 q 가 x 를 FOR UPDATE 로 읽는다. q 는 p 의 X 잠금 때문에 기다리고 그 뒤에 들어온 q 의 WRITE 와 COMMIT 은 대기열에 들어간다. FOR 절이 없는 r 의 READ 는 기다리지 않는다. p 가 커밋해 잠금을 풀면 q 의 READ 가 그 순간의 스냅숏으로 실행되어 11 을 읽고 대기열의 WRITE 와 COMMIT 이 이어서 실행된다.

init COMMIT

> BEGIN q

> READ p x FOR UPDATE

q WAIT p
> WRITE q x 12
> COMMIT q
> BEGIN r

> WRITE p x 11
p OK
> READ r x
r x=10
> COMMIT p
p COMMIT
q x=11
q OK
q COMMIT
> READ r x
r x=12
```

[6.3] 범위 잠금과 그 경계다. s 의 범위 잠금은 아직 값이 없는 키 c 까지 덮으므로 i 의 WRITE 가 기다린다. 끝 키 m 은 범위에 들지 않으므로 j 는 m 에 바로 쓴다. S 잠금끼리는 충돌하지 않으므로 j 의 FOR SHARE 는 기다리지 않고 k 의 FOR UPDATE 는 기다린다. FOR 절이 없는 s 의 SCAN 은 잠금을 요청하지 않고 REPEATABLE READ 스냅숏으로 읽으므로 j 가 커밋한 m 을 보지 못한다. s 가 커밋하면 먼저 기다리기 시작한 i 부터 실행한다.

```

init OK
> WRITE init d 1
init OK
> COMMIT init

> BEGIN j

> READ j d FOR SHARE

> COMMIT j

> BEGIN k

> SCAN s a z

> COMMIT s

i OK

```

[6.4] 충돌하는 트랜잭션이 여럿이다. c, a, b 의 순서로 BEGIN 했다. b 의 키 잠금과 c 의 범위 잠금이 모두 a 의 X 잠금 요청과 충돌하므로 WAIT 줄에 둘을 시작 순서대로 쓴다. b 가 커밋해도 c 의 잠금이 남아 있으므로 a 는 계속 기다리고 c 가 롤백한 뒤에야 쓴다.

```

> BEGIN a

> BEGIN b
b BEGIN

> WRITE a k 1

> COMMIT b
b COMMIT
> ROLLBACK c

```

[6.5] 잠금 승격으로 생기는 교착이다. p 와 q 가 x 에 S 잠금을 건 뒤 둘 다 X 잠금을 요청한다. q 가 기다리기 시작하면 p 에서 q 로, q 에서 p 로 가는 고리가 생긴다. 고리 위에서 시작 순서가 늦은 q 가 희생자다. 교착 처리가 끝난 뒤의 재개에서 p 의 WRITE 가 실행된다.

```

[6.6] 희생자가 방금 기다리기 시작한 트랜잭션이 아닌 교착이다. b 의 WRITE 로 a 에서 c, c 에서 b, b 에서 a 로 가는 고리가 생긴다. 희생자는 b 가 아니라 시작 순서가 가장 늦은 c 다. c 의 잠금이 풀려 a 의 WRITE 가 실행되고 b 는 a 가 커밋할 때까지 기다린다.

```
> BEGIN a

b COMMIT
```

[6.7] 기다리는 동안 생기는 화살표다. b 가 기다리기 시작할 때 k 에 걸린 잠금은 a 의 S 잠금뿐이므로 WAIT 줄에는 a 만 쓴다. 기다리는 요청은 다른 요청을 막지 않으므로 c 는 k 에 S 잠금을 얻는다. 이때부터 b 의 기다리는 명령은 c 의 잠금과도 충돌하므로 대기 그래프에 b 에서 c 로 가는 화살표가 있다. c 가 b 의 X 잠금이 걸린 y 를 기다리기 시작하면 c 에서 b 로, b 에서 c 로 가는 고리가 생긴다. 고리 위에서 시작 순서가 늦은 c 가 희생자다. WAIT 줄에 쓴 트랜잭션으로만 화살표를 그리면 이 교착을 찾지 못한다. a 가 커밋하면 b 의 WRITE 가 실행된다.

```

> BEGIN b

> BEGIN c

b OK

> WRITE b k 1

> READ c k FOR SHARE
c k=(none)
> READ c y FOR SHARE
c WAIT b

b OK
```

[6.8] 재개하는 순서와 대기열이다. h 가 커밋하면 b 와 a 가 모두 잠금을 얻을 수 있다. 시작 순서는 a 가 앞서지만 먼저 기다리기 시작한 b 부터 실행한다. a 는 x 의 잠금을 얻어 READ 를 실행한 뒤 대기열의 WRITE 가 b 의 S 잠금과 충돌해 다시 기다린다. 이 WAIT 줄은 h 의 COMMIT 줄을 처리하는 동안 나온다. b 가 커밋하면 a 의 WRITE 와 대기열의 COMMIT 이 실행된다.

## 7. 검사 방식

[7.1] 1단계 7.1~7.5, 7.7, 7.10 을 그대로 따른다.

[7.2] 대규모 테스트는 트랜잭션 60,000개 안팎과 입력 490,000줄 안팎으로 이뤄진다. 오래 활동하는 트랜잭션 수십 개가 키 200,000개 안팎에 잠금을 건 채 남아 있는 동안 다른 트랜잭션들이 READ, WRITE, SCAN 과 FOR 절을 섞어 실행한다. FOR 절이 붙은 SCAN 은 12,000번 안팎이다. 키 몇 개에는 저마다 트랜잭션 9,000개 안팎이 한꺼번에 몰려 줄지어 기다린다. 오래 활동하는 트랜잭션의 잠금을 기다리는 트랜잭션 수천 개는 테스트의 대부분 동안 기다린 채 남아 있다. 교착은 1,000번 안팎 생긴다. 동시에 걸려 있는 범위 잠금은 200개 이하다. 제한 시간은 15초다. 잠금을 요청할 때마다 걸려 있는 잠금을 모두 훑는 풀이와 잠금이 풀릴 때마다 기다리는 트랜잭션을 모두 다시 확인하는 풀이는 이 제한 시간을 넘기도록 규모를 정했다. 키 하나를 잠글 때는 그 키에 걸린 잠금만 찾더라도 범위를 잠글 때마다 걸려 있는 키 잠금을 모두 훑는 풀이도 이 제한 시간을 넘긴다.

[7.3] 2단계 검사 입력에는 5.2 의 줄이 나오지 않는다.

[7.4] 2단계를 검사할 때는 1단계 테스트를 먼저 다시 실행한다. 3단계를 검사할 때도 2단계 테스트를 다시 실행한다.

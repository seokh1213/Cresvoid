# 시각·기계·순번 비트 배치

## 1. 개요

[1.1] 여러 기계가 발급할 때마다 서로 통신하지 않고 고유한 ID를 만드는 명령 처리기를 구현한다. ID에는 시각, 기계 번호, 같은 밀리초 안의 순번을 넣는다. 비트 배치를 설정하고 가상 시계로 ID를 발급하며 발급한 값을 다시 해석하는 것이 이 단계의 범위다. 예상 구현 시간은 2시간이다.

[1.2] 모든 명령은 한 프로세스에서 입력 순서대로 처리한다. 실제 시계, 스레드, 네트워크, 영속 저장소는 사용하지 않는다. 기계 번호를 중복 배정하지 않는 책임은 이 프로그램이 맡는다. 정상 설정을 새로 적용하면 이전 발급 이력이 사라지므로, 고유성은 한 설정이 유지되는 동안에만 보장한다.

## 2. 배경 개념

[2.1] 고유성과 시간순 정렬은 서로 다른 성질이다. 서로 다른 기계가 서로 다른 번호를 쓰면 시각과 순번이 같아도 ID가 다르다. 하지만 기계 시계가 실제 시각과 다르면 더 늦게 만든 ID가 더 작을 수 있다. 이 단계는 기계 하나에서의 시각 역행을 다루며, 기계 사이의 순서 문제는 뒤 단계에서 다룬다.

[2.2] 밀리초 단위의 기준 시각을 epoch라 한다. ID에는 절대 시각 대신 epoch부터 지난 밀리초를 담는다. 시각에 t비트를 배정하면 표현 가능한 차이는 0부터 2^t−1까지다. 비트 수를 늘리면 사용 기간이 길어지지만, 같은 64비트 안에서 기계 수나 밀리초당 발급량에 쓸 공간이 줄어든다.

[2.3] 같은 기계가 같은 밀리초에 여러 ID를 만들면 순번으로 구분한다. 순번을 처음 값으로 되돌리는 것만으로 넘침을 처리하면 같은 ID를 다시 만들 수 있다. 시계가 뒤로 갈 때도 이미 사용한 시각과 순번을 다시 사용할 위험이 있다. 거절은 즉시 실패를 돌려주는 정책이고, 대기는 사용해도 되는 시각이 관측될 때까지 발급을 미루는 정책이다.

[2.4] Kotlin의 Long은 부호 있는 64비트 정수다. 이 과제는 최상위 부호 비트를 0으로 고정하고 나머지 63비트 안에 필드를 넣는다. 사용하지 않는 상위 비트도 0이다. 따라서 ID 0도 유효하며 숫자 오름차순으로 비교할 수 있다. 비트 수의 합이 64인 배치는 이 과제에서는 유효하지 않다.

[2.5] UUID는 더 넓은 식별 공간을 사용하는 대안이며, 정렬 특성은 종류에 따라 다르다. 중앙 DB 시퀀스는 발급 순서를 한곳에서 관리하는 대신 발급 경로가 해당 서비스에 의존한다. 이 과제는 두 대안을 구현하지 않고, 기계별 상태와 제한된 비트 공간으로 발급하는 경우를 다룬다.

[2.6] 배경 자료는 [Twitter Snowflake README, snowflake-2010](https://github.com/twitter-archive/snowflake/blob/snowflake-2010/README.mkd)다. 원문의 시각 41비트·기계 10비트·순번 12비트 배치를 참고하되, 이 과제는 비트 수와 시계 역행 정책을 입력으로 받고 유한한 시각 표본으로 대기를 재현한다. 아래 규칙이 채점 계약이다.

## 3. 입출력 규칙

[3.1] 표준 입력을 EOF까지 한 줄씩 읽는다. 빈 줄은 무시한다. 나머지 줄은 공백과 탭으로 구분한 토큰이며 명령어와 정책은 대문자다. 각 명령은 정확히 한 줄을 출력한다. 출력 토큰 사이에는 공백 하나를 쓴다. 안내문이나 디버그 문자열은 출력하지 않는다.

[3.2] 이름은 정규식 `[a-z][a-z0-9-]{0,31}`을 만족한다. 숫자는 부호를 붙일 수 있는 10진 정수이며 Long 범위 안에 들어온다. 선행 0과 `+` 부호는 입력에 나오지 않고, 음수에는 `-`를 쓴다. 숫자 토큰이 아니거나 Long 범위 밖인 입력, 이름 형식 위반, 알 수 없는 명령, 토큰 수 오류는 채점에 나오지 않는다. 단, 뒤 단계에서 추가하는 명령 이름은 이 단계의 오류 입력으로 사용하지 않는다.

[3.3] ID·시각·epoch는 Long으로 표현한다. 계산 결과는 수학적인 정수값을 기준으로 판단하며 정수 넘침으로 값이 바뀐 결과를 인정하지 않는다. 출력 정수는 선행 0이나 `+` 없이 쓴다.

## 4. 명령 규칙

[4.1] `CONFIG <t> <m> <s> <epoch> <policy>`는 시각·기계·순번 비트 수와 기준 시각, 역행 정책을 설정한다. t, m, s는 각각 1 이상이고 합이 63 이하여야 한다. epoch는 0 이상이며 `epoch + 2^t − 1`이 Long.MAX_VALUE 이하여야 한다. policy는 `REJECT` 또는 `WAIT`다. 하나라도 어기면 `ERR CONFIG`를 출력한다. 성공하면 설정을 교체하고 등록된 모든 기계와 발급 이력을 지운 뒤 `OK`를 출력한다.

[4.2] ID의 낮은 쪽부터 s비트는 순번, 다음 m비트는 기계 번호, 다음 t비트는 경과 밀리초다. 절대 시각을 time, 기계 번호를 machine, 순번을 seq라 할 때 ID는 `(time − epoch) × 2^(m+s) + machine × 2^s + seq`다. 유효한 필드 범위는 경과 밀리초 0 이상 2^t 미만, 기계 번호 0 이상 2^m 미만, 순번 0 이상 2^s 미만이다.

[4.3] `NODE <name> <machine>`은 이름과 기계 번호를 등록한다. 설정이 있어야 하며 machine이 범위 밖이면 `ERR MACHINE`이다. 이름이나 기계 번호 중 하나라도 이미 등록되어 있으면 `ERR EXISTS`다. 같은 이름과 같은 번호를 다시 등록해도 오류다. 성공하면 아직 한 번도 발급하지 않은 생성기를 만들고 `OK`를 출력한다. 삭제 명령은 없다.

[4.4] `NEXT <name> <r> <time1> ... <timer>`는 해당 생성기의 발급 요청 한 건이다. r은 1 이상이며 뒤에 정확히 r개의 시각 표본이 온다. 먼저 모든 표본이 epoch 이상이고 경과 밀리초가 2^t 미만인지 확인한다. 하나라도 어기면 아직 읽지 않을 표본이라도 `ERR TIME`을 출력한다. 표본 사이의 증가나 감소는 제한하지 않는다.

[4.5] 유효한 표본은 왼쪽부터 관측한다. 아직 발급 이력이 없으면 첫 표본에서 순번 0으로 발급한다. 마지막으로 성공한 발급 시각을 last, 순번을 lastSeq라 한다. 관측 시각이 last보다 크면 그 시각에서 순번 0으로 발급한다. last와 같고 lastSeq가 2^s−1보다 작으면 순번을 하나 늘려 발급한다. 발급에 성공하면 남은 표본은 사용하지 않고 `ID <id>`를 출력한다.

[4.6] 관측 시각이 last와 같고 순번을 모두 썼다면 그 표본에서는 발급하지 않고 다음 표본을 관측한다. 순번이 찬 뒤 새 시각에서 발급할 때 순번은 0이다. 현재 정책과 관계없이 다음 밀리초를 임의로 만들어 쓰지 않는다.

[4.7] 관측 시각이 last보다 작으면 REJECT 정책에서는 즉시 `ERR CLOCK`을 출력하고 그 요청을 끝낸다. WAIT 정책에서는 해당 표본을 건너뛴다. 이 규칙은 순번이 찬 뒤 관측하는 표본에도 적용한다. WAIT에서 last로 돌아온 표본은 순번에 여유가 있으면 사용할 수 있고, 여유가 없으면 last보다 커야 한다. 마지막 성공 이후 시각이 얼마나 크게 뒤로 갔는지에 따른 별도 임계값은 없다.

[4.8] 발급하지 못한 채 r개의 표본을 모두 쓰면 `ERR WAIT`를 출력한다. 실패한 요청은 last와 lastSeq를 바꾸지 않는다. 실패한 요청의 표본은 다음 요청으로 넘기지 않는다. 각 NODE는 자기 last와 lastSeq만 관리하며 다른 NODE의 요청이나 실패가 그 상태에 영향을 주지 않는다.

[4.9] `DECODE <id>`는 ID를 현재 설정으로 해석한다. 0 이상이고 2^(t+m+s) 미만인 모든 값이 유효한 ID다. 합이 63일 때 Long.MAX_VALUE도 유효하다. 이 프로그램이 실제로 발급했는지나 해당 기계가 등록되어 있는지는 확인하지 않는다. 유효하면 `PARTS <절대 시각> <기계 번호> <순번>`을 출력하고 범위를 벗어나면 `ERR ID`를 출력한다. 해석은 발급 상태를 바꾸지 않는다.

## 5. 오류 규칙

[5.1] 프로세스 시작 시에는 설정이 없다. CONFIG 이외의 이 단계 명령은 먼저 설정 유무를 확인하며 없으면 `ERR UNCONFIGURED`를 출력한다. 오류가 난 명령은 어떤 설정이나 등록·발급 상태도 바꾸지 않는다. 오류 후 다음 입력 줄을 계속 처리하고 정상적인 EOF에서는 종료 코드 0으로 끝낸다.

[5.2] NODE는 설정 유무, 기계 번호 범위, 중복 순서로 확인한다. NEXT는 설정 유무, 이름 존재 여부, 전체 시각 표본 범위, 표본 관측 순서로 확인한다. 없는 이름은 `ERR NODE`다. DECODE는 설정 유무, ID 범위 순서로 확인한다. 여러 오류가 겹치면 이 순서에서 처음 만난 오류만 출력한다. 잘못된 CONFIG는 기존의 정상 설정과 상태를 보존한다.

[5.3] r이 1 이상이라는 조건과 숫자·이름의 형식은 입력 보장이다. 비트 수, epoch, 기계 번호, 시각, ID의 의미상 범위는 입력 보장이 아니므로 위 오류 규칙으로 처리한다. policy 토큰은 항상 REJECT 또는 WAIT 중 하나다.

## 6. 예시

[6.1] 아래 예시는 순번 소진, 대기 실패의 상태 보존, 역행 거절을 보여 준다. 배치는 시각·기계·순번 3·2·1비트이며 epoch는 100이다. ID 18은 경과 시각 2, 기계 1, 순번 0이므로 `2 × 8 + 1 × 2`다.

```text
입력
CONFIG 3 2 1 100 REJECT
NODE east 1
NEXT east 1 102
NEXT east 1 102
NEXT east 2 102 102
NEXT east 3 102 103 104
DECODE 26
NEXT east 2 101 104
NEXT east 1 103
DECODE 255

출력
OK
OK
ID 18
ID 19
ERR WAIT
ID 26
PARTS 103 1 0
ERR CLOCK
ID 27
ERR ID
```

[6.2] WAIT는 역행 중에도 시각을 만들어 내지 않는다. 아래에서 표본 9는 발급에 쓰지 않았지만 범위 검사 대상이므로 요청 전체가 실패한다. 마지막 요청은 직전의 순번 1 다음 값인 2를 쓴다.

```text
입력
CONFIG 2 1 2 10 WAIT
NODE west 0
NEXT west 1 12
NEXT west 3 10 11 12
NEXT west 2 12 9
NEXT west 1 12
DECODE 18

출력
OK
OK
ID 16
ID 17
ERR TIME
ID 18
PARTS 12 0 2
```

## 7. 검사 방식

[7.1] 프로그램을 빌드한 뒤 테스트마다 새 프로세스로 run.sh를 실행하고 명령 목록을 표준 입력으로 전달한다. 출력 줄 끝의 공백·탭·CR과 마지막 빈 줄을 제거한 뒤 줄 수와 나머지 문자를 정확히 비교한다. 종료 코드가 0이 아니어도 실패다. 컴파일 시간을 제외한 테스트 한 건의 제한 시간은 15초다.

[7.2] 입력 한 건은 비어 있거나 최대 30,000개 명령, 최대 10,000개 NODE, NEXT 전체를 합쳐 최대 200,000개 시각 표본을 포함한다. 긴 대기와 큰 시각 역행도 표본으로만 표현한다. 실제로 자거나 현재 시각이 바뀌기를 기다릴 이유가 없다. 이 단계에는 별도의 성능 선별용 대규모 테스트를 두지 않으며 마지막 규모 검사는 이 상한 안에서 수행한다.

[7.3] 비트 합 63과 그 초과, 기준 시각의 양 끝, Long 범위, 순번 소진 뒤의 첫 발급, 실패 후 재시도, 여러 기계의 독립성을 함께 확인한다. 정해진 예시만 재현하는 것으로는 통과할 수 없다. 공개 함수나 클래스 이름은 정하지 않으며 표준 입출력 동작을 검사한다.

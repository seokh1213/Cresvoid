# 여러 생성기의 ID 순서

## 1. 개요

[1.1] 여러 생성기의 ID 흐름을 받아 ID 오름차순으로 병합하고 그 순서가 실제 생성 시각과 얼마나 어긋나는지 검사하는 분석 영역을 추가한다. 1·2단계 명령과 출력은 그대로 유지한다. 예상 구현 시간은 2시간이다.

[1.2] 이 단계는 시계 오차가 일정한 생성기들의 기록을 분석한다. ID를 새로 발급하거나 실제 시계를 측정하지 않는다. 외부에서 가져온 ID와 실제 시각을 입력받으며 이 프로세스에서 앞서 발급한 ID일 필요는 없다. 분석 대상은 1단계의 시각·기계·순번 배치다. 샤드 ID는 분석 대상으로 취급하지 않는다.

## 2. 배경 개념

[2.1] 시각 필드가 ID의 상위에 있으면 기록된 시각이 이른 ID가 먼저 정렬된다. 같은 기록 시각에서는 기계 번호와 순번이 순서를 정한다. 이 순서는 실제 생성 순서나 명령이 도착한 순서와 다를 수 있다. 예를 들어 시계가 빠른 기계가 실제로 먼저 만든 ID를, 시계가 느린 기계가 나중에 만든 ID보다 큰 값으로 만들 수 있다.

[2.2] 여기서 시계 오차 offset은 `ID에 기록된 절대 시각 − 실제 생성 시각`이다. offset이 양수이면 시계가 빠르다. 각 생성기의 offset은 한 분석 세션 동안 일정하며 절댓값이 bound 이하다. 여러 생성기가 각자 단조롭게 발급해도 서버 사이의 오차가 사라지지는 않는다.

[2.3] 이 과제에서 k-정렬 보장은 밀리초 단위로 정의한다. ID 오름차순의 임의의 두 기록 i, j에서 i가 먼저 나올 때 `actual_i − actual_j ≤ k`이면 보장을 만족한다. 즉, 실제로 k밀리초보다 더 늦게 생성된 기록이 먼저 정렬되는 역전은 허용하지 않는다. k는 건수나 정렬 위치의 차이가 아니다. 정확히 k밀리초인 역전은 허용한다.

[2.4] 검사에는 인접한 두 기록만이 아니라 앞뒤의 모든 쌍이 포함된다. 중간 기록을 여러 개 끼우면 인접한 시각 차이는 작아도 멀리 떨어진 쌍의 역전 폭이 클 수 있다. 모든 시계 오차의 절댓값이 bound 이하이고 기록이 아래 조건을 만족하면 2 × bound 밀리초의 보장은 성립한다. 실제 기록에서 필요한 최소 k는 이 상한보다 작을 수도 있다. 기록이 없거나 하나뿐이면 필요한 최소 k는 0이다.

[2.5] 배경 자료는 [Twitter Snowflake README의 대략 시간순 요구사항](https://github.com/twitter-archive/snowflake/blob/snowflake-2010/README.mkd)이다. 원문의 운영상 목표 수치를 이 과제의 고정 보장으로 사용하지 않는다. 위의 모든 쌍에 대한 시간 차이를 이 단계의 k-정렬 정의로 사용하며 통신 지연이나 인과관계는 분석하지 않는다.

## 3. 입출력 규칙

[3.1] 줄 단위 입력과 숫자·이름 형식, EOF, 출력 비교를 위한 공백 규칙은 1단계를 따른다. 새 명령은 ORDER_BEGIN, STREAM, APPEND, MERGE, AUDIT다. 이름은 흐름마다 쓰며 1단계 NODE 이름이나 2단계 서버 이름과 같아도 된다.

[3.2] 모든 새 명령도 한 줄을 출력한다. MERGE의 여러 ID는 같은 줄에 공백 하나로 구분해 출력한다. actual과 k는 입력상 Long 범위 정수이며 음수 여부는 명령의 의미상 오류로 검사한다. 실제 시각에는 epoch 이전 값이 올 수 있다. 양의 offset 때문에 그 시각에 생성한 ID의 기록 시각이 epoch 이후가 될 수 있기 때문이다.

## 4. 명령 규칙

[4.1] `ORDER_BEGIN <bound>`는 새 분석 세션을 연다. 먼저 1단계 CONFIG 설정이 있는지 확인하고 없으면 `ERR UNCONFIGURED`다. bound는 0 이상 1,000,000,000,000 이하의 정수이며 범위 밖이면 `ERR BOUND`다. 성공하면 현재 CONFIG의 t·m·s·epoch를 분석 세션에 복사하고 모든 흐름과 기록을 비운 뒤 `OK`를 출력한다. REJECT·WAIT 정책과 NODE의 발급 이력은 복사하지 않는다.

[4.2] 분석 세션은 복사한 배치를 끝날 때까지 사용한다. 나중에 CONFIG나 SHARD_CONFIG가 바뀌어도 기존 분석 세션은 바뀌지 않는다. ORDER_BEGIN을 다시 성공시키면 그때의 CONFIG를 복사해 새로 시작한다. 잘못된 ORDER_BEGIN은 이전 세션과 기록을 보존한다. 이 명령은 어느 발급 영역의 상태도 바꾸지 않는다.

[4.3] `STREAM <name> <machine> <offset>`은 한 생성기의 흐름을 등록한다. machine은 분석 세션의 m비트 범위 안이어야 하고 offset은 −bound 이상 bound 이하여야 한다. 위반 시 각각 `ERR MACHINE`, `ERR OFFSET`이다. 이름 또는 기계 번호가 이미 분석 세션에 등록되어 있으면 `ERR EXISTS`다. 성공하면 빈 흐름을 만들고 `OK`를 출력한다. NODE 등록은 필요하지 않다. 등록 후 offset이나 기계 번호를 바꾸거나 흐름을 지우는 명령은 없다.

[4.4] `APPEND <name> <actual> <id>`는 해당 흐름 끝에 기록 한 건을 넣는다. name이 없으면 `ERR STREAM`이다. actual은 0 이상이어야 하며 아니면 `ERR TIME`이다. id는 분석 세션에 복사한 배치에서 0 이상 2^(t+m+s) 미만이어야 하며 아니면 `ERR ID`다. 다음으로 ID 안의 기계 번호가 흐름의 machine과 같은지 확인하고 다르면 `ERR MACHINE`이다.

[4.5] ID를 분석 세션의 배치로 해석한 절대 시각을 recorded라 한다. `recorded − actual`이 흐름에 등록한 offset과 정확히 같아야 하며 다르면 `ERR OFFSET`이다. 계산은 수학적 정수 기준이다. 실제 시각과 기록 시각은 각각 Long으로 표현 가능한 음이 아닌 값이므로 그 차이도 Long으로 표현 가능하다.

[4.6] APPEND에서 앞의 조건을 만족하면 같은 흐름의 직전 기록과 비교한다. 새 ID는 직전 ID보다 반드시 커야 하고 actual은 직전 actual 이상이어야 한다. 하나라도 어기면 `ERR ORDER`다. 빈 흐름에는 비교 대상이 없다. 성공하면 기록을 추가하고 `OK`를 출력한다. 순번을 빠뜨렸거나 중간 밀리초의 ID를 누락한 흐름도 허용하며 이 프로그램의 NEXT를 실행해 재현 가능한 발급 이력인지까지 확인하지 않는다.

[4.7] `MERGE`는 모든 흐름의 모든 기록을 모아 ID 숫자 오름차순으로 `IDS <id1> ... <idN>`을 출력한다. 기록이 하나도 없으면 `EMPTY`를 출력한다. 서로 다른 흐름은 기계 번호가 다르고 같은 흐름의 ID는 엄격히 증가하므로 ID 중복은 없다. 명령 도착 순서나 흐름 등록 순서는 병합 순서에 영향을 주지 않는다. MERGE는 기록을 소비하거나 변경하지 않는다.

[4.8] `AUDIT <k>`는 k가 음수이면 `ERR K`를 출력한다. 그 외에는 MERGE와 같은 ID 순서에서 모든 i < j에 대한 `actual_i − actual_j`와 0 중 최댓값 d를 계산한다. d는 이 기록 집합에 필요한 최소 허용 역전 폭이다. 기록이 0개나 1개여도 d는 0이다. d가 k 이하면 `ORDERED <d>`를 출력한다.

[4.9] d가 k보다 크면 `VIOLATION <d> <earlierId> <laterId>`를 출력한다. 두 ID는 ID 순서에서 앞·뒤에 놓이며 실제 시각 차이가 정확히 d인 증거 쌍이다. 그런 쌍이 여러 개면 earlierId가 가장 작은 쌍을 택하고 그것도 같으면 laterId가 가장 작은 쌍을 택한다. d는 양수인 경우에만 증거 쌍을 출력한다. AUDIT도 기록을 변경하지 않으므로 APPEND와 조회를 번갈아 수행하거나 같은 조회를 반복할 수 있다.

## 5. 오류 규칙

[5.1] ORDER_BEGIN을 제외한 이 단계 명령은 분석 세션이 있는지 먼저 확인하고 없으면 `ERR SESSION`을 출력한다. STREAM은 세션, 기계 범위, offset 범위, 중복 순서로 확인한다. APPEND는 세션, 흐름 존재, actual 범위, ID 범위, ID의 기계 번호, offset 일치, 흐름 내 순서 순으로 확인한다. AUDIT는 세션 다음 k를 확인한다. MERGE에는 세션 외의 오류 조건이 없다.

[5.2] 어떤 오류에서도 세션의 배치·bound·흐름·기록과 두 발급 영역의 상태는 모두 보존한다. 성공한 분석 명령도 1·2단계의 설정·발급 이력을 바꾸지 않는다. 숫자의 파싱 가능 여부, 이름 형식, 토큰 수는 이전 단계처럼 입력 보장이다.

## 6. 예시

[6.1] 다음 예시는 실제로 나중에 생성된 ID 7이 먼저 병합되는 경우다. 0·1번 기계의 offset은 각각 +2, −2다. ID 7은 기록 시각 1·기계 1·순번 1이며 ID 16은 기록 시각 4·기계 0·순번 0이다. 실제 시각 차이는 `3 − 2 = 1`이므로 k가 0이면 위반하고 1이면 만족한다.

```text
입력
CONFIG 5 1 1 0 WAIT
ORDER_BEGIN 2
STREAM fast 0 2
STREAM slow 1 -2
APPEND fast 2 16
APPEND slow 3 7
MERGE
AUDIT 0
AUDIT 1
APPEND slow 2 2
MERGE

출력
OK
OK
OK
OK
OK
OK
IDS 7 16
VIOLATION 1 7 16
ORDERED 1
ERR ORDER
IDS 7 16
```

[6.2] 인접 기록만 비교해서는 최대 역전 폭을 구할 수 없다. 아래의 ID 순서는 80, 84, 90이고 실제 시각은 10, 9, 8이다. 인접 역전은 각각 1이지만 전체 최댓값은 2다. 중간 CONFIG 변경은 이미 열린 분석 세션의 배치를 바꾸지 않는다.

```text
입력
CONFIG 5 2 1 0 REJECT
ORDER_BEGIN 3
STREAM a 0 0
STREAM b 2 1
STREAM c 0 3
STREAM c 1 3
APPEND a 10 80
APPEND b 9 84
APPEND c 8 90
MERGE
AUDIT 1
CONFIG 2 1 1 0 WAIT
AUDIT 2

출력
OK
OK
OK
OK
ERR EXISTS
OK
OK
OK
OK
IDS 80 84 90
VIOLATION 2 80 90
OK
ORDERED 2
```

## 7. 검사 방식

[7.1] 테스트마다 새 프로세스에 전체 명령을 표준 입력으로 전달한다. 출력의 줄 끝 공백·탭·CR과 마지막 빈 줄을 제거한 뒤 줄 수와 각 줄을 정확히 비교하며 종료 코드가 0이 아니면 실패다. 컴파일 시간을 제외한 한 테스트의 제한 시간은 20초다. 앞 두 단계의 테스트도 누적 적용한다.

[7.2] 이 단계의 확장 입력은 전체 최대 250,000개 명령을 허용한다. 한 세션에 최대 4,096개 흐름과 최대 120,000개 기록이 온다. 모든 MERGE·AUDIT 호출이 조회하는 기록 수의 합은 최대 1,000,000이다. 새 ORDER_BEGIN으로 비운 기록도 이 합에서는 이미 조회한 만큼 계산한다. 앞 단계 명령은 각 단계의 명령만 세어 최대 30,000개이며, 기계·샤드 개수와 시각 표본 수는 해당 단계 상한을 따른다. ID와 실제 시각을 저장하는 방식은 지정하지 않는다.

[7.3] 마지막 대규모 테스트는 최대 120,000개 기록에 대해 MERGE와 AUDIT를 수행한다. 모든 쌍을 일일이 비교하는 AUDIT는 이 규모를 처리해야 하므로 허용되지 않는다. 그 밖의 시간 복잡도나 병합 알고리즘은 지정하지 않는다. 앞뒤 기록 사이에 여러 기록이 끼는 역전, 증거 쌍의 동률, 정확히 k인 경계, 큰 Long 값, 빈 흐름, 실패 후 상태 보존, 세션 배치의 독립성을 함께 확인한다.

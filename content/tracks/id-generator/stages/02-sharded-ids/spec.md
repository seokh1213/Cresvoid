# 샤드 번호를 담은 ID

## 1. 개요

[1.1] ID의 가운데 필드에 논리 샤드 번호를 담는 별도 발급 영역을 추가한다. 논리 샤드와 물리 서버의 대응표를 관리하고 샤드를 옮긴 뒤에도 과거 ID로 현재 서버를 찾게 한다. 1단계의 명령과 출력은 그대로 유지한다. 예상 구현 시간은 2시간이다.

[1.2] 이 단계의 샤드 설정·대응표·발급 상태는 1단계의 CONFIG·NODE 상태와 독립적이다. CONFIG를 다시 적용해도 샤드 영역은 유지되고, SHARD_CONFIG를 다시 적용해도 1단계 영역은 유지된다. 두 영역 사이의 ID 고유성이나 ID만으로 영역을 판별하는 기능은 보장하지 않는다. 샤드 명령에 쓰는 ID는 샤드 설정으로만 해석한다.

## 2. 배경 개념

[2.1] 논리 샤드는 데이터가 속하는 고정된 구획이고, 물리 서버는 그 구획을 현재 보관하는 위치다. 서버를 ID에 직접 넣으면 데이터를 옮길 때 과거 ID의 위치 정보가 낡는다. 논리 샤드를 넣고 별도 대응표로 현재 서버를 찾으면 ID를 바꾸지 않고 구획의 위치를 옮길 수 있다. ID만으로 알 수 있는 것은 논리 샤드까지이며 현재 서버를 알려면 대응표가 필요하다.

[2.2] 재배치 중에도 같은 논리 샤드의 이전 발급 상태가 이어져야 한다. 서버가 바뀌었다는 이유로 순번을 초기화하면 같은 밀리초에 같은 ID를 다시 만들 수 있다. 실제 시스템에는 단일 작성자 보장과 상태 이전 절차가 필요하다. 이 과제에서는 명령 하나가 원자적으로 소유권과 발급 상태를 함께 넘기는 것으로 모델링한다. 실제 데이터 복사나 장애 복구 프로토콜은 구현 범위에 포함하지 않는다.

[2.3] [Instagram Engineering, Sharding & IDs at Instagram](https://instagram-engineering.tumblr.com/post/10853187575/sharding-ids-at-instagram)은 많은 논리 샤드를 더 적은 물리 서버에 대응시키고 ID에 논리 샤드 번호를 담는 사례다. 원문의 41·13·10비트 배치와 DB 시퀀스 사용을 그대로 복제하지 않는다. 이 과제는 1단계처럼 부호 비트를 예약하고 밀리초별 순번과 대기 정책을 사용한다. 비트 배치·재배치·오류에 관한 아래 규칙이 채점 계약이다.

## 3. 입출력 규칙

[3.1] 줄 단위 입력, EOF, 빈 줄, 토큰 구분, 숫자와 이름의 형식, 출력 형식은 1단계를 따른다. 서버 이름도 1단계의 이름 정규식을 만족한다. 새 명령도 성공이나 실패마다 한 줄을 출력한다. 1단계에서 유효했던 입력의 출력은 바뀌지 않는다.

[3.2] 이 단계 명령은 SHARD_CONFIG, PLACE, MOVE, SHARD_NEXT, SHARD_DECODE, LOCATE다. 비트 수나 샤드 번호에 의미상 범위를 벗어난 정수가 올 수 있지만, 각 명령의 토큰 수와 숫자·이름 형식은 올바르다. SHARD_NEXT의 r은 1 이상이며 뒤에 정확히 r개의 표본이 온다.

## 4. 명령 규칙

[4.1] `SHARD_CONFIG <t> <h> <s> <epoch> <policy>`는 샤드 영역을 설정한다. t, h, s는 각각 1 이상이고 합이 63 이하여야 한다. epoch는 0 이상이고 `epoch + 2^t − 1`이 Long.MAX_VALUE 이하여야 한다. policy는 REJECT 또는 WAIT 중 하나다. 잘못된 설정은 `ERR CONFIG`다. 성공하면 샤드 설정을 교체하고 대응표와 모든 샤드의 발급 이력을 지운 뒤 `OK`를 출력한다.

[4.2] ID의 낮은 쪽부터 s비트는 순번, 다음 h비트는 논리 샤드 번호, 다음 t비트는 경과 밀리초다. 식은 `(time − epoch) × 2^(h+s) + shard × 2^s + seq`다. 유효한 shard는 0 이상 2^h 미만이다. 같은 논리 샤드 안에서는 단 하나의 발급 이력을 공유하고 서로 다른 논리 샤드의 발급 이력은 독립적이다. 물리 서버 이름은 ID에 들어가지 않는다.

[4.3] `PLACE <shard> <server>`는 아직 배치하지 않은 샤드를 server에 배치한다. 샤드 번호가 범위 밖이면 `ERR SHARD`, 이미 대응표에 있으면 같은 서버를 지정해도 `ERR EXISTS`다. 성공하면 아직 발급 이력이 없는 샤드를 등록하고 `OK`를 출력한다. 물리 서버는 이름이 처음 쓰일 때부터 존재하는 것으로 취급하며 별도 등록이나 수용량 제한은 없다. 한 서버에 여러 샤드를 둘 수 있다.

[4.4] `MOVE <shard> <from> <to>`는 현재 소유자가 from인 샤드를 to로 옮긴다. 번호가 범위 밖이면 `ERR SHARD`, 배치되지 않았으면 `ERR UNMAPPED`, 현재 소유자가 from과 다르면 `ERR OWNER`다. 성공하면 대응표의 서버만 바꾸고 마지막 발급 시각과 순번을 그대로 보존한 뒤 `OK`를 출력한다. from과 to가 같아도 소유자 검사를 통과하면 성공하며 발급 상태는 유지된다. 과거 소유자는 이동 직후부터 발급할 수 없다.

[4.5] `SHARD_NEXT <shard> <server> <r> <time1> ... <timer>`는 현재 소유자인 server에서 해당 논리 샤드의 ID 한 개를 발급한다. 번호가 범위 밖이면 `ERR SHARD`, 배치되지 않았으면 `ERR UNMAPPED`, server가 현재 소유자와 다르면 `ERR OWNER`다. 소유자가 맞으면 모든 시각 표본의 범위를 검사한다. 하나라도 epoch 미만이거나 경과 밀리초가 2^t 이상이면 `ERR TIME`이다.

[4.6] 시각 표본의 관측, 첫 순번 0, 같은 밀리초의 증가, 순번 소진 시 대기, REJECT의 즉시 `ERR CLOCK`, WAIT의 역행 표본 건너뛰기, 표본 소진의 `ERR WAIT`는 1단계 NEXT와 같다. 이때 t·s·epoch·policy는 SHARD_CONFIG의 값이며 마지막 발급 시각과 순번은 해당 논리 샤드의 값이다. 성공 출력은 `ID <id>`다. 실패 시 발급 이력과 대응표를 모두 보존한다.

[4.7] `SHARD_DECODE <id>`는 현재 샤드 설정으로 해석해 `PARTS <절대 시각> <논리 샤드 번호> <순번>`을 출력한다. 0 이상이고 2^(t+h+s) 미만인 ID가 유효하다. 부호 비트와 사용하지 않는 상위 비트는 0이어야 한다. 해당 샤드의 배치 여부나 실제 발급 여부는 검사하지 않으며 범위 밖이면 `ERR ID`다.

[4.8] `LOCATE <id>`는 SHARD_DECODE와 같은 범위 검사를 한 뒤 논리 샤드 번호를 얻는다. ID가 범위 밖이면 `ERR ID`, 해당 샤드가 대응표에 없으면 `ERR UNMAPPED`다. 성공하면 `SHARD <논리 샤드 번호> <현재 서버 이름>`을 출력한다. 이동 전에 발급한 ID도 이동 후의 서버를 가리킨다. 조회는 어떤 상태도 바꾸지 않는다.

## 5. 오류 규칙

[5.1] SHARD_CONFIG 이외의 이 단계 명령은 먼저 샤드 설정 유무를 확인하고 없으면 `ERR UNCONFIGURED`를 출력한다. 1단계 CONFIG만 적용한 상태에서도 같다. 잘못된 SHARD_CONFIG는 이전 샤드 설정·대응표·발급 이력을 그대로 남긴다. 모든 오류에서 해당 명령의 변경은 전혀 일어나지 않으며 다음 줄 처리를 계속한다.

[5.2] PLACE는 설정, 샤드 범위, 중복 순서로 확인한다. MOVE는 설정, 샤드 범위, 배치 여부, 현재 소유자 순서다. SHARD_NEXT는 설정, 샤드 범위, 배치 여부, 현재 소유자, 전체 시각 표본 범위, 표본 관측 순서다. SHARD_DECODE는 설정과 ID 범위, LOCATE는 설정과 ID 범위와 배치 여부 순서다. 둘 이상 어겨도 이 순서에서 처음 만난 오류만 출력한다.

## 6. 예시

[6.1] 아래 예시는 시각·샤드·순번 3·2·1비트를 사용한다. shard 2의 시각 102·순번 0은 `2 × 8 + 2 × 2 = 20`이다. 재배치 후 시각 102에서 계속 발급하면 순번 1을 사용한다. 다음 발급은 같은 시각의 순번을 모두 썼으므로 103을 기다린다.

```text
입력
SHARD_CONFIG 3 2 1 100 WAIT
PLACE 2 db-a
SHARD_NEXT 2 db-a 1 102
MOVE 2 db-a db-b
LOCATE 20
SHARD_NEXT 2 db-a 1 103
SHARD_NEXT 2 db-b 1 102
SHARD_NEXT 2 db-b 2 102 103
SHARD_DECODE 28
MOVE 2 db-a db-c
LOCATE 21

출력
OK
OK
ID 20
OK
SHARD 2 db-b
ERR OWNER
ID 21
ID 28
PARTS 103 2 0
ERR OWNER
SHARD 2 db-b
```

[6.2] 샤드 영역과 기존 생성기 영역은 별개다. 아래의 두 CONFIG는 샤드 대응표를 지우지 않는다. 발급하지 않은 ID 6도 해석할 수 있지만, 대응하는 샤드 3이 없으므로 위치 조회는 실패한다.

```text
입력
CONFIG 2 1 1 0 REJECT
SHARD_CONFIG 2 2 1 0 REJECT
PLACE 1 primary
SHARD_DECODE 6
LOCATE 6
CONFIG 3 1 1 0 WAIT
LOCATE 2
SHARD_CONFIG 0 2 1 0 WAIT
LOCATE 2

출력
OK
OK
OK
PARTS 0 3 0
ERR UNMAPPED
OK
SHARD 1 primary
ERR CONFIG
SHARD 1 primary
```

## 7. 검사 방식

[7.1] 테스트마다 새 프로세스의 표준 입력에 명령을 전달한다. 출력 비교와 종료 코드 판정은 1단계와 같으며, 컴파일 시간을 제외한 테스트 한 건의 제한 시간은 15초다. 이 단계 구현에는 1단계 테스트도 누적 적용한다.

[7.2] 한 입력에는 최대 30,000개 명령, 최대 10,000개 배치된 논리 샤드, SHARD_NEXT 전체를 합쳐 최대 200,000개 시각 표본이 온다. 1단계 명령이 섞일 때 각 발급 영역의 개수 제한은 해당 단계의 제한도 만족한다. 별도의 성능 선별용 대규모 테스트는 두지 않으며 마지막 규모 검사는 이 상한 안에서 재배치와 발급·조회를 조합한다.

[7.3] 같은 서버의 여러 샤드, 연속 재배치, 소유권 검사 실패, 순번 소진 직전과 직후의 이동, 과거 ID의 위치 조회, 설정 실패와 두 발급 영역의 독립성을 확인한다. 실제 DB나 Docker는 필요하지 않으며 공개 API 이름은 지정하지 않는다.

# 트라이와 접두어 질의

## 1. 개요

[1.1] 검색창에 입력한 접두어로 시작하는 검색어를 빈도순으로 반환하는 프로그램을 만든다. 이 단계에서는 검색어 등록, 빈도 누적, 동점 정렬, 접두어 검색을 구현한다. 목표 작업 시간은 1~3시간이다.

[1.2] 검색어는 공백이 없는 문자열 하나다. 실제 검색창의 띄어쓰기, 초성 검색, 오타 교정, 입력기 조합 상태는 다루지 않는다. 표준 입력으로 받은 명령을 순서대로 처리하는 단일 프로세스이며, 실행할 때마다 빈 상태에서 시작한다. 파일 저장과 네트워크 통신은 없다.

## 2. 배경 개념

[2.1] 접두어는 문자열의 맨 앞부터 연속해서 취한 부분이다. `가방`의 접두어에는 빈 문자열, `가`, `가방`이 있다. 검색어 전체와 같은 접두어도 일치한다. 중간에만 나타나는 부분 문자열은 일치하지 않는다.

[2.2] 트라이는 문자열의 접두어를 공유하는 트리다. 루트는 빈 접두어를 나타내고 경로의 각 글자는 접두어를 한 글자씩 늘린다. 어떤 경로가 검색어 하나의 끝이면서 더 긴 검색어의 시작일 수 있으므로 검색어가 끝나는 사실과 다음 글자가 존재하는 사실은 다르다. 이 관계를 이용하면 접두어와 무관한 검색어를 매번 확인하는 일을 줄일 수 있다. 자료구조의 내부 표현과 탐색 방식은 직접 정한다.

[2.3] 상위 k개를 고르려면 후보의 범위와 순위 기준을 함께 정해야 한다. 같은 빈도의 후보가 많아도 항상 같은 결과를 내도록 순위에 문자열 순서를 포함한다. 빈도는 누적값이며 입력 횟수와 같지 않을 수 있다.

[2.4] 한글 완성 음절과 자모는 서로 다른 문자 코드로 표현될 수 있다. 예를 들어 `가`는 U+AC00이고 분해된 `가`는 U+1100 U+1161이다. 호환 자모 `ㄱ`은 U+3131이다. 정규화는 이런 표현 중 일부를 같은 형태로 바꾸는 작업이다. 이 트랙에서는 정규화나 초성 변환을 하지 않고 받은 코드의 열 그대로 비교한다. 따라서 `ㄱ`과 `ᄀ`은 `가방`의 접두어가 아니며 `ᄀ`은 `가`의 접두어다.

[2.5] 배경 자료는 [Princeton Algorithms의 Tries](https://algs4.cs.princeton.edu/52trie/)와 [Unicode UAX #15의 정규화 설명](https://www.unicode.org/reports/tr15/)이다. 트랙의 주제는 Alex Xu의 『System Design Interview』 1권 13장에서 가져왔다. 여기의 명령 언어와 동작 규칙은 이 과제를 위해 따로 정했다.

## 3. 입출력 규칙

[3.1] 입력은 UTF-8 텍스트이며 한 줄에 명령 하나를 쓴다. 줄바꿈은 LF 또는 CRLF다. 각 줄의 앞뒤 ASCII 공백(U+0020)과 탭(U+0009)을 무시하고 인자는 하나 이상의 ASCII 공백이나 탭으로 나눈다. 공백뿐인 줄은 무시하고 출력하지 않는다. EOF까지 처리하며 종료 명령은 없다. 명령 이름은 대문자로만 인정한다.

[3.2] 검색어와 비어 있지 않은 접두어의 길이는 1~32글자다. 허용 문자는 ASCII 소문자 `a`~`z`, 숫자 `0`~`9`, 한글 자모 U+1100~U+11FF, 호환 자모 U+3131~U+318E, 완성 음절 U+AC00~U+D7A3이다. 이 범위의 각 문자는 UTF-16 코드 단위 하나이므로 길이는 Kotlin `String.length`와 같다. 허용 문자 밖의 문자는 오류이며 대소문자 변환, 공백 합치기, 자모 분해·합성을 하지 않는다.

[3.3] 조회 명령의 접두어 인자 `*`는 빈 접두어를 뜻한다. 빈 접두어는 등록된 모든 검색어와 일치한다. `*`는 검색어로 등록할 수 없고 접두어의 일부로도 쓸 수 없다. 빈 접두어를 빈 인자로 전달하는 문법은 없다.

[3.4] 모든 숫자 인자는 ASCII 숫자 `0`~`9`만으로 이루어진 십진수다. 앞의 0은 허용하지만 부호와 소수점은 허용하지 않는다. 빈도 증가량은 1~9,223,372,036,854,775,807이고 조회 개수 k는 1~100이다. 누적 빈도도 9,223,372,036,854,775,807을 넘을 수 없다. 정수 비교는 정확하게 하며 부동소수점 근사를 쓰지 않는다.

[3.5] 빈도가 큰 검색어를 먼저 내보낸다. 빈도가 같으면 문자열을 앞에서부터 비교해 처음 다른 글자의 문자 코드가 작은 검색어를 먼저 내보낸다. 한 문자열이 다른 문자열의 접두어이면 짧은 문자열이 먼저다. 이 문자 범위에서는 Kotlin `String.compareTo`의 오름차순과 같다. 등록 순서는 순위에 영향을 주지 않는다.

[3.6] 성공한 등록은 `OK` 한 줄을 출력한다. 조회는 순서대로 `검색어:빈도`를 ASCII 공백 하나로 이어 한 줄로 출력한다. 후보가 k개보다 적으면 있는 만큼만 출력한다. 후보가 없으면 `(none)` 한 줄을 출력한다. 출력의 모든 숫자는 십진수이며 값 0을 제외하면 앞에 0을 붙이지 않는다. 정상적으로 처리한 명령은 결과 줄 하나만 내보내며 안내문이나 디버그 출력을 표준 출력에 섞지 않는다.

## 4. 명령 규칙

[4.1] `ADD <검색어> <증가량>`은 검색어의 빈도에 증가량을 더한다. 처음 보는 검색어는 빈도 0에서 더하며 이미 있는 검색어는 같은 항목의 빈도만 바꾼다. 빈도를 줄이거나 검색어를 삭제하는 명령은 없다. 성공하면 `OK`를 출력한다.

[4.2] `QUERY <k> <접두어>`는 현재까지 성공한 모든 ADD를 반영한 상태에서 접두어와 일치하는 검색어 상위 k개를 출력한다. 접두어 자체가 등록되어 있으면 후보에 포함한다. 조회는 빈도와 그 밖의 상태를 바꾸지 않는다.

[4.3] 예를 들어 빈도가 7인 `app`, `apple`, `apply`는 `app`, `apple`, `apply` 순이다. 상위 목록에 들지 못한 검색어도 빈도를 계속 유지한다. 나중에 ADD로 빈도가 높아지면 새 순위에 맞게 조회 결과에 들어간다.

## 5. 오류 규칙

[5.1] 알 수 없는 명령, 인자 개수 불일치, 잘못된 문자열, 잘못된 숫자 또는 범위 밖의 숫자를 받으면 `ERR` 한 줄을 출력한다. ADD 결과가 누적 빈도의 상한을 넘는 경우도 `ERR`다. 잘못된 줄 하나 때문에 프로세스를 종료하지 않고 다음 줄을 계속 처리한다.

[5.2] 실패한 명령은 어떤 상태도 바꾸지 않는다. 같은 줄에 오류가 여러 개 있더라도 출력은 `ERR` 한 줄뿐이다. 빈 줄은 오류가 아니라 3.1의 무시 대상이다.

## 6. 예시

[6.1] 다음 입력은 같은 빈도의 문자열 순서, 목록 밖 검색어의 재진입, 전체 조회, 오류 뒤 상태 보존을 보여 준다. 입력 코드 블록과 출력 코드 블록은 위에서부터 대응한다.

입력:
```text
ADD apple 7
ADD app 7
ADD apply 2
QUERY 2 app
ADD apply 6
QUERY 3 app
QUERY 2 *
ADD app -1
QUERY 1 app
QUERY 2 z
```

출력:
```text
OK
OK
OK
app:7 apple:7
OK
apply:8 app:7 apple:7
apply:8 app:7
ERR
apply:8
(none)
```

[6.2] 다음 입력의 두 번째 검색어는 호환 자모 `ㄱ`과 `ㅏ`의 열이고 세 번째 검색어는 U+1100 U+1161의 열이다. 화면에서 비슷하게 보이더라도 세 검색어를 합치지 않는다.

입력:
```text
ADD 가방 4
ADD ㄱㅏ 4
ADD 가 4
QUERY 5 가
QUERY 5 ㄱ
QUERY 5 ᄀ
QUERY 5 *
```

출력:
```text
OK
OK
OK
가방:4
ㄱㅏ:4
가:4
가:4 ㄱㅏ:4 가방:4
```

## 7. 검사 방식

[7.1] 검사기는 Kotlin 표준 라이브러리와 JDK 21로 프로그램을 빌드한다. 테스트마다 새 프로세스의 표준 입력으로 명령을 보낸 뒤 입력을 닫는다. 종료 코드는 0이어야 한다. 각 출력 줄 끝의 공백·탭·CR과 전체 출력 끝의 빈 줄을 제거한 뒤 기대 출력과 줄 수 및 문자를 비교한다. 줄 안의 공백, 문자열 순서, 숫자 표기는 그대로 비교한다. 시작 코드는 `main`의 TODO를 채우는 곳부터 구현한다.

[7.2] 고정 예시와 오류 조합, 한글 표현 구분, 무작위 입력을 검사한다. 작은 테스트는 테스트 하나당 실행 제한 시간 10초다. 빌드 시간은 실행 제한 시간에 포함하지 않는다. 입력과 출력은 각각 64MiB 이하이며, 정상 입력에서 서로 다른 검색어는 최대 2,000,000개다. 제한 수량은 검사 데이터의 상한이며, 이를 넘는 입력에 대한 오류 처리는 요구하지 않는다.

[7.3] 마지막 대규모 테스트는 서로 다른 검색어 2,000,000개를 포함하고 ADD는 최대 2,050,000회, QUERY는 최대 50,000회다. 검색어 길이는 최대 12이고, 빈 접두어를 포함해 실제로 존재하는 서로 다른 접두어 수는 최대 2,500,000개다. 빈 접두어 조회는 최대 5회이며, 나머지 조회마다 일치하는 검색어는 최대 32개다. 실행 제한 시간은 120초다. 이 규모는 모든 조회에서 전체 검색어를 훑는 방식과 접두어로 후보 범위를 좁히는 방식의 비용 차이를 확인하기 위한 것이다.

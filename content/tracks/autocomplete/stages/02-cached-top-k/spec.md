# 노드별 상위 k 저장과 갱신

## 1. 개요

[1.1] 1단계 프로그램에 상위 목록 캐시를 더한다. 즉시 갱신 모드와 일괄 재생성 모드에서 같은 등록을 처리하고, 조회 결과의 최신성과 논리 작업량을 비교한다. 목표 작업 시간은 1~3시간이다. 1단계의 입력 문법, ADD·QUERY 출력, 순위와 오류 규칙은 그대로 유지한다.

[1.2] 실시간 원본과 캐시가 보여 주는 상태를 구분한다. QUERY는 항상 원본을 조회한다. 새 명령 CQUERY만 캐시를 조회하므로 일괄 모드에서도 QUERY의 기존 의미는 바뀌지 않는다. 이 단계의 명령을 쓰지 않은 실행에는 캐시가 없다.

## 2. 배경 개념

[2.1] 접두어의 상위 목록을 미리 저장하면 조회할 때 그 접두어 아래의 모든 후보를 다시 정렬하지 않아도 된다. 트라이 노드에 상위 목록을 두는 것이 대표적인 예다. 저장할 수 있는 개수는 제한되어 있으므로 목록 밖의 검색어도 원본에는 남아 있어야 한다. 저장 목록과 원본을 같은 것으로 취급하면 이후 빈도가 커진 검색어를 놓칠 수 있다.

[2.2] 즉시 갱신은 등록이 끝난 뒤 바로 새 순위를 볼 수 있는 대신 등록 경로에서 작업한다. 일괄 재생성은 그 작업을 모으지만 재생성 전까지 오래된 결과를 보여 준다. 동일한 검색어를 여러 번 갱신하면 즉시 갱신은 매번 비용을 치르는 반면, 전체 재생성 비용은 그 시점의 검색어 수와 길이에 의해 정해진다. 반대로 변경이 적은데 전체를 다시 만들면 낭비가 커진다.

[2.3] 실행 시간은 기계의 부하에 따라 달라지므로 이 단계의 COST는 밀리초가 아닌 논리 작업량을 출력한다. 한 검색어의 현재 빈도를 접두어 하나의 순위에 반영하는 일을 1단위로 센다. 길이 L인 검색어에는 빈 접두어와 전체 검색어를 포함해 L+1개의 접두어가 있다. 이것은 비교를 위한 비용 모형이며 실제 자료구조의 명령 횟수나 메모리 사용량을 뜻하지 않는다. 내부 표현과 캐시 유지 방법은 직접 정한다.

## 3. 입출력 규칙

[3.1] 새 명령은 `CACHE <모드> <용량>`, `CQUERY <k> <접두어>`, `REFRESH`, `COST`다. 모드는 정확히 `IMMEDIATE` 또는 `BATCH`이고 용량은 1~100이다. 용량과 k의 숫자 문법은 1단계와 같다. CQUERY의 접두어와 출력 형식도 QUERY와 같다.

[3.2] 캐시의 논리 상태는 생성 또는 갱신 시점의 검색어와 그때의 빈도를 담는다. 조회 때 원본의 새 빈도만 가져와 오래된 순서와 섞어서는 안 된다. 각 접두어의 결과는 해당 캐시 상태에서 순위를 매긴 상위 용량 개까지이며, CQUERY는 그중 처음 k개를 출력한다.

[3.3] 논리 작업량은 `incremental`과 `rebuilt` 두 누적 카운터로 나눈다. 두 값은 0 이상의 정수이고 출력은 `incremental=<값> rebuilt=<값>` 한 줄이다. 실제 실행 시간이나 구현 방식과 관계없이 아래 명령 규칙의 수식대로 계산한다. 검사 데이터에서 두 누적값은 각각 9,223,372,036,854,775,807 이하임을 보장한다.

## 4. 명령 규칙

[4.1] `CACHE <모드> <용량>`은 현재 원본 전체를 바탕으로 캐시 하나를 새로 만들고 `OK`를 출력한다. 이미 캐시가 있으면 모드, 용량, 저장 내용과 카운터를 모두 교체한다. 생성 직후 incremental은 0이고 rebuilt는 현재 서로 다른 검색어 각각의 `(길이+1)`을 합한 값이다. 빈 원본에서는 두 값이 모두 0이다. 생성 전에 성공한 ADD는 incremental에 포함하지 않는다.

[4.2] 캐시가 IMMEDIATE 모드이면 성공한 ADD마다 그 등록이 만든 원본 상태를 즉시 반영한다. incremental에는 그 ADD의 검색어 길이에 1을 더한 값을 더한다. 검색어가 신규인지, 기존인지, 상위 용량 개에 드는지와 무관하게 같은 수식을 쓴다. rebuilt는 바꾸지 않는다. 성공한 ADD를 마친 뒤 CQUERY와 QUERY는 k가 용량 이하이면 같은 결과를 내야 한다.

[4.3] 캐시가 BATCH 모드이면 ADD는 원본만 바꾼다. 캐시의 검색어, 빈도, 순위와 두 카운터는 모두 그대로다. 따라서 생성 또는 직전 REFRESH 이후에 추가된 검색어와 바뀐 빈도는 CQUERY에 나타나지 않는다. 성공한 ADD의 `OK` 출력은 두 모드에서 같다.

[4.4] `REFRESH`는 모드와 용량을 유지한 채 현재 원본 전체로 캐시를 다시 만들고 `OK`를 출력한다. rebuilt에 현재 서로 다른 검색어 각각의 `(길이+1)`을 합한 값을 더하고 incremental은 유지한다. 두 모드에서 모두 사용할 수 있다. 바뀐 검색어가 없어도 같은 작업량을 더한다. 빈 원본이라면 더하는 값은 0이다.

[4.5] `CQUERY <k> <접두어>`는 현재 캐시 상태의 상위 k개를 출력한다. 캐시가 필요하며 k는 현재 용량 이하여야 한다. 현재 원본에만 있는 접두어는 BATCH 캐시에서 `(none)`일 수 있다. 조회는 캐시를 자동으로 만들거나 갱신하지 않고 카운터도 바꾸지 않는다.

[4.6] `COST`는 현재 캐시의 두 카운터를 3.3의 형식으로 출력한다. COST와 QUERY는 갱신 작업량에 포함하지 않는다. 캐시가 없는 동안의 ADD도 작업량을 기록하지 않는다.

## 5. 오류 규칙

[5.1] 캐시를 만들기 전에 CQUERY, REFRESH, COST를 실행하면 `ERR`다. 알 수 없는 모드, 범위 밖 용량, 현재 용량보다 큰 CQUERY의 k, 잘못된 인자도 `ERR`다. 나머지는 1단계의 오류 규칙을 따른다.

[5.2] 실패한 명령은 원본, 모드, 용량, 저장 내용과 두 카운터를 모두 보존한다. 특히 빈도 상한을 넘은 ADD는 캐시도 갱신하지 않고 incremental도 더하지 않는다. 잘못된 CACHE는 기존 캐시를 지우지 않는다.

## 6. 예시

[6.1] 다음 입력에서는 `app`의 논리 작업량이 4이고 `apple`과 `apply`는 각각 6이므로 최초 rebuilt가 16이다. BATCH는 재생성 전의 빈도까지 보존한다. CACHE로 모드를 바꾸면 카운터를 새로 시작한다.

입력:
```text
ADD app 7
ADD apple 7
ADD apply 2
CACHE BATCH 2
COST
ADD apply 6
CQUERY 2 app
QUERY 2 app
REFRESH
CQUERY 2 app
COST
CACHE IMMEDIATE 2
ADD apple 5
CQUERY 2 app
COST
CQUERY 3 app
COST
```

출력:
```text
OK
OK
OK
OK
incremental=0 rebuilt=16
OK
app:7 apple:7
apply:8 app:7
OK
apply:8 app:7
incremental=0 rebuilt=32
OK
OK
apple:12 apply:8
incremental=6 rebuilt=16
ERR
incremental=6 rebuilt=16
```

[6.2] 다음 입력은 캐시보다 나중에 생긴 검색어, 빈 원본 재생성, 캐시 생성 전 오류를 보여 준다. BATCH의 빈 캐시는 ADD 뒤에도 그대로 남는다.

입력:
```text
COST
CACHE BATCH 1
REFRESH
ADD 가 9
CQUERY 1 *
QUERY 1 *
COST
REFRESH
CQUERY 1 *
COST
```

출력:
```text
ERR
OK
OK
OK
(none)
가:9
incremental=0 rebuilt=0
OK
가:9
incremental=0 rebuilt=2
```

## 7. 검사 방식

[7.1] 1단계와 같은 표준 입력 및 줄 단위 출력 비교를 사용한다. 1단계 검사도 누적 실행한다. 작은 테스트의 실행 제한 시간은 각각 10초다. 캐시 생성 시점, 목록 밖 항목의 재진입, 동점 재정렬, 잘못된 명령 뒤 상태와 비용 보존, 모드 교체를 검사한다.

[7.2] 마지막 대규모 테스트는 서로 다른 검색어 2,000,000개, 검색어 길이 최대 12, 빈 접두어를 포함한 서로 다른 접두어 최대 2,500,000개를 사용한다. ADD는 최대 2,050,000회, CACHE와 REFRESH는 합쳐 최대 6회, CQUERY는 최대 50,000회, QUERY는 최대 20회, COST는 최대 100회다. 캐시 용량과 각 조회의 k는 최대 5다. 빈 접두어 또는 많은 검색어가 공유하는 짧은 접두어를 반복 조회하고 소수 검색어의 빈도를 여러 번 올린다. 실행 제한 시간은 180초다. 입력과 출력은 각각 64MiB 이하다.

[7.3] 대규모 테스트는 조회마다 접두어 아래 전체 검색어를 다시 훑거나, IMMEDIATE의 ADD마다 원본 전체를 다시 처리하는 비용을 구별하기 위한 것이다. COST는 이 시간 제한을 대신하는 성능 측정값이 아니다. 배치 결과의 지연과 논리 작업량은 출력으로, 반복 조회와 갱신의 비용은 실행 제한으로 따로 확인한다.

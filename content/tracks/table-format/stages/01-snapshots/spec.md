# 1단계: 스냅숏과 매니페스트

## 1. 개요

[1.1] 이 트랙에서는 메모리 안의 가짜 객체 저장소 위에서 테이블 하나를 관리하는 테이블 포맷을 만든다. 프로그램은 표준 입력에서 명령을 한 줄씩 읽어 실행하고 결과를 표준 출력에 쓴다. 1단계에서는 메타데이터 파일, 스냅숏, 매니페스트 목록, 매니페스트로 이루어진 메타데이터 계층을 만들고 커밋할 때마다 스냅숏을 하나씩 더한다. 현재 스냅숏과 과거 스냅숏을 읽을 수 있고 숨은 파티셔닝과 열 값의 하한·상한으로 조건에 맞는 행이 있을 수 있는 파일만 골라 읽는다.

[1.2] 1단계의 명령은 아래 열 가지다.

| 명령 | 하는 일 | 정상 출력 |
|---|---|---|
| `CREATE <열 정의> … [PARTITION <파티션 필드> …]` | 테이블을 만든다 | 1줄 |
| `BEGIN <트랜잭션>` | 트랜잭션을 시작한다 | 1줄 |
| `APPEND <트랜잭션> <파일> <행> …` | 데이터 파일을 써서 트랜잭션이 더할 파일로 적는다 | 1줄 |
| `REMOVE <트랜잭션> <파일>` | 테이블에서 지울 데이터 파일을 트랜잭션에 적는다 | 1줄 |
| `COMMIT <트랜잭션>` | 트랜잭션을 커밋한다 | 1줄 |
| `SNAPSHOTS` | 현재 메타데이터 파일의 스냅숏 목록을 보여 준다 | 여러 줄 |
| `MANIFESTS <스냅숏>` | 스냅숏의 매니페스트 목록을 보여 준다 | 여러 줄 |
| `ENTRIES <매니페스트>` | 매니페스트의 항목을 보여 준다 | 여러 줄 |
| `LS` | 객체 저장소에 있는 객체의 이름을 보여 준다 | 여러 줄 |
| `SCAN [AT <스냅숏>] [WHERE <조건> …]` | 스냅숏 하나를 조건으로 읽는다 | 여러 줄 |

[1.3] 2단계는 같은 메타데이터 파일에서 시작한 트랜잭션들이 차례로 커밋할 때 생기는 교체 실패와 재시도, 충돌 판정을 다룬다. 2단계는 압축, 스냅숏 만료, 고아 파일 정리도 더한다. 3단계는 위치 삭제와 동등 삭제를 더하고 읽을 때 순서 번호로 삭제를 적용하며 압축이 삭제를 데이터 파일에 반영하게 한다. 이 문서의 입출력 규칙과 명령 규칙은 3단계까지 그대로 적용한다. 뒤 단계는 이 문서가 정한 출력을 바꾸지 않는다. 이 문서는 뒤 단계에서 뜻이 생기는 입력의 출력을 정하지 않는다. 그런 입력은 4.44 에 적는다.

## 2. 배경 개념

[2.1] 디렉터리 테이블은 분산 저장소의 디렉터리 하나를 파티션 하나로 삼고 그 아래 파일의 행을 모두 테이블의 행으로 본다. 질의를 계획하려면 읽을 파티션마다 디렉터리 목록을 받아야 하고 여러 파티션에 걸친 변경은 디렉터리마다 따로 반영되어 한 번에 커밋되지 않는다. Apache Iceberg 같은 테이블 포맷은 테이블에 속한 파일을 디렉터리 단위로 다루지 않고 메타데이터에 하나씩 적는다. 쓰는 쪽은 파일을 먼저 써 두고 메타데이터를 바꾸는 커밋 한 번으로 그 파일들을 테이블에 넣는다.

[2.2] 테이블의 상태는 메타데이터 파일에 있다. 메타데이터 파일은 스키마, 파티션 설정, 스냅숏 목록과 그 가운데 현재 스냅숏이 무엇인지를 담는다. 스냅숏은 어느 시점에 테이블에 속한 데이터 파일 전체를 나타내며 매니페스트 목록 하나를 가리킨다. 매니페스트 목록은 여러 매니페스트를 가리키고 매니페스트는 데이터 파일마다 경로, 파티션 값, 행 수, 열 값의 하한과 상한을 적는다. 이 계층의 파일은 한 번 쓰면 고치지 않는다. 그래서 바뀐 내용은 새 파일로 쓰고 바뀌지 않은 매니페스트는 다음 스냅숏의 매니페스트 목록에 그대로 다시 넣는다.

[2.3] 커밋은 테이블의 현재 메타데이터 파일을 가리키는 포인터를 새 메타데이터 파일로 바꾸는 한 번의 원자적 교체다. 이 트랙은 메타데이터 파일 하나를 테이블의 판 하나로 보고 포인터가 가리키는 판을 현재 판이라 한다. 메타데이터 파일, 매니페스트 목록, 매니페스트, 데이터 파일을 쓰는 일은 원자적이지 않다. 교체 전에는 새로 쓴 파일이 테이블에 속하지 않으므로 여러 파티션에 걸친 변경도 모두 보이거나 하나도 보이지 않는다. 읽는 쪽은 스냅숏 하나를 골라 그 스냅숏이 가리키는 파일만 읽는다. 옛 스냅숏이 메타데이터 파일에 남아 있는 동안 그 스냅숏으로 그 시점의 테이블을 그대로 다시 읽는 일을 시간 여행이라 한다.

[2.4] 매니페스트의 항목에는 상태가 있다. ADDED 는 그 항목에 적힌 스냅숏이 파일을 더했다는 뜻이고 EXISTING 은 앞선 스냅숏이 더한 파일이 테이블에 남아 있다는 뜻이다. DELETED 는 그 항목에 적힌 스냅숏이 파일을 테이블에서 지웠다는 기록이다. Iceberg 명세는 DELETED 항목을 정보로만 남기고 조회에 사용하지 않는다고 정한다. 파일을 지우는 커밋은 그 파일이 든 매니페스트를 고칠 수 없으므로 매니페스트를 새로 쓴다. 새로 쓴 매니페스트에서 지운 파일은 DELETED 가 되고 남은 파일은 EXISTING 이 된다.

[2.5] 커밋에 성공한 스냅숏에는 앞선 스냅숏보다 큰 순서 번호가 붙고 스냅숏이 더한 파일은 그 번호를 이어받는다. Iceberg 는 새 파일을 적은 매니페스트에 순서 번호를 비워 두고 읽을 때 매니페스트 목록에 적힌 번호로 채운다. 커밋을 다시 시도해 번호가 바뀌어도 매니페스트 목록만 새로 쓰면 되게 하려는 설계다. 순서 번호는 3단계에서 어느 삭제가 어느 데이터 파일에 적용되는지를 정한다.

[2.6] 파티션 설정은 원본 열의 값에 변환을 적용해 파티션 값을 만든다. `day` 변환은 시각에서 날짜를 꺼내고 `bucket[N]` 변환은 값의 해시를 N 으로 나눈 나머지를 결과로 삼는다. 이렇게 얻은 값은 메타데이터에만 적히고 테이블의 열이 아니어서 숨은 파티셔닝이라 한다. 쓰는 쪽은 파티션 값을 직접 넣지 않고 질의도 데이터 열에 조건을 건다. 계획할 때는 데이터 열의 조건을 파티션 값의 조건으로 바꾸는데 맞는 행이 있을 수 있는 파티션을 빠뜨리지 않도록 넓게 바꾼다. Iceberg 명세는 이 방식을 포함 투영(inclusive projection)이라 부르고 `ts > X` 를 `ts_day >= day(X)` 로 바꾸는 예를 든다. 이 트랙의 4.37 도 같은 방식이지만 X 의 시·분·초가 23:59:59 이면 이 예보다 좁다. 시각을 초 단위로 적으므로 날짜 day(X) 에는 X 보다 뒤인 시각이 없어 4.37 은 day(X) 를 허용하지 않는다. 해시는 값의 순서를 보존하지 않으므로 `bucket` 필드로는 같음 조건만 파티션을 거를 수 있다.

[2.7] 읽기는 세 층에서 파일을 건너뛴다. 매니페스트 목록은 매니페스트마다 파티션 필드 값의 범위를 적어 두므로 조건에 맞는 파티션이 들어 있을 수 없는 매니페스트는 열지 않는다. 연 매니페스트에서는 항목의 파티션 값과 열 값의 하한·상한으로 조건에 맞는 행이 있을 수 없는 파일을 건너뛴다. 남은 파일만 행을 읽어 조건과 맞춰 본다. 앞의 두 층은 넓게 거르므로 고른 파일에 조건에 맞지 않는 행이 섞일 수 있고 맞는 행이 하나도 없는 파일을 고를 수도 있다.

[2.8] 이 트랙은 Iceberg 를 단순하게 줄인다. 실제 JSON·Avro 메타데이터 형식 대신 명령의 출력으로 메타데이터를 보여 준다. 스냅숏 ID 는 무작위 수가 아니라 그 스냅숏을 커밋한 트랜잭션의 이름이고 파일 이름은 4.13 의 규칙을 따른다. `bucket` 의 해시는 32비트 Murmur3 대신 손으로 셀 수 있는 4.10 의 식을 사용한다. 테이블에는 스키마와 파티션 설정이 하나씩만 있고 바꿀 수 없다. 열 값에는 null 이 없고 시각은 시간대 없이 초 단위로 적는다. Iceberg 의 쓰는 쪽은 작은 매니페스트를 하나로 합치기도 하지만 이 트랙은 합치지 않는다.

## 3. 입출력 규칙

[3.1] 프로그램은 표준 입력에서 명령을 한 줄씩 읽어 입력이 끝날 때까지 처리하고 결과를 표준 출력에 쓴다.

[3.2] 입력이 끝나면 종료 코드 0 으로 끝난다. 커밋하지 않은 트랜잭션이 남아 있어도 아무것도 출력하지 않고 끝난다.

[3.3] 입력은 UTF-8 이다. 줄은 LF(U+000A)로 나눈다. 마지막 줄 뒤에 LF 가 없어도 그 줄을 처리한다.

[3.4] 이 문서에서 공백은 U+0020 한 글자만 가리킨다. 탭(U+0009)과 CR(U+000D)은 공백이 아니다.

[3.5] 줄 앞뒤의 공백은 무시한다. 빈 줄과 공백만 있는 줄은 건너뛰고 아무것도 출력하지 않는다.

[3.6] 명령어는 줄 맨 앞부터 첫 공백 바로 앞까지다. 공백이 없으면 줄 전체가 명령어다. 명령어 뒤의 나머지에서 공백이 아닌 문자가 최대로 이어진 구간 하나하나가 인자다. 공백이 여럿 이어져도 빈 인자는 생기지 않는다.

[3.7] 명령어는 대소문자를 구분한다. 예약어 `PARTITION`, `AT`, `WHERE`, `AND`, 열 형식 `long`, `string`, `timestamp`, 변환 이름 `day`, `bucket` 도 대소문자를 구분한다.

[3.8] 출력하는 줄은 모두 LF 로 끝낸다.

[3.9] 프로그램은 테이블도 객체도 트랜잭션도 없는 상태로 시작한다. 이전 실행의 상태를 이어받지 않는다.

[3.10] 이 문서의 정규식은 문자열 전체에 적용한다.

[3.11] 이름은 `^[a-z][a-z0-9]{0,15}$` 에 맞는 문자열이다. 영문 소문자로 시작하고 영문 소문자와 숫자로만 된 16글자 이하의 문자열이다. 트랜잭션, 데이터 파일, 열은 이름으로 부른다. 트랜잭션 이름, 파일 이름, 열 이름은 서로 상관없으므로 같은 문자열이어도 된다.

[3.12] 문자열의 사전식 순서는 두 문자열을 앞 글자부터 차례로 비교해 처음으로 다른 글자가 나온 자리에서 그 글자의 ASCII 코드가 작은 쪽을 앞에 둔다. 다른 글자가 나오기 전에 한 문자열이 끝나면 짧은 쪽이 앞이다. 그래서 `-` 는 숫자보다 앞이고 숫자는 영문 소문자보다 앞이다. `a-m10` 은 `a-m2` 보다 앞이고 `f1` 은 `meta-1` 보다 앞이다.

[3.13] SNAPSHOTS, MANIFESTS, ENTRIES, LS, SCAN 은 첫 줄에 그 뒤에 올 줄의 수를 적고 다음 줄부터 항목을 한 줄에 하나씩 쓴다. 줄의 모양은 4절의 명령마다 정한다. 오류가 나면 오류 줄 하나만 출력한다(5.1).

[3.14] 스냅숏이 없음을 나타내는 자리에는 `-` 를 쓴다. `-` 는 이름이 아니므로 어떤 스냅숏 ID 와도 겹치지 않는다.

## 4. 명령 규칙

### 값과 행

[4.1] 열의 형식은 `long`, `string`, `timestamp` 세 가지다. `long` 값은 `^(0|-?[1-9][0-9]{0,17})$` 에 맞는 십진 정수다. 앞에 0 을 붙인 `07` 과 `-0` 은 `long` 값이 아니다. `string` 값은 `^[a-z0-9]{1,16}$` 에 맞는 문자열이다. `timestamp` 값은 `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}$` 에 맞고 4.2 를 지키는 시각이다.

[4.2] `timestamp` 값 `YYYY-MM-DDThh:mm:ss` 에서 연도 YYYY 는 1970 이상이고 월 MM 은 01~12 다. 일 DD 는 그 달에 있는 날이어야 한다. 1, 3, 5, 7, 8, 10, 12월은 31일, 4, 6, 9, 11월은 30일까지 있고 2월은 윤년에 29일, 나머지 해에 28일까지 있다. 윤년은 4로 나누어떨어지되 100으로는 나누어떨어지지 않는 해와 400으로 나누어떨어지는 해다. 시 hh 는 00~23, 분 mm 은 00~59, 초 ss 는 00~59 다. 예를 들어 `2024-02-29T10:00:00` 은 값이고 `2023-02-29T10:00:00`, `2024-03-01T24:00:00`, `2024-03-01T10:00` 은 값이 아니다. 시각에는 시간대가 없다.

[4.3] 같은 형식의 값끼리 비교한다. `long` 은 수의 크기로, `string` 은 3.12 의 사전식 순서로, `timestamp` 는 시각의 앞뒤로 비교한다. `timestamp` 값은 자릿수가 고정되어 있으므로 시각의 앞뒤는 문자열의 사전식 순서와 같다. 4.1 의 형식에서는 같은 값을 적는 방법이 하나뿐이므로 두 값이 같다는 것은 두 값을 적은 문자열이 같다는 뜻이다.

[4.4] 행은 테이블의 열 값을 쉼표(`,`)로 이은 인자 하나다. 값은 열을 정의한 순서대로 열마다 하나씩 적고 각 값은 그 열의 형식에 맞아야 한다. `1,,x` 처럼 빈 값이 있거나 값의 수가 열의 수와 다르면 행이 아니다.

### 테이블 만들기

[4.5] `CREATE <열 정의> … [PARTITION <파티션 필드> …]` 는 테이블을 만든다. 열 정의는 `<열 이름>:<형식>` 꼴의 인자이고 1개 이상 8개 이하다. 열 이름은 3.11 의 이름이고 서로 달라야 한다. 열 정의를 적은 순서가 열의 순서다.

[4.6] `PARTITION` 인자가 있으면 그 뒤의 인자는 모두 파티션 필드이고 1개 이상이어야 한다. 파티션 필드는 `day(<열 이름>)` 이나 `bucket[<N>](<열 이름>)` 꼴이다. 괄호 안의 열을 그 필드의 원본 열이라 한다. `day` 필드의 원본 열은 `timestamp` 열이어야 하고 `bucket` 필드의 원본 열은 `long` 열이나 `string` 열이어야 한다. N 은 `^[1-9][0-9]{0,2}$` 에 맞는 정수, 곧 1 이상 999 이하다. 한 열은 파티션 필드 하나에만 원본 열로 쓸 수 있다. 파티션 필드의 이름은 `day` 필드가 `<원본 열 이름>_day`, `bucket` 필드가 `<원본 열 이름>_bucket` 이다. 파티션 필드를 적은 순서가 필드의 순서다.

[4.7] `PARTITION` 인자가 없으면 테이블은 파티션을 나누지 않는다. 이때 파티션 필드는 하나도 없고 모든 파일의 파티션 값은 4.11 의 빈 파티션 값 `{}` 이다.

[4.8] CREATE 는 스냅숏이 없는 첫 메타데이터 파일 `meta-1` 을 쓰고 포인터가 그 파일을 가리키게 한 뒤 `CREATE meta-1` 을 출력한다. 테이블은 입력 전체에서 하나뿐이다.

### 변환과 파티션 값

[4.9] `day` 변환의 결과는 `timestamp` 값의 앞 10글자인 날짜 `YYYY-MM-DD` 다. 날짜끼리는 사전식 순서로 비교한다. 날짜 d 에 속한 시각은 d 의 00:00:00 부터 23:59:59 까지다.

[4.10] `bucket[N]` 변환의 결과는 값의 해시를 N 으로 나눈 나머지다. 값의 해시는 값을 적은 문자열의 글자에 앞에서부터 1, 2, 3, … 의 자리 번호를 매기고 각 글자의 ASCII 코드에 그 글자의 자리 번호를 곱해 모두 더한 수다. 예를 들어 `17` 의 해시는 1×49 + 2×55 = 159 이므로 `bucket[4]` 의 결과는 3 이다. `-5` 의 해시는 1×45 + 2×53 = 151 이고 `click` 의 해시는 1×99 + 2×108 + 3×105 + 4×99 + 5×107 = 1561 이다. 해시는 언제나 양수이고 결과는 0 이상 N 미만의 정수다. `bucket` 결과끼리는 수의 크기로 비교한다.

[4.11] 행의 파티션 값은 파티션 필드마다 그 필드의 원본 열 값에 변환을 적용한 결과를 필드 순서대로 모은 것이다. 파티션 값은 `{<필드 이름>=<결과>,<필드 이름>=<결과>}` 처럼 중괄호 안에 필드 순서대로 쉼표로 이어 쓴다. 결과는 `day` 필드면 4.9 의 날짜로, `bucket` 필드면 십진 정수로 쓴다. 파티션을 나누지 않는 테이블의 파티션 값은 `{}` 다. 두 파티션 값은 모든 필드의 결과가 같을 때 같다.

### 객체 저장소

[4.12] 객체 저장소는 이름으로 객체를 찾는 메모리 안의 저장소다. 객체는 메타데이터 파일, 매니페스트 목록, 매니페스트, 데이터 파일 네 종류다. 객체는 쓴 뒤에 내용이 바뀌지 않는다. 1단계에서는 객체를 지우지 않는다.

[4.13] 메타데이터 파일의 이름은 쓴 순서대로 `meta-1`, `meta-2`, `meta-3`, … 이다. 매니페스트 목록의 이름은 `snap-<트랜잭션>-<시도 번호>` 이고 시도 번호는 4.24 가 정한다. 매니페스트의 이름은 그 매니페스트를 쓴 트랜잭션의 이름 뒤에 `-m` 과 차례 번호를 붙인 것이다. 차례 번호는 그 트랜잭션이 쓴 매니페스트 가운데 몇 번째인지를 1 부터 센 수이므로 트랜잭션 `a` 의 매니페스트는 `a-m1`, `a-m2`, … 다. 데이터 파일의 이름은 APPEND 에 적은 파일 이름이다. 데이터 파일 이름에는 `-` 가 없으므로 다른 종류의 객체 이름과 겹치지 않는다.

[4.14] 포인터는 현재 메타데이터 파일의 이름을 담는다. 이 저장소에서 원자적인 일은 포인터를 바꾸는 교체 하나뿐이다. 교체는 기대한 메타데이터 파일 이름과 새 메타데이터 파일 이름을 받는다. 포인터가 기대한 이름을 담고 있으면 새 이름으로 바꾸고 성공한다. 그렇지 않으면 아무것도 바꾸지 않고 실패한다. 객체는 쓰는 즉시 저장소에 남고 교체의 성공 여부와 상관없이 그대로 있다.

### 메타데이터

[4.15] 메타데이터 파일은 스냅숏 목록, 현재 스냅숏, 마지막 순서 번호, 이전 메타데이터 파일 기록을 담는다. 스냅숏 목록은 순서 번호가 작은 스냅숏부터 늘어놓는다. 이전 메타데이터 파일 기록은 이 메타데이터 파일보다 먼저 현재 메타데이터 파일이었던 파일들의 이름 목록이다. `meta-1` 은 스냅숏 목록이 비어 있고 현재 스냅숏이 없으며 마지막 순서 번호가 0 이고 이전 메타데이터 파일 기록이 비어 있다. 현재 메타데이터 파일은 포인터가 가리키는 메타데이터 파일이다. 이 문서에서 그냥 현재 스냅숏이라 하면 현재 메타데이터 파일의 현재 스냅숏을 뜻한다.

[4.16] 스냅숏에는 ID, 순서 번호, 부모 스냅숏, 매니페스트 목록이 있다. 스냅숏 ID 는 그 스냅숏을 커밋한 트랜잭션의 이름이다. 부모 스냅숏은 그 스냅숏을 만들 때 바탕으로 삼은 스냅숏이고 없을 수도 있다.

[4.17] 매니페스트 목록은 매니페스트를 차례대로 늘어놓고 매니페스트마다 내용 종류, 순서 번호, 상태별 항목 수, 파티션 범위를 적는다. 1단계와 2단계의 매니페스트는 모두 데이터 파일을 담으므로 내용 종류가 `data` 다. 상태별 항목 수는 그 매니페스트의 ADDED, EXISTING, DELETED 항목 수다. 파티션 범위는 파티션 필드마다 그 매니페스트의 모든 항목이 가리키는 파일의 파티션 값에서 그 필드의 가장 작은 결과와 가장 큰 결과다. DELETED 항목이 가리키는 파일도 파티션 범위에 넣는다. 현재 메타데이터 파일에 있는 스냅숏들의 매니페스트 목록에서 한 매니페스트는 늘 같은 순서 번호로 적힌다(4.28).

[4.18] 매니페스트는 항목을 차례대로 담는다. 항목에는 상태, 파일, 스냅숏 ID, 순서 번호가 있다. 항목은 파일의 이름과 함께 그 파일의 파티션 값, 행 수, 열의 하한과 상한을 담는다. 상태는 ADDED, EXISTING, DELETED 가운데 하나다. ADDED 항목과 EXISTING 항목을 살아 있는 항목이라 한다. 스냅숏의 살아 있는 파일은 그 스냅숏의 매니페스트 목록에 든 매니페스트들의 살아 있는 항목이 가리키는 파일이다. 한 스냅숏에서 한 파일을 가리키는 살아 있는 항목은 하나뿐이다. 스냅숏에서 파일의 순서 번호는 그 스냅숏에서 그 파일을 가리키는 살아 있는 항목의 순서 번호다.

[4.19] 데이터 파일은 행을 차례대로 담는다. 행의 위치는 첫 행을 0 으로 세는 차례다. 데이터 파일에는 파티션 값 하나, 행 수, 열마다 값의 하한과 상한이 있다. 열의 하한과 상한은 그 파일의 모든 행에서 그 열의 가장 작은 값과 가장 큰 값이다.

### 트랜잭션

[4.20] 트랜잭션은 BEGIN 으로 시작해 COMMIT 으로 끝난다. 아직 끝나지 않은 트랜잭션을 활동 중인 트랜잭션이라 한다. 트랜잭션 이름 하나는 입력 전체에서 한 번만 BEGIN 할 수 있다.

[4.21] `BEGIN <트랜잭션>` 은 트랜잭션을 시작한다. 그 순간의 현재 메타데이터 파일을 그 트랜잭션의 기준 판이라 하고 기준 판의 현재 스냅숏을 그 트랜잭션의 시작 스냅숏이라 한다. 시작 스냅숏은 없을 수도 있다. BEGIN 은 `<트랜잭션> BEGIN <시작 스냅숏> <기준 판>` 을 출력한다. 시작 스냅숏이 없으면 그 자리에 `-` 를 쓴다.

[4.22] `APPEND <트랜잭션> <파일> <행> …` 은 행들을 담은 데이터 파일을 그 이름으로 객체 저장소에 바로 쓰고 트랜잭션이 더할 파일로 적어 둔다. 행은 하나 이상이고 인자에 적은 순서가 파일 안의 행 순서다. 모든 행의 파티션 값이 같아야 하고 그 값이 파일의 파티션 값이다. APPEND 는 `<트랜잭션> APPEND <파일> <파티션 값> rows=<행 수>` 를 출력한다. 쓴 데이터 파일은 그 트랜잭션이 커밋하기 전에는 어느 스냅숏에도 속하지 않는다.

[4.23] `REMOVE <트랜잭션> <파일>` 은 그 파일을 테이블에서 지울 파일로 트랜잭션에 적고 `<트랜잭션> REMOVE <파일>` 을 출력한다. 파일은 그 트랜잭션의 시작 스냅숏에 살아 있는 데이터 파일이어야 한다. 한 트랜잭션이 같은 파일을 지울 파일로 두 번 적을 수 없다. 같은 트랜잭션이 APPEND 로 쓴 파일은 시작 스냅숏에 없으므로 지울 수 없다.

[4.24] `COMMIT <트랜잭션>` 은 트랜잭션이 더할 파일과 지울 파일을 반영하는 커밋 시도를 한다. 더할 파일도 지울 파일도 없으면 시도하지 않고 오류를 낸다(5.5). 이 문서는 기준 판이 현재 메타데이터 파일인 트랜잭션의 COMMIT 만 다룬다. 그 트랜잭션의 시도는 기준 판을 바탕으로 하고 시도 번호가 1 이며 교체에 성공한다. COMMIT 은 트랜잭션을 끝내고 `<트랜잭션> COMMIT seq=<순서 번호> <메타데이터 파일>` 을 출력한다. 순서 번호는 그 시도가 만든 스냅숏의 순서 번호이고 메타데이터 파일은 그 시도가 쓴 메타데이터 파일이다.

### 커밋 시도

[4.25] 커밋 시도는 메타데이터 파일 하나를 바탕으로 새 스냅숏 하나를 만든다. 바탕으로 삼은 메타데이터 파일을 그 시도의 기준 판이라 하고 기준 판의 현재 스냅숏을 그 시도의 부모 스냅숏이라 한다. 새 스냅숏의 ID 는 트랜잭션 이름이고 순서 번호는 기준 판의 마지막 순서 번호에 1 을 더한 값이며 부모 스냅숏은 그 시도의 부모 스냅숏이다.

[4.26] 트랜잭션에 더할 파일이 있으면 그 파일들을 담는 새 매니페스트를 쓴다. 이 매니페스트는 더할 파일마다 ADDED 항목 하나를 트랜잭션에 적은 순서대로 담는다. 항목의 스냅숏 ID 는 트랜잭션 이름이다. 항목의 순서 번호는 비워 두고 이 매니페스트가 든 매니페스트 목록에 적힌 순서 번호를 이어받는다. 이 매니페스트는 트랜잭션의 첫 커밋 시도에서 한 번만 쓴다.

[4.27] 부모 스냅숏의 매니페스트 목록에 든 매니페스트를 차례대로 하나씩 처리한다. 지울 파일을 가리키는 살아 있는 항목이 있는 매니페스트는 새 매니페스트로 다시 쓴다. 다시 쓴 매니페스트는 원래 매니페스트의 살아 있는 항목을 같은 차례로 옮겨 담고 DELETED 항목은 옮기지 않는다. 지울 파일을 가리키는 항목은 상태를 DELETED 로, 스냅숏 ID 를 트랜잭션 이름으로 바꾼다. 나머지 항목은 상태를 EXISTING 으로 바꾸고 스냅숏 ID 는 그대로 둔다. 옮긴 항목은 모두 원래 항목의 순서 번호를 직접 적는다. 원래 항목이 순서 번호를 이어받고 있었으면 이어받은 값을 적는다. 지울 파일이 없는 매니페스트 가운데 살아 있는 항목이 하나 이상 있는 매니페스트는 그대로 두고 살아 있는 항목이 없는 매니페스트는 새 스냅숏의 매니페스트 목록에 넣지 않는다.

[4.28] 새 스냅숏의 매니페스트 목록은 4.26 의 새 매니페스트를 맨 앞에 두고 그 뒤에 4.27 에서 남긴 매니페스트를 부모 스냅숏의 목록 순서대로 둔다. 다시 쓴 매니페스트는 원래 매니페스트가 있던 자리에 들어간다. 그 시도가 쓴 매니페스트는 목록에 새 스냅숏의 순서 번호로 적는다. 그대로 둔 매니페스트는 부모 스냅숏의 목록에 적힌 순서 번호를 그대로 적는다.

[4.29] 한 시도는 4.26 의 새 매니페스트, 4.27 에서 다시 쓴 매니페스트들, 매니페스트 목록, 메타데이터 파일 순서로 객체를 쓴다. 다시 쓴 매니페스트들은 부모 스냅숏의 목록 순서대로 쓴다. 매니페스트의 차례 번호는 이 순서로 매긴다. 매니페스트 목록의 이름은 `snap-<트랜잭션>-<시도 번호>` 이고 메타데이터 파일은 4.13 의 다음 이름을 받는다.

[4.30] 새 메타데이터 파일은 기준 판의 스냅숏 목록 끝에 새 스냅숏을 더한 스냅숏 목록을 담는다. 현재 스냅숏은 새 스냅숏이고 마지막 순서 번호는 새 스냅숏의 순서 번호다. 이전 메타데이터 파일 기록은 기준 판의 기록 끝에 기준 판의 이름을 더한 것이다. 시도는 마지막으로 교체를 한다. 교체의 기대한 이름은 기준 판의 이름이고 새 이름은 새 메타데이터 파일의 이름이다.

### 조회 명령

[4.31] `SNAPSHOTS` 는 현재 메타데이터 파일의 스냅숏 목록을 보여 준다. 첫 줄은 `SNAPSHOTS <현재 메타데이터 파일> <스냅숏 수>` 다. 그 뒤에 스냅숏마다 `<스냅숏 ID> seq=<순서 번호> parent=<부모 스냅숏 ID> list=<매니페스트 목록>` 을 순서 번호가 작은 스냅숏부터 한 줄씩 쓴다. 부모 스냅숏이 없으면 `parent=-` 다.

[4.32] `MANIFESTS <스냅숏>` 은 현재 메타데이터 파일의 스냅숏 목록에 있는 그 스냅숏의 매니페스트 목록을 보여 준다. 첫 줄은 `MANIFESTS <스냅숏 ID> <매니페스트 수>` 다. 그 뒤에 매니페스트마다 `<매니페스트> <내용 종류> seq=<순서 번호> added=<ADDED 수> existing=<EXISTING 수> deleted=<DELETED 수>` 를 목록 순서대로 한 줄씩 쓴다. 파티션 필드가 있으면 그 줄 끝에 필드마다 공백 하나와 `<필드 이름>=<가장 작은 결과>..<가장 큰 결과>` 를 필드 순서대로 붙인다.

[4.33] `ENTRIES <매니페스트>` 는 매니페스트의 항목을 보여 준다. 매니페스트는 현재 메타데이터 파일의 스냅숏 목록에 있는 스냅숏 가운데 하나 이상의 매니페스트 목록에 들어 있어야 한다. 첫 줄은 `ENTRIES <매니페스트> <항목 수>` 다. 그 뒤에 항목마다 `<상태> <파일> snapshot=<스냅숏 ID> seq=<순서 번호> <파일의 파티션 값> rows=<파일의 행 수>` 를 매니페스트의 차례대로 한 줄씩 쓴다. 순서 번호를 이어받는 항목에는 그 매니페스트가 든 스냅숏의 목록에 적힌 순서 번호를 쓴다. 4.17 에 따라 이 값은 어느 스냅숏의 목록에서 읽어도 같다.

[4.34] `LS` 는 객체 저장소에 있는 객체의 이름을 보여 준다. 첫 줄은 `LS <객체 수>` 이고 그 뒤에 객체 이름을 3.12 의 사전식 순서로 한 줄에 하나씩 쓴다.

### SCAN

[4.35] `SCAN [AT <스냅숏>] [WHERE <조건> [AND <조건>] …]` 은 스냅숏 하나를 조건으로 읽는다. `AT <스냅숏>` 이 있으면 현재 메타데이터 파일의 스냅숏 목록에 있는 그 스냅숏을 읽고 없으면 현재 스냅숏을 읽는다. `AT` 은 `WHERE` 보다 앞에 온다. `WHERE` 뒤에는 조건이 하나 이상 오고 조건 사이에는 `AND` 인자가 하나씩 온다. `WHERE` 가 없으면 조건이 없다.

[4.36] 조건은 `<열 이름><연산자><값>` 꼴의 인자 하나다. 연산자는 `=`, `<`, `<=`, `>`, `>=` 가운데 하나다. 인자의 맨 앞에서 영문 소문자와 숫자가 최대로 이어진 부분이 열 이름이고 그 바로 뒤가 연산자다. 연산자 자리가 `<=` 나 `>=` 로 시작하면 두 글자 연산자로 읽는다. 연산자 뒤의 나머지 전체가 값이고 값은 그 열의 형식에 맞아야 한다. 예를 들어 `id<=-5` 의 열은 `id`, 연산자는 `<=`, 값은 `-5` 다. 행은 모든 조건에서 그 행의 열 값과 조건의 값이 연산자의 관계를 만족할 때 조건에 맞는다.

[4.37] 조건의 열이 `day` 필드의 원본 열이면 그 조건이 허용하는 날짜는 아래와 같다. 연산자가 `=` 이면 날짜 d 가 값의 날짜와 같을 때 d 를 허용한다. `<` 이면 d 의 00:00:00 이 값보다 앞일 때, `<=` 이면 d 의 00:00:00 이 값보다 뒤가 아닐 때 d 를 허용한다. `>` 이면 d 의 23:59:59 가 값보다 뒤일 때, `>=` 이면 d 의 23:59:59 가 값보다 앞이 아닐 때 d 를 허용한다. 곧 d 에 속한 시각 가운데 조건을 만족하는 시각이 하나라도 있으면 d 를 허용한다. 예를 들어 `ts<2024-03-02T00:00:00` 은 2024-03-02 를 허용하지 않고 `ts<=2024-03-02T00:00:00` 은 허용한다.

[4.38] 조건의 열이 `bucket[N]` 필드의 원본 열이면 연산자가 `=` 일 때만 값의 `bucket[N]` 결과 하나를 허용한다. 연산자가 `=` 가 아니면 모든 결과를 허용한다.

[4.39] 조건은 매니페스트를 제외할 수 있다. 조건의 열이 어떤 파티션 필드의 원본 열이고 매니페스트 목록에 적힌 그 필드의 파티션 범위가 lo..hi 일 때 lo 이상 hi 이하인 결과 가운데 그 조건이 허용하는 결과가 하나도 없으면 그 조건이 그 매니페스트를 제외한다. 조건 하나 이상이 제외한 매니페스트는 읽지 않고 나머지 매니페스트를 읽는다. 파티션을 나누지 않는 테이블에서는 어떤 매니페스트도 제외하지 않는다.

[4.40] 조건은 읽은 매니페스트의 살아 있는 항목이 가리키는 데이터 파일을 파티션 값으로 제외할 수 있다. 조건의 열이 어떤 파티션 필드의 원본 열이고 그 조건이 파일의 파티션 값에서 그 필드의 결과를 허용하지 않으면 그 조건이 그 파일을 제외한다.

[4.41] 조건은 데이터 파일을 열의 하한과 상한으로도 제외할 수 있다. 파일에서 조건의 열의 하한이 L, 상한이 U 일 때 연산자가 `=` 이면 값이 L 보다 작거나 U 보다 크면 제외한다. `<` 이면 L 이 값보다 작지 않으면, `<=` 이면 L 이 값보다 크면 제외한다. `>` 이면 U 가 값보다 크지 않으면, `>=` 이면 U 가 값보다 작으면 제외한다. 읽은 매니페스트의 살아 있는 항목이 가리키는 데이터 파일 가운데 4.40 과 이 문단의 규칙으로 어떤 조건도 제외하지 않은 파일을 계획한 파일이라 한다.

[4.42] SCAN 은 계획한 파일마다 조건에 맞는 행을 센다. 첫 줄은 `SCAN <스냅숏 ID> manifests=<읽은 매니페스트 수>/<목록의 매니페스트 수> files=<계획한 파일 수> rows=<조건에 맞는 행 수의 합>` 이다. 그 뒤에 계획한 파일마다 `<파일> rows=<그 파일에서 조건에 맞는 행 수>` 를 파일 이름의 사전식 순서로 한 줄씩 쓴다. 조건에 맞는 행이 없는 계획한 파일도 `rows=0` 으로 쓴다. 조건이 없으면 매니페스트와 파일을 하나도 제외하지 않고 모든 행이 조건에 맞는다.

[4.43] `AT` 이 없고 현재 스냅숏이 없으면 읽을 스냅숏이 없다. 이때 SCAN 은 `SCAN - manifests=0/0 files=0 rows=0` 한 줄만 출력한다.

### 뒤 단계에서 뜻이 생기는 입력

[4.44] 명령어가 `ABORT`, `COMPACT`, `EXPIRE`, `ORPHANS`, `POSDEL`, `EQDEL` 인 줄은 이 문서가 출력을 정하지 않는다. ABORT, COMPACT, EXPIRE, ORPHANS 는 2단계에서 뜻이 생기고 POSDEL 과 EQDEL 은 3단계에서 뜻이 생긴다. 5절의 오류에 걸리지 않고 커밋 시도를 하게 되는 COMMIT 가운데 그 트랜잭션의 기준 판이 현재 메타데이터 파일이 아닌 COMMIT 도 출력을 정하지 않는다. 이런 COMMIT 은 2단계에서 뜻이 생긴다. 이 문단의 줄이 나온 뒤의 출력도 이 문서는 정하지 않는다.

## 5. 오류 규칙

[5.1] 오류가 나면 오류 줄 하나만 출력한다. 오류를 낸 줄은 어떤 상태도 바꾸지 않으므로 오류를 낸 APPEND 는 데이터 파일을 쓰지 않는다. 프로그램은 다음 줄을 이어서 처리한다.

[5.2] 명령어가 1.2 의 열 명령 가운데 어느 것과도 정확히 같지 않으면 `ERR UNKNOWN_COMMAND` 를 출력한다. 4.44 의 명령어는 이 규칙을 적용하지 않는다.

[5.3] 테이블이 없을 때 CREATE 가 아닌 명령은 `ERR NO_TABLE` 을 출력한다. 테이블이 있을 때 CREATE 는 `ERR TABLE_EXISTS` 를 출력한다.

[5.4] 인자 수나 형식이 아래와 맞지 않으면 `ERR BAD_ARGUMENT` 를 출력한다. CREATE 의 인자는 4.5 와 4.6 을 지켜야 한다. BEGIN 과 COMMIT 의 인자는 트랜잭션 이름 하나다. APPEND 의 인자는 트랜잭션 이름, 파일 이름, 행 하나 이상이고 각 행은 4.4 의 행이어야 한다. REMOVE 의 인자는 트랜잭션 이름과 파일 이름 둘이다. SNAPSHOTS 와 LS 는 인자가 없다. MANIFESTS 의 인자는 이름 하나다. ENTRIES 의 인자는 하나이고 그 형식은 따지지 않는다. SCAN 의 인자는 4.35 와 4.36 을 지켜야 한다. `AT` 뒤에는 이름 하나가 와야 하고 조건의 열은 테이블의 열이어야 한다.

[5.5] 인자 수와 형식이 맞는 줄은 상태를 확인한다. BEGIN 은 그 이름으로 BEGIN 한 적이 있으면 `<트랜잭션> ERR TX_EXISTS` 를 출력한다. APPEND, REMOVE, COMMIT 은 그 이름으로 BEGIN 한 적이 없으면 `<트랜잭션> ERR NO_TX` 를, 그 트랜잭션이 끝났으면 `<트랜잭션> ERR TX_ENDED` 를 출력한다. APPEND 는 파일 이름을 이미 데이터 파일 이름으로 쓴 적이 있으면 `<트랜잭션> ERR FILE_EXISTS <파일>` 을, 행의 파티션 값이 모두 같지는 않으면 `<트랜잭션> ERR MIXED_PARTITION` 을 출력한다. 오류를 낸 APPEND 의 파일 이름은 쓴 적이 없는 이름으로 남는다. REMOVE 는 4.23 을 어기면 `<트랜잭션> ERR NOT_LIVE <파일>` 을 출력한다. COMMIT 은 더할 파일도 지울 파일도 없으면 `<트랜잭션> ERR EMPTY` 를 출력하고 트랜잭션은 활동 중으로 남는다. MANIFESTS 와 SCAN 은 스냅숏이 현재 메타데이터 파일의 스냅숏 목록에 없으면 `ERR NO_SNAPSHOT <스냅숏>` 을 출력한다. ENTRIES 는 인자가 4.33 의 매니페스트가 아니면 `ERR NO_MANIFEST <인자>` 를 출력한다.

[5.6] 줄마다 명령어(5.2), 테이블(5.3), 인자 수와 형식(5.4), 상태(5.5)를 차례로 확인하고 처음 걸린 오류 하나만 출력한다. 상태는 트랜잭션을 먼저 확인한다. APPEND 는 그다음 파일 이름, 파티션 값 순서로 확인한다.

[5.7] 이 단계의 오류 줄은 아래와 같다.

| 오류 줄 | 뜻 |
|---|---|
| `ERR UNKNOWN_COMMAND` | 모르는 명령어 |
| `ERR NO_TABLE` | 테이블이 없는데 CREATE 가 아닌 명령을 받음 |
| `ERR TABLE_EXISTS` | 테이블이 있는데 CREATE 를 받음 |
| `ERR BAD_ARGUMENT` | 인자 수나 형식이 틀림 |
| `<트랜잭션> ERR TX_EXISTS` | 이미 쓴 트랜잭션 이름으로 BEGIN 함 |
| `<트랜잭션> ERR NO_TX` | 시작한 적 없는 트랜잭션 |
| `<트랜잭션> ERR TX_ENDED` | 이미 끝난 트랜잭션 |
| `<트랜잭션> ERR FILE_EXISTS <파일>` | 이미 쓴 데이터 파일 이름 |
| `<트랜잭션> ERR MIXED_PARTITION` | 데이터 파일의 행들이 한 파티션에 들지 않음 |
| `<트랜잭션> ERR NOT_LIVE <파일>` | 시작 스냅숏에 살아 있는 데이터 파일이 아니거나 이미 지울 파일로 적은 파일 |
| `<트랜잭션> ERR EMPTY` | 더할 파일도 지울 파일도 없는 트랜잭션의 COMMIT |
| `ERR NO_SNAPSHOT <스냅숏>` | 현재 메타데이터 파일에 없는 스냅숏 |
| `ERR NO_MANIFEST <인자>` | 현재 메타데이터 파일의 스냅숏들이 사용하지 않는 매니페스트 |

## 6. 예시

[6.1] 예시 블록 하나는 프로그램을 한 번 실행한 기록이다. `> ` 로 시작하는 줄은 입력이고 나머지 줄은 바로 위 입력의 출력이다. 실제 입력에는 `> ` 가 없다.

[6.2] 메타데이터 계층이다. a 는 데이터 파일 둘을 더하고 b 는 하나를 더한다. id 17 의 해시는 159 라서 f1 의 버킷은 3 이고 id 5 의 해시는 53 이라서 f2 의 버킷은 1 이다. id 21 의 해시는 1×50 + 2×49 = 148 이라서 f3 의 버킷은 0 이다. b 의 매니페스트 목록에는 b 가 쓴 b-m1 이 앞에 오고 a 가 쓴 a-m1 이 그대로 뒤에 들어간다. a-m1 은 b 의 목록에도 a 의 목록과 같은 순서 번호 1 로 적힌다. a-m1 의 항목은 순서 번호를 목록에서 이어받는다. LS 는 메타데이터 파일 셋, 매니페스트 목록 둘, 매니페스트 둘, 데이터 파일 셋을 사전식 순서로 보여 준다.

```
> CREATE ts:timestamp id:long kind:string PARTITION day(ts) bucket[4](id)
CREATE meta-1
> BEGIN a
a BEGIN - meta-1
> APPEND a f1 2024-03-01T09:00:00,17,click 2024-03-01T12:30:00,17,view
```

## 7. 검사 방식

[7.1] 엔진은 테스트마다 풀이의 `run.sh` 를 새 프로세스로 실행한다. 작업 디렉터리는 풀이 디렉터리다.

[7.2] 엔진은 테스트의 입력 줄을 LF 로 잇고 마지막 줄 뒤에도 LF 를 붙여 표준 입력에 쓴 뒤 표준 입력을 닫는다.

[7.3] 프로세스가 0 이 아닌 종료 코드로 끝나면 실패다.

[7.4] 표준 출력만 기대 출력과 비교하고 표준 오류는 비교하지 않는다. 각 줄 끝의 공백, 탭, CR 을 지우고 끝에 붙은 빈 줄을 지운 뒤 줄 수와 각 줄의 내용이 정확히 같아야 한다.

[7.5] 일반 테스트의 제한 시간은 10초다. 제한 시간을 넘기면 엔진이 프로세스를 끝내고 실패로 판정한다.

[7.6] 대규모 테스트는 `CREATE ts:timestamp id:long kind:string PARTITION day(ts) bucket[16](id)` 로 만든 테이블에서 실행한다. 트랜잭션 1,500개 안팎이 하나씩 차례로 BEGIN 하고 COMMIT 한다. 트랜잭션 하나는 하루치 데이터 파일 60개 안팎을 APPEND 하고 다섯에 하나꼴로 앞선 트랜잭션이 더한 파일 몇 개를 REMOVE 한다. 데이터 파일은 90,000개, 행은 450,000개 안팎이다. SCAN 은 180,000번 안팎이고 그 가운데 절반가량은 AT 으로 과거 스냅숏을 읽는다. SCAN 의 조건은 하루 안의 시각 범위와 id 같음을 섞어서 SCAN 하나가 계획하는 파일이 몇 개 안팎이다. 제한 시간은 15초다. 매니페스트 목록의 파티션 범위로 매니페스트를 건너뛰지 않고 SCAN 마다 스냅숏의 모든 살아 있는 데이터 파일을 조건과 맞춰 보는 풀이는 매니페스트마다 파티션 값을 배열에 모아 두고 맞춰 보더라도 이 제한 시간을 넘기도록 규모를 정했다.

[7.7] 검사 입력의 한 줄은 UTF-8 로 2,000바이트 이하다.

[7.8] 1단계 검사 입력에는 4.44 의 줄이 나오지 않는다.

[7.9] 2단계와 3단계를 검사할 때도 1단계 테스트를 다시 실행한다.

[7.10] 3.3 의 마지막 문장과 3.8 은 엔진이 검사하지 않는다. 엔진은 입력의 마지막 줄 뒤에도 LF 를 붙이고(7.2) 출력 줄 끝의 CR 과 끝에 붙은 빈 줄을 지운 뒤 비교하기(7.4) 때문이다. 두 규칙은 표준 입출력 프로그램의 관례라서 적어 둔다.

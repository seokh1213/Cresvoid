# 03. 시퀀스 번호와 조건부 색인

## 1. 개요

[1.1] 앞 두 단계의 주 샤드 상태에 연산 식별자를 더하고 읽은 버전에 대한 조건부 쓰기를 구현한다. 별도로 복제본 하나의 수신 상태를 두어 순서가 뒤바뀐 기록, 중복 전달과 이전 임기의 기록을 처리한다. 목표 풀이 시간은 2~3시간이다. 기존 명령의 출력은 바꾸지 않는다.

[1.2] 실제 병렬 스레드나 네트워크는 쓰지 않는다. 명령 한 줄을 끝까지 처리한 뒤 다음 줄로 넘어간다. 입력 순서가 클라이언트의 경쟁, 복제 지연과 주 샤드 담당 변경을 표현한다. 이 단계는 복제본을 주 샤드로 복사하는 선출 알고리즘이나 분산 합의까지 구현하지 않는다.

## 2. 배경 개념

[2.1] 클라이언트가 문서를 읽은 뒤 다른 클라이언트가 같은 문서를 고칠 수 있다. 첫 클라이언트의 오래된 읽기를 근거로 무조건 덮어쓰면 나중 변경을 잃는다. 낙관적 동시성 제어는 읽은 버전과 현재 버전이 같은지 쓰기 시점에 검사하고 달라졌으면 쓰기를 거절한다. 검색 공개가 늦어도 충돌 검사는 최신 상태를 기준으로 해야 한다.

[2.2] 시퀀스 번호는 주 샤드가 성공한 연산에 붙이는 순서다. 샤드 전체의 카운터이므로 한 문서의 번호 사이에 다른 문서의 연산 번호가 낄 수 있다. 시퀀스 번호와 주 임기의 쌍은 해당 변경을 식별한다. 주 임기는 주 샤드 담당이 바뀌는 경계를 구분한다. 문서를 다시 쓰지 않는 한 문서에 저장된 임기가 새 임기로 바뀌지는 않는다.

[2.3] 복제 기록은 생성 순서대로 도착한다는 보장이 없다. 같은 id의 최신 기록을 받은 뒤 더 오래된 PUT을 받더라도 최신 본문을 되돌려서는 안 된다. 최신 기록이 DEL이어도 마찬가지다. 본문을 없앤 뒤에도 삭제 연산의 식별자를 남기는 삭제 표식이 있어야 오래된 PUT으로 문서가 되살아나는 것을 막을 수 있다.

[2.4] 복제본에서 가장 큰 수신 번호와 빠짐없이 받은 연속 구간의 끝은 다르다. 예를 들어 0과 2를 받으면 최댓값은 2지만 연속 구간은 0에서 끝난다. 나중에 1이 오면 연속 구간의 끝은 2가 된다. 특정 문서의 최신 상태를 바꾸지 못한 오래된 기록도 전달 자체는 완료된 기록일 수 있다.

[2.5] 현재 임기보다 낮은 기록을 차단하는 경계와 같은 id의 오래된 버전을 무시하는 경계는 다르다. 전자는 이전 담당자의 지연 요청을 차단한다. 후자는 현재 허용된 기록 사이에서 문서의 변경 순서를 지킨다. 아래 명령은 이 둘과 중복 전달 판정을 별도로 관찰하게 한다.

[2.6] 배경은 Elastic의 [Optimistic concurrency control](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/optimistic-concurrency-control)을 따른다. 연산의 시퀀스 번호와 임기, 최신 변경 쌍을 조건으로 쓰는 개념을 참고한다. 아래의 PROMOTE·REPLAY, 복제본 초기화와 번호 할당기 보존은 이 과제의 수신·복구 모형이며 실제 Elasticsearch 전체 프로토콜의 계약은 아니다.

## 3. 입출력 규칙

[3.1] 앞 단계의 입력·출력 규칙을 유지한다. 새 명령은 `VERSION <id>`, `CAS <id> <예상 번호> <예상 임기> <본문...>`, `PROMOTE`, `REPLAY <번호> <임기> PUT <id> <본문...>`, `REPLAY <번호> <임기> DEL <id>`, `RGET <id>`, `RSTATE`다. id와 본문은 앞 단계 형식을 쓴다.

[3.2] 명령에 입력하는 시퀀스 번호는 0~1,000,000,000의 정수이고 임기는 1~1,000,000,000의 정수다. 십진 숫자 표기는 앞 단계와 같다. 출력 번호와 현재 임기의 상한은 입력 크기에서 자연히 정해지며 별도의 순환이나 최댓값 포화 처리는 없다.

[3.3] 시작 현재 임기는 1, 주 샤드의 다음 할당 번호는 0이다. 주 샤드 문서별 변경 식별자와 삭제 표식은 비어 있다. 복제본도 비어 있으며 수신 번호가 하나도 없을 때 연속 수신 경계와 최대 수신 번호는 모두 -1이다.

[3.4] VERSION과 RGET의 출력 형식은 같다. 살아 있는 문서면 `<마지막 번호> <그 연산의 임기> <본문>`을 출력한다. 마지막 연산이 DEL인 id면 `DELETED <마지막 번호> <그 연산의 임기>`를 출력한다. 기록 자체가 없으면 `MISSING`이다. GET은 앞 단계처럼 본문 또는 MISSING만 출력하며 삭제 표식의 유무는 구분하지 않는다.

## 4. 명령 규칙

[4.1] 주 샤드에서 성공한 PUT과 DEL은 각각 다음 할당 번호 하나와 그때의 현재 임기를 받는다. 할당 뒤 다음 번호는 1 증가한다. 없는 id의 DEL과 같은 본문으로의 PUT도 번호를 소비한다. 기존 PUT·DEL 출력은 계속 OK다. 오류, 충돌과 모든 관찰·관리 명령은 번호를 소비하지 않는다.

[4.2] 주 샤드는 id별 마지막 성공 연산의 번호와 임기를 저장한다. PUT은 본문과 함께 식별자를 바꾸고, DEL은 본문을 없애되 식별자는 삭제 표식으로 남긴다. VERSION은 refresh 여부와 관계없이 이 최신 상태를 읽는다. VERSION과 GET은 검색 이력이나 버퍼를 바꾸지 않는다.

[4.3] `CAS <id> <예상 번호> <예상 임기> <본문...>`는 현재 주 샤드에 살아 있는 문서가 있고 그 문서의 마지막 연산 번호와 임기가 두 예상 값에 각각 같을 때만 성공한다. 성공하면 일반 PUT과 똑같이 본문 교체, 버퍼 추가, translog 기록과 현재 내구성 모드의 동기화를 수행하고 새 번호를 할당한다. 성공 출력은 `OK <새 번호> <현재 임기>`다.

[4.4] CAS의 조건이 맞지 않으면 `CONFLICT`를 출력하고 모든 상태를 유지한다. 삭제 표식이 예상 쌍과 일치해도 살아 있는 문서가 아니므로 충돌이다. 예상 임기는 문서에 저장된 임기와 비교하며 현재 임기와 직접 비교하지 않는다. 따라서 담당 변경 뒤에도 이전 임기에 읽은 문서가 한 번도 바뀌지 않았다면 그 쌍으로 CAS할 수 있다.

[4.5] `PROMOTE`는 현재 임기만 1 증가시키고 `TERM <새 현재 임기>`를 출력한다. 주 샤드의 문서·삭제 표식·버퍼·세그먼트·translog·커밋·다음 할당 번호를 바꾸지 않는다. 복제본 문서와 이미 수신한 번호도 유지한다. 이 명령은 기존 상태를 가진 새 담당자가 쓰기를 이어받는 사건이다. 복제본의 본문을 주 샤드로 복사하거나 기존 문서에 새 임기를 일괄 부여하지 않는다.

[4.6] 복제본은 주 샤드의 버퍼·세그먼트·translog와 독립된 수신 모형이다. PUT·DEL·CAS·refresh·flush·동기화가 복제본으로 자동 전송되는 일은 없다. REPLAY의 기록은 외부에서 제공되며 현재 프로세스의 주 샤드 쓰기 이력과 대조하지 않는다. REPLAY는 주 샤드의 문서나 번호 할당기를 바꾸지 않는다. RGET은 복제본의 최신 수신 상태를 즉시 읽고, SEARCH와 GET은 계속 주 샤드만 읽는다.

[4.7] REPLAY는 먼저 기록의 임기와 현재 임기를 비교한다. 더 낮으면 `STALE_TERM`을 출력하고 수신 여부를 포함한 모든 상태를 유지한다. 더 높으면 `ERR TERM`을 출력하고 모든 상태를 유지한다. 같은 임기일 때만 나머지 수신 규칙을 처리한다. 이 순서는 중복 판정보다 앞선다. 따라서 이전 임기에 수신했던 기록의 재전달도 PROMOTE 뒤에는 STALE_TERM이다.

[4.8] 현재 임기의 REPLAY에서 이미 수신한 번호가 다시 오면 `DUPLICATE`를 출력하고 아무것도 바꾸지 않는다. 같은 번호를 가진 REPLAY는 임기·종류·id·본문까지 완전히 같은 기록이라는 입력 보장이 있다. PROMOTE와 CRASH 전후를 포함해 서로 다른 기록이 같은 번호를 쓰는 입력은 주지 않는다. 단, 주 샤드가 자체 할당한 번호와 외부 REPLAY 번호 사이에는 이 동일성 보장을 적용하지 않는다.

[4.9] 현재 임기의 처음 받은 번호라면 먼저 그 번호를 수신 집합에 추가한다. 해당 id에 마지막 기록이 없거나 새 번호가 그 id의 마지막 번호보다 크면 기록을 적용하고 `APPLIED`를 출력한다. PUT은 본문과 식별자를 교체하고 DEL은 삭제 표식과 식별자를 남긴다. 해당 id에 더 큰 번호의 기록이 이미 있으면 본문과 식별자를 유지하고 `IGNORED`를 출력한다. IGNORED도 수신 완료한 번호이며 이후 같은 번호를 받으면 DUPLICATE다. 서로 다른 id 사이에서는 최대 수신 번호가 더 커도 적용을 막지 않는다.

[4.10] `RSTATE`는 `checkpoint=<연속 수신 경계> max=<최대 수신 번호>`를 출력한다. max는 실제 수신 집합의 최댓값이다. checkpoint는 0부터 그 값까지 모든 번호가 수신 집합에 들어 있는 가장 큰 정수다. 0이 없으면 -1이다. PROMOTE는 빠진 번호를 받은 것으로 간주하지 않는다. STALE_TERM과 ERR TERM은 수신 집합에 추가되지 않는다. RGET과 RSTATE는 주 샤드·복제본의 어떤 상태도 바꾸지 않는다.

[4.11] 주 샤드의 translog 기록은 해당 연산에 할당된 번호와 임기도 포함한다. FLUSH의 커밋은 최신 문서뿐 아니라 주 샤드의 마지막 변경 식별자와 삭제 표식도 저장한다. REFRESH와 MERGE는 식별자나 삭제 표식을 제거하지 않는다. 세그먼트의 삭제 행을 물리적으로 버려도 VERSION이 관찰하는 마지막 DEL은 남는다. 복구 시 동기화된 기록은 원래 번호와 임기로 재적용하며 새 번호를 할당하지 않는다.

[4.12] CRASH 뒤 주 샤드의 문서별 식별자와 삭제 표식은 커밋과 동기화된 translog로 복구한다. 유실된 쓰기의 식별자는 사라지므로 이전 식별자가 다시 최신이 될 수 있다. 현재 임기와 다음 할당 번호는 커밋·translog와 별개인 조정 상태로 보존한다. 유실된 연산의 번호도 다시 할당하지 않는다. 이것은 복구 뒤 번호 중복을 피하기 위한 이 과제의 규칙이다. CRASH의 나머지 주 샤드 동작은 앞 단계와 같다.

[4.13] CRASH는 복제본의 모든 문서·삭제 표식·수신 집합을 비우고 checkpoint와 max를 -1로 초기화한다. 복제본에는 별도의 내구성이나 커밋이 없다. 현재 임기는 보존되므로 다시 전달할 때도 그 임기 경계를 적용한다. SYNC와 FLUSH는 복제본 상태를 저장하지 않는다.

## 5. 오류 규칙

[5.1] 새 명령의 인자 개수·종류·id·본문·숫자 형식이나 범위가 틀리면 `ERR INPUT`이다. REPLAY는 PUT과 DEL만 허용한다. 문법 검사를 먼저 마친 뒤 임기, 중복, 번호 순서를 판정한다. 따라서 문법도 틀리고 임기도 오래된 줄은 ERR INPUT이다.

[5.2] 문법이 올바른 CAS의 조건 불일치는 CONFLICT이며, 문법이 올바른 REPLAY의 미래 임기는 ERR TERM이다. 이 출력들과 STALE_TERM·DUPLICATE는 시각·검색 이력·번호 할당·동기화 등 어떤 부수 효과도 내지 않는다. IGNORED는 문서를 바꾸지 않지만 수신 집합은 바꾸므로 구별한다. 앞 단계의 ERR INPUT 무변경 규칙도 유지한다.

## 6. 예시

[6.1] 다음 예시에서는 이전 임기의 변경 쌍으로 CAS할 수 있지만 한 번 변경한 뒤 같은 쌍을 재사용할 수는 없다. 삭제 표식으로는 CAS할 수 없다. 마지막 refresh는 PUT 세 번과 DEL 한 번을 순서대로 반영하므로 살아 있는 행 하나와 삭제 행 두 개를 만든다.

입력:

```text
PUT a red
VERSION a
PROMOTE
CAS a 0 1 blue
CAS a 0 1 green
DEL a
VERSION a
CAS a 2 2 gold
PUT a gold
VERSION a
REFRESH
SEGMENTS
LOG
```

출력:

```text
OK
0 1 red
TERM 2
OK 1 2
CONFLICT
OK
DELETED 2 2
CONFLICT
OK
3 2 gold
OK
1:1:2
generation=1 total=4 synced=4
```

[6.2] 다음 예시에서는 늦게 온 번호 0이 a를 되돌리지 못하지만 수신 구간에는 포함된다. b의 삭제 표식도 전달된 기록이다. 담당 변경 뒤 거절된 번호 3은 현재 임기의 다른 기록으로 주지 않는다. 대신 번호 3을 비워 둔 채 번호 4를 받으므로 연속 수신 경계는 2에 머문다.

입력:

```text
REPLAY 2 1 PUT a newer
RSTATE
REPLAY 0 1 PUT a older
REPLAY 1 1 DEL b
RSTATE
RGET a
RGET b
REPLAY 1 1 DEL b
PROMOTE
REPLAY 3 1 PUT c stale
REPLAY 4 2 DEL a
REPLAY 5 3 PUT c future
RSTATE
RGET a
RGET b
REPLAY 1 1 DEL b
CRASH
RSTATE
```

출력:

```text
APPLIED
checkpoint=-1 max=2
IGNORED
APPLIED
checkpoint=2 max=2
2 1 newer
DELETED 1 1
DUPLICATE
TERM 2
STALE_TERM
APPLIED
ERR TERM
checkpoint=2 max=4
DELETED 4 2
DELETED 1 1
STALE_TERM
OK
checkpoint=-1 max=-1
```

[6.3] 다음 예시에서 번호 1의 쓰기는 유실되지만 할당기는 되돌아가지 않는다. 복구된 a의 버전은 0·1이고, 새 CAS는 번호 2와 현재 임기 2를 받는다. async 모드가 유지되므로 CAS 성공만으로는 동기화되지 않는다.

입력:

```text
DURABILITY async
PUT a red
SYNC
PUT a blue
PROMOTE
CRASH
VERSION a
CAS a 0 1 green
VERSION a
LOG
SYNC
CRASH
VERSION a
```

출력:

```text
OK
OK
OK
OK
TERM 2
OK
0 1 red
OK 2 2
2 2 green
generation=1 total=2 synced=1
OK
OK
2 2 green
```

## 7. 검사 방식

[7.1] 앞 두 단계와 같은 표준 입출력 검사, 정확한 출력 비교와 테스트당 30초 제한 시간을 쓴다. 기존 단계 검사도 모두 실행한다. 실제 스레드, HTTP, 디스크 쓰기나 외부 서비스는 요구하지 않는다. 한 줄의 처리 결과만 결정적으로 관찰한다.

[7.2] 입력 규모는 앞 단계처럼 테스트 하나당 최대 6,000개 명령과 서로 다른 id 2,000개다. id 상한은 주 샤드와 복제본에서 사용하는 id의 합집합에 적용한다. SEARCH 출력 id 총개수는 30,000개 이하, 가상 시각은 10억 밀리초 이하다. REPLAY 번호는 드문드문 주어질 수 있으며 최대 10억이므로 그 사이의 모든 번호가 전달된다고 가정하지 않는다. 별도 성능 강제용 대규모 테스트는 두지 않는다. 마지막 규모 확인은 이 상한 안에서 충돌·삭제·복구·임기 변경·역순 및 중복 전달을 섞는다.

[7.3] REPLAY의 동일 번호 동일 기록 보장 이외에 같은 id의 전달 순서를 가정하지 않는다. 현재 임기의 낮은 번호가 높은 번호 뒤에 올 수 있다. 검사는 전역 수신 경계와 문서별 최신 번호를 따로 확인하고 문서가 삭제된 뒤 오래된 PUT이 도착해도 되살아나지 않는지 확인한다.

# 02. translog와 내구성

## 1. 개요

[1.1] refresh와 세그먼트 단계 위에 내구성을 더한다. 검색에 이미 보인 쓰기가 장애로 사라지는 경우, 검색에는 아직 안 보인 쓰기가 복구되는 경우를 모두 구현한다. 목표 풀이 시간은 2시간 안팎이다. 앞 단계의 명령과 출력 형식은 유지하며 이 문서는 추가되는 규칙만 정의한다.

[1.2] 실제 파일 쓰기, 운영체제 캐시, fsync 호출은 하지 않는다. 메모리 안에서 영속 상태와 휘발 상태를 구별한다. 장애는 CRASH 명령으로만 일어나며, 프로세스 종료와 다음 테스트 실행 사이에는 어떤 상태도 넘기지 않는다.

## 2. 배경 개념

[2.1] refresh는 검색에 공개할 경계를 만들지만 영속 저장을 완료하지는 않는다. 반대로 연산을 복구할 수 있게 저장했다고 해서 그 연산을 검색에 공개한 것도 아니다. 검색 가능성과 장애 후 복구 가능성을 독립된 축으로 다뤄야 한다.

[2.2] translog는 아직 커밋에 포함하지 않은 쓰기 연산의 기록이다. 마지막 커밋을 읽고 그 뒤의 안전하게 저장된 연산을 다시 적용하면 최근 상태를 복구할 수 있다. 문서의 최종 본문만 보관하는 것과 달리 삭제와 같은 상태 변화도 기록해야 한다.

[2.3] fsync는 기록을 장애 뒤에도 남는 경계 안으로 옮기는 것으로 모델링한다. request 내구성은 쓰기 성공을 알리기 전에 이 경계를 전진시킨다. async 내구성은 성공 응답과 저장 경계를 분리하므로 성공한 연산도 잃을 수 있다. 나중의 request 쓰기나 수동 동기화는 앞서 쌓인 async 연산까지 함께 안전하게 만들 수 있다.

[2.4] flush는 현재 색인을 커밋하고 새 translog 세대를 시작하는 경계다. 마지막 커밋까지 들어간 내용은 복구할 때 연산을 다시 적용할 필요가 없다. 이 과제에서는 세그먼트 모양도 커밋에 포함하므로 병합 직후의 모양이 장애로 되돌아갈 수 있다.

[2.5] 배경은 Elastic의 [Translog settings](https://www.elastic.co/docs/reference/elasticsearch/index-settings/translog)를 따른다. 실제 Elasticsearch의 복제본 확인이나 파일 기반 복구까지 재현하지 않는다. 아래의 세대 번호, 명령 순서와 복구 직후 공개 상태는 이 과제가 정한 단순화다.

## 3. 입출력 규칙

[3.1] 앞 단계의 줄 처리, id·본문 형식, 숫자 표기와 한 명령당 한 줄 출력 규칙을 그대로 쓴다. 새 명령은 `DURABILITY <모드>`, `SYNC`, `FLUSH`, `CRASH`, `LOG`다. 모드는 소문자 `request` 또는 `async`다. 인자가 없는 명령에는 다른 토큰을 붙이지 않는다.

[3.2] 시작 모드는 request다. 시작 translog 세대는 1이며 현재 세대의 전체 기록과 동기화된 기록은 모두 0개다. 시작 커밋은 빈 최신 문서, 빈 세그먼트, 다음 세그먼트 번호 1을 담는다. 다른 초기 상태는 앞 단계와 같다.

[3.3] DURABILITY, SYNC, FLUSH와 CRASH의 성공 출력은 `OK`다. LOG는 `generation=<세대> total=<현재 세대 기록 수> synced=<현재 세대에서 동기화된 기록 수>`를 이 순서로 출력한다. LOG는 상태를 바꾸지 않는다. 이전 세대의 기록이나 커밋에 들어간 연산은 total과 synced에서 세지 않는다.

## 4. 명령 규칙

[4.1] 성공한 PUT과 DEL은 앞 단계의 최신 문서·버퍼 변경과 함께 현재 translog 끝에 연산 하나를 기록한다. 없는 id에 대한 DEL과 같은 본문으로의 PUT도 각각 한 기록이다. 오류 명령은 기록하지 않는다. 읽기·refresh·병합·시계 이동·내구성 설정·동기화·flush 자체는 쓰기 기록을 추가하지 않는다.

[4.2] 동기화는 현재 세대에 그때까지 쌓인 모든 기록을 영속 상태로 만든다. 그 결과 synced는 total과 같아진다. 동기화 뒤에 추가된 기록은 다음 동기화 전까지 synced에 포함하지 않는다. 기록 수는 줄지 않으며 중간 기록만 동기화하는 경우는 없다.

[4.3] request 모드에서 성공한 PUT과 DEL은 기록을 추가한 뒤 동기화까지 마치고 OK를 출력한다. async 모드에서는 기록을 추가한 뒤 동기화 없이 OK를 출력한다. `DURABILITY <모드>`는 이후 쓰기에 쓸 모드만 바꾼다. 같은 모드로 바꿔도 성공이며, 모드 변경 자체는 동기화하지 않는다.

[4.4] `SYNC`는 모드와 관계없이 동기화를 한 번 실행한다. 기록이 없어도 성공한다. 이 명령은 버퍼, 세그먼트와 검색 이력을 바꾸지 않는다.

[4.5] TICK은 앞 단계의 1,000밀리초 refresh 경계에 더해 이동 구간 안의 5,000밀리초 배수 시각마다 동기화를 실행한다. 주기적 동기화는 request와 async 양쪽 모드에서 모두 실행하며 검색 휴면 여부와 무관하다. 같은 시각에 두 경계가 있으면 동기화를 먼저 하고 그다음 앞 단계 조건에 따라 refresh한다. 명령 사이의 실제 경과 시간이나 DURABILITY·CRASH 실행 시각을 기준으로 주기를 다시 잡지 않는다.

[4.6] `FLUSH`는 휴면 여부와 관계없이 먼저 refresh를 한 번 실행한다. 이어서 현재 최신 문서 전체, 현재 세그먼트의 행·삭제 표시, 다음 세그먼트 번호를 새 영속 커밋으로 교체한다. 현재 translog를 폐기하고 세대 번호를 1 늘린 뒤 total과 synced를 0으로 만든다. 버퍼가 비어 있어도 커밋 교체와 세대 증가는 일어난다. FLUSH는 병합하지 않으며 가상 시각·검색 이력·내구성 모드는 바꾸지 않는다. 크기나 시간에 따른 자동 flush는 없다.

[4.7] `CRASH`는 장애와 재시작을 한 명령으로 수행한다. 먼저 현재 최신 문서, 버퍼, 모든 미커밋 세그먼트 변경을 버린다. 마지막 커밋에 저장한 최신 문서와 세그먼트, 다음 세그먼트 번호를 복원한다. 그런 다음 현재 translog의 동기화된 접두부만 기록 순서대로 최신 문서에 적용하면서 동일한 연산들을 빈 버퍼에 쌓는다. 동기화되지 않은 접미부는 영구히 버린다. 복구 과정에서 새 translog 기록을 추가하거나 refresh·병합을 실행하지 않는다.

[4.8] CRASH 뒤 translog 세대 번호는 그대로이며, 남은 total과 synced는 둘 다 장애 직전의 synced와 같다. 복구된 기록은 다음 FLUSH 전까지 translog에 남는다. 따라서 FLUSH 없이 다시 CRASH해도 마지막 커밋부터 같은 접두부를 다시 적용한다. 세그먼트 번호는 커밋의 다음 번호로 되돌아가므로 미커밋 상태에서 사용했던 번호를 복구 뒤 재사용할 수 있다.

[4.9] CRASH는 가상 시각과 내구성 모드를 유지하되 검색 이력을 없앤다. 복구 직후 GET은 커밋과 동기화된 기록을 모두 반영한 최신 상태를 본다. SEGMENTS와 STATE의 visible은 커밋의 공개 상태만 본다. 첫 SEARCH는 검색 이력이 없으므로 복구 버퍼를 refresh한 뒤 결과를 낸다. CRASH 자체는 그 검색을 대신 수행하지 않는다.

[4.10] REFRESH와 MERGE는 영속 커밋이나 translog의 동기화 경계를 바꾸지 않는다. 삭제가 동기화되지 않은 채 사라지면 장애 전 삭제되었던 문서가 되살아날 수 있다. 반대로 새 문서가 refresh로 검색에 보였더라도 커밋에도 동기화된 translog에도 없으면 사라진다. 장애가 없는 입력에서 앞 단계의 명령 결과는 그대로 유지된다.

## 5. 오류 규칙

[5.1] 모드가 request·async 이외의 값이거나 새 명령의 인자 개수가 맞지 않으면 `ERR INPUT`이다. 앞 단계의 오류 규칙도 계속 적용한다. 오류 명령은 내구성 모드, 동기화 경계, 커밋과 세대 번호를 포함한 모든 상태를 유지한다. 뒤 단계에 추가되는 명령 이름은 이 단계의 오류 검사 대상으로 쓰지 않는다.

## 6. 예시

[6.1] 다음 예시의 첫 문서는 flush로 커밋된다. async로 받은 삭제는 검색에는 반영되지만 동기화되지 않아 장애로 사라지고, 커밋의 문서가 되살아난다. 반면 장애 뒤의 새 문서는 SYNC만으로 복구되며, 복구 직후에는 버퍼에 남는다.

입력:

```text
PUT a old
FLUSH
DURABILITY async
DEL a
REFRESH
SEARCH *
LOG
CRASH
GET a
SEGMENTS
PUT b fresh
SYNC
CRASH
STATE
LOG
SEARCH *
SEGMENTS
```

출력:

```text
OK
OK
OK
OK
OK
NONE
generation=2 total=1 synced=0
OK
old
1:1:0
OK
OK
OK
time=0 buffer=1 visible=1
generation=2 total=1 synced=1
a b
1:1:0 2:1:0
```

[6.2] 다음 예시에서 모드 변경만으로는 이전 기록이 저장되지 않는다. 뒤의 request 쓰기가 앞선 async 쓰기까지 저장한다. 5,000밀리초의 주기적 동기화는 검색 이력이 없어도 작동한다. 그 뒤의 덮어쓰기는 장애로 사라진다.

입력:

```text

```

출력:

```text

generation=1 total=1 synced=0
OK
generation=1 total=2 synced=2
OK
OK
OK
OK

OK
first

```

## 7. 검사 방식

[7.1] 입력 방식, 출력 비교, JDK·라이브러리 범위와 30초 제한 시간은 앞 단계와 같다. 이 단계 참조 구현과 학습자 구현은 앞 단계 검사도 통과해야 한다. 앞 단계에 없던 LOG 등의 명령으로 새 동작을 관찰하며 기존 STATE와 SEGMENTS의 출력 형식은 늘리지 않는다.

[7.2] 테스트 하나당 최대 6,000개의 명령, 서로 다른 id 2,000개, SEARCH 출력 id 총 30,000개, 전체 가상 시각 10억 밀리초라는 상한을 유지한다. 별도 성능 강제용 대규모 테스트는 두지 않는다. 마지막 규모 확인은 상한 안에서 모드 변경, 부분 동기화, 삭제·재색인, 병합, 여러 차례의 flush와 crash를 섞는다. 물리 파일 용량이나 실제 디스크 지연은 검사하지 않는다.

# 01. refresh와 세그먼트

## 1. 개요

[1.1] 샤드 하나에 문서를 쓰고 검색하는 색인 경로 시뮬레이터를 구현한다. 쓰기 직후의 문서, 검색에 공개된 문서, 세그먼트에 남은 삭제된 행을 구분한다. 이 단계는 메모리 버퍼, refresh, 삭제 표시, 병합과 검색 휴면을 다룬다. 목표 풀이 시간은 Kotlin 백엔드 경력자 기준 2시간 안팎이다.

[1.2] 실제 Elasticsearch나 Lucene을 실행하지 않는다. 모든 상태는 프로세스 안에서 표현한다. 파일 형식, 역색인 압축, 검색 점수와 자동 병합은 구현 범위에 없다. 아래의 세그먼트 생성·병합·휴면 경계는 관찰 가능한 결과를 정하기 위한 이 과제의 규칙이다.

## 2. 배경 개념

[2.1] 색인 요청에 성공했다고 검색 결과가 즉시 바뀌는 것은 아니다. 쓰기 경로는 최신 문서 상태를 먼저 받아들이고, 검색 경로는 마지막으로 공개된 상태를 읽을 수 있다. 이 시간차를 두면 매번 검색용 상태를 다시 여는 비용을 쓰기 요청마다 부담하지 않아도 된다. 이 과제의 GET은 최신 상태, SEARCH는 공개 상태를 관찰한다.

[2.2] 메모리 버퍼는 아직 검색에 공개하지 않은 연산을 담는 영역이다. refresh는 버퍼의 내용을 검색에 반영하고 새 세그먼트를 여는 경계다. 세그먼트는 문서 행의 묶음이다. refresh는 검색 가능성을 바꾸는 작업이며, 장애 뒤에도 데이터가 남는다는 보장과는 별개다. 내구성은 다음 단계에서 다룬다.

[2.3] 같은 id를 다시 색인하면 기존 행을 제자리에서 고친다고 볼 수 없다. 기존 행에 삭제 표시를 하고 새 행을 추가하는 두 효과가 생긴다. 검색은 삭제 표시된 행을 제외하지만 그 행은 병합 전까지 세그먼트의 물리적인 행 수에 남는다. 같은 버퍼 안에서 여러 번 덮어쓴 문서도 이 구분을 따른다.

[2.4] 병합은 여러 세그먼트의 살아 있는 행을 새 세그먼트로 모으고 삭제된 행을 버리는 작업이다. 검색 결과가 같아도 세그먼트 수와 삭제 행 수는 달라질 수 있다. 버퍼를 공개하는 refresh와 이미 공개된 행을 정리하는 병합은 서로 다른 경계다.

[2.5] 검색이 오랫동안 없으면 주기적인 refresh를 생략할 수 있다. 쓰기를 받지 않는다는 뜻은 아니다. 휴면 뒤 처음 온 검색은 밀린 연산을 공개한다. 최근에도 검색이 있었다면 다음 주기까지 기존 공개 상태를 볼 수 있다. 이 과제에서는 실제 대기 대신 가상 시계를 움직여 두 경우를 구분한다.

[2.6] 배경은 Elastic의 [Near real-time search](https://www.elastic.co/docs/manage-data/data-store/near-real-time-search)를 따른다. 해당 문서는 refresh로 커밋 없이 검색 가능해지는 과정과 최근 검색이 있는 색인의 주기적 refresh를 설명한다. 이 과제의 명령 언어와 물리적 행 계산은 아래 문단이 정의한다.

## 3. 입출력 규칙

[3.1] 표준 입력을 EOF까지 한 줄씩 처리한다. 명령 개수나 초기 설정을 나타내는 머리 줄은 없다. 토큰 사이에는 ASCII 공백이나 탭이 하나 이상 올 수 있고 줄 앞뒤 공백은 무시한다. 빈 줄은 출력 없이 무시한다. 명령 이름은 대문자이며 대소문자를 구분한다.

[3.2] id는 정규식 `[a-z][a-z0-9_]{0,15}`에 맞는 문자열이다. 본문은 `[a-z]{1,20}`에 맞는 단어 1~8개다. 본문의 단어 순서와 중복은 보존하되, GET 출력에서는 단어 사이를 공백 하나로 잇는다. SEARCH의 검색어는 본문 단어 하나 또는 모든 문서에 일치하는 `*`다. 부분 문자열 검색이나 대소문자 변환은 하지 않는다.

[3.3] 비어 있지 않은 입력 줄마다 출력은 정확히 한 줄이다. PUT, DEL, REFRESH, MERGE, TICK의 성공 출력은 `OK`다. 관찰 명령 GET, SEARCH, SEGMENTS, STATE는 각 명령이 정한 형식으로 출력한다. 안내 문구나 로그를 표준 출력에 섞지 않는다.

[3.4] 시작할 때 최신 문서와 공개 문서, 버퍼와 세그먼트는 모두 비어 있다. 가상 시각은 0밀리초이며 검색 이력은 없다. 세그먼트 번호는 1부터 시작한다. 이전 실행의 상태를 읽거나 실제 시각을 참조하지 않는다.

## 4. 명령 규칙

[4.1] `PUT <id> <본문...>`은 최신 문서를 즉시 해당 본문으로 바꾸고 버퍼 끝에 PUT 연산 하나를 추가한다. 같은 본문을 다시 써도 별개의 연산이다. 공개 문서와 기존 세그먼트의 삭제 표시는 이때 바뀌지 않는다.

[4.2] `DEL <id>`는 최신 문서를 즉시 없애고 버퍼 끝에 DEL 연산 하나를 추가한다. 최신 문서에 없는 id를 지워도 성공이며 연산 하나가 쌓인다. DEL은 새 문서 행을 만들지 않는다.

[4.3] `GET <id>`는 최신 문서의 본문을 출력한다. 없으면 `MISSING`을 출력한다. 버퍼의 미공개 쓰기도 보지만 refresh를 실행하지 않고 검색 이력도 바꾸지 않는다.

[4.4] refresh가 일어나면 그 직전 버퍼의 모든 연산을 입력 순서대로 한 번씩 공개 상태에 반영한다. PUT은 같은 id의 현재 살아 있는 공개 행이 있으면 그 행에 삭제 표시를 하고 새 행 하나를 추가한다. DEL은 같은 id의 살아 있는 공개 행이 있으면 삭제 표시만 한다. 이때 새로 추가된 행도 뒤의 연산으로 삭제될 수 있다. 이미 삭제된 행은 다시 세지 않는다.

[4.5] 한 번의 refresh에서 버퍼에 PUT이 하나라도 있으면 그 PUT들이 만든 모든 행을 담은 세그먼트 하나를 새 번호로 생성한다. 행이 모두 삭제되었어도 해당 세그먼트를 생성한다. PUT이 없으면 세그먼트를 만들지 않는다. 어느 경우든 버퍼는 비워진다. 세그먼트 번호는 실제 생성할 때만 1 증가한다. 없어진 번호를 재사용하지 않는다.

[4.6] `REFRESH`는 휴면 여부와 관계없이 refresh를 한 번 실행한다. 버퍼가 비어 있으면 상태 변화 없이 성공한다. 수동 refresh는 가상 시각과 마지막 검색 시각을 바꾸지 않는다.

[4.7] `SEARCH <검색어>`는 살아 있는 공개 행 중 검색어가 본문의 단어 하나와 정확히 일치하는 문서의 id를 출력한다. `*`이면 모든 살아 있는 공개 문서가 대상이다. id는 중복 없이 ASCII 사전순으로 정렬하고 공백 하나로 잇는다. 일치하는 문서가 없으면 `NONE`을 출력한다.

[4.8] SEARCH를 실행하기 직전, 검색 이력이 없거나 현재 시각에서 마지막 검색 시각을 뺀 값이 30,000밀리초 이상이면 휴면 상태다. 휴면 상태의 SEARCH는 먼저 refresh를 한 번 수행한 뒤 검색한다. 휴면이 아니면 refresh하지 않는다. 어느 경우든 결과를 구한 뒤 마지막 검색 시각을 현재 시각으로 기록한다. 결과가 NONE이어도 검색 이력을 남긴다.

[4.9] `TICK <delta>`는 가상 시각을 delta밀리초 앞으로 옮긴다. delta는 0~60,000의 정수다. 이동 전 시각을 t, 이동 후 시각을 u라 할 때 t보다 크고 u 이하인 1,000의 배수 시각을 오름차순으로 처리한다. 각 시각 e에서 검색 이력이 있고 `e - 마지막 검색 시각 < 30000`이면 refresh를 한 번 수행한다. 그 밖에는 생략한다. 시각을 옮기는 명령은 TICK뿐이며 다른 명령은 시간이 걸리지 않는 것으로 취급한다.

[4.10] `MERGE`는 버퍼를 공개하거나 변경하지 않고 현재 세그먼트 전체를 병합 대상으로 삼는다. 세그먼트가 없거나 세그먼트가 정확히 하나이고 삭제 행이 없으면 아무것도 하지 않는다. 그 밖에는 모든 기존 세그먼트를 제거한다. 살아 있는 행이 남으면 그 행들만 가진 새 세그먼트 하나를 다음 번호로 만든다. 살아 있는 행이 없으면 새 세그먼트를 만들지 않는다. 자동 병합은 없다. 병합은 최신 문서, 공개 문서, 검색 이력과 시각을 바꾸지 않는다.

[4.11] `SEGMENTS`는 현재 세그먼트를 생성 번호의 오름차순으로 출력한다. 세그먼트 하나의 표현은 `<번호>:<살아 있는 행 수>:<삭제 행 수>`이며, 여러 개면 공백 하나로 잇는다. 하나도 없으면 `NONE`이다. 버퍼의 행이나 연산은 세지 않는다. 삭제 행만 남은 세그먼트도 출력한다.

[4.12] `STATE`는 `time=<현재 시각> buffer=<버퍼 연산 수> visible=<살아 있는 공개 문서 수>`를 출력한다. 항목 순서와 공백은 이 형식과 같다. 버퍼 연산 수는 아직 공개되지 않은 PUT과 DEL의 합이며, 최신 문서 수나 추가될 행 수가 아니다. GET, SEGMENTS와 STATE는 상태를 바꾸지 않는다.

## 5. 오류 규칙

[5.1] 정의되지 않은 명령, 인자 개수 오류, id·본문·검색어 형식 오류, delta의 정수 형식이나 범위 오류는 모두 `ERR INPUT`이다. 숫자 토큰은 정규식 `0|[1-9][0-9]*`에 맞는 십진 숫자열이며 부호·소수점·선행 0을 허용하지 않는다. 오류 줄 전체를 무시하고 다음 줄을 계속 처리한다.

[5.2] 오류가 난 명령은 어떤 상태도 바꾸지 않는다. 특히 검색 이력을 남기거나 부분적인 쓰기를 버퍼에 추가하지 않는다. 뒤 단계에서 추가하는 명령 이름은 이 단계의 오류 검사 대상으로 쓰지 않는다.

## 6. 예시

[6.1] 다음 예시는 같은 버퍼의 두 PUT이 모두 행으로 남는 경우와, 아직 공개되지 않은 삭제를 병합이 처리하지 않는 경우를 보여 준다. 첫 SEARCH는 검색 이력만 만든다. 두 번째 SEARCH는 활성 상태이므로 쓰기를 공개하지 않는다.

입력:

```text
SEARCH *
PUT note blue
PUT note red red
SEARCH red
GET note
REFRESH
SEGMENTS
DEL note
MERGE
SEGMENTS
SEARCH red
REFRESH
SEGMENTS
MERGE
SEGMENTS
STATE
```

출력:

```text
NONE
OK
OK
NONE
red red
OK
1:1:1
OK
OK
2:1:0
note
OK
2:0:1
OK
NONE
time=0 buffer=0 visible=0
```

[6.2] 다음 예시에서 1,000밀리초의 refresh는 검색 이력이 없어 생략된다. 31,000밀리초는 마지막 검색으로부터 정확히 30,000밀리초가 지난 경계다. 그 시각에 들어온 새 쓰기는 주기적 refresh 없이 남아 있다가 휴면 검색이 공개한다.

입력:

```text
PUT b green
TICK 1000
STATE
SEARCH green
TICK 30000
PUT a green
TICK 0
STATE
SEARCH green
SEGMENTS
```

출력:

```text
OK
OK
time=1000 buffer=1 visible=0
b
OK
OK
OK
time=31000 buffer=1 visible=1
a b
1:1:0 2:1:0
```

## 7. 검사 방식

[7.1] JDK 21과 Kotlin 표준 라이브러리만 사용한다. 최상위 main 함수 하나로 실행하며 표준 입력과 출력으로 검사한다. 테스트마다 새 프로세스에서 빈 상태로 시작한다. 공개 API의 이름이나 내부 자료구조는 지정하지 않는다.

[7.2] 빌드 시간을 제외하고 테스트 하나의 실행 제한 시간은 30초다. 종료 코드는 0이어야 한다. 각 출력 줄 끝의 공백·탭·CR과 출력 끝의 빈 줄을 제거한 뒤, 줄 수와 나머지 문자를 정확히 비교한다. 앞쪽 공백이나 항목 순서의 차이는 오답이다.

[7.3] 입력은 테스트 하나당 최대 6,000개의 비어 있지 않은 명령이며 서로 다른 id는 최대 2,000개다. SEARCH가 출력하는 id의 총개수는 최대 30,000개다. SEGMENTS가 출력하는 세그먼트 표현의 총개수도 최대 30,000개다. 오류로 주는 줄도 길이 256바이트 이하이고 전체 가상 시각은 10억 밀리초를 넘지 않는다. 이 크기를 넘는 성능 강제용 대규모 테스트는 두지 않는다. 마지막 규모 확인은 이 상한 안에서 덮어쓰기·삭제·refresh·병합·휴면을 반복한다.

[7.4] 앞 단계가 없는 첫 단계다. 뒤 단계의 구현도 이 단계에서 정의한 명령의 출력과 오류 시 무변경 규칙을 유지해야 한다. 시작 코드의 TODO를 대체하고 필요한 Kotlin 소스 파일을 추가해 완성한다.

# 비교 비용과 놓친 중복쌍 측정

[1] 시작 코드를 관찰한 뒤 후보 생성 규칙을 구현해라. 먼저 `CandidateSearch.kt`에서 비교 대상으로 남는 쌍을 예측하고 실험을 실행해라. `recall`, `missed_pairs`, `comparisons`, `comparison_budget`, `p95_ms`를 함께 기록한 뒤 후보 생성만 고쳐라. 비교 횟수가 작다는 이유만으로 결과가 보존된다고 판단하지 마라.

[2] JDK 21과 Kotlin 표준 라이브러리만 사용해라. `./build.sh`는 `build/app.jar`를 만들며 `PORT=18080 ./run.sh`는 `127.0.0.1:18080`에서 HTTP 서비스를 시작한다. 실행할 때마다 사용 가능한 루프백 포트를 지정해라. `GET /health`는 상태 200과 UTF-8 본문 `ready\n`을 반환한다. 빌드와 실행 스크립트는 공통 템플릿이며 실행 가능해야 한다.

[3] 공개 계산 API는 `POST /pairs`다. 요청과 응답은 UTF-8 평문이다. 요청 첫 줄은 `n p q`이고 뒤에 정확히 n개의 레코드 줄을 둔다. 레코드 줄은 `id category timestamp tokens`이며 필드 사이는 ASCII 공백 하나다. tokens는 쉼표로 이은 정수 목록이고 빈 집합은 `-`다. 요청 끝에는 줄바꿈을 허용한다. JSON과 자연어 토큰 정규화는 사용하지 않는다.

[4] n은 0 이상 500 이하, id는 요청 안에서 고유한 양의 Int, category는 `[a-z][a-z0-9-]{0,31}`, timestamp는 Long 범위 정수다. 토큰은 0 이상 Int 최댓값 이하의 서로 다른 정수이며 오름차순으로 최대 32개를 준다. 임계값은 `1 <= p <= q <= 1000000`인 분수다. 곱셈은 Long으로 계산해라. timestamp와 입력 순서는 직접 중복 여부에 영향을 주지 않는다. 요청 사이에 데이터나 계측값을 누적하지 마라. 유효하지 않은 계산 요청은 상태 400을 반환한다. 실험은 유효한 요청만 보낸다.

[5] 범주가 다르면 중복이 아니다. 같은 범주의 토큰 집합 A와 B는 Jaccard 값 `|A∩B| / |A∪B|`가 p/q 이상이면 직접 중복이다. 경계와 같은 값도 포함한다. 빈 집합 둘의 유사도는 1, 빈 집합과 비어 있지 않은 집합의 유사도는 0으로 정한다. 빈 집합 규칙을 제외한 판정은 `|A∩B| * q >= |A∪B| * p`다. 부동소수점으로 임계값을 비교하지 마라.

[6] 같은 범주와 같은 토큰 집합을 가진 레코드를 정확 일치 그룹으로 묶는다. 시각이 달라도 같은 그룹이다. 그룹 내부는 모든 원래 id의 쌍을 반환한다. 서로 다른 그룹이 직접 중복이면 두 그룹의 원래 id를 데카르트 곱으로 펼친다. 출력은 대표 id나 연결 요소가 아니라 직접 중복쌍 전체다. A-B와 B-C가 중복이어도 A-C를 자동으로 추가하지 마라.

[7] 정상 응답은 상태 200이다. 첫 줄은 `COMPARISONS c`이고 뒤에는 직접 중복쌍을 `작은id 큰id`로 한 줄씩 쓴다. 두 id는 반드시 요청에 존재하고 서로 달라야 한다. 작은 id 오름차순, 같으면 큰 id 오름차순으로 정렬하며 중복된 쌍은 허용하지 않는다. 쌍이 없으면 첫 줄만 반환한다. 마지막 줄바꿈은 허용하며 다른 본문은 추가하지 마라.

[8] c는 해당 요청에서 `Similarity.matches`를 실제 호출한 횟수다. 한 후보 그룹쌍을 판정할 때마다 성공 여부와 무관하게 1을 센다. 같은 쌍을 다시 판정하면 다시 센다. 정확 일치 그룹 내부의 쌍 확장은 판정 호출이 아니므로 0이다. 파싱, 정확 키의 해시·동등성 검사, 집합 크기 필터, 원래 id로 펼치기와 정렬도 c에 포함하지 않는다. 이 작업들의 실행 비용은 이 실험의 직접 판정 비용과 별개다. 다른 곳에서 교집합을 직접 계산해 계측을 우회하지 마라. 서로 다른 그룹의 유사도 판정은 제공된 `Similarity.matches`를 거쳐야 한다.

[9] 한 요청의 비교 예산 B는 정확 일치 그룹의 서로 다른 무순서 쌍 가운데 범주가 같고 `min(sizeA,sizeB) * q >= max(sizeA,sizeB) * p`를 만족하는 쌍의 개수다. 요청마다 `0 <= c <= B`여야 한다. 이 크기 조건은 가능한 최대 유사도의 상한이다. 서로 다른 길이 구간, 무작위 분할, 최근 N건 제한이 같은 상한을 보장한다고 가정하지 마라. 같은 범주의 모든 항목이 비슷한 크기이면 비교를 크게 줄일 수 없다. 그런 자료에 임의로 작은 예산을 강요하지 않는다.

[10] 수정할 파일은 `src/main/kotlin/CandidateSearch.kt` 하나다. 함수 `candidatePairs(groups, threshold)`의 서명을 유지하고 필요한 보조 함수는 같은 파일에 둬라. 반환하는 `GroupPair`는 그룹 목록의 인덱스이며 `0 <= left < right < groups.size`를 만족해야 한다. 그룹 목록은 요청에서 각 정확 키가 처음 등장한 순서다. 제공된 `Model.kt`, `Engine.kt`, `Similarity.kt`, `Main.kt`와 프로젝트 설정·실행 스크립트는 고치지 마라. 후보 생성 함수 안에서 I/O나 유사도 직접 계산을 하지 마라. 정확 그룹화·쌍 확장·HTTP 응답·계측은 제공된 코드가 담당한다.

[11] 관찰 예시로 임계값 1/2, 같은 범주의 세 집합 `{1,2}`, `{1,2,3}`, `{2,3}`에 id 1, 2, 3을 차례로 붙여라. 크기로 제외할 그룹쌍은 없으므로 B는 3이다. 직접 중복쌍은 `1 2`, `2 3` 두 개다. 연결 요소는 하나지만 직접 중복쌍은 두 개이며 `1 3`은 반환하면 안 된다. 제공된 판정 함수로 세 후보를 모두 검사하면 c는 3이다.

```text
3 1 2
1 a 10 1,2
2 a 20 1,2,3
3 a 30 2,3
```

```text
COMPARISONS 3
1 2
2 3
```

[12] 실험 자료는 합성 자료이며 각 실험은 주 자료 요청 6개와 공통 확인 요청 6개, 총 12개를 보낸다. 주 자료의 레코드 목록만 `kotlin.random.Random(20261105 + i)`로 섞으며 i는 0부터 5까지다. id와 시각·토큰은 보존한다. 서버 준비 확인 뒤 100ms 후 첫 요청을 보내고 이후 100ms 간격의 예정 시각에 비동기로 보낸다. 앞 요청의 응답을 기다린 뒤 다음 요청을 보내는 방식은 쓰지 않는다. 각 요청의 본문은 독립된 한 묶음이다.

[13] `collection-a`의 주 자료는 73건이다. alpha 범주에는 `{1,2,3,10+g}`를 가진 그룹 g=0..5를 각각 10건씩 두고, `{200..215}`를 가진 1건을 둔다. separate 범주에는 `{100+k}`를 가진 1건씩 k=0..11을 둔다. 레코드는 이 설명 순서로 생성하고 id는 1부터 증가시키며 timestamp는 `id % 7`이다. 임계값은 3/5다. 정확 그룹은 19개이고 예산은 `6*5/2 + 12*11/2 = 81`이다. 큰 집합은 크기 조건으로 제외된다. 원래 레코드의 전수쌍은 2628개이며 기준 직접 중복쌍은 1770개다.

[14] `collection-b`의 주 자료는 모두 alpha 범주인 48건이다. `{1..8,100+k}`인 36건(k=0..35)을 먼저 만들고 `{500+k}`인 12건(k=0..11)을 뒤에 만든다. id·timestamp 부여 규칙은 [13]과 같다. 임계값은 4/5다. 예산은 `36*35/2 + 12*11/2 = 696`이다. 크기가 9와 1인 그룹 사이만 제외된다. 원래 전수쌍은 1128개이며 기준 직접 중복쌍은 630개다.

[15] `collection-c`의 주 자료는 36건이다. 범주 c0..c11에 `{1..5}`를 가진 1건씩 먼저 만들고, 같은 범주 순서로 `{1..6}`을 가진 1건씩, 이어 `{1..15}`를 가진 1건씩 만든다. id·timestamp 부여 규칙은 [13]과 같다. 임계값은 4/5다. 각 범주에서 크기 5와 6의 쌍만 크기 조건을 통과하므로 B는 12다. 원래 전수쌍은 630개이며 기준 직접 중복쌍은 12개다.

[16] 공통 확인 요청 6개의 레코드 수는 차례로 0, 1, 4, 4, 3, 6이다. 첫째는 빈 자료(p/q=1/1), 둘째는 a 범주의 빈 집합 하나(1/1)다. 셋째는 a 범주 빈 집합 둘, a 범주 `{1}` 하나, b 범주 빈 집합 하나(1/2)다. 넷째는 a 범주의 `{10}`, `{20}`, `{30}`, `{40}`(1/2)다. 다섯째는 [11]의 자료(1/2)다. 여섯째는 순서대로 a의 `{1,2}`, a의 `{1,2,3}`, a의 `{8,9}`, b의 `{1,2}`, a의 빈 집합, a의 `{2147483647}`이며 임계값은 666666/999999다. 각 요청에서 id는 1부터 붙이고 timestamp는 id다. 이 여섯 요청의 예산은 차례로 0, 0, 0, 6, 3, 3이며 기준 직접 중복쌍 수는 0, 0, 1, 0, 2, 1이다.

[17] 실험기는 각 요청의 원래 레코드를 전수 비교하여 독립 기준 정답 집합을 만든다. 모든 요청에서 기준 정답 집합과 응답 쌍 집합이 같아야 한다. 직접 중복쌍 재현율은 찾아낸 기준 쌍 수를 기준 정답 쌍 수로 나눈 값이며 분모가 양수이면 1이어야 한다. 오탐은 응답에만 있는 쌍으로 요청마다 0이어야 한다. 기준 정답 쌍이 0개이면 재현율을 1로 채우지 말고 분모 0으로 취급하며 응답 쌍도 0개인지 별도로 판정한다. 한 요청의 누락을 다른 요청의 결과로 메울 수 없다.

[18] 지표는 12개 요청을 합산하여 출력한다. `completed_requests`는 정상 형식의 HTTP 200 응답 수이며 12여야 한다. `recall`은 합산 재현율, `recall_denominator`는 합산 기준 쌍 수, `missed_pairs`는 누락 수, `false_positives`는 오탐 수다. 합산 분모가 0이면 recall의 숫자 자리는 0으로 출력하고 분모 0을 근거로 미정의라고 읽어라. `zero_reference_requests`는 분모 0인 요청 수이며 각 시나리오에서 3이다. 주 자료 6회와 공통 확인을 합친 분모는 a=10624, b=3784, c=76이고 비교 예산 합계는 a=498, b=4188, c=84다.

[19] `comparisons`는 실제 c의 합, `comparison_budget`는 B의 합이다. 합계가 예산 이하인 것만으로 합격하지 않으며 요청마다 상한을 확인한다. 응답에 포함된 서로 다른 정확 그룹 사이의 연결 하나에는 적어도 한 번의 판정 호출이 필요하다. 실험기는 그 연결 수보다 작은 c도 계측 계약 위반으로 센다. `violations`는 형식·완료·계측·지연 기준 위반의 수이며 0이어야 한다. 누락과 오탐은 각각의 지표로 따로 센다. 비교 횟수 하나만 보고 정합성을 추정하지 마라.

[20] `p95_ms`는 HTTP 전송 직전부터 본문 수신 완료까지 잰 12개 응답 시간의 오름차순 `ceil(0.95*12)`번째 값이다. 이 자료에서는 최댓값과 같다. 5000ms 이하여야 하며 요청별 HTTP 제한은 8초, 준비 대기는 20초, 시나리오 전체 제한은 90초다. 이 제한은 멈춤·심한 지연을 검출하는 용도다. 기기별 처리량 배수나 시작 코드 대비 속도 배수는 합격 기준으로 쓰지 않는다. 모든 요청은 정상 완료해야 한다.

[21] 수정 전후에 같은 시나리오를 각각 세 번 반복하고 매번 정합성·비교 예산·완료 불변식을 확인해라. 수정 전에는 후보로 남은 그룹쌍과 기준 직접 중복쌍을 따로 적고 관측값이 예측과 같은지 확인해라. 관찰을 마친 뒤 제외해도 되는 쌍의 근거를 세우고 후보 규칙을 구현해라. 참조 구현과 비교용 변형의 반복 검증은 제작자가 수행한다. 학습자는 자신의 작업 공간만 수정하고 hidden/을 열거나 비교용 변형을 만들 필요가 없다. 빌드 실패나 시간 초과, 지표 누락은 의도한 학습 실패로 세지 마라.

[21.1] 합산 지표만으로 실패 요청을 특정할 수 없으면 [13]~[16]의 공개 자료로 요청 본문을 만들어 `POST /pairs`에 하나씩 다시 보내라. 먼저 [11]과 공통 확인 요청을 검사한 뒤 주 자료의 여섯 입력 순서를 재현해라. 각 요청에 구분 이름을 붙이고 상태 코드·본문·소요 시간을 기록해라. 정상 완료와 상태 200을 먼저 확인하고, [7]의 첫 줄·id·정렬·중복 형식을 확인해라. 이어 정확 일치 그룹을 직접 정리하여 [9]의 B를 세고 해당 응답의 `COMPARISONS c`와 대조해라. 응답 쌍이 잇는 서로 다른 정확 그룹의 연결 수보다 c가 작지 않은지도 확인해라. 마지막으로 [5]~[6]으로 만든 정답 쌍과 응답을 비교하여 누락·오탐을 구분하고, 12개 응답의 시간으로 [20]의 지연 기준을 따로 확인해라. 단독 재현이 통과해도 예정된 부하에서만 생기는 실패가 있을 수 있으므로 같은 시나리오의 반복 실험으로 마무리해라.

[21.2] 예를 들어 자신의 작업 공간에서 `./build.sh`를 실행한 뒤 사용 가능한 포트로 `PORT=18080 ./run.sh`를 띄워라. 다른 터미널에서 [11]의 요청을 `request.txt`로 저장하고 `curl --max-time 8 -sS -D response.headers -o response.txt -w 'status=%{http_code} seconds=%{time_total}\n' -H 'Content-Type: text/plain; charset=utf-8' --data-binary @request.txt http://127.0.0.1:18080/pairs`로 보내라. 포트를 바꿨으면 URL도 맞춰라. curl 종료 코드가 0인지 확인하고 `response.headers`와 `response.txt`를 읽어라. 이 예시의 B는 3이며 [11]의 응답은 개선 후 기대 결과다. 진단이 끝나면 서버 터미널에서 Ctrl-C로 서비스를 종료해라.

[22] 개념 근거는 [Python Record Linkage Toolkit Indexing](https://recordlinkage.readthedocs.io/en/latest/ref-index.html)의 전수 후보, blocking, sorted neighbourhood 설명이다. 후보를 만드는 규칙과 최종 판정은 별개이며 자료의 모든 정답 쌍이 후보에 남는지는 따로 검증해야 한다. 이 실험의 Jaccard·빈 집합 규칙·무손실 합격 조건과 자료별 예산은 과제의 계약이다. 원문의 성능 수치를 합격 기준으로 옮기지 않는다.

[23] HTTP 구현 근거는 JDK 21 공식 API인 [HttpServer](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.httpserver/com/sun/net/httpserver/HttpServer.html)와 [HttpClient](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.html)다. HttpServer는 지정 주소·포트에 바인딩하고 경로별 처리기와 실행기를 붙일 수 있다. 실험기는 HttpClient의 비동기 전송으로 예정된 부하를 보내고 응답 본문까지 측정한다. 외부 브로커, Spark, 실제 운영 데이터는 사용하지 않는다.

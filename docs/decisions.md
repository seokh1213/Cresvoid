# 설계 결정

공개 코드와 콘텐츠에 적용되는 결정을 정리한다. 개인 작업 이력은 공개하지 않는다.

## D1. 서버 없이 로컬에서 처리한다

채점, 문서 보기, 진행 기록을 로컬 CLI로 처리한다. 별도 서비스 운영이 필요하지 않게 한다.

## D3. 콘텐츠 형식은 JSON과 마크다운이다

트랙·문항·테스트는 JSON, 지문·안내·스펙은 번호 문단이 있는 마크다운이다. 계약은 `content/FORMAT.md`다.

## D5. 고정 테스트 기대값은 스펙에서 독립적으로 유도한다

참조 풀이와 테스트는 다른 에이전트가 만든다. 고정 테스트 기대값은 참조 풀이를 보지 않고 스펙에서 계산한다. 생성 테스트만 참조 풀이의 출력을 기대값으로 쓴다.

## D6. 에이전트는 동시에 최대 두 개다

사용자가 순차 실행을 요청하면 하나씩 실행한다. 검증 역할의 독립성은 동시 실행 여부와 무관하게 유지한다.

## D7. 병렬 실행의 캐시로 재개하지 않는다

호출 순서에 묶인 캐시와 파일 상태가 어긋날 수 있다. 결과 기록을 확인하고 끝나지 않은 단계만 다시 실행한다.

## D8. 엔진과 생성기를 Kotlin으로 통일한다

엔진은 Kotlin/JVM 프로그램, 생성기·색인·검사는 `.main.kts`다. 매번 컴파일하지 않도록 엔진은 jar로 실행한다. 즉시 실행해야 하는 진입점은 셸로 둔다.

## D9. 참조 풀이는 독립 Kotlin 프로젝트다

참조 풀이는 학습자 작업 공간과 같은 모양이며 `cresvoid solution`으로 볼 수 있다. D20에 따라 통과 여부와 관계없이 요청할 수 있다.

## D10. 엔진은 표준 라이브러리와 JDK만 쓴다

작은 JSON 파서와 출력기를 엔진에 둔다. 필드 철자와 중복 키도 계약에 맞게 검사한다.

## D11. 구현·독해·코드 읽기·버그 수정을 지원한다

build, reading, code, fix를 별도 트랙 종류로 둔다. lab은 아직 지원하지 않는다. 종류를 더할 때는 형식·엔진·제작 스킬을 함께 정의한다.

## D14. 카드 하나를 파일 하나로 두고 색인을 생성한다

카드는 영역·도메인별 front matter가 있는 마크다운이다. `content/ideas/index.main.kts`가 계약을 검사하고 INDEX.md를 만든다.

## D15. 외부 자료는 주제와 사실 확인에 쓴다

공식 문서와 공개 연구·기술 글로 사실을 확인하고 문장은 새로 쓴다. 공개되지 않은 자료나 조직 고유 정보는 콘텐츠에 넣지 않는다.

## D16. 코루틴 활용은 공식 라이브러리로 먼저 익힌다

코루틴 활용 콘텐츠에는 kotlinx-coroutines-core와 가상 시간 검증용 test를 허용한다. 라이브러리를 익힌 뒤 내부 실행기를 직접 구현하는 순서다. 카드의 env는 `kotlinx-coroutines`다.

## D17. 단계 번호는 제작할 때 정한다

단일 단계 카드는 제작 전까지 slug를 쓰고 제작 시 INDEX.md의 다음 번호를 붙인다. 여러 단계의 순서를 정하는 build 카드는 처음부터 번호를 쓴다. 문서의 다른 절은 번호 대신 제목으로 가리킨다.

## D18. 엔진은 Gradle 프로젝트와 효과 경계 인터페이스로 나눈다

Gradle 9.6.0, Kotlin 2.4.20, JDK 21을 사용한다. Kotest 6.2.5로 시험한다. `jar`가 실행 의존성을 포함한 `cresvoid.jar`를 만든다.

저장은 `ProgressRepository`, 프로세스는 `ProcessRunner`, 출력은 `Console`, 터미널은 `Terminal`, 시각은 `Clock` 뒤에 둔다. `Main.kt`가 구현체를 조립한다. 트랙 규칙, 다음 할 일, 화면 표시, 검증 순서를 책임별로 나눈다.

## D19. 콘텐츠 공통 파일은 템플릿에서 복사한다

`content/templates/kotlin/`의 빌드·실행·Gradle·JDK 파일을 sync 스크립트로 복사한다. 빌드 중단으로 깨진 jar가 남지 않도록 임시 파일에서 컴파일한 뒤 옮긴다. 생성기는 단계마다 자기 완결로 둔다.

## D20. 콘텐츠·엔진·학습자 공간을 나누고 채점 자료를 숨긴다

`content/`, `engine/`, `practice/`, `docs/`로 나눈다. 테스트·문항 정답·생성기·참조 풀이는 단계의 `hidden/`에 둔다. `hidden/`은 학습 흐름에서 열지 않는 범위이며 저장소 접근을 막는 보안 경계는 아니다.

실패 시 테스트 이름, 실패 종류, 다시 읽을 근거, 재현 seed 명령, 참조 풀이 명령만 보여 준다. 숨은 입력·기대 출력·풀이 프로그램 출력은 보여 주거나 저장하지 않는다. 빌드 오류는 보여 준다. 학습자 코드와 진행 기록은 Git에 넣지 않는다.

## D21. kotlinx.coroutines는 버전을 고정한 jar로 배포한다

core-jvm과 test-jvm 1.11.0을 `content/templates/kotlin/lib/`에 두고 sync가 `lib/`를 가진 프로젝트에 복사한다. 빌드에는 표준 라이브러리 외 네트워크 의존성 조회가 필요하지 않다.

core SHA-256은 `d1d75aa01dffbb4d1c520e67e4c4e7f5f6174718e7cb4632412503f2f0e604fa`, test는 `d4f7ee71da708af4719dceb6d3200c8f9dc5146ea1a812cb628ed53c64196f96`이다. 학습자에게 실험 API를 요구하지 않고, 가상 시간 실행 틀에 꼭 필요한 OptIn만 제한한다.

## D22. 카드 번호는 종류·주제·학습 순서다

`<종류>-<주제>-<순서>`를 쓴다. 종류는 R, B, C, F, L이다. 순서는 10, 20, 30처럼 간격을 두고 같은 차례의 카드는 일의 자리로 구분한다. 색인 생성기가 꼴·종류·주제·중복·실제 단계를 검사한다.

## D23. 작업 규칙은 AGENTS.md와 docs/agents.md가 원본이다

스킬 원본은 `content/skills/`다. 도구별 연결 파일에는 규칙을 복제하지 않는다. Workflow 도구가 없을 때도 독립 출제·검증과 결과 schema를 유지한다.

## D24. 프로젝트 이름과 공개 범위를 Cresvoid로 정한다 (2026-10-13)

Cresvoid는 crescent와 void의 합성어다. CLI·패키지·스킬·빌드 산출물은 `cresvoid`를 쓴다. GitHub의 Cresvoid 저장소와 main 브랜치를 사용한다. 개인 도구 설정·작업 기록·학습자 공간·빌드 결과는 공개에서 제외한다.

## D25. 버그 수정 단계는 필요할 때 수정 파일을 제한한다 (2026-10-13)

출력만 맞추려고 관찰용 실행 틀이나 가짜 서비스를 바꾸면 실제 버그가 남을 수 있다. 단계의 `hidden/allowed-edits.txt`가 있으면 `cresvoid test`는 시작 코드와 풀이를 비교해 명시한 Kotlin 파일 밖의 수정을 거절한다. `cresvoid validate`는 참조 풀이에도 같은 제한을 확인한다. 이 목록은 실제 수정 위치를 숨기는 단계에는 두지 않는다.
